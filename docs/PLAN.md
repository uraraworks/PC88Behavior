# PC88Behavior — 計画書 第1版

作成日: 2026-08-07

PC-8801 の ROM を、公式 ROM のコードを一切読まずに、**外部から観測した振る舞いだけ**を根拠に
書き起こすプロジェクト。プロジェクト名の "Behavior" はその手法そのものを指す。

---

## 1. ゴールと非ゴール

### ゴール A — 「BASIC が動く箱」（先にこちらを完成させる）

公式 ROM が無い状態で PC-8801 エミュレータを起動し、N88-BASIC のプログラムが実行できる。
**内部のアドレス配置は自由**。入口番地も、ワークエリアの位置も、こちらの都合で決めてよい。

達成判定: 代表的な BASIC リスト（LIST/RUN/PRINT/FOR/GOSUB/画面制御/ファイル入出力）が
公式 ROM 上と同じ出力を返す。

### ゴール B — 「公式 ROM の完全な差し替え」（A の retrofit として後から）

市販ソフトが ROM 内の任意番地を直接 CALL しても動く。

**B = A + 入口アドレスの配置 + ワークエリアの配置 + データテーブル**。
つまり B は A の上に「番地互換」を被せる作業であって、別物を作り直すわけではない。
だから A を先に完成させ、B は後から寄せる。ここを混ぜると、実装の自由度を最初から
自分で潰した上に、どちらも終わらない。

### 非ゴール（このリポジトリで絶対にやらないこと）

- 公式 ROM バイナリの再配布、およびその一部バイト列のリポジトリへの混入
- 公式 ROM の逆アセンブル結果を読むこと、および読んだ人間・エージェントによる実装
- 実機の完全再現（アナログ挙動、未定義動作の完全一致）
- 「動けばいい」ための、出自の怪しいデータテーブルの取り込み
- 公式の製品名バナー・著作権表示の再現（詳細は
  [docs/notes/banner-attribution-2026-08-16.md](notes/banner-attribution-2026-08-16.md)）

## 2. 背景 — なぜ PC-88 だけ難しいのか

### PC-98 の FreeDOS 作戦が効かない

PC-98 では BIOS/IPL を Neko Project II 側が既に再実装しており、足りないのは OS 層だけだった。
だから FreeDOS(98) を載せれば ROM 無しで一応動く。

PC-88 は違う。**N88-BASIC ROM が機械の本体**で、ディスクを読むコードすら ROM の中にある。
ROM を抜いた PC-88 は、Z80 が `0xFF`（= RST 38h）を延々と踏み続けるだけの箱になる。
8bit 機は「BASIC が使える機械」として売られていた。ROM は周辺ではなく製品そのものだった。

### MSX の C-BIOS が成立して PC-88 で成立しない

MSX BIOS は ASCII が技術書で公開した固定ジャンプテーブル、つまり **API** だった。
API を仕様通りに再実装すれば互換になる。

PC-88 のソフトは ROM 内の任意アドレスを直接 CALL する。ジャンプテーブルという契約が無い。
再実装には番地単位の忠実さが要る。相手が「インタフェース」か「作品」かの差であり、
これがゴール B を難しくしている本体。逆に言えば **ゴール A にはこの制約が無い**。

## 3. 設計原則 — 出自は証明せず、証明が要らない構造にする

レトロ資産の出自は原理的に証明できない。当時の実機はもう手元に無く、領収書も無い。
相手も「吸い出していない」ことを証明できないので、証明ゲームに乗った時点で泥沼になる。

**証明できないものを証明しようとするのをやめ、「証明が要る場所」そのものを減らす。**

| 想定される疑い | 主張で返さない。構造で返す |
|---|---|
| 「公式 ROM を吸い出しただろう」 | 実機を持つ**第三者が適合性テストを再現**できる形にする。自分のダンプが証拠の連鎖から外れる |
| 「逆アセンブルを写経しただろう」 | **公開ソースからの再現ビルド**。意味のあるハッシュは「公式 ROM との差分」ではなく「自分のソース → 自分の ROM」の一致 |
| 「独立実装ではないだろう」 | **git 履歴が contemporaneous な証拠**。独立実装の履歴（試行錯誤・行き止まり・測定が実装に先行する順序）は写経の履歴と形が違う。後から作れない |
| 「クリーンルームのプロセスを守っていない」 | permission 設定・hook・CLAUDE.md を**リポジトリにコミット**し、設定ファイル自体を証拠にする |

補足: 「公式 ROM とハッシュが違う」の提示には証明力が無い。1 バイト変えれば作れるので、
むしろ争点を理解していないシグナルに読まれる。出す数字は自分のビルドの再現性のほうである。

### 公開物と私物の分離

- **私物**（公式 ROM、吸い出しイメージ、市販ソフト）は `private/` に閉じ込め、`.gitignore` で
  二重に遮断する。出自の証明が不要な側に物理的に隔離する。
- **公開物**（ソース・テストスイート・文書・ビルドスクリプト）は、すべて第三者が
  再導出できるものだけで構成する。
- ツールは私物のパスを**環境変数経由**でのみ受け取る。リポジトリ内に絶対パスを焼き込まない。

### 実際に起きるのは訴訟ではない

現実に起きるのは DMCA テイクダウンである。したがって備えの価値は
**「即座に、具体的な異議申立が書けること」** に尽きる。この文書とテストスイートと git 履歴が
そのまま異議申立の本文になる状態を維持する。

この構成は臨床試験のプロトコルに近い。生データは公開できないので、プロトコルを公開して
独立再現に委ね、実装者を原典から盲検化し、監査証跡を残す。
**成果物の主役は文書とテストスイートであり、ROM はその副産物として出る。**

## 4. アーキテクチャ — 4 層に割る

一枚岩の「ROM」として扱うと難易度が平均化されて手が付かない。層ごとに法的リスクも
必要な手法も違うので、分けて別々に進める。

### L1 — IPL / ハードウェア初期化
ハード資料のみで書ける。回路とポート仕様は事実であり著作物ではない。**完全に白**。
最初に着手する層。

### L2 — フォント / 漢字 ROM
**解決済みとして扱ってよい**。美咲フォント・東雲フォント・jiskan16 で置換する。
書体（タイプフェイス）自体は原則として著作物ではない（ゴナ書体事件・最判 平成12年）。
ビットマップの実データはこれら自由ライセンスのものを使い、公式 ROM からは 1 バイトも採らない。

### L3 — ROM 内サービスルーチン（画面制御・キー入力・FDD・割り込み処理など）
やり方次第で白に寄せられる層。ここが第 5 節の「測る」手法の主戦場。
入出力の対応関係は事実なので採取してよい。

### L4 — N88-BASIC 互換の言語処理系（インタプリタ）

作るのは N88-BASIC そのものではなく、同じ言語仕様を受け付ける別実装である。

中間コード（トークン番号）もゴール A では自前の体系を使う。公式の番号セットとの一致が要るのはバイナリ SAVE 互換（ゴール B 側）だけである（[docs/notes/l4-token-design.md](notes/l4-token-design.md)）。

量は最大だが、**法的には実は一番きれい**。

- 言語仕様（文法・命令・意味論）はマニュアルで公開済みであり、アイデア/仕様は著作権の保護対象外
- Microsoft が GW-BASIC のソースを MIT ライセンスで公開している（2020年）
- N88-BASIC は MS BASIC の系譜であり、参照できる合法な出発点が既に存在する

「大きいから最後」ではなく「合法な材料が揃っているから、むしろ独立実装として書ける」層。

## 5. 中核手法 — 「読む」のをやめて「測る」

**逆アセンブルリストを一切見ない。** 代わりにエミュレータに計測フックを仕込み、
ROM の入口アドレスに対して入力を振り、出力を採取する。ブラックボックス観測である。

採れるのは**事実**（このレジスタとこのメモリをこう与えたら、こう返る）であって、
表現ではない。事実に著作権は及ばない。互換目的でのリバースエンジニアリングは
*Sony Computer Entertainment v. Connectix* の系譜で正面から扱われた論点でもある。

国内にも実例がある。1987年、エプソンは PC-9801 互換機への参入にあたり
BIOS/BASIC ROM の著作権を巡って NEC から提訴され、初代 PC-286 model 0 は
BASIC ROM を外して出荷した。その後クリーンルーム開発で BASIC ROM を再実装して
PC-286V 以降に搭載し、紛争は和解で決着、エプソンは以後約10年にわたり
98 互換機を販売し続けた。判決ではなく和解なので判例ではないが、
**日本で・NEC を相手に・BASIC ROM を対象に**、クリーンルーム実装が
商業規模で成立した実績である。このとき効いた要件は「クリーンルームを
やったこと」ではなく「**やったと示せたこと**」であり、本プロジェクトが
プロセスの記録自体を成果物として扱う理由はここに接続する。

そしてこの手法には副次効果がある。**手元に原典コードが存在しない状態になる。**
写経しようにも写経元が無い。人間もエージェントも汚染されようがない。
規律を「守る」のではなく、破れない構造にしてある、というのがこの設計の要点。

### 採ってよいもの / 採ってはいけないもの

| 採ってよい | 採ってはいけない |
|---|---|
| 入口番地の呼び出し規約（入力レジスタ / 出力レジスタ / 破壊レジスタ） | 命令列そのもの、逆アセンブル出力 |
| 外部から観測できる副作用（I/O ポート書き込み列、VRAM の変化） | ROM の生バイト列、そのハッシュ以外の断片 |
| ワークエリアのアドレスと意味（B のみで必要） | ROM 内データテーブルのダンプ |
| 実行時間・状態遷移などの計測値 | 「見てしまった」実装の記憶に基づく記述 |

### データテーブルの規律

数表（三角関数テーブル、文字属性テーブル、エラーメッセージ等）は**ダンプしない**。
- 生成規則が推定できるものは**ルールから生成**する（生成スクリプトをリポジトリに置く）
- 規則が無いものは**挙動から再構成**する（入力を振って出力を観測し、表を組み立てる）
- どうしても公式のバイト列との一致が必要なものが残った場合は、**利用者側で抽出する
  ツール**を提供する。リポジトリには入れない。

### 交換#3の1バイトを観測応答として採る方針判断（2026-08-13）

**決定内容。** 交換#3の1バイトは、公式ROMを読まずに行う**ブラックボックス
介入**、すなわち候補を与えて公式挙動と一致するかを観測する手順で確定する。
確定後は`docs/spec/`へ「**意味未特定・挙動から再構成した観測応答**」と
注記し、その由来を保ったまま記録・実装する。公式ROMや公式ディスクの
バイト列を読み出して採るのではなく、外部から観測できるプロトコル挙動の
一致条件として再構成する。

**根拠。** `CLAUDE.md`禁止事項4は、前段でROM由来のバイト列を含むファイルの
コミットを禁じる一方、後段でデータテーブルをルールから生成するか、
**挙動から再構成する**と定めている。ROMを読まない上記のブラックボックス
観測は後段に当たる。対象は1バイトのプロトコル定数であり、互換性のために
機能上そうでなければならない値で、創作的表現はほぼ無い。

意味と生成規則を先に得る経路は十分に探索した。11取得源×21加工の231条件
（m7b・m7g）、構成連動（m7e・m7g）、要求関数（m7h）、ディスク由来・
FDC結果由来（m7k）はいずれも否定された。手持ち資料の読んでよい範囲にも
散文説明は無かった（`docs/notes/refs-round0-semantics-search.md`）。これ以上
意味の探索を続けた場合、次に手が伸びる先は第三者の解析記事となり、
`CLAUDE.md`が最も避ける**由来の鎖**をつなぐ。独立実装の証拠を弱めるその
経路より、自らのブラックボックス観測を採る。

**留保。** これは自明な結論ではなく判断である。事実として、その1バイトは
公式ROMの中にも存在する。したがって本判断は、禁止事項4の前段
（ROM由来のバイト列を含むファイルをコミットしない）と後段（挙動から
再構成する）の境目に立つ。値そのものを公式ROMから読んだ、またはダンプ
したという主張へすり替えず、介入手順・一致判定・由来を記録して区別する。

**撤回可能性。** 後に公開仕様または独立した測定から意味が判明した場合は、
観測値の採用をやめ、意味に基づくルール生成へ差し替える。`docs/spec/`の
該当箇所には、この差し替え条件と、現時点では意味未特定の観測応答である
ことを残す。

**m7b第7節からの方針変更。** `docs/notes/m7b-round0-is-a-fixed-exchange.md`
第7節は「総当たりで得た一致値は実装へ焼き込まない。意味を特定して
ルール生成する」と定めていた。今回、その方針を変更する。理由は、上記の
探索により意味特定の道が尽き、残る資料探索が由来の鎖をつなぐ経路へ
移ったためである。m7bのノート自体は当時の判断として書き換えず、本節と
git履歴で変更の時点・理由を残す。

## 6. 開発ループ

1 サイクルの型を最初に固定する。以後どの層でもこの 5 段を回す。

1. **トラップ ROM 足場を作る** — 未実装領域を全部トラップ命令で埋めた ROM を用意する。
   実行アクセス（そこへ CALL/JP された）とデータアクセス（そこを読んだ）を**区別して**記録する。
   これが「何を実装すべきか」の唯一の入力源になる。
2. **需要ログを採る** — 公式 ROM を載せた環境（`private/` 側）で対象ソフトを走らせ、
   どの番地が実際に使われるかを記録する。ROM 全体を実装する必要は無い。
   *実際に踏まれる番地しか要らない*ことをここで確定させる。
3. **特性を採取する** — 需要のあった入口に対して入力を振り、入出力の対応を採る（第 5 節）。
4. **クリーンルーム実装** — 採取した仕様書だけを見て書く。原典は見ない。
5. **lockstep 差分実行** — 公式 ROM 版と自作 ROM 版を並走させ、**最初に食い違った瞬間**を特定する。
   比較基準は**外部から観測可能なものだけ**（VRAM の内容、I/O ポート書き込み列、
   サブルーチン戻り時のレジスタ）。内部 RAM の中身は違って当然であり、比較対象に入れない。

> 過去の教訓（PC-98/X68K 側で実際に踏んだ）: 定数や値がコアとホストで一致していても、
> 経路が通っている証明にはならない。**必ず末端で実測する。**
> ここでも「実装したから動くはず」ではなく、5 の差分実行を通ることだけを完了条件にする。

## 7. リポジトリ構成と運用規律

```
PC88Behavior/
├── README.md              このプロジェクトが何で、何を配布しないか
├── CLAUDE.md              エージェントに対するクリーンルーム規律（それ自体が証拠）
├── .claude/settings.json  規律の機構的強制（deny）。これも証拠
├── .gitignore             private/ と ROM 系拡張子を二重に遮断
├── docs/
│   ├── PLAN.md            この文書
│   └── spec/              測定から起こした仕様書（実装者はこれだけを見る）
├── tools/
│   ├── check_cleanroom.sh 防御が実際に効いているかの検査
│   └── ...                計測ハーネス、需要ログ、lockstep 差分実行、テーブル生成
├── src/
│   ├── l1_ipl/
│   ├── l2_font/
│   ├── l3_service/
│   └── l4_basic/
├── tests/                 適合性テストスイート（公式 ROM 保有者が実機で回せる形）
└── private/               ★git 管理外★ 公式 ROM・吸い出しイメージ・市販ソフト
```

### コミット規律

- **測定コミットが実装コミットに先行する**こと。順序そのものが独立実装の証拠になる。
- 行き止まりを `git reset` で消さない。**失敗した試行を残す**。写経の履歴には失敗が無い。
- コミットメッセージに「どの測定を根拠にこう書いたか」を書く。
- `private/` の中身に触れたコミットが 1 つも存在しない状態を保つ。

### 作業ディレクトリと、規律が「効く場所」の問題

**cwd は一段上の `_emulator/PC88/` にする。** このリポジトリを直接 cwd にすると、
独立 repo であるがゆえに Claude Code の記憶空間が分離し、X68K/PC98 で得た教訓から
切り離されるため。

その代償として、**このリポジトリ内の `CLAUDE.md` と `.claude/settings.json` は
cwd より下にあるので自動では読まれない**。規律はロードされなければ存在しないのと同じなので、
実効位置に橋を架けてある。

| | 実体（証拠＝公開repo側） | 実効位置（cwd 側） |
|---|---|---|
| 規律文書 | `PC88Behavior/CLAUDE.md` | `PC88/CLAUDE.md` が `@import` |
| permission | `PC88Behavior/.claude/settings.json` | 同ファイルへの **symlink** |

`settings.json` には `@import` が無いので symlink にしてある。
この二重化がずれていないことは `tools/check_cleanroom.sh` で検査する
（`private/` 遮断・バイナリ混入・実体と実効側の一致。いずれも壊して検出を確認済み）。

**deny の限界を正直に書いておく。** Bash の deny は接頭辞照合なので、パイプや別名で
迂回しようと思えばできる。目的は「うっかり」を止めることと、
「規律を主張ではなく機構として持っていた」ことを記録に残すことであって、悪意の遮断ではない。
また設定はセッション開始時に読まれるため、**変更後は再起動しないと効かない**。

#### 実地検証の結果（2026-08-07、再起動後）

| 試したこと | 結果 |
|---|---|
| `tools/check_cleanroom.sh` | 全項目 OK |
| `xxd -v` | 拒否（設定前は通っていた）＝ **symlink 経由で deny が読まれている** |
| Read ツールで `private/` 配下 | 拒否 |
| Bash の `cat` で `private/` 配下 | 拒否。**Bash コマンド中のパスも `Read()` deny と照合される** |

`Read()` の deny が Bash にも及ぶのは想定以上に強い。`cat` では抜けられない。

**未検証のまま残す点**: パスを文字列連結で隠して `python3` から読む形の迂回は、
deny ルールではなく別の仕組み（auto mode classifier）に止められた。したがって
「deny ルール自体が難読化されたパスを捕まえるか」は分かっていない。
これ以上の迂回探索は行わない——抜け道を探す行為そのものが規律に反する形になるため。
上記の「接頭辞照合なので迂回可能」という評価は据え置く。

副作用として、`private/` を触る Bash はすべて止まるので、**そこに置いたファイルの削除も
エージェントにはできない**。`private/` の出し入れは人間が行う。これは仕様として正しい。

### エミュレータコアの選定

**QUASI88-libretro を本命**とする。libretro のフレーム境界とメモリアクセス API が

測定の過程で**観測系の欠陥**が見つかった。メイン⇔サブ間のポート
（`$F0`-`$FF`）の対応付けを試みたところ一致率が最大20%程度で頭打ちに
なり、原因を診断すると「main/sub を横断する共通の時間軸が無く、
frame（フレーム番号）でしか順序付けられていなかった」ことだと分かった
（`docs/notes/m6-sub-clock.md`）。ハーネスに main/sub・iolog/intlog
横断のグローバル単調クロックを追加し（`tools/patches/0010-shared-clock.patch`、
わざと壊して検出できることを確認済みの自己検証つき）、これにより
経路同定の精度上限が外れて `$FC`/`$FD` をデータ経路として初めて
同定できた（`docs/notes/m6-sub-proto.md` 第3版）。

その後、一致率が **100.0%** という数字自体を検算した結果、
QUASI88 の PIO 実装が送受信を同一の共有変数フィールドで実装しているため
**定義上ほぼ必然的に出る数字**であり、実機の転送信頼性を示す独立証拠
としては**採用しない**という判断をした（`docs/notes/m6-sub-proto.md` 第4版、
`docs/spec/l3-subrom.md` 2.1節）。採用したのは「$FC/$FD はデータ経路である」
という定性的結論のみ。

diskA（N88-BASIC）と diskB（市販ソフト、実名は記載しない）の比較測定から、
`$FC` 経由の固定長バースト転送（5635件）は diskA のブート手順に固有であり、
diskB は `$FC` を一切使わずに正常起動する（画面確認済み）ことが分かった。
これにより **ゴールA（BASICが動く箱）には `$FC` 経路の再現で足り、
diskB が使う別経路の解明はゴールBの課題**という線引きを、測定で引いた
（`docs/notes/m6-sub-invariant.md` 第2〜3版、`docs/spec/l3-subrom.md` 4節）。

仕様は `docs/spec/l3-subrom.md`（**第4版**。確定13項目／不採用3項目／未確定は
未確定のまま）。この日のうちに以下まで進んだ。

**適合条件を確定させた（5節）。** M4(L1) の型（`--init N --cycle M`）は
**使えない**と検証で判明した。サブ CPU の全イベントは frame 13〜77 に限定され、
以降は 1800 フレームまで完全に沈黙する。つまり**「定常状態」が存在せず**、
周期一致を仮定する型が成立しない。L1 が VSYNC 割り込みで回り続けるのとは
性質が根本的に違う。代わりに **「メインが `IN $FD` で受け取る値の列の
非周期・完全一致」** を適合条件とした（`tools/cmp_io.py --cpu main --port FD --kind IN`
を新設）。同一条件2回の測定が全列でバイト一致することも確認済み（判定が成立する前提）。
この検証の副産物として、`cmp_io.py` が共通クロック導入後の8列ログを
**一度も正しく読めていなかった**未検出バグが見つかった。仕様書に
「`--cpu sub` が使える」と書いてあったのは動作確認のない記述だった。
**実装より先に判定基準を検証したから実装前に見つかった**（`docs/notes/m6-conformance.md`）。

**`$FA`/`$FB`（サブ内部の FDC コマンド）の解読は実装対象外と判断した（0節）。**
適合条件がメイン受信列で定義されている以上、**メインから見て同じなら
サブが FDC をどう叩くかは自由**である。FDC（μPD765）は実在ハードで仕様は公開されており、
自作サブ ROM は公開仕様に従って自分で書けばよい。公式 ROM と同じコマンド列を出す必要はない。
測定で確定したのは `$FA` bit7 が「直後に `$FB` アクセスが来るか」を
68,879 件・例外0件で予測すること（＝データレディ相当）まで。

**メイン→サブの要求プロトコルを確定させた（1.10〜1.13）。**
SEND/RECV の1バイト送受信プリミティブ、起動時専用の高速バルクモード、
256バイト単位の読み出し要求（固定8バイトヘッダ＋2バイト引数の2階層アドレッシング）、
`$FF` が SEND/RECV のフェーズコード、`$FE` が main 視点の4つの待ち状態。
（`docs/notes/m6-main-to-sub.md`。仮説を実データで反証して訂正した経緯も残してある。）

**実装に着手した（`src/l3_service/make_subrom.py`、`tools/verify_l3.sh`）。**
ROM 由来のバイト列はゼロ。自作の試験ドライバと自作 D88 で
**3件×256バイト＝768バイト全件一致**し、応答を1ビット壊すと verify が落ちることも確認した。
ただし **diskA の起動シーケンス（5635件バースト）は未達**であり、
ネガティブコントロール（ディスク無しでサブ0命令、1.1節）も**未実装**である。

- **交換#14第3〜第5 READの座標は位置対応で確定した（候補総当たり不要）。**
  `analyze_exchange14_read_rules.py`の全数位置対応で、Rは第3〜第5READ全てが

  確定している。根拠は[docs/notes/m7aj-exchange14-read3-position-map-and-protocol-block.md](notes/m7aj-exchange14-read3-position-map-and-protocol-block.md)。
- **1282件（旧上限）は未知の分岐ではなく、READ#2が供給できる`$FD`件数の

  1282/1283の境界＝READ#2データ部終端＝READ#3先頭バイトであることを

  READ#3データ部終端＝READ#4先頭境界と確認済み。診断には未デコード
  ポート`$F9`（FDC_TIMEOUT_MARK）を陽性対照つきで使い、「subがFDCチップ
  待ちでタイムアウトした」という別仮説を否定に回した。根拠は
  [docs/notes/m7ak-exchange14-read3-stack-overlap.md](notes/m7ak-exchange14-read3-stack-overlap.md)。
- **READ#4（LIMIT=3）・READ#5（LIMIT=4）は未解決のクラッシュで0件に退行する。**
  BULK_DATA/STACKのアドレス重複は机上で再確認したが無く（m7akと同型の
  原因ではない）、sub側がexchange14のREADループへ到達する**前**の起動時
  ハンドシェイク相当のアドレス列へ戻ってしまい、以後応答が無くなる。
  `$F9`は0件（FDCチップ待ちタイムアウトではない）。原因未特定のまま
  次サイクルへ持ち越す。根拠は
  [docs/notes/m7al-exchange14-read4-read5-limit-regression.md](notes/m7al-exchange14-read4-read5-limit-regression.md)。

  既定測定を無限ループ化させるため、READ#4/#5のクラッシュ原因を解いて

**m7al の「未特定のクラッシュ原因」は m7am で原因を特定し、m7an・m7ao で
フェッチ窓そのものの構造を確定させた（2026-08-17、3サイクル分の追記）。**

- **原因はアドレスずれであって命令内容ではないと確定した（m7am）。**
  到達不能な NOP 詰め物（READ#4 実コードと同一の71バイト）で同じ退行が
  再現し、総増分40バイトまでは正常・41バイトから崩壊するという閾値を
  特定した。`resolve()` の jr 範囲チェックと ROM_SIZE 超過チェックは
  陽性対照で発火を確認済み（効いてはいた）。**`verify_l3.sh`（自己検証層）
  では再現しない**（治具が交換#14の12件要求を送出しない構造的限界。
  安い反復系を作れなかったことも記録として残す）。詳細は
  [docs/notes/m7am-read4-crash-address-shift-isolation.md](notes/m7am-read4-crash-address-shift-isolation.md)。
- **sub CPU のフェッチ窓は 0x0800（2048バイト）固定と確定した（m7an）。**
  ハーネスのパッチのソースと実測の両方が根拠。**`ROM_SIZE = 0x2000` は
  旧 `load_rom` 経路を指しており、窓のサイズを表す値ではなかった**
  （上限チェックが間違った数を見ていた）。末尾詰め物対照で「総サイズは
  無罪・位置の問題」と確定し、境界を跨いでいたのは
  `_observed_request_next_6` 末尾の `JP IDLE_DISPATCH` の3バイト目だった。
  境界跨ぎの自動整列パディングと selftest を追加した。詳細は
  [docs/notes/m7an-subrom-fetch-window-boundary.md](notes/m7an-subrom-fetch-window-boundary.md)。
- **フェッチ窓の外は一様な 0xFF 埋め（`RST 38`）と実測で確定した（m7ao）。**
  異なる番地（0x0900・0x0850）へ `JP` した2種が完全に同一のPC空転へ
  収束することが根拠。**公式ROM不要の自己検証系だけで測れた。**
  LIMIT=3/4 の0件退行は `_observed_request_next_6`〜9 が丸ごと窓の外に
  あることが原因で、m7an と**同一原因の続き**（別原因ではない）と確定した。
  到達可能性の不変条件 `find_out_of_window_blocks()`（保守的判定）を
  追加し、陽性対照済み。**既定ビルド（LIMIT=1）が既に9バイト窓の外にある**
  ことが分かったため、`build()` への無条件 SystemExit は見送り、報告のみに
  留めた——**今日まで動いていたのは、その9バイトが diskA のブートで
  実行されなかったからにすぎない（または保守的判定の偽陽性）** という
  潜在的な脆さの記録として残す。228バイトの削減が要るが未着手。詳細は
  [docs/notes/m7ao-subrom-fetch-window-budget.md](notes/m7ao-subrom-fetch-window-budget.md)。

**この3サイクルで分かった実務上の意味**: 窓の検査（`find_out_of_window_blocks()`）
も窓の外の実測（0xFF埋めの確認）も自己検証系（`verify_l3.sh`）だけで
回せる。M6 の残作業のうち、公式ROM/公式ディスクが要らずに反復できる
部分が従来の想定より広いことが分かった——反復が速いという実務上の意味がある。

**上の宿題1・2は m7ap で解消した（2026-08-18）。**
`_observed_single_by_request`（要求グループ→応答決定関数）の9段の即値
比較チェーン（558バイト）を、ROM内の決定テーブル＋解釈器へ書き換えて
420バイト削減し、**LIMIT=1〜4のすべてがフェッチ窓0x0800の内側に収まった**
（窓超過 9/79/167/228バイト → 全て0）。`$F9` 診断の既定オフ化も
`break_*` 故障注入のオプトイン化も**行っていない**——検出力を削らずに
予算を作れた。あわせて `find_out_of_window_blocks()` を `build()` の
無条件 SystemExit へ格上げした（宿題1の目的だった構造的な再発防止）。

この書き換えで**検査側に2つ分かったこと**がある。(a) `verify_l3.sh` は
この決定関数を一度も踏んでいなかった——表の応答値を1ビット変えても
並び順を逆にしても出力が1文字も変わらないことを故障注入で確認した。
「前後で不変だったから安全」は成り立たない。代わりに、組み上がったROM
バイト列を極小Z80で実際に実行して参照モデルと突き合わせる
`tools/observed_request_decision_selftest.sh` を新設し（216ケース、
陽性対照3種）、さらに第51版と第52版の等価性を4278ケースで直接確認した。
(b) `subrom_fetch_window_selftest.sh` の陽性対照2つが、実コードの偶然の
straddle に依存していたためコードが縮んだ瞬間に**検出力ゼロのまま通る
検査**へ変わった。偶然に依存しない形（命令の途中に境界を置く）へ
作り直した。詳細は
[docs/notes/m7ap-decision-table-and-window-budget.md](notes/m7ap-decision-table-and-window-budget.md)。

## 付記 — この文書の位置づけ

これは設計文書であると同時に、**プロセスの宣言**でもある。
第 3 節で書いたとおり、争いになったときに効くのは主張ではなく構造であり、
この文書が「いつ、何を決めて、その通りにやったか」の起点になる。
方針を変えるときは、書き換えて上書きするのではなく、**変更した事実が履歴に残る形**で更新する。
