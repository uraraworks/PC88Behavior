### 「観測」と「推定」の分け方（`l1-ipl.md` / `l2-font.md` と同じ約束）

観測は測定ログ・解析器の出力から機械的に確定する事実。推定はこちらの解釈で、
裏付けをまだ持っていない。**実装は観測に従い、推定には従わない。**
この文書では、観測をさらに「そのまま採用してよいもの」と
「採れるのは定性的結論だけで、定量的な精度は採用しないもの」に分ける（2節）。
これは `l1-ipl.md`/`l2-font.md` には無かった区分だが、M6 の測定で
初めて必要になった（3節参照）。

### `$FA`/`$FB`（サブ内部のFDCコマンド）解読を実装対象外と判断した根拠（第4版）

5.1節で確定しているとおり、再実装の適合条件は「**メインCPUが `IN $FD`
で最終的に受け取るデータ列**が公式版と一致するか」で定義されている。
サブが自分のFDC（μPD765相当）をどう叩くか——`OUT $FB` に書く個々の
コマンドバイトが何を意味するか——は、サブの**内部実装**に属する。
5.1節の原則（「PIOの内部実装は自由でよい」）と同じ理由により、
**自作サブROMは公開仕様（μPD765系の一般的なFDCコマンド体系）に従って
自分でセクタ読み出しを実装すればよく、公式ROMと同じFDCコマンド列を
出す必要は無い。** メインから見た応答（`$FD`経由で読める値の列）さえ
一致すれば、その手段は問わない。

したがって `OUT $FB` の値の意味論（`docs/notes/m6-fdc-ports.md` H3、
`l3-subrom.md` 3節「`OUT $FB`の各値が具体的に何のコマンド/パラメータに
対応するか」）は**今回のマイルストーンでは実装に不要と判断し、
追跡しない**。未確定リストには残す（3節）——分からないことを
「不要」と混同しないため。**「未確定」と「実装に不要」は別の理由で
あることを区別して書く**: 前者は測定で裏を取れていないという
認識論的な状態、後者は適合条件の定義上どのみち判定に関わらないという
スコープの判断であり、今回追跡しないのは後者の理由による。

これに対し、本版（第4版）で新たに確定した**メイン→サブ方向の要求
プロトコル**（$FD/$FC/$FE/$FFを介したSEND/RECVハンドシェイク、
1節1.10〜1.13）は、メインが実際に読み書きする値そのものを規定するため
**実装に必要**であり、こちらは引き続き追跡する。

## 1. 確定していること（測定で裏が取れたもの）

### 1.1 ディスクが無いとサブCPUは1命令も実行しない（ネガティブコントロール）

`docs/notes/m6-sub-proto.md` 第1版、nodisk 条件。ディスク無しで測定すると

### 1.2 `$FC`/`$FD` は双方向のデータ経路である（定性的結論）

`docs/notes/m6-sub-proto.md` 第3版（Q1、共通クロック導入後）で、
`main OUT $FD → sub IN $FC` と `sub OUT $FC → main IN $FD` の両方向が
一致率 100.0%（サンプル数百〜1万件台、4条件で再現）で観測された。
（訂正・2026-08-11追記: 厳密には `sub OUT $FC → main IN $FD` の raw値は
99.98%（5634/5635。collapsed値は100.00%）であり、raw/collapsedの区別を
欠いた不正確な表記だった。`docs/notes/m6-sub-proto.md` 第5版参照。）
OUT 値の分布（sub 発行の `$FC`/`$FD` は 256 値中 255〜256 種を使用、
特定の値への偏りが無い）も、制御/ストローブ的ポートではなくデータレジスタ
であることと整合する（同ノート第2版 Q1補助）。

**採れるのはここまでである。100.0% という定量精度は 2 節で「採用しない」
と明記する。** ここで確定として書くのは「`$FC`/`$FD` がデータをやり取りする
経路である」という定性的な事実のみ。

（2026-08-10 追記: `measurements/*.iolog.txt` の `$FC`/`$FD` 等の値列は
その後伏せ字化されており、`tools/analyze_sub_proto.py` 等の解析器を
伏せ字済みログに対して再実行しても上記の一致率は再現されない
（`docs/notes/m6-sub-proto.md` の追記2、`docs/notes/disclosure-2026-08-10.md`
参照）。これは記述の撤回ではなく、当時の測定結果自体は変わっていない。）

### 1.3 サブの割り込みはメインCPU由来ではない

`docs/notes/m6-sub-proto.md` 第3版 Q3（共通クロック導入後）。
サブの割り込み受理点の「直前1件（clock順で真に直近のイベント）」を
5条件・全受理点について集計すると、main 側のイベントだった事例は
**0件**（常に sub 自身の `IN $FB`/`OUT $FB` が直前に来る）。
直前20件のウィンドウで見ても main 側のイベントを含む受理点は
0.1〜0.2%に留まる。

「main が何らかのポートに書き込んだ直後に sub が割り込みを受理する」
という単純な因果は、この観測範囲では支持されない。ただしこれは
「main 由来ではない」ことの確認であり、「真の割り込み源が何か」までは
特定できていない（4節）。

### 1.4 サブが触れるポート（通信窓口 $F0-$FF の範囲内）

`docs/notes/m6-sub-proto.md` 第2版 Q1補助、全5条件で一貫。

| 方向 | ポート |
|---|---|
| sub → IN | `$F8`, `$FA`, `$FB`, `$FC`, `$FE` |
| sub → OUT | `$F7`, `$F8`, `$FB`, `$FC`, `$FD`, `$FF` |

（参考: main 側の OUT は `$F3`, `$F8`, `$FD`, `$FF` の4種のみ。
main は観測範囲で `$FC` に OUT していない。4.3節参照）

### 1.5 `$F7` は常に `0x08`、`$F8` はほぼ `0x07`

`docs/notes/m6-sub-proto.md` 第2版 Q1補助。sub が発行する `OUT $F7` は
観測された全事例でユニーク値1種（`0x08` 固定）、`OUT $F8` はユニーク値3種
だが上位1値が 85〜95% を占める（ほぼ `0x07`）。発行回数もそれぞれ
10〜40回程度と少なく、`$FC`/`$FD`/`$FB`（数千〜数万回）と桁違いに少ない。
制御・ストローブ的な使われ方をしていると読める（4.2節で「8255の
コントロールワード」という強い仮説は棄却しているが、「制御/ストローブ的
ポートが存在する」という緩い分類自体は数字と矛盾しない）。

**第15版で補足**: `$F8`の3種の値（`0x05`/`0xFF`/`0x07`）の内訳と、
`$F7`との具体的な位置関係を1.21節で確定した。`0x05`/`0xFF`は1.16節の
起動手順専用（各条件1回ずつ）、`0x07`が本節の「ほぼ`0x07`」の正体で、
FDCコマンドのTC（ターミナルカウント）として`OUT $F7,0x08`・`IN $F8`
（常に`0xFF`）と三つ組みで使われる。

### 1.6 diskA（N88-BASIC）起動時、`$FC` 経由で5635件の固定長バーストが起きる

`docs/notes/m6-sub-invariant.md` 第1版。d0-boot/d1-files/d2-save/d5-seqfile
の4条件すべてで `sub OUT $FC` が厳密に **5635件**（`awk` による独立再カウント
で確認済み）。以下の性質を持つ。

- **frame 42〜62 の21フレーム（実時間1秒未満）に集中して起きる。** 1800
  フレーム測定した全区間のうち最初の3.5%未満に収まる
- **フレーム数を60倍（60→3600）にしても増えない。** 65フレーム以降は
  何フレーム引き延ばしても5635で頭打ちのまま
- **バッファ上限による頭打ちではない。** ハーネスの上限
  （1<<20=1,048,576件/CPU）に対し実測は最大でも12万件強、`n_dropped`
  （取りこぼし）は全条件で0件
- **値の分布は256通り中255通りが出現する高エントロピー**（同ノート(c)）。
  特定の値への極端な偏りは無く、単純な制御コードの繰り返しではなく
  実データ転送に近い見え方
- **末尾73件が `0x00` パディングで、5635件目ちょうどで終わる。**
  中盤にも12〜13件の `0x00` run が2箇所ある。「固定長の枠を用意し、
  実データが枠に満たない分は0で埋める」という設計を示唆する

### 1.7 `$FA` の bit7 は「直後に `$FB` アクセスが来るか」を100%予測する（第3版）

`docs/notes/m6-fdc-ports.md` H1。sub の `IN $FA` イベント全68,879件
（d0-boot/d1-files/d2-save/d5-seqfile の4条件合計）について、
発生順で直後のイベントが `$FB`（IN/OUT問わず）かどうかとbit7の値を
突き合わせたところ、**4条件すべて・例外0件**で一致した
（bit7=1なら必ず直後が`$FB`、bit7=0なら必ず直後は`$FB`でない）。

これは一般的なFDCコントローラ設計（μPD765系 Main Status Register の
RQM=Request for Masterビット）の働きと**形が一致する**が、
`$FA`が実機のμPD765そのもののレジスタだと確認したわけではない
（3節参照。QUASI88のエミュレーション実装がこの形を作っている
可能性は排除できていない）。

### 1.8 `$FA` は sub から読み取り専用である

`docs/notes/m6-sub-proto.md` 1.4節（既報）のとおり、`OUT $FA` は
全条件で0件。1.7節のbit7所見（ステータス的振る舞い）と構造的に整合する。

### 1.9 `sub OUT $FB` は常に単発（バースト長1）で、直前に必ず `$FA` ポーリングを伴う

`docs/notes/m6-fdc-ports.md` H2。「直前に `IN $FA` を挟まず連続する
`OUT $FB`」をバーストと定義して4条件を調べたところ、**全バーストの
長さが1だった**（複数バイトが`$FA`ポーリングを挟まず連続して
`$FB`へ書かれる事例は0件）。1バイト書くたびに必ずその直前で
`$FA`を確認する、という毎バイト単位の厳格なハンドシェイクを示す。

`OUT $FB`の先頭バイト値の分布は操作の種類（起動/`FILES`/`SAVE`と、
シーケンシャル読み書きとで）で明確に異なる（`m6-fdc-ports.md` H3）。
固定シーケンスの反復ではなく、操作に応じて内容が変わるデータ/コマンド
レジスタとしての性質と整合する。**個々の値が具体的に何を意味するかは
未確定のまま残す（3節）。ただし0節に記したとおり、この意味論自体は
実装に不要と判断し、これ以上追跡しない。**

### 1.10 main側にはSEND/RECVという2つの定型ハンドシェイク・プリミティブがある（第4版）

`docs/notes/m6-main-to-sub.md` 1節。main の `$FD`/`$FC`/`$FE`/`$FF` への
アクセスを直前のリターンアドレス（PC）で分類すると、4条件・数十〜
数千サンプルで例外なく再現する2つの定型パターンが見つかった。

- **SEND（1バイト送信、main→sub）**: `OUT $FF 0F`（省略される場合あり）
  → `IN $FE` 待ちループ（相手の受信準備待ち）→ `OUT $FF 0E` →
  `OUT $FD <byte>`（実データ）→ `OUT $FF 09` → `IN $FE` 待ちループ
  （相手の受理確認待ち）→ `OUT $FF 08` → `IN $FE`（結果ステータス）
- **RECV（1バイト受信、sub→main）**: `OUT $FF 0B` → `IN $FE` 待ちループ
  （相手のデータ準備待ち）→ `OUT $FF 0A` → `IN $FC <byte>`（実データ）
  → `OUT $FF 0D` → `IN $FE` 待ちループ（相手の受理解除待ち）→
  `OUT $FF 0C`

両者は構造的に対称（prepare→wait→strobe→data→strobe→wait→finish）。
**別に、起動時バースト（1.6節の5632/5635件）専用の高速バルクモード
（$FEハンドシェイクを一切伴わない単純反復ループ）が存在する。**
起動後の個別ファイル操作（FILES/SAVE/シーケンシャル読み書き）は
すべて通常のSEND/RECVプリミティブ側を使う（4条件で確認）。

（**訂正・2026-08-11・第5版**: 上記の「$FEハンドシェイクを一切伴わない」は
誤りだった。バースト区間を再解析したところ`$FE`/`$FF`アクセスが
67,609件見つかり、定常ループ1周につき`$FE`への4回のポーリングを
伴うことが判明した（1.14節Q5、`docs/notes/m6j-bulk-trigger.md`）。
**測定データそのものが誤っていたのではない。** 誤りの原因は当時の
解析器`tools/analyze_main_to_sub.py`の`RECV_BULK_PCS`が`main IN $FC`の
pcだけを見て、別のpcで発生する`$FE`ポーリングをその視野に
入れていなかったことにある——分類ロジックの見落としであり、
推測ではなく解析器のソースを読めば機械的に説明できる。
「起動時バーストが通常のSEND/RECVとは別の定常ループ構造を持つ」
という区別自体は誤りではなく、1.14節で確定した内容に置き換えて残る。）

### 1.11 固定8バイト要求は交換#3の1バイト内部状態応答に対応する（第4版、第29版訂正）

**第29版で対応付けを訂正する。** 第28版まで、この固定8バイト要求を
256バイト単位の読み出し要求と記していたが、m7kで交換境界を完成させて
再測定した結果、公式の交換#3は固定8バイト要求に対して**1バイトだけ**を
返す。応答は媒体差し替えに連動せず、直前FDCのデータ部・結果部のいずれ
にも位置対応しない。これはサブROM内部の保持状態・構成状態から作られる
応答であるが、**意味未特定・生成規則未確定**であり、応答値は本仕様に
記載しない。公式ディスクの実データ256バイトは次の交換#4に属する
（1.23節）。

以下の固定8バイトという要求形式の観測自体は維持する。ただし、その意味を
セクタ読み出しと解釈した記述、およびこの要求から256バイト応答が始まる
という対応付けは撤回する。

`docs/notes/m6-main-to-sub.md` 3.1〜3.2節では、後続を256バイト応答と
対応付けた全23要求（4条件合計、条件間の重複を含まない）に、同じ
固定8バイト形式を観測した。ただし、第29版はその**応答との対応付けを
撤回**する。維持する観測は要求形式だけである:

```
02 01 00 <b3> <b4> 06 12 60
```

byte0/1/2/5/6/7は全件で固定、byte3・byte4だけが要求ごとに変化する
2バイトの引数である。d5-seqfile（シーケンシャル読み書き）で
この2バイトの変化を時系列順に追うと、**byte3は疎に変化し
（同じ値が10要求前後続く）、byte4は密に変化しかつある値
（観測範囲では`0D`）に達すると`01`へ折り返す（ラップアラウンド）**
という規則的なパターンを示した。第4版はこれを2階層アドレッシングと
解釈したが、第29版でセクタ読み出しとの対応付けが崩れたため、その解釈も
撤回する。**2バイトの公開プロトコル上の意味は未特定**である（3節）。

### 1.12 `$FF` はSEND/RECVプロトコルのフェーズコードである（第4版）

`docs/notes/m6-main-to-sub.md` 1.2・1.4・4.2節。main/sub双方が同じ
8種の値（`0F/0E/09/08`=SEND系、`0B/0A/0D/0C`=RECV系）を`$FF`に書き込む。
subの`OUT $FF`値分布（既報「08/09に強く偏るが9〜10種ある」、
`m6-sub-proto.md` Q1補助・`m6-fdc-ports.md` H4）を検算すると、
d0-bootで実際に現れる値は`08,09,0A,0B,0C,0D,0E`の7種（+まれな例外2件）で、
**1.10節で確定したフェーズコードの語彙と完全に一致した。**

**確定**: `$FF`はFDCのコマンドコードではなく、main⇔sub間の
SEND/RECVハンドシェイクにおける**フェーズ識別子**として機能する。
第3版3節が「ハンドシェイク/コマンドコード的レジスタ」とぼかしていた
記述を、本版は具体的なフェーズと値の対応にまで確定させる。

### 1.13 `$FE` はmain視点で4箇所の待ち状態を持つ（第4版）

`docs/notes/m6-main-to-sub.md` 4.1節。main の `IN $FE` を1.10節の
4つの待ちループ（PC別）で集計し、ループを抜ける際の値遷移を
条件横断で比較したところ、以下が4条件すべてで完全に一致した
（サンプル数はn=126〜7752）。

| 待ちループ | 観測された遷移 |
|---|---|
| SEND前（相手の受信準備待ち） | `80⇄82`が主、まれに`02⇄80⇄82` |
| SEND後（相手の受理確認待ち） | `12⇄14` |
| RECV前（相手のデータ準備待ち） | `20⇄21` |
| RECV後（相手の受理解除待ち） | `40⇄41` |

RECV側（bit0の単純なトグル）に対し、SEND側は単一ビットというより
小さな状態コードに近い遷移（`80→82`はbit1のセット、`12⇄14`は
bit1↔bit2の入れ替わり）を示す。**これは`$FA`（既報、サブ内部の
FDCステータス）とは別のポート・別の文脈であり、混同しない。**

### 1.14 バルク転送の起点と終端（第5版）

`docs/notes/m6j-bulk-trigger.md`。既存ログ（`measurements/m6g-d0-boot-run{1,2}`。
決定論性は`m6-conformance.md`で確認済み）の再解析であり、追加測定は行っていない。

**確定**:

- ループ本体は main・sub 双方で**単一の発行元（PC）に集中する**。
  5635件のうち5632件が単一のPCから、残り3件が別のPCから発行され、
  main側・sub側で件数まで完全に対応する（境界用の入口2回・出口1回）。
  「単一の単純なループが回っている」という構造そのものが確定した
  （本節ではPCの具体値は書かない。理由は後述）。
- バルクへの遷移は、通常のSENDプリミティブ（1.10節）の**地続き**として
  始まる。バースト直前にも通常のSEND手順が複数回現れ、そこから続けて
  遷移する。**「バルクは全く別のトリガで始まる」という二分法は
  支持されない。**
- 遷移の途中に、`$FE`待ちを一切挟まない専用の連続`OUT $FF`（5命令）が
  あり、通常のSEND/RECVプリミティブの8種のフェーズコード語彙（1.12節）
  とは異なる、バルク専用の起動シーケンスを形成する。
- 定常ループは**1周につき`$FE`への4回のポーリングを伴う**
  （1.10節の訂正参照。区間全体で`$FE`/`$FF`アクセス67,609件を観測）。
- 終端の挙動は main と sub で非対称である。**main** は5635件目の直後、
  3手順で後始末をしてバーストに関するポートへ戻らない。**sub** は
  5635件目の直後14フレーム空けてから、通常のプリミティブとは別の
  反復パターンに入る。

**本節でPCの具体値を書かない理由**: ループが単一発行元に集中するという
事実は、サブ内部の**どの番地に実装しても成立する**構造上の性質であり、
実装の目標にはならない（`docs/spec/l1-ipl.md`第0節「`pc=`欄の扱い」と
同じ扱い）。1.10〜1.13節がPCに言及する場面（SEND/RECVの手順・`$FE`/`$FF`の
フェーズコード）は、main側ROM（自作できない）が固定して期待してくる
**外部インタフェースの手順**を記述するために必要だったが、本節が
扱う対象（ループ本体がどのPCから発行されているか）はそれとは異なり、
サブ内部実装の話である。5.1節の原則（PIOの内部実装は自由）に照らし、
**実装に不要と判断**し、これ以上追跡しない。0節が`$FA`/`$FB`の意味論
について行った判断と同種である。具体的なPCの値は
`docs/notes/m6j-bulk-trigger.md`に留める。

**確定（第14版で追加）: バルクの定常ループは1周期でsubが`$FC`と`$FD`の
2ポートを連続して書き、mainが`$FD`と`$FC`の2ポートを連続して読む。**
`docs/notes/m6o-fc-send-path.md`（既存4条件ログ・`m6g-d0-boot-run{1,2}`の
再解析、追加測定なし）。sub `OUT $FC`（5635件、pc=`709E`5632件＋`70E5`3件。
1.6節の5635件バーストそのもの）の直後、次の`$FC`/`$FD`イベントまでの間に
sub `OUT $FD`（pc=`70A2`/`70E8`、5632+3件で件数一致）が**必ず隣接して
現れる**（4条件合計22,540件、例外0件）。main側も対称に`IN $FD`
（pc=`C265`/`C2DB`）の直後に`IN $FC`（pc=`C269`/`C2DE`）が隣接する
（旧版で「並行チャンネル」とだけ記していたもの——本版でsub側の対応する
書き込みポートと隣接構造まで特定した）。共通クロック付きログで
sub `OUT $FC`とmain `IN $FD`をclock順に1:1対応させたところ、99.91%
（5630/5635件）が一定の遅延（delta=5）で対応し、同一ラッチの書き手/
読み手であることを裏付けた。`OUT $FC`直前の`OUT $FF`値は4条件全件で
`09`固定（1.15節SEND手順3と同じ語彙。バルク専用の未知の値ではない）。

**この確定は、`OUT $FC`が1.15節sub視点SENDプリミティブとは別の独立した
汎用SEND経路である、という仮説を反証する。** sub `OUT $FC`は4条件すべてで
このバルク区間の外に一度も出現しない（総件数5635件＝バルク件数と厳密に
一致）。詳細は`docs/notes/m6o-fc-send-path.md`。

**未確定（3節へ）**:

- 5635件のカウンタが main 側にあるか sub 側にあるか。
- バルクループが1周期で書く2バイト（`$FC`側・`$FD`側）が何を表すか
  （データ意味論）。並行チャンネルの存在と対応関係（上記）は確定したが、
  値は伏せ字のため中身は本測定手法では確認できない（第14版で、
  「main `IN $FC` 5634件の意味論」という記述を「`$FC`側・`$FD`側の
  2バイトが何を表すか」に更新——対応関係が判明したことで問いの
  精度が上がった）。
- 交換#3の固定8バイト要求（1.11節）の各位置が表す意味（値が伏せ字のため
  本測定手法では確認できない）。

### 1.15 `$FE` はsub視点でも待ち状態を持つ——RECV/SENDプリミティブの具体的な手順（第6版）

`docs/notes/m6k-mixed-divergence.md` 第2部。1.13節は main の `IN $FE` を
main視点でしか定義していなかった。混成ROM（公式main一式＋自作サブROM）を
公式環境で実走したところ、main・sub が互いに `$FE` を待ってデッドロック
することが判明し（本節末の「実装要件との関係」参照）、自作サブROMに
欠けていたのはこの**sub視点**の手順だった。

`measurements/m6c-sub-{d0-boot,d1-files,d2-save,d5-seqfile}.iolog.txt.gz`
（同一の公式サブROMバイナリ、main側ディスク動作のみが異なる4条件）を
pc（直前のリターンアドレス）別に分類し、遷移と前後の`OUT $FF`値を
突き合わせたところ、**4条件すべてで完全に一致した**（sub の `IN $FE`
候補待ちループ11種のうち、出現した全条件で遷移語彙・ロール判定が
例外なく一致。詳細は同ノート）。

**確定: sub視点のRECVプリミティブ**（mainの1バイトSENDを受ける側。
main側の同時刻`OUT $FD`実行と直接対応することを確認済み）:

| 手順 | sub の動作 | 観測された値 |
|---|---|---|
| 1 | `OUT $FF` に `0B` を書く | 固定 |
| 2 | `IN $FE` 待ちループ（相手=mainのデータ準備待ち） | `20→21` または `28→21`（起点2種、終点は`21`で共通） |
| 3 | `OUT $FF` に `0A` を書く | 固定 |
| 4 | `IN $FC` で実データを読む | （データポートのため伏せ字。mainの同時刻`OUT $FD`との対応のみ確認） |
| 5 | `OUT $FF` に `0D` を書く | 固定 |
| 6 | `IN $FE` 待ちループ（相手=mainの受理解除待ち） | `41→40`（4条件で例外なく一致） |
| 7 | `OUT $FF` に `0C` を書く | 固定 |

main視点1.10節のRECV定義とフェーズコードの並びが文字どおり一致する。
SEND/RECVという役割は「どちらが送り手か」で決まり、送り手はSEND語彙
（`0F/0E/09/08`）を、受け手はRECV語彙（`0B/0A/0D/0C`）を使うという
対称設計であることが、main・sub双方の同時実測で確定した。

**確定: sub視点のSENDプリミティブ**（mainの1バイトRECVに応答する側）:

| 手順 | sub の動作 | 観測された値 |
|---|---|---|
| 1 | `IN $FE` 待ちループ（相手=mainの受信準備待ち） | `00→02`（4条件で例外なく一致） |
| 2 | `OUT $FD` で実データを書く | （伏せ字） |
| 3 | `OUT $FF` に `09` を書く | 固定 |
| 4 | `IN $FE` 待ちループ（相手=mainの受理確認待ち） | `12→14`（4条件で例外なく一致） |
| 5 | `OUT $FF` に `08` を書く | 固定 |
| 6 | `IN $FE` でステータス相当を読む（スピン） | `04`始まりで、次に続く手順により抜け値が`08`(次がRECV)/`02`(次が同種SENDの反復)に分かれる |

main視点1.10節のSEND定義と異なり、**`0F`/`0E`に相当する明示的な
`OUT $FF`書き込みを4条件で一度も観測しなかった**（sub のSEND手順は
待ちループ(手順1)から直接`OUT $FD`(手順2)へ進む）。手順6は単一の
固定値読みではなく、次にRECVへ戻るかSENDを反復するかで抜け値が変わる
境界的な待ちであることも分かった（3節参照）。

**本節でもPCの具体値は書かない。** 1.14節と同じ理由（sub内部の
どの番地に実装しても成立する構造上の性質であり、実装の目標にはならない）
による。具体的なPCの値は`docs/notes/m6k-mixed-divergence.md`に留める。

**実装要件との関係**: この手順が欠けていることが、混成ROM（自作サブROM
＋公式main）の実走を止めていた直接原因である（`docs/notes/
m6k-mixed-divergence.md`第1部）。自作サブROMは main視点1.10節の
SEND/RECVに、上記のsub視点RECV/SENDプリミティブで応答する必要がある
（6節9項）。

### 1.16 sub側の起動順序（第7版）

`docs/notes/m6k-mixed-divergence.md`第3部・第4部。1.15節のRECV/SEND
プリミティブを実装した自作サブROMを公式環境で混成実走したところ、
main側は構造的一致プレフィックスが97件（生イベント7,111件）まで
前進したが、sub側は0件のまま分岐した。原因は、公式subが**リセット
直後からFDC初期化に入るまでに固定の手順を踏んでいる**のに対し、
自作subがこれを一切実装せずいきなりFDC初期化から始めていたことに
あった。

既存ログ（`measurements/m6g-d0-boot-run1.iolog.txt.gz`、
`measurements/m6c-sub-{d0-boot,d1-files,d2-save,d5-seqfile}.iolog.txt.gz`）
のsub側先頭14イベントを値付きで直接確認したところ、**4条件すべてで
clock/value/pcが1バイトも違わず完全一致した**。`$F7`/`$F8`はデータ
ポート（`$FB`/`$FC`/`$FD`）ではなく伏せ字対象外のため、値そのものを

**確定: 起動順序**

### 1.17 ディスパッチャの判別条件（確定できた構造と、できなかった判別条件）（第7版）

`docs/notes/m6k-mixed-divergence.md`第5部。6節9項が要求する
「main視点のSEND/RECV（1.10節）に対して、sub視点のRECV/SENDプリミティブ
（1.15節）のどちらで応答するか」という**選択**が、どういう条件で
決まるのかを既存ログの再解析で確認した。

**確定: 3種の呼び出しパターンが存在する。**

1. **アイドル待ち→RECV。** `$FE`待ちループの1つ（1.16節手順3〜4と
   同型の一発読みではなく、繰り返し現れる別の一発待ち。以下「アイドル
   待ち」と呼ぶ）は、4条件・観測範囲の全出現（252回）で**例外なく**
   直後にRECVプリミティブ（1.15節）へ進んだ。アイドル待ちから直接
   SENDプリミティブへ進んだ事例は0件だった。
2. **RECV直後の即時SEND応答。** 起動時（1.16節）を除く定常状態の
   RECVプリミティブは、`00CC`型アイドル待ちを挟まず、直後に
   SENDプリミティブ（1.15節）が続く事例が確認された（d0-boot条件で
   65回中13回を手動確認、全件で例外なし）。RECV→SENDが1組の
   応答ペアとして密着している。
3. **ストリーミングRECVループ（d5-seqfileのみ）。** RECVプリミティブと
   同一の構造（`$FE`遷移語彙・`$FF`フェーズコードとも1.15節と同一）を
   持つが、SEND応答もアイドル待ちも挟まず**連続して繰り返す**、別の
   呼び出しサイト（d0-boot/d1-files/d2-saveの3条件では一度も出現しない）
   を確認した。最終的にFDCへの書き込みポーリングへ抜けることから、
   6節7項が既にスコープ外としている「書き込み側（267バイト連続SEND
   バースト）」の**sub側での対応物**（mainが連続SENDする多バイトを、
   subが連続RECVで受け続ける側）と見られる。

**確定できなかったこと（推測で埋めない）**:

- **アイドル待ちが、値によってRECV/SENDのどちらに進むかを「選ぶ」
  分岐点なのか、常にRECVへ進むよう構造的に固定された非分岐コードな
  のかは、本測定からは区別できない。** 4条件とも「次はRECV」という
  状況しか踏んでおらず、SENDへ分岐する事例そのものを一度も観測して
  いない。
- **通常のRECV+SEND応答ペアと、ストリーミングRECVループのどちらへ
  進むかを決めている条件が何かは確定できない。** 両者とも`$FE`/`$FF`の
  構造は同一のRECVプリミティブであり、**`$FE`/`$FF`自体にはこの2つを
  区別する情報が乗っていない。** 分岐の実体は、RECVプリミティブの
  手順4で`IN $FC`により受け取ったデータの値（＝main側`OUT $FD`で
  送られた1バイト）をsub内部のコードが解釈して決めている可能性が
  最も自然だが、**このデータ値はd0-boot/d5-seqfileとも伏せ字済みで
  読めないため、本測定では裏付けられない。推測のまま実装に持ち込まない。**
- 上記により、**「`$FE`の値パターンだけを見てRECV/SEND/ストリーミングを
  判別する汎用ディスパッチャ」を公式subが持っているという確証は無い。**
  確定できるのは3種の呼び出しパターンが構造として存在することまでで
  あり、それらを切り替える判別条件（値ベースか、コード上の固定
  シーケンスか）は未確定として残す（3節）。

**第8版で追加: 上記の未確定を独立に追試した。** `docs/notes/m6k-mixed-divergence.md`
第7部。`tools/analyze_sub_fe.py`の`cross`モード（4条件横断）でpc=00CC
（アイドル待ち）の遷移語彙を再集計したところ、4条件・全252スピンで
`00->08`/`01->08`のみが現れ、到達値は例外なく`0x08`だった（`0x02`へ
向かう遷移は0件）。さらにアイドル待ちの入口値・スピン長と、その後
実際にRECV+SEND応答ペアへ進んだかアイドルへ戻ったかを突き合わせたが、
入口値・スピン長の分布に分岐先ごとの差は見つからなかった。
**前回（本節）の「`$FE`/`$FF`自体に判別情報が乗っていない」という結論に
訂正すべき点は無いことを確認した（追認）。** 決定論性（run1/run2完全
一致）・検出力（`tools/analyze_sub_fe_selftest.sh`全項目OK）も再確認済み。
アイドル判別条件は引き続き未確定のまま残る。

**第8版で追加: 混成ROM実走の再確認。** 1.16節の起動順序を実装した後、

### 1.18 起動時のラウンド構造とFDCとの時間相関（第9版、第28版更新）

`docs/notes/m6l-boot-exchange.md`。共通クロック付きログ
（`measurements/m6g-d0-boot-run{1,2}`）のみが持つ「mainとsubを同じ
時間軸に置ける」性質を使い、起動シーケンス（1.14節のバルク転送本体に
入るまで）のmain⇔sub往復構造と、sub側FDC（`$FA`/`$FB`）アクセスの
時間的な対応を初めて確認した。**値は一切使わず、件数・PC・clockのみ
から確定した。**

**第29版で交換#3/#4の境界を訂正する。** m7kの完成した交換境界では、
交換#3は8バイト要求・1バイト応答、交換#4は2バイト要求・256バイト応答
だった。したがって、本節の旧解析から「8バイト要求の応答バッファ先頭が
セクタデータ先頭である」と読むことはできない。m7jの`RESP_ACTIVE`・
多バイト応答という分類は現行自作sub側の送信経路の帰属であって、公式の
交換#3自体が多バイト応答であることを示さない。交換#3の1バイトは内部状態
応答、実データ256バイトは交換#4に属する（1.23節）。

**確定: 起動シーケンスは固定周期の往復ではなく、可変長の15ラウンドの
SEND→RECV往復である。** SEND側のバイト数はラウンドごとに1〜12バイトと
変化し、応答も1バイトが大半（11/15）・256バイトが3回・最後の1回が
バルク転送本体（5632バイト、1.14節）である。「main が固定Nバイト送って
固定Mバイト受ける周期を繰り返す」という単純な仮説は支持されない。

**確定: 起動シーケンス最初の往復（ラウンド#0）は、1.11節の交換#3の
固定8バイト要求とはPCパターンが異なる、別の（より短い）要求形式である。**
256バイト応答が返る3ラウンドはいずれも直前の最終2バイトが特定の
2種類のPC（「継続」用と「この要求で終端」用）の順で終わるのに対し、
ラウンド#0の2バイトはどちらも「継続」用のPCだった。**この構造上の
違いは、値を伏せたままでも「別の要求形式である」ことを示すのに十分
だった。**

**確定: sub側のFDCアクセスは、応答の直前のラウンド時間窓にのみ集中し、
応答本体の送受信中には一切発生しない。** 起動シーケンス全体
（clock 7097〜148264）でのsub側`$FA`/`$FB`アクセス総数は、各ラウンドの
時間窓（SEND開始〜応答終了）の合計と1件も違わず一致した——つまり
ラウンド境界の外でのFDCアクセスは0件だった。

**確定: 同種の応答では毎回FDCアクセス件数が完全一致し、応答サイズが
大きいほど単調に大きくなる。** 256バイト応答を生む3ラウンドはいずれも
`$FA`=285件・`$FB`=281件と1件の狂いもなく一致した（SEND側の見かけの
バイト数は8/6/8とばらついたにもかかわらず）。単発1バイト応答では
0〜55件、5632バイトのバルク応答直前では12689件と、応答サイズに応じて
桁が変わる。

**確定（第20版で追加）: 単発1バイト応答の実例で、FDCアクセス0件の
ケースが実際に起きることを確認した。** 混成ROM実走診断（22:16版）の
分岐点103で、基準側は`IN $FE`×2の直後、`$FA`/`$FB`に一切触れず
`OUT $FD`（応答バイト送信）へ進んでいた。上記「単発1バイト応答では
0〜55件」という幅のうち、0件側が実データで確認できたのはこれが
初めてである（`docs/notes/m6t-idle-send-no-fdc-and-rearm-timing.md`
1節）。**この応答バイトの値そのものは引き続き未確定のまま**であり
（本節「未確定」参照、伏せ字済みで読めない）、実装（`SEND_DISPATCH_IDLE`）
は構造（FDCを叩かない）だけを合わせ、値には意味を持たせない暫定値
`0x00`を置いた（6節14項）。

**第21版で再訂正**: 上記の`0x00`固定を公式環境で実走したところ、
main側の構造的一致件数が第9版（258件）より後退した（102件、
`docs/notes/m6u-idle-send-holds-last-fdc-in-result.md`）。「構造を

値がmain側の分岐に影響することが分かった。既存ログの再解析

STATUS結果2バイト目相当）であり、それ以降追加のFDCアクセスは無い

MSR、`$F8 IN`、PIO-A/C、無効命令ST0）へ21種の単純加工を施した231条件は、

なので除外した。直接読めるハードウェア状態からラウンド#0応答を導けない
ことが測定で裏付けられ、m6xの内部ワークエリア由来という見立てを支持する。

d0-boot/d1-files/d2-save/d5-seqfileの4条件を短縮再測定すると、ラウンド#0の
2バイト要求は両位置とも条件間で同一、`$FF`/`$FE`フェーズ構造も同一で、
1バイト応答は1グループだった。固定的な構成情報の交換である可能性と
整合するが、4条件はいずれも同一ディスク系なのでディスク非依存は未確定。
意味を資料から特定し、ルールから生成する方針とする。

なお今回の調査開始時に「ラウンド#0は5バイト要求」と読み違えたが、記録上の
要求長は#0〜#2の順に`2,1,5`で、5バイトはラウンド#2である。現行m6wと
本節は既に正しく記録していたため、既存文書の誤記ではなく今回の読み違いを
訂正する。根拠は`docs/notes/m7b-round0-is-a-fixed-exchange.md`。

**この節の結論（今回の実装方針の裏付け）**: 「sub は FDC から得た結果を
そのまま main へ返す」という仮説は、値を一切見ない構造的な相関
（応答直前だけにFDCアクセスが集中する・同種応答で件数が完全一致する・
応答サイズに応じて単調にスケールする）によって支持される。**ただし
これは構造の相関であり、値レベルの証明ではない。** バイト列の中身が
一致するかどうかは、伏せ字を緩めない限りこの測定手法では確認できない
（6節の実装要件参照）。

**本節でPCの具体値を書かない理由**: 1.14節と同じ判断。「継続用/終端用の
2種のPCがある」という構造は、mainのROM（自作できない）が固定して
期待してくる外部インタフェースそのものではなく、**こちらが観測に
使った分類ラベル**（測定手法上の識別子）に過ぎない。自作サブROMの
実装が正しく動くかどうかは「mainが受け取る最終的なデータ列」で
判定されるのであって、この節が言う「2種のPC」を実装が内部に持つ
必要はない。具体的な値は`docs/notes/m6l-boot-exchange.md`に留める。

  d0-bootにしか無く、追試していない）。
- **（第20版で追加）単発1バイト応答（FDCアクセス0件のケース含む）で

### 1.19 `$FE`待ち判定はビット単位で成立する（第10版）

`docs/notes/m6m-fe-bit-analysis.md`。混成ROM（公式main一式＋自作サブROM）を
公式環境で実走したところ、mainが`IN $FE pc=37DC`（1.13節「SEND前」）で
1,041,413回、subが`IN $FE pc=00CC`（1.17節「アイドル待ち」）で
1,048,477回スピンしてデッドロックした。診断は「subのアイドル判別が
`$FE==0x08`の完全一致になっており、意味を持つビットの隣で別のビットが
動いているとループを抜けられない」というものだった。この見立てを
`tools/analyze_sub_fe.py`に追加した`bit_significance()`（スピンの
最終読み取り値の集合と、スピン継続中に読まれた値の集合をビットごとに
比較し、単一ビットで両者を分離できるかを機械的に判定する）で検証した。

**確定: main視点1.13節の4ループはいずれも単一ビットで説明できる。**

| ループ | 効いているビット | 例外 |
|---|---|---|
| SEND前（37DC相当） | bit1=1 | 0件（4条件とも） |
| SEND後（37FF相当） | bit2=1（bit1=0も同格） | d5-seqfileのみ3/1273件（0.24%） |
| RECV前（3853相当） | bit0=1 | 4条件合計6/5511件（0.11%）、d0-bootのみ0件 |
| RECV後（386F相当） | bit0=0 | 4条件合計10/5513件（0.18%） |

RECV前・RECV後の少数例外はサンプル数にほぼ比例して増えており、
本解析手法が「同一pcの連続するIN $FE読み取り」をスピンとしてまとめる
際に、境界の異なる2つの実際の呼び出しを誤って1スピンに結合する
アーティファクトの可能性が高いと見ているが、**確定はできない**
（3節）。SEND前は4条件・全サンプルで例外が一件も無く、上位ビット
（0x80）はexit/loop継続の判定に無関係であることが確定した——これは
今回の診断（「意味を持つビットの隣で別のビットが動いている」）と
直接一致する観測である。

**確定: sub視点1.15節のRECV/SEND各プリミティブの4待ちも、同じ4ビットで
説明でき、例外は一件も無い。**

| 手順 | 効いているビット | 例外 |
|---|---|---|
| RECV手順2（相手のデータ準備待ち） | bit0=1 | 0件 |
| RECV手順6（相手の受理解除待ち） | bit0=0 | 0件 |
| SEND手順1（相手の受信準備待ち） | bit1=1 | 0件 |
| SEND手順4（相手の受理確認待ち） | bit2=1（bit1=0も同格） | 0件 |

main側とsub側で同じビット番号が同じ役割（bit0=RECV系、bit1=SEND開始系、
bit2=SEND確認系）を持つのは興味深いが、両者は物理的に別のレジスタ
（main自身の`$FE`とsub自身の`$FE`はハードウェア上別の窓口、1.4節）
であり、この一致がなぜ生じるかは本測定の対象外（3節）。

**訂正: SEND手順6（「境界的な待ち」、1.15節）も、待ちの終了条件自体は
単一ビット（bit2=0）で説明できる。** 1.15節は「単一の固定値読みでは
なく、次に続く手順により抜け値が変わる境界的な待ち」としていたが、
これは待ちの**終了条件**（bit2がクリアされる）と、終了後に何をするか
を決める**後続の分岐**（結果値のbit1/bit3を見てSEND反復かRECV移行かを
選ぶ）という2つの異なる情報が1バイトに同居していたことによる混同
だった。定常状態のサイト（4条件合計10752件、0例外）で確認したところ、
bit2=0への到達後、bit1=1（512件）なら直後に`OUT $FF`へSEND開始
（`0x09`）が、bit3=1（4件）なら直後にRECV開始（`0x0B`）が書かれることを
確認した——待ちの終了条件と後続の分岐先の両方が、値を見ずに構造的に
対応付けられた。

**確定: アイドル判別のRECV分岐（1.17節）はbit3=1で説明でき、例外は
一件も無い（4条件合計252スピン）。** 旧実装（`cp_n(0x08)`完全一致）は
このログのentry値のバリエーション（`0x00`/`0x01`のみ、いずれもbit3=0）
がたまたま狭かったために結果的に正しく動いていたに過ぎず、entry値に
bit3以外の未観測ビットが変化する値（例:`0x09`,`0x0C`）が現れれば
完全一致判定は誤って「まだアイドル」と判定し続ける——診断が指摘した
脆弱性そのものである。

**未確定のまま残る: アイドル判別のSEND分岐（`0x02`相当）。**
pc=00CC自体では、4条件のどのスピンも`bit1=1`（SEND側）へ進んだ事例が
無い（1.17節第8版の追試と同じ結果、変化なし）。ただし、SEND手順6の
定常サイトでは`bit1=1`→SEND開始という同じ対応が実際に508件観測されて
おり、**同一サブROM内の別サイトで確認済みの慣行**ではある。それでも
pc=00CC本体でこの分岐が実際に使われているかどうかは、本測定では
直接確認できていない。

**実装要件との関係**: `src/l3_service/make_subrom.py`の待ちループ
（`WAIT_FE_*`）とアイドル判別（`IDLE_DISPATCH`）を、上記「確定」の
範囲でビット判定（`AND`によるビットテスト）に置き換える。「未確定の
まま残る」アイドル判別のSEND分岐は、既存実装がすでに採用している
暫定構造（1.17節・3節）の判定方式だけをビット判定に揃え、確定度の
格上げは行わない（6節参照）。

### 1.20 run境界（連続送信の途中か終わりか）の判別 — 構造は確定、選択根拠は未確定（第11版）

`docs/notes/m6n-run-boundary.md`。1.17節は「通常のRECV+SEND応答ペア」
「ストリーミングRECVループ（d5-seqfile固有）」という2種の呼び出しパターン
の**存在**までは確定していたが、両者を切り替える条件は未確定のまま
だった。本節は、sub の `OUT $FF=0C`（1.15節手順7、RECVプリミティブの
完遂）の**直後**に来るイベントを (kind, port, pc) で分類し、各後継サイトが
最終的にどちらの`OUT $FF`語彙（1.12節: RECV系`0B/0A/0D/0C` / SEND系
`0F/0E/09/08`）に至るかを4条件横断で確認した。

**確定: RECV完遂直後、subは複数の後継サイトへ分岐するが、各サイトは
必ず単一の行き先（次はRECVか、SENDか）に一意に決まる（4条件・全サンプルで
例外0件）。**

| 後継サイトの型 | 行き先 | 備考 |
|---|---|---|
| `$FE`待ちループを経ない直接再武装（即`OUT $FF 0B`） | **必ずRECV** | 4条件で観測された最頻パターン（39〜144件）。複数バイトのヘッダ/バーストrunの継続に対応すると見られる |
| d5-seqfile固有の別サイト（1024件） | **必ずRECV** | 1.17節「ストリーミングRECVループ」に対応すると見られる（サイト自体の同定はしていない） |
| 専用の`$FE`待ちループ（`00→02`、bit1=1で抜ける） | **必ずSEND** | 1.15節・1.19節「sub視点SENDプリミティブ手順1」と遷移語彙が完全一致。**RECV完遂直後に専用で存在すること（直前が必ず`OUT $FF=0C`）を本節で新たに確認した** |
| もう1つの少数サイト | **必ずSEND** | 上記と役割は同じだが別PC。両者の使い分け条件は未確定 |

**確定できないこと（推測で埋めない）**: **subの実行コードが、RECV完了
直後にどの後継サイトへ分岐するかを何で選んでいるかは、本節の手法
（`$FE`/`$FF`の値・PCのみ）の外側で起きており確認できない。** 直接
再武装のケースは`$FE`/`$FF`のいずれも経由せずに分岐するため、原理的に
本手法の観測範囲外である。最も自然な説明は「直前のRECVで`IN $FC`により
受け取ったデータの値をsub内部のコードが解釈して分岐している」という
ものだが、このデータ値は伏せ字済みで読めない（1.17節が既に未確定と
していた内容と同じ結論の再確認であり、覆すものではない）。

また、当初検証した2つの副次仮説はいずれも実装の根拠にならないことが
分かった: (a) main側SEND run内で`OUT $FF 0F`がrun先頭バイトだけに
伴うという仮説は84〜99%の統計的傾向にとどまり100%ではない、
(b) run長の偶奇と`pc=3811`／`37F4`の対応（パリティ仮説）は反証された
（`docs/notes/m6l-boot-exchange.md`が観測した「256バイト応答直前は必ず
`37F4`→`3811`で終わる」という所見自体は変更しないが、これを一般化した
パリティ規則としては使えない）。

**run境界は「応答をいつ返すか」の駆動条件でもある（第13版で追加）。**
`docs/notes/m6k-mixed-divergence.md`第10部で、自作subがラウンド境界を
無視して受信バイトを通算8バイト貯めてから8バイトヘッダとして解釈して
いたバグが見つかった。1.18節が確定した「起動シーケンスは1〜12バイトの
可変長ラウンドで、ラウンドごとに応答が返る」という構造から、**run
（連続受信区間）の終わりは「通算8バイト受け取ったこと」ではなく、
このrun境界（bit1の観測）そのもので決まる**ことになる——runの終端に
達して初めて、そのrunを一つの要求として確定する。**第29版で、run長から
応答形式を決める第13版の規則は撤回した。交換#3の固定8バイト要求には
1バイトの内部状態応答、続く交換#4の2バイト要求には256バイトの実データ
応答を返す（1.23節）。** 第11版まではrun境界の判別を「runを続けるか
SENDへ転じるか」
の分岐にしか使っておらず、応答形式の決定（8バイト到達で即座に
シーク・読み出しへ進む）は依然として通算バイト数だけで行っていた
——これが、複数ラウンドにまたがる通算8バイト（例:2+1+5）を1つの
ヘッダと取り違える余地を残していた原因である。第13版はrun境界を
「runの継続/終了」だけでなく「応答をいつ・どの形式で返すか」の駆動
条件そのものとして扱うよう改めた（6節17項）。

### 1.21 `$F8`（TC）は結果フェーズ直後に固定三つ組みで発行される — 個々のFDCコマンドごとではなくバッチ単位（第15版）

`docs/notes/m6p-tc-and-f8.md`。混成ROM実走診断の分岐点28（sub側の
構造的一致プレフィックスが27件で切れる箇所。基準側の直前は
「`OUT $FB`→`IN $FA`×2→`IN $FB`→`IN $FA`→`IN $FB`」というFDCコマンド
結果フェーズで、直後に`OUT $F8 pc=06D5`が来る）を確定させた。

**確定1: `OUT $F8,0x07`→`OUT $F7,0x08`→`IN $F8`(常に`0xFF`)は固定の
三つ組みで、4条件・全事例（d0-boot 9件、d1-files 16件、d2-save 23件、
d5-seqfile 43件）で例外なく隣接する。** `OUT $F7`は本節の三つ組みでも
1.16節起動手順1と同じ値・同じpc（`0x08`・`036E`）を使う共用ルーチンで
ある。`IN $F8`は複数回ポーリングするビジーウェイトではなく、三つ組みの
一部として1回だけ読む単発確認（値は常に`0xFF`）。これは1.16節が確定
させた起動時単発`OUT $F8,0x05`/`OUT $F8,0xFF`（直前にFDCアクセスが
無い）とは別物である。

**確定2: 三つ組みはFDCコマンドの結果フェーズ（`IN $FB`の連続run）
直後に来ることはあるが、結果フェーズが終わるたび必ず来るわけではない。**
`IN $FB`のrunが終わった直後に即座に三つ組みが始まる事例は4条件とも
必ず5件（run長の内訳は`{2,2,3591,4103,4103}`で条件間完全一致）。一方、
同じrun長（例:結果2バイト、SENSE INTERRUPT STATUS相当。または
256+7=263バイト、1セクタ読み出し相当）を持つ他の大多数の事例は、
直後に次のFDCコマンド（`OUT $FB`）へ直接進み、三つ組みを経由しない。
「直前の（最も近い）`IN $FB` run」という基準で見ると全事例に対応する
runが見つかる（run長の集合は4条件で一致、件数のみディスク操作量に
応じて増減）。**解釈**: 三つ組みは個々のFDCコマンド呼び出し1回ごとの
TCではなく、複数のFDCコマンド呼び出しから成る一連のバッチ（例:
RECALIBRATEをトラック0まで繰り返す一連の呼び出し、1セクタ読み出しの
一連の呼び出し）の最後にのみ現れる。**バッチの区切り条件そのもの
（`$FA`/`$FB`の値を見ずに確定できる範囲）は未確定**（3節）。

**確定3: `$F8`は主に`OUT`で使われる。`IN $F8`は三つ組み専用の単発
読みに限られ、それ以外の文脈では一度も観測されなかった。** 4条件合計
の`OUT $F8`/`IN $F8`件数はいずれも`OUT`が`IN`を上回り（起動時2件の

## 2. 明示的に「採用できない」こと

### 2.1 `$FD`→`$FC` の値一致率100.0% は実装上ほぼ必然であり、実機の証拠として採用しない

> **この区別は仕様書の信頼度に直結する。目立つ形で書く。**

`docs/notes/m6-sub-proto.md` 第4版(3)。QUASI88 のソース
（`vendor/quasi88-libretro/src/pio.c`。GPL の第三者エミュレータ実装で、
公式 ROM とは無関係。読むことは規律上の禁止対象外）を確認した結果、
PIO は `pio_work pio_AB[2][2]`（`[side][port]`）という**共有配列**で
実装されており、

```
pio_write_AB(side, port, data)  →  pio_AB[side][port].data = data
pio_read_AB(side, port)         →  return pio_AB[side^1][port^1].data
```

という構造になっている。main の `OUT $FD` が書き込む先（`pio_AB[M][B].data`）
と、sub の `IN $FC` が読み出す元（`pio_AB[M][B].data`）が**同一の構造体
フィールド**である。中間バッファ・遅延・上書き競合の余地が実装上
そもそも存在しない。

**したがって「100.0%・取りこぼし0件」という定量的な精度そのものは、
QUASI88 のこの実装のもとでは、実際にどんなデータをやり取りしていたかに
関わらずほぼ必然的に出る数字である。** ソースコードを読むだけで
「この2ポートは一致することになっている」と分かってしまう以上、
この一致率は「$FC/$FD が経路として使われている」ことの独立な実証には
ならない。

**採用してよいのは 1.2 節の定性的結論（$FC/$FD がデータレジスタとして
機能していること。OUT 値分布という別の独立した証拠とも整合する）までである。
「実機でも100%取りこぼさない」という強い記述は本書では一切しない。**

（2026-08-11追記: `tools/verify_analyzer_corruption.py`の公式環境モードを
初めて完全実行し、解析器自体の検出力は健全（クロック順破壊・値改変の
いずれでも一致率が大きく崩れる）と確認された。ただしこれは「解析器が
正しく測っている」ことの証明であり、上記の「実機の転送信頼性の証拠には
ならない」という結論を変えるものではない。詳細は
`docs/notes/m6-sub-proto.md` 第5版。）

なお、実機の PIO（8255系 PPI 相当）で出力ラッチが相手の入力ピンに
直結される構成なら「書いた値がそのまま読める」のは物理的に自然であり、
この一致率は実機の挙動を積極的に否定するものでもない。晴らすには
別実装のエミュレータコアでの再測定、または実機 PIO の結線・ハンドシェイク
（STB/ACK/BUSY）の資料照合が要るが、いずれも本版のスコープ外（着手していない）。

### 2.2 8255（PPI）の「ポートA/B/C＋コントロールワード」4本構成仮説は棄却

`docs/notes/m6-sub-proto.md` 第2版・第3版 Q1補助。観測された OUT ポートは
main側4種・sub側6種の**合計6種類**で4本構成に一致しない。`$FF` は
両CPUから1万〜2万回オーダーで繰り返し書かれておりコントロールワード
（通常初期化時に1回）の性質と合わない。**強い形の8255仮説は不支持のまま
本版でも採用しない。** 「データポートと制御ポートが分かれている」という
緩い分類のみ採る（1.5節）。

### 2.3 「5635はディスク非依存の固定シーケンス」も棄却

`docs/notes/m6-sub-invariant.md` 第2版。diskB（市販ソフト）で同じ計測を

## 4. ゴールAとゴールBの線引き

（`docs/PLAN.md` 第1節を参照。ゴールA＝内部アドレス配置が自由な「BASICが
動く箱」、ゴールB＝番地互換までの retrofit）

`docs/notes/m6-sub-invariant.md` 第2版・第3版の測定結果、次の切り分けが
**測定によって**引かれた。

- **`$FC` 経由の固定長バースト転送（5635件、1.6節）は diskA（N88-BASIC）の
  ブート手順に固有の挙動である。** diskB（市販ソフト）は `$FC` を
  **一度も使わずに正常起動する**ことが画面確認（`m6f-diskA/B-shot-*`、
  `--screenshot` によるタイトル画面の段階的完成を目視確認）で裏付けられている
  （`m6-sub-invariant.md` 第3版）。「diskBのI/O量が多いから起動していると
  考えられる」という間接証拠（第2版）から、画面を直接見た直接証拠（第3版）
  へ格上げ済み。
- **したがって、ゴールA（BASICが動く箱）には `$FC` 経路の再現で足りる。**
  ゴールAが要求するのは「代表的なBASICリスト（LIST/RUN/PRINT/…・ファイル
  入出力）が公式ROMと同じ出力を返す」ことであり、diskA のブート経路と
  BASIC 標準のファイルI/Oを押さえれば満たせる範囲である。
- **diskB が使う別経路（`$FF`/`$FD` 主体、`$FC` 不使用）の解明はゴールBの
  課題として切り出す。** ゴールB（市販ソフトが番地互換で直接動く）は
  「サブROM内の任意入口の挙動を番地単位で再現する」ことを要求するため、
  diskA だけを踏むゴールAの範囲には含まれない。市販ソフト全般が
  この「別経路」を使うのか diskB 固有なのかも未確定（3節）であり、
  ゴールBに着手する段階で追加のサンプル（別の市販ディスク）が要る。

**この線が測定によって引かれたものであることの根拠。** 「diskAはBASIC、
diskBは市販ソフトだから別扱いにする」という区分は方針の言明ではなく、
`sub OUT $FC` の発行回数という1つの観測量（diskA=5635件固定、diskB=0件、
`m6-sub-invariant.md` 第2版(a)）と、画面の目視確認（同第3版）という
2つの独立な測定から導かれている。

## 5. 再実装の適合条件（どうなったら完成と言えるか）

`docs/spec/l1-ipl.md` 第6節・`docs/spec/l2-font.md` 第5節と同じ原則
（**実装より先に決める。物差しなので実装に合わせて緩めない**）を踏襲する。

### 5.1 判定はPIOの実装精度に依存させない

2.1節で確認したとおり、「$FD→$FC が100.0%一致する」という定量精度は
QUASI88のPIO実装（共有変数の直結配線）に固有の産物であり、実機の
転送信頼性の証拠にはならない。**したがって、自作実装がQUASI88と同じ
共有変数実装であることを適合条件にしてはいけない。** そうすると
「たまたま同じ実装方式を選んだかどうか」を判定してしまい、
「メインCPUが最終的に受け取るデータ列が公式版と一致するか」という
本来問うべきことから外れる。

**適合条件は「メインCPUが最終的に受け取るデータ列が、公式版と一致するか」
で判定する。** PIOの内部実装（共有変数か、FIFOか、ハンドシェイク付きの
レジスタか）は自由でよい。末端（mainが `IN $FD` で読み取る値の列）が
一致することだけを見る。

### 5.2 具体的な条件

1. **diskA 起動時、main が `IN $FD` で読み取る値の列が、frame 42〜62
   に対応する区間で公式版と一致すること。** 1.6節で確定した「5635件・
   末尾73件が0x00パディング」という構造上の特徴（件数・パディング位置）
   が再現されていることをまず確認する。値そのものの完全一致は
   `tools/cmp_io.py --cpu main --port FD --kind IN`（下記5.3節。
   第2版で確定。`--cpu sub` の生ログではなく main の受信列を見る）で見る。
2. **diskB 起動時、`$FC` を一切使わずに起動が完了すること。**
   4節の線引きにより、diskB 相当の経路（$FF/$FD主体）はゴールBの課題
   だが、**「diskA固有のバーストが誤ってdiskBでも発生しない」**ことは
   ゴールAの範囲でも確認しておく（diskAの経路をdiskB相当の状況で
   誤発火させないことは、diskA自体の再現精度の裏付けになる）。
3. **サブの割り込み受理が、mainの直接のI/O操作を直前イベントとしないこと**
   （1.3節の観測をそのまま条件にする。`l1-ipl.md` 第6節③「定常状態に
   `IN 40` が現れないこと」と同じ型——観測になったことをそのまま
   条件にする）。
4. **ディスク無しでは、サブCPU相当の実装コードが1命令も実行されず、
   I/O・割り込みともに0件であること**（1.1節、ネガティブコントロール
   としてそのまま条件化できる）。

**開発中の補助指標（第27版、第28版更新）**: 分岐点259より前の`$FC IN`について、
`tools/cmp_io.py --cpu main --port FC --kind IN --location-only`と両側の
seq上限を使い、値を表示せずに値一致プレフィックス長を測る。現時点では
現行ST3実発行では3件中0件一致であり、0→1→2→3件とラウンド単位で改善を
評価する。第28版の全256定数走査では1件一致まで到達したが、構造一致は
258件のままだった。一致定数そのものは記録・実装せず、意味論から生成する。
これは探索用の局所指標であって、構造的一致プレフィックスおよび本節1項の
最終適合条件を置き換えない。3件が異なる値を要求する場合、単一定数の
スキャンでは原理的に3件すべてを一致させられない点にも注意する。

### 5.3 M4(L1)の型は使えるか — 検証済み（第2版）

**第1版の「未検証」に決着をつけた。根拠は `docs/notes/m6-conformance.md`。**

#### 決定論性（判定が成立する前提）

同一条件（diskA d0-boot、`--frames 1800`）で2回測定
（`measurements/m6g-d0-boot-run{1,2}.iolog.txt`）した結果、
**main・sub両節・全列（seq/clock/frame/port/value/pc）が完全に
バイト一致した（diff 0行）。** 揺れは無い。比較による適合判定は
成立する。

副産物として、`tools/cmp_io.py` が第1版当時 **7列形式決め打ちで、
`0010-shared-clock.patch` 導入後の8列形式（`m6c-*`以降の全ログ）を
一度も正しく読めていなかった**ことが判明した（第1版5.3節の
「`--cpu sub` はコード上サポートされている」という記述は検証されて
いなかった）。7列/8列両対応に修正済み。

#### L1の型（`--init N --cycle M`）は **(c) 使えない**

`docs/notes/m6-conformance.md` 2節。sub CPUの全78,798イベントは
frame 13〜77（21フレーム弱）に収まり、**それ以降1800フレームの終わりまで
1件も無い。** L1のmain CPUは測定区間全体でVSYNC駆動の周期的OUTを
続けるが、M6のsub CPUはブート処理を終えると完全に沈黙する。
「初期化区間のあとに定常区間が続く」というL1の前提そのものが
成り立たないため、`--init N --cycle M` をどう当てはめても
（試行した範囲で）1周も周期が成立しない。

一方で、「バーストは一回限り・長さ固定（5635件）なので、むしろ完全一致
判定に向いている」という見立ては支持された。ただし「L1型の延長」では
なく、次項の**別の判定モード**としてである。

#### M6の適合条件（確定）

5.1節の原則（「PIOの内部実装は自由でよい。mainが受け取るデータ列だけを
見る」）に立ち返り、比較対象を **`--cpu sub` の生ログではなく、
main が `IN $FD` で受け取る値の列** に置き直した。sub側の生ログ
（ポート往復の回数・`$FF`ハンドシェイクの発行パターン）を条件にすると
「実装方式が同じかどうか」を判定してしまい、5.1節が退けた罠に
再び陥るため。

`tools/cmp_io.py` に **`--port/--kind`** モードを新設した
（L1型の `--init/--cycle` とは独立な第3の判定軸）。

```
tools/cmp_io.py <基準> <対象> --cpu main --port FD --kind IN
```

指定ポート・指定方向のイベントだけを発生順のまま取り出し、
**非周期の完全一致**で比較する。`m6g-d0-boot-run1` と `run2` で
5635件の完全一致を確認済み。**これが M6 の適合条件1（5.2節1項）を
機械的に判定する具体的な手段である。**

分岐点検出（差分実行の基礎）も動作を確認した。`d0-boot` と
`d1-files`（`FILES`打鍵あり）を既定モード（`--cpu main`）で比較すると
frame 301→302・pc=E7F5で最初の食い違いが人間に分かる形
（件数・seq・frame・pc）で報告される。同じ2条件を
`--port FD --kind IN` で比較すると両方とも5635件で完全一致し、
`FILES`による分岐がブート後のプロンプト処理側で起きること（＝
1.6節のブートバースト自体には影響しないこと）の追加の傍証になった。

`tools/cmp_io_selftest.sh` にテスト19〜26を追加し、8列パース・
`--port/--kind`の一致/不一致検出・引数誤りの検出を、いずれも
**わざと壊して**確認済み（全26項目OK）。

## 6. 実装要件（次のマイルストーンでやること。今回は仕様のみ）

まだ実装には入っていない。次のマイルストーンで着手する際は次を満たすこと。

1. diskA のブート手順における `$FC` 経由の固定長バースト転送（5635件、
   末尾73件0パディング）を再現する
2. サブ側の割り込みハンドラを、mainの直接介入なしに動く形で実装する
   （1.3節）
3. 5.1節の原則どおり、PIOの内部実装を自作の設計で選び、
   「mainが最終的に受け取るデータ列」で適合を判定する
4. diskB 相当の別経路（$FF/$FD主体、$FC不使用）はゴールBの課題として
   本マイルストーンのスコープには含めない（4節）
5. **（第4版で追加）main側のSEND/RECVハンドシェイク（1.10節）に、
   mainから見て正しく応答すること。** `$FE`/`$FF`のフェーズコード・
   待ち状態遷移（1.12・1.13節）はmain側の実装（公式ROM）が固定して
   期待してくる形なので、自作サブROM側がこれに合わせて応答する
   必要がある。ここは「サブの内部実装は自由」の対象**外**——
   mainのコードは自作できないため、mainが期待する外部インタフェース
   としてこの手順は固定である。
6. **（第4版で追加、第29版訂正）交換#3/#4を1.23節どおりに区別して
   応答する。** 交換#3の固定8バイト要求には1バイトの内部状態応答を返し、
   交換#4の2バイト要求には直前FDCデータ部に対応する256バイトの実データを
   返すこと。交換#3をセクタ読み出し要求とみなし、256バイト応答を開始しては
   ならない。交換#3の応答は意味未特定・生成規則未確定として明示し、値を
   推測で仕様化しない。適合条件は「mainのIN $FD列が公式版と一致するか」
   のみで判定する。
7. **（第4版で追加）書き込み側（267バイト連続SENDバースト）は、
   構造が未確定（3節）のため本マイルストーンの実装対象には含めない。**
   次のスコープで追加測定してから着手する。
8. **（第5版で追加）起動時バルク転送も`$FE`ハンドシェイクを伴う設計に
   すること。** 1.10節の訂正（1.14節Q5）により、バルクモードは
   `$FE`ポーリングを一切伴わない特別な高速ループではないことが
   判明した。ハンドシェイク無しの単純反復ループとして実装すると、
   mainが`$FE`応答を待ってスピンし続け、適合しない。定常ループ1周に
   つき`$FE`への応答を返す設計にし、1.13節で確定した4種の遷移語彙が
   バルクの定常ループ内でも使われるかは実装時に別途確認するのが
   望ましい（`m6j-bulk-trigger.md`は値そのものを確認していないため）。
9. **（第6版で追加）sub側は、main視点のSEND/RECV（1.10節）に対して
   1.15節で確定した**sub視点RECVプリミティブ**（`$FF`に`0B→0A→0D→0C`の
   順で書き、`$FE`を`20/28→21`・`41→40`の遷移で待つ）と
   **sub視点SENDプリミティブ**（`$FE`を`00→02`・`12→14`の遷移で待ち、
   `$FF`に`09→08`の順で書く）を実装しなければならない。5項が指す
   「main視点の外部インタフェース」の具体的な手順がこれである
   （混成ROM実走で、このプリミティブが未実装だとmain/subが互いに
   `$FE`を待ってデッドロックすることを確認済み。
   `docs/notes/m6k-mixed-divergence.md`第1部）。
10. **（第6版で追加）sub は `$FE` に書き込まないこと。** 1.15節・
    `docs/notes/m6k-mixed-divergence.md`第1部で、公式subが観測範囲
    （sub OUT イベント全種類）で一度も`$FE`へOUTしないことを確認した
    （1.4節の既報「sub OUT: F7,F8,FB,FC,FD,FF」とも整合する——$FEは
    元々subのOUT対象に含まれていない）。自作サブROMが誤って`$FE`に
    書き込むと、mainまたはsub自身のポーリングを乱す可能性がある。
11. **（第7版で追加）リセット直後は1.16節の起動順序どおりに動くこと。**
    `OUT $F7=0x08` → `OUT $FF=0x91` → 単発`IN $FE`読み2回（値は捨ててよい）
    → RECVプリミティブ1回（**応答のSENDは行わない**）→ `OUT $F8=0x05` →
    `OUT $F8=0xFF` → FDC初期化、の順を守ること。この順序を守らないと
    （例: FDC初期化を先に行うと）、mainは起動直後のSEND（main視点1.10節・
    1.15節冒頭のRECVプリミティブに対応するmain側の手順）に対する応答を
    永遠に待ち続け、混成ROM実走で確認された`$FE`デッドロック
    （`docs/notes/m6k-mixed-divergence.md`第3部）を再発する。
12. **（第7版で追加）ディスパッチャの判別条件は未確定（1.17節・3節）
    なので、値ベースの分岐を推測で実装しないこと。** 通常のRECV+SEND
    応答ペアとストリーミングRECVループの切り替え条件は確定できていない。
    本マイルストーンで実装するのは、確定済みの構造（アイドル待ち→RECV、
    RECV直後の即時SEND応答という定常ループ）までとし、ストリーミング
    RECVループ（6節7項がスコープ外とする書き込みバーストのsub側対応物）
    は実装対象に含めない。
13. **（第8版で追加。第10版でRECV分岐をビット判定に修正）**
    アイドル時に`$FF`へ何も書かず`IN $FE`を読み、確定済みの到達条件
    （1.19節: `bit3=1`。1.17節「アイドル待ち」の到達値、4条件252件で
    例外なし）に達するまでRECVへ進まないこと。** 混成ROM実走
    （`docs/notes/m6k-mixed-divergence.md`第6部）で、旧実装が「何を
    要求されているか決まる前に`$FF`へ`0B`を書いてしまう」ことが
    main/subの`$FE`相互デッドロックの直接原因と判明した。12項の制約
    （値ベースの分岐を推測で作らない）は維持したまま、`bit1=1`
    （1.15節SEND手順1の到達値からの類推。未確定、1.19節参照）が
    立った場合だけSENDへ分岐する暫定構造を許容する。**このSEND分岐は
    確定した判別条件ではなく、実装（`src/l3_service/make_subrom.py`）
    にもその旨を明記すること。** 値の正しさ（適合条件1のハッシュ一致）
    はこの構造の目標に含まれない。
14. **（第9版で追加）RECVプリミティブでmainへ返す応答バイトの値は、
    測定ログから採らないこと。** 1.18節が確認した構造的相関（sub側の
    FDCアクセスが応答直前のラウンド時間窓にのみ集中し、同種の応答では
    件数が完全一致し、応答サイズに応じて単調にスケールする）を根拠に、
    自作サブROMは**自分が実際にμPD765相当のFDCを叩いて得た結果バイトを
    そのままmainへ返す**構成にすること。測定ログの`$FB`/`$FC`/`$FD`の
    value列はCLAUDE.md禁止事項5により伏せ字済みで、公式版が実際に
    何を返しているかはこの先も分からないままでよい——**分からないことを
    埋めるのではなく、「値を知らなくても正しい値が出る」構造
    （FDCへ実際に問い合わせる）を選ぶことで解消する。** これは1.9節・
    3節が「`OUT $FB`の値の意味論は実装に不要」と判断したのと同じ理由の
    延長であり、**5.1節の原則（メインが最終的に受け取るデータ列だけが
    適合条件）と矛盾しない。** 値を仕様書に一切書かないこと自体が
    今回の方針であり、伏せ字の運用（緩めない）を変えるものではない。
    ラウンド#0（1.18節、256バイト読み出し要求とは異なる短い要求形式）の
    応答についても同じ方針を適用すること——値の中身が未確定のまま
    残っている（3節）ことを理由に、ここだけ値を推測で埋めてはならない。
15. **（第10版で追加）`$FE`待ちループ（`WAIT_FE_*`）とアイドル判別の
    RECV分岐は、確定したビット判定（1.19節）に置き換えること。**
    完全一致（`CP`命令での比較）ではなく、`AND`によるビットテストで
    判定すること。完全一致は、実際に観測された範囲の値でしか正しく
    動かない（entry値のバリエーションが狭い場合にたまたま一致するに
    過ぎない）ことが、1.19節・`docs/notes/m6m-fe-bit-analysis.md`で
    確定した。対応表:
    - RECVプリミティブ手順2（相手のデータ準備待ち）: `bit0=1`
    - RECVプリミティブ手順6（相手の受理解除待ち）: `bit0=0`
    - SENDプリミティブ手順1（相手の受信準備待ち）: `bit1=1`
    - SENDプリミティブ手順4（相手の受理確認待ち）: `bit2=1`
    - SENDプリミティブ手順6（境界的な待ち）: `bit2=0`で待ちを終了する
      （1.19節で「単一の固定値読みではない」という1.15節の記述を訂正
      した。待ちの終了条件自体はビット判定できる）
    - アイドル判別のRECV分岐: `bit3=1`
    - アイドル判別のSEND分岐（`bit1=1`）は13項どおり未確定のまま、
      判定方式だけビット判定に揃える（確定度は格上げしない）
16. **（第11版で追加）RECVプリミティブを1回完遂した直後は、無条件で
    アイドルディスパッチャへ戻らないこと。** 1.20節・3節で確定した
    とおり、run境界（連続受信を続けるか、応答のSENDへ転じるか）の
    選択根拠そのものは確定できていない。この未確定を推測で埋める
    代わりに、**確定済みの範囲だけで両方のデッドロック
    （RECV完遂ごとに毎回アイドルへ戻ってしまい、mainの連続SEND runの
    途中で噛み合わなくなる旧構造／runの続きを見誤って早期にSENDへ
    転じる構造）を同時に避けられる暫定構造**を採用する:
    RECV完遂直後、subは**RECVを再武装**（`OUT $FF 0B`を書く）した
    うえで、`$FE`のポーリングで**bit0**（1.19節: RECVプリミティブ
    手順2の確定ビット、「相手=mainのデータ準備完了」）と**bit1**
    （1.19節: SENDプリミティブ手順1の確定ビット。1.20節で、RECV完遂
    直後に専用で存在する待ちループ`$FE`が同じビットで抜けることを
    新たに確認済み）の**両方を同時に監視し、先に立った方へ分岐する**。
    bit0が先ならRECVデータを読む（runが続いている）。bit1が先なら
    SENDプリミティブへ切り替える。**この構造は公式subの内部分岐
    （どの後継サイトへ飛ぶか、1.20節）を推測で再現したものではない。**
    使っているビットはいずれも別の文脈（1.19節）で確定済みのものを、
    RECV完遂直後という新しい局面に機械的に適用しているだけであり、
    新しい推測を追加していない。ただし「RECV完遂直後に毎回この2ビットを
    同時ポーリングする」という構造自体は、公式subの観測された振る舞い
    （直接再武装のケースは`$FE`/`$FF`を経由せず無条件に分岐する）とは
    異なる**自作subの暫定的な設計選択**であり、確定した判別条件では
    ないことを実装（`src/l3_service/make_subrom.py`）にも明記すること。
    値の正しさ（適合条件1のハッシュ一致）はこの構造の目標に含まれない。
17. **（第13版で追加、第29版訂正）runの終端（bit1の観測）を「応答をいつ・どの
    形式で返すか」の駆動条件にすること。固定バイト数（8バイト）での
    打ち切りを再導入しないこと。** `docs/notes/m6k-mixed-divergence.md`
    第10部が診断したとおり、16項の構造（RECV完遂直後に毎回bit0/bit1を
    同時ポーリングする）はrunの継続/終了は正しく判別できていたが、
    「8バイト到達で即座にシーク・読み出し・応答フェーズへ進む」という
    応答形式の決定自体は通算バイト数（`HDR_PTR`がREQ_HDR+8に達したか）
    だけで行っており、run境界とは無関係に判定していた。これが、
    複数ラウンドにまたがる通算8バイト（1.18節のラウンド0〜2:
    2+1+5バイト）を1つのヘッダに取り違える原因だった。**runが終わる
    （bit1を観測する）まで受信を続け、run終了時点のrun長を見て応答
    形式を判断すること。** **第29版で、run長8を256バイト応答へ結び付ける
    第13版の規則を撤回する。交換#3の8バイト要求は1バイトの内部状態応答、
    続く交換#4の2バイト要求は256バイト実データ応答である（1.23節）。**
    あわせて、runの開始時（RECV_DISPATCHへの
    進入時）にHDR_PTR・run長カウンタ・RESP_ACTIVEを明示的に初期化する
    こと——旧構造はRESP_ACTIVEを応答フェーズ終了時にしかクリアして
    おらず、応答送信の途中でmainが送り手へ戻った場合の残留状態が次の
    runを汚す余地があった。受信バッファは1.18節が確定した最大12バイト
    のラウンドに余裕を持たせ、8バイトより大きく確保すること。**「run長
    ==8なら256バイト応答」という旧ルールを再導入しないこと。** 応答形式は
    1.23節の交換状態に従って決め、要求長だけで推測しない。
18. **（第14版で追加）8項の起動時バルク転送は、1周期で`$FC`・`$FD`の
    両ポートを書く構造で実装すること。** 1.14節・`docs/notes/
    m6o-fc-send-path.md`で確定したとおり、公式subのバルク定常ループは
    `OUT $FC`の直後に必ず`OUT $FD`を伴う（4条件合計22,540件、例外0）。
    自作subがこの一方（`$FC`側）を実装しないと、mainが起動時バーストで
    期待する`IN $FD`（5635件）が0件のまま進まなくなる（混成ROM実走
    診断の観察と一致）。**1.15節sub視点SENDプリミティブの拡張としてでは
    なく、8項のバルクループ自体の一部として実装すること**——本節・
    1.14節で確定したとおり、`OUT $FC`はバルク区間の外では一度も
    観測されておらず、1バイト単位の汎用SEND/RECVハンドシェイク
    （1.15節）とは別の話である。2バイトそれぞれの値の意味は未確定
    （3節）のため、14項と同じ方針（値を推測で埋めず、実際にFDCへ
    問い合わせて得た結果をそのまま使う構造にする）に従うこと。
19. **（第15版で追加）`$F8`（TC）は`OUT`で送るポートであり、`IN`では
    ない。** 1.21節で確定したとおり、公式subの`$F8`は主に`OUT`で
    使われ、`IN $F8`は「`OUT $F7,0x08`の直後に1回だけ読む単発確認」
    （値は常に`0xFF`）に限られる。旧実装（`P_TC`を`IN`で読む）は
    vendor実装のコメント由来の方向の取り違えであり、修正すること。
20. **（第15版で追加）`FDC_READ_SECTOR`のTCは、256バイトのデータ
    フェーズと7バイトの結果フェーズを両方読み終えた後に送ること。**
    1.21節確定2（run長`263`=256+7が三つ組みに対応する事例が全4条件で
    確認された）に基づく。TCを`OUT $F8,0x07`で送った直後に、
    `OUT $F7,0x08`→`IN $F8`（結果は捨ててよい。値は常に`0xFF`だが、
    このビットの意味は未確定のため分岐条件には使わないこと）を続ける。
21. **（第15版で追加）`FDC_SEEK`/`FDC_RECALIBRATE`/`FDC_SENSE_*`には
    TCを追加しないこと。** 1.21節・3節で確定したとおり、これらの
    コマンド単体（結果フェーズ長`1`/`2`）はTCを伴わない事例が大多数
    であり、いつバッチが終わってTCを送るべきかの条件が未確定のまま
    追加すると、公式ROMには無い過剰なTCを発行する推測実装になる。
22. **（第16版で追加、第17版でbatch2を追加、第18版でbatch3〜7を追加、
    第19版でTC位置を訂正）
    `FDC_RECALIBRATE`/`FDC_SEEK`はドライブ番号引数（レジスタE、
    0-3）を取ること。** μPD765/8272データシート公開仕様のとおり、
    コマンドフェーズ第2バイトの下位2ビット(US1,US0)がドライブ選択。
    起動時（`BOOT_HANDSHAKE`手順8）は、既存の`FDC_SPECIFY`呼び出しの
    直後に次の順で発行し、`MAIN_LOOP`へ進むこと:
    batch1=`FDC_RECALIBRATE`(E=0)、単発TC(`OUT $F8,0x07`のみ。
    1.21節の三つ組みではなく`OUT $F7`/`IN $F8`を伴わない単発。1.22節
    で確定した簡略形）、batch2=`FDC_SEEK`(E=0、目標シリンダは任意値
    でよい——1.22節第17版・`docs/notes/m6r-specify-vs-seek.md`5節の
    理由により、mainへ渡らず直後のRECALIBRATE(batch3)で上書きされる
    ため構造上等価。実装は`0x00`を使う。**TCなし**——第18版時点は
    ここに単発TCを発行していたが誤りだった。第19版で訂正)、batch3=
    `FDC_RECALIBRATE`(E=0、TCなし)、batch4=`FDC_RECALIBRATE`(E=1、
    **単発TCあり**。第19版でbatch2から移した正しい位置)、batch5=
    `FDC_SEEK`(E=1、目標シリンダ`0x00`。batch2と同じ理由、TCなし)、
    batch6=`FDC_RECALIBRATE`(E=1、TCなし)、
    batch7=`FDC_RECALIBRATE`(E=2、TCなし)。**batch2・3・5・6・7の
    後にTCを発行しないこと** — 1.22節第19版が訂正したとおり、TCは
    batch1・batch4の直後にのみ現れる。既存の呼び出し箇所（`MAIN_LOOP`
    起動時のRECALIBRATE、`FDC_READ_SECTOR`前のSEEK）は、意味を変えない
    よう`E=0`（ドライブ0）を明示的に渡すこと。**batch1内の順序
    （RECALIBRATEが先かSEEKが先か）は未確定のまま**なので、実装は
    RECALIBRATE→SEEKの順を維持し、これを確定事項として扱わないこと
    （3節）。
23. **（第21版で追加、第23版・第28版で更新、第29版訂正）
    交換#3ではFDCのデータ部先頭・結果部・SENSE DRIVE STATUSの実測値を
    直接返さず、1バイトの内部状態応答を返すこと。** その意味と生成規則は
    未確定であり、値を仕様へ記載しない。実装には未確定であることを明示する。
    実データ256バイトは交換#4で返す（1.23節）。以下の第21〜28版の記述は、
    交換#3/#4を取り違えていた時点の試行履歴であり、第29版の実装要件としては
    採用しない。

    第23版で`LAST_FDC_RESULT`方式を廃止してこの構造へ戻した。
    これは公式subの「この場面ではFDCを叩かない」という構造測定とは
    意図的に食い違うが、main側の適合を優先する暫定実装である。
    第25版の介入測定では、FDC実発行を残したまま送出1バイトだけを自作側の
    定数へ差し替え、上位4ビットの立ち数1〜3の全14組み合わせが258件で
    飽和し、258件を超える候補は無かった。よって、**259件目を突破する
    目的で応答値をさらに推測・調整してはならない**。原因は別にあり、
    次は診断の回数差一覧14件を調べる。測定表の送出値はすべて自作側の
    定数で、公式ROM・公式ディスクの値列に由来しない
    （`docs/notes/m6y-response-byte-value-saturation.md`）。
    第26版の介入測定では、0/2/3バイト応答は大きく後退して1バイト構造の
    必要性を確認した一方、短長2種のウェイトは258件・分岐点259を維持した。
    よって本項の1バイト応答仕様は変更しない。また、259突破のために
    送出タイミングを調整してはならない。次の調査対象は直前ラウンドではなく、
    それ以前のバルク転送でmainが受け取る内容である
    （`docs/notes/m6z-divergence-259-not-response-round.md`）。
    **第27版で再訂正**: セクタ座標の不一致は259より後であり、直前の
    バンク選択値・判断材料も一致したため、バルク転送原因説を撤回する。
    259より前のmain受信データは`$FC IN`3件だけで、ラウンド#0の1件目から
    値が不一致だった。259はこの内部状態差が表面化した地点である。
    m6yの値介入は全256通りではなかったため、FDC実発行・1バイト・
    ウェイト無しを維持して全256値を調べる。その際は構造的一致長だけでなく、
    値を表示しない`$FC IN`値一致プレフィックス長を補助指標にする。
    3ラウンドが別々の値を要求する場合、単一定数の走査だけでは解けない
    （`docs/notes/m7a-value-divergence-at-round0.md`）。
    **第28版で更新**: 全256定数の中にラウンド#0だけを一致させる候補は
    あったが、構造一致は258件のままだった。11取得源×21加工の231条件は
    すべて値一致長0であり、現行実装が直接取得できるハードウェア状態からは
    生成できない。4条件で要求2バイト・応答1バイトが固定だったことから、
    構成情報交換の可能性を資料で調べる。**一致定数を本項の実装へ焼き込んでは
    ならない。** 意味を特定し、公開されたルールから生成できる場合に限って
    実装方針を更新する（`docs/notes/m7b-round0-is-a-fixed-exchange.md`）。
