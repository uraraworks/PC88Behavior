## 1. 観測 — フォントメモリの構造

`memory.c:334-336` で `font_mem` / `font_mem2` / `font_mem3` はいずれも
`8*256*2 = 4096` バイト確保される。内訳は前半 2048 バイトが「通常フォント」、
後半 2048 バイトが「グラフィックフォント」で、`font.h` 側の3配列
（`built_in_font_ANK` / `built_in_font_ANH` / `built_in_font_graph`）が
いずれも `[8*256*1]`＝2048バイトの宣言であることと一致する
（配列の**宣言サイズ**だけを見た。中身のバイト列は見ていない）。

- **1 文字 = 8 バイト**（1 バイト = 1 ラスタ行、8 行ぶん＝8x8 の 1bpp ビットマップ）
- **256 文字ぶん**で 1 つの「面」（2048 バイト）を構成する
- コード `0x00-0xFF` が通常のANK文字、`0x100-0x1FF`（同じ面のオフセット
  `0x800-0xFFF`）がグラフィック文字。`get_font_gryph()` が
  `attr & ATTR_GRAPH` の有無でどちらを引くか決める（`crtcdmac.c:731-734`）
- 文字コードの並び順そのもの（JIS X0201 の可視部分がどこに来るか等）は
  **今回はコードから確定できていない**。半角ANK+半角カナで256種を
  埋める設計であることは配列サイズと用途コメント（`font.h:2`
  「セミグラフィック文字は内蔵文字を使用」等）から読めるが、
  コード⇔グリフの対応表そのものは font.h のデータ行を読まない限り
  確定できないため、**推定に留める**（8節）

### `font_type` / `font_loaded` / `use_built_in_font` の意味（観測）

| 変数 | 意味 | libretro版での実態 |
|---|---|---|
| `font_mem` / `font_mem2` / `font_mem3` | Font1/Font2/Font3 の実体（各4096バイト） | `font_mem` のみが実際に画面へ出る（下記） |
| `font_type`（0/1/2） | `font_rom`（実際に描画で参照するポインタ）を `font_mem`/`font_mem2`/`font_mem3` のどれにするかの選択 | **常に既定値 0 のまま。** 変更するのは `menu.c:1667`（設定メニュー）だけで、libretro 版はこの呼び出し元を持たない |
| `font_loaded` | ロードに成功したフォント種別をビットで記録（bit0=Font1, bit1=Font2, bit2=Font3） | セットはされるが、参照している箇所は見つからなかった（表示用ステータスの可能性はあるが未確認） |
| `use_built_in_font` | スタンドアロン版の設定項目「内蔵フォントを使う」 | `getconf.c:540-541` にのみ現れ、libretro 版では未使用（設定メニューが無いため） |
| `has_kanji_rom` | 漢字ROMの読み込み成否 | `memory.c` 側のロード経路でのみセットされる。**libretro.c 側の独自ロードはこの変数を一切参照しない**（2.3節） |

**結論（観測）**: `font_type` が libretro 版で切り替わることは無いため、
**実際に画面へ出るのは `font_mem`（Font1）だけ**であり、`font_mem2`・
`font_mem3`（＝ FONT2.ROM・FONT3.ROM を読み込んでも）は描画に一切使われない
死んだ経路になっている。

## 2. 観測 — 画面に出るまでの経路

`get_font_gryph()`（`crtcdmac.c:703-751`）が文字コード→グリフ変換の一点。
`font_rom`（`font_mem` を指す。1節）から該当する 8 バイトを取り出し、
`T_GRYPH`（`bit8 b[12]`）の `b[0]`〜`b[7]` にコピーする。`b[8]`〜`b[11]` は
0 初期化で、`ATTR_LOWER` 属性が立っているときだけ
`b[crtc_font_height-1]` に下線用のベタパターン（`0xff`）を焼く
（`crtcdmac.c:743`）。

`screen-vram.h` の描画ループがこの `T_GRYPH` を 1 ラスタラインずつ
消費して VRAM 相当のバッファへ書く。消費回数（`CHARA_LINES`）は
`screen-vram-base.h` で次のように定義される。

```
200LINE時   CHARA_LINES = 200 / ROWS
400LINE時   CHARA_LINES = 400 / ROWS
```

`docs/spec/l1-ipl.md` 第0節・第2節が確定させた測定対象
（80桁×20行・24kHz・400ライン）に当てはめると
**`CHARA_LINES = 400 / 20 = 20`**。1 文字セルは 20 ラスタラインを使う。

フォント側の消費は `IF_LINE200_OR_EVEN_LINE()` というマクロが制御する。
400ライン用の定義（`screen-vram-full.h:34` ほか）は

```c
#define IF_LINE200_OR_EVEN_LINE()  if ((k & 1) == 0)
```

すなわち **k（0〜19）が偶数のときだけ次の1バイトを読む**。
同じフォントバイトを連続する2ラインへそのまま出す、単純な縦2倍の
ライン倍化である（補間・拡大処理は無い）。

`k=0,2,4,...,18` の10回でフォントバイトを読むが、`T_GRYPH` に実際の
グリフが入っているのは `b[0]`〜`b[7]` の8バイトだけなので、
**上位8回ぶん（k=0〜14の偶数、ラスタ行0〜15）がグリフ本体、
残り2回ぶん（k=16,18、ラスタ行16〜19）は空白**（`ATTR_LOWER` が
立っているときだけラスタ行18〜19にアンダーラインが乗る）。

**結論（観測）— 1文字のセルサイズと配置**:

```
8x8 の 1bpp グリフを、20 ラスタラインの文字セルの
上位 16 ライン（8行 × 縦2倍）にそのまま描画し、
下位 4 ラインは空白（ATTR_LOWER 属性時のみ下2ラインに下線）。
```

フォント自体を8x10や8x20に拡大・生成し直す必要は無い。
**必要なのは 8x8 の 1bpp ビットマップ、256文字ぶん、それだけ。**

### 漢字ROMを使わずANKだけで動くか（観測）

`memory_allocate()`（上流の標準経路、`memory.c:403-527`）は、
`FONT.ROM` が無くても `has_kanji_rom` が真であれば漢字ROMの一部
（`kanji_rom[0][(1<<11)]`）を ANK フォント代わりに使うフォールバックを
持つ。漢字ROMも無ければ `built_in_font_ANK`（出所不明の内蔵データ）に
落ちる。**つまり上流のコードは「ANKだけで動く」ことを前提にしており、
漢字ROMは無くても動く**（L2 の対象は KANJI1/2.ROM ではなく
FONT.ROM／built-in の代替に絞ってよい）。

ただし libretro 版はこの `has_kanji_rom` 分岐を経由せず、独自の
ロードロジック（3節）で上書きするため、**上流の設計意図どおりには
動いていない**。

## 3. 観測 — 「黙ってすり替わる」経路

M1（`docs/notes/m1-quasi88-survey.md` 4.1/4.2）で扱った疑似BIOSと同じ
「ROMが揃わなくても黙って別のものが動く」構図が、フォント経路にも複数ある。
`docs/notes/m5-font-survey.md` 2.3節で洗い出した表をそのまま引く。

| 対象 | ROMファイルを見つけた場合 | 見つからなかった場合 |
|---|---|---|
| font_mem[0x000-0x7FF]（Font1 ANK。**実際に画面へ出る**） | **読み込んだ内容を使わず**、`kanji_rom[0]` の一部で上書き | `built_in_font_ANK`（出所不明） |
| font_mem[0x800-0xFFF]（Font1 グラフィック。**実際に画面へ出る**） | `built_in_font_graph`（出所不明）で上書き | **何もしない**（`malloc` 直後の未初期化メモリがそのまま残る） |
| font_mem2[0x000-0x7FF]（Font2。描画には使われない） | **読み込んだ内容を使わず**、`built_in_font_ANH`（出所不明）で上書き | 同じく `built_in_font_ANH` |
| font_mem2[0x800-0xFFF]（描画には使われない） | 読み込んだ内容を保持 | `built_in_font_graph`（出所不明） |
| font_mem3[0x000-0x7FF]（描画には使われない） | 読み込んだ内容を保持 | 0 埋め |
| font_mem3[0x800-0xFFF]（描画には使われない） | `built_in_font_graph`（出所不明）で上書き | 0 埋め |

**実際に画面へ出る2箇所（font_mem の前半・後半）は、どちらも
「ROMファイルの読み込みに成功したかどうかに関わらず」中身がすり替わる。**
これは「無ければ代替」という通常のフォールバックより一段悪い。
**ROMが揃っていても、libretro 版の二重ロードがそれを踏みつぶす。**

原因は、`libretro.c:559` が上流の標準ロード関数 `memory_allocate()`
（すでに `font_mem` を正しく埋める経路を含む）を呼んだ**直後に**、
`libretro.c` 独自のロードロジック（560〜638行、コメントに
「PC88Behavior 計測ハーネス」とある区画のすぐ後ろ）が同じ
`font_mem`／`font_mem2`／`font_mem3` を**もう一度**上書きすることにある。
`memory_allocate()` 側の結果は握りつぶされ、後から実行される
libretro.c 側だけが有効になる。

また、libretro.c 側は `has_kanji_rom` を一切参照せず、
`kanji_rom[0][(1<<11)]` の中身が実際に正しく読み込まれているかの
確認をしないまま使う（`libretro.c:602`）。KNJ1.ROM の読み込みに
失敗していても、それを検出せずにそのまま使う経路になっている
（`load_system_file` はファイルの発見と `open` の成否しか見ておらず、
`filestream_read` が実際に何バイト読めたかを確認していない。
`libretro.c:493`）。

### 3節の実測（グリフのバイト列を含まない）

`tools/measure.sh` は libretro の `log_cb`
（`RETRO_ENVIRONMENT_GET_LOG_INTERFACE`）をフロントエンド経由で
標準エラーに転送する。これを使い、**ROMファイル探索の成否だけ**を
確認した（採取したのはファイルパスと「見つかった／見つからなかった」の
別だけで、グリフのバイト列や漢字ROMの中身は一切出力・保存していない）。

このリポジトリの `private/rom` に対して実行した結果:

- `KANJI1.ROM` / `KANJI2.ROM` → 読み込み成功
- `FONT.ROM` / `FONT2.ROM` / `FONT3.ROM` → 3つとも「見つからない」

この条件で `memory_allocate()`（上流の標準経路）は
`has_kanji_rom == TRUE` のため `font_mem[0x000-0x7FF]` を
`kanji_rom[0][(1<<11)]` 由来のデータで埋めるはずだが、直後に走る
`libretro.c` 側の独自ロードが「`FONT.ROM` が見つからない」場合の
分岐として無条件に `built_in_font_ANK`（出所不明）で上書きする
（`libretro.c:606`）。**実在する漢字ROMを使えたはずの経路が、
二重ロードによって出所不明のフォントに差し替えられていることを、
実測ログで確認した。**

### すり替わり経路のまとめ

**画面に効く経路（font_mem）だけで2本**（ANK半分・グラフィック半分）、
**画面に効かない経路（font_mem2, font_mem3）を含めれば6本**、
すり替わりが起きる。加えて、KNJ1.ROM の読み込み成否を確認せずに
使う経路が1本。**合計 7 箇所。**

### 塞ぐ方針

L2 の実装（今回はやらない。次のマイルストーンの範囲）では、次を満たすこと。

1. **`libretro.c` 側の独自ロードを廃止し、`memory_allocate()`（またはその
   置き換え）の結果だけを唯一の経路にする。** 二重ロードそのものを無くす
2. **ROMファイルの読み込みに成功したら、その内容を一切上書きしない。**
   成否に関わらず固定データへ差し替える現状の分岐を消す
3. **ROMが見つからない場合の代替は、出所不明の `built_in_font_*` ではなく、
   L2 で採用する自由フォント（4節）に固定する**
4. **`filestream_read` の戻り値（実際に読めたバイト数）を確認し、
   期待サイズと一致しない場合は「読み込み失敗」として扱う。**
   現状はファイルが `open` できさえすれば成功扱いになる
5. **`has_kanji_rom` 相当のガードを、実際に使う直前で必ず確認する。**
   未確認のバッファ（`kanji_rom` が読み込めていない場合）をフォントとして
   使わない
6. どの供給源が有効になったかを、`font_loaded` 相当のフラグとログで
   外部から確認できるようにする（3節の実測で使った経路をそのまま
   実装の検証にも使えるようにする）

## 4. 使用するフォントの候補

必要なのは **8x8 の 1bpp ビットマップ、256文字ぶん（半角ANK＋半角カナ相当）**
（1・2節で確定）。ライセンス条項は一次情報（配布元ページ）を確認したものだけを
候補に入れる。

### 4.1 美咲フォント（Misaki Font） — 有力候補

- 配布元: <https://littlelimit.net/misaki.htm>（本体）、
  <https://littlelimit.net/font.htm>（ライセンス条項の所在）
- ライセンス条項（一次情報より引用）:
  > "These fonts are free software. Unlimited permission is granted to use,
  > copy, and distribute them, with or without modification, either
  > commercially or noncommercially."
  > "THESE FONTS ARE PROVIDED 'AS IS' WITHOUT WARRANTY."
- 再配布・改変・商用利用いずれも無条件に許諾。無保証。
  **再配布・バイナリ生成ともに問題なし**
- サイズの注意: 美咲フォントは「8x8＝漢字・ひらがな・カタカナ・記号」
  「4x8＝半角英数・半角カナ・記号」という構成。**半角(ANK)は 4x8 であり、
  本プロジェクトが必要とする 8x8 とは幅が違う。** そのまま使うなら
  4x8 グリフを 8x8 セルの中に配置する調整（左詰め＋余白、または
  他候補との併用）が要る。**この調整方法は未決定**（8節）

### 4.2 東雲フォント（Shinonome） — サイズ不一致で候補から後退

- 配布元: /efont/ プロジェクト。原ページ（openlab.ring.gr.jp/efont/shinonome/）
  はリンク切れで、archive.org 上に写しがある
- ライセンス: パブリックドメイン（複数の二次情報が一致。ただし今回は
  一次のライセンス文そのものを確認できていない。原ページがリンク切れの
  ため）
- サイズの注意: 半角ANK用の `shnm8x16.bdf` は **8x16**（幅8・高さ16）で、
  本プロジェクトが必要とする 8x8 ではない。**サイズが合わないため、
  今回の第一候補からは外す。** ライセンスの一次確認も未了なので、
  採用する場合は改めてライセンス文そのものを確認すること

### 4.3 k8x12 / k12x8（littlelimit.net） — サイズ不一致で候補から後退

- 配布元: <https://littlelimit.net/k8x12.htm>、
  <https://littlelimit.net/k12x8.htm>
- ライセンス: 4.1 と同じ littlelimit.net のフォント共通ライセンス
  （`font.htm`）。再配布・改変・商用利用いずれも無条件に許諾
- サイズの注意: 8x12 または 12x8 であり、8x8 ではない。**k8x12S**
  （非漢字を8ドット高にした変種）があるが、幅は8で高さ8の非漢字部分
  でも「JIS第一・第二水準の漢字」用フォントであり、半角カナを含む
  ANK 用途を想定した構成かどうかは未確認

### 4.4 まとめと未決定事項

**ライセンスが一次情報で確認でき、かつ再配布・改変・商用利用に問題が
無いのは 4.1（美咲フォント）と 4.3（k8x12系、littlelimit.net 共通ライセンス）
である。** ただしどちらも「8x8・ANK（半角英数+半角カナ）専用」という
今回の要求サイズにそのまま一致するものではない
（美咲は 4x8、k8x12系は 8x12/12x8）。

**東雲フォントはライセンスの一次確認が済んでいないため、現時点では
候補に入れない**（`CLAUDE.md`「ライセンスが確認できないフォントは
候補に入れない」）。改めて一次のライセンス文を確認できれば再考の余地はある。

**未決定（実装時に決めること。8節）**:
- 美咲フォントの 4x8 半角グリフを 8x8 セルにどう配置するか
  （左詰め＋余白／他フォントとの合成／別途 8x8 専用フォントを探す）
- 半角カナの文字コード対応表（JIS X0201）をどう作るか
  （美咲フォントの半角カナグリフの並びと、PC-8801 の ANK コード表の
  対応付けは今回未調査）

## 5. 適合条件（何をもって「L2 が正しく差し替わった」とするか）

**実装より先に決める。物差しなので実装に合わせて緩めない**
（`l1-ipl.md` 第6節と同じ原則）。

**公式ROM保有者でなくても検証できることを優先する。**

### ① ソース経路の条件（コードレビューで検証。ROM不要）

- 3節で数えた 7 箇所のすり替わり経路が、実装後のコードで
  **1箇所も残っていないこと**。具体的には:
  - ROMファイルの読み込みに成功した場合、その内容を上書きする分岐が
    存在しないこと
  - `filestream_read`（またはその置き換え）の戻り値を確認し、
    期待サイズと一致しない場合は「失敗」として扱っていること
  - フォント読み込みの経路が1本化されており、二重ロードで
    後勝ちになる構造が無いこと

### ② ROM非保有者でも検証できる条件（実測。ROM不要）

- **ROM無しで起動し、`font_loaded` 相当のフラグ（またはログ）で
  「どの供給源が有効になったか」を外部から確認できること。**
  3節の実測（`log_cb` 経由でファイル探索ログを見る）と同じ方法で、
  今度は「フォント供給源そのもの」を報告させる
- **ROM無しで表示された文字のビットパターンが、4節で採用した
  自由フォントのグリフと一致すること。** 自由フォントのデータは
  ライセンス上リポジトリに含めてよいので、既知の文字コード
  （例: `'A'`, `'0'`, 半角カナの一部）を画面に出し、
  VRAM相当のバッファから読み取ったビットパターンを、リポジトリに
  持つ採用フォントのデータと比較するテストで検証する。
  **これは公式ROMの有無に関係なく実行できる**

### ③ ROM保有者だけが検証できる条件（任意。参考情報）

- 実在する `FONT.ROM` を用意した環境で、`font_mem[0x000-0x7FF]` が
  読み込んだファイルの内容と一致すること（ファイルの内容とメモリ上の
  内容を比較するだけで、値そのものをリポジトリやログに書き出さない）。
  **このテストの実行と合否判定はROM保有者の手元でのみ行い、
  結果（一致/不一致）だけを報告する**運用にする

①②が実装の必須条件、③は「せっかく本物のROMがあるなら壊れていないか
確認できる」という位置づけの任意条件であり、③が無くてもL2は完成とみなす
（③はROMを持たない第三者には原理的に実行できないため、必須条件にすると
「公式ROM保有者でなくても検証できる」という目的に反する）。
