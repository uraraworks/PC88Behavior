## 位相は決まっていない（本稿最大の留保）

**O-E1の列は`U`から始まり`R`で終わる。** 素直に読むと
「runが1本走ってから要求が1つ出る」に見えるが、**そうとは限らない。**

- **窓は`frame >= 700`である。** 窓の外（`frame < 700`）に要求があれば、
  同じ列は`R`（窓の外）→`U`→`R`→`U`…とも読める。
- **直前に`R`が無い`U`が各水準1件ずつある**のは、まさに窓の左端で切れて
  いる徴候である。

**したがって「要求が先か、runが先か」は本稿では決まらない。**
**`m7jx`で引いた線のとおり、「外側の4はmain側」も確定しない。**
言えるのは**「公式では要求1つとrun 1本が1対1に交互している」**までである。

## 記述（判定ではない）

**言えること:**

- **公式では、要求とrunがきれいに1対1で交互する**（12対12。O-E3では24対24）。
  **1つの要求のあとにrunが複数続く形（GA2）ではない。**
- **`m7jw`で浮かんだ「3対象×4回＝12」という数合わせは、少なくとも
  『要求とrunが1対1』という点では整合する。** ただし
  **要求の中身は見ていない**ので、**同じ対象を4回要求したのかどうかは
  分からない**（`m7jx`で先に線を引いたとおり）。
- **混成では1対1にならない**（要求11・run 5、最長の連続`R`が3）。
  **自作サブROMのほうが、runを伴わない要求が多い。**
- 打鍵を2回にすると、混合列はちょうど2倍（24→48）になる。

**言えないこと:**

- **位相が決まっていない**（上記）。**「4はmain、9はsub」は確定しない。**
- **時刻順の隣接は因果ではない**（`m7hb`のH3がこの方法で失敗している）。
  本稿は順序の形しか主張していない。
- **要求の中身（どの対象を指すか）は見ていない。**
- **記号から値を推定しない**（`--emit-spec-table`は使っていない）。
- 条件・打鍵・ディスクを固定した1つの使い方しか見ていない。

## 次に何を測れば絞れるか

1. **位相を決める。** 窓を`frame < 700`まで広げて、**列の左端が`R`で
   始まるか`U`で始まるか**を見る。**これが決まれば「要求→run」か
   「run→要求」かが言える。** 本稿最大の留保がここで解ける。
2. **要求の中身の異同を、値を出さずに測る**（`m7jk`でrunに対してやったのと
   同じやり方）。**要求12本が3種類に分かれ、同じ種類が4本ずつなら、
   「mainが同じ対象を4回要求した」が言える。**
   **1と2が揃えば「外側の4はmain側」が確定する。**
3. 混成で要求が束になる（最長の連続`R`が3）ことの意味は、自作の実装を
   直す材料になる。ただし**先に仕様が要る。**
