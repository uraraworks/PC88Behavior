## 2. 原因 — 窓の番兵が、比べる単位の外まで窓を開いた

到達指標のうち `state_event_counts_consistent`（関門G7 の「同じ事象を2状態へ
重複計上しない」を支える整合検査）が偽になっていた。

解析器は `a`（FDC 初期化7 batch）の位置 `shape` を基準に、2つの窓を作る。

- 起動専用の窓: `clock < init_start`
- ラウンド#0応答の窓: `init_end < clock < issue_clock`

**FDC 初期化が起きない腕では `shape` が `None` になり、`init_start` と
`init_end` に番兵 `-1` が入る。** その結果:

- 起動専用の窓 `clock < -1` は**空**になる
- ラウンド#0応答の窓 `-1 < clock < issue_clock` は**走の先頭から開きっぱなし**になる

G-N と G-L0 では sub が起動ハンドシェイクを回しており、そこで sub の
`OUT $FD` が出る。開きっぱなしの窓がそれを拾い、「ラウンド#0応答があったのに
マーカー `c` は0」という不整合になった。

**同じ番兵が、2つの窓を逆方向へ壊した。** 片方は空、片方は無制限である。

## 3. m6i-b では表面化しなかった理由

m6i-b の B1 は sub をリセット直後のゲートで止めており、**sub は I/O を
1件も出していなかった**。だから開きっぱなしの窓でも拾うものが無かった。

本稿の G-L0 はゲートを持たない（[事前登録](m6i-g-clean-preamble-boundary-preregistration.md) §2）。
**ゲートを外したことで、sub が自然に起動ハンドシェイクを回すようになり、
その差が器具の側の穴を露わにした。** 事前登録は「G-L0 は m6i-b の B1 と同じ腕
ではない」「sub は I/O を行う」と先に書いていたが、**解析器がその前提に
追従していなかった。**

## 4. 直し方（[追補1](m6i-g-addendum1-window-without-init.md) で行う）

初期化が起きなかった場合の窓を、番兵ではなく**意味**で定義し直す。

## 5. 直しが結果へ波及しないこと

**修正は `shape is None` の経路にしか触れない。** G-L1・G-L2 は初期化が
完了しており、`shape` は `None` ではない。したがって両腕の到達判定・結果は
修正の影響を受けない。

それでも**全4腕を取り直す。** 一部の腕だけ旧器具の結果を流用しない。
