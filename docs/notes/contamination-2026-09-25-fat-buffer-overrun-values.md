# 汚染の記録 — m6f-c の事後観察で、ROM が割り当て表へ書いた不定値を出力した

記録日: 2026-09-25

## 1. 何が起きたか

m6f-c 本測定6回目（`m6f_c_blank_disk_accepted`）の後、事前登録の導出 C4 が `not_found` に
なった理由を調べるため、メインセッション（Claude Opus 5.5、2026-09-24〜25 のセッション。
m6f-c の事前登録・器具の担当）が、A3 の1走目の測定後の媒体（自作媒体、リポジトリ外）から、
割り当て表 (18,1,14) の「0xFF でない位置とその値」を**全部**標準出力へ出した。

位置 160〜255 には、割り当て単位に対応しない位置であるにもかかわらず、ROM が書いた値が
並んでいた。その並びは、命令列または作業域の中身のように見えた。**ROM がメモリ上の
バッファの外側の内容を媒体へ書き込んだものと考えられ、ROM 由来のバイト列である可能性が
ある**（禁止事項1・4）。

## 2. 見た範囲

- A3 の1走目の像の (18,1,14) の、位置 160〜255 のうち 0xFF でない約 94 バイトの値
  （位置 237・238 は 0xFF で、出力されていない）。
- 表示はこのセッションの標準出力だけである。**リポジトリ・ノート・コミットメッセージには
  値を転記していない。** 導出器 `derive_m6fc.py` の出力（C3）は位置の列だけで値を含まない。
- 同じ内容は、リポジトリ外の測定後の像（`~/_claude_work/m6fc-raw6/`）に残っている。

## 3. 措置

1. **値はどの文書にも書かない。** 仕様書には「位置 160 以降は割り当て単位に対応せず、
   ROM は不定の値を書く」という事実だけを書く。
2. **このセッションを、ディスクBASIC の割り当て表バッファまわり（割り当て表を読み書きする
   ときのメモリ上の扱い）の実装から外す。** 何のバイト列かは特定していない（特定しようと
   すると、さらに中身へ近づくため）。
3. 以後の導出器・観察用スクリプトは、割り当て表の値を出すとき**位置 0〜159 に限る**
   （位置 160 以降は「変わったかどうか」だけを扱う）。m6f-d の事前登録にこの制限を書く。
4. リポジトリ外の像は、**2026-09-25 に利用者の判断で削除した**（`~/_claude_work/m6fc-raw5`・`m6fc-raw6` の
   測定後の像 49 個と、診断用の一時領域の媒体・入出力ログ・画面レポート）。結果の JSON
   （座標・目印・位置だけ）は残した。

## 4. 教訓

自作媒体なので「媒体全体を読んでよい」（m6f-c 事前登録 §0.1）と決めていたが、**ROM が
書いた値には、こちらの入力から決まる構造だけでなく、ROM の内部の内容が混ざりうる。**
「自作媒体だから中身は安全」は成り立たない。出力する値は、意味が分かっている欄に限る。
