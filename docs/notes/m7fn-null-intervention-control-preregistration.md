# m7fn: 段4・段6がROM像に依存するかを陰性対照で切り分ける（事前登録）

実施日: 2026-09-03

## 位置づけ

本稿は`m7fm`の続きである。`m7fm`は軸D（段27の`out_imm`並べ替え）を実測し、
READ DATA 9段全正常終了・SEEK 11段全一致という強い示唆を得た一方で、事前
登録した合格条件5（段0〜段26の外形がベースラインから不変）が崩れたため
**不合格・未採用**と判定した。条件5が崩れた原因として、段4・段6
（`SENSE INTERRUPT STATUS`）のunit/head分類が「(a) ROMの内容そのもの
（バイト列・配置）に依存している」可能性と「(b) 軸Dの並べ替えにまだ特定
できていない前方への影響がある」可能性の2つを`m7fm`は挙げ、どちらとも決めて
いない。本稿はこの2つを切り分ける対照実験を、実装・測定より前に事前登録
するものである。**本稿の作成時には実装、測定、既存ログの再解析、エミュレータ
起動を行っていない。以下の介入内容、決めること、解釈規則は結果を見る前に
固定する。**

## 何が分かっていないか

`m7fm`は、段27（`_exchange14_prepare_first_read`）で実行される命令の並べ替え
が、実行順序上はそれより前に実行される段4・段6の外形を変えたことを実測した。
実行順序では説明がつかないこの変化について、(a)「段4・段6がROM像（バイト
列・配置）に依存しており、軸Dがコードの配置を変えたことの副作用として現れた」
のか、(b)「軸Dの並べ替え自体に、まだ特定できていない前方への影響経路がある」
のかが分かっていない。

## 陰性対照の設計（と、それが意味を変えないことの確認）

**意味を変えずにROM像だけを変える**ビルドを作り、段4・段6のunit/head分類が
変わるかを見る。

### 具体案: `align_padding_bytes`の強制

`src/l3_service/make_subrom.py`の`build_subrom(..., align_padding_bytes=...)`は、
`SUB_ROM_FETCH_WINDOW`(0x0800)の境界を跨ぐ命令が無くなるまで、`build()`が
`align_padding_bytes`を0から1バイトずつ増やしながら再アセンブルする仕組みで
ある。本稿の対照実験では、これを**強制的に1（跨ぎが解消しない場合は2以上）**
にし、`build()`の自動調整を経由せず`build_subrom()`を直接呼ぶことで、コードの
意味は変えずに配置とバイト列だけをずらしたビルドを作る。

### この案が意味を変えないことの確認（コードを読んで確認した範囲）

`src/l3_service/make_subrom.py`の該当箇所を読んで確認した。

- パディングの挿入位置（2470〜2488行）は次の形になっている。

  ```
  if align_padding_bytes > 0:
      a.jr("_align_padding_skip")
      for _ in range(align_padding_bytes):
          a.nop()
      a.label("_align_padding_skip")
  ```

  挿入するのは`jr`で無条件に飛び越す先にある`nop`列であり、**このNOP列自体は
  実行されない**（`jr`が常に`_align_padding_skip`へ飛ぶため、間のNOPは到達
  不能な区間になる）。したがって、このブロックの挿入は、実行時のレジスタ・
  メモリ・I/O列に一切影響しない。
- この挿入によって変わるのは、**この位置より後にあるすべてのラベル・命令の
  アドレス**である。既存の命令列そのもの（順序・内容）は変わらず、番地だけが
  一律にずれる。したがってバイト列（機械語コード）は、パディング挿入位置以降
  で全体的にシフトされたものになる。
- `align_padding_bytes`は`build_subrom()`のパラメータとして既に存在しており
  （848行）、`build()`はこれを0から自動的に増やして再アセンブルする仕組みを
  既に持っている（2968〜3024行、`find_fetch_window_straddles`がFalseを返す
  まで1ずつ増やす）。したがって、`align_padding_bytes`を対照実験のために
  強制する呼び出しは、**`src/l3_service/make_subrom.py`を変更せず**、既存の
  公開関数`build_subrom()`を外部の使い捨てスクリプトから直接呼ぶだけで実行
  できる（`m7fg`が`build()`を使い捨てスクリプトから直接呼んで検証した前例と
  同じ手法）。

以上の範囲で、**この案は実行時の意味（レジスタ・メモリ・I/O列）を変えず、
ROM像（バイト配置）だけを変える、と確認できた。** ただし、以下は本稿では
確認できていない。

- `align_padding_bytes`を強制した結果、境界跨ぎ・窓外配置の関門
  （`find_fetch_window_straddles`・`find_out_of_window_blocks`）を新たに
  破ってしまわないか。これは対照実験の実行時に確認する（下記「陽性対照」の
  前段として、`build_subrom()`実行後にこの2関門を明示的に検査する）。
- パディング挿入位置は`BULK_SEND`ラベルの直前（2489〜2492行付近、
  `_recv_dispatch_continue`または`IDLE_DISPATCH`への`jp`の前）であり、この
  位置は段27（`_exchange14_prepare_first_read`、2380〜2396行）より後にある。
  したがって、この挿入によってアドレスがずれるのは**段27を含むそれより後の
  コード全体**であり、**段27より前（起動時FDC初期化、`BOOT_HANDSHAKE`
  1197〜1272行を含む）のアドレスはずれない可能性が高い**。この点は本稿の
  対照実験の前提として重要であり、次節「決めること」に反映する。

### 確認できなかった場合の代替案（併記）

上記の確認は成立したため、本稿では主案（`align_padding_bytes`の強制）を採用
する。ただし、万一実行時に境界跨ぎ・窓外配置の関門を新たに破ることが判明した
場合、あるいは挿入位置が想定と異なることが判明した場合に備え、代替案を併記
する。

- **代替案:** 意味を変えないコメントのみの変更ではバイト列は変わらないため、
  無効な代替にしかならない。実質的な代替は、`align_padding_bytes`と同じ
  「到達不能なNOP埋め」を、挿入位置を変えて（例えば`BOOT_HANDSHAKE`の直後、
  段27より前の位置）追加する、**別の到達不能パディング挿入点を`src/`へ一時的
  に追加する**案である。ただしこれは`src/`の変更を伴うため、本稿の
  「`src/`・`tools/`は変更しない」という制約（サブエージェントとしての制約）
  の範囲内では実行できない。**この代替案が必要になった場合は、親セッションで
  改めて実装可否を判断する。**

## 比較する対象

- **ベースライン（現行HEAD、padding=0）**
- **ベースライン（padding強制、意味は同じ）**

の2つを比較する。**軸Dは含めない。** 軸Dを混ぜると、意味の変更（軸D）と
配置の変更（padding強制）が交絡し、段4・段6の変化がどちらに起因するかを
切り分けられなくなる。

## 決めること（先に固定する）

**段4・段6のunit/head分類が、意味を変えないROM像の変更で変わるか。**

- **変わった場合:** 段4・段6はROM像に依存する。したがって条件5（段0〜段26の
  外形がベースラインから不変）は、**ROMのバイト列を変える介入すべてが落ちる
  条件**であり、合格条件として成立しない可能性がある。`m7fg`が容量条件を
  差し替えたのと同じ形の「壊れた条件」として扱い、差し替えを検討する。
  差し替え案（複数、先に挙げる）:
  - **案1:** 段0〜段26について、「ベースラインとの不変」ではなく「条件O
    （公式）との一致が悪化していないこと」を見る。すなわち、ベースラインが
    条件Oと不一致だった段（段4・段6）が介入後に条件Oと一致する方向へ変わる
    ことは許容し、ベースラインが条件Oと一致していた段が介入後に不一致へ
    変わることだけを不合格とする。
  - **案2:** 条件5の対象から、`m7ey`が「未初期化ワークエリア依存」と特定
    済みの段（段3・段5、およびそれに連動する段4・段6）を除外し、それ以外の
    段0〜段26の外形不変だけを見る。ただしこれは`m7ey`の指摘範囲に限定した
    除外であり、除外の妥当性自体は別途確認が要る。
  - **案3:** 条件5を「外形の不変」から「外形の変化に対して、変化の説明
    （ROM像依存か、意味的な副作用か）を切り分けられること」という手続き的な
    条件へ改め、数値的な合否ではなく切り分け手順の実施を要求する。
  - どの案を採るか、あるいは他の案にするかは、本稿では決めない。次段階の
  判断とする。
- **変わらなかった場合:** 段4・段6はROM像に依存しない。したがって軸Dの
  並べ替えには前方への影響がある、ということになり、**その影響の経路を
  特定するまで軸Dを採用しない。**

**どちらの結果でも、段30の原因は決めない。**

## 結果ごとの解釈

- **段4・段6のunit/head分類が変わった場合:** 上記「決めること」のとおり、
  条件5が「ROM像を変える介入すべてが落ちる条件」である可能性が高まる。
  ただし、これは**軸Dの判定（`m7fm`の不合格・未採用）を書き換える理由には
  ならない。** 条件5そのものが妥当かを問う結果であり、`m7fm`の判定はそのまま
  残る（下記「解釈規則」参照）。
- **段4・段6のunit/head分類が変わらなかった場合:** 軸Dの並べ替えが前方
  （段4・段6）へ及ぼした影響は、ROM像の変化では説明できないことになる。
  この場合、軸Dの並べ替えそのものに、まだ特定できていない実行上の経路
  （例えば、`push_af`/`pop_af`やスタックの状態、他の経路との相互作用）が
  あることになり、**その経路を特定するまで軸Dは採用しない。** 条件5自体は
  「ROM像を変える介入すべてが落ちる条件」ではないことになるが、それでも
  「軸Dが条件5を落とした」という事実（`m7fm`）は変わらない。

## 陽性対照（必須）

**陰性対照のビルドのSHA-256が、ベースラインと異なることを先に確認する。**
これは**必須**である。同じROMを2回測って「変わらなかった」と言ってしまう
事故（介入が実際にROMへ反映されていないのに「変わらなかった」と結論する
事故）を防ぐためである。SHA-256が同一だった場合、`align_padding_bytes`の
強制が実際にはビルドへ反映されていないことになるため、その場で結論を出さず、
呼び出し方法を再確認する。

また、`build_subrom()`を`align_padding_bytes`強制で直接呼んだ後、
`find_fetch_window_straddles`・`find_out_of_window_blocks`の2関門を明示的に
実行し、境界跨ぎ・窓外配置が新たに発生していないことを確認する
（`build()`の自動調整を経由しないため、この確認を対照実験側で明示的に行う
必要がある）。

## 解釈規則

- **この対照実験は軸Dの合否を事後に書き換えるためのものではない。** `m7fm`
  の判定（不合格・未採用）はそのまま残る。条件5そのものが妥当かを別に調べる
  ものであり、この順序を明記する。すなわち、本稿の結果がどちらに転んでも、
  「`m7fm`はやはり不合格だった」という結論を変えるものではない。条件5の
  妥当性が確認・否定された場合、**改めて事前登録したうえで**軸Dの再評価を
  検討することはあり得るが、それは本稿の範囲外の次の一歩である。
- 「変わらなかった」を「条件5は妥当だった」と即断しない。陰性対照が1本
  通っただけである。単一の対照実験は、条件5が「常に妥当である」ことの証明
  にはならない。

置き、コミットしない。
