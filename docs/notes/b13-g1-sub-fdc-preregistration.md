# B13: 公式の上の G1 で、サブの FDC の命令とその発行元の領域を見る — 事前登録

記録日: 2026-10-31
位置づけ: [B12](b12-sub-1024-byte-read-results.md) の次段。公式サブの `0x02` は 1024 バイトのセクタを読めなかった。G1 が公式の上でどう読むかを、値を見ずに確かめる。
**このノートは測定より先にコミットする。** 結果を見てから規則を変えない（変えるときは後続ノートで）。

## 1. 問い

公式の上の G1 で、N=3 の READ DATA を出しているのは公式サブ ROM のコードか、RAM 上のコードか。その前に何が起きるか。

サブの ROM 領域は `0x2000` 未満、RAM は `0x4000` 以上とする（`l3-subrom.md` のメモリ配置）。発行元 PC は `lo`（`0x2000` 未満）と `hi`（`0x2000` 以上）の 2 つにだけ分ける。

## 2. 条件

OO・SS 各 2 走（自作は `impl/l3-sub-multi-read` 2a4f910）。条件は B7 第2節と同じ。クラウドの実行環境で行う。
実装は `tools/b13_sub_fdc.py`。`--io-log` の `# sub` 節から求める。B11 と同じ対照を通す。

## 3. 記録

順に最初の 400 件まで:

- `fdc <番号> <命令名> <lo|hi> <C> <H> <R> <N> <EOT>`。読み書きの命令だけ引数を書き、他の命令は `-` にする

全体の集計:

- `count <命令名> <lo|hi> <回数>`
- `port <IN|OUT> <4桁16進> <lo|hi> <回数>`（サブの全ポート）

## 4. 判定（事前に決める）

OO について排他的に 1 つ選ぶ。

- **RAM から:** 最初の N=3 の READ DATA が `hi`。G1 の途中でサブが RAM 上のコードを実行している、と観察として書く
- **ROM から:** 最初の N=3 の READ DATA が `lo`。公式サブ ROM に 1024 バイトを読む経路がある
- **N=3 が無い:** 最初の 400 件にも集計にも無い。別の見方が要る

SS は同じ番号の命令を並べて、最初に違う番号と両方の命令を書く。原因は書かない。

## 5. 記録しないもの

サブの PC の番地、入出力の値（FDC のコマンドの引数のうち上の 5 個を除く）、ディスクのバイト列、メモリの中身、画面本文、ゲーム名やファイル名。
**サブの RAM の内容やそこへ送られたコードは読まない。** G1 のコードを読むことに当たるので、方針ノート第6節のとおり別に判断する。
