# M6: メイン/サブCPU通信窓口(ポートF3〜FF)の外部観測解析

対象ログ: `measurements/m6-sub-{nodisk,d0-boot,d1-files,d2-save,d5-seqfile}.iolog.txt`
/ `.intlog.txt`（コミット 496bfbf で採取済み）。
解析器: `tools/analyze_sub_proto.py`（第三者が再実行可能。絶対パスは焼き込んでいない）。
解析出力: `measurements/m6-sub-proto-<条件>.txt`。

本稿は解析器と観測ログのみから書いている。仕様書(`docs/spec/`)の執筆・実装はまだ行わない。

## 対象条件と規模

| 条件 | main IO | sub IO | main 割込 | sub 割込 |
|---|---:|---:|---:|---:|
| nodisk | 19,404 | 0 | 575 | 0 |
| d0-boot | 95,046 | 78,798 | 1,761 | 13,593 |
| d1-files | 105,435 | 89,861 | 1,996 | 15,399 |
| d2-save | 116,530 | 100,962 | 2,207 | 17,205 |
| d5-seqfile | 138,275 | 122,289 | 2,560 | 20,301 |

nodisk ではサブCPUのI/O・割り込みが**一切記録されていない**。ディスクアクセスが
無い限りサブCPUは（少なくとも観測窓口の範囲では）動いていないと読める。これは
QUASI88固有の省略動作である可能性を排除できない（後述）。

## Q1: データ経路の実証（OUTポート → INポート の値一致率・順序）

通信窓口 `$F0`〜`$FF` のポートのみを対象にし、サンプル数10未満のペアは除外した
（範囲外のポートはCRTC/FDC等の主基板側ハードウェアで無関係、少数サンプルは偶然
一致の可能性が高いため）。

**結論: 「OUTが必ず先行する」という順序条件はすべてのペアで100%成立した
（順序逆転は0件）。しかし値の一致率は最大でも20%程度に留まり、単純な
1バイトミラーとして機能しているポートペアは見つからなかった。**

代表値（d5-seqfile、最もイベント数が多い条件）:

- main→sub: `OUT $FD → IN $FC` 一致16.6% (390/2349)、`OUT $FD → IN $F8` 一致16.3% (383/2346)
- sub→main: `OUT $FD → IN $FC` 一致8.1% (768/9526)、`OUT $FF → IN $FC` 一致2.4%

全条件で `OUT $FD → IN $FC` が最も一致率が高い組(main→sub, sub→mainの双方)だったが、
20%前後という水準は「たまたま同じ値だった」を積極的に否定できるほど高くない
（1バイトの一様分布なら偶然一致率は約0.4%なので、ゼロよりは明確に高いが、
「これがデータ経路だ」と断定するには弱い）。

**断定できないこと**: 本手法は「OUTのframe以降で同ポートに現れた最初のIN」を
比較する粗い対応付けであり、フレーム内に多数のI/Oが起きるため真の1:1対応を
保証しない。一致率が低い主因は「経路でない」のか「対応付けの粗さ」なのか、
本解析だけでは切り分けられない。より高分解能（seq単位、割り込み境界単位）の
対応付けが必要。

## Q2: ステータスビットの所在

各(CPU, INポート)についてビット0〜7を「常に0/常に1/変化」に分類した。
`$F0`〜`$FF`の主要ポートは全条件で一貫して以下の傾向:

- main `IN $FC`, `IN $FD`: 全8ビットが変化 → データレジスタ的
- main `IN $FE`: bit3のみ常に0、他7ビットは変化
- sub `IN $FA`: bit3のみ常に0、他7ビットは変化
- sub `IN $FB`: 全8ビットが変化
- sub `IN $FE`: bit0(b0)のみ常に0、他7ビットは変化

「常に0のビット1つを除き全ビットが変化する」という形は、8251的USARTの
ステータスレジスタというより**データバイトそのものの読み出し**に近い見え方。
状態ビット（常に0/1に偏るビットで、かつ特定のOUT操作後だけ変化するもの）を
明確に切り出すには、本解析のような全区間集計ではなく、割り込み前後・
コマンド発行前後で条件を絞った集計が要る。**現状は「不変ビットが少ない」という
事実のみが言え、それが何を意味するかは断定できない。**

## Q3: 割り込み源

サブの割り込み受理点の直前20件のI/Oイベントを集計した。

- `IN $FA` と `IN $FB` が全条件で直前ウィンドウの50〜71%をカバー（両者は
  ほぼ同数で常にペア、後述のQ4の交互パターンと符合）
- 次点で `OUT $FF` / `IN $FE` がペアで出現（d0-bootで29%、d5-seqfileでは
  49%まで増加 — ディスクI/Oが増えるほど比率が上がる）
- 直前1件（最も直近のイベント）で見ると `IN $FB` または `IN $FE` が
  受理点の大半を占め、この2つが交互に主要な直近トリガー候補になっている

**言えること**: 割り込み受理の直前に `$FA`/`$FB` の読み取りペア、または
`$FE` の読み取りが高頻度で存在する。これは「割り込みハンドラ自身が
直前にこれらのポートを読んでいる」可能性と「これらのポートへのアクセスが
割り込みを誘発している」可能性の両方があり得て、**本解析（直前N件の集計）
だけでは因果の向きを判定できない**。割り込み受理点そのものが多数（1回のsleep
ループの一部かもしれない）であるため、通常のポーリングループの一部を
「割り込み直前」として拾っているだけの可能性もある。

## Q4: 反復単位（n-gram）

サブの (kind, port) 記号列で頻出パターンを抽出した。全条件で共通して:

- `I$FA I$FB` / `I$FB I$FA` の交互読み出しが最頻出（d5-seqfileでn=2で
  18,541回・18,440回）。n=8まで伸ばしても `I$FA I$FB I$FA I$FB I$FA I$FB I$FA I$FB`
  のような単純交互パターンが崩れずに続く → **`$FA`/`$FB` を交互にポーリングする
  ループが存在する**、というのは高い確度で言える
- もう一系統として `O$FD O$FF I$FE I$FE` を核とする4〜8長のパターンが
  5,600〜9,500回台で頻出。`$FC`/`$FD`/`$FF`(OUT) と `$FE`(IN) の組合せが
  一塊で繰り返されており、こちらは「コマンド発行→ステータス確認」的な
  トランザクション単位の候補に見える

**断定できないこと**: n-gramの頻度だけでは、これが1つの意味的トランザクション
（例: 1バイト転送1回）に対応するのか、ハードウェアのビジーウェイトが
たまたま同じ形に揃っているだけなのかを区別できない。トランザクションの
境界（開始・終了）を決める外部の手がかり（割り込み、フレーム境界など）と
突き合わせる追加解析が要る。

## QUASI88エミュレーション由来の可能性について

以下の観測は、実機のサブCPU/FDCの挙動そのものではなく、**QUASI88の
エミュレーション実装の特性（ポーリングウェイトの実装方法、割り込みタイミングの
近似など）を反映している可能性を排除できていない**:

- Q3で見た割り込み受理点の直前パターンの一貫性（全条件でほぼ同じ比率）は、
  実機のタイミングというより、QUASI88内部でのポーリングループのステップ数が
  一定であることの反映かもしれない
- Q4の交互パターンが「崩れずに」何百回も続く点も、実機の非決定的なタイミング
  揺らぎがエミュレータでは失われている可能性がある
- nodisk条件でサブCPUが完全に無活動なのは、実機のサブCPU（常時Z80が動作し
  続ける設計の可能性がある）とは異なり、QUASI88がディスクアクセスが無い間
  サブCPUのエミュレーションをスキップしている可能性がある

これらは測定だけでは切り分けられない。実機での同種の測定、または複数の
エミュレータ実装（別コア）での再測定と突き合わせるまでは、**「実機の挙動」と
「QUASI88の実装都合」を区別せずに仕様として採用しない**こと。

# 第2版: Q1再解析（対応付けの高分解能化・8255仮説の検証）

第1版のQ1（一致率最大20%）を受けて、`tools/analyze_sub_proto.py` に3つの改善を
加えて再実行した。対象ログ・条件は第1版と同一（`measurements/m6-sub-{nodisk,
d0-boot,d1-files,d2-save,d5-seqfile}.iolog.txt` / `.intlog.txt`）。
解析出力: `measurements/m6-sub-proto2-<条件>.txt`。

**第1版の20%という数字は消していない（上のQ1節参照）。それがなぜ低く出ていたのかは
下の「改善(1)」で説明する — 対応付け方向が逆だったために、離れた場所にある複数の
OUTが同じ近傍のINに多重対応し、ノイズが乗っていた。**

## 改善した3点

1. **対応付けの粒度をIN単位に反転した。** 第1版は「各OUTについて、それ以降で
   最初に現れた同ポートのIN」を探していた（OUT基点・前向き）。これだと、離れた
   時刻の複数のOUTが同じ1件のINに多重に対応づけられてしまう。第2版は
   「各INについて、それ以前で最も近い、当該ポートへの相手CPUのOUT」を探す
   （IN基点・後ろ向き）方式に変えた。順序条件（OUTがINに先行）は対応付けの定義上
   自動的に満たされるため、代わりに「対応するOUTが見つからなかったIN件数
   （no_preceding）」を分母外として別掲するようにした。
   （注: main/subはseq自体が別々のカウンタで、seqを跨いで比較する意味を持たない
   ——`iolog.txt`のヘッダに明記されている。「seq単位」という指示は
   「フレーム単位の粗い対応付けをやめてイベント単位にする」という意味に解釈し、
   共通の時間軸として引き続きframeを使っている。frame自体もCPU間の真の前後関係を
   厳密には保証しない疎な軸である点は変わらない。）
2. **ポーリングによる分母の膨張を除いた。** 同一ポート・同一値が連続するIN列を
   1件に畳んだ「値が変化した瞬間のIN」だけを対象にした一致率を、畳む前(raw)と
   併記するようにした。
3. **制御ポート/データポートの区別を数字で出した。** 各(CPU, OUTポート)について
   書き込まれた値のユニーク数・上位値の分布を集計する節（Q1補助）を追加した。

## 結果: 一致率は依然として低い（改善後も20%台が上限）

d5-seqfile（最もイベント数が多い条件）の代表値:

- main→sub: `OUT $F3/$F8 → IN $FA`（値変化時のみ）20.0%、
  `OUT $F8/$FD → IN $FE` raw 13.7% / 値変化時 15.9〜16.1%
- sub→main: `OUT $FC/$FD → IN $FC` raw 8.2〜12.0% / 値変化時 2.5〜2.6%
  （**畳むと一致率が下がる**——rawの高さの多くはポーリングによる水増しだった
  ことを示す）

5条件すべてで一貫した傾向:

- main→sub方向の `$F8/$FD → $FE` は raw・値変化時ともに 13〜23% で近い
  （ポーリング水増しの影響が比較的小さい）
- sub→main方向は raw で 5〜12% 出ても値変化時には 2〜3% まで下がるペアが多く、
  rawの一致の大半はポーリング（同値の連続読み）による偶然一致だったと読める

**結論: 対応付けを高分解能化しても、単純な1バイトミラーとして機能している
ポートペアは見つからなかった。** 第1版の20%はある程度「対応付けの粗さ」で
説明できたが（改善後も上限は同程度の20%前後で、大きく上がらなかった）、
値変化時のみで見るとむしろ下がるペアが多く、**「経路が無い」可能性を積極的に
補強する材料も出てきた**。20%前後という水準そのものは、1バイト一様分布での
偶然一致率（約0.4%）よりは明確に高いが、「これがデータ経路だ」と断定できる
水準ではない。

### 見つかった手法上の落とし穴（記録として残す）

d0-bootで `OUT $00F3 → IN $00FB` の raw一致率が **96.6%**（257/266）という
値が出た。一見強い相関に見えるが、Q1補助を見ると `main OUT $00F3` は
d0-bootで**2回しか発行されていない**（n=2）。IN基点・後ろ向き対応付けでは、
OUTの発行頻度が低いポートほど「同じ1回のOUT」が後続の大量のINに再利用されて
対応づく。値がたまたまその後の長い区間で変わらなければ、実際には1回きりの
書き込みが数百件のINと「一致」してしまう。実際、値変化時のみに畳むと
25.0%（3/12）まで落ちる。**サンプル数が少ないOUTポートの一致率は、
たとえ`MIN_SAMPLE=10`の足切りを越えていても割り引いて読む必要がある。**

## Q1補助: 8255仮説の検証結果 — 支持されなかった

タスクで立てた仮説（8255 PPIのポートA/B/C＋コントロールワードの4ポート構成）を、
OUT値のユニーク数・分布で検証した。5条件で一貫した数字:

| ポート | 発行元 | ユニーク値数(目安) | 上位1値占有率(目安) | 判定 |
|---|---|---:|---:|---|
| $FC | sub | 255 | 5% | データポート的（ほぼ全256値を使用） |
| $FD | sub | 256 | 8〜14% | データポート的（全256値を使用） |
| $FD | main | 19〜150 | 14〜20%（サンプル数依存） | 中間〜データポート的 |
| $FB | sub | 17〜150 | 16〜23% | 中間〜データポート的 |
| $F7 | sub | **1** | **100%** | 制御/ストローブ的（常に08固定） |
| $F8 | sub | 3 | 85〜95% | 制御/ストローブ的（ほぼ07固定） |
| $F8 | main | 1 | 100% | 制御/ストローブ的（常に00、n=2のみ） |
| $FF | main/sub 両方 | 9〜10 | main 30〜49%, sub 37〜49% | **中間的（断定不可）** |

**支持された点**: データポート的なポート（$FC/$FD/$FB、特にsub OUT $FC/$FDは
ほぼ全256値を使い切っている）と、制御/ストローブ的なポート（$F7が常に08固定、
$F8がほぼ07固定）が数字の上ではっきり分かれた。これは「データポートと制御ポートが
別々に存在する」という仮説の骨格とは矛盾しない。

**支持されなかった点**: 8255仮説が要求する「ポートA/B/C＋コントロールワード」の
4本構成には収まらなかった。

- 通信窓口として観測されたOUTポートは main側 $F3,$F8,$FD,$FF、sub側
  $F7,$F8,$FB,$FC,$FD,$FF の**合計6種類**で、4本という数に一致しない
- $FFは両CPUから頻繁に（1万〜2万回オーダーで）書き込まれ、値が08/09に
  強く偏るがユニーク値は9〜10種ある。8255のコントロールワードは**通常
  初期化時に1回だけ書く**ものだが、$FFはセッションを通して繰り返し書かれて
  おり、コントロールワードというより「限られたコマンドコードを持つ
  ハンドシェイク用レジスタ」に近い見え方をしている
- $F7・$F8（sub発行）は発行回数が10〜40回程度と極端に少なく、$FC/$FD/$FB
  （数千〜数万回）と比べて桁が3〜4桁違う。8255のポートA/B/Cが対等な
  データ経路なら、この発行頻度の非対称性は説明しにくい

**結論: 8255仮説（4ポート構成）は数字で支持されなかった。** 「データ/制御の
区別がある」という緩い形の仮説は数字と矛盾しないが、「4本のうち1本が
コントロールワード専用」という強い形の仮説は $FF の書き込み頻度・
ユニーク値数のどちらとも整合しない。資料（8255の一般仕様）に測定を
合わせることはせず、測定結果をそのまま報告する。

## まだ確定していないこと

- **メイン⇔サブ間で1バイト単位のデータ転送が行われている経路そのものが
  存在するかどうかは、依然として確定していない。** 値変化時一致率が
  10〜23%に留まる以上、「経路がある」とも「経路が無い」とも断定できない
- 高一致率ペア（main $F8/$FD→sub $FE）が本当に意味のある経路なのか、
  それとも別の共通要因（例えば両者が同じフレームカウンタや共通のウェイト
  ループに同期しているだけ）による見かけ上の一致なのかは、本解析では
  切り分けられない
- QUASI88のエミュレーション実装由来である可能性（前掲「QUASI88エミュレーション
  由来の可能性について」）は今回も排除できていない。$FFの08/09集中パターンが
  実機のプロトコルなのか、QUASI88内部のポーリングウェイトの実装都合なのかは
  本解析だけでは分からない
- 対応付けに使っているframe軸は、メイン/サブが別々のZ80クロックで動くため、
  同一frame内の複数イベントの真の前後関係を保証しない。frameより細かい
  共通時間軸（例えば両CPUのクロックサイクル数を単一の外部カウンタで記録する）
  が無い限り、この解析手法の精度には天井がある

## 確定したこと

- 「OUTがINに先行する」という順序制約は、第1版・第2版いずれの手法でも
  例外なく成立している（今回の対応付け方式では定義上自明だが、no_preceding
  以外のすべてのペアでOUTが実在することは確認できている）
- sub OUT $FC/$FDはほぼ全256値を使っており、明確にデータポート的である
- sub OUT $F7は観測された全事例で値08固定、$F8はほぼ07固定であり、
  明確に制御/ストローブ的である
- 8255の「ポートA/B/C＋コントロールワード」という4本構成の仮説は、
  観測されたOUTポート数（6種類）・$FFの書き込み頻度とユニーク値数の
  両方で数字上支持されなかった

第1版・第2版の記述・数字（20%という結論を含む）は上に残したまま、

## Q1: データ経路 — 今回初めて経路を同定できた

**結論: `$FC`/`$FD` の組が、メイン⇔サブ間の実データ転送経路であると
同定できる。** 判定基準（(i) 偶然を大きく超える一致率 (ii) 十分なサンプル数
(iii) OUT先行の順序）の3つがすべて揃った。

d5-seqfile（代表値）:

- main→sub: `OUT $FD → IN $FC` 一致率 **100.0%**（raw 2294/2294、
  値変化時 1568/1568、対応OUTなし0件）
- sub→main: `OUT $FD → IN $FC` 一致率 **100.0%**（raw 9526/9526、
  値変化時 7541/7541）
- sub→main: `OUT $FC → IN $FD` 一致率 **100.0%**（raw 5634/5635、
  値変化時 5433/5433。raw側の1件のみ不一致——後述）

d0-boot・d1-files・d2-saveの3条件でも同じ3ペアが同じく100.0%
（サンプル数はd0-bootで66〜70件、d1-filesで115〜127件、d2-saveで
169〜186件と条件により変わるが、いずれもMIN_SAMPLE=10を大きく超え、
かつ発行元OUTの絶対数も20件以上——「少数OUT罠」には該当しない）。
sub OUT $FCの発行数はd0-boot〜d5-seqfileの4条件すべてで**厳密に
5635件**と一致しており（`awk`で実カウントを直接確認済み）、起動時に
毎回同じ量のデータが転送されていることを示唆する。nodiskではsubの
I/Oイベントが0件のため比較不能（既知の通り、ディスクアクセスが無いと
subが動かない）。

偶然一致率（1バイト一様分布で約0.39%）との比は**256倍**（＝1/0.39%）。
一致率100.0%という数字自体が「1バイトの値がたまたま揃った」の対極に
あり、(i)は明確に満たす。サンプル数も数千〜1万件台で(ii)も満たす。
対応付けの定義上OUTが常に先行する(iii)も、no_precedingが0件（一部1件）
であることから実際に成立している。

**raw側で1件だけ不一致になった`sub OUT $FC → main IN $FD`（5634/5635）
について**: 値変化時のみ(collapsed)ではこの不一致は消えて5433/5433=
100.0%になる。つまり不一致の1件はポーリングで同値を読み続けている
区間に混じった、対応付け上のノイズ（別の後続OUTがまだ届いていない
瞬間のIN、あるいは初回読み出し時の残留値）であり、経路の否定材料には
ならないと判断する。全4条件で同一の「raw 1件だけ不一致」が再現して
いる点も、単発の測定ノイズではなく決まった位置（おそらく起動直後の
最初の読み出し）で起きる構造的なものであることを示唆する。

**まだ言えないこと**: mainは観測範囲で`$FC`にOUTしていない
（mainのOUTポートは$F3/$F8/$FD/$FFの4種のみ）。そのため「main OUT $FC
→ sub IN $FD」の対称ペアは検証しようがない。`$FC`/`$FD`が対称な
双方向チャネルなのか、`$FD`＝送信専用・`$FC`＝受信専用という非対称な
役割分担なのかは、この観測だけでは決められない。

他のペア（`$F3`/`$F8`/`$FF`→`$FA`/`$FB`/`$FE`など）は第2版までと同様、
一致率が数%〜30%台に留まり、多くは値変化時に畳むとさらに下がる
（ポーリングによる水増し）。これらについては引き続き「経路とは
言えない」という第2版の判断を維持する。

## Q1補助: 8255仮説の扱い — 変わらず不支持、ただし経路の性質はより明確に

OUT値の分布は第2版と同じ傾向（`$FC`/`$FD`はユニーク値255〜256でデータ
ポート的、`$F7`は08固定・`$F8`はほぼ07固定で制御/ストローブ的）。
観測されたOUTポート数も6種類（main: $F3,$F8,$FD,$FF / sub: $F7,$F8,
$FB,$FC,$FD,$FF）のままで、8255の「ポートA/B/C＋コントロールワード」
という4本構成には今回も一致しなかった。**8255仮説（強い形）は棄却の
まま変わらない。**

一方、Q1で`$FC`/`$FD`が実データ経路だと分かったことで、「データポート
と制御ポートが分かれている」という緩い仮説はより具体的な形を取れる
ようになった: `$FC`/`$FD`が相互ミラー式のデータレジスタ対（自分の
`$FD`への書き込みが相手の`$FC`読み出しに、subの`$FC`書き込みがmainの
`$FD`読み出しに、それぞれ即座に反映される）、`$FF`が高頻度
（1万〜2万回オーダー）だが値が08/09/0A/0B/0C付近に偏るハンドシェイク/
コマンドコード的レジスタ、`$F7`/`$F8`が低頻度の制御ストローブ、という
役割分担が数字から読める。ただしこれが8251 USART的な構成なのか、
共有RAM/FIFOをポート経由で覗いているだけなのかは、本解析（ポート値の
統計）だけでは区別できない。

## Q3: 割り込み源 — main由来ではないことが明確になった

共通クロックにより、サブの割り込み受理点の直前ウィンドウにmain側の
I/Oイベントが含まれるかどうかを初めて区別できるようになった。

5条件すべてで一貫した結果（d5-seqfile代表値、n=20301件中）:

- 直前20件のウィンドウにmain側のイベントが1件でも含まれた受理点は
  **33件（0.2%）のみ**（他の条件でも0.1〜0.2%で同水準）
- 直前1件（clock順で真に直近のイベント）は**常にsub自身のイベント**
  （`sub IN $FB`が89〜99.7%、`sub OUT $FB`がほぼ全残り）。全5条件・
  全割り込み受理点を通じて、直前1件がmain側だった事例は**0件**
- 直前20件ウィンドウを見ても`sub IN $FA`は100%出現、`sub IN $FB`も
  89.6〜99.9%出現——第1版・第2版で見えていた「$FA/$FB交互ポーリング」
  が割り込み受理点の直前に張り付いている構図そのものは変わらない

**言えるようになったこと**: 割り込み受理の直前（clock順で真に直近）に
mainのI/Oイベントが存在したことは、5条件・全受理点を通じて一度も
無かった。つまり「mainが何らかのポートに書き込んだ直後にsubが割り込み
を受理する」という単純な因果は、この観測範囲では**支持されない**。
割り込みは、sub自身の`$FA`/`$FB`ポーリングループの内部で（＝mainの
直接の介入なしに）発生しているように見える。

**まだ言えないこと**: これは「割り込み源がmainではない」ことを積極的に
示すものであり、「割り込み源が何であるか」までは特定できていない。
候補として: (a) FDC（フロッピーディスクコントローラ）チップ自体からの
ハードウェア完了割り込み（ポートI/Oを介さない専用の割込線）、
(b) QUASI88内部のディスクエミュレーション実装が、実機のFDC割込みタイミング
を近似するために内部タイマ/ステップカウンタで割込みを生成している
可能性、の両方が排除できない。切り分けるには、FDCの物理レジスタ
（ステータス/コマンドポート、本解析の`$F0`〜`$FF`窓口とは別の可能性がある）
へのアクセスとの相関を追加で測る必要がある。

## Q4: 反復単位

n-gramパターン自体は第1版・第2版と同じ（`I$FA I$FB`交互ポーリングが
最頻出）で、clock基点に変えても崩れなかった。Q1でデータ経路が

- `$FC`/`$FD`が対称な双方向チャネルか非対称な役割分担かは、mainが

- `$FA`/`$FB`（ポーリング/ステータス系）・`$FF`（高頻度・値が偏る

# 第4版: 100%という結果の検算（観測系の故障・自己参照の疑いを晴らす）

第3版で得た「`$FC`/`$FD` 一致率100.0%」は前進だが、**100%という数字は
観測系の故障や解析器の自己参照でも出る**（本リポジトリの規律）。以下4点を
検算した。検算に使ったスクリプトは `tools/verify_analyzer_corruption.py`
（第三者が再実行可能）。

## (1) 「d0-bootで66〜70件」と「sub OUT $FCが4条件で厳密に5635件」の整合性

**矛盾ではなく、別のポート対の数字だった。** 第3版本文の同じ段落に2つの
異なるペアの数字が並記されていて紛らわしかったため、ここで切り分ける。

- 「66〜70件」は **main→sub方向**（`main OUT $FD` → `sub IN $FC`）のペア。
  main側が起動時に発行する`OUT $FD`の回数そのもので、条件により変化する
  （d0-boot 70件、d1-files 127件、d2-save 186件、d5-seqfile 2349件——
  ワークロードが増えるほど増加。`awk '$4=="main" && $5=="OUT" && $6=="00FD"'`
  で独立に再カウントし確認済み）。
- 「5635件」は **sub→main方向**（`sub OUT $FC` → `main IN $FD`）のペア。
  こちらは d0-boot・d1-files・d2-save・d5-seqfileの4条件すべてで
  **厳密に同じ5635件**（`awk '$4=="sub" && $5=="OUT" && $6=="00FC"'`で
  独立に再カウントし確認済み。nodiskのみ0件）。

両者は発行元CPU・方向・ポートがすべて異なるペアなので、数字が一致しないのは
当然であり「解析器の集計バグ」ではない。**それとは別に、sub OUT $FCが
ワークロード量に関わらず4条件で寸分違わず5635件という点自体は興味深い
不変量である。** d5-seqfileはd0-bootよりディスクI/Oが大幅に多い
（sub IOイベント総数 78,798 対 122,289）にもかかわらず、この特定の
OUTだけは増えない。固定長のブート時転送（IPL相当のデータを毎回同じ量だけ
送る）である可能性が高いが、これは今回の検算の範囲外であり別途の測定課題
として残す。

## (2) 解析器をわざと壊す — 検出力は健全

`tools/verify_analyzer_corruption.py` で d5-seqfile条件のiologに対し
2種の破壊を加え、`analyze_sub_proto.py`を再実行した
（結果: `measurements/m6c-corruption-check/d5-seqfile-summary.txt`、
個別レポート: 同ディレクトリの`*-report.txt`。破壊後の合成iolog自体は
16MB×2と大きく完全に再生成可能なためコミットしていない——スクリプトを
再実行すれば同じ乱数シードで同一のものが再現される）。

- **(a) shuffle-clock**（clock列の値集合はそのまま、行への割り当てだけを
  シャッフルし真の発生順を破壊）: `main OUT $FD -> sub IN $FC` は
  100.0%→**4.9〜5.1%**、`sub OUT $FC -> main IN $FD`は99.98%→**約1.0%**
  まで低下した。理論上の偶然一致率(0.39%)よりはやや高いが
  （ポーリングによる同値連続区間が局所的な自己相関を残すためと考えられる）、
  100%から2桁落ちており、解析器が実際にclock順の真の前後関係に依存して
  判定していることを裏付ける。
- **(b) offset-value**（全INイベントのvalueに+1 mod 256）: 両ペアとも
  **厳密に0.00%**まで崩れた。解析器がOUT値とIN値を独立した変数として
  比較していること（同じ値を両辺に使い回す自己参照ではないこと）の
  直接的な証拠。

**結論: `analyze_sub_proto.py`自体に自己参照や集計バグは見つからなかった。
検出力は健全と判断する。**

## (3) `$FC`/`$FD`はQUASI88内部で同一実体か — Yes、文字通り同じ変数だった

QUASI88のソース（`vendor/quasi88-libretro/src/pio.c`, `pc88main.c`,
`pc88sub.c`。GPLの第三者エミュレータ実装で読むことは禁止対象外）を確認した。

PIOは `pio_work pio_AB[2][2]`（`[side][port]`、side=M/S, port=A/B）という
共有配列で実装されている。書き込みは**自分のスロット**へ、読み出しは
**相手側・逆ポートのスロット**から直接行う:

```
pio_write_AB(side, port, data)  →  pio_AB[side][port].data = data
pio_read_AB(side, port)         →  return pio_AB[side^1][port^1].data
```

main側 `OUT $FD` は `pio_write_AB(M, PORT_B, data)` で `pio_AB[M][B].data`
に書く。sub側 `IN $FC` は `pio_read_AB(S, PORT_A)` で
`pio_AB[S^1][A^1].data = pio_AB[M][B].data` を読む——**書き込み先と
読み出し元が同一の構造体フィールド**である。sub `OUT $FC` → main `IN $FD`
も同様に `pio_AB[S][A].data` を介した同一フィールドの共有になっている
（対称）。

**これは「独立した2つの変数がたまたま同じ値になった」のではなく、
1個の共有バイトを介した直結配線であり、中間バッファ・遅延・
上書き競合の余地が実装上存在しない。** 100.0%（raw側の1件だけの不一致は
起動直後、pio_init()の初期値0x00をまだ誰も上書きしていない区間で
たまたま起きたと考えれば整合する）という数字は、**この実装のもとでは
プログラムが実際にどんなデータをやり取りしていたかに関わらず、
定義上ほぼ必然的に出る**。ソースコードを読むだけで「この2ポートが
一致することになっている」と分かってしまう以上、今回の測定は
「$FC/$FDが経路として使われている」ことの独立な実証にはならない
（測定するまでもなく実装から自明だった）。

一方で、これは実機の挙動を否定するものではない。8255系PPIの出力ラッチが
相手側の入力ピンに直結される構成では、実機でも「書いた値がそのまま
読める」のは物理的に自然な振る舞いである（ラッチが保持する電圧＝
読み出される値、という素朴な事実）。QUASI88のこの実装は、PPIの
データラッチ的性質を単純化して模倣したものと解釈でき、**「$FC/$FDが
データレジスタである」という定性的な結論そのものは実機と矛盾しない
可能性が高い。** 疑わしいのは「100.0%・取りこぼし無し」という
定量的な精度の部分——実機では上書き競合・ハンドシェイク（STB/ACK）
未成立時の読み捨て・バスタイミングのずれで取りこぼしが起こり得るが、
QUASI88のこの実装にはそれを起こす余地がそもそも無い。

## (4) 100%という結果を採用してよいか — **条件付き採用**

- **採用してよいこと（定性的結論）**: `$FC`/`$FD`が制御/ストローブではなく
  データレジスタとして機能していること。これはQ1補助のOUT値分布
  （ほぼ全256値を使用）という別の独立した証拠とも整合する。
- **条件付き（定量的結論）**: 「100.0%・1バイトも取りこぼさない」という
  精度の高さそのものは、QUASI88のPIO実装が共有変数による直結配線で
  中間バッファ・競合が存在しないことの反映であり、**実機の転送信頼性を
  示す独立証拠としては採用できない。** 仕様書(`docs/spec/`)に書く際は
  「(measured, QUASI88) $FC/$FDはデータ経路である」の形にとどめ、
  「実機でも100%取りこぼさない」という強い記述は避ける。
- **晴らすには何を測ればよいか**: (a) 別実装のエミュレータコア
  （QUASI88以外、可能ならCPU間タイミングを独立に模倣しているもの）で
  同じ解析を再実行し、100%が実装非依存に再現するか確認する。
  (b) 実機のPIO/8255相当チップの結線・ハンドシェイク（STB/ACK/BUSY）が
  ドキュメント化されている場合はそれを参照し（ハードウェア事実として
  資料を読むことは規律上問題ない）、実機でも取りこぼしが原理上起こり
  得ない設計かどうかを確認する。(a)(b)いずれも本タスクの範囲外として
  今回は着手していない。
- (1)で見つけた「sub OUT $FCが4条件で厳密に5635件」という不変量も、
  固定長ブート転送の裏付けとして別途測定する価値がある（未着手）。
