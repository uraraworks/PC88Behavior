# l4-mbf-oracle — GW-BASIC 数値部の予測器（M7 / L4 段階4 事前登録用）

記録日: 2026-09-15

## 位置づけ

`docs/notes/l4-design.md`「2. GW-BASIC は数値部だけ移植する」の方針に従い、
Microsoft が MIT ライセンスで公開した GW-BASIC のソース（コミット
`edf82c2ebf6bfe099c2054e0ae125c3efe5769c4`、2020-05-21）の数値演算部分だけを
読み、その浮動小数点（Microsoft Binary Format、以下 MBF）の丸め・整形規則を
Python で再現した予測器を `tools/l4_mbf_oracle.py` として作った。

**目的は「公式 ROM を測る前に、GW-BASIC のアルゴリズムを Z80 へ移せば
N88 と一致するか」という仮説を事前登録することであり、この予測器自体は
実装の正解ではない。** 一致・不一致は今後、公式 ROM を測った結果
（別担当が並行して作る事前登録・測定）と突き合わせて判定する。本予測器
および `docs/notes/l4-s4a-gwbasic-predictions.tsv` は公式 ROM を一切
参照せずに作った。

## 読んだ範囲・読んでいない範囲

読んだ:
- `refs/GW-BASIC/LICENSE`（MIT ライセンス全文）
- `refs/GW-BASIC/MATH1.ASM`（数値部の中心。定数入力 `$FIN`/`$FIDIG`、
  型強制 `$FINEX`/`$FINFC`、正規化 `$NORMS`/`$NORMD`、整数変換
  `$INT`/`$QINT`、オーバーフロー/ゼロ除算 `$OVFLS`/`$DIV0S`/`DOINF`、
  自由形式整形 `$FOFMT` の該当行だけを `grep -na` と `Read` で選んで読んだ）
- `refs/GW-BASIC/MATH2.ASM`（`$FIDIG` 本体、`$FINEX`、`$FINFC`
  (`$FIND`/`$FINS`/`$CSD`)、`$ROUNS`（偶数丸め）、`$FOUT`/`$FOFMT` の入口、
  `$SIGD` の該当行）

読んでいない: 上記2ファイルの他の関数（三角関数・対数・べき乗・乱数等）、
`GWEVAL.ASM`・`GWMAIN.ASM` 等の他ファイル（`NUMINS`/`DOASIG` 周辺だけ
`grep` で確認したが、これは `INPUT`/`READ` 文用の経路であり本予測器の対象
（直接モード `PRINT` の定数・式）には使っていない）。GW-BASIC 以外の
Microsoft BASIC 派生（MBASIC・Altair BASIC・MSX-BASIC 等）や PC-88 の
解析記事は一切参照していない。Web 検索もしていない。

`measurements/`・`private/`・`docs/notes/l4-s4a-*` の事前登録（別担当が
並行で書いている）は触っていない。

## 確認できたこと（ソースの該当行から直接読み取った）

1. **偶数丸め。** `$ROUNS`（MATH2.ASM 1779-1796）は、ガードバイトへ
   0x80 を加算した結果ちょうど桁上がりが起きた場合、ZF（加算結果が
   ちょうどゼロ、すなわち「元の値がちょうど半分」を意味する）を見て
   丸め方向を分ける。ZF=1（ちょうど半分）のときは
   「偶数になるように丸める」（コメント原文 "IF ZF=1 WANT TO ROUND TO
   EVEN"）。本予測器は round-half-to-even として再現した。
2. **小文字 e/d の扱い。** `$FINCH` テーブル（MATH1.ASM 670-678）は
   `"." / 小文字"e" / "E" / "%" / "#" / "!" / "D" / 小文字"d"` の8文字を
   持ち、`$FIN` のディスパッチ（MATH1.ASM 2094-2118, FN95 ジャンプ表）で
   小文字"e"と"E"は同じ `FN200` へ、小文字"d"と"D"は同じ `FN92` へ飛ぶ。
   **大文字化はしておらず、字句テーブル自体が両ケースを直接認識する。**
3. **E は単精度強制・D は倍精度強制。** `$FINEX`（MATH2.ASM 100-137）が
   `$VALTP` が既に倍精度でなければ `$FINFC`（MATH2.ASM 186）を呼び、
   ZF に応じて `$FD`（強制倍精度、D 側）か `$FS`（強制単精度、E 側）へ
   分岐する。D の場合は `FN92` で `XOR AL,AL`（ZF=1 を作る）、E の場合は
   `FN200` の `$CHKEL` 通過後に ZF=0 のまま `FN94` へ落ちる、という経路の
   違いから確認した。**既に倍精度なら E は何もしない（倍精度のまま）。**
4. **整数→単精度の昇格しきい値。** `$FIDIG`（MATH2.ASM 21-52）は、
   整数として蓄積中の値が 3277（10進、`3277D` と明記）以上になったら
   次の桁を足す前に単精度へ変換する。変換後の乗算加算で 32768/32769 に
   達した場合（符号ビット）も単精度へ落ちる（`FFI10`）。
5. **単精度→倍精度の昇格しきい値。** `$FIDIG`（MATH2.ASM 53-61,
   `FFFI20`/`FI35`）は、単精度で蓄積中の値が「100万相当」以上になったら
   次の桁を足す前に倍精度へ変換する（比較定数は `$DBUFF+4/+6` に置かれた
   MBF 倍精度の即値で、命令単位の値そのものは読んだが、ここでは「約100万」
   という近似規則として実装した。厳密な比較対象値そのものをコメントに
   転記してはいない）。
6. **オーバーフロー・ゼロ除算は「継続する」エラー。** `$OVFLS`/`$DIV0S`/
   `DOINF`（MATH1.ASM 1252-1313）は、エラーメッセージを出したあとも
   `RET` で呼び出し元に戻り、`$FAC` にはその型で表現できる最大値
   （符号は演算結果もしくは被除数の符号）が入ったまま処理が続く。
   つまり **直接モード `PRINT` の式の中でオーバーフロー／ゼロ除算が
   起きても、その文の実行自体は止まらず、代入された最大値がそのまま
   続けて PRINT される**と読める。本予測器はこれに基づき、
   `kind=error` の予測に「エラー種別;続く数値行」の形を採用した。
   （エラートラップ (`ON ERROR GOTO`) が有効なときの分岐 (`TRAPER`) は
   直接モードでは働かない前提で無視した。実機測定で確かめる対象。）
7. **単精度/倍精度の有効桁数予算。** `$FOFMT`（MATH1.ASM 1338-1341,
   1364, 1384）は単精度 7 桁・倍精度 16 桁を使って固定小数点/指数表記の
   判定と丸めを行う。
8. **指数表記の記号と桁。** `$FOFMT`（MATH1.ASM 1424-1442）は単精度に
   "E"、倍精度に "D" を使い、符号は常に付け（"+"/"-"）、指数は常に2桁。
9. **1桁の "%" は定数解析に効果がない。** `FN400`（MATH1.ASM 2141-2144）
   は "%" を読み飛ばすだけで、型を強制する呼び出しをしていない（"#"の
   `$FIND`・"!"の`$FINS`とは異なる）。本予測器の32腕には"%"を使う腕が
   無いため実害はないが、ノートとして残す。
10. **`-32768` は単精度を経由しても整数に戻る。** `FINF`
   （MATH1.ASM 2152-2160）は、符号反転後に単精度でちょうど `-32768`
   になった場合、`$CONI2` で整数へ変換し直す。

## 近似・推測として区別する箇所（要検証）

以下は「ソースを読んで確信を持てた」のではなく、**限られた時間で追い切れず
一般的な整合規則として近似した箇所**である。実測との不一致が出たら、まず
ここを疑うこと。

1. **固定小数点⇔指数表記の切替しきい値そのもの。**
   ~~`$FOFMT` の `FFM10`〜`FFM30`（MATH1.ASM 1338-1399）は分岐が細かく、
   命令単位までは追い切れていない。本予測器は
   「値を `d.ddd…×10^E` の形にしたときの `E` が
   `-有効桁数 < E <= 有効桁数` の範囲なら固定小数点、それ以外は指数表記」
   という対称なしきい値を採用した。既知の期待例（`.1`/`.01`/`.001` が
   固定小数点、`1E-10` が指数表記、`999999`/`9999999` が固定小数点、
   `1E10` が指数表記）とは矛盾しないが、境界そのもの（例えば単精度で
   `E=-7` や `E=8` のときにどちらになるか）は本予測器では未検証。~~
   **【2026-09-15追記、l4-s4eで解消】** Codexが命令単位で
   `$FOFMT`/`$FOTNV`/`$SIGD` を読み切った分析
   （`docs/notes/l4-gwbasic-fofmt-analysis.md`）により、正確な規則は
   「`E>=0`（`|v|>=1`）は `E<N` で固定、`E<0`（`|v|<1`）は
   `k+s<=N` で固定（`k=-E-1` は先頭0の個数、`s` は末尾0除去後の有効桁数、
   ともに丸め後の値から）」と判明した。この式は、`|v|<1` 側は本文書
   「l4-s4c: |v|<1 側の切替の候補規則」で定義した `LEN(T)`（`T=N`固定）
   と数学的に同じであり、`|v|>=1` 側は本予測器がv1から変えていなかった
   規則（`e<=有効桁数`、`E=e-1`なので`E<N`と同値）とも一致する。
   つまり**この項目の近似はl4-s4eで解消し、`--small-rule gw` として
   実装した**（詳細は本文書「l4-s4e: GW-BASIC本来の判定規則の組み込み」
   節）。旧来の`"sym"`（対称近似則）はl4-s4a/b/cとの後方互換のために
   既定のまま残しているが、これは「GW-BASICの実際の規則」ではなく
   「後方互換のための近似」であることを明記する。
2. **`$FOTNV`/`$SIGD` による末尾ゼロの扱いの細部。** 有効桁数丸め後の
   末尾ゼロ抑制・小数点位置の決定は `$SIGD`（MATH2.ASM 1809-1880）が
   絡むが、命令単位のトレースはしていない。本予測器は「丸めた桁文字列の
   右側から0を落とす」という素直な規則で近似した。
3. **加算・減算・乗算・除算そのものの丸め。** `$FADDS`/`$FMULS`/`$FDIVS`
   のガードバイト蓄積・シフトの命令列は読んでいない。本予測器は
   「両オペランドの厳密値を有理数として正確に計算し、結果の型の精度へ
   1回だけ偶数丸めする」方式で近似した（$ROUNS の偶数丸めは直接確認済み
   だが、桁合わせのシフトで捨てるビットの「スティッキービット」の扱いが
   実際の実装と完全に同じかどうかは未検証）。
4. **定数の指数適用（`$FINE`/`MDP10`）の丸め回数。** 実際のソースは
   10進定数の指数適用を常に倍精度の10のべき表で行い、最後に必要なら
   単精度へ丸め直す（2回丸めになりうる）。本予測器は「厳密値を計算して
   最終型へ1回だけ丸める」方式に単純化した（二重丸めの違いが出る場合が
   ありうる。今回の32腕では該当しないと考えているが未検証）。
5. **オーバーフロー時の残留値 `DOINF` の実バイト列。** `$INFPD`/`$INFMD`
   という定数テーブルの実バイト列そのものは読んでいない（読むと ROM では
   なく GW-BASIC 自身のデータテーブルなので禁止事項には触れないが、
   時間の都合で読まなかった）。本予測器は「その型で表現できる最大値
   （仮数全ビット1、指数バイト255）」として独自に導出した
   （既知のMBF単精度バイト列4件で符号化そのものは検証済みなので、
   この導出自体は自己無矛盾だが、実際の `$INFPD`/`$INFMD` と一致する
   保証はない）。
6. **倍精度の桁列生成における10進指数の探索。** `_decimal_exponent`/
   `_significant_digits`（`tools/l4_mbf_oracle.py`）は `Fraction` の
   厳密比較で桁位置を決めており、アルゴリズムとしては exact だが、
   GW-BASIC 内部の `$FOTNV` のアルゴリズム（10のべきを使った逐次
   ブラケット）とは実装方法が異なる。結果が一致する保証は数学的な
   正しさに基づくものであり、命令単位の一致確認ではない。

## 追記（2026-09-15、別セッション）— 仮説H6で採った規則

l4-s4a の測定結果から「N88 は単精度を6桁で出力し、6桁を超えると指数表記
になる（GW-BASIC は7桁）」という仮説 H6 が立った。この追記は
`docs/notes/l4-s4a-float-print-results.md`（測定結果ノート）や
l4-s4b の事前登録は読まずに書いている（測定より先に予測を固定する、
という本予測器の位置づけをH6でも踏襲するため）。

`tools/l4_mbf_oracle_v2.py`（命令単位で四則演算を再現したv2）に
`--single-digits N`（既定7）を追加した。GW-BASIC の `$FOFMT` が単精度用
の有効桁数を独立した定数として持つ構造（MATH1.ASM 1338 `MOV AL,LOW 8D
;assume single precision - print 7 digits`、この定数がその後の桁数計算
全体に伝播する作り）にならい、**この定数（本予測器では `single_digits`
引数）だけを差し替え、倍精度の桁数（16）・丸め（偶数丸め）・型昇格・
四則演算のアルゴリズムはいっさい変えていない。** つまりH6は「N88は
GW-BASICと全く同じ手順を踏むが、`$FOFMT` に渡す有効桁数の定数だけが
6だったら」という仮説として実装した。

### 固定小数点⇔指数表記のしきい値（N=6での扱い）

`docs/notes/l4-mbf-oracle-v2.md`「命令単位で追い切れず、v1のままにした
箇所」のとおり、この判定式自体（`-有効桁数 < E <= 有効桁数 なら
固定小数点`）は命令単位で確認し切れていない近似則のままである。
H6の実装は、この近似則の中の「有効桁数」という1変数だけを7から6に
差し替えている（式の形そのものは変えていない）。したがって **H6の
予測もこの近似則を経由しており、`docs/notes/l4-s4b-h6-predictions.tsv`
の全23腕・`docs/notes/l4-s4a-h6-posthoc.tsv`の全32腕で `approx=1` に
なる。**

### 小さい側（.0001・1e-7 など）の切替規則

しきい値の式が対称（`-有効桁数 < E <= 有効桁数`）なので、N=6でも
「小さい側の許容範囲」は単純に1桁狭くなる（単精度で `E` が
`-6` 以下なら指数表記）。これは大きい側の切替としきい値の対称性を
保つという設計選択であり、GW-BASICの実際のコード（`$FOFMT`
`FFM11`のコメント「IF S.P. AND (AL) SMALLER THAN -7 MUST CALL SIGD」
がN=7のときに `-7` という非対称な値を使っていること）とは食い違う
可能性がある——v1/v2の時点で「大きい側は`E<=有効桁数`、小さい側は
`$SIGD`が絡む別の計算」であり、単純な対称式ではないことが分かって
いたが、命令単位で解決できずに対称近似で代用していたため。**この
非対称性を無視した対称近似のまま桁数だけ6に差し替えているので、
小さい側（`docs/notes/l4-s4b-h6-predictions.tsv` の B1-B6、
`docs/notes/l4-s4a-h6-posthoc.tsv` の S1-S4）は他の腕よりもさらに
不確かさが大きい。** 全腕が`approx=1`である中でも、この6腕
（B1-B6）+4腕（S1-S4）は特に注意して見るべき腕として、ここに
明記しておく。

### 動作確認（H6追加分）

`tools/l4_mbf_oracle_v2_selftest.sh` に、`--single-digits` を追加しても
**既定（7）のときは元の `l4-s4a-gwbasic-predictions-v2.tsv` とバイト
一致する**ことを検査する項目を追加した（`predict()`の引数省略と
明示的に7を渡した場合の一致、CLIの`--single-digits`省略時と`7`明示時の
一致、倍精度が`--single-digits`の影響を受けないことの3点）。

## 追記（2026-09-15、別セッション）— l4-s4c: |v|<1 側の切替の候補規則

l4-s4a/l4-s4b の測定で単精度の有効桁数は6桁（H6）と確定したが、
`|v|<1`（小さい側）の固定小数点⇔指数表記の切替規則は、これまでの
対称近似則（S0、下記）では説明できなかった。そこで候補規則を明示的に
列挙し、l4-s4c の腕で測定してどれが残るかを確かめることにした。

**本追記はl4-s4a/l4-s4bの測定結果ノート（`l4-s4a-float-print-results.md`
等）を読まずに書いている。** 候補は「盲検の仮説」ではなく、各規則を
そのまま機械的に適用した帰結として提示するものであり、GW-BASICの
`$FOFMT`を命令単位でこれ以上追った結果ではない（`tools/l4_mbf_oracle_v2.py`
の`_small_side_fixed()`参照）。

### 候補の定義

大きい側（値の絶対値が1以上、`E>=0`）は、どの候補でも現行の規則
（`E < 有効桁数`。有効桁数は単精度6・倍精度16）のまま変えない。
以下は `E<0`（`|v|<1`）のときだけの規則。値を型の有効桁数 `N` で
丸め、末尾の0を落として得た有効桁数を `nsig`、`v=d.ddd…×10^E` の
`E`（負）とする。

- **S0（対称近似則）**: 固定 iff `E > -N`。これまでのv1/v2の実装
  そのもの。
- **LEN(T)**: 固定表記にしたときの小数点より右の文字数
  （先頭の0を含む。`(-E-1)+nsig` = 本予測器の内部変数では
  `(-e)+nsig`、`e`は`_significant_digits()`が返す10進指数で
  `E=e-1`）が `T` 以下なら固定、超えたら指数。符号は数えない。
- 単精度の候補: `S0`・`LEN7`・`LEN8`・`LEN9`。
- 倍精度の候補: `S0`・`LEN16`。

`tools/l4_mbf_oracle_v2.py` に `--small-rule sym|len` と
`--small-len T` を追加し、`predict()`/`fout_format()`/`print_one()`
すべてにこの2引数を通した（既定は`small_rule="sym", small_len=0`で、
これまでの全予測表とデータ行一致することを selftest で確認済み）。

### 候補どうしで区別できない腕

`docs/notes/l4-s4c-candidate-predictions.tsv`（20腕）のうち、提示した
候補列がすべて同じ文字列になり、その腕単独では候補を区別できないもの:

- 単精度4候補（S0/LEN7/LEN8/LEN9）が全て一致: `K3`・`K6`・`K8`・`K9`
- 倍精度2候補（S0/LEN16）が一致: `L1`・`L2`・`L3`・`L5`

これら8腕は候補規則の判定には使えない（他の腕、あるいはl4-s4c以外の
腕で区別する必要がある）。残り12腕（単精度9腕・倍精度3腕）は少なくとも
1組の候補間で予測が分かれており、判定材料になる。

### 動作確認（l4-s4c追加分）

`tools/l4_mbf_oracle_v2_selftest.sh` に、`--small-rule`/`--small-len`
追加後も既定(sym/0)が32腕全件で変わらないこと、
`docs/notes/l4-s4c-candidate-predictions.tsv`の再生成がデータ行一致
すること、`LEN(T)`のTを1つずらすと判定が変わる境界例
（`1.5e-7`、単精度6桁でLEN7=指数表記・LEN8=固定小数点）で検出できる
ことを追加した。

## 追記（2026-09-15、別セッション）— l4-s4c: S0列の食い違いとその原因

l4-s4c候補予測表v1（コミット`0936808`）のS0列が、事前登録の定義
「`S0`: `v=d.ddd×10^E`（`E<0`）、`-N<E`で固定」と食い違っている
との指摘を受けた（`K3`=`1.5e-6`はE=-6・N=6で`-6<-6`が偽→指数のはずが
表は固定。ほかに`K5`・`K9`・`K13`・`L2`・`L4`も同様）。

### 原因

**`E`（指摘/定義で使われる標準的な「先頭桁の10のべき」）と、本予測器の
内部変数`e`（`_significant_digits()`が返す、`v ≈ d1.d2d3…×10^(e-1)`の
意味の10進指数）が1つずれていた。** 具体的には `E = e - 1`。

旧`"sym"`の実装（`_small_side_fixed()`、l4-s4c v1時点）は

```
return e > -ndig
```

だった。これを標準的な`E`で書き直すと `(E+1) > -N` すなわち
`E > -N - 1`、整数どうしの比較なので `E >= -N` と同じ意味になる。
事前登録の定義`E > -N`（`E=-N`は指数表記）に対し、旧実装は
`E >= -N`（`E=-N`は固定）を計算していたことになり、**境界`E=-N`
ちょうど1点だけが食い違う。** 指摘のあった6腕（`K3`・`K5`・`K9`・
`K13`・`L2`・`L4`）はいずれも実際に`E=-N`（単精度は`E=-6`、倍精度は
`E=-16`）に当たっており、この単一の境界のずれだけで全件説明できる。

**この`"sym"`実装自体は、l4-s4a/l4-s4b/l4-s4c v1のいずれの予測表とも
無矛盾（後方互換）だったため、これまでの自己検査では検出できなかった。**
`docs/notes/l4-mbf-oracle.md`のこれ以前の記述（「H6で採った規則」等）で
使っていた「`E`」は、実は本予測器の内部変数`e`（標準的な`E`ではない）を
指していたことになる——この文書自体が変数名の意味を明示しないまま
「`E`」という記号を2つの異なる定義で使っていたことが、今回の混同の
一因だった（教訓として明記する）。

### 対応

`tools/l4_mbf_oracle_v2.py`に新しい選択肢`--small-rule sym-def`を
追加した。`_small_side_fixed()`で

```
if small_rule == "sym-def":
    return e > -ndig + 1   # 標準的なE=e-1で書くと E > -ndig
```

事前登録の定義を文字どおりに計算する。**既定の`"sym"`は変更していない**
（l4-s4a v1/v2・l4-s4b・l4-s4c v1のいずれの予測表ともデータ行一致する
ことをselftestで再確認済み）。`"sym"`は「後方互換のためにこれまでの
挙動を維持した選択肢」、`"sym-def"`は「事前登録の定義どおりに計算した
選択肢」として、どちらも予測器に残している。

`docs/notes/l4-s4c-candidate-predictions-v2.tsv`のS0列を`sym-def`で
作り直した。**LEN列はv1と完全に同一**（LENは先頭0の個数＋有効桁数から
直接計算しており、`E`/`e`のずれの影響を受けないため。selftestで確認）。
S0列がv1と異なる腕は`K3`・`K5`・`K9`・`K13`・`L2`・`L4`の6件（指摘の
とおり）で、いずれも「v1=固定小数点 → v2=指数表記」の向きに変わった
（旧`"sym"`がゆるすぎた分だけ、`"sym-def"`のほうが指数表記になりやすい）。

### 動作確認（S0修正分）

`tools/l4_mbf_oracle_v2_selftest.sh`に、`sym-def`が定義どおりの6例
（`K3`/`K5`/`K9`/`K13`/`L2`/`L4`相当）で指数表記になること、旧`"sym"`
（既定）がv1のS0列と一致すること（後方互換の確認）、l4-s4c v2予測表の
LEN列がv1と完全一致・S0列の差分腕がちょうど上記6件であること、
v2予測表の再生成がデータ行一致することを追加した。`l4-s4c-candidate-predictions.tsv`
（v1、コミット`0936808`）は1バイトも変更していない。

## 追記（2026-09-15、別セッション）— l4-s4d: 倍精度の小さい側の候補規則

l4-s4c で単精度の小さい側の候補（S0/LEN7/LEN8/LEN9）を並べたのに続き、
l4-s4d では倍精度の小さい側の候補を2つ追加した。定義（大きい側・単精度
は現行のまま。倍精度 N=16 で有効数字に丸め末尾0を落とし `v=d.ddd×10^E`、
`E<0`、`len=(-E-1)+有効桁数`）:

- **`LE17`**: `len<=17` かつ `E>=-15` なら固定、それ以外は指数。
- **`LE18`**: `len<=18` かつ `E>=-15` なら固定、それ以外は指数。

`E`はl4-s4c事前登録と同じ標準的な定義（`v=d.ddd×10^E`のE）である。
l4-s4cでS0列が内部指数`e`（`=E+1`）を使って定義と1つずれた教訓
（本文書「l4-s4c: S0列の食い違いとその原因」）を踏まえ、
`tools/l4_mbf_oracle_v2.py`の`"lene"`は必ず`E=e-1`へ変換してから
定義式どおりに`len`・`E`の2条件を比較する（`_small_side_fixed()`
参照）。`--small-rule lene --small-len T --small-emin -15`で選べる。
**既定（`"sym"`）は変えていない**（これまでの全予測表とデータ行一致
することをselftestで確認済み）。

### M1・M4 を定義から手で検算した過程

**M1: `.001234567890123456#`**（倍精度、`#`で強制）

- 値 = 0.001234567890123456
- 16桁で有効数字に丸め、末尾0を落とす: 仮数部の16桁がそのまま
  `1234567890123456`（末尾0なし、切り捨て・繰り上げも発生しない
  ちょうど16桁の値なので丸めの影響なし）→ 有効桁数 `nsig=16`
- `v=d.ddd×10^E`の形にすると `1.234567890123456×10^-3` → `E=-3`
- `len=(-E-1)+nsig=(-(-3)-1)+16=(3-1)+16=2+16=18`
- `LE17`: `len<=17`は`18<=17`で偽 → **指数表記**
  （`E>=-15`は`-3>=-15`で真だが、`len`条件が先に不成立なので全体として
  指数表記になる。`len<=T`と`E>=Emin`は**両方**満たして初めて固定なので、
  片方でも偽なら指数）
- `LE18`: `len<=18`は`18<=18`で真、かつ`E>=-15`は`-3>=-15`で真 →
  **固定小数点**（`.001234567890123456`）
- 本予測器の出力（`docs/notes/l4-s4d-double-candidate-predictions.tsv`）:
  `LE17=" 1.234567890123456D-03 "`・`LE18=" .001234567890123456 "`
  で一致。

**M4: `1.234d-15`**（倍精度、`d`指数で強制）

- 値 = 1.234×10^-15
- 16桁で丸めると末尾に12個の0が付く形（`1234000000000000`相当）だが、
  末尾0はすべて落とすので有効桁数は元の桁数のまま → `nsig=4`
  （`1234`、末尾0落とし後）
- `v=d.ddd×10^E`はもともとこの形 → `E=-15`
- `len=(-E-1)+nsig=(-(-15)-1)+4=(15-1)+4=14+4=18`
- `LE17`: `len<=17`は`18<=17`で偽 → **指数表記**
- `LE18`: `len<=18`は`18<=18`で真、かつ`E>=-15`は`-15>=-15`で真
  （境界ちょうど、等号を含む） → **固定小数点**
  （`.000000000000001234`。先頭0が14個、続けて`1234`）
- 本予測器の出力: `LE17=" 1.234D-15 "`・`LE18=" .000000000000001234 "`
  で一致。M1と異なり、M4は`E`が`Emin=-15`の境界ちょうどに当たる例
  （`LE18`の`E>=-15`条件がなければ`M1`と同じ理由（`len<=18`のみ）で
  固定になるところ、`E>=-15`条件自体は今回どちらの候補でも通過して
  いる。`E`条件が実際に効くのは`docs/notes/l4-mbf-oracle-v2.md`等で
  今後より`E`の小さい腕を扱うとき）。

### LE17とLE18で予測が分かれる腕

`docs/notes/l4-s4d-double-candidate-predictions.tsv`（10腕）のうち、
`LE17`と`LE18`で予測が異なるのは `M1`・`M4`・`M6`・`M10` の4件
（いずれも`len`がちょうど18で、`T=17`では指数・`T=18`では固定になる
境界例）。残り6件（`M2`・`M3`・`M5`・`M7`・`M8`・`M9`）は`LE17`と
`LE18`で予測が一致しており、この腕だけでは2候補を区別できない。

### 動作確認（l4-s4d追加分）

`tools/l4_mbf_oracle_v2_selftest.sh`に、`--small-rule lene`追加後も
既定(sym/0/0)が32腕全件で変わらないこと、`LE17`/`LE18`がM1/M4相当の
4例で定義どおりであること、`E`の下限を1つずらす（`-15→-14`、
`1d-15`が固定→指数に変わる境界例）故障注入で検出できること、
`docs/notes/l4-s4d-double-candidate-predictions.tsv`の再生成が
データ行一致することを追加した。

## 追記（2026-09-15、別セッション）— l4-s4e: GW-BASIC本来の判定規則の組み込み

l4-s4a〜dで扱ってきた固定⇔指数の切替しきい値は、上の「近似・推測として
区別する箇所」1番のとおり本予測器では未解決の近似のままだった。今回、
Codex（gpt-5.6-sol）にGW-BASICのソース（`$FOFMT`/`$FOTNV`/`$SIGD`/
`$FOTCV`等）だけを命令単位で読ませた分析結果を受け取り、
`docs/notes/l4-gwbasic-fofmt-analysis.md`として取り込んだ。**この分析は
Codexが独立に行ったもので、PC88Behaviorの測定は参照していない。**

### 分析の要点

- `|v|>=1`（`E>=0`）: `E<N` なら固定、それ以外は指数。
- `|v|<1`（`E<0`）: `k+s<=N` なら固定、それ以外は指数。
  `k=-E-1`（先頭0の個数）、`s`は末尾0除去後の有効桁数（ともに`N`桁へ
  丸めた**後**の値から計算する）。
- `N`は単精度7・倍精度16（本予測器の`--single-digits`と同じ役割）。
- 6桁版（H6）を作るには`N`の置き換えが複数箇所（`$FOFMT`の初期値・
  しきい値・`$FOTNV`のスケール・`$FOTCV`の桁数テーブル）に及び、
  さらに丸めで桁が繰り上がる場合（例: 単精度6桁で`999999.5`→
  `1000000`）の再正規化ガードが要る、との指摘があった。

### 自分での確認

分析を受け取る前に、私自身も`tools/l4_mbf_oracle_v2.py`のv2開発時
（本文書のv2追記群参照）に `$FOFMT` の `FFM10`〜`FFM30`
（MATH1.ASM 1338-1399）を命令単位で読んでおり、`$FOTNV`後の`AL`
（分析でいう`A`）が「`N+1`初期値からの複雑な分岐で最終的に`AL=X`
（`$FOFMT`内の未加工の値）を保つ」構造であることは既に読み取れていた
（本文書「l4-s4c: S0列の食い違いとその原因」の`A=E-N+1`相当の議論）。
分析を受け取った後、以下を自分で行って独立に確認した:

1. **既存実装との突き合わせ。** 分析の`|v|<1`側の式（`k+s<=N`）は、
   `k=-E-1`・`s=nsig`という記号を使えば、私が以前から実装していた
   `"len"`候補（`(-e)+nsig<=T`、`e=E+1`なので`-e=-E-1=k`）と**T=Nに
   固定した場合とまったく同じ式**であることに気づいた。つまり
   分析の`|v|<1`側規則は、l4-s4cで既に実装・検証済みの`LEN(N)`
   そのものである。
2. **分析の表と自分の実装を突き合わせた。** 分析4節の倍精度表21件
   （`1#/3`〜`12345678901234567#`）と単精度表(a)(b)各14件
   （合計28件、6桁丸めの繰り上がりを含む`9999999`/`999999.5`/
   `1234567`を含む）を、`--small-rule gw`（新規実装、下記）で
   `predict()`に通し、**全49件が分析の予測文字列と完全一致**した
   （繰り上がりガードを要する`999999.5`(N=6)→`1E+06`、
   `1234567`(N=6)→`1.23457E+06`を含む。これは本予測器の
   `_significant_digits()`が丸め時の繰り上がり
   （`digits_int>=10**ndig`なら`e+=1;digits_int//=10`）を
   もともと実装していたためで、分析が指摘した「6桁版に必要な
   再正規化ガード」は既存コードに既に存在していた）。
3. **食い違いは見つからなかった。** 大きい側（`E<N`）は本予測器が
   v1から一貫して使っていた規則（`e<=ndig`）と数学的に同一で、
   こちらも変更不要だった。分析とこの独立確認のあいだに矛盾は無い。

### `--small-rule gw` の実装

`_small_side_fixed()`に`"gw"`を追加した。`k=-e`・`s=nsig`として
`k+nsig<=ndig`を計算するだけで、大きい側は`fout_format()`の既存分岐
（`e<=ndig`）をそのまま使う（分岐そのものを変更していない）。
**既定（`"sym"`）は変更していない**（これまでの全予測表
（l4-s4a v1/v2・l4-s4b・s4a事後・l4-s4c v1/v2・l4-s4d）とデータ行
一致することをselftestで確認済み）。

### l4-s4e の倍精度候補（RSTAR・RSTAR_B）

`GW16`は`--small-rule gw`をN=16で適用したものそのもの（`k+s<=16`）。
これに加え、次の2候補を追加した:

- **`RSTAR`**: `k<=1` または（`k+s<=16` かつ `k<=14`）なら固定。
  `GW16`より`k`の上限がもう1つ加わった、より制限的な候補。
- **`RSTAR_B`**: `k'<=1` または `k'+s<=16` なら固定。ただし`k'`は
  「丸める前の2進の値そのもの」（MBFの値、`GwNum.exact()`が返す
  厳密有理数）の10進指数`E'=floor(log10|v|)`から計算する
  （`k'=-E'-1`）。表示する有効桁数`s`は丸め後の値のまま。
  `_decimal_exponent()`（既存関数、丸めを経ない厳密比較）を
  `fout_format()`内で`av`（丸め前の絶対値）に直接適用して`E'`を得る。

`k'`（丸め前）と`k`（丸め後）がずれるのは、丸めによって桁上がりが起き
10進指数が変わる場合（例: `9.9999999999999995×10^-16`のような値が
丸めで`1.0×10^-15`に繰り上がるケース）に限られる。l4-s4dの分析
docstringにあるとおりの機序で、本予測器の`_significant_digits()`が
既に処理している繰り上がりと同種のものである。

### 動作確認（l4-s4e追加分）

`tools/l4_mbf_oracle_v2_selftest.sh`に、`--small-rule gw`追加後も
既定が32腕全件で変わらないこと、`gw`が分析4節の49件全部（倍精度21件・
単精度(a)(b)各14件）と一致すること、`rstar`/`rstar_b`が代表例で
`gw`と食い違う場合があること（`k<=14`の壁、丸め前後の`E`のずれ）を
追加した。

## 追記（2026-09-15、別セッション）— FOUTの桁生成をGWの手順どおりに再現（`--fout-algo gw`）

Z80実装担当がFIN/FOUTを自前手順で組んだところ、乱数入力の約2.6%で
予測器v2（exact）と最下位桁が1つずれた。近似#6（本文書「近似・推測
として区別する箇所」6番。`_significant_digits`が`Fraction`の厳密比較で
桁位置を決めており、`$FOTNV`の逐次ブラケットとは実装方法が違う）が
残っていたため、まず予測器側で「どちらがGWどおりか」を確定させる。

### `exact`と`gw`の違いの正体

`$FOTNV`/`$FOTCV`/`$SIGD`を命令単位で読み（docs/notes/
l4-gwbasic-fofmt-analysis.md 第1.3〜1.5節、l4-s4eで既に読了済みの範囲）、
2箇所の違いを特定した。

1. **丸め方式が違う。** `_round_half_even`（$ROUNSと同じ偶数丸め）に
   対し、`$FOTCV`/`$SIGD`自身の丸めは「整数でなければ`.5`を足してから
   切り捨てる」（`$VADDH`→`$VINT`、MATH2.ASM 1839-1853、$FOTCV側も
   同型）。**ちょうど半分（タイ）のとき常に切り上げになり、偶数丸め
   ではない。** これが乱数入力での食い違いの主因で、単精度6桁化した
   整数値がちょうど`…5`で終わる場合（例: `1720365`を6桁に丸めると
   `172036.5`）に必ず起きる。
2. **桁を整数部へ寄せるスケーリング自体が不正確。** `$FOTNV`は`$FOTB`
   テーブルの見積もりのあと`MDPTEN`（MATH1.ASM 1228-1249）で10のべきを
   掛け／割りするが、これは常に**倍精度**（56bit仮数）で行われ、しかも
   10のべき乗定数自体が倍精度に丸めた近似値である（10進のべき乗は
   2進で割り切れない限り厳密値ではない）。つまり厳密値を1回で丸める
   のではなく、「不正確な定数で1回スケーリングしてから丸める」という
   二段階の精度落としになっている。

`_significant_digits_gw()`はこの2点を再現する: `_scale_by_pow10_gw()`
で10のべきを`encode_mbf(・,56)`により倍精度へ丸めた定数として掛け／
割りし（演算結果自体も倍精度へ丸め直す）、`_round_half_up_int()`で
`.5`を足して切り捨てる。**大きい側(E>=0)は`$FOTNV`自体のスケーリング
だけが違い、固定小数点⇔指数の判定式（`E<N`/`k+s<=N`等）はexact/gw
共通のまま**（判定に使う`E`の算出自体は厳密なlog10ブラケットで、
これはl4-s4eで「テーブルの近似精度によらず数学的に確定する」と
確認済み。本追記で変えたのは桁の**生成**だけ）。

`--fout-algo gw`として`fout_format()`/`print_one()`/`predict()`に
追加した。**既定`"exact"`は変更していない**（既存の全予測表
（l4-s4a v1/v2・l4-s4b・s4a事後・l4-s4c v1/v2・l4-s4d・l4-s4e2種・
l4-s4f）とデータ行一致することをselftestで確認した。データ行が
変わった予測表は0件）。

### FINの近似の有無（確認）

$FINE（定数への指数適用）は$FOTNVと同じ`MDPTEN`を使っており、
「小数点以下の桁数」と「明示指数」の差（`net_exp`）が非ゼロなら
必ず呼ばれる（decimal pointがあるだけの`"1.5"`のような単純な小数も
`net_exp=-1`となり対象になる）。つまりFOUTと同じ不正確な倍精度
スケーリングがFINにも及ぶ可能性がある構造だと確認した。

**実験で確かめたところ、実害の出方はFOUTとFINで非対称だった。**
`_scale_by_pow10_gw()`を使い、厳密なリテラル解析（exact）とgw方式の
指数適用を比較する実験を行った（型へエンコードしたあとのバイト列を
比較。20000件ずつ）:

- **倍精度リテラル（`net_exp`を±30まで許した場合）**: 20000件中290件
  （約1.45%）で最終的なバイト列が食い違った（指数を大きく振った場合
  に限る。本予測器のl4-s4a〜fの実際の腕は`net_exp`の絶対値が小さい
  ものが大半で、そちらでは食い違いが出にくい）。
- **単精度リテラル（`net_exp`を同様に振った場合）**: 20000件中**0件**。
  倍精度（56bit）で一旦スケーリングしてから単精度（24bit）へ丸める
  ため、スケーリング由来のLSBノイズが単精度への丸めでほぼ必ず吸収
  される（「精度の余裕」がFOUTには無くFINにはある、という非対称性。
  FOUTは表示する桁数ぴったりでスケーリングするため誤差がそのまま
  最下位桁に出るが、FINは56bit精度で一旦計算してから24bitへ切り詰める
  ため、スケーリング由来の誤差が切り詰めで消えてしまうことが多い）。

**結論: FINには近似が残っており、倍精度の指数付きリテラル（`net_exp`
の絶対値が大きいもの）では実害が測定可能な水準である。** これを受け、
`parse_literal()`に`fin_algo`（既定`"exact"`）を追加し、`"gw"`のときは
指数適用を`_scale_by_pow10_gw()`で行うようにした。`predict()`は
`fout_algo="gw"`のとき`fin_algo`も自動的に`"gw"`にする（実際のGWが
FIN/FOUTどちらも同じ`MDPTEN`を使っているのに合わせた、1つのフラグで
両方を切り替える設計）。**既定は変更していない**ため既存予測表への
影響はない。

### `exact`と`gw`が食い違う打鍵可能な定数（探索）

N88想定の設定（単精度6桁・LEN7、倍精度RSTAR・LG16）で、一様乱数の
10進定数を`--fout-algo exact`と`gw`に通して比較した
（`tools/gen_l4_fout_exact_vs_gw_candidates.py`、
`docs/notes/l4-fout-exact-vs-gw-candidates.tsv`）。

- **単精度**（符号・小数点込みで数字最大7桁）: 60000件中20件目が
  12537件目で見つかった。**すべて丸め位置がちょうど半分（タイ）に
  当たる入力**で、上記「丸め方式が違う」の直接の帰結（スケーリングの
  不正確さは効いていない、単精度は`net_exp`が小さい範囲でしか試して
  いないため）。
- **倍精度**（`#`付き、数字最大16桁、明示指数なし）: 200000件中
  **0件**。上記のFIN実験と同じ理由（倍精度は56bit全体を使うため
  16桁への丸めでタイに当たる確率が単精度よりずっと低い）に加え、
  FOUT側のスケーリング不正確さも「明示指数なし」の入力では
  ほぼ効かない（`net_exp`が小さいため）。人為的に17桁ちょうどで
  タイになるよう仕込んだ入力（乱数の結果ではないため表には含めて
  いない）では実際に食い違いが起きることを別途確認済みで、「倍精度は
  原理的に食い違い得るが、素朴な乱数では極めて起きにくい」という
  位置づけになる。

### 動作確認（FOUT gw追加分）

`tools/l4_mbf_oracle_v2_selftest.sh`に、`--fout-algo gw`追加後も既定
（`exact`）が32腕全件で変わらないこと、既存の全9予測表とデータ行一致
すること、`gw`の丸め方式（.5を足して切り捨て、タイは常に切り上げ）が
偶数丸めと違う具体例（`1720365`を単精度6桁で丸めると、6桁目の直前が
ちょうど半分`172036.5`になり、`exact`は偶数丸めで`172036`
（`" 1.72036E+06 "`）・`gw`は常に切り上げで`172037`
（`" 1.72037E+06 "`）になる）で確認できること、`fin_algo`が
`fout_algo="gw"`のとき自動的に`"gw"`になることを追加した。

## 追記（2026-09-15、別セッション）— l4-s4h: 倍精度の丸めの半端(タイ)の候補

l4-s4gで単精度の半端はGW（絶対値の大きい側、常に切り上げ）が唯一残った
（コミット`e637eca`）。倍精度は乱数探しで候補0件だった
（`docs/notes/l4-fout-exact-vs-gw-candidates.tsv`参照。一様乱数では
16桁への丸めがちょうど半分になる確率が低いため）。l4-s4hはこれを
「16桁の整数に`.5`を付ければ2進でちょうど表せて、16桁への丸めが
ちょうど半分になるはず」という狙い撃ちで確かめる腕。

### exact_binary（H1〜H7、いずれも`yes`）

MBF倍精度は56bit仮数を持つ（IEEE754倍精度の53bitより3bit広い）。
16桁の整数部（`1234567890123456`〜`9007199254740992`はいずれも
50〜54bit程度）に`.5`（1bit）を足しても54〜55bit程度に収まり、
56bitの範囲内なので**H1〜H7すべて2進でちょうど表現できる**
（`GwNum.exact()`が返す厳密値と、10進で意図した値をFractionで直接
比較して確認した）。

**H6（`9007199254740992.5#`）は特に、IEEE754倍精度の限界
（`2^53=9007199254740992`、これに`0.5`を足すと54bit必要になり
IEEE754の53bit仮数では表現できなくなる、よく知られた境界）を
狙い撃ちした腕だが、MBF倍精度は56bit仮数を持つため、この境界では
まだ余裕がある（55bit必要、56bit以内）。** つまりH6は「IEEE754なら
表現できない値」を確かめる狙いだったと考えられるが、**MBFでは
表現できてしまう**、という結果になった。IEEE754の限界を本当に突く
腕が必要なら、`.5`を足す対象をもう1桁大きく（17桁の整数、または
`2^55`前後の値）取る必要がある。

### EXACTとGWで予測が分かれる腕・分かれない腕

`docs/notes/l4-s4h-double-tie-predictions.tsv`のH1〜H7のうち、
**EXACTとGWで予測が分かれるのはH1・H3・H4・H6・H7の5件**。
**H2・H5は分かれない。**

分かれる/分かれない理由は「16桁へ丸めたときの切り捨て側（下側）の
整数の最下位桁が偶数か奇数か」で説明できる。EXACT（偶数丸め）は
タイのとき「下側」「上側」のうち偶数の側を選ぶ。GW（常に切り上げ）は
タイのとき常に「上側」を選ぶ。したがって:

- 下側の最下位桁が**偶数**（例: H1の`…456`は6で偶数、H3の`…000`は
  0で偶数、H4はH1の符号違い、H6の`…992`は2で偶数）の場合、
  EXACTは下側に留まりGWは上側へ進むので**両者が食い違う**。
- 下側の最下位桁が**奇数**（H2の`…457`は7で奇数、H5の`…333`は
  3で奇数）の場合、EXACTも「上側が偶数なので上側へ進む」ことになり、
  GWの「常に上側」と**結果が一致してしまう**（食い違わない）。

H7（`1234567890123456#+.5`、算術演算での構成）はH1と数値的に同じ値
になるため、H1と同じ理由（下側`…456`が偶数）で食い違う。

**結論: この5腕（H1・H3・H4・H6・H7）は、l4-s4gで確認された「単精度は
GWが残る」という傾向が倍精度でも成り立つかを測るのに使える。H2・H5は
（2進でちょうど表せるタイであるにもかかわらず）EXACT/GWどちらの規則
でも同じ予測になるため、この2腕では規則を区別できない。**
