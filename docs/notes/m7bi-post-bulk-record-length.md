# m7bi: バルク直後のレコード境界を2通りの窓で検算する

測定日: 2026-08-19

## 情報境界

新規測定は行っていない。既存の伏せ字済みログ
`measurements/m6g-d0-boot-run{1,2}.iolog.txt.gz`（公式ROM一式・公式diskA
（使い捨て複製）を**実行して**得た測定。読んでいない）を再解析した。
本稿・解析器・出力に `$FB`/`$FC`/`$FD`（データポート）の値は一切登場しない
——出しているのは件数・run長・clock位置・`$FE`/`$FF`（フェーズコード。
データポートではないため伏せ字対象外）だけである。解析器
`tools/analyze_record_boundaries.py` は入力ログのデータポートが実際に
伏せ字されているかを自分でも検査し、されていなければ解析を拒否する。

## 1. 背景

`docs/notes/m7bh-post-bulk-read-coordinates.md` で、公式のバルク直後の
最初のREADが**受信5件の時点**で行われており、自作の6バイトレコード規則
（m7ax）とは違う区切り方をしていることが分かった。ただし窓（=何をもって
「1レコードの区切り」とするか）を1通りしか見ていなかったので、
本稿は**独立な2通りの窓**で同じ結論が出るかを検算する。

- 窓(a): sub視点で、連続する`IN $FC`の間に`sub OUT $FB`か`sub OUT $FD`が
  割り込んだらそこでrunを切る（データ方向の切り替わりを検出する）。
- 窓(b): 1.12節で確定した`$FF`フェーズコード語彙のうち、RECVプリミティブの
  完了（`OUT $FF 0x0C`）の直後に**再アーム**（`OUT $FF 0x0B`）が来るかどうかで
  runを切る（続けて次のバイトを受け取る気があるかどうかを検出する）。

両者は見ている対象が違う（(a)は別ポートの出現、(b)は`$FF`の語彙）ので、
一致すれば結論の裏付けになり、食い違えばそこが未解明として残る。

## 2. 測定結果

`measurements/m6g-d0-boot-run1.iolog.txt.gz`（公式ROM一式での起動測定、
run1・run2の2本は同一条件の別実行）を
`tools/analyze_record_boundaries.py`で解析した
（`measurements/m7bi-record-boundaries-run{1,2}.txt`）。run1とrun2は
ラベル以外**完全に同一の出力**（決定論性の確認）。

`sub IN $FC`総数66件、バルク終端（最後の`sub OUT $FC`）以降。

| | 窓(a) | 窓(b) |
|---|---|---|
| run数（全体） | 25 | 27 |
| run長ヒストグラム（全体） | {1:16, 4:1, 5:5, 7:3} | {1:16, 2:2, 4:1, 5:7, 7:1} |
| バルク後のrun長（出現順） | [5, 1, 1, 1] | [5, 1, 1, 1] |

**全体のヒストグラムは窓(a)(b)で不一致**（27件対25件。差はバルク**前**の
runの切れ方——窓(b)は再アーム有無という細かい基準で、バルク前のどこかを
窓(a)より多く分割している）。一方、**バルク後のrun長は両窓とも
`[5, 1, 1, 1]`で完全一致**する。

バルク後の各runについて「run終了後に最初に来たsubの行動」も両窓で一致した:

- run1（長さ5）終了後 → `sub OUT $F8`（TCコマンド。再アームせずFDCコマンド
  列へ入る。`docs/notes/m7bh-post-bulk-read-coordinates.md`が見た「5バイト目の
  あと再アームなし」の再確認）
- run2〜4（各長さ1）終了後 → いずれも`sub IN $FE`（待ちループへ）

## 3. 結論

m7bhの中心的な観測——**バルク直後の最初のREADは受信5件の時点で行われ、
5件目のあと再アームしない**——は、窓の取り方を変えても崩れなかった。
これで「窓の取り方次第で結論が変わった」というm7bhの経緯（比較の窓を
「READ直前の6バイト」から「バルク後の受信列」へ取り直して結論が反転した
経験）に対する検算が済んだことになる。

## 4. まだ確定していないこと

- **公式のC=18の出所**（m7bhから持ち越し。このレコードの中には見当たらない）
- **5バイトレコードの各位置と(C,H,R)の対応**（種別・値を見ていないので、
  「5バイト目 = R」といった対応は本稿だけでは決められない）
- **`kind 0x01 → 5バイト`という仮説**（m7bgは6バイトレコードの種別が
  すべて0x01であることを確認したが、「5バイトレコードも種別0x01か」
  「種別バイトの位置がバルク直後だけ違うのか」は未検証）
- 全体のrun長ヒストグラムが窓(a)(b)で食い違う理由（バルク**前**側。
  適合条件には影響しないため優先度は低いが、未解明のまま残す）

**推測で実装しない。**

## 5. 次の一手

値まで見る再測定（`PC88_REF_ROM_DIR` / `PC88_REF_DISK_DIR`が要る）で、
5バイトレコードの各位置と(C,H,R)の全数位置対応を取る。

## 6. この節の教訓

**窓を変えても結論が崩れないことを確かめてから、結論を確定として扱う。**
m7bhでは窓を変えたら結論が反転した経験があったため、今回は最初から2通りの
独立な窓を実装し、両方で同じ場所（バルク後run長`[5,1,1,1]`・再アームなし）
に行き着くことを確認してからノートに書いた。
