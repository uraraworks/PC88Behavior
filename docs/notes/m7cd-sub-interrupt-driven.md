# m7cd: 自作subへ有限ポーリング併用の割り込み受理を実装

実施日: 2026-08-23

## 1. 根拠と設計判断

根拠は仕様書1.40節と、その測定根拠であるm7ccだけである。公式subの
割り込みモード・ベクタ・レジスタ退避法はI/Oログから確定できない。
従って、それらを公式と同じだとは扱わず、自作subの実装自由度として
IM 1を選んだ。IM 2の表を持たず`0x0038`の1ベクタだけで済み、残り66バイト
だった2KBフェッチ窓へ収めやすいためである。

`0x0038`は変更前コードで`RECV_BYTE`の末尾RET直後、`RECV_FIRST_ARMED`
入口と同じ番地だった。この境界へAF保存→`IN $FA`→AF復元→RETIの6バイトを
挿入し、後続コードをずらした。前段の命令長が変わった場合は生成時の番地検査で
失敗させる。リセット直後のDI、スタック設定、PIO起動交換は変えず、FDC初期化の
直前にIM 1を設定する。

## 2. 待ち構造とタイムアウト

`FDC_IN`/`FDC_OUT`の`$FA`有限ポーリング、`0x0400`回上限、方向食い違いの
即時中断を残した。RQM/DIOが目的方向になった後だけEI→NOPを置き、要求中なら
NOP直後に受理する。ハンドラは再EIせず、復帰後に主線が従来の`IN/OUT $FB`
を1件だけ実行してDIする。割り込みが来なくても同じ`$FB`アクセスへ進み、
HALTは使わない。

最初の試行ではFDC初期化前に常時EIし、ハンドラも再EIした。この構造は要求が
残る間にハンドラへ再入し続け、自作mainの受信が0件になったため不採用とした。
許可区間を転送直前へ限定し、ハンドラから再EIしない現構造では通常応答が完走した。

EIは正常転送分岐にしか無い。タイムアウトと方向食い違いはその手前で従来どおり
`FDC_ABORT`を立て、必要なら`FDC_TIMEOUT_MARK`を出し、`$FB`へ進まない。
`--break-fdc-timeout-reads-anyway`はタイムアウト1件と直後`IN $FB`1件を再現し、
正常版は同じ強制条件で直後`IN $FB`0件だった。`disable_fdc_timeout_mark`を含む
生成経路も単独・`break_fdc_timeout_reads_anyway`併用の両方がフェッチ窓内で
生成できた。`verify_l3.sh`が持つ全故障注入の検出も維持した。

## 3. I/O外形

`$FE/$FF/$FC/$FD`を発行する既存命令は変更していないため、その順序・回数・値は
変えない設計である。変更前コミットba632c1から生成したROMと変更後ROMを、同じ
自作main・自作ディスクで各120フレーム走らせて比較すると、sub側4ポートの
`(方向,ポート,値)`列はともに4121件で全件一致した。`$FB`も883件、`$F7`は4件、
`$F8`は10件で列が全件一致した。割り込みハンドラの`IN $FA`だけが919件から
1713件へ794件増えたため、FDC側I/O外形はこの点だけ変わる。同じ変更後ログの
共通clock解析は次の結果だった。

| 項目 | 件数 |
|---|---:|
| sub割り込み受理 | 794 |
| 直前main I/O | 0 |
| 直前sub `IN $FA` | 781 |
| 直前sub `OUT $FB` | 13 |
| 直後sub `IN $FA` | 794 |

従って適合条件3はこの自己ハーネスで判定可能になり、直前main 0件となった。
ただし公式外形は直前に`IN $FA`が現れないのに対し、自作は781件あるため一致しない。
主線のデータ転送、有限タイムアウト、mainとのハンドシェイクを変えないことを
優先した実装差である。1.40節の外形を新しい適合条件へ格上げしていない。

## 4. 検証

- 生成コード: 1982バイトから1996バイト。2KB窓の残り52バイト。
- `tools/verify_l3.sh`: rc=0。通常READ、WRITE、SENSE、タイムアウトを含む正常版が
  すべて完走し、既存の全故障注入は引き続き不一致として検出された。
- `tools/run_all_selftests.sh`: 外側を`LC_ALL=C`、`LC_ALL=ja_JP.UTF-8`に
  変えて各1回実行し、いずれも全32項目が期待rcどおり、NG 0件、Traceback
  0件。`conform_l3.sh`は両方とも公式環境なしのSKIPで、本体は未実行。
- 最初の全自己検査で、直前コミットm7ccのselftestに`$fault_rc`直後が全角
  括弧となるシェル変数境界違反を1件検出した。判定内容は変えず
  `${fault_rc}`へ明示境界化し、その後の両ロケール実走で解消を確認した。
- `tools/check_l3_cond3.py`: 自己ハーネスで受理794件、判定対象794件、
  直前main 0件。

`tools/conform_l3.sh`本体の条件1・2・3・4・5は、公式環境の環境変数が
このセッションへ渡っていないため実行していない。従って、条件1の5635件・
SHA-256、条件5のWRITE 8件・2112バイト・SHA-256、および公式main相手の条件3を
合格とは報告しない。今回の自己検証も自作mainと自作subの組合せなので、公式環境での
再実走を最終確認とする。
