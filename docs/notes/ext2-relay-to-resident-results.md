# ext2 — バンク側ルーチンから常駐部ルーチンをCALLする設計の可否 — 結果

記録日: 2026-09-19
根拠: 事前登録
[ext2-relay-to-resident-preregistration](ext2-relay-to-resident-preregistration.md)。
器具は`tools/harness/make_ext2_rom_test.py`・本走ランナー
`tools/harness/ext2_run.py`（いずれも本コミット）。

**使ったROMは全て自作**（`tools/harness/make_ext2_rom_test.py`が
`tools/asm/z80text.py`で組み立てたもの）。`private/`・公式ROMディレクトリは
一切参照していない。写し・生ログ（`--mem-write-log`・`--int-log`）は
リポジトリ外のscratchpadに置き、本ノート作成後に削除した。本ノートに
載せているのは自作ROMのRAMマーカー値・カウントのみで、公式ROM由来の内容は
一切含まない（CLAUDE.md禁止事項1-7のいずれにも該当しない）。

## 器具の不具合と修正（測定前に発見・修正済み）

初回実行時、Q2の腕（`call-b5`/`call-b6`）が200往復のうち1回も完走せず
（`completed=0`または`1`）、`call-b6`では`ACTIVE_HIT`が`26478`という
`--int-log`の総件数（499件）を大きく超える異常値になった。原因は
`make_ext2_rom_test.py`の`build_bank_q2()`で、バンク側の窓
（`0x6020`–`0x7FFE`の未使用領域）を`0xFF`（Z80では`RST 38h`相当）で
埋める際、`CALL RESIDENT_LONGLOOP_ADDR`（3バイト）+`RET`（1バイト）=
計4バイト（`0x0020`–`0x0023`）のうち、保護範囲の計算が
`range(0x0020, 0x0023)`（3バイトぶんしか保護しない）になっており、
`RET`本体（4バイト目、オフセット`0x0023`）が`0xFF`で上書きされていた。
これにより`RESIDENT_LONGLOOP`から戻った直後に`RST 38h`が実行され、
割り込みベクタ(`0x0038`)へ暴走的に再入し続けていた（`ACTIVE_HIT`の
異常な大きさと整合する）。`range(0x0020, 0x0024)`に修正し、修正後は
全腕が2走とも決定論的に一致する結果になった（下記）。この経緯自体が
CLAUDE.mdの「対照と故障注入」節の実例（器具側のバグが、あたかも
被測定対象〈設計そのもの〉が壊れているかのような結果を作った）である。

|---|---|---|
| G3 決定論性 | **真** | 全腕2走、下表のとおり完全一致。 |
| G4 陽性対照 | **真** | `call-b5`（割り込み無効ベースライン）が200/200一致、`ACTIVE_HIT==0`。 |
| 関門P | **真** | `call-b6`で`ACTIVE_HIT=390 >= 5`。判定を採用する。 |

| G6 故障注入 | **真** | `call-badadd`（`RESIDENT_ADD`をB+CからB-Cへ差し替え）で`MATCH`が200→0に落ち、判定ロジックに検出力があることを確認。 |

## Q1: バンク側から常駐ルーチンをCALLし、戻って、さらにバンク側から中継へRETできるか

腕`call`、2走とも完全一致:

| | walk1 | walk2 |
|---|---|---|
| COMPLETED | 200 | 200 |
| MATCH（結果が(B+C)&0xFFと一致した回数） | 200 | 200 |
| RESID_HITS（RESIDENT_ADDが実行された回数） | 200 | 200 |

- **200回すべてで結果が一致した** → `q1_call_result_matches_200` = **真**。
  毎回`B=ITER&0xFF`（0〜199で変化）・`C=5`固定という異なる入力を使い、
  単に「同じ固定値が返る」ことの取り違えを避けている。
- **RESID_HITSが200と一致**（常駐部の`RESIDENT_ADD`が実際に200回実行
  されたことのRAMカウンタによる独立確認） → `q1_resident_hit_count_matches`
  = **真**。
- 対照（G6）: `RESIDENT_ADD`の演算をB-Cへ差し替えた腕`call-badadd`では
  `MATCH=0`（`COMPLETED=200`・`RESID_HITS=200`は変わらない）。判定ロジック
  （結果の値そのものを照合している）に検出力があることを確認した。

**結論: バンク側ルーチンが常駐部(0x6000未満)のルーチンをCALLし、戻り、
さらにバンク側から中継(この測定では中継自体は単純化した直接CALLだが、
機構としては同じCALL/RET)へRETする、という3段のCALL/RETの往復は、
200回とも値まで一致して成立した。**

## Q2: 常駐ルーチン実行中（窓はバンクのまま）に割り込みが来ても正しく受理・復帰するか

腕`call-b5`（陽性対照、割り込み無効）・`call-b6`（本体）、2走とも完全一致:

| | b5 walk1 | b5 walk2 | b6 walk1 | b6 walk2 |
|---|---|---|---|---|
| COMPLETED | 200 | 200 | 200 | 200 |
| MATCH（窓ヘッダが期待どおり） | 200 | 200 | 200 | 200 |
| ACTIVE_HIT | 0 | 0 | 390 | 390 |
| --int-log 総件数 | 0 | 0 | 499 | 499 |
| ret_pcが窓の外(<0x6000)だった件数 | - | - | 499 | 499 |

- `call-b5`: `MATCH=200`・`ACTIVE_HIT=0` → `q2_no_interrupt_baseline_ok`・
  `q2_baseline_no_active_hit` ともに**真**。
- `call-b6`: `ACTIVE_HIT=390 >= 5`（関門P充足）。`MATCH=200`・
  `COMPLETED=200` → `q2_interrupt_during_resident_call_ok` = **真**。
  `ACTIVE_HIT>=5` → `q2_interrupt_actually_occurred`（1本目の証拠）=
  **真**。
- `--int-log`の`ret_pc`が窓の外（`<0x6000`）だった件数は**499件中499件**
  （全件）。これは「割り込みが発生した瞬間、PCは一度も窓の中には無かった」
  ことを独立ログから示す。`ACTIVE_HIT`（RAMフラグ、390件がバンク有効中の
  受理）と**組み合わせる**と——バンク有効中に実際に受理した390件のうち、
  そのときのPCが窓の中だったケースは0件（もしあれば`ret_pc`が
  `0x6000`–`0x7FFF`に入るはずだが、499件全てが窓の外だった）——
  「バンク有効中の割り込み受理は、PCが常駐部側（`RESIDENT_LONGLOOP`
  実行中）にあるときに起きている」ことが確認できる
  → `q2_ret_pc_outside_window_while_bank_active` = **真**（2本目の証拠）。
  **限界の明記**: この計測は`ACTIVE_HIT`（RAMフラグ由来）と
  `ret_pc`外れ件数（`--int-log`由来）をそれぞれ独立に集計したものであり、
  「バンク有効中に受理した1件1件のret_pcが窓の外だった」ことを1件単位で
  突き合わせる計装はしていない（`ret_pc`外れが499件全件＝100%なので、
  この場合は結論に影響しないが、次回以降に厳密な突き合わせが要る場面が
  あれば計装を追加する）。

**結論: 常駐ルーチン実行中（窓はバンクへ切り替わったまま、PCは
`0x6000`未満の常駐部コードを実行中）に割り込みが発生しても、ハンドラが
窓の外の固定番地に置かれ窓の中を呼ばない設計であれば、200往復すべて
正しく受理・復帰できた。** これは`ext1`の`q3_interrupt_during_window_ok`
（バンク側のコード自身が窓の中で実行されている間の割り込み安全性）を、
「PCが窓の外（常駐部）にある間、窓は有効なまま」という新しい組み合わせに
拡張して確かめたものであり、同じ結論（ハンドラが窓の外にあれば安全）が
この組み合わせでも成り立つことを示した。

## Q3: 陰性対照 — 呼び先を窓の中（メインROM側番地のつもり）にすると壊れる

腕`call-neg`、2走とも完全一致:

| | walk1 | walk2 |
|---|---|---|
| COMPLETED | 200 | 200 |
| NEG_VALS[0..3]（バンク0〜3で最後に観測した`0x6050`の返り値） | D0,D1,D2,D3 | D0,D1,D2,D3 |

バンク側の中継が`CALL 0x6050`を「常駐部と同じ固定の共有ルーチン」の
つもりで呼んだ場合、もし本当に固定の共有ルーチンであれば結果はバンク
番号に依らず一定のはずである。実際には**バンクごとに異なる値
（`0xD0+n`）が返り**、`NEG_VALS[n] == 0xD0+n`が4バンクとも成立した
→ `q3_window_target_is_bank_local` = **真**（陰性対照が「壊れた＝
バンク依存になった」ことそのものが合格。`ext1`のG5と同じ「対照が失敗
状態になることが合格」という扱い）。

**結論: 窓の中の番地を「常駐部の共有ルーチン」のつもりで呼ぶ設計は、
実際には現在有効なバンクの内容がそのまま実行されるため、意図した
共有ルーチンには到達しない。この呼び出し方は使えない（禁止のまま
確定）。**

## Q4: 常駐ルーチンがRAMの作業域・スタックを使っても窓に影響しないこと

腕`call`に同居。`RESIDENT_ADD`は`PUSH/POP HL`とRAMカウンタ
（`RESID_HITS`）を使う実装のまま、Q1の200往復すべてで窓復帰前
（ポート復元前）に窓ヘッダ`0x6000`を読み、期待値`0xA0+bankno`と
一致した回数（`WIN_OK`）を数えた。

| | walk1 | walk2 |
|---|---|---|
| WIN_OK | 200 | 200 |

200回すべて一致 → `q4_window_intact_after_resident_use_of_ram_stack` =
**真**。

**結論: 常駐ルーチンがRAMの作業域・スタックを使っても、窓の状態
（バンク切替の内容）には影響しなかった。** これはポートベースの切替
（`0x71`/`0x32`）とRAM/スタックが独立したハードウェア資源であることの
帰結であり、驚く結果ではないが、実際にそのとおり動くことを確認した。

## 未確定（この測定では埋めない）

- **バンク側から常駐部を経由して、さらに別のバンクへ跨って呼ぶ**設計
  （バンクA→常駐部ルーチン→バンクBのように、常駐部ルーチンの中で
  さらに別のEXT_BANK_CALLを行うような設計）は測定していない。今回の
  常駐部ルーチン（`RESIDENT_ADD`・`RESIDENT_LONGLOOP`）はいずれも
  ポート`0x71`/`0x32`に一切触れない前提で設計しており、この前提が
  崩れる場合（常駐ルーチンが自らバンクを切り替える場合）は対象外。
- **実機での挙動は未検証**（`ext1`と同じ限界）。
