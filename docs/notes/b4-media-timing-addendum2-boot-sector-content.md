# B4 追補2: 照合の自作媒体の (0,0,1) は 0xFF ではなかった（記述の訂正）

記録日: 2026-10-26
親: [b4-media-timing-preregistration.md](b4-media-timing-preregistration.md)、[b4-media-timing-results.md](b4-media-timing-results.md)

## 1. 訂正

事前登録第1節に「どちらも l3-disk-format 第4節のデータディスクで、(0,0,1) は全 0xFF」と書いたが、
**確かめずに書いた前提で、誤りだった。** 照合器具の修正の途中で分かり、生成器の出力を直接調べた（自作媒体。値の種類数だけを見た）。

| 媒体（生成器） | (0,0,1) のデータ |
|---|---|
| `D1.d88`（`make_m6fe_disk.py`） | 1種類の値で埋まっている（0xFF ではない） |
| `ascii.d88`（`make_m6fi_disk.py`） | 13種類の値。テキスト状のデータが入っている |

## 2. 結果への影響

- **P（Q1）の結論は変わらない。** P は「照合と同じ媒体を最初から入れた」ときの観測そのもので、BASIC に届かず
  (0,0,1) を読み直し続けた（51回）。どちらの媒体の値も l3-boot-sector 1.3節の5値（BASIC に届く値）に当たらないので、
  1.3節とも整合する。ただし「0xFF で埋めた掃引と同じ形」という予測の理由づけは不正確だった。
- **Q（Q2）は (0,0,1) を読まない**（読み回数 0）ので影響しない。
- **R（Q3）** は (0,0,1) を C9 で埋めた複製を使った。`ascii.d88` の (0,0,1) にあったデータは上書きされたが、
  LOAD の腕はドライブ2から読むので、照合の対象には入らない。R の画面は Q と全腕で一致しており、結論は変わらない。

## 3. 照合器具への含意

ドライブ1を空で起動して判定のあとで入れる形（l3-boot-sector 第3版 第5節）では、仕様どおりの自作 ROM は
起動を試みない（1.4節）ので、(0,0,1) の中身は結果に効かない。器具の側で (0,0,1) を書き換える必要は無く、
**書き換えない**（照合の媒体を、期待値を取ったときと同じに保つ）。
