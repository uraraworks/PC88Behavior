## 位置づけ(親からの指摘)

l4-s7aは(1)tie腕が4本と少ない、(2)残差2腕(`9.9!-3.3!`・`9.9!*3!`)が
10進小数オペランド(`9.9!`・`3.3!`)のREP01読み取り(FIN)の丸めと演算
そのものの丸めを切り分けられていない、という2点の指摘を受けた。
本ノートは**オペランドを単精度で正確に表現できる値だけ**(7〜8桁の
整数、`2^24`未満)に限定し、FIN側の丸めが一切混ざらない形で四則演算
そのものを再測定する。整数(`2^24`未満)は`tools/l4_mbf_oracle_v2.py`
のFIN(`exact`・`rep01`どちらでも同じ)で常に厳密に読める
(`_rep01_single_magnitude`は`net_exp==0`のとき反復乗算を1回も行わない
ため、丸めが発生しない)。

## オペランド制約の言い換え(手順1、数学的な制約の確認)

親は「7桁以内の整数(2^24未満)」と指示したが、**2^24=16,777,216は
8桁の数**であり、「7桁以内」と「2^24未満」は同じ集合ではない。本ノート
は括弧内の`2^24未満`を実際の制約として採用し、必要な腕では8桁の整数
(最大16,777,215)も使う。理由は以下の解析による。

### 加算・減算は"tie"(ちょうど半分)しか作れない

両オペランドが`2^24`未満の正の整数のとき、和は`2^25`未満に収まる。
和の値をSとし、Sの必要ビット数を24+Dとすると、D(丸めで捨てる下位
ビット数)は**必ず0か1**にしかならない(D=2以上にするには和が`2^25`
以上必要で、それには少なくとも一方のオペランドが`2^24`以上でなければ
ならず、オペランド自体が単精度で正確に読めなくなる)。D=1のとき、
捨てる1bitは0(丸め不要)か1(捨てる範囲の**ど真ん中**、必ずtie)の
どちらかしかない。**つまり2つの`2^24`未満の正整数の和からは、
「half+sticky」「half-epsilon」「false_tie(ガードバイト方式との
食い違い)」を作れず、作れるのは"tie"だけ**である。減算も同様
(2つの正の`2^24`未満整数の差は必ず`2^24`未満になり丸めが一切発生
しない——差を使ったtieは原理的に作れない)。

このため、減算のtieは「大きい正整数から**負の**整数を引く」
(`A! - (-B!)`、内部的には`MBF_ADD`へ符号反転して入る`MBF_SUB`の
経路をそのまま通る)という形で作る。数学的には`A - (-B) = A + B`で
加算と同じ構造のtieになるが、実際にBASICへ打つ式は`-`演算子
(`MBF_SUB`)そのものであり、加算の経路(`MBF_ADD`直接呼び出し)とは
別の命令列を通る。

### tie(丁度半分)には"偶数側/奇数側"で意味が違う

正しい丸め(round-half-even)とround-half-awayは、tieのとき**候補
(丸める前の24bit仮数)が偶数のときだけ**結果が割れる(even側は据え
置き、away側は+1)。**候補が奇数のときは、どちらの規則も必ず+1
(切り上げ)で一致する**(奇数の隣接偶数へ丸めるのがeven規則の定義
そのものであるため)。よって「偶数側」のtie腕だけがeven/awayを
判別でき、「奇数側」のtie腕は判別力が無い代わりに「tieは必ず
切り上げられる(切り捨てられることはない)」という対照になる。
本ノートは両方を用意し、この非対称性を結果ノートで明示する。

### 乗算・除算は`2^24`未満の整数だけで全カテゴリを作れる

2つの`2^24`未満の整数の積は最大約48bitになるため、tie・
half+sticky(半分+最下位スティッキーのみ)・half-epsilon(半分より
僅かに下)・false_tie(ガードバイト方式(`coarse8`)が偽のtieを
作る、D≥9で構成)のいずれも整数×整数の探索(scratchpad、コミット
対象外)で直接構成できた。除算は商が2進で有限桁にならないため
真のtieは(l4-s7aで確認済みのとおり)作れず、親の指示どおり
「半分に極めて近い(上下)」と「スティッキー型」だけを用意する。

## 候補

l4-s7aと同一(`tools/l4_mbf_oracle_v9_s7a.py`を無改変で再利用、新規
ツールは追加しない)。`even`/`away`/`trunc`/`coarse8`/`fmuls`
(乗算のみ)。「ガードビット1つだけ見てスティッキー無しで丸める」
候補は、厳密値(Fraction)を使う限り数学的に`away`と完全に一致する
(1bitだけ余分に見て切り上げ判定する操作は、厳密な remainder>=half
判定そのものと同値であり、近似の余地が無い——スティッキーの省略が
意味を持つのは`coarse8`のように**複数ビットの窓**を切り捨てる場合
だけ)ため、追加しない。この理由を候補として明示することで、
親の「必要なら追加」の判断に代える。

## 判定

- 加減算のtie_disc腕(8本)でeven/awayどちらが勝つか。l4-s7aの
  G1・G2・H1(away勝ち)と方向が一致するかを確認する。
- 加減算のtie_ctrl腕(6本)は、even==away(切り上げ)が的中する
  はず、という対照確認。
- 乗算のtie_disc/tie_ctrl(5本)、half_plus_sticky(3本)、
  half_minus_eps(3本)、false_tie(3本)で、l4-s7aの結論
  (単発乗算は正しい丸め、coarse8/fmuls棄却)が整数専用オペランド
  でも再現するかを確認する。
- 除算のhalf_minus_eps(2本、対照)・half_plus_sticky(2本)・
  false_tie(3本)で、coarse8が引き続き棄却されるかを確認する。
- l4-s7aの残差2腕(`9.9!-3.3!`・`9.9!*3!`)は、本ノートの整数腕で
  演算自体の丸め規則が確定すれば「FIN側の丸め起因」と判定でき、
  確定しなければ「演算自体にも未解明の要素が残る」と判定する
  (結果ノートで明記)。

## 手順5: 既存実装`src/l4_basic/mbf_single.asm`への申し送り(実装は変えない)

測定結果が出たあと、`MBF_ADD`(加減算共通)・`MBF_MUL`の既定経路・
`MBF_DIV`のそれぞれについて、本測定で確定した規則との異同を
**予測器上で**指摘する(実装コードは変更しない)。l4-s7aで指摘した
「`MBF_ADD`はコード上偶数丸めだが実測はaway寄り」「`MBF_MUL`既定は
粗いROUNS再現だが単発乗算の実測は正しい丸め」を、整数専用の再測定
でも支持されるかどうかで確定させる。
