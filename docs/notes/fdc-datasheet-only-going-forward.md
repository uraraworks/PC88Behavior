# FDC実装の根拠整理 — 今後はμPD765データシートのみに限る

作成日: 2026-08-12
対象: `src/l3_service/make_subrom.py` のFDC駆動部（`FDC_IN`/`FDC_OUT`/
`FDC_SENSE_INT`ほか）

## 経緯（隠さず書く）

コミット`ce3bd5b`（SENSE INTERRUPT STATUSの結果バイト数修正＋FDCステータス
待ちタイムアウト追加）は、コミットメッセージに明記したとおり
`vendor/quasi88-libretro/src/fdc.c`（GPLの第三者エミュレータ実装）を
参照して調べた。`fdc.c`のr_phase()テーブル（SNS_I行は2バイト、INVALID行
は1バイト）を突き合わせ材料として使い、修正内容自体の根拠づけに引用した。

`fdc.c`は公式ROMではなく、`docs/spec/l3-subrom.md` 2.1節・
`make_subrom.py`冒頭docstring「$FA/$FBのポート番号について」節が既に
`src/pc88sub.c`（ポート配置というハードウェアの事実）を確認済みと明記
しているのと同じ扱い——公式ROMや公式ディスクの中身ではなく、GPL公開の
第三者ソフトウェアである。読むこと自体はクリーンルーム規律の禁止事項
（公式ROM・公式ディスクの禁止）には触れない。

## それでも根拠をデータシート側に置き直す理由

`ce3bd5b`で見つけた欠陥（SENSE INTERRUPT STATUSの結果フェーズが
「保留中の割り込みが無ければST0の1バイトだけで終わる」）は、
**μPD765/8272データシートの規定だけで完全に説明がつく**。`fdc.c`の
テーブルはそのデータシートの規定をこのハーネスがどう実装しているかの
確認に過ぎず、`fdc.c`を見なくても導ける結論だった。

`docs/PLAN.md`第3節の主張（独立実装であること）は、実装のたびに
「測定で裏が取れる種類の情報だけを採る」（`CLAUDE.md`）という規律を
一貫して守れているかどうかにかかっている。FDCコマンド体系のように
**公開仕様（データシート）だけで完結する領域**では、GPL実装であっても
「読んだ」という事実そのものが由来の鎖に新しい環（このハーネス固有の
実装選択）を足してしまう。今回のSIS修正も、続く結果フェーズ終了判定・
タイムアウト時の中止（本コミット）の修正も、実際にはデータシートの
規定（RQM/DIOの意味、コマンドごとの結果バイト数）だけで導出できる
内容だった。**見る必要が無かったものを見た**、というのが正直な整理で
ある。

## 方針（今後）

- FDCの実装根拠は**μPD765/8272データシート**（`docs/spec/l3-subrom.md`
  が引用しているハードウェアの事実の分類、`CLAUDE.md`「資料の使い方」
  (a)）に限る。
- `vendor/quasi88-libretro`のソースは、**ポート番号のようなこのハーネス
  固有の配置の確認**（データシートには書かれていない、ハーネス側の
  アドレスマッピング）にとどめ、**コマンドの振る舞い・結果フェーズの
  規定の根拠には使わない**。
- 本コミット（結果フェーズ終了判定・タイムアウト時の中止の修正）は
  `fdc.c`を参照していない。RQM/DIOの意味とコマンドごとの結果フェーズの
  規定（μPD765/8272データシート）だけで導出した。

## なぜこの整理が要るか

後から由来を問われたとき、「公式ROMを見て書いたROMか、データシートを
見て書いたROMか」の違いは大きい。`fdc.c`はGPLソフトウェアであって公式
ROMではないが、**見なくても導ける結論のために見た**という事実は、
「測定で裏が取れる種類の情報だけを採る」という規律の運用としては
緩みだった。次回以降、同種の欠陥調査でも先にデータシートだけで説明が
つくかを試し、それで足りるならハーネスのソースは開かない。
