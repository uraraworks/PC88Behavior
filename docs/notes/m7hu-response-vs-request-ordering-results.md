# m7hu: 要求の差と応答の差はどちらが先か — 結果

実施日: 2026-09-07

## 位置づけ

[m7ht](m7ht-response-vs-request-ordering-preregistration.md)が事前登録した
測定の結果である。事前登録は測定開始前に単独コミット（`9453a64`）してあり、
本稿では窓・段階・中止規則・判定規則を後から動かしていない。`src/`は本稿では
変更していない（`tools/`には事前登録どおり応答run抽出器を追加した）。

**結論を先に書く: 主判定はE3（比較不能）である。** 窓内の応答runは、条件O
（18本）と条件M（15本）で**本数が揃わず**、run長の並びも添字14で食い違った。
事前登録の判定規則は「run数またはrun長が揃わなければE3」と定めており、
それに従う。**したがって「要求の差と応答の差のどちらが先か」は、本稿では
決まっていない。**

**ただしE3の中身は「まったく比べられなかった」ではない。** 応答run 0〜13は
**内容が完全に一致**しており、食い違いは添字14の1本——**大量転送のrun**——で
起きている。そして**本稿の窓はその大量転送の途中で切れている**。
これは測定の設計上の欠陥であり、後述する。

## 段階1: 対照の妥当性を、新しい比較対象について取り直した

「受信run（要求）を動かす」ことを確認したものであって、応答runを動かすことは
確認していなかった。比較対象が変わった以上、対照の妥当性も取り直す——
`m7hq`の教訓の直接の適用である。

| 比較 | 結果 |
|---|---|
| 条件M vs 条件M+arm 9（窓内の応答run） | 応答run数 15→**77**、最初に食い違うrun番号=4、不一致数264 |

**arm 9は応答runを実際に動かした。** よって有効な対照として採り、段階2へ
進んだ（中止規則には該当しなかった）。

## E3の中身（判定ではなく記述）

事前登録の`ambiguous`と同じく、E3も「揃わなかった」で畳むと中身が消える。
数え直した（値は出していない）。

| 項目 | 公式 | 混成 |
|---|---|---|
| 応答runのrun長の並び | `[1,1,1,1,256,1,1,256,1,1,1,1,256,1,5632,1,256,1]` | `[1,1,1,1,256,1,1,256,1,1,1,1,256,1,4759]` |
| run 0〜13 の内容 | **完全一致**（値・run長とも） | 同左 |
| run 14 の run長 | 5632 | 4759 |
| run 14 の開始clock／終端clock | 44470／134906 | 58187／**153707** |

**言えること:**

- **応答run 0〜13は内容が完全に一致している。** 食い違いは添字14の1本だけで
  ある。
- 添字14は**大量転送のrun**（run長が4桁）であり、他のrun（1または256）とは
  桁が違う。
- **混成側のrun 14の終端clockは153707——窓の終端そのものである。**
  すなわち**このrunは窓の境界で切られており、本来の長さは分かっていない。**
  run長5632対4759という差は、**窓による打ち切りの結果かもしれない。**

**言えないこと:**

- **「応答が先に食い違った」とは言えない。** run 14の長さの差が実体なのか
  打ち切りの産物なのかが分からない以上、内容の食い違いがあったとも無かったとも
  言えない。
- したがって**E2a（応答の差が先）／E2b（要求の差が先）のいずれも主張しない。**
  `m7hs`が残した留保「1バイト差は原因か結果か」は、**未解決のまま残る。**
- run 0〜13は値が一致する一方、clockは公式・混成で一貫してずれている
  （run 0で7241対7259、run 13で18774対19728）。これは自作subの命令タイミング差
  であって内容の食い違いではない。**本稿はこのずれを差として扱っていない。**

## 事前登録の設計に、測定後に見つかった欠陥（次稿へ回す。本稿では直さない）

**窓の取り方が、比較対象の切れ目と合っていない。**

本稿の窓（終端clock=153707）は、`m7hs`が使った**要求側**の基準——公式の分岐段の
SEEK発行clock——から決めた。要求（受信run）はこの位置で自然に切れるが、
**応答run（大量転送を含む）はこの位置で切れる保証が無い。** 実際、混成側の
run 14はちょうど窓の境界で切断されている。

**要求側の基準で切った窓を、そのまま応答側に流用したのが誤りである。**
事前登録は「窓の終端clockは条件O側の分岐段から求め、条件Mにも同じclock値を
使う（両条件で別々に求めると窓がずれる）」と書いており、両条件で同じclockを
使う点は正しかったが、**その窓が応答runの境界を割らないかを確認していなかった。**

**本稿では窓を取り直さない。** 測定後に窓を動かせば事前登録である意味が無い。

なお、`m7ht`が事前に書いた「抽出器の捉え漏れがあればE1へ偏る」という留保は、
本件には当たらない（E1ではなくE3になった）。**偏りの向きを事前に書いておいた
ことで、出た結果がその偏りによるものかどうかを後から判定できた。**

## 次に何を測れば絞れるか

1. **窓を応答runの境界に合わせて取り直す。** 具体的には、窓の終端を
   「公式の分岐段のSEEK発行clock」ではなく、「**そのclock以前に完了している
   応答runのうち最後のものの終端clock**」とする。こうすれば両条件とも完結した
   応答runだけを比べられる。この定義は条件O・条件Mで別々に求めると窓がずれる
   ため、**公式側で求めた値を両条件に使う**という本稿の方針は保つ。
2. **1で窓を直しても、混成側のrun 14が窓内に収まらない可能性がある**
   （大量転送の開始clockが公式58187対混成44470とずれているため）。その場合は
   「窓内に完結した大量転送runを両条件とも含められない」ことになり、
   **大量転送runを比較対象から外すか、大量転送の完了まで窓を延ばすか**を
   事前登録で決める必要がある。延ばす場合は分岐点より後ろへ出るため、
   「場面が揃っている」という前提が崩れる——**この緊張関係を次稿の事前登録で
   明示的に扱う。**
3. `PLAN.md`が既に記録している「公式sub13593件に対する自作sub13362件の受理件数差」
   は、本稿の添字14（大量転送）と同じものを見ている可能性がある。**次稿では
   この既知の差との関係を先に確かめる**（同じ現象を二度別名で追わないため）。

## 開示

- 応答run抽出器の実装と自己検査の拡張をサブエージェントへ委譲した。委譲したのは
  実装のみで、測定・解釈・判定は親セッションが行った。委譲先の報告をそのまま
  採らず、親セッションで(1)自己検査を再実行してrc=0と全10項目を確認し、
  (2)`stage3`の出力経路を目視監査して、出力に到達するのが件数・真偽・添字・
  clockだけであることを確認した。
- 本稿は追加の実測を行っていない。`m7hl`・`m7hq`・`m7hs`で取得済みのログ
  （条件O・条件M・arm 9。いずれも独立2回のバイト一致を確認済み）を再利用した。
- **E3の中身を数え直す際、run 14の内容を先頭から突き合わせる比較は行っていない。**
  行えば「内容が一致するか」は分かるが、それは事前登録が`comparable=False`で
  止めると定めた比較を、判定が出た後に条件を変えて走らせることになる。
  **意図的に行わなかった**ことをここに明記する（次稿の事前登録で扱う）。
- 上記以外の手順逸脱・事故は無い。無言でSKIPした分岐は無い。測定中に
  `git stash`・ブランチ切替・`src/`の編集は行っていない。
