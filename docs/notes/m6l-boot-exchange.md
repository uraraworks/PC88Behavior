# M6l 起動時（バルク転送に入るまで）のmain⇔sub往復構造とFDC相関

測定日: 2026-08-12
対象: タスク指示「起動時の要求／応答の構造を、値を一切使わずに測る」。
`docs/spec/l3-subrom.md` 1.10〜1.14節がmain視点のSEND/RECVプリミティブと
バルク転送の起点・終端を確定しているが、**main→sub往復1回ごとの応答直前に
sub が実際にFDC($FA/$FB)を叩いているか**という、今回の実装方針
（「応答の値は測定から採らず、サブROMが実際にFDCを叩いて得た結果を
返す」）を裏付けるための相関はまだ確認されていなかった。

追加測定は行っていない。既存の `measurements/m6g-d0-boot-run{1,2}.iolog.txt.gz`
（diskA起動、共通クロック付き、決定論性は`docs/notes/m6-conformance.md`で
確認済み）だけを再解析した。**共通クロックを持つのはこの2本のログのみ**
（`measurements/m6c-sub-*` は「メインCPUとサブCPUは別々のZ80として並行に
走っており、互いのseq/frameを比較しても実際の前後関係にはならない」と
ヘッダに明記されている）。そのため本稿のFDC時間相関（4部）は d0-boot条件
に限定される。1〜3部（main側のSEND/RECV回数・順序、sub側の対応イベント
件数）はPC・ポート・件数のみを見ており条件非依存の一般的な手法だが、
今回時間の都合で d0-boot 以外への追試は行っていない（未確定として明記）。

解析器: `tools/analyze_boot_exchange.py`（新規）。
`tools/analyze_main_to_sub.py` の `parse_iolog`/`classify_transactions`/
`tx_kind` を import して再利用し、パーサ・SEND/RECV分類を二重実装して
いない。**使っているのは cpu/clock/kind/port/pc の各列のみで、value
（伏せ字済み）は一度も参照していない。**

再実行方法:

```
python3 tools/analyze_boot_exchange.py \
    --iolog measurements/m6g-d0-boot-run1.iolog.txt.gz \
    --label m6g-run1 \
    --out measurements/m6l-boot-exchange-run1.txt

python3 tools/analyze_boot_exchange.py \
    --iolog measurements/m6g-d0-boot-run2.iolog.txt.gz \
    --label m6g-run2 \
    --out measurements/m6l-boot-exchange-run2.txt
```

## 1. main側の往復構造（バルク転送本体に入るまで）

`measurements/m6l-boot-exchange-run1.txt` のラウンド表（値は一切含まない、
SEND/RECVの件数とPCのみ）を要約する。d0-boot条件では、main はバルク転送
本体（`docs/spec/l3-subrom.md` 1.14節、5632件の定常ループ）に入るまでに
**15ラウンドのSEND→RECV往復**を行う（最後の1ラウンドがバルク転送本体
そのものへの遷移）:

| # | SEND件数 | 応答 | 備考 |
|---|---:|---|---|
| 0 | 2 | 1byte | 最初の往復。両バイトともpc=`37F4`（後述） |
| 1 | 1 | 1byte | |
| 2 | 5 | 1byte | |
| 3 | 8 | 1byte | **FDCアクセスを伴う（4部）** |
| 4 | 2 | **256byte** | 最終2バイトがpc=`37F4`→`3811` |
| 5 | 1 | 1byte | |
| 6 | 6 | 1byte | **FDCアクセスを伴う** |
| 7 | 2 | **256byte** | 最終2バイトがpc=`37F4`→`3811` |
| 8〜10 | 1,5,5 | 1byte | |
| 11 | 8 | 1byte | **FDCアクセスを伴う** |
| 12 | 2 | **256byte** | 最終2バイトがpc=`37F4`→`3811` |
| 13 | 1 | 1byte | |
| 14 | 12 | **BULK(5632)** | バルク転送本体への遷移。**FDCアクセスを伴う（桁が違う）** |

**確定できたこと**:

- **周期は固定の「Nバイト送ってMバイト受ける」ではない。** SEND側の
  バイト数は1・2・5・6・8・12と要求ごとに変わり、応答も1バイトが
  大半（11/15ラウンド）で、3回だけ256バイト、最後の1回がバルク
  （5632バイト）になる。**「main が固定Nバイト送って固定Mバイト受ける
  周期を繰り返す」という単純な仮説は支持されない。**
- **256バイト応答が返るラウンドは、必ず直前の最終2バイトが
  `pc=37F4`→`pc=3811` の順で終わる。** `3811`は
  `docs/notes/m6-main-to-sub.md`が確定した「SEND終端マーカー候補」の
  PCで、本稿の観測でも**256バイト応答の直前にのみ、かつ例外なく**
  現れた（3/3件）。バルク転送本体への遷移（ラウンド14）の最終SEND列
  にも通常のSENDプリミティブ延長が続くことは`docs/notes/m6j-bulk-trigger.md`
  1.14節Q2で既報のとおり。
- **最初のラウンド（#0）だけ、応答が1バイトなのに送信2バイトが両方とも
  `pc=37F4`で、終端マーカー`3811`を伴わない。** 256バイト応答を伴う
  ラウンドとは明確にPCパターンが異なる、**別の（より短い）要求形式**
  であることが構造的に確認できる（4節・6節で1.11節との関係を整理する）。

## 2. sub側の対応イベント件数

main の SEND（`OUT $FD`、pc=`37F4`/`3811`）は、ポート番号としては
**sub の `IN $FC`** で受け取られ、main の RECV（`IN $FC`）は
**sub の `OUT $FD`** から送られている（両CPUとも「自分から見た送信は
`$FD`、自分から見た受信は`$FC`」という、CPUごとに対称なポート番号を
使う設計。$FC/$FDそれぞれに主→従・従→主の共有ラッチが1本ずつある、と
考えれば矛盾しない）。この対応関係は、7部の時刻ウィンドウ
（clock 7097-7225 付近、`measurements/m6l-boot-exchange-run1.txt`
生成に使った生ログの手動確認）で直接確認した。

起動シーケンス全体（ラウンド0〜14の時間窓、クロック7097〜148264）での
件数対応:

| | main視点 | sub視点 | 差 |
|---|---:|---:|---:|
| SEND→RX | main OUT $FD = 61件 | sub IN $FC = 58件 | **-3** |
| RECV→TX | main IN $FC = 6411件 | sub OUT $FD = 6413件 | **+2** |

**確定できたこと**: 件数はほぼ一致するが完全一致ではない。差の内訳は
pc別集計から説明できる:

- sub IN $FC は pc=`06F5` の1種のみ（58件）。main OUT $FD のうち
  pc=`3811`（終端マーカー、3件——256バイト応答ラウンド3回分）には
  **対応する sub IN $FC が見つからなかった**。終端マーカーバイトは
  sub側で明示的に「読む」動作を伴わない（あるいは別の経路で処理される）
  可能性がある。**推測で埋めず、未確定として残す（5節）。**
- sub OUT $FD は pc=`0789`/`079E`（256バイト応答の2種、384件ずつ＝768件）、
  pc=`071E`（1バイト応答、11件）、pc=`70E8`（2件）、pc=`70A2`（5632件、
  バルク境界）の内訳。**`70E8`/`70A2`はバルク転送の入口・境界に対応する
  sub側のPC**で、`docs/notes/m6j-bulk-trigger.md`のQ3が確定した
  「sub OUT $FCの境界用PC（`70E5`、3件）」とは別の変数（本稿は
  `OUT $FD`＝TX方向を見ている）。境界用の数バイトのズレは1.14節が
  既報の「入口2回・出口1回の境界」と同種の現象と解釈でき、矛盾しない。

## 3. バルク転送への接続

`docs/notes/m6j-bulk-trigger.md`（1.14節）が既に確定したとおり、バルク
転送本体（pc=`C265`/`C269`、5632件）への遷移は**通常のSENDプリミティブの
延長**として始まる。本稿のラウンド14（SEND12バイト相当→BULK応答5632件）
はまさにこの遷移そのものであり、1.14節の記述と矛盾しない。新たに
確認できたのは、**この最終SENDの時間窓（clock 19580〜57739、ラウンド12
終了から実に38159クロック＝十数フレーム相当）に、極めて大量のFDCアクセス
（$FA=12689件・$FB=12669件）が集中している**ことである（4節）。

## 4. FDC（$FA/$FB）との時間的対応 — 最重要項目

`measurements/m6l-boot-exchange-run1.txt`「ラウンド別」表から、応答種別
ごとにsub側FDCアクセス件数（値ではなく件数のみ）を抜き出す:

| 応答種別 | 件数(n) | $FA | $FB |
|---|---:|---|---|
| 1byte（うちFDCアクセスを伴う3件） | 11 | `[55, 0, 0, 285, 0, 285, 0, 0, 0, 285, 0]` | `[40, 0, 0, 281, 0, 281, 0, 0, 0, 281, 0]` |
| 256byte | 3 | `[0, 0, 0]` | `[0, 0, 0]` |
| BULK(5632byte) | 1 | `[12689]` | `[12669]` |

**確定できたこと**:

1. **FDCアクセスは応答の中ではなく、応答の直前のSENDラウンドの時間窓に
   起きる。** 256バイト応答・バルク応答のいずれの本体区間も
   `$FA`/`$FB`アクセスは**0件**。sub は応答を送り返している最中には
   FDCを一切触っていない。
2. **256バイト応答を生む3ラウンドすべてで、FDCアクセス件数が
   `$FA=285`・`$FB=281`と完全に一致する。** SEND側のバイト数の見かけ上の
   ばらつき（8バイト/6バイト/8バイト——1節参照、スケジューリング起因の
   run分断と考えられる）とは無関係に、**FDCアクセス件数は3回とも
   1件も違わず同一**だった。これは「256バイトを読むための固定FDC
   トランザクション（コマンド発行＋結果読み出しの決まった手順）が
   毎回同じ回数のポーリングで完了している」という見方と強く整合する。
3. **応答サイズが大きいほどFDCアクセス件数も大きい**（単発1バイト応答:
   0または55件、256バイト応答直前: 285件、5632バイトのバルク応答直前:
   12689件）。厳密な1バイト=1アクセスの比例ではない
   （285/256≈1.11、12689/5632≈2.25 — 比率自体は応答サイズごとに異なる）
   が、**単調にスケールしている**ことは確認できた。
4. **起動シーケンス全体でのFDCアクセス総数（$FA=13599, $FB=13552、
   clock 7097〜148264）は、各ラウンドの時間窓の合計と完全に一致する**
   （`measurements/m6l-boot-exchange-run1.txt`「FDCアクセスの集中度確認」
   節）。つまり**起動シーケンス中のsub側FDCアクセスは、例外なく
   いずれかの「応答直前のSENDラウンド」の時間窓の内側で起きており、
   ラウンド境界の外（応答本体の最中や、FDCアクセスを伴わないラウンドの
   最中）では一切発生していない。**

**この節の結論（タスクが指定した最重要項目）**: 「sub は FDC から得た
結果をそのまま main へ返している」という仮説は、**件数の対応だけからは
反証されず、むしろ支持される**。根拠は上記2〜4:
応答の直前・かつ応答直前だけにFDCアクセスが集中すること（2・4）、
同種の応答（256バイト）では毎回寸分違わぬFDCアクセス件数になること
（2）、応答サイズが大きいほどFDCアクセス件数も大きくなること（3）。
**ただし、これは「値」を一切見ていない構造的な相関にとどまる。**
「FDCが返した結果バイトの並びが、応答としてmainに送られたバイトの並びと
一致するか」は、値が伏せ字である以上この測定手法では確認できない
（伏せ字を緩めない、という方針上、確認する予定もない）。**構造的相関の
確認であって、値レベルの証明ではないことを明記する。**

## 5. 未確定のまま残すこと

- **pc=3811（終端マーカー）バイトに対応する sub側の明示的な受信動作が
  見つからなかった理由。** sub が読まずに捨てている、割り込みで別経路
  処理している、あるいは本稿の分類ロジック（pc=`06F5`固定）が
  この特定のケースを見落としている、のいずれの可能性も排除できない。
- **FDCアクセス件数と応答バイト数の正確な比例関係。** 285/256、
  12689/5632 のいずれも整数比にならず、単調な相関以上のことは
  言えない。
- **最初のラウンド（#0、応答1バイト、FDCアクセス55件）が、1.11節の
  256バイト読み出し要求や、他の1バイト応答ラウンドとどう違う独立した
  要求種別なのか。** PCパターン（終端マーカー3811を伴わない）は
  構造的に異なることを示すが、それが具体的にどんなFDCコマンド
  （ドライブ選択、シーク、モータ起動確認等）に対応するかは値が
  読めないため確認できない。
- **d0-boot以外の条件でも同じFDC相関が成立するか。** 共通クロックを
  持つログが d0-boot（m6g）にしか無く、時間の都合で追加測定は
  行っていない（0節）。

## 6. 1.11節（256バイト読み出し要求の固定8バイトヘッダ）との関係

`docs/spec/l3-subrom.md` 1.11節は、伏せ字前の測定（`m6-main-to-sub.md`
3.1節、2026-08-08時点）で、256バイト応答を生む要求の直前SEND列が
**値として** `02 01 00 <b3> <b4> 06 12 60` の固定8バイト形式であることを
確定している。本稿はこれを**反証も再確認もできなかった**:

- 本稿の1節で見たとおり、256バイト応答の直前にある「最後の"送信ラウンド"」
  の見かけのSEND件数は8・6・8とばらつく。これは
  `tools/analyze_main_to_sub.py`の`reconstruct_requests`と同様、
  **「連続する送信の合間に単発の1バイトRECVが挟まると、送信runが
  そこで機械的に分断される」という解析上の切り出し方の限界**であり、
  値を見ずにPCとclockだけから「本当の8バイトヘッダの境界」を
  再構成する手段が無い（値を使わずに済ませる、という本稿の制約上の
  限界）。
- 一方、4節で確認したFDCアクセス件数（285/281）は、SEND runの見かけの
  分断とは無関係に3回とも完全一致しており、**「何らかの固定サイズの
  要求」が3回とも同じ形で処理されている**ことは支持する。この点で
  1.11節の「固定8バイトヘッダ」という結論と矛盾はしない。
- **起動時の最初の往復（#0、SEND2バイト・応答1バイト、終端マーカー
  3811を伴わない）は、1.11節の256バイト読み出し要求とはPCパターンが
  明確に異なる、別の（より短い）要求形式である。** これは1.11節の
  8バイトヘッダ形式のバリエーションではなく、独立した要求種別だと
  構造的に判断できる。**混成ROM実走の分岐点（`docs/notes/m6k-mixed-divergence.md`
  第8部追記参照）は、まさにこの最初の往復（#0相当）で起きていた。**

**結論**: 1.11節の「256バイト読み出し要求は固定8バイトヘッダを持つ」
という記述自体は変更しない（値ベースの確定であり、本稿の値を使わない
手法では反証も再確認もできないため）。**追記すべきは、起動時最初の
往復がこの8バイトヘッダ形式とは別の、より短い要求形式である**という
構造上の事実である。

## 決定論性・検出力の確認

- **決定論性**: `measurements/m6g-d0-boot-run1.iolog.txt.gz` と
  `run2.iolog.txt.gz` の双方に `tools/analyze_boot_exchange.py` を実行し、
  `diff` で比較した。**ラベル文字列を出す1行を除いて完全に一致
  （0行差）。** `docs/notes/m6-conformance.md` で確認済みの決定論性と
  整合する。
- **検出力**: `tools/analyze_boot_exchange_selftest.sh`（新規、
  `tools/run_all_selftests.sh` に登録済み）で確認した。
  - a. 正常フィクスチャ（FDCアクセス無し1件・FDCバースト10件1件・
    5バイト応答1件を合成）で、ラウンド別FDC件数・集中度確認
    （全体=ラウンド合計）が期待どおりに出ることを確認。
  - b. clockシャッフルで、ラウンドBのFDC集中（10/10）が実際に崩れる
    ことを確認（真の時間窓を見ていることの検出力）。
  - c. main OUT $FD の pc を未知の値に破壊すると、ラウンドが1つも
    検出されなくなることを確認（pcベースのSEND分類が実際に効いている
    ことの検出力）。
  - 全項目OK。
