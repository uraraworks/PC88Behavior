# 自作の SAVE ,A が入力待ちの Ok を出していなかった（適合検査がすり抜けた）— 2026-10-02

## 何が起きていたか

`d061465`（SAVE ,A の取り込み）以降、自作 main は直接モードの `SAVE "…",A` が成功すると、
**通常の入力待ちの `Ok` まで出さずに**入力待ちへ戻っていた（`program.asm` の `BASIC_HANDLE_LINE` が
`SAVE_DONE_FLAG` を返して `Ok` を抑止）。l4-basic.md 第13.1節規則2「完了しても `Ok` の行を足さない」を、
「入力待ちの `Ok` も出さない」と読み違えた実装だった。

公式ROMでは、`cls:save "2:qsb",a`（m6f-j J-1 の打鍵）と `cls:kill "2:qsb"`（m6f-k K-1）の後の最終画面は、
**0行目が `Ok`（署名で一致を確認、本文は出していない）とファンクションキー行だけ**だった。
つまり規則2は「`LOAD`（第12.1節規則3）のように、入力待ちとは別の `Ok` を足すことはしない」の意味である。

## なぜ見逃したか

`tools/save_conform_check.py` の `screen_rows` は、最後の行を「入力待ち行は公式ROMと自作ROMで異なる」として
**中身を見ずに捨てて**いた。公式の画面（`Ok` 1行）も自作の画面（空）も、捨てた後は同じ空になり一致した。
同じ「最後の行を無条件に捨てる」形が `files_conform_check.py`・`load_conform_check.py` にもあった。

見つけたのは m6f-k の器具の関門 G5（最終画面に行が1つも無ければ止める）で、KILL の実装を同じ器具で
自作ROMに掛けたときに止まった。SAVE も同じ器具の形（m6f-j）で自作に掛けると止まることを確かめた。

## 直したこと

- `program.asm`: 直接モードの完了後は通常どおり `Ok` を出す（`SAVE_DONE_FLAG` は通信の完了判定にだけ使う）。
  `SAVE ,A`・`KILL`・`NAME` は入力待ちの `Ok` が1回出る。`LOAD` の2行目の `Ok` は従来どおり。
- `compare_screen_signatures.without_ready_prompt`: 捨てる最後の行が存在し、かつその行番号での `Ok` の署名で
  あることを要求する。SAVE・FILES・LOAD の照合器をこれに揃えた（期待値は変えていない）。陰性対照
  （行が無い・`Ok` でない・文字数違い・行番号違い）を各自己検査に足した。
- 委譲先は LOAD の E-3 で「捨てた後の1行も `Ok`」と要求していたが、実際は打った行（公式も同じ形）だったので外した。

## 教訓

「公式と自作で異なるから比較しない」と書いて捨てる行は、**何が異なるのかを確かめないと、欠落も一致に化ける。**
捨てる前に「何であるべきか」を署名で要求する。
