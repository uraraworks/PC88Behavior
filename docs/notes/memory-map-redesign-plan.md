# 自作ROMの RAM 配置の組み替え — 計画

状態: **計画**（2026-10-04）。実装はまだ無い。段ごとに測定・実装の結果をこの文書の末尾へ追記する。

## なぜ組み替えるか

- `l4-s9d`（[結果](l4-s9d-round1-results.md)、l4-basic 第20節）で、公式の利用者から見えるメモリは
  `clear ,a` が 0x8C00〜0xE400 の格子で受理され、`fre(0)=a−35098`、既定の上限は 0xE5FD と推定された。
  つまり利用者は 0x8xxx〜0xE5FD の約23KBを使え、`clear ,a` より上は利用者のデータ置き場になる。
- 自作は 0x8000〜0xF000 を作業領域で埋めており、プログラム本文は 0xEA00 からの 1KB しかない。
  - `l4-s9b`（PEEK・POKE）の公式腕は `clear ,49151` の上の 0xC000 を使うが、自作はそこを浮動小数点の作業領域に
    しているので 30腕中12腕しか一致しない（a0f958b）。
  - 1KB を超えるプログラムは**誤りも出さずに黙って保存されない**（program.asm `_pia_full`）。
- 棚卸し（作業メモ `PC88/tmp/memmap-work/inventory.md`、コミットしない）で分かったこと:
  - 固定のままでよい作業領域は約3,030B（文をまたいで保持するもの約235B、1回の処理の中だけのもの約2,790B）。
  - 動かすべき構造は11個（本文、変数表、配列表、長文字列、FOR、GOSUB、SAVE の画面捕捉、ON ERROR、RESUME、DATA、CONT）。
  - 番地の直書きが約54か所、同じ番地を別ファイルが独立に定義する別名 EQU が約75か所ある。
  - 本文を指す絶対番地（GOSUB・FOR の再開位置・DATA・CONT・RESUME・RESUME NEXT の文頭、計約23本）は、
    行の編集・NEW・LOAD で無効化されない。本文を動かす設計ではここが実害になる。
  - CPU スタックは `LD SP,0F000h` の1か所で、下限の検査は無い。式評価スタック（VAL_STACK）にも溢れ検査が無く、
    超越関数の作業域と番地が重なっている。

## 目標の配置

| 範囲 | 用途 |
|---|---|
| 0x8000–0x83FF | 使わない（テキストウィンドウに当たる範囲。公式での扱いは測っていないので避ける） |
| 0x8400– | **利用者領域の始まり**。本文 → 単純変数 → 配列 → 空き → 長文字列（上から下へ） → FOR/GOSUB スタック域 → 上限 |
| 〜上限（既定 0xE5FD 付近、`clear ,a` で下げられる） | 利用者領域の終わり。上限より上は利用者のデータ置き場で、自作は触らない |
| 0xE600–0xEFFF（2,560B） | 自作の固定作業領域（主に1回の処理の中だけ使うもの） |
| 0xF000–0xF3C7（968B） | CPU スタック（0xF3C8 から下へ） |
| 0xF3C8–0xFD27 | テキスト VRAM（変更しない） |
| 0xFD28–0xFFFF（728B） | 自作の固定作業領域（主に保持するもの） |

固定作業領域の置き場は 2,560＋728＝3,288B で、必要な約3,030B に足りる。余裕が小さいので、
1回の処理の中だけ使う領域どうしの共用（FILES と SAVE/KILL の FAT など、棚卸し第2節の候補）を併せて行う。

FOR/GOSUB スタックは、マニュアルの CLEAR の第3引数（FOR・GOSUB 用スタックの大きさ）に合わせて
利用者領域の上限の直下に置く（既定 512 相当は `l4-s9d` の推定）。

## 値まで公式に合わせるかどうか（決めたこと・決めないこと）

- **合わせる**: `clear ,a` の受理範囲と誤り番号、上限より上を自作が触らないこと、FOR/GOSUB の深さが
  第3引数で変わること、`fre(0)` が上限に対して傾き1で変わること。
- **合わせない（合わせられない）**: `fre(0)` の値そのもの（式の定数 35098）。自作は本文を文字のまま保存し
  （公式は内部形式が違うと考えられるが、測っていない）、変数の持ち方も違うので、同じプログラムでも
  使うバイト数が違う。`fre(0)` は「自作の空きバイト数」を正直に返す。
- **まだ決めない**: 0x8000–0x83FF を公式がどう扱うか、既定上限のちょうどの値（格子からの外挿。追補で詰める）。

## 段の分け方

各段は「既存の適合検査が全部通る」ことを関門にして進める。段の途中で止めても ROM は動く状態を保つ。

### 段A — 番地を1か所から配る（中身は変えない）

- 直書き約54か所と別名 EQU 約75か所を、1つの定義（ビルド時に生成する EQU 表）から配る形に置き換える。
- **番地の値は1つも変えない。** したがって**ビルドした ROM が段Aの前とバイト単位で一致する**ことを関門にする
  （一致すれば、置き換えの取りこぼしも書き間違いも無いことの証明になる）。
- 測定は要らない（挙動を変えないため）。

### 段B — 固定作業領域とスタックを上へ移す

- 段Aの定義表の値だけを変えて、固定作業領域を 0xE600– と 0xFD28– へ、CPU スタックを 0xF3C8 から下へ移す。
- 式評価スタックに溢れ検査を付け、超越関数の作業域との重なりを解く。
- 関門: 全適合検査（conform_l4・l3_editor・files/load/save/killname・strfunc/strcmp/inkey/hexconst/rnd 等の照合）。

### 段C — 行の編集・NEW・LOAD で何が消えるかを測る（測定）

- 公式で、行を挿入・削除・置換した後に、変数の値・CONT・RETURN（GOSUB の途中）・NEXT（FOR の途中）・
  READ の続き がどうなるかを測る（自分のプログラムの PRINT と ERR 番号だけで取れる）。
- 本文を動かすと古いポインタが実害になるので、その扱いを測定で決めてから実装する。

### 段D — 本文と変数・配列を利用者領域へ（動的配置）

- 本文を 0x8400 から置き、その後ろに単純変数・配列を続ける（件数の上限を外す）。
- 段Cの結果に従い、編集・NEW・LOAD で古いポインタを無効化する。
- 空きが尽きたら Out of memory（今の「黙って保存しない」をやめる）。

### 段E — 長文字列と SAVE の画面捕捉を利用者領域へ

- 長文字列のページ（256B）を、FOR/GOSUB スタック域の下から下向きに割り当てる（件数の上限16を外す。
  ページは固定長なので詰め直し〔ガーベジコレクション〕は要らない）。
- SAVE の画面捕捉（今は 0x9000–0xBFFF の 12KB 固定）を、配列の終わりから長文字列の下までの空きに置く。

### 段F — CLEAR と FRE

- `clear ,上限,スタック` を配置に反映し、`fre(0)` を実装する。既定上限と受理の境目を `l4-s9d` の追補で詰めてから。
- 関門: `expected_l4_peekpoke.tsv` の30腕（今は12腕）、`expected_l4_memlimit.tsv` のうち値まで合わせない腕を除いた形。

## 壊れやすいところ（棚卸しより）と対策

1. スタックが本文末尾を壊す → 段Bでスタックを本文と別の固定域へ。段Dの「空き」の計算にスタックを含めない。
2. 本文を指す古いポインタ → 段Cで測ってから段Dで無効化。
3. 直書き・別名 EQU → 段Aでバイト一致を関門に一掃。
4. 式評価スタックの溢れと重なり → 段Bで検査を付け、重なりを解く。
5. 長文字列ページの番地を変数レコードが持つ → ページを動かさない（割当てだけ動的にする）ので書き換え不要。
