# ext2 — バンク側ルーチンから常駐部ルーチンをCALLする設計の可否 — 事前登録

記録日: 2026-09-19
状態: 事前登録、測定前

## 位置づけ

[ext-rom-bank.md](../spec/ext-rom-bank.md) 第2節 制約3・第3節項3は
「バンク側(窓の中)のコードから、窓の中の他番地・常駐部の外側のルーチンを
直接CALLする設計は使わない(測定していないため)」としている。拡張ROM
バンクへ数値関数(SIN等)を載せる準備として、**バンク側ルーチンが常駐部の
既存ルーチン(単精度の四則演算等)をCALLして戻ってくる**設計を許可できるか
を測る。[ext1-rom-bank-preregistration.md](ext1-rom-bank-preregistration.md)
と同型の事前登録（自作試験ROMのみ、`private/`は参照しない、器具は
`q88measure`直叩き、腕ごとに2走・決定論性G3）。

対象は「main→bank」という既存のEXT_BANK_CALL方向ではなく、**bank→main
(常駐部)という逆方向のCALL**が、Z80の`CALL`/`RET`機構としてポート切替
(`0x71`/`0x32`)と衝突せず成立するか、という素のCPU動作の確認である
（`0x6000`–`0x7FFF`の読み出し切替そのものは`ext1`で確認済みで対象外）。

## 前提とスコープ

- 使うROMは全て自作（`tools/harness/make_ext2_rom_test.py`、新設）。
  `tools/asm/z80text.py`で組み立てる。`private/`・公式ROMディレクトリは
  参照しない。
- 器具は`tools/harness/frontend/q88measure`を直接叩く
  （`tools/harness/ext1_run.py`と同じ流儀のランナー
  `tools/harness/ext2_run.py`を新設）。
- 打鍵は使わない。ROM自身のコードが起動直後から手順を実行する。

## 試験ROMの設計

常駐部(`0x0000`–`0x5FFF`)に以下を置く（すべて`0x1000`番地以降、
`0x6000`未満）:

- `RESIDENT_ADD`（`0x1000`）: `B`+`C`を`A`へ返す単純な演算ルーチン。
  内部でRAMのワークカウンタ(`RESID_HITS`)を`PUSH/POP HL`経由で更新する
  （Q4「作業域・スタックを使っても窓に影響しない」を確かめるための
  意図的な作業域・スタック使用）。
- `RESIDENT_LONGLOOP`（`0x1010`）: 5385回の16bitデクリメントループ
  （`ext1`の`BANK_ROUTINE`と同じ見積り、約2.1フレーム分）で意図的に
  長時間化した簡易ルーチン。Q2（割り込み安全性）専用。
- `LOOP`（`0x0100`〜）: バンク切替→バンク側ルーチンをCALL→復元、を
  N回繰り返すドライバ（`ext1`の`BANKLOOP`/`LOOP`と同じ定型）。

拡張ROMバンク側（`N88_0.ROM`〜`N88_3.ROM`、各8KB、腕ごとに内容を変える）:

- 腕`call`（Q1・Q4用）: `0x6000`=識別ヘッダ(`0xA0+n`)、`0x6010`に
  `CALL 0x1000` `RET`（`RESIDENT_ADD`を1回CALLして戻るだけの中継）、
  `0x7FFF`=識別フッタ(`0xB0+n`)。
- 腕`call-b5`/`call-b6`（Q2用）: `0x6000`=識別ヘッダ、`0x6020`に
  `CALL 0x1010` `RET`（`RESIDENT_LONGLOOP`を1回CALLして戻る）、
  `0x7FFF`=識別フッタ。
- 腕`call-neg`（Q3陰性対照用）: `0x6000`=識別ヘッダ、`0x6010`に
  `CALL 0x6050` `RET`（**窓の中の番地を呼ぶ、禁止設計**）、`0x6050`に
  `LD A,(0xD0+n)` `RET`（バンクごとに異なる値を置く）、`0x7FFF`=
  識別フッタ。

## 観測方法

結果マーカーはRAM `0xC200`〜（`ext1`の`0xC1xx`帯と衝突しない専用の帯）。
`--mem-write-log --mem-write-range 0xC200-0xC22F`で採取する。Q2は
`ext1`と同じく`--int-log`も併用し、`ACTIVE_HIT`（バンク有効中受理回数）と
`--int-log`の`ret_pc`列の両方を独立の2証拠とする。自作データのみなので
値をそのまま報告してよい（CLAUDE.md禁止事項7の対象外、画面出力を一切
使わない）。

## 問い・腕・判定名（事前固定）

### Q1: バンク側から常駐ルーチンをCALLし、戻って、さらにバンク側から
中継へRETできるか（多数回、結果の値まで照合）

- **腕`call`**: `LOOP`が200回、毎回`B=ITER&0xFF`・`C=5`(固定)を積んでから
  `CALL 0x6010`（バンク側中継→`RESIDENT_ADD`→バンク側→`LOOP`、3段の
  CALL/RETが毎回成立する必要がある）。**期待**: 200回とも
  `A == (B+C)&0xFF`と一致し、`COMPLETED==200`
  → 判定名`q1_call_result_matches_200`。
- 対照: `RESIDENT_ADD`自身が実行された回数(`RESID_HITS`、RAMカウンタ経由
  で独立に数える)が200と一致すること →
  `q1_resident_hit_count_matches`（「値が一致した」だけでなく「実際に
  常駐部のコードを通った」ことの独立証拠）。

### Q2: 常駐ルーチン実行中（窓はバンクのまま）に割り込みが来ても正しく
受理・復帰するか（`ext1` Q3と同型）

- 関門P（`ext1`と同じ）: `ACTIVE_HIT`が5件未満の腕は`not_exercised`。
- **腕`call-b5`（陽性対照、割り込み無効）**: 200回往復、全て
  `q2_no_interrupt_baseline_ok`（窓復帰確認＝各往復末尾で窓ヘッダが
  `0xA0+bankno`と一致した回数`MATCH==200`）、`ACTIVE_HIT==0`
  → `q2_baseline_no_active_hit`。
- **腕`call-b6`（本体）**: 割り込み有効（ハンドラは常駐部固定番地、窓の
  外）。**期待**: `MATCH==200`かつ`COMPLETED==200`
  → `q2_interrupt_during_resident_call_ok`。`ACTIVE_HIT>=5`
  → `q2_interrupt_actually_occurred`（1本目の証拠）。`--int-log`の
  `ret_pc`が窓`0x6000`–`0x7FFF`の外（常駐部側、`RESIDENT_LONGLOOP`
  実行中に割り込まれた回）にある件数が1件以上
  → `q2_ret_pc_outside_window_while_bank_active`（2本目の証拠。**ext1の
  `ret_pc_in_window`とは逆に「窓の外」を数える**——今回はPCが常駐部
  〈窓の外〉にある間にバンクが有効のままという新しい組み合わせを
  確かめるため）。

### Q3: 陰性対照 — 呼び先を窓の中（メインROM側番地のつもり）にすると
壊れる／バンク側の内容が実行される

- **腕`call-neg`**: バンク側の中継が`CALL 0x6050`を呼ぶ。もし`0x6050`が
  「常駐部と同じ固定の共有ルーチン」であるなら、結果はバンク番号に
  依らず一定のはずである。**期待（壊れることの実演）**: 200回の
  各往復で`0x6050`から返る値をバンク番号ごとに記録すると
  (`NEG_VALS[0..3]`)、`NEG_VALS[n] == 0xD0+n`(バンクごとに異なる、
  バンク側ROMの中身がそのまま実行された値)になる
  → `q3_window_target_is_bank_local`（陰性対照が「壊れた＝バンク依存に
  なった」ことそのものが合格。`ext1`のG5と同じ「対照が失敗状態になる
  ことが合格」という扱い）。逆に4バンクとも同じ値になった場合は
  `q3_negative_control_did_not_break`としてNGを出す
  （判定スクリプト側に明記）。

### Q4: 常駐ルーチンがRAMの作業域・スタックを使っても窓に影響しないこと

- 腕`call`に同居（独立腕は立てない）。`RESIDENT_ADD`が`PUSH/POP HL`と
  RAMカウンタ`RESID_HITS`を使う実装のまま、Q1の200往復のうち**窓復帰前**
  （ポート復元前）に窓ヘッダ`0x6000`を読み、`0xA0+bankno`と一致した
  回数を`WIN_OK`で数える。**期待**: `WIN_OK==200`
  → `q4_window_intact_after_resident_use_of_ram_stack`。

## 器具・関門

- **G3 決定論性**: 各腕2走、マーカー値・`clock`列が一致。
- **G4 陽性対照**: `call-b5`のベースライン一致。
- **関門P**: `call-b6`で`ACTIVE_HIT>=5`未満は`not_exercised`。
- **G5 陰性対照**: `call-neg`（バンク依存値が出ることが合格）。
- **G6 故障注入**: `call`腕の判定ロジックを検証するため、`RESIDENT_ADD`を
  誤った演算（`B-C`）に差し替えた版で走らせ、`MATCH`が200から明確に
  下がる（判定ロジックに検出力があること）ことを確認する。

## 結果の行き先

測定後、`docs/spec/ext-rom-bank.md`第2節 制約3の改訂（「呼び先が窓の外
（常駐部）であり、かつ呼び先自身がバンク切替・EXT_BANK_CALLを呼ばない
場合に限り可」等、測定が支える範囲だけを許可へ変える）と第3節の該当項の
更新を行う。実装（`src/ext_bank/relay.asm`のコメント更新、
`src/build_main_rom.py`への「バンクから呼んでよい常駐ルーチン一覧」の
配置検査、`tools/ext_bank_selftest.sh`への検査追加）は測定・仕様更新の
後に行う（測定コミット→実装コミットの順序、CLAUDE.mdコミット規律）。

## 迷った点・設計判断

1. **Q2のret_pc判定はext1と逆向き**にした（「窓の外」を数える）。窓は
   有効なままPCだけが常駐部にいる、という`ext1`では扱わなかった組み合わせ
   を確かめる測定なので、証拠として意味のある列も逆になる。
2. **Q3は「共有ルーチンのつもりで呼ぶと実際にはバンク依存の内容が
   実行される」という壊れ方**を選んだ（`ext1`のB7＝ハングと同型の壊れ方
   ではなく、値の食い違いという別の壊れ方）。CALL先番地自体は有効な
   Z80コード（`LD A,n`/`RET`）なので暴走はしないが、意図した「常駐部の
   共有ルーチン」には到達しない、という設計上の罠をそのまま見せる方が、
   この測定の目的（バンク→常駐部CALLの許可条件）に直結すると判断した。
3. **G6の故障注入は`RESIDENT_ADD`の演算を変える**方式にした（`ext1`の
   G6はバンクの入れ替えだったが、今回の主張は「値が正しく戻ること」
   なので、判定ロジックの検出力はその値自体を誤らせて確かめるのが
   直接的）。
