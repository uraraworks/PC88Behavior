# m7aw: 交換#14 READ準備をテーブル駆動化して139バイト削減、陽性対照が2回空振りした話

作業日: 2026-08-18

## 情報境界

自作サブROMの書き換えと、その回帰確認のみ。公式ROM・公式ディスクは
**実行のみ**（適合テスト`conform_l3.sh`）。値は扱わず、件数とバイト数だけを
記録する。

## 0. なぜやったか

m7av（書き込み経路の実装）でコードが2027バイトまで伸び、サブCPUのフェッチ窓
0x0800 に対して**残り21バイト**しかなくなった。PLANに「次に足す前に削る」と
書いた、その削る作業。

## 1. どこにバイトが積まれているかを先に測った

ラベル区間ごとのサイズを出したところ、`_bulk_unit_done_2`〜`_5`
（交換#14のREAD#2〜#5の準備コード）が 67+69+67+36 = **239バイト**を占めて
いた。4回ぶんの同型コードが展開されており、READごとに違うのは
**参照する要求位置・セクタ数・格納先・Hの反転有無だけ**だった。

## 2. 書き換え

ROM上の6バイト表（`c_pos, r_pos, sectors, dest_lo, dest_hi, h_xor`）＋共通の
準備ルーチンへ置き換えた（m7apで要求グループ決定関数に対してやったのと同じ
手口）。ついでに2箇所を圧縮した:

- unit/head の生成を、分岐2本（`jr z` / `ld a,4` / `ld a,0`）から
  **`AND 1` → `RLCA` → `RLCA`**（bit0をbit2へ動かす）へ。
- `REQ_HDR` が256バイト境界に整列していることを使い、`LD L,A` だけで
  `REQ_HDR + 位置` を作る。

結果（LIMIT=4）: **2027 → 1888 バイト（139バイト削減）**。フェッチ窓の残りは
21 → **160バイト**になった。判定の順序・参照位置・生成するFDCパラメータは
第49版と同一で、意味論は変えていない。

## 3. 陽性対照が2回空振りした（今回いちばん重要な記録）

「適合テスト`[混成]`の5635件＋SHA-256がこの書き換えを見張れるか」を故障注入で
確かめようとして、**2回続けて空振りした**。

### 空振り1: 死んだ複製の側を壊していた

最初の実装では、READ表を**呼び出し側と表本体の2箇所に書いて**いた。
呼び出し側は `_idx` からラベル名を作るだけで、タプルの中身は**長さ以外
使っていない**。故障注入がその死んだ側に当たり、「壊したのにROMが1バイトも
変わらない」という形で発覚した。**ROMが変化したかを確認せずに
「注入したのに検出されない＝検出力が無い」と結論していたら、逆の誤りを
記録するところだった。**

→ 表を**単一の定義**（`BULK_READ_TABLE`）に統合して再発を止めた。

### 空振り2: 効かない壊し方だった

単一定義にしてから、表のエントリ2と3を入れ替えた。**ROMは変化したが、
適合テストは通った。** 2つのエントリは `r_pos`・`sectors` が同じで、
`c_pos` が参照する2つの位置も同じ値を持つため、読み出す座標が実質同じに
なる。違うのは格納先と`h_xor`だけで、同じ内容を別の場所に置き替えるだけの
入れ替えになっていた。**「表を壊した」ように見えて、ストリームは変わらない。**

### 効いた壊し方

- エントリ0の `sectors` を 14 → 13
- エントリ0の `r_pos` を 3 → 2

どちらも `[混成]` が **件数5635は一致するがSHA-256が不一致** として落ちた。
**この2つが、この書き換えに対する適合テストの検出力の証拠である。**

## 4. 教訓

- **故障注入は「成果物が実際に変わったか」を先に確認する。** 変わっていない
  なら、それは検出力の話ではなく注入の話。
- **同じ表を2箇所に書くと、片方が死んでいても気づけない。** 単一定義にする。
- **壊し方には効くものと効かないものがある。** 「壊したのに通った」を
  検出力の欠如と読む前に、その壊し方が出力を変えうるかを考える。

## 5. 回帰確認

- `verify_l3.sh`: 変化なし（書き込み経路の3項目が増えた以外は同一）
- `conform_l3.sh`: `[本番]`・`[混成]` とも 5635件・SHA-256一致、適合条件2・4も合格
- `run_all_selftests.sh`（公式環境つき）: 25本すべてOK
