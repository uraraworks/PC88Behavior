# m7hq: 分岐点直前の要求が公式と混成で同一かを、場面を揃えて測る — 結果

実施日: 2026-09-07

## 位置づけ

[m7hp](m7hp-scene-matched-request-comparison-preregistration.md)が事前登録
した測定の結果である。事前登録は測定開始前に単独コミット（`5260ff5`）して
あり、本稿では対象・判定規則を後から動かしていない。`src/`・`tools/`は
本稿では変更していない。

**結論を先に書く: 主判定はO（測定不能）である。** 事前登録した合格条件1の
故障注入対照——「`--break-drive-selector`を条件Mの代わりに置いたとき、
分岐位置または対照区間の比較結果が条件Mのときと変わること」——が
**通らなかった**。条件M-brokenの比較結果は、条件Mの結果と**1文字も
違わなかった**。事前登録は「変わらなければ判定Oとする」と定めており、
それに従う。

**比較そのものは動いており、差も1箇所見つかっている（後述）。だがそれを
D2として主張しない。** 差を検出できることが示せていない方法で「差が
あった」と言えば、`m7hl`以来この稿群が守ってきた合格条件の意味が無くなる。

## 判定に採らない観測（Oのため。記録だけする）

事前登録の手順どおりに比較した結果は次のとおりだった。**これは判定では
なく観測である。**

| 項目 | 条件M | 条件M-broken |
|---|---|---|
| 分岐段の候補数（公式／相手） | 4／4 | 4／4 |
| 候補のrun長（公式／相手） | [1,1,1,5]／[1,1,1,5] | [1,1,1,5]／[1,1,1,5] |
| `eq`が偽になった位置の数 | **1** | **1** |
| その位置 | 候補#3（0起点）のrun内位置4 | 同左 |

run長5の候補は、1.36節が確定した`0x02`類（run長5・直後READ）と同じ
分類に収まる位置にある。**差が出たのはその5バイトの最後の位置1つだけ**で、
先行する3本（run長1）は全一致だった。値は出していない。

**この観測をD2（要求が違う＝H1存続）として採らない理由**は上記のとおり、
故障注入対照が通っていないためである。

## なぜ対照が通らなかったか（原因の特定。これは判定の変更ではない）

対照が通らなかったのが「比較器が壊れている」からなのか「対照の選び方が
悪い」からなのかは、次の測定で切り分けられる。切り分けた。

| 項目 | 結果 |
|---|---|
| 条件Mと条件M-brokenの生ログ | 異なる（同一ではない） |
| FDCコマンド種別列の長さ | 71（M）／79（M-broken） |
| 共通部分での最初の種別差 | **無し**（Mの71件はM-brokenの先頭71件と一致） |
| 受信run総数 | 41（M）／49（M-broken） |
| 先頭から一致する受信run数 | **41**（Mの全41本がM-brokenの先頭41本と一致） |

**`--break-drive-selector`は、本稿が比較している量——分岐段までの
main→sub要求——を一切動かしていない。** 動かしたのはその後ろ（列が
71件から79件へ伸びた分）である。

**つまりこれは比較器の欠陥ではなく、対照が比較対象を迂回した事例である。**
`--break-drive-selector`は自作subのドライブ選択（FDCへ出す側）を壊す故障
注入であり、`m7hm`ではunit/head差13件としてよく効いた。しかし本稿が測って
いるのは**mainがsubへ送るバイト列**であって、subがFDCへ出すバイト列では
ない。**効く場所が違う故障を対照に選んだのは事前登録の誤りである。**

事前登録の時点でこの誤りに気づけたはずである——「差を検出できる方法である
ことの裏づけ」を要求しておきながら、**その裏づけに使う故障が、比較対象と
同じ量を動かすかどうかを確認していなかった**。

## 言えること・言えないこと

**言えること:**

- 場面を揃える設計（対比を「単発 vs 連続」から「公式 vs 混成」へ移す）は
  成立した。対照区間22本の受信runが全位置一致し、分岐位置は1.57節の
  56件目と一致した。**`m7hm`が残した宿題1（場面の交絡）は解消した。**
- 候補2本の同点解消を後知恵で決める必要も無かった。分岐段の候補数は
  公式・混成とも4で、順序込みの列としてそのまま比較できた。
  **宿題2も設計で回避できた。**
- 条件Mの決定論性を、生ログのバイト一致という最も強い形で初めて確認した。
- `--break-drive-selector`は、分岐段までのmain→sub要求を一切動かさない。

**言えないこと:**

- **要求が公式と混成で違うのかどうかを、本稿は主張しない。** 観測は
  「1位置だけ違う」だったが、その差を検出できることを示す対照が通って
  いない以上、D1・D2のいずれも主張しない。
- したがってH1（要求がレコード数を伝える）とH2（内部状態）の区別は、
  本稿でも付いていない。
- 観測された1位置が「レコード数」を意味するかどうかは、仮にD2が確定
  しても本稿の方法では言えない（`m7hl`が事前に書いたとおり）。

## 次に何を測れば絞れるか

**同じ比較を、比較対象を実際に動かす故障注入で対照を取り直せばよい。**
本稿の設計自体は成立しており、直すべきは対照1点である。

1. **main→sub要求を動かす介入を対照に使う。** `q88measure`には
   `--exchange-intervention RUN:MODE:VALUE`があり、これはsubがmainへ返す
   応答を差し替える。応答が変われば、mainが次に出す要求も変わりうる。
   **これが「比較対象と同じ量を動かす故障」の候補である。**
   次稿では、対照として使う前に「その介入が分岐段までの受信runを実際に
   変えること」を先に確認し、変えない介入は対照に採らない。
2. **対照の妥当性の判定を、事前登録の手順に組み込む。** 「故障注入Xを
   対照に使う」と書くだけでなく、「Xが比較対象の量を動かすことを先に
   確認し、動かさなければ対照を選び直す」という手順まで事前に書く。
   本稿の失敗はこの一手が抜けていたことに尽きる。
3. 上記が通れば、本稿の観測（1位置だけ違う）がD2として確定するか、
   対照を通した上で改めてD1になるかが決まる。

## 開示

- **事前登録した故障注入対照の選定が誤っていた。** 比較対象
  （main→sub要求）を動かさない故障を対照に選んだ。測定後にこれに気づいた
  が、**事前登録の判定規則に従って主判定をOとし、観測をD2へ格上げしな
  かった。** 対照を選び直して再測定することも本稿では行っていない
  （事前登録の範囲外であり、次稿の仕事とする）。
- 比較は使い捨てスクリプト（scratchpad配下、コミットしない）で行い、
  既存APIのみを呼んだ。新規ツールは作っていない。
- 条件Mのログは`m7hl`取得分を再利用し、決定論性確認のためrun2を新たに
  取得した（同一コマンド）。条件Oのログは`m7hl`取得分をそのまま使った。
- 上記以外の手順逸脱・事故は無い。無言でSKIPした分岐は無い。測定中に
  `git stash`・ブランチ切替・`src/`の編集は行っていない。
