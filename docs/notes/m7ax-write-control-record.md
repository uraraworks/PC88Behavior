# m7ax: 書き込み制御バイトの内訳を確定（論理トラックとセクタ）

測定日: 2026-08-18

## 情報境界

公式ROM一式・公式ディスク（diskAの使い捨て複製、複製側だけライトプロテクト
解除）を**実行して**測定した。読んでいない。生ログはリポジトリ外。
本ノートに載せるのは**件数・位置・種類数**だけで、値は1バイトも含まない。

## 0. なぜやったか

仕様書3節に「書き込み要求の制御バイトの内訳は未確定」が残っており、m7avの
実装はそのせいで**トリガをrunの長さだけ**で判別し、C/Hを「直前SEEKの目的
シリンダ」「`REQ_H`」という**たまたま一致していた別経路**から取っていた。

## 1. 変化を増やしてから測った

m7auの測定（1回のSAVE、WRITE 15件）では制御バイトの変化が乏しく、
着目した位置が2種類の値しか取らないため式を決められなかった。
**8回SAVEする条件**（`SAVE"TA"`〜`SAVE"TH"`）を新たに測り、
**WRITE DATA 64件**を得た。ここでも「データ部＝受信列の末尾ちょうど256
バイト」は **64/64** で成立した（m7auの15/15に加えて再現）。

## 2. 確定したこと

制御部の長さは、測定開始直後の1件を除き**すべて6の倍数**だった
（6が40件、12が16件、66が7件）。**6バイト単位のレコード列**である。

**データ部の直前6バイト（＝そのWRITEに対応するレコード）の末尾2バイトが
座標である。**

| 位置 | 内容 | 一致 |
|---|---|---|
| idx4（末尾-2） | **論理トラック = C*2 + H** | **63/63** |
| idx5（末尾-1） | **R（セクタ番号）** | **63/63** |

実装で使う向きでも確認した: **C == track>>1 が63/63、H == track&1 が63/63**。
値の種類は論理トラック8種（C 6種 × H 2種）あり、2値しか無かった
m7au時点とは違って**式を1つに絞れる分解能がある**。

idx0〜idx3 は**未確定のまま残す**（idx0は2種、idx1は1種、idx2/idx3は
レコード全体で見ると定数ではない）。推測で埋めない。

## 3. 実装を測定に寄せた

- C・H を **論理トラックから導く**（`C = track>>1`、`H = track&1`、
  `unit/head = drive0 | (H<<2)`）。第54版の「直前SEEKのラッチ」「`REQ_H`」
  依存をやめ、`FDC_SEEK` 入口のラッチ（`WRITE_C`）は削除した。
- 循環バッファの退避を**2段のシフトレジスタ**にして、データ部の直前
  1バイト（R）と2バイト目（論理トラック）の両方を取れるようにした。

コードは 1888 → **1903バイト**（窓2048に対して残り145バイト）。

## 4. 検証（公式環境不要）

`tools/check_l3_write.py` に**座標の検査**を足した——WRITE DATA の C/H/R が、
データ部の直前2バイトから導いた値と一致すること。`tools/verify_l3.sh` の
書き込みシナリオは **cyl=3 / sec=5**（非ゼロ座標）に変え、座標を取り違えたら
落ちるようにした。

陽性対照2種:

- `--break-write-data-window`（データ部の窓を1バイトずらす）→ 不一致で検出
- `--break-write-coords`（論理トラックをそのままCにしてHを0にする）→ 不一致で検出

公式環境つき `run_all_selftests.sh` 25本すべてOK（`conform_l3.sh` の
`[混成]` 5635件・SHA-256一致も維持）。
