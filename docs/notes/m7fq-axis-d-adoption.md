# m7fq: 軸Dを全条件測り直し、READ DATA 9段すべての正常終了を得て採用した

実施日: 2026-09-03

## 位置づけ

本稿は`m7fp`が指示した「軸Dの六条件すべてを測り直して判定する」を実施した結果である。
`m7fm`は条件5（段0〜段26の外形不変）をnoと記録して不合格・未採用としたが、`m7fp`は
その条件5の判定内容（段4・段6のunit/head変化、SEEK 11段すべて条件O一致）が
既存ログの再確認で再現しないことを示した。**`m7fm`のノート本文は書き換えていない。**
訂正の事実は`m7fp`に記録済みであり、本稿はその後に全条件を新規に測り直したもの
である。

段番号は0起点で統一し、種別名を併記する。`--list-all-stages`が出す番号は1起点
なので換算が要る（0起点段27(SEEK)＝1起点段28、0起点段30(READ DATA)＝1起点段31）。
**この起点の食い違いが`m7fm`の誤りの原因として疑われている**（`m7fp`が確認した、
ツールの「段N」が1起点である一方`m7fm`本文が「0起点」と明記している食い違い。
ただし`m7fp`はこれを`m7fm`の誤りの原因だと断定していない。本稿もそれを引き継ぎ、
断定しない）。

## 陽性対照（4点すべて成立）

1. 自作サブROMのSHA-256がベースラインと異なる
   （baseline=`179e93eb...`、axisD=`80853faa...`）。固定長8192バイトなので
   ファイルサイズ差は指標に使わない（`m7fe`の訂正）。
2. **q88measureへ実際に渡した`--rom-dir`内のサブROMのSHA
   （`80853faa...`）が、独立に再ビルドした軸D版のSHAと完全一致した。**
   コメント追加後の再ビルドでも同一SHAである（コメントはコード生成に影響しない）。
   これは`m7fp`が「軸Dの測定ログが実は条件Oだったのではないか」という疑いを
   否定した検査と同じ形の確認であり、本稿の測定にも同様の確認を行った。
3. 0起点段27(SEEK)のシリンダがbaseline対axisDで変化した
   （`seek_cylinder_match`=False）。
4. **`stage_cylinder_consistency`（0起点段27のSEEKと段30のREAD DATAのCの内部整合）が
   baseline=False → axisD=Trueへ変化した。**

すべて2run再現した。

## 合格条件（`m7fl`が事前登録した六条件。すべてyes）

### 条件1: READ DATA 9段すべてIC正常終了

0起点段18/22/26/30/34/38/42/46/50の9段すべてがIC=正常終了、ST1/ST2ともエラー
ビットなしだった。baselineは9段中8段のみ正常終了（段30のみ異常終了）である。
条件Oは9段すべて正常終了。**条件1=yes。**

### 条件2: 9段すべての`$FB` run長が条件Oと一致

9段すべての`$FB` run長が条件Oの対応段と完全一致した。baselineは段30のみ
run長7対263で不一致していた。**条件2=yes。**

### 条件3: `tools/conform_l3.sh`の適合条件1〜5すべて合格

`tools/conform_l3.sh`（環境変数3本を全て渡す）で、OK 434件、NG 3件、
**SKIP 0件**、rc=0だった。NG3件は自己検査b/c/dという既存の陽性対照
（ハッシュ改ざん・件数改ざん・存在しないポート抽出という自作フィクスチャに
対する意図的な不一致検出であり、`m7fh`・`m7fm`と同一の既知挙動）であり、
適合条件の失格ではない。**条件3=yes。**

### 条件4: 全32ビルド構成で`build()`が`SystemExit`を出さず成功

8構成 × `PC88_BULK_READ_INTERVENTION_LIMIT`=1〜4の全32通りで`build()`は
`SystemExit`を出さず成功した。判定は`m7fg`が確定した基準（`SystemExit`の
有無）だけで行い、**使用量の数値比較は判定に使っていない。** 使用量は
純粋な並べ替えという事前登録どおりベースラインと完全一致した。**条件4=yes。**

### 条件5: 段0〜段26（起動区間）の外形がベースラインから不変

**「起動区間」**（`--after-frame`で絞る「入口区間」ではない）の0起点段0〜26
（27件、SPECIFY/RECALIBRATE/SEEK/SENSE INTERRUPT STATUS/SENSE DRIVE STATUS/
READ DATAを含む）を、opcode・unit/head分類・結果ステータス復号名の3項目で
全件突き合わせた。**差は0件だった。**

`m7fm`が記録した「段4・段6のunit/head分類が軸Dで変化した」「SEEK 11段すべてが
条件Oと一致した」はいずれも再現しなかった。これは`m7fp`が既存ログの再確認で
得た結果と一致する。**条件5=yes。**

### 条件6: WRITE経路の発行I/O列がベースラインと完全一致

`tools/analyze_write_path.py`のコマンド内訳（SPECIFY 1 / RECALIBRATE 5 /
SENSE INT 34 / SEEK 29 / SENSE DRIVE 28 / READ 19 / WRITE 8）、各コマンドの
データ相・結果相バイト数が、baseline対axisDで完全一致した。
`tools/compare_l3_entry_fdc.py`でも種別列124件全長一致で、値差は軸Dが意図的に
変えた対象SEEKのみだった。**条件6=yes。**

## 決定論性

baseline・axisD・条件Oいずれも各2run取得した。iolog行数・DISK.ROMのSHA-256・
READ DATA 9段の判定・起動区間差分・陽性対照4点すべてが2run間で完全一致した。

## 採用

**六条件すべてyesなので採用した。** 差分は`out_imm`1行の移動と日本語コメント
7行の追加のみで、命令の追加・削除は無い（`git diff src/l3_service/make_subrom.py`
参照）。

**これで段30の異常終了が解消し、READ DATA 9段すべてが公式と同じ正常終了に
なった。** L3のこの経路で残っていた最後の食い違い（`m7fh`が「残る未確定は
段30の1件のみ」と記録していたもの）が埋まった。

## `m7fm`との関係

**`m7fm`の判定（不合格）は訂正済みで、訂正は`m7fp`にある。** `m7fm`のノート
本文は書き換えていない。本稿は`m7fp`の後に、条件1〜4・6を含む全六条件を
改めて測り直した結果であり、`m7fp`が示した「条件5は満たされる見込みが
立つ」を、見込みのまま採用せず、実測で確認したうえで判定している。

## 言えること・言えないこと

言えること:

- 軸Dの介入（`out_imm`の移動）は、段27のSEEKシリンダを変化させ、段27の
  シリンダと段30のREAD DATAのCの内部整合を公式と同じTrueへ変えた。
- 事前登録した六条件すべてがyesであり、事前登録どおりの手続きで採用した。
- READ DATA 9段すべてが正常終了し、`$FB` run長も9段すべて条件Oと完全一致した。
- 起動区間（段0〜段26）はbaselineから不変であり、軸Dの効果は標的とした
  段27のSEEKシリンダに局所化されている。
- WRITE経路・容量関門は不変である。
- **読解（`m7fk`）・陽性対照・実測が、すべて整合している。** これは
  非常に強い証拠であり、不当に低く扱わない。この整合そのものは事実として
  記録する。

言えないこと:

- **「段30の`WRONG CYLINDER`が消えた原因はOUT順序だった」と断定はしない。**
  読解・陽性対照・実測結果がすべて整合しているのは強い示唆だが、因果の
  断定ではない。本プロジェクトはこれまでも「変化した」を「正しい」と
  読み替えず、示唆と証明を区別してきた（`m7fk`・`m7fm`・`m7fp`と同じ扱い）。
  本稿もこの扱いを維持する。
- 公式READ側のTC位置、公式のシリンダ値は読んでいない（測定していない）。
- **起動区間に残るunit/head差2件（0起点段4・段6、SENSE INTERRUPT STATUS）は
  未解決のまま残る。** 軸Dはこの2件を一切動かしていない（条件5=yesはこの
  2件が「baselineから変化していない」ことを意味するのであって、
  「公式と一致した」ことは意味しない。`m7fp`が確認したとおり、この2件は
  軸D対条件Oでも不一致のまま残る）。
- **SEEK 11段のうち、軸D対条件Oで不一致が残る2段**（`m7fj`・`m7fk`が
  「1.22節の意図的な定数0」と記録している段3・段9）も未解決のまま残る。
  軸Dはこの生成元（`xor_a()`直後の即値0）には触れていない。

## 開示への言及

本測定の過程で情報境界に関わる事象があり、
[disclosure-2026-09-03.md](disclosure-2026-09-03.md)に記録した。
`tools/conform_l3.sh`の一部（`RUN"file"`デマンド入口テストの`na`セクション、
`compare_drive_request_runs.py`によるA/B要求run比較）がFDCパラメータの値を
標準出力へ表示する既存挙動を持っており、これに気づかず値がログへ表示された
という委譲先自身の申告に基づく。軸Dの介入箇所（段27のSEEK、
`_exchange14_prepare_first_read`）と、値が表示された箇所（`RUN"file"`入口・
ドライブ要求run）は別であり、**軸Dの採用がその値に由来するとは考えにくいが、
断定しない。** 詳細な評価は開示記録側に記した。

## 次にやること

由来のドライブ選択）に取り組む。** `m7ey`は、この振る舞いが実行環境のRAM

**事前登録してから行う。** 今回の結果を根拠に候補を挙げるだけで、本稿では
実施しない。
