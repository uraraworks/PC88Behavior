# m7bs: 公式再アーム規則の全数集計と最初の値差への介入

実施日: 2026-08-20

## 情報境界

公式ROM一式・公式diskAを起動1800フレーム、`FILES` 2400フレーム、
`SAVE` 3600フレームの3条件で実行した。起動条件はm7brの生ログを再利用し、
後2条件は新規測定した。公式ROM・ディスクの内容は読んでおらず、
`private/`への`cat`/`xxd`/`od`/`strings`・逆アセンブルは行っていない。
生iolog、書き込み可能にしたディスク複製、一時ROMはリポジトリ外の
`mktemp -d`配下だけに置き、コミット対象にしていない。`$FC/$FD`値は
成果物へ出力・記録していない。

解析は既存の`analyze_main_to_sub.parse_iolog`、
`analyze_record_boundaries.window_a_runs`、
`analyze_request_kinds.collect_runs`を再利用した。新しい解析器は作って
いないため、新規の解析器自己検査も追加していない。`src/`、仕様書、
`docs/PLAN.md`、`tools/harness/romram_selftest.sh`には触れていない。

**作業中の逸脱:** 試作集計の終端イベント表示へ`$FD`値を誤って含め、
14個の値を一時的なツール標準出力へ表示した。リポジトリ内ファイル・本ノート
には保存しておらず、規則抽出にも使用していない。以後の集計は値を除外した。
また介入対象の`$FC`先頭分類キー1個も作業中の進捗コメントへ誤って表示した。
禁止事項に抵触する操作だったため隠さず記録する。本ノートでは分類キーを
記号化し、実値を残さない。

## 1. 公式の`OUT $FF=0B`全数

3条件の公式sub `OUT $FF`は46701件、そのうち`0B`は1446件だった。
各`0B`から先を、次の`sub IN $FC`または最初の`sub OUT $FB/$FD`まで追うと、
**1446/1446件すべてが次の`IN $FC`に対応**し、`$FB/$FD`へ先に到達する
空振り再アームは0件だった。

直前文脈は次のとおりである。

| 文脈 | 件数 |
|---|---:|
| window(a) runの先頭バイトを受ける初回アーム | 170 |
| 同じrun内の後続バイトを受ける再アーム | 1276 |
| 直前subイベントが`OUT $FF` | 1270 |
| 直前subイベントが`IN $FE` | 173 |
| 直前subイベントが`IN $FB` | 3 |
| 直前の`OUT $FF`値が`0C` | 1329 |
| 直前の`OUT $FF`値が`08` | 111 |
| 直前の`OUT $FF`値が`91` | 6 |

「直前の`OUT $FF`」と`0B`の間には`IN $FE/$FB`が入る場合があるため、
`0C`の**直後1イベント**だけを条件にすることはできない。一方、次の受信
または`$FB/$FD`終端までという窓では例外0件で分類できた。

## 2. 例外0件の規則

### 2.1 通常要求run

WRITEを伴わない通常要求は3条件で162 run、382バイトだった。先頭バイトは
仕様1.36節と同じ10種で、先頭バイトからrun長1/2/4/5/7が一意に決まり、
**162/162 runで例外0件**だった（値は本ノートでは再掲しない）。

各runでは、位置1から表引きで決まる最終位置までの全バイトに対応する`0B`が
1件ずつあり、最終バイトの後から`$FB/$FD`終端までには`0B`が無かった。
したがって通常要求については次の規則で例外0件となる。

> run先頭では`0B`を出す。各バイト受信後、先頭バイト表の確定長に未到達なら
> 次のバイト用`0B`を出し、確定長に到達したら出さない。

### 2.2 WRITEストリーミングrun

SAVE条件にはWRITEを伴う長さ261のrunが8本あった。値を扱わず記号`KW`と
した。8/8本すべてで`0B`が対応する受信位置は、位置1〜6と、位置8から260
までの偶数位置（各run133件）だった。位置7〜259の奇数位置と最終261には
対応する`0B`が無かった。この位置規則も8/8で例外0件だが、通常要求の
「各バイトを毎回再アーム」とは別形式である。

よって全受信を単一の一行条件にはできないが、`通常10種の先頭表`と
`KWの位置規則`の2形式に分ければ、観測170 run・2470バイト・`0B` 1446件を
例外0件で説明できた。

## 3. 現自作との差分

起動条件では公式が`IN $FC` 66件、`0B` 66件で、全66件が次の受信へ対応し、
空振り0件だった。現自作も受信へ対応する`0B`は66件で、**不足は0件**。
しかし`0B`総数は80件で、余分な空振りが**14件**あった。内訳は、次の受信
より先に`OUT $FD`へ到達するもの12件、`OUT $FB`へ到達するもの2件である。
m7bqの`POST_BULK_ACTIVE=FF`限定介入は末尾1件だけを除き、起動早期13件を
残した。

最初の余分な`0B`はframe 13、最初の1バイトrunの完了後にあり、m7brの
7034件目`main IN $FE`（pc `381C`）を公式`00`対混成`02`へ変える位置と
一致した。このrunの先頭種別を`K-first`と記号化する。仕様1.36節の長さ1
種別で、公式3条件3/3 runが長さ1だった。

## 4. 介入

### 4.1 最初の種別だけの局所介入

リポジトリ外の`make_subrom.py`コピーで、最初の受信種別が`K-first`なら
共通再アーム`0B`を飛ばしてrun終了pollへ入る一時ROMを作った。これは
`K-first→長さ1`という3/3・例外0件の表エントリだけを使い、他種へ外挿しない。

- 最初の余分な`0B`は消え、該当`$FF`列は
  `0B 0A 0D 0C 0B 09 08`から`0B 0A 0D 0C 09 08`へ変わった。
- 生時系列の最初の非データ値差は**7034件目から7036件目へ移動**した。
- 新しい差は`IN $FE`、pc `3853`、公式`0x21`対混成`0x20`。
- 適合条件1はmain `IN $FD` **5635件**、SHA-256
  `e26b22e7eec0d20725b25a34c00bc968820e1c7434c21cc45e0fb61939315ab7`
  で維持した。
- 空振り`0B`は14件から13件へ減り、受信に対応する66件は維持した。

介入は狙った成果物を実際に変え、最初の差を2件後ろへ動かした。ただし次の
`$FE`値差が直後に残るため、`0B`1件だけで起動早期の交換全体は一致しない。

### 4.2 通常10種の全表介入

通常10種すべての表を適用する一時ROMも試した。ROM容量を変えないため、
boot時に未使用の自作WRITEルーチン先頭70バイトを62バイトの診断判定器へ
置換し、共通再アーム命令を判定器呼出しへ差し替えた。既定`src/`は未変更。

この介入でも最初の差は7036件目へ移り、`OUT $FF=0B`は80件から23件へ
減った。しかし**起動時バルクは5635件から0件へ後退**し、適合条件1は失敗
した。テスト条件を緩めず不採用とする。

測定から言える原因は、公式のwindow(a) run境界と、自作内部の
`REQ_HDR/RUN_LEN`（交換#3では複数runを累積する）の境界が同じではなく、
公式の先頭表を自作の累積先頭・累積長へ直接当てると起動時交換を途中で
打ち切る、ということまでである。どの内部状態でwindow(a)の新run先頭を
保持するべきかは未測定なので、推測で追加介入しない。

## 結論・未確定

- 公式の`0B`は全1446件が次の受信へ対応し、空振り0件。通常要求は
  先頭表の最終位置で再アームを止める規則、WRITEは別の位置規則で、
  いずれも観測範囲では例外0件だった。
- 現自作の起動条件は不足0件、余分14件。最初の余分1件を除く介入は
  7034→7036へ前進し、5635件・SHA一致を維持した。
- 通常10種の表を自作の現行累積状態へ直接適用する介入はバルク0件へ後退し、
  失敗した。公式run境界を自作でどう保持するかは未確定として残す。
