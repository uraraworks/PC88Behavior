# m7ak: LIMIT=2退行の帰属・$F9陽性対照・STACK/BULK_DATA重複バグの特定と修正

測定日: 2026-08-17

## 情報境界

公式1800フレームログ（m7ajで新規実走・構造一致確認済み）を基準に、
混成ROM（LIMIT=1／LIMIT=2／修正後LIMIT=2）を同条件で実走した。データポート値は
`tools/cmp_io.py --location-only`・`tools/cmp_fdc_sectors.py`の内部だけで扱い、
標準出力には位置・件数・一致長・帰属先だけを出した。生ログ・介入版ROMは全て
スクラッチ（リポジトリ外）に置き、コミットしていない。

## A. LIMIT=1とLIMIT=2の最初の構造的分岐点

`tools/diag_l3_mixed.py`（`--sub-pc`）で混成(LIMIT=1)を基準、混成(LIMIT=2)を
対象に比較すると、main側は畳み込み後3877件目まで完全一致し、3878件目で分岐した。

- 3877件目: `IN port=00FE pc=37DC`（$FEポーリング）。LIMIT=1は1回で抜けるが、
  LIMIT=2は433回（回数差検出器が「無限ループの疑い」と報告する閾値50倍を超える）。
- 3878件目: LIMIT=1は`OUT $FF pc=37F0`→`OUT $FD pc=37F4`（バルク転送を継続する
  経路）へ進むが、LIMIT=2は`OUT $0031 pc=E7F5`という**別分岐**へ進む。この
  `pc=E7F5`は、m7aj時点で確認済みの「公式 vs 混成(LIMIT=1)」比較のmain側258件目
  分岐点（`基準[259] OUT port=0031 pc=E7F5`）と同一PCである。

**帰属:** LIMIT=2ではmainが$FEを433回（約束の待ち上限相当）ポーリングしても
subからの応答が来ず、待ちを諦めて「公式との258件分岐」で使われるのと同じ
給油経路（pc=E7F5）へ落ちる。これはREAD#3のFDCコマンド発行**後**、データ
フェーズの途中でsubが応答を止めた（クラッシュまたはハングした）ことを示す。
sub側構造的一致プレフィックスは752件のまま不変（分岐点はREAD#2データ
フェーズ内で、READ#3追加より手前にあるため、この752件の壁とは別の問題）。

## B. $F9（FDC_TIMEOUT_MARK）の陽性対照と結果

`src/l3_service/make_subrom.py`には`P_FDC_TIMEOUT_MARK=0xF9`（未デコードポート、
副作用皆無を確認済み）があり、`--disable-fdc-timeout-mark`を指定しない既定では
sub内のFDCステータス待ちタイムアウト（`FDC_WAIT_TIMEOUT=0x0400`回のポーリング
上限）到達時に`OUT $F9`を記録する。

**陽性対照:** `tools/verify_l3.sh`の既存の検出力確認（
`--break-fdc-timeout-reads-anyway`相当の強制シナリオ）で、実際にタイムアウトが
発生した場合に`$F9`が1件記録され、直後に`IN $FB`を読んでいたことを検出できる
ことを確認済み（本セッションで`tools/verify_l3.sh`を再実行し、該当OKを確認）。
検出力は生きている。

**結果:** LIMIT=1・LIMIT=2いずれの混成生ログでも、sub側`OUT $F9`は**0件**
だった。したがって「subがFDCチップ自体の応答待ちでタイムアウトした」という
経路（`FDC_WAIT_TIMEOUT`側の仮説5前半）は否定される。問題はFDCチップとの
やり取りではなく、それより内側（データ受け渡し・スタック）にある。

## C. 仮説の可否

1. **バッファ長（第一候補）: 該当、原因はサイズ不足ではなく配置重複。**
   `BULK_DATA=0x4400`からREAD#2〜#5の合計12288バイト（0x3000）を連続確保して
   おり、末尾は`0x7400`（サブ側書き込み可能RAM上限`0x7FFF`の内側）。バッファ
   長そのものは十分だった。しかし`STACK=0x6000`が、READ#3のデータ書き込み
   範囲`0x5200`-`0x6200`（BULK_DATA+14セクタ分＝READ#2終端から16セクタ分）の
   **内側**に位置していた。READ#3のデータフェーズがこの範囲へ書き込むと、
   実行中の呼び出し列がスタックに積んだ戻り番地を上書きする。READ#2の範囲
   （0x4400-0x5200）はSTACKより手前なので影響を受けず、これがLIMIT=1で
   問題が起きなかった理由と整合する。
2. **TCの発行位置: 未着手（Aで原因が別に見つかったため優先度を下げた）。**
3. **結果部7バイトの吸い出し漏れ: 未着手（同上）。**
4. **ハンドシェイクの再武装: 未着手（同上）。**
5. **main側のタイムアウト: 部分的に確認。** Aで見た`pc=37DC`の433回ポーリング
   は「mainが待ちを諦める」経路そのものであり、上限自体は公式mainの経路
   （258件分岐と同一PC）なので、緩めるべきは無い。問題はsubが遅い/止まる
   側にあり、Bで「subがFDCチップ待ちでタイムアウトしていない」ことも確認
   したため、真因は1のスタック破壊であると判断した。

## 修正

`src/l3_service/make_subrom.py`の`STACK`を`0x6000`から`0x7FFE`（書き込み可能
範囲`0x7400`-`0x7FFF`の上端付近、下方向に約0xBFEバイトの余裕）へ変更した。
この範囲はBULK_DATA(0x4400-0x7400)と重ならない。

## 実測結果（2回連続一致）

`PC88_BULK_READ_INTERVENTION_LIMIT=2`で新規1800フレーム実走を2回行い、
`tools/cmp_io.py --location-only`で同一結果（seq値まで一致）を確認した。

- `tools/cmp_fdc_sectors.py`: 座標列一致プレフィックス6/6（変化なし、
  READ#3のFDCコマンド座標は修正前から一致していた）。
- main `IN $FD`: 先頭一致**1282件→3330件**、対象側到達件数5635件（公式と同数）。
- 3330/3331の帰属（値非依存の算術）: `analyze_exchange14_read_rules.py`が
  出したデータ部長（256,3584,4096,4096,512バイト）から、n番目FDのローカル
  オフセットL=2n-7（n≧4）を使うと、n=3330→L=6653はREAD#3内（0-4095中の4094、
  終端間近）、n=3331→L=6655はREAD#3範囲外＝**READ#4・第1セクタ・第1位置**
  に一致する。m7ajで確認した「1282/1283=READ#2終端/READ#3先頭」と同型の
  境界が、今度は「3330/3331=READ#3終端/READ#4先頭」として現れており、
  READ#4が未実装であることの自然な帰結であって新規の分岐ではない。

## 4指標（既定 `BULK_READ_INTERVENTION_LIMIT=1`、修正後）

`tools/verify_l3.sh`（既知のNG1件のみ、回帰なし）・`tools/conform_l3.sh`
（自己検査全OK、本番`[本番]`OK、`[混成]`は既存どおり不一致・回帰なし）を
再実行して確認した。

- 値一致長: 変更なし（未計測項目に触れる変更をしていない）
- main側構造的一致プレフィックス: 258件（変更なし）
- sub側構造的一致プレフィックス: 752件（変更なし）
- main `IN $FD`（既定LIMIT=1）: 5635件到達・先頭一致1282件・全位置一致1300件
  （変更なし。STACK移動はREAD#2の書き込み範囲と無関係なため無影響）

LIMIT=2（非既定・環境変数経由のみ）: 先頭一致3330件（1282件からの改善、
今回の主要な成果）。

## 既定を上げるかどうか

**上げない。** `BULK_READ_INTERVENTION_LIMIT`の既定は`1`のまま維持する。
LIMIT=2はmain `IN $FD`の一致件数こそ伸びるが、READ#4以降が未実装のため
READ#3データ枯渇後（3331件目相当）にmainが再度待ちを諦める経路へ入り、
sub側は応答を続けられず測定が無限ループ的に長引く（今回の実走は2回とも
ログ行数が2097180件に達し、1800フレーム分の他の起動処理を最後まで
終えられなかった）。既定を上げると、既定測定の所要時間・ログサイズが
悪化するだけでなく、他の回帰検出（verify_l3.sh・conform_l3.sh)がREAD#4の
未実装状態を「新規の失敗」として誤検出しかねない。READ#4/#5を実装してから
既定を上げるべきである。

## 次の対象

READ#4・READ#5はB表（m7aj）で座標がすでに一意化されている
（既存候補表に実装済み、C=要求1群、R=要求1/10群、EOT=R+15/R+1）ため、次
サイクルは`PC88_BULK_READ_INTERVENTION_LIMIT=3`・`4`で同じSTACK修正済み
コードを使い、READ#4・READ#5データフェーズでも同様の重複バグが無いかを
まず確認してから伸ばすとよい（BULK_DATA配置は今回の計算上READ#5末尾まで
0x7400に収まっており、STACK=0x7FFEとの重複は無いはずだが、実測で確認する
のが安全）。sub側752件の壁（READ#2データフェーズ内の反復回数差）は本
サイクルでも未着手のまま残っている。
