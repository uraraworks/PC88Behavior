# l4-mbf-oracle-v2 — GW-BASIC数値部の予測器v2（命令単位の再現）

記録日: 2026-09-15

## 位置づけ

`docs/notes/l4-mbf-oracle.md`（v1）は四則演算を「両オペランドの厳密値を
有理数で求め、結果の型へ1回だけ偶数丸めする」近似で再現していた。これは
出力の一致・不一致を直接左右する箇所であるにもかかわらず命令単位で
確認していなかったため、実測と食い違ったときに「GW-BASICの手順どおりに
実装しても一致しないのか」「予測器側の近似のせいなのか」を区別できない
という指摘を受け、v2として作り直した。

**v1（コミット `1444cb4` 時点のファイル）はこの作業で変更していない。**
v1とv2のどちらが公式ROMの実際の挙動に近いかは、今後の測定で判定する。

## 命令単位で確認できた箇所（v1から変更した）

`tools/l4_mbf_oracle_v2.py` のモジュールdocstringに対応表を書いた。要約:

1. **単精度乗算 `$FMULS`（MATH2.ASM 408-490）は正しい丸めではない。**
   24bit×24bitの厳密48bit積を8086の16bit `MUL` 命令で部分積として
   組み立てる際、最初の部分積（下位16bit×下位16bit）の下位16bitを
   スティッキービットへ畳み込まずにそのまま捨てている
   （MATH2.ASM 449-450 `MUL DX` の直後 `MOV CX,DX` で、積の下位ワードを
   保存せず破棄）。さらに丸め本体 `$ROUNS`（MATH2.ASM 1779-1796）も
   guard byteの下位5bitを `AND AH,340`(8進、0xE0)で捨ててから
   tie判定するため、2段階で精度を落としている。v2は
   `P48=MF*MO` の上位32bit（`P48>>16`、下位16bitは本当に捨てる）を
   作り、その中でだけ $ROUNS と同じ粗い偶数丸めを行う関数
   `_single_multiply_mantissa`/`_rouns_from_guard32` として実装した。
2. **倍精度乗算 `$FMULD`/`DMULT`（MATH2.ASM 308-407）は正しい丸め。**
   Knuthの Algorithm M（コメントに明記）で完全精度の積を作り、
   最後に捨てる下位バイト側を1バイトずつ走査してスティッキービットを
   立てる（`M5AA` ループ、MATH2.ASM 382-391 `LOOPZ M5AA`〜
   `OR BYTE PTR $DFACL-1,LOW 40`）。よって「厳密値→1回偶数丸め」と
   数学的に等価と確認できた（近似ではなく確認済みに格上げ）。
3. **加算・減算（単精度・倍精度とも）は正しい丸め。** 単精度は
   `$FADDS`/`$FSUBS`（MATH1.ASM 3265-3427）の位置合わせシフト
   （`FA23`〜`FA30`）でビット単位シフト中に"ST"(sticky)ビットを
   `OR AH,40` で保持する。倍精度は `$FADDD`/`$FSUBD`（MATH1.ASM
   3131-3263）が `$SHRA`（MATH1.ASM 1583-1616）を呼んで同様に
   STビットを保持する。どちらも「シフトで捨てるビットのどれかが
   1ならSTビットを立てる」という構造そのものが correctly-rounded
   加算の標準手法（guard+round+sticky）であり、「厳密値→1回偶数丸め」
   と等価と確認した。指数差が大きすぎて小さい方の値が影響しなくなる
   カットオフ（単精度25bit、倍精度57bit。MATH1.ASM 3175
   `CMP CL,LOW 57D`）も、カットオフの閾値がガード幅ぎりぎりに
   設定されているため数学的に「丸めた結果は変わらない」ケースにしか
   起きないことを確認した。
4. **除算（単精度・倍精度とも）は正しい丸め。** `$SDIV`/`$FDIVS`
   （MATH1.ASM 3666-3825）はKnuthの Algorithm D（2ワード長除算、
   コメントに明記）を使い、剰余が非ゼロなら明示的にスティッキー
   ビットを立てる（"OR DL,LOW 1 ;Set sticky bit if remainder not
   zero"、MATH1.ASM 3745）。よって「厳密値→1回偶数丸め」と
   等価と確認した。指数計算も `$AEXPS`/`$SEXPS`（MATH1.ASM
   2913-2970、乗算は`e1+e2-129`、除算は`$SDIV`内の`e1-e2+128`〔+商が
   1以上なら+1〕）を命令単位で追い、オーバーフロー/アンダーフローの
   境界を範囲チェックとして実装した。
5. **`$INFPD`/`$INFMD`（MATH1.ASM 776-792）の実バイト列を読んだ。**
   単精度・倍精度とも「仮数全ビット1、指数バイト255」で、v1が
   （既知のMBFバイト列4件からの演繹で）独自導出した値と完全一致した
   （selftestで `FF FF 7F FF` と確認）。v1は推測、v2は確認済み。
6. **`$CSD`（倍精度→単精度への切り詰め、MATH2.ASM 197-206）は
   タイ(tie)に到達しない。** 保持する24bitの直後のバイトを
   ガードバイトとして使うが、`OR AH,LOW 100` でbit6を強制的に1に
   するため、`$ROUNM` のtie判定（`guard&0xE0==0x80`）には到達し得ない
   （bit6=1だとmasked値は0x40台か0xC0台にしかならない）。つまり
   倍精度→単精度の切り詰めは「次のバイトのbit7だけで決まる」単純な
   規則（bit7=1なら切り上げ、0なら切り捨て）と確認した。
   `$FINE`/`MDP10`（定数へ指数を適用する処理、MATH1.ASM 1145-1249）は
   常に倍精度で計算してから最後に `$CSD` で単精度へ落とすため
   （FIN45 "JNB FIN50;CALL $CSD"）、この規則がそのまま数値定数の
   丸めにも効くと確認した。倍精度自体は56bitの余裕があるため、
   本予測器が扱う程度の桁数のリテラルでは「厳密値を直接その型の
   精度へ1回丸める」v1流の実装と結果が変わらないと判断し（二重丸め
   になりうる場面が実際には生じない）、リテラル解析自体はv1と同じ
   ロジックのままにした。

## 命令単位で追い切れず、v1のままにした箇所（`approx`）

- **`$FOFMT` の `FFM10`〜`FFM30`（固定小数点⇔指数表記の切替）、
  `$FOTNV` の実際のブラケット目標値、`$SIGD` との組み合わせ。**
  レジスタを1つずつ追い、`$AEXPS`と同様に閉じた式を立てようとしたが、
  既知の例（単精度 `999999` は固定小数点になるはずで、$FOTNVの戻り値を
  「E-有効桁数」と仮定する自分の式では矛盾する結果になった）を検算した
  ところで時間内に解消できなかった。`$FOTNV`自体の構造
  （MATH2.ASM 716-769）は、テーブル(`$FOTB`)による初期見積もりのあと
  `$DP06`（単精度側下限）・`HIDBL`（倍精度側上限、実バイト列で
  `9999999999999999.`と明記されているのを確認済み）との比較で必ず
  補正する作りなので、最終結果はテーブルの近似精度によらず数学的に
  確定するはずだと判断できたが、「有効桁数が7/16なのか8/17なのか」の
  対応づけで上記の矛盾が生じ、`$SIGD`の末尾ゼロ計算との相互作用も
  含めて解消し切れなかった。
  **v2はこの部分だけv1と同じ近似則
  （`-有効桁数 < E <= 有効桁数 なら固定小数点`、`E`は
  `d.ddd…×10^E`の意味）を維持している。** 既知の判定例
  （`999999`/`9999999`/`10000000`は固定小数点、`1E10`/`1E-10`は
  指数表記、`.1`/`.01`/`.001`は固定小数点）とは矛盾しないことを
  確認済みだが、境界そのもの（例えば単精度で`E=-7`や`E=8`のとき
  どちらになるか）は本版でも未検証のまま。

## `approx` 列について

`docs/notes/l4-s4a-gwbasic-predictions-v2.tsv` の `approx` 列は、
「この腕の `predicted` が、上記の未解決の固定小数点⇔指数表記の
しきい値則を経由して決まったか」を表す。**32腕すべてがこの表示規則
（`fout_format`）を通るため、全腕で `approx=1` になっている。**
四則演算の丸め自体（値がどう計算されるか）はこの版で命令単位の再現に
置き換えたが、「その値を固定小数点で出すか指数表記で出すか」の最終判定
だけが依然として近似則に依存する、という構造を正直に表している。

## v1とv2の出力差

32腕そのものについては **v1とv2で出力の違いは0件だった。**
（`tools/l4_mbf_oracle_v2_selftest.sh` 項目5で確認。）

ただし、単精度乗算の丸め方法の違い（上記1番）は実在する差であることを
示すため、32腕の外で人為的に探索し、**`9924.8*984025.0` で乖離を
1件見つけて固定した**（`tools/l4_mbf_oracle_v2_selftest.sh` 項目4）。

| | v1（厳密値→1回偶数丸め） | v2（8086の部分積どおり） |
|---|---|---|
| `PRINT 9924.8*984025.0` | ` 9.766252E+09 ` | ` 9.76625E+09 ` |

v2の結果は末尾の桁が1つ少ない（丸め後の仮数の末尾が0になり、自由形式
出力の末尾ゼロ抑制で消えた）。これは「8086が実際に捨てている下位16bit
にスティッキービットを畳み込んでいれば起きなかった差」であり、
`tools/l4_mbf_oracle_v2_selftest.sh` の故障注入
（`L4_ORACLE_FAULT=mul_sticky`）でこの分岐を無効化すると、v2の結果が
v1の値（` 9.766252E+09 `）に戻ることを確認している。

## 迷った箇所・判断が難しかった点

- **有効桁数の定数が複数ある。** `$FOFMT`は最初にCH/CLへ8(単精度)・
  17(倍精度)を入れる一方、直後に「+7」「+16」を別途加算する箇所があり、
  「7桁/16桁」という一見単純な仕様が、実装上は複数の異なる定数
  （8・17、そして+7・+16）に分散している。どの定数がどの意味を持つのか
  を完全に解きほぐせなかったのが、今回`approx`に残した最大の理由。
- **$FOTNVが返す「補完する指数」の符号の向き。** ドキュメントコメント
  だけでは正負の向きが自明でなく、「大きい数ほど正」という仮説を
  1E10の分岐ルート(JPO/JNS)から逆算して立てたが、999999の検算で
  破綻したため、この仮説自体に誤りがある可能性が高いと判断した。
- **単精度乗算のスティッキー破棄は「バグ」ではなく仕様として扱った。**
  正しい丸めから外れる箇所を見つけたとき、実装ミスとして「修正」
  するのではなく、GW-BASICが実際にそう動く前提でそのまま再現する
  ことを優先した（本予測器の目的は「GW-BASICのアルゴリズムを
  そのまま踏襲すればN88と一致するか」を検証することであり、
  理想化した正しい浮動小数点演算を作ることではないため）。

## 動作確認

`tools/l4_mbf_oracle_v2_selftest.sh`:
1. 既知のMBF単精度バイト列4件との一致・往復変換
2. `$INFPD`/`$INFMD`相当（最大値）のバイト列が`FF FF 7F FF`と一致
3. `docs/notes/l4-s4a-gwbasic-predictions-v2.tsv`の再生成がバイト一致
4. v1/v2の乖離例（`9924.8*984025.0`）を固定
5. 32腕自体はv1/v2で出力差0件であることの記録
6. 故障注入（`L4_ORACLE_FAULT=mul_sticky`）で単精度乗算の判定が
   v1相当（正しい丸め側）に戻ることの確認
7. 偶数丸めの故障注入（`L4_ORACLE_FAULT=round_up`、v1と同じ検査を流用）
8. 整数溢れ時の単精度昇格（v1と同じ検査を流用）

いずれもOK。`tools/run_all_selftests.sh`に登録した。
