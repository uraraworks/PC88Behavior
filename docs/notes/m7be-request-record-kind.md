# m7be: 要求レコードは読み書き共通の形で、種別は2バイト目にある

測定日: 2026-08-19

## 情報境界

公式ROM一式・公式diskA（使い捨て複製）を**実行して**測定した。読んでいない。
本ノートに書くのは**位置・件数・種類数**と、レコードの構造的な位置づけだけで、
ディスクの内容は扱わない。

## 1. SAVEは実行され、ディスクの管理領域で失敗していた

m7bdでBASICが起動したので、同じ打鍵（`10 PRINT "T"` → `SAVE"TQ"`）で公式と
混成を並べた。混成の画面には **`Bad allocation table`** が出た——**SAVEは
実行されており、その過程のディスク読み出しで失敗している**。

FDCコマンドを比べると差が明確だった。

| | 公式 | 混成 |
|---|---:|---:|
| READ | 19回 | **8回** |
| 8回目のREAD以降 | `SEEK→SINT→SDRV→READ` を繰り返す | **SENSE DRIVE STATUS ×140** |

最初の8回は**座標(C,H,R)まで完全に一致**していた。9回目以降が出ていない。
`SENSE DRIVE STATUS` の連発は自作subの**fallback**（どの要求グループにも
一致しないときの経路）そのものである——起動時に確定した9グループにしか
対応していないため、BASICが起動したあとの要求はすべて取りこぼしていた。

## 2. 読み出し要求も、書き込みと同じ6バイトレコードだった

m7axで書き込み用に確定した「6バイトレコードの末尾2バイトが
`[論理トラック(C*2+H), R]`」が、**読み出しにもそのまま当てはまる**か調べた。

| 対象 | 一致 |
|---|---|
| 起動後のREAD（直前6バイトの末尾2バイト） | **11/11** |
| WRITE（データ256の直前2バイト、参考） | **8/8** |

**読み書きで同じ形のレコードを使っている。**

## 3. 種別は2バイト目（idx1）にある

同じ形なら、何が読み/書き/単発応答を分けているのか。レコードの先頭4バイトを
位置ごとに比べた（値ではなく種類数と、集合が一致するかだけを見る）。

- READ直前レコード: idx0=2種、idx1=1種、idx2=1種、idx3=1種
- WRITE直前レコード: idx0=2種、idx1=1種、idx2=1種、idx3=1種
- **READとWRITEで値集合が違う位置は idx1 だけ**
- 起動時の6バイト要求グループ（既知の9グループのうち2つ）は
  **idx1・idx2ともREAD/WRITEとは別の値**

つまりレコードは `[?, 種別, ?, ?, 論理トラック, R]` という形で、
**2バイト目が操作の種別**を持つ。idx0は2種の値を取り（意味未確定）、
idx2/idx3は各種別の中では定数だった。

## 4. 次の一手（実装）

fallbackに落ちている起動後の要求を、**種別つきの一般経路**として実装する:

- idx1 が READ の値 → 論理トラックとRからC/H/Rを作り、SEEK＋READ DATAを
  発行して256バイトを応答する
- idx1 が WRITE の値 → 既存の書き込み経路（現在はrun長で判別している。
  ここも種別で判別できるようになる）
- idx1 が起動時の値 → 既存の9グループ表

**応答の形（起動後のREADに対して何バイト返すのか）はまだ測っていない。**
公式はバルク直後の8バイト要求に259バイト返していた（1+2+256と読める）ので、
起動後のREADについても同じ形かを先に測ること。**推測で実装しない。**

## 5. この節の教訓

**「同じ形のデータに別の意味を持たせる仕組み」は、種別フィールドを探せば
見つかる。** 読み出しと書き込みが同じレコードだと分かった時点で、
「では何が分けているのか」は先頭4バイトしか候補が無く、位置ごとの
値集合を比べるだけで1箇所に絞れた。
