# M6t — 単発1バイト応答はFDCを叩かない／RECV完遂直後の再武装タイミング検討

日付: 2026-08-12
根拠: 混成ROM実走診断（22:16版、`tools/diag_l3_mixed.sh`）＋既存ノート
（`docs/notes/m6n-run-boundary.md`）の再検討。**追加測定は行っていない**
（診断結果はユーザーが公式環境で実走した出力をそのまま受け取った）。

## 1. 確定: `SEND_DISPATCH_IDLE`（単発1バイト応答）はFDCを叩かない

22:16版の混成ROM実走診断で、sub側の構造的一致プレフィックスが93件→
102件に前進した。分岐点103の直前の対応は次のとおり:

```
基準[102] IN $FE ×2 (seq124) → 基準[103] OUT $FD (seq126)
混成[102] IN $FE ×3 (seq125) → 混成[103] IN  $FA (seq128)
```

基準側は`IN $FE`が2回連続した直後、`$FA`/`$FB`（FDCの制御・データ
ポート、1.7〜1.9節）に一切触れず`OUT $FD`（応答バイトの送信）へ
進んでいる。混成側（自作sub）は`FDC_SENSE_DRIVE_STATUS`を呼ぶために
`IN $FA`へ迂回しており、この迂回そのものが分岐点103の原因だった。

これは1.18節「単発1バイト応答ではsub側FDCアクセスが0〜55件」の、
**0件のケース**に対応する。第9版（`docs/spec/l3-subrom.md`）が
「でっちあげた値を送らない」ためにFDC問い合わせ構造へ差し替えた
判断は、**構造そのものが公式と食い違っていた**ことがこの実走で
初めて分かった。

### 対処

`src/l3_service/make_subrom.py`の`SEND_DISPATCH_IDLE`（および
`--break-dispatch-return`回帰専用パスの対応箇所`IDLE_SEND_BRANCH`）を、
FDCを叩かず`0x00`をその場で送る構造に戻した。

**この`0x00`は「正しい値の推測」ではない。** 送るべき値は依然として
未確定（`docs/spec/l3-subrom.md` 1.18節・3節）。6節14項の趣旨
（値を推測で埋めない）は維持しつつ、構造だけを公式に合わせるための
最小限の選択として、意味を持たせない値（0x00）を暫定的に置いた。
値そのものが正しいと主張しないことは、コード内コメント・仕様書
（1.18節・3節・改訂記録）の全てに明記した。

## 2. 検討: RECV完遂直後の「無条件再武装」を遅らせられるか

### 現状の回数差

同じ22:16版診断で、分岐点101・102に次の回数差が見つかっている
（分岐点103より手前、まだ構造的一致の範囲内）:

```
#101 OUT $FF pc=070B  基準=1回 → 混成=2回
#102 IN  $FE pc=0710  基準=2回 → 混成=3回
```

これは`_recv_dispatch_continue`（`RECV_DISPATCH`、仕様書1.20節・
6節16項）が、RECVを1バイト完遂するたびに**無条件で**
`OUT $FF,0x0B`（再武装）を書いてから`$FE`のbit0/bit1を同時ポーリング
する構造に由来する。run長が1（このケースのように、単発応答で
即座にrunが終わる場合）でも、実際にrunが終わるかどうかは事前に
分からないため、現在の実装は必ずこの再武装+ポーリングを1回余計に
経由してから`IDLE_DISPATCH`へ落ち、そこで改めて`$FE`を読んで
SEND側へ分岐する。基準側はこの1往復を経由しない。

### 検討した代替案

依頼された2案を検討した。

**案A: 再武装を「bit0が立ってから」に遅らせる。**
これは1.20節・m6n第5部が既に扱った、第11版で修正したデッドロックの
再現条件そのものである。main側が継続バイトで`OUT $FF 0F`を省略し、
sub側が既に再武装済み（＝mainの`$FE`にbit0相当の信号が立っている）
ことを前提に次のバイトを送ってくる場合、sub側の再武装を遅らせると
mainはsubがまだ受信可能とシグナルしていない状態で待ち続け、
双方向にデッドロックする（m6n第5部で確定済みの構造）。**この案は
確定済みの測定と直接矛盾するため採用しない。**

**案B: 先にbit1を1回だけ覗き見て、立っていなければ再武装する。**
`OUT $FF,0x0B`を書く前に`IN $FE`でbit1を読み、既に立っていれば
再武装せずそのままSEND側へ進み、立っていなければ現行どおり
再武装してポーリングを続ける、という順序変更である。

この案が案Aと違い安全かもしれない理由: bit1の読み取り自体は
副作用を持たない（`$FF`へは何も書かない）ため、「立っていなければ
その後すぐ再武装する」という経路は、現行構造と実質同じタイミングで
再武装が起きる。案Aのように再武装そのものを遅らせるわけではない。

**しかし、この案を採用しなかった。** 理由は次の2点:

1. **bit1が「RECV完遂の直後、まだ何もしていない時点」で既に立って
   いるかどうかが、本稿の測定手法では確認できない。** bit1
   （`FE_BIT_SEND_RECV_READY`）はmain側が能動的に書く信号であり、
   main・subは独立したクロックで動く別CPUである。分岐点101・102の
   回数差は「基準側はこの往復を経由しない」ことしか示しておらず、
   「bit1が事前に立っていたから経由しなかった」のか「経由しない
   別の分岐ロジック（1.20節が未確定としている、公式subの内部
   分岐選択そのもの）で最初から再武装を経由しない設計だったから」
   なのかを、この観測だけでは区別できない。前者なら案Bは正しい
   構造的知見の反映だが、後者なら案Bを実装しても「たまたま今回の
   ログでは同じ結果になる」だけで、一般には正しさの根拠にならない。
2. **1.20節・m6n第3〜5部は既にこの区別（直接再武装 vs 待ちループ
   経由のどちらへ進むかの選択根拠）を「本測定の手法の外側で起きて
   おり確認できない」と明記している。** 案Bはこの未確定の選択根拠を
   「bit1の値」で代替しようとする点で、6節12項・16項が禁じている
   「値ベースの分岐を推測で実装する」ことに該当する可能性がある。
   1.19節でbit1が確定しているのは「SENDプリミティブ手順1の待ち条件」
   としてであり、「RECV完遂直後という新しい局面でこの値を読むことに
   意味があるか」自体は6節16項が既に「新しい推測を追加しない」
   という条件付きで許容した範囲（両ビット同時ポーリング）を超える。

### 結論

**(2)は今回は直さない。** 現行の「無条件再武装→bit0/bit1同時
ポーリング」構造（仕様書6節16項、暫定的な設計選択と明記済み）を
維持する。分岐点101・102の回数差1件は、この暫定構造が公式subの
内部分岐選択（未確定）を再現できていないことの表れであり、
新しい観測でも未確定の範囲を確定させることはできなかった。

次にここへ進むには、mainとsubを共通クロックで同時に捉えたログ
（`m6g-d0-boot-run{1,2}`のような）で、RECV完遂直後の時点での
bit1の値と、その後の実際の分岐先（直接再武装かSENDかを事後的に
確定できる後続イベント列）を突き合わせる追加解析が必要になる
（既存の共通クロックログが同じ状況を含んでいるかは未確認）。
