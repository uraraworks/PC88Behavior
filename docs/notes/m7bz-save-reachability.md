# m7bz: SAVEはWRITE受信位相の分岐で停止していた

実施日: 2026-08-22

## 情報境界

公式ROM一式＋公式diskAの使い捨て複製、および公式main ROM一式＋自作sub ROMを
同期実行した。複製側だけライトプロテクトを解除し、原本へは書いていない。
公式ROM・ディスクの内容や`private/`の中身は読んでいない。生iolog、混成ROM、
ディスク複製はリポジトリ外の`mktemp -d`配下だけに置いた。解析器と本稿が扱う
出力は件数、長さ、SHA-256、公開FDCコマンド名、記号化した要求種別だけであり、
`$FB/$FC/$FD`およびFDCデータの値は出していない。

## 測定条件

`tools/conform_l3.sh`条件5と同じ4200フレーム、300FでRETURN、700Fから
`10 PRINT "T"`→`SAVE"TQ"`を入力した。公式一式／混成それぞれについて、
ディスク複製のライトプロテクトを解除しない条件も対照に置いた。各実行には
300秒のタイムアウトを設けた。

| 構成 | 複製の保護 | WRITE件数 | バイト数 | 期待SHA-256 |
|---|---|---:|---:|---|
| 公式一式 | 解除なし | 0 | 0 | 判定不能 |
| 公式一式 | 解除 | 8 | 2112 | 一致 |
| 混成 | 解除なし | 0 | 0 | 判定不能 |
| 混成 | 解除 | **0** | 0 | 判定不能 |

したがってライトプロテクト解除は必要だが、混成の未到達原因ではない。
`conform_l3.sh`は既に複製のヘッダだけを解除しており、条件訂正は不要だった。

## 最初の分岐位置

画面ではなくI/Oだけで段階を判定した。同じ打鍵を受理したことの終端側の指標は、
両構成が同じ2バイトrunの直後に、同じ先頭種別のSAVEデータrunを開始したこと
である。つまりBASIC起動、プログラム行入力、SAVE文の解釈、SAVE前のディスク
読出しまで通過している。FDCコマンド種別列も先頭**80件**まで一致した。

| 指標 | 公式 | 混成 |
|---|---:|---:|
| FDCコマンド総数 | 124 | 80 |
| READ DATA | 19 | 16 |
| WRITE DATA | 8 | 0 |
| SAVE候補run直前 | 長さ2 | 長さ2 |
| 同じ先頭種別のSAVE候補run | **261** | **12** |
| 最初のWRITE DATA | frame 881 | なし |

分岐は混成がSAVE候補runの12件目を通常runとして閉じ、K00列Bの完了出力を送った
位置である。公式は同じ位置でrunを閉じず、261件目まで受信を継続する。

## 公式WRITE専用受信位相

`tools/analyze_save_reachability.py`で公式8runを全数検査した。通常RECVの
「1バイトごとに完了」ではなく、位置6以降だけ2バイト一組になっていた。

| 位置 | 規則 | 一致 |
|---|---|---:|
| 1〜5 | 各バイト後に完了・再アーム | 40/40 |
| 6〜260の偶数位置 | 完了せず次の1バイトを直接受信 | 1024/1024 |
| 7〜259の奇数位置 | 2件目の後に完了・再アーム | 1016/1016 |
| 261 | 完了するが再アームしない | 8/8 |

これにより、真因は自作subの汎用`RECV_BYTE`をWRITEデータにも1バイトずつ
適用していたことへ帰属する。自作main相手のWRITE自己検証も同じ単発位相を
使っていたため、両側で同じ誤解を共有していて検出できなかった。

解析器の自己検査は合成ログの無傷版で合格し、WRITE位置6へ完了を1件注入して
2バイト位相を壊す陽性対照で不合格になった。常に例外で落ちる検査器ではなく、
症状そのものを検出している。

## 現時点の判定と次の実装境界

この測定コミット時点では条件5は**未到達**（混成WRITE 0件）のままである。
実装は、先頭種別K00かつ位置5到達後だけ公式の固定256バイト（128対）受信へ
切り替える。長さ1のK00は位置5へ到達せず、WRITE以外の通常runも対象外になる。
実装後は期待値8件・2112バイト・SHA-256一致まで再測定し、自己検証側のmain
ドライバも公式の2バイト位相へ直す。期待値や合格条件は緩めない。

## 実装中断後の追加測定: 1件目の先にも別の共有誤解があった

第1測定を根拠に2バイト位相を仮実装すると、混成はWRITE 0件から**1件**へ
進んだが、期待8件に届かなかった。公式・混成を別々の使い捨て複製で再実行し、
最初のWRITEのデータ部は**256/256位置一致**した一方、公開FDCパラメータは
6/8位置一致（不一致はEOT/GPL位置）だった。値は出さず、公開形式の分類で
全8件を照合すると次のとおりだった。

| 公式WRITE境界・パラメータ分類 | 一致 |
|---|---:|
| 結果7件の直後は、TCやsub応答よりmainからの1バイト受信が先 | 8/8 |
| その受信は既測定の要求グループ2、後続送信は同応答分類 | 8/8 |
| 長さ261 run末尾からWRITE発行までにモータ制御出力1件 | 8/8 |
| 同区間にF7出力1件、TC入力0件 | 8/8 |
| WRITEデータ256件の直後・結果7件の前にTC入力1件 | 8/8 |
| EOTは媒体形状（1トラックのセクタ数） | 8/8 |
| GPLは公開uPD765形式のN=1短GAP分類 | 8/8 |

仮実装は逆に、WRITE結果直後へTC三つ組みを置き、続けて明示的に1バイト応答を
送っていた。そのため1件目の結果後に公式mainが送ろうとする1バイトと衝突し、
相互待ちになった。既存の自作mainも「WRITE直後に応答受信」としていたので、
単発WRITE自己検証ではこの誤解を再び共有していた。

`tools/analyze_save_reachability.py`へ上表6条件を追加した。合成ログ無傷版は合格し、
結果直後へTCを先行、結果後応答分類を破壊、WRITE直前へTC入力を追加、
データ直後TCを欠落、EOT分類を破壊する5故障、および
従来の位置6単発化をそれぞれ不合格として検出した。したがって実装境界は、
WRITE直前を「モータ制御出力・F7出力・TC入力なし」、データ直後を「TC入力」
とし、結果後は明示応答を送らず汎用受信ディスパッチへ戻すことになる。

なお最初の追加測定記述では`OUT F8`を「TC出力」と誤記した。第三者エミュレータの
公開I/O実装（`vendor/quasi88-libretro/src/pc88sub.c`）と既存仕様1.21節を再確認し、
`OUT F8`はモータ制御、TCは`IN F8`だと訂正した。履歴は消さず本訂正を残す。

結果後の最初の受信・送信値も既存の記号分類だけで照合したところ、受信は
要求グループ2、送信はその既測定応答分類に8/8一致した。したがって新しい応答値は
不要で、WRITE完了時に読み出し後専用の保留状態を残さず、既存の要求グループ2
決定表へ渡すのが実装境界となる。

## 7件目後のREAD保留状態

WRITE直前へ公式と同じSEEK→SENSE INTERRUPT→SENSE DRIVEを接続すると、混成は
7件・1848バイトまで進んだ。公式のWRITE #6/#7後はどちらも受信run長が
`1,5,1,261`で、その間にREAD DATA 1件を挟む。混成も#6後は同じrun長と
FDCコマンド種別列で#7へ進んだが、#7後は長さ1だけで停止した。

停止した長さ1の受信は公式・混成とも要求グループ2分類だった。公式応答は
WRITE応答分類に一致する一方、混成は不一致だった。混成内部では直前READが
`SECTOR_READY`と`POST_BULK_ACTIVE`を保留したままmainが次のWRITEへ移っており、
WRITE結果後の要求グループ2が読み出し後専用経路に横取りされていた。したがって
WRITE完了は、未消費のREADデータ保留を無効化し、POST交換を既存終端状態へ畳んで
から要求グループ2決定表へ戻す必要がある。これは公式#7後の要求・応答分類と、
混成#6/#7の状態遷移の両方で識別された規則である。

## 条件5の実行状態分離

上記実装で手動の新規混成ROMディレクトリからSAVEを走らせると、WRITEは
8件・2112バイト・期待SHA-256一致となった。一方`conform_l3.sh`は、条件1の
1800フレーム実走に使った同じ混成ROMディレクトリを条件5でも再利用しており、
同順序を単独再現すると件数・バイト数は同じでもSHA-256だけが変化した。
コアはROMディレクトリ側に実行状態ファイルを置くため、独立な適合条件間で状態を
持ち越していたのが原因である。

条件5用の混成ROMディレクトリを公式main一式と現在の自作subから新規構築するよう
訂正した。期待値・フレーム数・打鍵・ライトプロテクト条件は変更しておらず、
合格しやすくする緩和ではなく「独立条件へ前段の状態を混入させない」修正である。
また公式環境未設定時の`conform_l3.sh`本体SKIPを`run_all_selftests.sh`がOK表示して
いた穴を、結果表の明示的なSKIP表示と故障注入つき自己検査で塞いだ。

新規ディレクトリ化だけではまだ不十分だった。`build_mixed_rom`の旧`cp *`は
公式ROMと同じディレクトリにコアが置く実行状態ファイルまでコピーしており、
公式側の前段実走が更新した状態を新規混成へ再注入していた。ディレクトリ一覧の
拡張子だけを用いてコピー対象をROMファイルへ限定した。公式ファイルの中身は
読んでおらず、個別ファイル名や絶対パスもスクリプトへ焼き込んでいない。

## 実装と容量

最終実装は、WRITE種別かつwindow位置5だけをゲートに、残る256件を128組の
2バイト位相で受信する。長さ261 run後はモータ制御、制御レコード由来Cへの
SEEK、SENSE INTERRUPT、SENSE DRIVE、F7の順でWRITEへ入り、データ256件後に
TC入力する。結果7件後は明示応答せず汎用受信へ戻る。EOT/GPLは第68版の公開
パラメータ分類へ訂正し、未消費READ状態を無効化して要求グループ2へ戻す。
自作mainと`check_l3_write.py`も同じ公式境界へ訂正した。

コード長は第66版の2026バイトから**2046/2048バイト**となった。機能追加を
そのまま積むと2072バイト相当になるため、次の挙動不変圧縮を入れた。

| 圧縮 | 削減 | 挙動不変の根拠 |
|---|---:|---|
| `FDC_TIMEOUT_MARK` / `FDC_BEGIN` / `FDC_TC`のAF保存除去 | 6 | 下記の全呼出元監査で、戻り後にAを上書き・復元・不使用 |
| SENSE INTERRUPT末尾を`RET Z`/`JP FDC_IN`化 | 2 | 旧`JR Z`/`CALL`/`RET`と戻り先・最終A・スタックが同じ |
| 起動時連続状態11バイトをゼロループ化 | 18 | 旧個別初期化と同じ連続RAM範囲。追加で`FDC_ABORT`も0、B/HLは直後不使用 |

### AF保存除去の全呼出元監査

- `FDC_TIMEOUT_MARK`は2箇所。`FDC_IN`正常中断は直後にAへ中断値をロードし、
  故障注入経路は直後のFDC入力でAを上書きする。`FDC_OUT`は入口でAFを保存済みで、
  正常・故障注入の両経路とも出力前または復帰前にそのAFを戻す。
- `FDC_BEGIN`は8箇所。SPECIFY、SENSE INTERRUPT、RECALIBRATE、SENSE DRIVE、
  WRITE、READ、BULK READは直後にコマンド語をAへロードする。SEEKだけは入口で
  目的CをAF保存し、`FDC_BEGIN`後に復元する。
- `FDC_TC`は2箇所の末尾呼び出し（単一READ/BULK READ）。いずれも戻ったAを
  呼出側が観測せず、次の状態ロードまたはディスパッチへ進む。

静的監査に加え、`verify_l3.sh`で通常版と既存の全故障注入（タイムアウト後読出し、
SENSE結果数、WRITE窓・座標・応答を含む）を実走し、正常版だけが適合、注入版は
すべて症状を検出した。

## 最終実測

| 項目 | 結果 |
|---|---|
| 条件5 | WRITE **8件・2112バイト・期待SHA-256一致** |
| 条件1 | 公式・混成とも**5635件・SHA-256一致** |
| 再アーム | 必要**66/66**、空振り**0**、未解決0 |
| 最初の非データ差 | **7036件目**（m7bwから後退なし） |
| WRITE自己検証 | データ窓**256/256**、座標一致、応答**1件** |
| 生成コード | **2046/2048バイト** |
| `verify_l3.sh` | rc=0、既存故障注入をすべて不合格検出 |
| `conform_l3.sh` | 環境変数設定下で本体を実行、rc=0（diskB任意条件だけSKIP） |
| `run_all_selftests.sh` | C/ja_JP.UTF-8の**32/32項目**がrc=0、NG 0・Traceback 0・本体SKIP行0 |

条件5の根拠は自己検証ではなく、公式main＋自作sub＋公式diskA使い捨て複製の
混成実走である。期待値・フレーム数・打鍵列は変更していない。
