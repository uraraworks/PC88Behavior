# M — 漢字（全角）の描画経路調査

日付: 2026-08-08

`docs/spec/l2-font.md` 7節「残っているもの」の
「漢字（全角）の描画経路は未測定」を受けた調査ノート。
**今回はコードを読んだだけで、実測（自作ROM・自作IPL）までは進めなかった。**
理由は3節で述べる。読んだファイルはすべて `vendor/quasi88-libretro/src` 配下の
BSD-3 コード（公式ROMではない）。バイト列は読んでいない。

## 0. 観測と推定の分け方

`l2-font.md` 第0節と同じ約束。観測はコードを読んで機械的に確定する事実。
推定はこちらの解釈。**実装（もし今後やるなら）は観測に従う。**

## 1. 観測 — テキスト画面の文字コード→字形変換に漢字経路は無い

- `get_font_gryph()`（`crtcdmac.c:703-751`）が文字コード→グリフ変換の
  唯一の関数（`l2-font.md` 第2節と同じ関数）。この関数内に
  `kanji_rom` への参照は無い（`grep -n kanji crtcdmac.c` はヒット0件）。
  分岐は `ATTR_GRAPH`（半角グラフィック文字か通常ANKか）だけで、
  「全角（2バイト）」に相当する属性ビットは存在しない
- `crtcdmac.c` で定義されている属性ビットは
  `ATTR_GRAPH`(0x10)・`ATTR_UPPER`・`ATTR_LOWER`・`ATTR_REVERSE`・
  `ATTR_SECRET`・`COLOR_MASK` のみ（`grep -n "define.*ATTR_" crtcdmac.c`）。
  `ATTR_KANJI` に類するものは無い
- `text_attr_buf[]` は 1 文字（1 桁）につき `unsigned short` 1 個
  （`screen-vram.h:26-27` の `text_attr_buf[...]` 宣言、`COLUMN_SKIP` は
  80桁/40桁の切替のみに使う）。**1桁=1コードという構造そのものが、
  2バイト（全角）を1セルとして扱う仕組みを持っていない**
- `screen-vram*.h`（`screen-vram-full.h`, `screen-vram-400.h`,
  `screen-vram-200.h` 等）にも `kanji` の文字列は一切現れない
  （`grep -rn kanji screen-vram*.h` はヒット0件）

**結論（観測）**: このコードベースの「テキストVRAM→CRTC→画面」という
経路（`l2-font.md` が確定させた ANK の経路そのもの）には、
**漢字（全角）を扱う分岐が存在しない。** ANKが受ける「400ライン時に
縦2倍」という規則（`l2-font.md` 第2節）は、この関数を通る文字だけに
適用される規則であり、**漢字はそもそもこの関数を通らないので、
「同じ規則を受けるか」という問いの前提が成立しない。**

## 2. 観測 — 漢字ROMへのアクセス経路はI/Oポート経由のみ

`pc88main.c` に漢字ROM読み出しの実装がある。

- `kanji1_addr` / `kanji2_addr`（`pc88main.c:76-77`。型は `pair`、
  つまり 16bit のアドレスレジスタ）
- アドレス書き込み: `OUT` ポート `0xE8`/`0xE9` が `kanji1_addr` の
  下位/上位バイトを、`0xEC`/`0xED` が `kanji2_addr` の下位/上位バイトを
  セットする（`pc88main.c:1178-1192` 周辺のコメント
  `/* OUT[E8-E9] 漢字ROM(第1) ADDR */` 等）
- データ読み出し: `IN` ポート `0xE8` が `kanji_rom[0][kanji1_addr.W][1]`、
  `0xE9` が `kanji_rom[0][kanji1_addr.W][0]`、`0xEC`/`0xED` が
  `kanji_rom[1]` 側の同型アクセス（`pc88main.c:1470-1482`、
  コメント `/* 漢字ＲＯＭ フォント入力 */`）

**結論（観測）**: 漢字ROMは **アドレスをポート出力→データをポート入力**
という、CRTC/DMACのテキスト表示経路とは完全に独立した I/O ポート経由の
アクセス機構である。**画面に文字として自動的に出るハードウェア機構
（CRTC側のテキスト属性）は存在しない。** 何かを画面に出すには、
ソフトウェア（N88-BASIC の漢字表示ルーチン、あるいは利用者プログラム）が
このポート経由でビットパターンを読み出し、**グラフィックVRAMへ
自分でビット単位に書き込む**しかない。

これは(a)ハードウェアの事実（ポート番号・アドレス指定/データ読み出しの
手順）であり、`CLAUDE.md` の資料分類でいう「読んでよい」種類の情報である。
**そのソフトウェア側の書き込み手順（どの順で何ライン書くか）は
N88-BASIC ROM の内部実装であり、これは読んでいない・読めない
（L3相当、禁止事項1・2の対象）。**

## 3. 今回はここで止める理由

計画（タスク指示）は「自作の合成漢字ROMを置き、自作IPLに全角指定の
手順を実装して画面に出す」ことを求めていたが、2節の観測により
**その前提（テキストVRAM側に全角を指定するアトリビュートがある）が
成立しないことが分かった。**

代替として「グラフィックVRAMに自分で（BASIC ROMを介さず）ビットパターンを
書き込むIPLを新規に書く」ことは技術的には可能だが、それをやるには
今回のIPL（`src/l1_ipl/make_ipl_rom.py`、テキスト画面DMA初期化までしか
実装していない）に**グラフィック画面のCRTC/DMAC初期化を新規に追加する**
必要があり、これは「漢字フォントの縦倍化を測る」というL2の範囲を超えて
**新しいL1機能（グラフィック画面初期化）の実装**になる。
指示の「全角表示の手順がL3相当の知識を要して今回の範囲を超えるなら、
そこまでで止めて報告する」に該当すると判断し、ここで止める。

## 4. 派生して分かったこと（参考。今回のスコープ外だが記録する）

2節を確認する過程で `screen-vram-400.h` の `TRANS_8DOT`/`STORE_8DOT`
マクロ（`crtcdmac.c` の外、グラフィックVRAMをテキストと重ね描画する
経路）を読んだ。**フォントとグラフィックVRAMでは扱いが異なる。**

- フォント（ANK）は `IF_LINE200_OR_EVEN_LINE()` により、400ライン時
  `k`（0-19の文字セル内ラスタ位置）が**偶数のときだけ**新しいバイトを
  読む＝縦2倍（`l2-font.md` 第2節、既知）
- 一方グラフィックVRAM側のポインタ参照 `*(src + k * 80)`
  （`screen-vram-400.h:20-30` の `TRANS_8DOT`/`STORE_8DOT`）は
  **`k` の値ごとに異なるアドレス**を読む。偶奇による間引きが無い。
  **400ライン時、グラフィックVRAMの内容はCRTC/描画側で縦2倍されない**
  （ソフトウェアが自分で複製しない限り、1ラスタ=1バイトの実データ）

**推定**: もし将来グラフィックVRAMへ漢字ビットマップを書くIPLを作るなら、
「縦に伸ばして見せたい」場合はソフトウェア側（書き込むコード）が
自分で行単位を複製する必要があり、ハードウェアが勝手に倍化はしない。
これはあくまでコードから読んだグラフィックVRAM側の一般則であり、
**漢字が実際にこう描かれるという確認ではない**（BASIC ROMの
書き込みルーチンを読んでいないため）。

## 5. ピクセルのアスペクト比（要因の切り分け。指示どおり別項目として測定）

`LIBRETRO/libretro.c` の `retro_get_system_av_info()`
（`libretro.c:864-873`）:

```
info->geometry.base_width   = WIDTH;   /* = 640 (screen.h の SIZE_FULL 640x400 と整合) */
info->geometry.base_height  = HEIGHT;  /* = 400 */
info->geometry.aspect_ratio = 1.6;
```

`1.6 = 640 / 400` と完全に一致する。**申告アスペクト比は解像度そのものの
比であり、実機CRT（4:3）に合わせた補正は含まれていない。**
libretro フロントエンドはこの申告値どおりに正方形ピクセルとして
表示・拡大するのが標準的な挙動なので、**「縦長に見える」という印象が
あるとすれば、それはこのコアの申告アスペクト比が作り出しているのではなく、
別の要因（実機CRTの物理縦横比、あるいはフロントエンド側の追加設定）に
よるものである。** このコア自体は 640x400 を等倍（正方形ピクセル）
として扱えという申告をしている。

## 結論まとめ

| 問い | 結論 | 根拠の種類 |
|---|---|---|
| 漢字はテキストCRTC経路で縦2倍されるか | **経路自体が存在しない**（ANKの規則は適用対象外） | 観測（コード） |
| 漢字ROMはどう読むか | I/Oポート `E8/E9`（第1）・`EC/ED`（第2）でアドレス指定→データ読み出し | 観測（コード、ハードウェア事実） |
| 画面に出すには何が要るか | ソフトウェアがグラフィックVRAMへ自分で書く。その書き込み手順は今回未調査（BASIC ROM内部＝L3） | 観測＋範囲外の明示 |
| グラフィックVRAMは400ライン時に縦2倍されるか | **されない**（`k`ごとに異なるアドレスを読む。フォントとは扱いが違う） | 観測（コード） |
| ピクセルのアスペクト比 | コア申告値 `1.6 = 640/400`。正方形ピクセル相当で、縦長化の補正を含まない | 観測（コード） |
