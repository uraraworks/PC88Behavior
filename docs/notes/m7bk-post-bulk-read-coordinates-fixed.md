# m7bk: バルク直後のREAD座標が一致した——食い違いはREAD完了後の応答へ移った

測定日: 2026-08-19

## 情報境界

公式ROM一式・公式diskA（`private/disk`配下の複製）を**実行して**測定した。
読んでいない。測定はメインセッションが公式環境で1800フレームの混成ROM実走
（比較対象は同条件の公式ROM実走）を行い、その結果を本ノートに転記している。
本セッションは再測定していない。座標（C/H/R）はFDCコマンドのパラメータで
あり、ディスクの内容ではない。

## 1. 経緯——`7c3be9e`は実走では効いていなかった

`docs/spec/l3-subrom.md` 1.36節（m7bj）は、受信runの先頭バイトがrun長を
一意に決める表引きであることを確定させ、`7c3be9e`でこの表引きを実装した。
ところが公式main実走で再測定すると、`7c3be9e`はバルク直後の挙動を
**何も変えていなかった**——受信run長は依然`[6,1,1]`（公式は`[5,1,1,1]`）の
ままで、READ DATAは0回、代わりにSENSE DRIVE STATUS(0x04)が128回連発する
という、m7bg時点（READ 11回）からの**後退**が起きていた。

原因は、`7c3be9e`が表引きを**「終わったrunの分類」**（SEND側で、受信済みの
runを見てどの応答を返すか決める後付け判断）にしか使っておらず、
**「受信を打ち切る判断」**（RECV側で、何バイト受け取ったらrunを終えるか）
には結線していなかったこと。受信ループは相変わらずbit1（run終了合図）
だけでrunを区切っていたので、先頭バイト0x02・run長5の判別は一度も
発火していなかった。

**「分類器」と「打ち切り判断」は別物である。** 同じ表を指していても、
どちらの用途に結線するかで効果が全く変わる。表を導入したこと自体は
正しくても、結線先を間違えると観測上「何も変わらない」どころか
「後退する」——今回は表引きが無かった場合よりも悪い状態（SENSE DRIVE
STATUS連発）になった。表引きの導入と、その結線先の検証は別工程として
扱う必要がある。

## 2. `b1b0f3a`——打ち切りを結線し、バルク完走後に限定するゲートを追加

`b1b0f3a`は、受信runの打ち切りそのものを先頭バイトの表引きで行うよう
修正した：先頭バイト0x02・`RUN_LEN==5`に達した時点で、bit1を待たず
`_general_read_request`へ直接分岐する。

これを最初は無条件（ゲート無し）で公式main実走に適用したところ、
**起動時交換#6/#7/#11/#12/#14自身の要求**（先頭バイトが0x02と衝突しうる）
まで誤って打ち切ってしまい、**起動時バルク転送そのものが0件になる**
致命的な後退が起きた。バルク転送の先頭付近にも先頭バイト0x02・長さ5の
並びが偶然含まれており、無条件の打ち切りはそこも「READ要求」と誤認する。

このため、バルク完走後にのみ1を立てる新しいRAMフラグ`POST_BULK_ACTIVE`を
追加し、1.36節の打ち切りをこのフラグと`EXCHANGE3_REQUEST_ACTIVE==0`の
両方でバルク後に限定した。これによりバルク5635件は再び完走し、その上で
バルク直後の最初のrunが公式と同じ長さ5で切れるようになった。

**ゲートが必要だった理由は、表引きの対象範囲が「バルク後の要求」だけに
限られていたこと（1.36節が未確定として残した種別を除く）である。**
表そのものは正しくても、どの区間で適用してよいかは別の情報で、
m7bjの測定はそこまでは扱っていなかった。

## 3. 結果——座標は完全一致、食い違いはREAD完了後の応答へ移った

| 指標 | 公式 | 自作(`b1b0f3a`) |
|---|---|---|
| バルク後の受信run長 | `[5,1,1,1]` | `[5]` |
| 最初のREADまでの受信件数 | 5件 | 5件（一致） |
| READ座標 (C,H,R) | (18,1,13) | (18,1,13)（**完全一致**） |
| バルク後のFDCオペコード | 0F/08/04/06 各1件 | 同じ |
| バルク後の受信の値一致 | — | 5/5一致 |
| バルク後の送信の値一致プレフィックス | — | 1件（自作はackを出さずに止まる） |

バルク後のイベントの並び（種別のランレングス。値は見ていない）:

- 公式: 送信1 / 受信5 / FDCコマンド4 / FDC結果2 / FDCコマンド2 / FDC結果1 /
  FDCコマンド9 / FDC結果263 / **受信1 / 送信1 / 受信1 / 送信256**
- 自作: 同じ並びを**FDC結果263まで完全に再現し、そこで止まる**

m7bhが指摘した「バルク直後の読み出し座標が違う」（公式(18,1,13)対自作
(6,1,6)）は**解消**した。原因はm7bjが既に特定していたとおり、自作が
6バイトで区切っていたためレコードの座標フィールド位置が1つずれていた
ことにあり、`7c3be9e`/`b1b0f3a`でその区切りを長さ5の表引きへ正しく
結線したことで解消した。

食い違いは**READ完了後の応答**へ移った。公式はFDC結果263（READのデータ
フェーズ）の後、受信1（1バイトack相当）→送信1（ackへの応答？）→受信1→
送信256（次のセクタデータ）と続くが、自作はFDC結果263で止まり、以降の
イベントを一切出していない。

## 6. この節の教訓

**「表を作ったこと」と「表を正しい場所に結線したこと」は別の主張であり、
別々に検証する必要がある。** `7c3be9e`は表引きを実装したと報告していたが、
実走で確かめるまで「終わったrunの分類にしか使われていない」ことに
気づかなかった。表がある＝効いている、ではない。結線先まで実走で
確認して初めて「効いた」と言える。

また、無条件の打ち切りが起動時バルク転送を破壊した経験は、
**「今回直したい区間の外」への適用範囲の広がりを常に疑う**必要が
あることを示す。先頭バイトの値は区間によって意味が変わりうる
（起動時の交換#6/#7/#11/#12/#14の先頭バイトとバルク後READ要求の先頭バイト
が偶然一致しうる）ので、表引きは無条件のグローバルルールではなく、
どの区間で有効かという文脈情報とセットで扱う必要がある。
