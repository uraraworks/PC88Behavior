# M6p — `$F8`（TC）と`$F7`の関係、FDCコマンド結果フェーズとの位置関係

測定日: 2026-08-12
対象: 混成ROM（自作sub＋公式main）を公式環境で実走した診断（`last.txt`）が
示した分岐点28（sub側の構造的一致プレフィックスが27件で切れる箇所）。
基準ログ（公式サブROM）側では、この直前が「`OUT $FB`→`IN $FA`×2→`IN $FB`
→`IN $FA`→`IN $FB`」（FDCコマンドの結果フェーズ）で終わり、直後に
`OUT $F8 pc=06D5` が来るが、自作subはここで`$FE`ハンドシェイクへ戻って
しまっていた。本稿はこの`OUT $F8`が何なのかを、既存ログの再解析だけで
確定させる。

**追加測定は行っていない。** 既存の `measurements/m6c-sub-{d0-boot,
d1-files,d2-save,d5-seqfile}.iolog.txt.gz`（4条件、同一の公式サブROM
バイナリ）を再解析した。値は `$F7`/`$F8`/`$FF` のみ見た。`$FA`/`$FB`/
`$FC`/`$FD` の値は見ていない（これらのポートは`tools/redact_iolog.py`が
`$FB`/`$FC`/`$FD`を伏せ字化済みだが、今回の指示は`$FA`も含めて値を見ない
ことなので、`$FA`の値はログ上残っているものの本稿の判断には一切使って
いない。件数・pc・kindのみを使った）。

新規解析器: `tools/analyze_tc_and_f8.py`。`tools/analyze_fdc_ports.py`の
`IoEvent`/`parse_iolog`をimportして再利用（二重実装しない）。

再実行方法:

```
python3 tools/analyze_tc_and_f8.py cross \
    --iolog d0-boot   measurements/m6c-sub-d0-boot.iolog.txt.gz \
    --iolog d1-files  measurements/m6c-sub-d1-files.iolog.txt.gz \
    --iolog d2-save   measurements/m6c-sub-d2-save.iolog.txt.gz \
    --iolog d5-seqfile measurements/m6c-sub-d5-seqfile.iolog.txt.gz \
    --out measurements/m6p-tc-and-f8-cross.txt
```

## 1. 確定: `OUT $F8,0x07` → `OUT $F7,0x08` → `IN $F8`(常に`0xFF`) は
固定の三つ組みで、4条件すべて・全事例で例外なく隣接して現れる

`$F7`/`$F8`のみを抜き出した列で直後関係を見ると、4条件すべてで

```
OUT $F8@06D5(=0x07)  →  OUT $F7@036E(=0x08)  →  IN $F8@0332 or 03C2(=0xFF)
```

が例外なく連続する（隣接ペアの集計、d0-boot: 9/9・9/9、d1-files:
16/16・16/16、d2-save: 23/23・23/23、d5-seqfile: 35/35(pc=0332)+8/8(pc=03C2)・
同数）。`OUT $F7`の値は全事例で`0x08`固定（1.16節手順1と同じ語彙、同じ
pc=`036E`）。`IN $F8`の値は全事例で`0xFF`固定（複数回ポーリングする
ビジーウェイトではなく、1回だけ読んで確認する単発チェック）。

**この三つ組みは1.16節が確定させた起動時の単発`OUT $F8,0x05`/
`OUT $F8,0xFF`（pc=`00F9`/`0103`、直前FBアクセス無し）とは別物。**
起動時の2件は1条件につき各1回のみで`直前FB=None`、三つ組みの方は
「直前に`$FB`アクセスがある（`last_fb_kind`が常に`IN`）」という条件で
一貫して現れる。

## 2. 確定: 三つ組みは「結果フェーズが終わった直後」に現れるが、
「結果フェーズが終わるたび必ず」ではない

`IN $FB`の連続run（間に`$FA`ポーリングを挟んでも`$FB`アクセスの
kindがINのまま続く限り同一runとみなす）の直後に来るイベントを
機械的に分類した。

- runの直後が即座に`OUT $F8@06D5`（=このTC）になる事例は
  4条件とも**必ず5件**（run長の内訳は`{2,2,3591,4103,4103}`で
  4条件間で完全一致）。
- 一方、run長`2`（2バイト結果。SENSE INTERRUPT STATUS相当の
  ST0+PCNパターンと合致するバイト数）自身は各条件で14〜40件出現するが、
  その大半（14/16、21/23、28/31、40/43）は直後に**別の`OUT $FB`
  （次のFDCコマンドの先頭）へ直接進み、TCを経由しない**。
  run長`263`（=256+7。1セクタ分のデータ読み出し＋7バイト結果フェーズと
  合致するバイト数）も同様に、大半（5/5〜23/23のうち、直後が即TCなのは
  0件）は次コマンドへ直接進む。
- ただし「直前の（最も近い）`IN $FB` runの長さ」という基準（間に他の
  イベントを挟んでもよい）で見ると、全11〜44件のTCすべてに何らかの
  run長が対応する。長さの内訳（d0-boot）: `{2:3, 263:4, 519:1, 3591:1,
  4103:2}`。4条件間で長さの集合は一致し、件数は条件の重さ（ディスク
  操作の量）に応じて263系列だけが増える（d1-files:11, d2-save:17,
  d5-seqfile:21、他は全条件で同数）。

**解釈（確定できる範囲）**: TCの三つ組みは個々のFDCコマンド呼び出し
1回につき1回ではなく、**複数のFDCコマンド呼び出しから成る一連の
バッチ（例: RECALIBRATEをトラック0まで繰り返す一連の呼び出し、
1セクタ読み出しの一連の呼び出し）の最後にだけ**現れる。バッチの
区切り条件そのもの（何をもって「このバッチは終わり」と判断している
か）は、`$FA`/`$FB`の値を見ない本解析の範囲では確定できない
（3節へ）。

## 3. 確定: `$F8`の方向は主に`OUT`。`IN $F8`は三つ組み専用の単発読み

4条件合計の内訳（`OUT $F8`はpc=`06D5`が主、pc=`00F9`/`0103`は起動時
各1回。`IN $F8`はpc=`0332`または`03C2`のみ）:

| | OUT $F8 | IN $F8 |
|---|---:|---:|
| d0-boot | 13 | 9 |
| d1-files | 20 | 16 |
| d2-save | 27 | 23 |
| d5-seqfile | 39 | 35 |

`OUT`が常に`IN`より多い（起動時の2件の差にほぼ一致）。**`IN $F8`は
`OUT $F7`の直後にのみ、三つ組みの一部として現れる。それ以外の文脈
（`OUT $FB`直後・`IN $FB`直後・任意の位置）では一度も`IN $F8`が
観測されなかった。** `IN $F8`が独立した状態確認ループとして多数回
ポーリングする使われ方は、この4条件のログには存在しない。

**結論**: 自作sub（`src/l3_service/make_subrom.py`）が`P_TC`(`$F8`)を
`IN`で61回読んでいたのは、方向の取り違えである。公式subの`$F8`は
「送る（`OUT`）」が主体で、`IN`は三つ組み専用の単発確認読みに限られる。
`make_subrom.py`379行目のコメント「`IN: FDC へ TC（ターミナルカウント）
を送る`」（vendor実装のコメントに由来）はこの意味で誤り——**TCは
`OUT`で送るもの**であり、`IN`は送った後の確認読みでしかない。

## 4. 分岐点28の自作sub側コードパスの特定

診断が指摘した分岐点28（起動直後、初めての「結果フェーズ完了→TC」
イベント）は、自作sub側では`BOOT_HANDSHAKE`（手順8）が呼ぶ
`FDC_SPECIFY`に対応する起動位置にあたる。ただし`FDC_SPECIFY`単体は
μPD765仕様上コマンドフェーズのみ（結果フェーズ0バイト）であり、
本節1.・2.で確認した「結果フェーズ直後」という構造そのものが
起きない。自作subは`inject_spurious_sense_int`（デバッグ用フラグ、
既定False）を有効にしない限り、起動時に一度も`$FA`/`$FB`の
結果フェーズを経由せず`MAIN_LOOP`（`$FE`ハンドシェイク）へ直行する
——これが分岐点28で自作subが「結果フェーズ直後のTC」を出せない
根本原因である（公式ROMの起動直後の最初のFDCコマンドが何であるかは
コマンド語(`$FB`書き込み値)を見ないため特定できないが、結果フェーズ
2バイトを伴う点はSENSE INTERRUPT STATUS系と符合する）。

自作sub内でTCに対応する既存コードは、`FDC_READ_SECTOR`終端の
`a.in_port(P_TC)`（1048行目、256バイトデータ転送後・7バイト結果
読み出し**前**に`IN`している）のみである。1.・2.節の確定（TCは
`OUT`であり、かつ本稿2節で確認した「263=256+7」という長さの一致
から、公式ROMでは**データ＋結果フェーズの計263バイトを読み終えた後に
TCが来る**）と照らすと、`FDC_READ_SECTOR`の現在の実装は次の2点で
既存の測定と食い違う。

1. 方向: `IN`ではなく`OUT`であるべき（3節）。
2. 位置: 7バイト結果フェーズを読む**前**ではなく**後**であるべき
   （本節、263バイトのrun長が結果フェーズ込みで一つのTCに対応する
   ことから）。

`FDC_SEEK`/`FDC_RECALIBRATE`/`FDC_SENSE_*`にTCを追加すべきかは、
2節で述べた「バッチ境界条件が未確定」のため**確定できない**。
これらの呼び出し単体（run長`2`や`1`）はTCを伴わない事例が大半であり、
安易にTCを追加すると公式ROMには無い過剰なTCを発行することになる
リスクがある。今回は追加しない。
