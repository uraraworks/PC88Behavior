# m7n: sub側173件目と交換#3要求の分節

測定日: 2026-08-13

## 1. 目的と情報境界

`tools/diag_l3_mixed.sh --brief`を公式main一式＋自作sub ROM、diskA起動、
1800フレームで再実行し、公式基準ログと混成ログを共通クロック上で比較した。
公式ROM・公式ディスク・通信データの値列は読まず、混成ログは解析前に
`tools/redact_iolog.py`で伏せた。以下はCPU、方向、ポート、件数、順序だけを
使った結果である。比較器の自己検査a〜lは全件合格した。

## 2. 173件目の構造差

sub側の畳み込み後構造列は172件まで一致した。直前のRECV完遂から次のRECVへ
移る境界で、公式subは受理解除フェーズを終えた後にいったん`IN $FE`のアイドル
待ちへ戻り、次の受信開始フェーズを`OUT $FF`で提示してから`IN $FE`のデータ
準備待ちへ進んだ。173件目はこの準備待ちである。

自作subは受理解除フェーズの直後に次の受信開始フェーズを先出しし、アイドル
復帰を省いて継続受信ポーリングへ入った。このため連続する2回の`OUT $FF`が
畳み込みで1件に縮まり、173件目では公式が`IN $FE`待ち、自作が受信フェーズを
進めた後の`IN $FC`となった。FDCコマンド発行や多バイト送信そのものが173件目
なのではなく、その前段のRECV境界の選択が相違点である。

## 3. 交換#3要求の分節

公式基準ログの交換#3要求区間を共通クロックで再集計すると、main側では8件の
要求としてまとまる一方、sub側RECVは次の構造に分節されていた。

1. 2件を受信し、アイドル待ちへ戻る。
2. 5件を連続受信する。
3. FDCのREAD系アクセスを行う。区間内は`$FA`/`$FB`だけで566件あり、
   `$FC`/`$FE`/`$FF`の通信アクセスは挟まらない。
4. アイドル待ちから最後の1件を受信し、1バイト応答へ移る。

最初の2件と次の5件の間にはFDCアクセスが0件であり、173件目は手順1から2へ
移るアイドル境界に対応する。交換#3の要求内容の意味、および2/5/1という分節を
選ぶ内部判定根拠は未確定である。値による判定は行っていない。

## 4. 測定時点の到達点

- sub側構造的一致プレフィックス: 172件
- main側構造的一致プレフィックス: 258件
- main側単発送受信列の値一致プレフィックス: 4件
- 混成照合のmain `IN $FD`: 0件

生ログと一時解析物はリポジトリ外に置き、コミットしない。

## 5. 第32版実装後の再測定

仕様1.25節・6節24項だけを根拠に、交換#3要求の進行状態をRAMへ追加した。
最初の2件後は要求ポインタと件数を保持してアイドルへ戻り、通算7件でFDCから
実データを準備し、最後の1件後に交換#3の単発応答を保留する構造とした。
新しい要求値判定は追加していない。

同条件の混成実走では、sub側構造的一致プレフィックスが172件から202件へ
伸びた。main側構造的一致プレフィックスは258件、main側`IN $FC`値一致
プレフィックスは4件、混成`main IN $FD`は0件で、いずれも変化しなかった。

次のsub側203件目は、公式subがFDC READ系へ入る直前に`OUT $F8`を1件発行する
のに対し、自作subが直接`IN $FA`へ進む差である。制御出力の値と意味、ここで
発行される理由は今回確定していない。期待値や比較条件は変更していない。

`tools/verify_l3.sh`では既存の交換#3/#4・FDC・負の検出力試験が通り、既知の
ディスク無し時I/Oだけが引き続き不適合だった。`tools/conform_l3.sh`は公式一式の
本番照合に合格し、混成照合は対象0件で不適合だった。
