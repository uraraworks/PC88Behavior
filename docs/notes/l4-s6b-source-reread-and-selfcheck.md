# l4-s6b(準備): GW-BASICソース再読と予測器の自己整合性チェック

実施日: 2026-09-19
状態: 測定前の準備作業のみ。**本ノートは公式ROMを一切使っていない。**
根拠は (1) GW-BASIC(MIT公開ソース)の再読、(2) `tools/l4_mbf_oracle_v3.py`
自身の内部計算をPython上で突き合わせた自己整合性チェックのみ。

## 位置づけ

`docs/notes/l4-s6a-transcendental-functions-results.md`の不一致腕
(N4 SIN(100)・C4 COS(100)・T4 TAN(100)・T2 TAN(.5)・N6 SIN(6.283185)・
N7 SIN(1000000))について、実装(l4_mbf_oracle_v3.py)側に命令単位の
読み違いが無いかを、公式ROMを使わずに先に確認する(タスク手順1)。

## 1. 範囲縮約(RR/RR1/RR2/RR3)・SIN/COS/TANの再読

GW-BASIC(MIT公開ソース、コミット`edf82c2ebf6bfe099c2054e0ae125c3efe5769c4`、
`MATH1.ASM`)の952-1143行を再取得して読み直した。`tools/l4_mbf_oracle_v3.py`
の`_rr_reduce`/`_frac_part_double`/`_sin_core`/`sin_impl`/`cos_impl`/
`tan_impl`と1行ずつ突き合わせた結果、以下を確認した(**食い違いは見つから
なかった**):

- `RR`は`$IN2PI`(倍精度1/(2π))を`$CDS`で倍精度化した引数に`$FMULD`で
  掛け、`RR3`(`$DINT`で整数部)・`RR2`(`$FSUBD`で減算後`$NEG`)を経て
  `frac(x/2π)`を倍精度のまま得る。`_rr_reduce`/`_frac_part_double`は
  この4段をそのままの順序(スタック側=ARG、FAC側の割り当ても含む)で
  再現しており、**位取り縮約は倍精度のまま行われ、単精度への丸め
  ($CSD)は縮約が終わったあと(`SIN51`)にだけ行われる**という構造が
  一致している。v3の`_sin_core`も`reduced_sp = force_to_single(reduced)`
  を象限判定・1-x変換のあとに置いており、同じ順序。
- `SIN30`のFAC指数バイトへの`ADD...,2`(4倍)は、2の整数乗を掛ける
  操作であり丸め誤差を生まない。v3は`frac_turns.exact()*4`という
  厳密Fraction演算で置き換えているが、2の整数乗の乗算は厳密演算と
  数学的に同一なので、ここも一致する。
- `TAN`はASM上も`$SIN`→(引数を退避)→`$COS`→`$FDIVS`という、
  **SINとCOSを別個に計算してから単精度除算するだけ**の実装であり、
  専用の多項式は無い。v3の`tan_impl`も同じ(`sin_impl(x)`・`cos_impl(x)`
  をそれぞれ計算して`gw_binop(s, c, "/")`)。

つまり、事前の懸念(「v3の範囲縮約がGW-BASICの命令列どおりか疑わしい」)
は、**再読の結果では裏付けられなかった**。v3のこの部分に命令単位の
読み違いは見つからなかった。

## 2. 発見: COSの範囲縮約は歴史的に変更されている(ソースのコメント)

`MATH1.ASM`の`$SIN`/`$COS`セクション直前(940行台)に以下のコメントが
ある(MIT公開ソースそのものからの直接引用、1行。GW-BASIC自体の
著作権表示はファイル冒頭に別途あり、これは開発者の変更履歴コメント):

> `Changed COS to double precision range reduction 24-JUN-82/NGT`

これは「1982年6月24日に、COSの範囲縮約を倍精度へ変更した」という
Microsoft社内の変更履歴コメントである。**この1983年公開スナップショット
にはこの変更が既に反映されている**(=`$COS`は`$SIN`と同じ`RR`を共有し、
両方とも倍精度)。しかし、このコメントの存在自体が「この変更より前には
COSだけ別の(おそらくより精度の低い)範囲縮約を使っていた」ことを示す
一次証拠である。GW-BASICのGitHubリポジトリはコミットが1個(`09ad7bc`、
2020年の単発公開)しか無く、変更前の版はこのリポジトリからは取得できない
(`git log --follow`相当をGitHub APIで確認済み、pathの履歴は1コミットのみ)。

N88-BASICはIBM PC版GW-BASICより前後の異なる時期・異なるCPU(Z80)向けに
分岐したMicrosoft BASICの系譜にあるため、**この1982年6月の修正が
N88側の数値部に反映されていない(=N88のCOSだけ、SINより精度の低い
範囲縮約を今も使っている)可能性**は、測定前の仮説として立てる価値が
ある。これは今回のソース再読で新たに見つかった、資料に基づく具体的な
手がかりである(「ハードウェアの事実」ではなく「同じ資料の別バージョンの
存在」という間接的な手がかりなので、資料の格付け上は測定でしか確定
できない)。

## 3. TAN(.5)不一致の自己整合性チェック(公式ROM不使用)

l4-s6aの不一致のうちT2(`TAN(.5)`)が特に不可解だった。理由:
その入力に対応するN2(`SIN(.5)`)・C1(`COS(.5)`)はどちらも
`predicted_match`(予測と一致)だったのに、両者の比であるはずの
TANだけ不一致になったため。

これをPythonで検算した(公式ROM不使用。`tools/l4_mbf_oracle_v3.py`の
関数を直接呼んだだけ):

```
sin(.5) = sin_impl(0.5)  # GwNum、24bit仮数
cos(.5) = cos_impl(0.5)  # GwNum、24bit仮数
tan(.5) = tan_impl(0.5)  # = gw_binop(sin, cos, "/")
```

`sin(.5)`と`cos(.5)`それぞれの厳密値(Fraction)を割った値
(`sin.exact()/cos.exact()`)を、`l4_mbf_oracle_v2.encode_mbf`
(v2 docstringで「正しい丸め」と確認済みの単精度エンコーダ)で
直接単精度へ丸めたところ、`tan_impl()`が`gw_binop`(=v2の$FDIVS
再現)で計算した結果と**符号・指数・仮数ビットまで完全一致**した。

つまり、**`tools/l4_mbf_oracle_v2.py`の除算実装自体にはバグが無い**
(sin(.5)とcos(.5)の予測値を割れば、TAN(.5)の予測値も無矛盾に出る)。
それでも実機のTAN(.5)がSIN(.5)・COS(.5)の予測と食い違わずにTAN(.5)
だけ食い違ったという事実は、**除算そのものではなく、「PRINTが表示する
6桁」では見えない下位ビットの差**が主因である可能性が高いことを示す。

### 見えてきた方法論上の欠陥: PRINTの6桁は候補を弁別できない

l4-s6aのN4/C4/T4/T2(「特筆すべき食い違い種類2」)はいずれも「符号・
桁数・小数点位置は一致し、末尾1桁が数ULPずれた」という記述だった。
これは、PRINTが単精度の値を**6桁の10進文字列**にしてから比較する
(禁止事項7を守るため、生の24bitではなく表示文字列でしか比較できない)
ため、**候補モデル同士が24bit仮数の下位数ビットでしか異ならない場合、
6桁表示では「一致」に見えてしまう組が混じる**ことを意味する。

したがって、l4-s6bで候補モデルを弁別する腕は、**候補間の予測値が
6桁表示の時点で実際に異なる**入力を選ばなければならない
(下記「候補と腕の設計」節に反映)。

## 4. 結論(手順1のまとめ)

- v3の範囲縮約・SIN/COS/TANの構造は、再読の結果、GW-BASICソースの
  命令列と一致しており、**新たなバグは見つからなかった**。
- ただし、ソース自体に「COSの範囲縮約は1982年6月に倍精度へ変更された」
  という歴史的コメントがあり、**N88がその変更を反映していない可能性**
  (COS・TANだけ精度が落ちる)は、測定前の仮説として立てられる。
- TAN(.5)の不一致は、v2の除算実装のバグではないことを自己整合性
  チェックで確認した。よって不一致の原因は「候補モデル間の差がPRINTの
  6桁では見えにくい」という測定設計側の限界を疑うべきで、次の測定の
  腕は、候補間で6桁表示が実際に割れる入力を選んで設計する。

## 禁止事項7の遵守について

本ノートに書いた数値(`sin(.5)`等の厳密値・ビットパターン)は、いずれも
`tools/l4_mbf_oracle_v3.py`/`l4_mbf_oracle_v2.py`という**自作の予測器
コード**をPython上で呼び出した出力であり、公式ROMには一切触れていない
(`PC88_REF_ROM_DIR`は本ノート作成中、未設定のまま)。GW-BASICソースの
引用(コメント1行)はMITライセンスの公開ソースであり、ROM由来ではない。
