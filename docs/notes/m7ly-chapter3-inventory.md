# m7ly — 3章「未確定として残すこと」の棚卸し

## 位置づけ

第217版で、3章の段30 `READ DATA`の項（第112版で追加）が第132版で
解消済みだったにもかかわらず印が無かったことが分かった
（`docs/notes/m7lx-interrupt-shape-rebaseline.md` 追記2）。1項がこの
状態だったなら他にも同型の見落としがあるはずだと考え、3章全体（84項）を
棚卸しした。目的は、M6区切りの判断材料を揃えることである——どの項が
1.58節へ統合済みで、どれが本当に未確定のまま残り、どれがゴールAの実装に
そもそも要らないかを、項目ごとに確認する。

## 方法

1. **一次分類**: 読み取り専用の担当3人に3章を行範囲で分担した
   （3717〜4396／4397〜5044／5045〜5934、第217版時点の行番号）。
   各担当は自分の範囲内の項だけを読み、統合・外形一致・解消・区切り・
   B送り・A不要・統合+残・残る、のいずれかに分類した。
2. **再検証**: 一次分類で「未確定・A要」（=ゴールAの実装に必要かもしれない
   未確定）とされた項を、別の担当が後続版の改訂履歴・適合テストの合格記録に
   照らして再検証した。
3. **確定**: 主セッションが、改訂の記録（特に第140版・第142版）と1.58節の
   記述を突き合わせて最終分類を確定した。

一次分類の担当3人は**後の版で該当項がどう扱われたかを追っていなかった**
ため、「未確定・A要」が過大に出た——11項→再検証で5項→確定で3項、という
経過をたどった。過大に出た項の大半は、実際には後続版で1.58節へ統合済み
だったか、適合テストで実質的に担保されていたかのいずれかだった。

## 分類の定義

TSV先頭のコメント（本稿の作業資料）どおり:

| 分類 | 意味 |
|---|---|
| 統合 | 1.58節（または1.57〜1.58節）へ統合済み |
| 外形一致 | 意味は未確定だが、第202〜206版で外形が公式と一致しゴールAの実装に要らない |
| 解消 | 後続版の測定・実装で解消済み |
| 区切り | 開発者判断・測定限界により追跡を区切った |

| 残る | 未確定のまま残る項 |

「既印」＝その項に既に解消・区切り等の印が付いている（新たな印は不要。

## 残る項（3項）

測れば閉じられる種類のものだけが残っている。

- **5448**: B:候補は1本（`disk#8`）でしかWRITE経路の一致を確認していない。
  他のB:候補でのWRITE一致は未測定のまま。
- **5485／5508**: 1.57〜1.58節へ統合されたが、自作媒体での外形一致
  （第202〜206版）にとどまり、`disk#10`実物での照合は第206版以降実施
  していない。

いずれも「測る対象と手順が存在し、実施していないだけ」という意味で
閉じられる種類の未確定である。

これとは別に、**5375**（交換#6経路の奇数シリンダ条件）は第142版で
「4つの梃子で奇数条件へ届かず」と、到達手段そのものが尽きた区切りである。
これは測れば閉じる残る項とは性質が異なり、**到達できない入力に対する
実装の脆さ**として残る（測定では埋められない）。

## 4557の証拠

対象は「sub視点SENDプリミティブ（1.15節）で`0F`/`0E`相当の`OUT $FF`が
SENDの本体そのものか、別の遷移か」という項（第218版棚卸しで解消と分類）。
確認したのは`$FF`（ハンドシェイク制御ポート。仕様書にも値が載っている）
への書き込みの出現状況のみで、`$FB`/`$FC`/`$FD`等のデータポートの値は
一切扱っていない。

ログはHEAD b13f837時点の`conform_l3.sh`全体実走の作業領域
（`/Users/haruurara/MyProject/_emulator/PC88/tmp/m7lw-conform2/`、
本リポジトリの外）にあるものを使った。

```
cd .../tmp/m7lw-conform2
for f in $(ls *.iolog.txt | grep -i official); do
  awk '$4=="sub" && $5=="OUT" && $6=="00FF" && ($7=="0F"||$7=="0E"){print FILENAME, $3, $7}' "$f"
done | sort | uniq -c
```

結果:

- **公式ログ32本すべて**で`0E`が**frame 42に1件ずつ**現れ、`0F`は
  **0件**だった（32本中32本が`0E`ちょうど1件、`0F`0件は全32本で一致）。
- そのうち1本（`bload.official.iolog.txt`）で、その`0E`の直前の
  `sub OUT $FF`列を見ると `81, 08, 0A, 0C, 0E` と続いていた。これは
  6章要件33（第44版）が定義する高速バルク遷移
  `OUT $FF,81,08,0A,0C,0E`そのものであり、SENDプリミティブの中の
  書き込みではない。
- **混成ログ（`grep -i mixed`）でも同じ`0E`が出た**——35本中34本。
  欠けた1本は`nodisk_mixed.iolog.txt`で、これは条件4の陰性対照
  （sub側イベント0件）であり、そもそもsub側`OUT`イベントが存在しない
  条件なので欠けて当然である。

以上から、この項が問うていた「`0F`/`0E`相当の`OUT $FF`がSENDプリミティブの
中の書き込みか」という疑いは解消し、観測される唯一の`0E`は要件33の
バルク遷移の一部であると確認した。
