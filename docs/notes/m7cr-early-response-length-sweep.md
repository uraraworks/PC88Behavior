# m7cr: no_disk +0受信中READ DATAの帰属と早期応答長sweep

日付: 2026-08-25

## 測定から言えること

branch-order実走は公式・混成とも交換がFDCより先だった。混成のREAD DATAは
+0要求runの途中、6件中5件を受信した時点で発行された。これは外部I/O順序の
測定であり、公式subの内部判断を観測したものではない。

軸直前応答の準備を混成の5clockから公式と2clockへ合わせた介入でも、
+0要求長の分岐は動かなかった。これで、256バイト応答値、1バイト応答値、
sub割り込み2件、遅い方向の2clock摂動に続く5つ目の容疑を除外した。
また「FDC発行が交換より先かもしれない」という見立ても、両者とも交換が先と
実測されたため外れた。

## 自作コードを読んで分かること

`RECV_DISPATCH`は各受信後に`WINDOW_RUN_COMPLETE`を呼ぶ。既定表の先頭
`0x02`は長さ5なので、5件目の直後に`_recv_dispatch_window_done`から
`_general_read_request`へ進む。自作subが+0の物理run 6件の5件受信時点でREAD DATAを
発行した実測と一致する。ただしこの表はsubの内部処理開始位置であり、mainが
既に選んだ送信runの物理終端ではない。従って「表を3にすれば+0要求長も3に
できる」という理解は誤りである。早期SENDは、mainが残りの送信を続ける間に
受信準備bitを待つ。長さ3を物理run短縮の陽性対照とした測定設計は成立しない。

`--restore-request-kind-length6`は旧「長さ6なら一般READ」判別を復元する陽性対照で、
現行の先頭種別→長さ表とは逆である。仕様1.13節由来の8/6/8は、要求長だけでは
応答形式を一般決定できないという未解決事項であり、今回の長さ5から応答形式を
導く根拠にはならない。

## 使い捨て介入

`--early-response-after N`（3〜12）は、no_disk校正済み+0の先頭0x02要求を
N件受信後にREAD DATAを出さず、一般READで既に使う1バイト
応答入口へ進む。5を特別扱いせず長さを振る。3未満はB-unitのスコープを判定
できないため扱わない。完全一致しても、公式subが同じ判断を持つとは結論しない。

`early-response-sweep`の初回実走は長さ3の陽性対照が落ち、結論を採らなかった。
その時点の関門はHEAD対既定の同一と、既定対介入の非同一までで、介入判定への
実行到達を数えていなかった。ROMバイト差だけでは介入成立を保証できない。

修正後はB-unit分岐の判定直前、0x0800フェッチ窓内にRETだけの専用マーカーを置き、q88hトラップのretモードで
実行回数を数える。各介入armは1回だけを正常とし、0回や過剰回数は指標の抽出・
出力前に失敗させる。未到達番地へmapを1バイトずらす故障注入で、0回を検出する。
対照の物理runが6件なので、N=7〜12はそのrun中には原理上到達できない。
以前はROM差があるだけでこれらも有効armとしたが、修正後の掃引は到達可能な
N=3〜6だけに限定する。後続実験で長さ6超を扱うなら、mainの物理run選択側を別に
介入する設計が必要である。N=3は物理run短縮の対照にはせず、専用マーカー1回到達と
controlからの観測成果物変化を組み合わせた、介入・観測系の陽性対照として扱う。

## 実走結果と結論

修正版はrc=0だった。既定ROMはHEAD基準と一致し、N=3〜6の介入ROMはすべて
既定と異なり、専用RETマーカーも各armでちょうど1回実行された。N=3の成果物変化も
陽性対照として成立した。三段の関門をすべて通った結果、交換prefixは対照36に対し
N=3〜5で12、N=6で18へ悪化し、一致する長さは無かった。「5バイトで応答へ転じる
のが正しい」という見立ては否定され、自作subがこの局面でREAD DATAへ進むことは
少なくとも誤りではない。原因発見ではなく、早期応答を6つ目の容疑者として潰した周である。

no_diskで除外した容疑者は通算6つになった。

1. 相対-3の256バイト応答の中身
2. 相対-1の1バイト応答の中身
3. sub側の割り込み受理2件
4. 応答準備を遅らせる方向の摂動
5. 応答準備を公式と同じ2clockにすること
6. 早期に応答へ転じること

1〜3は介入成立でも指標不変、4は正確に2clockずれても不変、5は2clockへ到達しても
不変、6は全長で悪化した。原因とmain側割り込み受理差の帰属は未確定のままである。

## 測定で確定した境界

交換列の最初の差は相対+0そのもので、手前は値まで一致する。分岐順序は公式・混成とも
交換が先（公式18030→18151、混成17954→18093）であり、「FDCが先かもしれない」
という見立ても外れた。自作subは+0のrun途中、6バイト中5バイト受信時点でREAD DATAを
発行する。応答準備5clockは共通クロック上のI/Oイベント通番差で、重複した`IN FE`2件
による。T-stateでは314T、そのうち削除可能な重複確認は73Tで、コードからの計数と実測が
一致した。

## 行き止まりと道具の成果

- 数値掃引14armは、指定量が実効clockへ出ず全点不成立だった。待ちを支配したのはCPU予算
  ではなくPIO C handoffで、照合検査がなければ14点の無意味な結論を出していた。
- `handoff_now`は成果物が対照とビット同一でineffectiveだった。後に自作sub側を短縮して
  2clockへ到達し、速い方向を測れない問題は解消した。
- ROM側フラグが生成ROMを変えない空振りがあり、実測せずROM比較だけで分かったはずだった。
- 既定ROMへ意図せず3バイト増え、差分が1740バイトになった。「既定ROMのサイズ・バイト列には
  影響しない」というコードコメントは事実と異なっていた。
- 早期応答介入を実行経路外の`0x07FD`（コード末尾）へ置き、実行回数0のまま実測した。
- 当初の陽性対照N=3は不適切だった。長さ表はsub内部の処理開始位置で、mainが選ぶ
  物理run長ではない。

この周の最大の成果は原因候補ではなく測定道具である。介入前段関門を、(1)既定ビルドが
基準とバイト一致、(2)介入ビルドが既定と異なり差分バイト数・位置も表示、(3)RETマーカーを
トラップして介入コードの実行回数が期待どおり、の三段にした。0回も過剰回数も失敗とする。
このセッションでは介入の空振りを7回踏み、すべて実測後に気づいた。三段関門は、そのうち
最初の3件を実測前に落とせる。
