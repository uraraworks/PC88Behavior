# L2 — 半角ANK 文字コード割り当ての根拠

作成日: 2026-08-07

`docs/spec/l2-font.md` 第2版・6節4「半角ANK（JIS X0201）のコード⇔グリフ対応表を作る」
（未決定事項）を埋める作業ノート。**公式 ROM のフォントデータは一切見ていない。**
参照したのは (a) N88-BASIC リファレンスマニュアル `../refs/manual.txt`（資料3・資料4）と
(b) JIS X0201 の規格（公開されている国際的な符号系。PC-8801固有の情報ではない）の
2つだけ。フォント自体は `tools/fetch_unscii.sh` で取得した unscii-8（4節で採用決定）。

対象は `font_mem` の前半 2048 バイト（ANK面、コード 0x00-0xFF）のみ。
後半（グラフィック面、0x100-0x1FF 相当）は文字コード対応表を作らず、
ルール生成（`src/l2_font/make_font_rom.py` のセミグラフィック節を参照）。

## 1. 参照した資料

| 資料 | 参照箇所 | 何を確認したか |
|---|---|---|
| `../refs/manual.txt` | 1119行付近「資料3 コントロールコード」 | 0x00-0x1F・0x7F が制御コード（可視グリフを持たない）であること。列挙されたコード（07H, 09H, 0AH, 0BH, 0CH, 0DH, 16H, 17H, 1CH, 1DH, 1EH, 1FH 等）はいずれもカーソル制御・画面制御 |
| `../refs/manual.txt` | 1119行付近「資料4 キャラクタコード」 | 16x16 の表（上位4bit×下位4bit）の**構造**（256コードの表であること、0x20-0x7E相当にASCII風の記号・英数字が並ぶこと）は読み取れた。ただし OCR 品質が低く（スキャンPDFからのテキスト抽出で文字化けが多い）、**カタカナ域の正確な列位置（コードが 0xA1 起点か 0x80 起点かなど）をこの資料単独でピクセル単位まで確定することはできなかった** |
| JIS X0201 規格（公開規格） | — | 半角英数記号（JIS X0201 ラテン文字用図形文字集合）が ASCII と可換だが 0x5C=¥（円記号）・0x7E=‾（オーバーライン）の2点で異なること。半角カタカナが 0xA1-0xDF の連続63コードに割り当てられ、Unicode の半角カタカナブロック U+FF61-U+FF9F と1対1で対応すること（この対応は国際的に広く使われている符号変換表で、PC-8801固有ではなく規格そのものに由来する） |

**方針**: 資料4は「256コードの表がある」「ASCII相当の部分がある」という**構造**の
裏付けとして使い、コードの具体的な割り当ては OCR で確定できる範囲を超えて
資料4だけから読み取ろうとしない。カタカナの正確な位置は、規格として公開されている
JIS X0201（資料4が言及する文字コード系そのもの。`../refs/manual.txt` 1164行
「資料7 半角文字／全角文字コード変換表」もJIS X0201前提の相互変換表であることから、
このマニュアルの体系自体がJIS X0201に準拠していることは資料7から確認できる）
に従う。**これは公式ROMのデータではなく、規格書という別系統の資料である。**

## 2. 割り当て表

| コード範囲 | 内容 | 出典 |
|---|---|---|
| 0x00-0x1F | 制御コード（資料3）。可視グリフなし | manual.txt 資料3 |
| 0x20-0x5B | JIS X0201 ラテン図形文字＝ASCII と同一（space, !"#$%&'()*+,-./0-9:;<=>?@, A-Z, [） | JIS X0201 |
| 0x5C | ¥（円記号、Unicode U+00A5）。ASCIIのバックスラッシュとの相違点 | JIS X0201 |
| 0x5D-0x7D | JIS X0201 ラテン図形文字＝ASCII と同一（], ^, _, `, a-z, {, \|, }） | JIS X0201 |
| 0x7E | ‾（オーバーライン、Unicode U+203E）。ASCIIのチルダとの相違点。**ただし unscii-8.hex にはこのグリフが収録されていない（後述4節）ため、実装では暫定的にASCIIのチルダ字形を代用している** | JIS X0201／実装上の妥協 |
| 0x7F | 制御コード（DEL相当）。可視グリフなし | 資料3の並びから類推（DELは0x7Fが業界標準のため。マニュアルには明記無し） |
| 0x80-0xA0 | **未決定。空欄のまま**（下記3節） | — |
| 0xA1-0xDF | 半角カタカナ 63字（4節・`src/l2_font/make_font_rom.py` のASCIIアート） | JIS X0201、Unicode U+FF61-U+FF9F との対応 |
| 0xE0-0xFF | **未決定。空欄のまま**（下記3節） | — |

半角カタカナの並び順（0xA1から順に）: 。「」、・ヲァィゥェォャュョッーアイウエオカキクケコサシスセソタチツテトナニヌネノハヒフヘホマミムメモヤユヨラリルレロワン゛゜
（JIS X0201 / Unicode U+FF61-U+FF9F の標準順序。実装ではコード表として
`src/l2_font/make_font_rom.py` の `HALFWIDTH_KANA_CODEPOINTS` にコードポイント配列で記載）

## 3. 空欄のまま残したコード（未決定）

- **0x80-0xA0**（33コード）と **0xE0-0xFF**（32コード）、合計 **65コード**。
- 資料4のOCRからは、この領域に何らかのグリフ（カタカナの拡張や記号）が
  存在する可能性を示す断片が見えるが、文字化けが激しく個別のコード↔文字の
  対応を資料から確定できなかった。
- ここを埋めるために公式フォントを見に行くことはしない（指示どおり）。
  実装（`make_font_rom.py`）ではこの範囲を **0x00 埋め（空白グリフ）** とし、
  `--selftest` で「空欄のコード一覧」として明示的に報告する。
- 将来、資料4の高品質な原本（OCRでなく目視）か、別の一次資料
  （回路図・ハードウェア技術書等、CLAUDE.mdが許可する範囲）が手に入れば
  埋め直せる。

## 4. unscii-8 とのコードポイント対応（実装メモ）

- ASCII部分（0x20-0x7E、円記号・オーバーライン含む）: unscii-8.hex は
  Unicode コードポイントをキーにした `.hex` 形式。0x20-0x7D はキー
  `00020`-`0007D` でそのまま1対1（オーバーラインの0x7Eを除く）。
  円記号は `000A5`（U+00A5 YEN SIGN）として収録されていることを確認した
  （`grep -i '^000a5:' unscii-8.hex`）。
- **オーバーライン（U+203E）は unscii-8.hex に収録されていない**
  （`grep -i '^0203e:' unscii-8.hex` は空）。したがって 0x7E は
  やむを得ず ASCII のチルダ字形（`0007E`）を代用する。JIS X0201 の
  規格上は誤りだが、実害は小さいと判断した（利用者確認事項として報告）。
- 半角カタカナ（0xA1-0xDF）: 4.0節の方針により unscii の半角カナは
  **使わない**（出自の説明を要する素材を中核に置かないため）。
  代わりに `make_font_rom.py` 内に 8x8 の ASCII アートとして直書きする
  （5節・6節）。
