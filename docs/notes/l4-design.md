# M7（L4）設計ノート 第1版 — 着手にあたっての整理

記録日: 2026-09-15
状態: M6 はいったん完了（2026-09-14）。M7 は未着手。実装より先に、範囲・方針・段階分けを固定する。

## 位置づけ

M7 は `docs/PLAN.md` 第8節では「L4 N88-BASIC 互換処理系（ゴール A）」とだけ
書かれているが、実際に必要な作業は L4 単体ではない。**main 側の L3（画面出力・
キー入力・割り込み・後段でサブ CPU との通信を担う main 側）を含む。** M6 で
作ったのはサブ ROM（`DISK.ROM`）だけで、main ROM（N88.ROM 相当・32KB）は
公式のままだった。自作の main ROM を載せる以上、そこが呼んでいた main 側の
サービス一式もこちらで用意する必要がある。

このノートの名前を `m7-*` にしなかった理由: 既存の `m7a`〜`m7lz` は M6 の中の
作業番号（サブROM周りの各測定・実装ステップ）であり、M7 という節目そのものを
指す名前ではない。M7 関連のノートは `l4-*` を使う。

## 開発者判断（2026-09-15）

### 1. 最初の到達点は「ROM BASIC 核」

ディスクを使わずに自作 main ROM を起動し、自作バナー → `Ok` → 直接モードの
`PRINT` が公式と同じ画面になるところまでを最初の到達点とする。ディスク系
（自作サブ ROM との接続）はその後段に回す。

### 2. GW-BASIC は数値部だけ移植する

Microsoft が 2020 年に MIT ライセンスで公開した GW-BASIC のソースから、
**浮動小数点（Microsoft Binary Format）演算と数値⇔文字列の変換だけ**を移植する。
出力を公式と一致させるには同系統の数値表現・丸めが要るため。トークン番号・
インタプリタ全体の構造・その他の命令は自前で書く。移植したファイルには MIT の
著作権表示とライセンス文をそのまま残す。

- 取得元: https://github.com/microsoft/GW-BASIC 、コミット
  `edf82c2ebf6bfe099c2054e0ae125c3efe5769c4`（2020-05-21）。置き場はリポジトリ外
  `_emulator/PC88/refs/GW-BASIC/`（パスは相対の説明にとどめ、スクリプトには
  焼き込まない）。数値部の中心は `MATH1.ASM` / `MATH2.ASM`（8086 アセンブリ）。
- 規律上の位置: `CLAUDE.md`「やってよいこと」に GW-BASIC の MIT 公開ソースを
  読むことが明記済み。公式 N88 ROM とは別物であり、由来の鎖は Microsoft 自身の
  ライセンスで閉じる。
- 留保: GW-BASIC の数値ルーチンが N88 と同じ結果を出す保証は無い。一致は
  段階4で公式 ROM との画面比較によって測って確かめる（測定 > 資料の原則）。

### 3. 道具は Python 製の .asm テキストアセンブラにする

`src/l3_service/make_subrom.py` の `Asm` クラスを土台に、普通の Z80 アセンブリ
表記を読むアセンブラを新しく作る。外部依存ゼロ・python3 だけで第三者が
再生成できる方針（L1/L3 と同じ）を保つ。インタプリタ規模（数十KB）になると、
Python のメソッド呼び出しで命令を並べる現行の書き方は読みにくくなるため。

## 段階（案）

- **段階0 アセンブラ**: 検査として、L1 IPL とサブ ROM を .asm で書き直した版を
  アセンブルし、既存生成器（`make_ipl_rom.py` / `make_subrom.py`）の出力と
  バイト一致させる。既存2生成器が正解役（オラクル）になり、バイト一致は機能
  検証も兼ねる。わざと壊して不一致を検出できることも確かめる。
- **段階1 main側L3の測定**: 公式 ROM で、テキスト VRAM の文字と属性の配置、
  スクロール、キー割り当てを測る。
- **段階2 自作main ROM**: L1 IPL＋画面＋キーから、自作バナー → `Ok` →
  1行入力まで。
- **段階3 BASIC核**: 直接モード `PRINT`（整数・文字列）で公式と画面一致。
- **段階4 GW-BASIC数値部の移植**: 浮動小数点の `PRINT` まで一致。
- **段階5 プログラムモード**: 行番号・`LIST`・`RUN`・`FOR`・`GOSUB` →
  代表プログラム群（`PLAN` 第1節ゴール A の達成判定）。
- **後段 ディスク**: 自作サブ ROM と接続。M6 の再開条件（新しい入口で main
  受信列か画面が食い違ったら M6 を再開する）がここで効く。

## main側L3で既に分かっていること（既存記録から）

- **確定**: テキスト VRAM 先頭 `F3C8`、CRTC（μPD3301、ポート `50`/`51`）と
  DMA の初期化、カーソル位置の置き方（定常状態は毎フレーム置き直し）、main側
  VSYNC 割り込み（IM 2・レベル1、`E4` で再アーム）、キーマトリクスのポート
  （`00`〜`0B` を走査、押下で0）。
- **未確定**: VRAM 内の文字と属性の並び、スクロール、属性の意味、手元機種の
  キー割り当て全表、キーリピート、ビープの鳴らし方、リセット直後の状態。
- **流用できる足場**: `src/l1_ipl/make_ipl_rom.py` の初期化・キースキャン・
  VSYNC ハンドラ。

### テキスト画面の行数について（事実確認）

`docs/spec/l1-ipl.md` を grep して確かめた。起動時に CRTC へ実際に設定される
行数は **20行**（DIP スイッチ `IN 30 → DB` の実測、CRTC パラメータ
`93`=L5-L0=19、DMA 転送量 `095F`=2400=(80桁+40属性)×20行の3系統が一致。
同文書 第0節・第5節）。一方 VRAM 先頭 `F3C8` は、**25行ぶんの領域
（(80桁+40属性)×25行=3000バイト=`$BB8`）が `$FF80` で終わるように逆算して
決められた番地**であり（同文書「テキストVRAMが `F3C8` である理由」節）、
25行という数はこの逆算のための仮想的なサイズであって、起動時に画面へ
実際に出ている行数ではない。つまり「20行（実際の表示・DMA転送量）」と
「25行（VRAM確保サイズの逆算に使った数）」は矛盾ではなく、後者は前者を
包含する余裕を持たせた確保サイズの話である。M7 で画面出力を作る際は、
起動直後の実際の表示行数として **20行** を採用し、25行ぶんの VRAM 領域は
そのまま流用する。

## 物差し（試験器具）

- **既存で足りるもの**: 全自作 ROM 一式をディスク無しで起動する経路
  （`--rom-dir`。トラップ ROM で実績あり）、打鍵注入（`--type-at` / `--type`、
  英数記号と改行、複数行可）、画面署名と比較（`tools/check_l3_screen_output.py`、
  本文を出さず食い違いの行・列まで判定）、`conform_l3.sh` と同型の場面定義。
- **足りないもの**: 特殊キー（カーソルキー・STOP・ファンクションキー）の
  打鍵、N88.ROM 以外に必須の ROM ファイルの確認、自作 main ROM 用の期待値運用。
- **バナー行は比較から除外する。** 禁止事項6により自作 ROM は別名を名乗るので、
  起動画面は定義上一致しない。比較は `CLS` の後、またはコマンド入力後の領域に
  限る。除外の仕方（領域指定か `CLS` 後か）は段階2で決める。

## トークン

自前体系（`docs/notes/l4-token-design.md`）を維持する。**GW-BASIC のトークン
番号も採らない。** GW-BASIC の番号の並びは N88 と多数（第三者の実測で
184個中128個）が共通するため、数値部を移植しても番号体系は独立に設計する。
