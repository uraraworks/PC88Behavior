# m7fo: 陰性対照は対象を踏んでおらず、RAM初期値の由来を確認した

実施日: 2026-09-03

## 位置づけ

本稿は`m7fn`（事前登録）を受けた実測結果と、その結果に対する追加のコード
読解の記録である。`m7fn`は、`m7fm`が実測した「段27の並べ替え（軸D）が、
実行順序上はそれより前の段4・段6の`SENSE INTERRUPT STATUS` unit/head分類を
変化させた」現象について、(a)段4・段6がROM像（バイト列・配置）に依存する
のか、(b)軸Dの並べ替えに未特定の前方影響があるのかを切り分けるため、
`align_padding_bytes`を強制した陰性対照（意味を変えずにROM像だけを変える
ビルド）を事前登録した。

本稿ではこの陰性対照を実測した。**結果は「変わらなかった」だったが、
これは(a)を棄却する証拠にはならない。** パディングの挿入位置が段27より
後であり、段4・段6を作るコードのバイト配置をほとんど動かせていないためで
ある——**検査が対象を踏んでいなかった疑いが強い。** これは委譲先自身が
自己申告した弱点である。

そこで本稿は追加で、`m7fn`が決めることの前提とした「(a)が成り立つ経路が
あるか」を、ROM/RAMロードの実装コードから直接確認した。**結論を先に書くと、
サブ側RAM（0x4000-0x7FFF、REQ_HDRを含む）は、ROMファイルの内容に一切
依存しない固定値0xFFで初期化される経路しか、コードでは確認できなかった。**
すなわち、少なくとも「RAM初期値がROMファイルのバイト列を反映する」という
形の(a)の経路は、確認した範囲では**存在しない**。

## 1. 陰性対照の結果（実測済み）

- `align_padding_bytes=1`を`build_subrom()`へ直接渡した。両関門
  （`find_fetch_window_straddles`・`find_out_of_window_blocks`）を1回目で
  通過した。
- **陽性対照:** 自作サブROMのSHA-256はベースラインと**異なった**
  （コード長 2042→2045、`jr`+NOP1個分の+3バイトと整合）。介入はビルドへ
  実際に反映されている。
- **段4・段6のunit/head分類は、ベースライン対陰性対照で変わらなかった。**
  段0〜段49の`--list-all-stages`出力（種別列・シリンダ一致・
  `SENSE INTERRUPT STATUS`の復号名）がすべて一致した。陰性対照対条件Oは、
  ベースライン対条件Oと同じ形の不一致のまま残った。
- 参考項目も不変だった: `READ DATA` 9段のIC/ST1/ST2とrun長が9段全一致、
  `SEEK` 11段のシリンダ一致も全一致。**陰性対照の前提（意味を変えていない
  操作で参考項目が動かないこと）は崩れていない。**
- 決定論性は両条件とも成立した（FDCポート値列の一致prefixが13577件で
  全長一致）。
- 条件Oは新規に1回測定した（既存ログの流用ではない）。

## 2. この陰性対照は弱い（(a)を棄却する証拠にはならない）

`align_padding_bytes`のパディング挿入位置は`BULK_SEND`ラベル直前
（`src/l3_service/make_subrom.py` 2484行付近）であり、**段27
（`_exchange14_prepare_first_read`、2380〜2396行）より後**にある。
`m7fn`自身が事前登録時点で「この挿入によってアドレスがずれるのは段27を
含むそれより後のコード全体であり、段27より前（起動時FDC初期化を含む）の
アドレスはずれない可能性が高い」と記していた。

実測した自作ROM同士のバイト列を比較すると、最初のバイト差は先頭付近では
なく後方（段27より後の領域）でしか生じない。これは事前登録時の推測と
整合する。

**したがって、段4・段6を作るコードのバイト配置（アドレス・並び）は、
この陰性対照ではほとんど動いていない。** 「変わらなかった」という結果は、
「(a)の経路が無い」ことの証拠ではなく、**「検査が対象を踏んでいなかった」
ことの結果である可能性が高い。** `m7fn`が事前登録した決定ルールは
「変わらなければ(b)（軸Dの前方影響）」だったが、**その前提（段4・段6の
バイト配置が実際に動いていること）が満たされていないため、この決定ルールを
機械的に適用しない。**

この弱点は、対照実験を実行した委譲先自身が測定結果の報告時に自己申告した
ものであり、本稿はそれを隠さず記録する。

## 3. RAM初期値の調査結果

`CLAUDE.md`が許可する範囲（自作コード・自作ハーネス・第三者エミュレータ
`vendor/quasi88-libretro`のソース）を読み、公式ROM・公式ディスクは一切
参照していない。

### 3.1 サブ側RAMは何で初期化されるか

`vendor/quasi88-libretro/src/memory.c`の`memory_allocate()`（324〜412行）
を読んだ。この関数は`retro_init()`から1回だけ呼ばれる
（`LIBRETRO/libretro.c:583`。他に呼び出し箇所はソース全体で無い）。

該当箇所（408〜410行）:

```
					/* SUB側 ROM ミラー生成、RAMクリア */
  memcpy( &sub_romram[0x2000], &sub_romram[0x0000], 0x2000 );
  memset( &sub_romram[0x4000], 0xff, 0x4000 );
```

**RAM領域（0x4000-0x7FFF、REQ_HDR=0x4200を含む全域）は、`memcpy`による
ROM複写より後で、`memset(..., 0xff, 0x4000)`により一律0xFFへ上書きされる。**
この`memset`は、直前のROMロード（`load_rom`、下記3.2）が成功したか失敗した
かに関わらず、`memory_allocate()`内で無条件に実行される。この関数（と
呼び出し元の`retro_init`の該当箇所）は本ハーネスのパッチ
（`tools/patches/0001-cleanroom-harness.patch`）が変更していない範囲であり、
上流（`vendor/quasi88-libretro`）の元の実装のままである。

なお、`retro_reset()`（`LIBRETRO/libretro.c:715`、`quasi88_reset()`経由）は
`memory_allocate()`を呼ばず、RAM再クリアの経路も確認できなかった。ただし
本稿の測定は起動1回のプロセスなので、この経路の有無は本稿の結論に影響しない
（確認できなかった範囲として記録するに留める）。

### 3.2 サブROMのロード先とRAMは同じ配列を共有しているか

共有している。`memory.c:116`・`336`:

```
byte	*sub_romram;			/* サブ ROM/RAM [0x8000] (32KB)	*/
...
sub_romram   = (byte *)           mem_alloc( sizeof(byte) *  0x8000 );
```

**`sub_romram`は0x8000（32KB）1本の配列で、ROMとRAMを同じ配列上の異なる
オフセットとして共有している。** `pc88sub.c`の読み書き関数（`sub_fetch`・
`sub_mem_read`・52/68行、`sub_mem_write`・79/85行）はいずれも
`sub_romram[addr & 0x7fff]`でこの配列へ直接アクセスしており、ROM/RAMの
切り替えは無い（バンク切替非対応）。書き込みは`(addr & 0xc000) == 0x4000`
の場合のみ許可される（`sub_mem_write`、79行）——これは`make_subrom.py`の
コメント「サブ側は0x4000-0x7FFFのみ書き込み可」と一致する。

`0003-bus-trace-sub.patch`が追加したコメント（`pc88sub.c`、自作ハーネス
コードなので読んでよい）も同じ境界を記録している:「`sub_romram`は
0000-3FFFがDISK.ROMの実体（2KBを0800/1000/2000で複製してミラーしてある）、
4000-7FFFがRAMで固定」。

### 3.3 REQ_HDRはこの配列のどこに当たるか

`REQ_HDR = 0x4200`（`make_subrom.py` 638行）は、上記のRAM領域
（0x4000-0x7FFF）の内側であり、`memory_allocate()`の`memset(&sub_romram[0x4000], 0xff, 0x4000)`が及ぶ範囲に含まれる。`m7ey`が指摘した`REQ_HDR+2`
（未初期化ワークエリアのbit0をunitとして読んでいた箇所）も同様にこの範囲
内にある。

### 3.4 ROMファイル8192バイトのうち、ロードされない残りはどう扱われるか

これが本稿で最も重要な追加確認である。**サブROMのロードには2つの独立した
経路があり、両方を追った。**

**経路1（`memory_allocate()`内蔵、上流のまま・未パッチ）:**
`memory.c:367`
`load_rom( rom_list[ SUB_ROM ], sub_romram, 0x2000, DISP_FNAME )`。
`load_rom()`の実装（205〜250行）は`osd_dir_rom()`が返すディレクトリ配下の
ファイルを探して読む。**`osd_dir_rom()`はlibretroビルドでは常にNULLを
返す。** 根拠: `dir_rom`（`LIBRETRO/file-op.c:43`）はstatic変数で明示的な
初期化が無く（ゼロ初期化＝NULL）、これを設定する`osd_set_dir_rom()`の
呼び出しは`getconf.c`（スタンドアロン版の設定ファイル解析、libretroビルド
では使われない）にしか無い。`LIBRETRO/libretro.c`（原文・パッチ後とも）に
`osd_set_dir_rom`の呼び出しは無い。この事実は本ハーネス自身のコメント
（`0008-font-remove-builtin.patch`、`libretro.c`618行付近、自作コードなので
読んでよい）にも「`osd_dir_rom()`がlibretro版では設定されず
`memory_allocate()`の内部ロードが必ず失敗する」と明記されている（漢字ROMに
ついての文脈だが、同じ`load_rom()`を使うSUB_ROMにも同様に当てはまる）。

`load_rom()`の該当箇所（205〜233行）:
```
  const char *dir = osd_dir_rom();
  if( dir ){ ... }               /* dir==NULLなのでこのブロックは丸ごとスキップされる */
  if( load_size < 0 ){			/* ファイル見つからず */
    memset( ptr, 0xff, size );
  }
```
`dir`がNULLのため`if(dir)`ブロックは実行されず、`load_size`は初期値`-1`の
まま。したがって**この経路は必ず失敗し、`memset(ptr, 0xff, 0x2000)`が実行
される。** これは`sub_romram[0x0000:0x2000]`全域（＝ROM扱いの領域）を
0xFFで埋める。続く`if(size <= 0x800){ ミラー }`（375〜378行、`size`は
`load_rom`の戻り値`-1`なので条件成立）は、この全0xFFの内容を
0x0800/0x1000へ複写するだけで、実質的には無意味な操作になる。さらに
`memory_allocate()`終端の`memcpy(&sub_romram[0x2000], &sub_romram[0x0000], 0x2000)`（409行）でこの全0xFF状態が0x2000-0x3FFFへも複写され、直後の
`memset(&sub_romram[0x4000], 0xff, 0x4000)`（410行）でRAM領域も0xFFになる。
**この時点で`sub_romram`全域（0x0000-0x7FFF）が0xFFで埋まっている。**

**経路2（本ハーネスがパッチした、実際にDISK.ROMを読む経路）:**
`LIBRETRO/libretro.c`の`retro_init()`が`memory_allocate()`の**後**に
呼ぶ`load_system_file(SUB_ROM, sub_romram, 0x00800)`。この関数
（`load_system_file`本体、`filestream_read`を呼ぶ部分）はパッチが変更して
いない上流のままで、`filestream_read(file, rom_data, rom_size)`により
**要求サイズ（0x800）ちょうどのバイト数だけ**ファイル先頭から読む。読めた
バイト数が0x800と一致しなければ失敗として扱われ（起動中止）、一致すれば
`sub_romram[0x0000:0x0800]`だけが実際のDISK.ROM先頭0x800バイトで上書き
される。**ファイルの0x0800バイト目以降（本リポジトリの`make_subrom.py`が
書き出す8192バイトのファイルなら残り6144バイト、いずれも生成時点では
0x00埋めのパディング）は、`filestream_read`が要求サイズ分しか読まないため、
一度も読み出されない。** ロードされないのではなく「そもそも読まれない」。

**この経路2は、経路1がRAM領域（0x4000-0x7FFF）を0xFFで埋め終えた後に
実行され、かつ`sub_romram[0x0000:0x0800]`しか書き換えない。** つまり
経路2は、経路1が作った「ROM領域0x0800-0x3FFFとRAM領域0x4000-0x7FFF全域が
0xFF」という状態に対して、ミラーの再生成を一切行わない。結果として、
**`SUB_ROM_FETCH_WINDOW`（0x0800）より後のROMミラー領域（0x0800-0x3FFF）も、
実際にはDISK.ROMファイルの内容を反映しておらず、恒常的に0xFFのまま**
という副次的な事実も確認できた（これは`make_subrom.py`が既に運用している
「フェッチ窓0x0800を跨いではならない」という制約と矛盾しない——その領域には
そもそも到達可能な命令を置かない設計になっている）。

### 3.5 (a)の経路はあるのか無いのか

**確認できた範囲では、「RAM初期値がROMファイルの内容を反映する」という
形の(a)の経路は存在しない。** RAM領域（0x4000-0x7FFF、REQ_HDRを含む）は
常に固定値0xFFで初期化され、その0xFFは経路1（`load_rom`の失敗時
`memset`）に由来するものであって、DISK.ROMファイルの実際のバイト列とは
無関係である。経路2（実際のROM読み込み）はRAM領域に一切触れない。

ただし、これは「RAM**初期値**がROM内容を反映する経路」を否定するだけで
あり、`m7fn`/`m7fm`が問題にしていた「段4・段6のunit/head分類がROM像
（コードのバイト配置）に依存するかどうか」という、より広い(a)の主張全体を
否定するものではない。段4・段6を作るコード自体が、ROM上の**自分の命令の
アドレス**（＝コード配置。RAM初期値ではなく、命令フェッチ元アドレスや
分岐先計算など）に依存する可能性は、本稿では検討・排除できていない。
**したがって「RAM初期値経由の(a)は無い」と「(a)全体が無い」は別の主張で
あり、混同しない。** 後者を確かめるには、2節で述べたとおり、段4・段6を
作るコード自体のバイト配置を実際に動かす、より強い陰性対照が要る。

## 4. 言えること／言えないこと

**言えること:**

- サブ側RAM（0x4000-0x7FFF、REQ_HDRを含む）は、確認できた唯一の初期化
  経路（`memory_allocate()`内の`memset`）では、ROMファイルの内容と無関係な
  固定値0xFFで初期化される。
- DISK.ROMファイルの0x0800バイト目以降（本リポジトリの生成物では6144
  バイトのパディング）は、実際のロード経路では一度も読まれない。
- 本稿の陰性対照（`align_padding_bytes=1`）は、段27より後のバイト配置しか
  動かしておらず、段4・段6を作るコードのバイト配置をほとんど動かせていない。

**言えないこと:**

- (a)と(b)の切り分けは**まだついていない**。RAM初期値経由の(a)は本稿で
  排除できたが、「段4・段6を作るコード自身のバイト配置に依存する」という
  形の(a)は排除できていない。(b)（軸Dの前方への未特定の影響）が正しいとも
  まだ言えない。
- 段30（`WRONG CYLINDER`）の原因は決めない。
- `m7fm`の判定（軸D不合格・未採用）は変わらない。この判定は条件5そのものが
  妥当かどうかとは独立に確定済みであり、本稿の結果によっても書き換わらない。

## 5. 次にやること

段4・段6を作るコード自体のバイト配置を実際に動かす、**より強い陰性対照**が
必要である。具体的には、`BOOT_HANDSHAKE`付近（段27より**前**）へ到達不能な
パディングを挿入し、段4・段6を作るコードのアドレスを実際にずらしたうえで、
段4・段6のunit/head分類が変わるかどうかを見る。これは`m7fn`が「確認できな
かった場合の代替案」として既に記していた案と同じ形だが、**`src/`の変更を
伴うため、事前登録してから、`src/`の変更が許される場（親セッション）で
実行する必要がある。**

- (a)（コード配置依存）が実測で確認された場合: 条件5は「ROMのバイト列・
  配置を変える介入すべてが落ちる条件」になりうる。`m7fg`が容量条件を訂正
  したのと同じ形で、条件5の差し替え（`m7fn`が挙げた案1〜3、あるいは別案）を
  検討する。
- (a)が確認されなかった場合（配置を実際に動かしても段4・段6が変わらな
  かった場合）: (b)（軸Dの前方への未特定の影響）の経路特定が次段階になる。
  `push_af`/`pop_af`やスタック状態、他の経路との相互作用を疑う対象として
  調べる。
- **どちらの調査も、実装前に事前登録してから行う。**
