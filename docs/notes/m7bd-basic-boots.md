# m7bd: 自作サブROMで公式N88-BASICが起動した

測定日: 2026-08-19

## 情報境界

公式ROM一式・公式diskA（使い捨て複製）を**実行して**測定した。読んでいない。
本ノートに書くのは件数・位置・状態フラグ名だけで、ディスクの内容は扱わない。
診断に未デコードポート `$F9` を使ったが、**既定では無効**（環境変数
`PC88_DEBUG_RUNLEN_MARK` を明示したときだけ有効。公式subには存在しない
イベントなので適合テストに出すROMには入れない）。

## 1. 追い方

m7bcで固着を抜けたあと、混成は `ID Sector Read Error` を出して止まっていた。
`tools/diag_post_bulk.py` でバルク後の一致が225件まで伸びていることを確認し、
そこから**subが何をしていないか**を見た。

| | 公式 | 混成（m7bc時点） |
|---|---:|---:|
| バルク後のFDCコマンド | 4件（SEEK→SENSE_INT→SENSE_DRV→READ 256バイト） | **0件** |
| バルク後のsub受信 | 8バイト | **6バイト** |
| バルク後のsub送信 | 259バイト | **3バイト** |

通信の並びを1イベントずつ突き合わせると、**同じ6バイト**（既知の要求
グループ9と同じ並び）を受け取った直後に、公式はそのグループの応答を返すのに、
自作は別の値を返していた。

## 2. 憶測をやめて診断ポートで見た

決定関数（`_observed_single_by_request`）の入口で `RUN_LEN` を `$F9` へ出す
一時診断を入れたところ、**バルク後は決定関数に一度も入っていなかった**。
次に `SEND_DISPATCH` の入口で `RESP_ACTIVE` を出したところ0で、
なお2バイト送っていた——**`SECTOR_READY` が残っていた**のが原因だった。

`SEND_DISPATCH` は `SECTOR_READY` が立っていると「交換#4の256バイト応答の
開始」と判断する。バルク前の交換で立てたフラグが残っていたため、6バイト要求
への応答の代わりに `SECTOR_BUF` を流し始めていた（送っていた2バイトは
そのバッファの先頭2バイトだった）。

## 3. 直したこと

バルク送信を終えた時点で**受信の進行状態を畳む**ようにした:
`HDR_PTR` / `RUN_LEN` / `EXCHANGE3_REQUEST_ACTIVE` / `RESP_ACTIVE` /
**`SECTOR_READY`** / `EXCHANGE3_RESPONSE_PENDING` を初期化する。

## 4. 結果 — BASICが起動した

| | m7bc時点 | m7bd |
|---|---:|---:|
| バルク後のsub受信 | 6 | **8**（公式と同数） |
| バルク後のFDCイベント | 0 | **384** |
| `main IN $FC` の件数 | 6415 | **6672（公式と同数）** |
| FDCコマンド総数（4200フレーム） | 47 | **187** |

そして画面に**N88-BASICの起動画面が出た**——バナー・空きバイト数・`Ok`
プロンプトまで到達し、打鍵した行も表示される。**公式ROMを1バイトも読まずに
書いた自作サブROMで、公式のN88-BASICが起動した。**

## 5. まだ届いていないもの

`SAVE` は実行されていない（`WRITE DATA` 0件）。打鍵は画面に出ているが
実行に至らず、起動直後に `Syntax error` が1回出る。打鍵のタイミングを
frame 1500 / 2200 に変えても同じだったので、**打鍵の届き方そのもの**を
見る必要がある（キーボード入力経路はサブROMの担当範囲かどうかも含めて）。

適合条件1（5635件・SHA-256）は維持、`verify_l3.sh` 全項目OK、
`conform_l3.sh` rc=0。コードは1939バイト（窓2048に対して残り109）。

## 6. 教訓

**「どの分岐に入ったか」を憶測で詰めない。** 応答の値から経路を推理して
2回外した（fallbackだと思った→FDCイベント0件で否定、決定関数だと思った→
$F9診断で否定）。未デコードポートへ状態を1バイト出すだけで即座に決まった。
状態フラグの消し忘れは**症状が「別の正しそうな動作」として出る**ので、
外から見て推理するのが難しい。
