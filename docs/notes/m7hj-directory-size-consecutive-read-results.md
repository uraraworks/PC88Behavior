# m7hj: ファイル数を振ってディレクトリ列挙の連続READを探す — 結果

実施日: 2026-09-04

## 位置づけ

[m7hi](m7hi-directory-size-consecutive-read-preregistration.md)が事前登録
した測定の結果である。事前登録は測定開始前に単独コミット（`f7026ca`）して
あり、本稿では事前登録の条件・水準・判定規則を後から動かしていない。
`src/`・`tools/`は本稿では変更していない。

**結論を先に書く: 測定できた2水準（S=8本・M=32本）は、いずれも連続READ
DATAが1件も現れなかった（run長はすべて1）。最大水準（L=128本）は書込み
段階で容量超過（`Disk full`）となり、事前登録どおり未測定・未解釈のまま
残った。段階1で連続READが現れなかったため、段階2・段階3は事前登録どおり
実施していない。主判定はP3（測定できた範囲では、ディレクトリの大きさ
＝ファイル数では連続READの出現を説明できない）である。**

**測定中に手順上の事故が1件あった（詳細は後述の開示節）。L水準の読み出し
測定の完了判定を使い捨てデバッグで確認する過程で、画面本文の生の行を
標準出力へ表示してしまい、`disk#8`の実際のディレクトリ内容（実ファイル名
を含む）が一時的にツール呼び出しの出力へ露出した。コミットした成果物には
一切含まれていないが、CLAUDE.mdの「画面本文を書かない」「実ファイル名を
展開して表示しない」という規律に反した事実として、隠さず記録する。**

## 陽性対照（最初に書く）

1. `build_mixed_rom ... --break-drive-selector`（1.46節の既存故障注入）を
   条件M・`FILES 2`・B:=disk#8複製（水準無関係の対照専用複製）で比較した。
   `tools/compare_l3_entry_fdc.py --after-frame 700`のunit/head差件数は
   **3件**（0件より大きい）。
2. `tools/analyze_error_exchange_shape_selftest.sh`は全4項目OK・rc=0。

**両方通ったため、以降の解釈を行う。**

## 判定規則をベースラインへ当てる（合格条件2）

条件O（公式一式）を、本稿のS水準の読み出し測定（後述）で独立2回行い、
`tools/compare_l3_entry_fdc.py --list-all-stages`（`--after-frame`無し）
で比較した。

| 比較 | 結果 |
|---|---|
| O run1 vs O run2（全段、SEEKシリンダ一致/不一致等） | 完全一致（不一致0件、`grep -c 不一致`＝0） |
| FDCコマンド種別列（`command_names`、prefix一致） | 79件全長一致 |
| FDCポート値列 | 15800件全長一致（値そのものは比較のみで出力していない） |

**判定規則は偽陽性を作らないことを確認した。**

## 段階0: 打鍵列の長さ

ディレクトリ拡大プログラム（`RUN`込み）の打鍵数を投入前に機械的に数えた。
名前を3桁固定幅（`D001`〜）にしたことで、水準間の差は`<M>`の数値リテラル
の桁数差のみになった。

| 水準 | M（ループ回数） | 打鍵数 |
|---|---:|---:|
| S | 8 | 111 |
| M | 32 | 112 |
| L | 128 | 113 |

`FILES 2\n`の打鍵数は全水準共通で8。いずれも512未満。実測でも「打鍵列が
長すぎる」という警告は全試行で0件だった（作業領域のstderrファイル群を
`grep -rl`で確認）。**通った。**

## 構文・接続の妥当性（段階1項目に相当。手順逸脱として開示）

事前登録した`OPEN "O",#1,F$`という旧式構文（変数展開する形）を最初に
試したところ、**`Syntax error`**になった。`m7hg`/`m7hh`が特定していた
現代形式`OPEN F$ FOR OUTPUT AS #1`に切り替えたところ動作した。これは
事前登録の「構文の妥当性そのものは段階1で実測して確認する」という想定
内の手続きであり、水準・意図は変えていない。

また、ディレクトリ拡大プログラムのファイル名指定`"2:D..."`は**B:ドライブ
（第2ドライブ）を指す**ため、`--disk2`でB:複製を渡さずに`--disk`だけで
実行したところ、`RUN`後に応答が返らず`Ok`まで到達しなかった（`reached
(['run'])=False`のまま、framesを1.5倍にしても変化なし）。A:を`--disk`
（起動用固定複製）、B:を`--disk2`（水準ごとの書込み対象複製）として渡す
構成に修正したところ、正常に完了した。これも構文ではなく引数構成の
誤りであり、内容・水準・意図は変えていない（隠さず記載する手順逸脱と
して扱う）。

各水準、B:の独立した複製に対して測定した。

### 水準S（M=8）

| 項目 | 結果 |

  `mismatch`（行数17→18、文字数766→891、SHA相違） |

  1回で成功（frames=3000） |

  （**連続READが1件も現れなかった**） |
| 決定論性 | 独立2回目も`--list-all-stages`で完全一致
  （不一致0件、FDCコマンド種別列79件・ポート値列15800件とも全長一致） |

### 水準M（M=32）

| 項目 | 結果 |
|---|---|

| ファイル数増加の独立確認 | S水準複製との`FILES 2`画面署名比較で

**参考（値は見ない範囲の比較）**: S水準複製とprewrite参照複製の

（総READ DATA件数も16件同士で一致）だった——**ファイルを8本追加しても
FDCコマンド種別列の構造（16件のREAD DATA、すべて単発）自体は変化せず、
ポート値列だけが13842件目以降で異なった。** M水準では総コマンド数が87件・
READ DATA18件に増えており、ディレクトリ読み出しに使うFDCコマンド数は
ファイル数の増加とともに緩やかに増えてはいるが、増分は小さく、連続READへ
移行する兆候は無かった。

### 水準L（M=128）— 容量超過

| 項目 | 結果 |
|---|---|
| 書込み | rc=0（プロセス自体は正常終了）だが、画面表示が`Disk full`という

**事前登録どおり「超えた」として記録し、代替の水準を追加していない。**
M水準（M=32）からL水準（M=128）への間で容量を使い切ったことがわかる。
書込みが未完了（`Disk full`）のため、L水準は`m7hh`のL水準と同じ扱いで
——大きさ変化の解釈対象にしない。読み出し測定・連続READ構造の記述は
L水準では公式の解釈対象として扱っていない（後述の開示節のとおり、完了
判定を試みる過程でL水準の画面本文が一度露出した事故はあったが、その
内容は結果の判定には使っていない）。

## `general_read_request`を通るか（合格条件4）

段階1で連続READが1件も現れなかったため、事前登録の代替規則（現れなければ
S水準）に従い、S水準の読み出し打鍵について、条件M（`build_mixed_rom`
混成、`--probe-site general_read_request --probe-mode cyl`）と探針なし
基準を、同じ書込み済み複製（の別コピー）に対して`--list-all-stages`で
比較した。

**SEEK段6段でシリンダ指定が不一致になった**（`grep -c 不一致`＝6件、
うち`grep 不一致 | grep -c SEEK`＝6件、全件SEEK段）。**この打鍵での
読み出し区間は`general_read_request`を通る。通った。**

## 決定論性

- S水準は読み出し測定を独立2回行い、`--list-all-stages`で不一致0件・
  FDCコマンド種別列79件・ポート値列15800件とも全長完全一致を確認した。
- M水準は1runにとどめた（差が出なかった水準は1runにとどめるという
  事前登録の明記事項）。
- L水準は書込み自体が完了しなかったため、決定論性の対象外。
- 陽性対照・`general_read_request`探針測定は1回のみ（事前登録の合格
  条件に決定論性を要求されていない項目であり、`m7hb`〜`m7hh`も同様の
  扱い）。

## 元ディスクを壊さない

全測定で使ったのは`tools/stage_disk_by_digest.sh`が作る使い捨て複製の
みである。`disk#8`元ファイルへの書込みコマンド（`--save-to-disk-image`）
は、すべて`--disk2`（複製先パス）に対してのみ指定した（`--disk`は起動用
固定複製`boot/650cfac8.d88`のみに使い、`--save-to-disk-image`はB:選択の
打鍵しか行わない書込みプログラムと組み合わせているが、A:の内容自体は
本稿のプログラムでは変更していない）。元ファイルパスを直接`--disk`/
`--disk2`へ渡したことは一度もない。全測定終了後、`PC88_REF_DISK_DIR`
配下のファイルからbasenameのダイジェストが`650cfac8`に一致する1本を
特定し、SHA-256が計算できることを確認した（`tools/stage_disk_by_digest.sh`
が複製専用に読み取り専用の`cp`しか行わないこと——スクリプト本文で確認
済み——と矛盾しない。値そのものは記録しない）。

## P1〜P5の判定

- **P1**（件数がファイル数に追随） / **P2**（一定）: 段階1で連続READが
  1件も現れなかったため、判定対象外（追随する/しないを議論する前提で
  ある「連続READが現れる」こと自体が成立しなかった）。
- **P3**（どの水準でも現れない）: **成立。採用（測定できた範囲では）。**
  S水準（総READ DATA16件）・M水準（総READ DATA18件）のいずれも、run長
  がすべて1で、連続READ DATAは1件も現れなかった。
- **P4**（段階3で1.57節の差が再現） : 段階3は未実施のため判定対象外。
- **P5**（陽性対照不通過／ファイルを作れない）: 陽性対照は通ったが、
  **L水準に限っては「容量超過で作れなかった」という意味でP5の一部に
  該当する。** ただしS・M水準は正常に作成・測定できているため、実験
  全体がP5で無効になるわけではない。

**主判定はP3（S・M水準の範囲で）。ただしL水準は容量超過により未測定の
まま残った（決まらなかった）。**

## 言えること・言えないこと

**言えること:**

- `disk#8`上に、`FILES`署名比較で独立に確認できるだけのファイル数の
  違いを持つ2つの状態（S水準=8本追加、M水準=32本追加）を作り、それぞれ
  `FILES 2`を打鍵して読み出したが、**いずれもREAD DATAはすべて単発
  （run長1）で、一度も連続しなかった。**
- 未書込み参照複製とS水準（8本追加）を比較すると、**FDCコマンド種別列
  自体（16件のREAD DATA、すべて単発という構造）は変化せず**、ポート
  値列だけが差分を示した。ファイルを8本追加しても、ディレクトリ読み出し
  に発行されるFDCコマンドの「形」自体は変わらなかった。M水準（32本
  追加）では総READ DATA件数が18件へわずかに増えており、ファイル数の
  増加に応じてコマンド数がまったく無反応というわけではないが、増分は
  小さく、連続READへ移行する兆候は無かった。
- S水準の読み出し打鍵が`general_read_request`を通ることを、
  `--probe-site general_read_request --probe-mode cyl`で確認した
  （6段中6段でシリンダ不一致、全件SEEK段）。
- L水準（M=128）は`disk#8`の複製上で容量を使い切り、`Disk full`という
  BASICのエラーで書込みが打ち切られることを確認した。

**言えないこと:**

- L水準（大きい方の極値）でどうなるかは、容量超過のため測定できて
  いない。**「ファイル数をさらに増やせば連続READが現れる」可能性を、
  本稿は否定も肯定もできていない。** S・M水準という、本稿が容量内で
  作れた範囲でのみ「現れない」と言える。
- **`disk#10`の連続READ構造が、本当に「ディレクトリの大きさ」以外の
  別の性質に由来するのかどうかは、本稿だけでは確定できない。** 本稿が
  切り分けたのは「`disk#8`という書込み可能な土俵の上で、ディレクトリの
  ファイル数を測定できた範囲（最大32本追加）まで増やしても現れない」
  という事実だけである。`disk#10`固有の他の可能性——例えば`m7hf`が
  確認した`bad allocation table`（新規ファイルを一切書けない状態）自体
  が、ディレクトリの空き状況や断片化と関係する何らかの性質を示して
  おり、それが連続READとも関係するかどうかは、本稿では検討していない
  （両者が同じ根本原因を共有する可能性を、支持も反証もしていない）。
- `disk#8`の**ディレクトリ自体の構造**（何セクタ・何トラックがディレクト
  リ領域として予約されているか）を本稿は一切確認していない（値を見ない
  という制約の範囲内であり、この確認自体を試みていない）。ファイル数の
  増加に対してFDCコマンド数がほとんど反応しなかった（16件→18件）事実
  は、「ディレクトリ領域自体が固定サイズで、空き具合に関わらずほぼ
  全域を毎回読む」という可能性と整合するが、本稿はこれを積極的に検証
  していない（示唆にとどまる）。
- L水準（128本、容量超過に至る規模）でディレクトリがどう振る舞うかは
  未測定である。

## 次に何を測れば絞れるか

1. **容量に余裕を残したより大きい水準を新たに事前登録する。** 本稿の
   M水準（M=32）とL水準（M=128、容量超過）の間（例えばM=64前後）を
   狙う新水準を立てれば、「ファイル数を今回より増やしても現れない」
   という主張の範囲をさらに広げられる。
2. **`disk#10`の`bad allocation table`（`m7hf`）とディレクトリ状態の
   関係を、BASIC言語仕様の範囲で確認する。** `refs-nec-manuals-
   2026-09-04.md`が可としている資料のエラーメッセージ一覧を確認し、
   このエラーが具体的に何を検査して出るものか（(a)の範囲）を見る
   価値がある。これが分かれば、`disk#10`のどんな状態が「連続READ」
   とも無関係ではないかの手がかりになる可能性がある。
3. **`disk#1`・`disk#2`以外の候補ディスクを新たにスクリーニングし、
   `disk#10`ほどではなくても連続READ区間が現れる別候補がないか探す。**
   `disk#10`に依存しない再現条件を得られれば、「大きさ」「位置」以外の
   変数（例えばディレクトリの断片化状態）を切り分ける土俵になる。
4. **本稿で確認した「ファイル数を増やしてもFDCコマンド数がほぼ変化
   しない」という観察を、より広い水準幅で確認する。** S→M（8本→32本）
   で16件→18件という小さな増分だったが、これが線形なのか、閾値的な
   のかは、本稿の2点だけでは判定できない。

## 開示

**手順上の事故（隠さず記載する）:** L水準の読み出し測定の完了判定
（`reached`が偽になった原因の切り分け）を行う使い捨てデバッグの過程で、
`tools/check_l3_entry_screen.py`の`screen_rows()`が返す画面本文の生の行を
`print()`で標準出力へ直接表示した。この出力には`disk#8`の実際のディレクト
リ一覧（既存の実ファイル名を含む）が含まれていた。これはCLAUDE.mdの
「使い捨てのデバッグでもディスクの実ファイル名を展開して表示しない」
「値（…画面本文）を書かない」という明示的な禁止事項への違反である。

この出力は**コミットした成果物（本稿を含む）には一切含めていない**。
発生箇所はツール呼び出しの標準出力（本稿の担当セッションの作業ログ）
に限られ、`private/`・追跡ファイル・git履歴のいずれにも書き込んでいない。
発覚後、直ちに以降のすべての画面確認を、行数・文字数・SHA-256による署名
比較、または`reached()`系関数が返す真偽値のみに限定する方式へ切り替えた
（本稿の結果の記述・判定は、この署名・真偽値ベースの再測定にのみ基づく。
露出した生の内容そのものは判定に使っていない）。

この事故を踏まえた再発防止として、本稿以降の測定では、画面本文を扱う
すべてのヘルパ関数呼び出しの戻り値を、直接`print`せず署名（`screen_
signature`）または真偽値経由でのみ扱うよう統一した。

それ以外の手順逸脱: `OPEN "O",#1,F$`から`OPEN F$ FOR OUTPUT AS #1`への
構文切替（1回）と、`--disk2`の付け忘れによる無応答からの構成修正
（1回）が発生した。いずれも事前登録の「構文の妥当性そのものは段階1で
実測して確認する」という想定内の手続きの範囲であり、水準・意図は
変えていない。L水準の`Disk full`は隠さず記録した（事前登録どおり、
代替水準を追加せず「超えた」とだけ扱った）。測定はすべてフォアグラウンド
で実行し、測定中に`git stash`・ブランチ切替・ファイル編集は行っていない。
無言でSKIPした分岐は無い。
