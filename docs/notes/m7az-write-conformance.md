# m7az: 書き込みの適合判定を用意した。ただし混成はまだSAVEに届かない

作業日: 2026-08-19

## 情報境界

公式ROM一式・公式diskAの**使い捨て複製**（複製側だけライトプロテクト解除。
原本には書かせていない）を**実行して**測定した。読んでいない。
期待値ファイルに置くのは**件数・総バイト数・SHA-256だけ**で、値は置かない
（`tests/conformance/expected.tsv` と同じ方針。CLAUDE.md禁止事項4）。
本ノートも件数と一致件数だけを扱う。

## 1. まず「そもそも届くのか」を測った

判定の設計より先に、**混成ROM（公式main + 自作サブROM）が公式diskAで
SAVEまで進むのか**を測った。同じ打鍵（`10 PRINT "T"` → `SAVE"TQ"`）で
4200フレーム走らせて比較した。

| 構成 | FDCコマンド総数 | READ DATA | **WRITE DATA** |
|---|---:|---:|---:|
| 公式ROM一式 | 124 | 19 | **8件** |
| 混成（自作サブROM） | 47 | 8 | **0件** |

画面出力でも差が出た。公式はBASICの起動バナーとプロンプトまで出て打鍵内容が
表示されるが、**混成はBASICの起動途中（ファンクションキーの案内行の表示まで）
で止まる**。読み出し側の適合条件1（5635件）は満たしているので、そこから先の
どこかで止まっていることになる。

**したがって書き込みの適合は、いま判定しても必ず「未到達」になる。**
それでも判定の仕組みは先に置く——次に進む先を示す指標になるし、進んだ瞬間に
自動で判定へ切り替わるからである。

## 2. 判定の形

適合条件1（`main が IN $FD で受け取る値の列`）と同じく**ハッシュだけ**で置く。

- 対象: subがFDCへ発行したWRITE系コマンドの**パラメータ8バイト＋データ部**を
  発生順に連結した列
- 出す数値: コマンド件数・総バイト数・SHA-256（`tools/hash_write_stream.py`）
- 期待値: `tests/conformance/expected_write.tsv`（1行、値は含まない）

**決定論性を確認してから期待値にした**——公式ROM一式で同条件3回、
件数8・2112バイト・SHA-256とも完全一致。

「mainが受け取る列」ではなく「subがFDCへ流した列」を対象にしたのは、
SAVEという操作の**成果物がディスクの中身だから**である。sub内部のI/O列全体の
一致（仕様書第22版が「適合条件ではない」と明記している）を要求するものでは
なく、書き込みの中身と座標だけを見る。

## 3. `conform_l3.sh` への配線

書き込みが0件なら**失格ではなく「未到達」**（`--`）として報告する。
判定できないことを黙って合格にも失格にもしない。1件以上あれば期待値と
突き合わせる。現時点の出力は未到達である。

## 4. 検出力

`tools/analyze_write_path_selftest.sh` に3項目を追加した（合成フィクスチャ
のみ、公式データ不使用）:

- 同じ内容の合成ログからは同じSHA-256が出る（決定論性）
- **陽性対照**: データ部を1バイト減らすとSHA-256が変わる
- 書き込みが1件も無いログは判定不能（rc=2）として報告される
  ——黙って合格に化けないこと

## 5. 途中で見つけたハーネスの既知欠陥（起動時クラッシュ）

条件5を配線したあと `conform_l3.sh` が**不安定に落ちる**ようになったので追った。
結論は**私の追加分ではなく、前からあった欠陥**である。

- `q88measure` は**公式ROM一式を `--rom-dir` に与えたときだけ**、起動時に
  `Abort trap: 6` で落ちることがある。実測 **8回中3回**（自作ROM一式では
  8回中0回）。ロケールには依存しない（C でも UTF-8 でも起きる）。
- 落ちるのは**フレームループへ入る前**で、**ログファイルは1バイトも作られない**。
  部分的な測定結果を拾ってしまう危険は無い。

**ここで私は一度観測を誤った。** 最初「クラッシュしても同じログが出ている
（ハッシュ11件が全部一致）」と読んだが、実際は**成功した実行のログだけを
数えていた**（失敗した実行はファイルを残さないので、そもそも比較対象に
入っていなかった）。デバッグ出力を入れて確かめ直したところ、落ちる位置は
終了処理ではなく**起動時**だった。

対処: `tools/lib_l3_measure.sh` に `run_q88measure_retry` を追加し、
`conform_l3.sh` の全測定をこれ経由にした。**失敗を隠すためのものではない**——
再試行したことも、全試行が失敗したことも、必ず標準エラーへ出す（最初の実装は
注記を測定ログ側のファイルへ吸わせてしまい、画面には「ログが無い」という
別の例外だけが見える状態になった。呼び出し元のstderrへ出す形に直した）。
上限は4回（`Q88_MEASURE_ATTEMPTS` で変更可）。

**根治はしていない。** 第三者コアの起動処理に起因すると見られるが、原因は
未特定のまま既知欠陥として残す。再試行の注記が毎回出るので、頻度が悪化
したら気づける。

## 6. 次に効くこと

混成がBASICの起動途中で止まる原因の切り分けが、書き込み適合の前提になる。
`tools/diag_l3_mixed.sh` の構造的一致プレフィックス（main側258件）とは別に、
**5635件を超えたあとの区間**を見る必要がある。
