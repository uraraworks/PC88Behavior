# B54: `0x16` のあとの G1 の次の分かれ目を測る — 結果

記録日: 2026-11-01
規則: [b54-g1-next-divergence-preregistration.md](b54-g1-next-divergence-preregistration.md) どおり。測定はクラウドの実行環境で OO・SS 各 1 走。関門 2 項目は通った。値は記録していない。記録は `measurements/b54-g1-*.txt`。

## 結果

- 27 バイトの要求は、公式も自作も 27 バイト読む（B49 の 23 から直った）。位置の差の変わる点は無くなった
- RAM 上のコードの最初の違いは 499686 件目で、発行元 `7838` が番地 `7817` を読む値が違う。その直前は `7838` が `7815`、`7816` を読み、`7839` が `69D0`、`69D1` を読んでいる
- 公式は次に `seek` を含む FDC の読みへ進み、自作は main から 4134 バイトを受け取る別の道へ進む

## 読み方（推定）

RAM 上のコードは `7815` からの数バイトを、`69D0` からの数バイトと順に比べている。`7815`・`7816` は同じで、**`7817` で違う**。B34 の `7815-781A` は ROM が書いた範囲である。

自作の `0x16` は先頭 2 バイトしか書かないので、ここで違うのは当然である。つまり**公式は G1 の `0x16` で先頭 2 バイトより多く書いている。** B52 の「2 バイトだけ」と合わない。

原因はプローブの送り方と考える。B52 のプローブは組のあいだに `OUT $FF` 0x0F と bit 1 の待ちを入れた。B49 の G1 の送り方には組のあいだの 0x0F は無い。0x0F は要求の始まりの合図なので、公式はそこで本体を打ち切った可能性がある。**第231版の「先頭 2 バイトだけ」は誤りの可能性が高い。** B52d で送り方を直して測り直す。
