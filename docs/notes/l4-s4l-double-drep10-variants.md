# l4-s4l — 倍精度の定数読み取り新候補DREP10の2変種（DREP10E/DREP10A）

記録日: 2026-09-15。l4-s4k(ec794b9)はno_survivor(DEXACT/DGW/DREP01の
どれも実測を再現できなかった)だったのを受け、Codex(gpt-5.6-sol)が
GW-BASIC edf82c2のソースとl4-s4kの実測36件から新しい候補DREP10を立てた。
**測定はしていない。判定には使わない。**

## Codexの分析ノート(出所)

Codex(gpt-5.6-sol)が、GW-BASIC MIT公開ソース(コミット
`edf82c2ebf6bfe099c2054e0ae125c3efe5769c4`)のMATH1.ASM/MATH2.ASMと、
l4-s4kの実測結果(自分で打った式のPRINT出力、親セッションから渡された値)
から導出した分析。要点(測定した生の値そのものは転記しない、クリーンルーム
規律7番)は`docs/notes/l4-dfin-model-search.md`にまとめた。

## DREP10の定義

数字を先頭から`acc=acc*10+d`で積み上げ1手ごとに倍精度(56bit仮数)へ丸め、
正味の指数`n`が正なら10を`n`回掛け、**負なら真の÷10を`|n|`回行い**、
1手ごとに56bitへ丸める。l4-s4kのDREP01(負側は倍精度に丸めた0.1との乗算)
との違いはここだけ——DREP10は「厳密な0.1」相当を毎回の真の除算で処理する。

Codexの分析はl4-s4kの実測36件すべてをDREP10で再現できることを確認した。
丸め方(ちょうど半分のタイの扱い)は「最近接偶数(EVEN)」でも「絶対値の
大きい側(AWAY)」でも36件とも一致したため、2変種
**DREP10E**(round-half-even)・**DREP10A**(round-half-away)が両方とも
候補として残った。

## ソースで確認できたこと(Codexの分析より)

- `$FMULD`/`$ROUND`(倍精度乗算・丸め、`MATH2.ASM`)と`DDIV`(倍精度除算、
  `MATH1.ASM`)は、拡張byte(ガード)へ`80h`を加えてcarryを伝播し、
  厳密な半分では保持仮数LSBを0にする——つまり**最近接偶数**であることが
  ソースの命令列から確認できる。
- 一方、`$FINE/MDPTEN`(定数の指数適用)自体は倍精度`10^n`表による
  **一括**乗算/除算であり、1桁ずつ反復する`$MUL10`/`$DIV10`をこの経路が
  呼ぶ根拠はソースにない。**つまりDREP10の「1桁単位で反復する」という
  手順自体は、36件の実測から得た事後の推測であり、edf82c2のソースに
  直接の根拠はない。** 丸め方(最近接偶数)・真の除算であること(倍精度の
  `$DIV10`も内部的には丸め済み0.1定数との乗算であり真の除算ではない、
  という点も含め)はソース根拠がある一方、反復回数を常に1桁単位にする点
  だけが実測からの特定である。

## リポジトリへの実装

`tools/l4_dmodels.py`に`drep10e`/`drep10a`を追加した(l4-s4kのDEXACT/DGW/
DREP01と同じ独立実装の方針、`tools/l4_mbf_oracle_v2.py`は変更していない)。
数字の積み上げは常にround-half-even(`$MUL10`→`$FADDD`を別々に呼ぶ構造を
再現し、桁ごとに2回roundする)、指数適用の×10/真の÷10だけがDREP10E/
DREP10Aで丸め方を切り替える。

**Codexのdfin_model_search.py(scratchpad)との突き合わせ**: 乱数1万件
(小数点を除いて8〜16桁、指数-20〜+20)でDREP10E/DREP10Aとも**バイト単位で
完全一致**した(不一致0件)。桁数を8〜30桁に広げた追加の1万件(候補の
`x-c`形で使う大きい整数の`c`を模した範囲)でも不一致0件だった。

**突き合わせ中に見つけた自分の実装ミス**: 最初、数字の積み上げを
「×10と+dをまとめて1回round」で実装していたところ、20桁を超える大きい
整数(候補の`x-c`形で使う`c`)でCodexの結果と食い違った。$FIDIGが
`$MUL10`と`$FADDD`を別々に呼ぶ構造どおり「×10をround」→「+dをround」の
2回roundに直したところ、突き合わせが完全一致した(詳細は
`tools/l4_dmodels.py`の`_magnitude_drep10`のコメント参照)。

## 候補と対照

`tools/gen_l4_s4l_candidates.py`/`tools/gen_l4_s4l_controls.py`で生成。
書式は4候補とも共通(16桁・rstar・`--fout-algo gw`)。

- 候補(`docs/notes/l4-s4l-candidates.tsv`、16件): group
  pos(正の指数側、Codexの5本+自前3本)8件、hash(#付き小数+明示指数)4件、
  intdec(8桁以上の整数+小数+明示指数)4件。DEXACTとも異なるものは6件。
- 対照(`docs/notes/l4-s4l-controls.tsv`、12件): 4グループ各3件、
  DREP10E/DREP10A/DEXACT/DREP01の4方式すべてが一致する式。9件は答えが
  0でない。

### neg(負の指数側)で見分ける式が見つからなかった理由

候補表のgroup negは0件である。負の正味指数(真の÷10の反復)だけを使う
打鍵可能な式(`#`付き小数・8桁以上の整数+小数を含む、明示指数を付けない
自然な形はすべてこちらに属する)を、直接のPRINT出力・`x-c`形の引き算の
両方で合計10万件以上乱数探索したが、DREP10EとDREP10Aが1件も食い違わ
なかった(リテラル単体のMBFエンコード比較でも0件)。

理由の見立て: ×10の反復(group pos)は1手ごとに仮数が約3.32bit分
「はみ出す」ため、はみ出した下位ビットが偶然ちょうど半分のパターンに
なる(タイが起きる)頻度がそれなりにある。一方、真の÷10の反復は
剰余(mod 5^k的な性質)の分布によるタイの出現条件がはるかに狭いらしく、
本探索の乱数分布では1件も再現できなかった。Codex自身が提示した5本の
判別式(`docs/notes/l4-dfin-model-search.md`参照)もすべて正の指数側
(×10)であり、この非対称性と整合する。**厳密にタイが起こりえないという
証明ではなく、探索で見つからなかったという結果である。**

## 手検算用の途中経過(候補表2行、DREP10EとDREP10Aが分かれる例)

いずれも`tools/l4_dmodels.py`の`_round_even_frac`/`_round_away_frac`
(56bit)を使い、数字の積み上げ(×10→+dの2回round)のあと、正味指数の分だけ
×10を1手ずつ丸め直す過程を追った。「TIE」と書いた手は、その手で
round-half-evenとround-half-awayの結果が実際に分かれた(=厳密にちょうど
半分だった)ことを意味する(それ以外の手はどちらの丸め方でも同じ結果に
なる=タイではない)。

### 1. `print 8937451488973898e+7-89374514889738978066432`(group pos、
   source=codex)

定数`8937451488973898e+7`: 桁文字列`"8937451488973898"`(16桁)、
小数点以下0桁、指数`7`なので正味指数`n=7`。

- 桁の積み上げ(2回round×16桁)は厳密(16桁の整数は56bitに収まるため
  丸めの影響なし)。積み上げ後: `acc=8937451488973898`。
- 正味指数`n=7`なので、`acc*10`を7回、毎回56bitへ丸め直す。
  - 1手目: `89374514889738980`(EVEN=AWAY、タイなし)。
  - **2手目でタイが起きる**: `893745148897389792`(EVEN)と
    `893745148897389808`(AWAY)に分かれる。
  - 3〜7手目もそれぞれの経路上でタイが起き続け、両者は再収束しない。
  - 7手目(最終)の結果: EVEN=`89374514889738978066432`、
    AWAY=`89374514889738982260736`。
- 候補式はこの定数から整数`89374514889738978066432`(EVEN側の値そのもの)
  を引く形なので、EVEN側は`0`、AWAY側はその差`4194304`(`=2^22`)が
  そのまま残差としてPRINTに現れる。

### 2. `print 873010505.746e+16-8730105057459999780896768`(group pos、
   source=own)

定数`873010505.746e+16`: 桁文字列`"873010505746"`(12桁)、小数点以下3桁、
指数`16`なので正味指数`n=16-3=13`。

- 桁の積み上げは厳密。積み上げ後: `acc=873010505746`。
- 正味指数`n=13`なので`acc*10`を13回、毎回56bitへ丸め直す。
  - 1〜8手目はタイなし(EVEN=AWAY)。
  - **9手目でタイが起きる**: `873010505745999986688`(EVEN)と
    `873010505746000003072`(AWAY)に分かれる。
  - 10〜13手目もタイが起き続け、再収束しない。
  - 13手目(最終)の結果: EVEN=`8730105057459999780896768`、
    AWAY=`8730105057460000049332224`。
- 候補式はEVEN側の値を引く形なので、EVEN側は`0`、AWAY側は差
  `268435456`(`=2^28`)がPRINTに現れる。
