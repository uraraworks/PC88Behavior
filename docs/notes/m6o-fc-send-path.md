# M6o — sub `OUT $FC` / main `IN $FD`（5635件）は独立した「もう1本のSEND経路」か

測定日: 2026-08-12
対象: 混成ROM（自作sub＋公式main）を公式環境で実走した診断で得られた
ポート別内訳。基準ログ（公式sub）では sub `OUT $FD`=6672件・
main `IN $FC`=6672件（対）、sub `OUT $FC`=5635件・main `IN $FD`=5635件
（対）の2組の一致が見つかった一方、混成ログでは後者が両CPUとも
0件だった（自作subが`OUT $FC`を一切実装していない）。これが
`docs/spec/l3-subrom.md` 1.15節「sub視点のSENDプリミティブ」
（手順2`OUT $FD`のみを定義）に対する**もう1本の独立したSEND経路**なのか、
既存の1.6節・1.14節「起動時バルクバースト」・`tools/analyze_bulk_trigger.py`
（m6j）が既に見つけていた「並行チャンネル」（当時は意味論未確定のまま
3節に残されていた）の**同一物**なのかを確認した。

**追加測定は行っていない。** 既存の `measurements/m6c-sub-{d0-boot,
d1-files,d2-save,d5-seqfile}.iolog.txt.gz`（4条件）と、共通クロック付きの
`measurements/m6g-d0-boot-run{1,2}.iolog.txt.gz`を再解析した。値は
一切使わず、port/kind/pc/clockの各列だけを見ている。

新規解析器: `tools/analyze_fc_send_path.py`。`tools/analyze_bulk_trigger.py`
の`find_target`/`pc_histogram`をimportして再利用し、パーサ・分類ロジックを
二重実装していない。

再実行方法:

```
python3 tools/analyze_fc_send_path.py cross \
    --iolog measurements/m6c-sub-d0-boot.iolog.txt.gz \
            measurements/m6c-sub-d1-files.iolog.txt.gz \
            measurements/m6c-sub-d2-save.iolog.txt.gz \
            measurements/m6c-sub-d5-seqfile.iolog.txt.gz \
    --label d0-boot d1-files d2-save d5-seqfile \
    --out measurements/m6o-fc-send-path-cross.txt

python3 tools/analyze_fc_send_path.py clockpair \
    --iolog measurements/m6g-d0-boot-run1.iolog.txt.gz \
    --out measurements/m6o-fc-send-path-clockpair-run1.txt
```

## 1. 結論: 独立した第2のSEND経路ではなく、既存のバルクループの一部

**確定**: sub `OUT $FC`（5635件）は、4条件すべてで例外なく、
`docs/spec/l3-subrom.md` 1.6節・1.14節が既に確定していた
起動時バーストと同一のイベント集合である。

- pc分布が完全一致: `709E`5632件＋`70E5`3件（境界2種）。
  `tools/analyze_bulk_trigger.py` Q3（m6j既報）と同じpc・同じ件数。
- 発生frameが42〜62（1.6節既報の範囲）に収まる（d0-bootで確認、
  他条件も件数一致から同一と判断）。
- **新たに確認**: sub `OUT $FC`の直後、次のFC/FDイベントまでの間に
  sub `OUT $FD`（pc=`70A2`側の対）が**必ず隣接して現れる**
  （4条件合計 22,540件のFCイベントすべてで隣接あり、例外0件。
  `tools/analyze_fc_send_path.py`のQ3集計）。つまりバルクループは
  1周期につき`OUT $FC`→`OUT $FD`の順で**2バイトを連続して書く**構造であり、
  「`$FC`経由の転送」（1.6節）と「`$FD`経由の転送」は別々の経路ではなく、
  **同じ1つのループが両方のポートを毎周期ペアで使っている**。
- main側も対称: `IN $FD`(`C265`)の直後に`IN $FC`(`C269`)が来る同じ構造
  （`tools/analyze_bulk_trigger.py`が既に「補足」として記録していたが、
  sub側の対応する書き込みpcまでは特定していなかった）。

**新たに確認**: sub `OUT $FC`の直前で最も近い sub `OUT $FF`の値は、
4条件すべて・全5635件で例外なく`09`だった（`fc_ff_before`）。これは
1.15節sub視点SENDプリミティブの手順3「`OUT $FF`に`09`を書く」と
**同じ語彙**であり、バルクループ専用の未知の値ではない。ペア先の
`OUT $FD`直後の`OUT $FF`は主に`08`（1.15節手順5と同じ語彙）だった。
1.14節Q2（m6j既報）が見つけていた「`$FE`待ちを挟まない専用の
5命令`OUT $FF`列」は、この定常ループそのものではなく**バルクへの
遷移（入口）でのみ**現れる別の手順であり、定常ループ本体は既存の
SEND語彙（`08`/`09`）を再利用している。

## 2. main `IN $FD`とsub `OUT $FC`の対応（時間的裏付け）

共通クロック付きログ`measurements/m6g-d0-boot-run1`で、sub `OUT $FC`
（pc=`709E`、clock付き5635件）とmain `IN $FD`（pc=`C265`/`C2DB`、
clock付き5635件）を発生順に1:1対応させ、clock差（main−sub）の分布を見た。

| delta | 件数 |
|---|---:|
| 5 | 5630 |
| 26 | 3 |
| 25 | 1 |
| 6 | 1 |

**99.91%が`delta=5`で一定。** subの書き込みが常に先行し、mainがほぼ一定の
短い遅延で追随する——同一ラッチの書き手/読み手であることの直接証拠になる。
少数の外れ値（delta=25/26が4件、境界pc`70E5`/`C2DB`付近と推定）は
バーストの入口・出口での特殊経路（1.14節既報）によるものと考えられ、
定常ループの結論を覆さない。

`run2`でも同じ解析を実行し、末尾のファイル名行以外で`diff`が0行である
ことを確認した（決定論性）。

## 3. 4条件での一致状況

`tools/analyze_fc_send_path.py cross`の結果（`measurements/
m6o-fc-send-path-cross.txt`）:

- `sub_OUT_00FC`・`main_IN_00FD`のpc分布パターン: **4条件完全一致**
  （件数まで一致。5632/3固定）。
- `sub_OUT_00FD`・`main_IN_00FC`のpc分布パターン: 一致しない
  （**想定どおり**。この2ポートはバルク分5635件に加え通常ハンドシェイク
  SEND/RECV分も含み、条件ごとにファイル操作の回数が違うためハンドシェイク分の
  件数が変わる。バルク分5632/3は下記のとおり全条件で共通）。
- `fc_ff_before`（`OUT $FC`直前の`OUT $FF`値）: **4条件完全一致**
  （常に`09`のみ）。
- `fc_fd_adjacent`（`OUT $FC`直後に`OUT $FD`が隣接）: **4条件とも
  100%（隣接なし0件）**。
- `fd_ff_before`/`fd_ff_after`（`OUT $FD`前後の`OUT $FF`値）: 件数の内訳は
  条件ごとに異なるが、これはハンドシェイク分の回数差によるもので、
  値の**語彙自体**（`{0C,09,08,None}`）は4条件で変わらない。

1件も例外なく成立した項目（pc分布・隣接・`fc_ff_before`）と、
条件依存で件数が変わるが語彙は共通の項目（`fd_ff_*`）を区別して記載した。

## 4. 未確定として残すこと（推測で埋めない）

- **`OUT $FC`/`OUT $FD`の2バイトが何を表すか（データ意味論）。** 値が
  伏せ字のため本測定手法では確認できない。「粗いカウンタ+実データ」
  「2つの独立したバイト列のインターリーブ」等はいずれも推測であり、
  本稿では採用しない。`docs/spec/l3-subrom.md` 3節の既存項目
  「バースト中に並行して発生するmain `IN $FC`（5634件）の意味論」を
  引き継ぐ（今回、対応するsub側の書き込みポート`OUT $FD`の特定・
  main `IN $FD`との時間的対応の確認まで進んだが、データの意味は
  未確定のまま）。
- **このバルクの2チャンネル書き込み構造が、4条件（すべてdiskA起動を含む
  シナリオ）以外の操作でも同じ形で現れるか。** 本稿は起動時バーストの
  範囲でしか確認していない。
- **`fd_ff_after`で`09`/`08`の内訳がハンドシェイクpc（`0789`/`079E`/`071E`）
  とどう対応するかの詳細な切り分け。** 大まかな傾向（バルク分は`08`、
  ハンドシェイク分は主に`09`/一部`08`）は見えるが、pc単位で厳密に
  1:1対応させる分析は本稿では行っていない（本稿の主目的である
  「独立経路か既存バルクの一部か」の判定には不要と判断した）。

## 5. 実装への示唆

**1.15節（sub視点SENDプリミティブ）への追記は行わない。** 当初の見立て
（「sub視点SENDに`OUT $FD`とは別の`OUT $FC`経路がもう1本ある」）は、
本稿の解析で**支持されなかった**。実態は、1.14節が既に確定していた
起動時バルク転送ループ（frame42〜62、単一pc、$FEハンドシェイクを伴う
定常ループ）が、**1周期につき`OUT $FC`→`OUT $FD`の2ポートを連続して
書く構造**だったというだけであり、1.15節が扱う「1バイト単位の
汎用SEND/RECVハンドシェイク・プリミティブ」とは別の話である。
4条件すべてでsub `OUT $FC`はバルク区間の外に一度も出現しない
（総件数5635件＝バルク件数と厳密に一致）ため、汎用プリミティブとして
`$FC`書き込みが使われる場面は本稿の測定範囲では見つからなかった。

この結果は、混成ROM実走診断の観察（自作subの`IN $FD`が0件のまま）を
説明する: 自作subは1.14節のバルク転送ループ自体を実装していない
（`OUT $FC`を一度も発行しない）ため、mainが起動時バーストで期待する
2チャンネル分の書き込みのうち片方（`$FC`）が届かない。**対処は
1.15節の拡張ではなく、1.14節が要求するバルクループ自体の実装**
（6節・実装要件）であるべきで、これは本稿のスコープ外（実装コミットは
測定コミットの後、かつ今回は行わない）。
