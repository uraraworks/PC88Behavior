# m6i-d 第1回の試行 — 器具の不備で測定不成立（記録として残す）

記録日: 2026-09-23

[事前登録](m6i-d-gate-release-audit-preregistration.md)・[追補1](m6i-d-addendum1-unverified-arms.md)
に従って7腕×2走を実施したが、**器具の不備が2つ出て測定は成立しなかった。**
行き止まりを消さず、何が起きたかを記録する。腕の結果は使わない。

## 1. 結果

関門 G1〜G7 はすべて真だった（`run_all_selftests.sh` rc=0・107項 OK・SKIP 3項、
`check_cleanroom.sh` rc=0、凍結表照合 OK、`check_m6ib_rom_gate.py` の12腕 OK）。
そのうえで7腕×2走を回した結果、

- **14走すべてが `reached=false`** になった。事前登録の定義により全腕 `unreached`、
  総合判定は **`m6i_d_inconclusive`**。
- 同時に、**ゲートを持たない陰性対照 D-B0 でゲート run が観測された**
  （1本、長さ65535）。事前登録 §4 の定義により **`m6i_d_observation_unusable`**。

どちらも2走で同じだった。

## 2. 不備1 — 走らせた後に、走らせると変わるものを検査していた

`tools/analyze_m6id.py` の到達判定は、ROM 一式の SHA-256 照合に加えて
`sizes_valid(rom_dir)`（ROM ディレクトリの中身が所定の7ファイル**ちょうど**で
あること）を要求していた。

**エミュレータは実行中に、その ROM ディレクトリへ `generated.srm` を書き込む。**
解析は走らせた後に行うので、この検査は**必ず**落ちる。

- SHA-256 の照合は通っていた（`rom_set_sha256` は所定の7ファイルだけを対象に
  計算するので、増えたファイルの影響を受けない）。落ちていたのは
  「ちょうど7ファイル」の側だけである。
- `sizes_valid` は事前登録 §2 の到達指標に無い。**器具が独自に足した条件が、
  測定を丸ごと止めた。**

同型の器具（`tools/analyze_m6ic.py`）はこの検査を持っていなかったので、
m6i-c では表面化しなかった。

## 3. 不備2 — 観測していたのはゲートではなく、sub の通常の待ちループだった

陰性対照 D-B0 は**ゲートを持たない腕**なのに、長さ65535のゲート run が出た。
事前登録が定めた観測（`IN $FE` が連続する長さ32以上の run）は、
**sub が暇なときに待ちループでポーリングしている状態**と、
**ゲートで詰まっている状態**を区別できていない。

I/O ログには PC が入っているので、どの番地でポーリングしているかが分かる。
診断として、ゲートを持つ腕と持たない腕の sub の `IN $FE` を PC 別に数えた。

| 腕 | 最多の PC | 件数 | その番地の正体 |
|---|---|---:|---|
| B0（ゲートなし） | `044A` | 65535 | `IDLE_DISPATCH` |
| B5（ゲートあり） | `044A` | 65537 | `IDLE_DISPATCH` |
| B1（ゲートあり） | `0453` | 65535 | `IDLE_DISPATCH` |
| B2（ゲートあり） | — | 最大260 | 長いスピンなし |
| B6-A0（ゲートなし） | — | 最大262 | 長いスピンなし |

番地の正体は、`src/l3_service/make_subrom.py` の `build()` に `metadata` を
渡して得たラベル表から引いた（自作ROMのラベルであり、公式ROMは関与しない）。

**どの腕でも、長いスピンは `IDLE_DISPATCH` だった。ゲートではない。**

### ゲートは詰まっていない

同じラベル表から各腕のゲート番地を引き、その番地での sub の I/O を数えた。

| 腕 | ゲート番地 | その番地での sub I/O | 直後以降の sub I/O |
|---|---|---:|---:|
| B1 | `0x003E` | 1件 | 65661件 |
| B2 | `0x00EB` | 2件 | 2310件 |
| B5 | `0x0774` | 1件 | 65534件 |

**いずれも最初のポーリングで抜けている。** ゲートは
`IN $FE` / `AND` / `JR Z` の3命令であり、待ちビットが既に立っていれば
1回読んで通過する。**どの腕でもそうなっていた。**

## 4. これが意味すること

### m6i-c の副問は誤っていた

[m6i-c 結果](m6i-c-b5-b6a0-divergence-results.md) §5 は、C0・C3 の副問判定を
`gate_never_released` とし、

> sub は、main の通常SEND開始を最後まで検出できないまま、ゲートの中で回り続けていた。

と書いた。**この帰属は誤りである。** 長い run は `IDLE_DISPATCH` であり、
ゲートは最初の1回で抜けている。訂正は
[m6i-c 副問の訂正](m6i-c-subquestion-correction.md) に置く。

**m6i-c の総合判定 `m6i_c_sub_gate_only` は影響を受けない。** 総合判定は
4腕の通常READの成否だけで決まり、ゲート run の観測に一切依存していない
（[m6i-c 追補2](m6i-c-addendum2-reach-and-release.md) が到達指標から
ゲート観測を外していたため）。**従属する問いが崩れても主問が立つように
作っておいたことが、ここで効いた。**

### m6i-b の腕を疑う理由は消えていない。理由が変わる

m6i-c は「sub のゲートの有無だけが成否を決めている」を確定している。その一方で
ゲートは詰まっていない。**したがってゲートの実害は「止めること」ではなく、
`IN $FE` を1回余分に行うこと**にあるとしか考えられない。**本ノートはその機序を
測っていないので、ここで確定しない。**

いずれにせよ、ゲートを持つ B1〜B5 の結果は、ゲートの有無という1軸で
成否が変わる腕の結果である。**疑う理由は残る。** 変わったのは疑う理由の中身で
あって、疑わなくてよくなったのではない。

## 5. 次にやること

1. 到達判定から、走らせると変わるものへの検査を外す（不備1）。
2. 観測を、run の長さではなく**ゲート番地を踏んだかどうか**で行う（不備2）。
   ラベル表から番地が引けるので、ROM は1バイトも変えなくてよい。
3. 上を[追補2](m6i-d-addendum2-pc-anchored-observation.md)として測定前に置き、
   判定器を固定し直してから7腕を取り直す。

**本ノートの診断値（PC別の件数、ゲート番地での件数）を、取り直しの結果として
使わない。** 診断は器具の不備を特定するために行ったものであり、事前登録された
腕の測定ではない。

## 6. この記録で決まらないこと

- m6i-b のどの腕が使えるかは決まらない。本試行は測定として成立していない。
- ゲートの実害の機序（余分な `IN $FE` が何を壊すか）は決まらない。
- 公式ROM内部の実装、公式の送受信値、実機での絶対時間は決まらない。
- `docs/spec/l3-subrom.md` 1.65節は未確定のままである。
