# m7ap: 要求グループ決定関数のテーブル駆動化でフェッチ窓の予算を作り、窓超過を関門へ格上げ

測定日: 2026-08-18

## 情報境界

公式ROM・公式ディスクは今回一切使っていない。触ったのは自作サブROMの
生成器（`src/l3_service/make_subrom.py`）と自作の検査ツールだけで、
実行したのも公式環境の要らない自己検証系（`tools/verify_l3.sh`・
`tools/run_all_selftests.sh`）のみである。新設した
`tools/observed_request_decision_probe.py` は**自作ROMのバイト列だけ**を
解釈する（公式ROMは読まない）。本ノートに書く数値は自作コードのバイト数・
ケース数・件数であって、公式ROM/公式ディスクの内容ではない。

## 1. やったこと — 9段の即値比較チェーンをテーブル駆動へ

m7ao の宿題1（既定ビルドの9バイト窓超過の解消）と宿題2（LIMIT=4で
228バイトの削減）に着手した。削減対象は m7ao が名指ししていた
`_observed_single_by_request`（要求グループ→応答グループの決定関数）。

第51版までは9個の要求グループを即値比較の9段チェーンで書いていた。
1エントリあたり `LD A,(RUN_LEN)` + `CP n` + `JP NZ` の8バイト、
比較バイト1個ごとに `LD HL,nn` + `LD A,(HL)` + `CP n` + `JP NZ` の9バイト、
末尾に `LD A,n` + `CALL` + `JP` の8バイト。9エントリ・比較46バイトぶんで
**558バイト**を消費していた。

第52版ではこれを **ROM内の決定テーブル + その解釈器**へ書き換えた。

- テーブル1エントリ: `run_len, 比較バイト数n, 期待値[n], 送信種別, 応答値`
  （送信種別 0 = `SEND_BYTE`、1 = `SEND_BOOT_SINGLE_TRACKED`）
- 終端は `run_len = 0`（run_len は1以上しか取らないので終端に使える）
- 解釈器は `LD A,(DE)` / `CP (HL)` / `DJNZ` の素直な突き合わせループ

判定の**順序・比較する番地・比較値・応答値・送信ルーチンの選択**はいずれも
第51版と同一で、意味論は1ビットも変えていない。目的はフェッチ窓の予算だけ。

### 効果（自作コードのバイト数のみ）

| LIMIT | 第51版 used | 第52版 used | 第51版 窓超過 | 第52版 窓超過 |
|---|---|---|---|---|
| 1（既定） | 2106 | 1686 | 9 | **0** |
| 2 | 2180 | 1755 | 79 | **0** |
| 3 | 2246 | 1826 | 167 | **0** |
| 4 | 2320 | 1895 | 228 | **0** |

420バイトの削減で、**LIMIT=1〜4のすべてがフェッチ窓 0x0800 の内側に
収まった**。m7ao で「削るたびに指標が不変であることを確認する」ために
候補に挙がっていた `$F9` 診断の既定オフ化や `break_*` 故障注入の
オプトイン化（＝検出力を削って予算を作る手）は**一つも行っていない**。
検出力は第51版のまま全部残っている。

## 2. 窓超過を「報告」から「関門」へ格上げした

m7ao は `find_out_of_window_blocks()` を追加しながら、既定ビルドが既に
9バイト超過していたため `build()` を失敗させる関門には格上げできず、
報告に留めていた。1節で超過が0になったので、`build()` に無条件の
`SystemExit` を入れた。到達可能性の判定は m7ao のまま保守的
（`KNOWN_UNREACHABLE_LABELS` に明示したものだけ除外。現在も空集合）。

あわせて `build()` 内の straddle 検査を、既定引数で束縛された定数ではなく
**呼び出し時にモジュール定数を読む**形へ直した。selftest が
`SUB_ROM_FETCH_WINDOW` を差し替えて検出力を確認できるようにするため。

故障注入版を含む全ビルド（`--break-response` / `--break-dispatch-return` /
`--break-run-continuation` / `--inject-spurious-sense-int` /
`--break-sense-int-result-count` / `--break-fdc-timeout-reads-anyway` /
`--disable-fdc-timeout-mark`）× LIMIT=1〜4 の32通りが、新しい関門を
通ることを確認した（最大でも1909バイト）。

## 3. 陽性対照が2つ死んでいたので作り直した

`tools/subrom_fetch_window_selftest.sh` の陽性対照1・2は、
「LIMIT=2の既定ビルドが実際に straddle を1件持つ」という**実コードの
偶然**を検出力の源にしていた。テーブル駆動化でコードが縮み跨ぎが消えた
結果、この2つは**壊れているのに通る検査**（＝検出力ゼロ）になった。
実際、書き換え直後の実行で NG として顕在化した。

偶然に依存しない形へ作り直した:

- 陽性対照1: 幅2以上の命令を1つ選び、**その途中に境界を置けば必ず検出・
  先頭に置けば必ず非検出**であることを確認する（検出力と false positive
  の両方）
- 陽性対照2: `SUB_ROM_FETCH_WINDOW` を命令の途中へ動かし、
  `MAX_ALIGN_PADDING_ATTEMPTS=0` で `build()` が `SystemExit` すること
- 陽性対照4（新設）: 窓を 0x0400 に縮めると、2節で入れた窓外の関門が
  `build()` を止めること

最後の「窓超過量を報告する」節も、報告から**検査**へ格上げした
（LIMIT=1〜4で超過0バイトでなければ NG）。

## 4. `verify_l3.sh` はこの決定関数を一度も踏んでいなかった

書き換えの前後で `tools/verify_l3.sh` の判定14項目は完全に一致した。
**しかしそれを根拠にしてはいけない**ことを故障注入で確かめた。

- 故障注入A: 表の応答値を1ビット変える → `verify_l3.sh` の出力は**1文字も
  変わらない**
- 故障注入B: 表の並び順を逆にする（最初に一致するエントリが変わる）→
  **1文字も変わらない**

つまり `verify_l3.sh` はこの決定関数を一度も踏んでいない。「変更前後で
同一だった」はこの書き換えについて何も証明しない。**検出力を確認せずに
「不変だから安全」と書いていたら、そこで話が終わっていた。**

### 代わりに作った検出力のある検査

`tools/observed_request_decision_probe.py` +
`tools/observed_request_decision_selftest.sh` を新設した。

決定関数が使う命令だけを解釈する極小Z80を持ち、**組み上がったROMバイト列
そのもの**を `_observed_single_by_request` から実行する。`SEND_BYTE` /
`SEND_BOOT_SINGLE_TRACKED` への CALL、または `_observed_request_next_9`
（フォールバック）への到達で停止し、そのときの応答値と停止理由を結果と
する。未知のオペコードに当たったら黙って読み飛ばさず例外にする。

これを仕様側の参照モデル（表を上から見て最初に一致したものを採る、という
定義そのもの）と突き合わせる。216ケース（9グループ・各バイトの1点変異・
run_len違い・どれにも一致しない要求）で一致を確認。陽性対照は3種
（応答値の破壊・送信種別の反転・比較バイト数を1減らす）で、いずれも
期待どおり不一致として検出された。

### 第51版との等価性を直接確認した

同じ極小Z80で `git show HEAD` の第51版と第52版の両方を実行し、
**4278ケースで停止理由と応答値が完全に一致**することを確認した
（フォールバック経路の A レジスタは、入口の `CALL FDC_SENSE_DRIVE_STATUS`
が使う前に上書きするため比較から外している。この routine が引数として
レジスタを取らないことはコードで確認済み）。この突き合わせ自体の陽性対照
として、新側のテーブルを1バイト壊すと食い違いが出ることも確認した。

レジスタ規約の差分も確認した: 第51版はAとHLだけを壊したが、第52版は
B・C・DE も壊す。到達先3つ（`SEND_BYTE`・`SEND_BOOT_SINGLE_TRACKED`・
`FDC_SENSE_DRIVE_STATUS`）はいずれも引数を A でしか取らず、決定関数の
全経路は `JP IDLE_DISPATCH` で終わって呼び出し元へ戻らないため、
B/C/DE に生きた値は無い。
