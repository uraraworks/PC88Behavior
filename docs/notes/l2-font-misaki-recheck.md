# 美咲フォントの再判定 2026-08-07 — 「4x8だから不採用」は取りこぼしだった

## 経緯

`docs/spec/l2-font.md` 4.2節は美咲フォントを「半角(ANK)グリフが4x8」という
理由で不採用にした。これは ASCII 半角側については事実だが、美咲フォントは
そもそも **8x8 の日本語ビットマップフォント** であり、**全角側のかな・
カタカナは 8x8 で描かれている**。PC-88 のテキストセルはどの文字も 8 ドット幅
なので、必要なのは「8x8 のカタカナのグリフ」であって「半角と呼ばれている
グリフ」ではない。全角/半角という呼び名で切ってしまい実寸法で見ていなかった
のが取りこぼしの原因。現在の自作カナ(`KANA_ART`)は「判読できるが読みやすくは
ない」という評価が出ており、完成品である美咲に差し替えると改善する見込みが
あるため、再判定する。

対象: **X11 BDF 版**（`tools/fetch_misaki.sh` が取得する形式）。
確認日: 2026-08-07。一次情報のみを根拠にした
（配布元ページ `https://littlelimit.net/misaki.htm` と、配布アーカイブ
`misaki_bdf_2021-05-05.zip` 同梱の `misaki.txt` / `readme.txt`）。

## (a) 8x8のカタカナ63字が揃っているか — **揃っている**

JIS X0201 の半角カナ63字（`。「」、・ヲァィゥェォャュョッー` + `ア`〜`ン` +
濁点`゛`・半濁点`゜`、Unicode の U+FF61-U+FF9F に対応）それぞれについて、
**全角側の等価グリフ**（JIS X0201 半角カナ→全角対応表による。例:
U+FF71ｱ → U+30A2ア）が `misaki_gothic.bdf` に存在するかを、BDF を自前で
パースして機械的に確認した（公式ROMを一切参照しない検査。63字ぶんの
`ENCODING`/`DWIDTH`/`BBX` を突き合わせただけ）。

結果: **63字すべてが存在し、すべて `DWIDTH 8`（送り幅8ドット）**。
`BBX` の幅・高さも最大 7x7（`FONT_ASCENT 6` + `FONT_DESCENT 2` = セル高8に
収まる設計）で、8x8セルの内側に描かれていることを確認した。欠けている文字は
無い。

（`misaki.txt` の概要にも「一部の記号を除いた全ての文字は7×7ドットの範囲に
収まっているため、文字同士を隣接させても行間・字間が確保できる」との記載が
あり、実測と整合する。）

## (b) 出自の記述 — **気になる記述が1件ある。判断を保留する**

配布元ページ `https://littlelimit.net/misaki.htm` の「制作の経緯」節
（一次情報。アーカイブ同梱の `misaki.txt`/`readme.txt` にはこの節は無く、
Web ページ側にのみ記載がある）に、以下の記述がある（原文引用、下線相当は
`*1``*2``*3` の脚注参照）:

> 美咲フォントは PC-E500 系ポケコンの SCRNJPN*1 用に作られました。
> SCRNJPN で使用されるフォントは恵梨沙フォント*2 ですが、8×8 ドット一杯に
> 作られているためにどうしても文字同士の接触が発生してしまいます。
> （中略）その環境を見た美咲 礼威氏から「7×7 ドット内に文字を収めれば
> 字間ができて読みやすくなるのでは」との発言を受け、試作することにしました。
>
> [*2] 8×8 ドットの日本語ビットマップフォント。恵梨沙フォント PJ 作。

**評価（判断材料として提示。差し替え可否の最終判断はしない）:**

- unscii の "半角カナは MSX の 6x8 ROM フォントを参考に描き起こした" は
  **グリフの形そのものを既存フォントから引いた**という**derivation（派生）の
  申告**である。
- 美咲のこの記述は方向が逆で、**既存フォント（恵梨沙フォント）の字詰まりが
  読みにくいという問題を解決するために、7x7ドットに収める新設計を試作した**
  という**動機の説明**であり、字形を写した・参考にしたという申告ではない。
  恵梨沙フォント自体も「他機種の ROM フォント」ではなく、PC-E500 用に
  「PJ」氏が作った自作ビットマップフォント（SCRNJPN ドライバが使用）である。
- とはいえ、**別の既存8x8日本語フォントの名前が「制作の経緯」に明示的に
  登場する**という点は、今回の選定基準「出自を説明せずに済むか」
  （`docs/spec/l2-font.md` 4.0節）に照らすと**ゼロではない**。
  「なぜ美咲か」を説明する際に「恵梨沙フォントというものが先にあった」まで
  含めて語る必要が生じる可能性がある。

**この判定は自分（実装セッション）だけでは確定させない。** 指示にある
「(b) で気になる記述が出てきた場合は、差し替えずに報告して止まる」に従い、
**差し替え（3節の作業）は実施していない**。現状は自作カナ(`KANA_ART`)を
維持する判断のまま止めてある。

## 判断（利用者、2026-08-07） — **差し替えを進めてよい**

(b) は保留のまま提示し、最終判断を利用者に委ねた。以下の理由で「進めてよい」
との判断が出た。判断そのものをここに記録する（判定ノートは判断の根拠を
残す場所であり、判断者が変わっても経緯が読めることが目的）。

1. **引用箇所は動機の説明であって、字形の由来の申告ではない。** 「恵梨沙
   フォントは8×8いっぱいで字が接触するので、7×7に収める設計を試した」は、
   **既存フォントとは違う設計方針を採った**という説明であり、unscii の
   「MSXの6x8 ROMを参考に描き起こした」とは向きが逆（後者は字形そのものの
   derivation申告）。
2. **恵梨沙フォントはメーカーの ROM フォントではない。** PC-E500 用に
   有志（PJ氏）が作った自作ビットマップフォントであり、警戒している
   「原典ROM→誰かの解析→素材→実装」という由来の鎖には当たらない。
3. 出自を聞かれたときの答えが「美咲フォント。PC-E500用に7×7に収める設計
   方針で作られたもの」で済み、メーカー名もROMも出てこない。
   `docs/spec/l2-font.md` 4.0節の基準（出自を説明せずに済むか）を満たす。

止まった判断そのものは誤りではなく、指示どおりの動きとして扱う。

## 差し替えの実施

- `src/l2_font/make_font_rom.py`: `KANA_ART`（手描きASCIIアート、第2〜3版）は
  **削除せず残し**、ビルドには使わない扱いに変更。半角カナ63字は
  `--misaki-bdf` で渡した `misaki_gothic.bdf` から `parse_misaki_bdf()` /
  `misaki_glyph_to_rows()` で取得するように変更した。美咲は7x7に収める
  設計で文字ごとにBBX(幅・高さ・オフセット)が違うため、BDFの座標系
  （`FONT_ASCENT`/`FONT_DESCENT` とBBXのxoff/yoff）をそのまま8x8セルへ
  写像している（決め打ちで揃えるとずれるため）。
- `tools/l2_verify_independent.py`: 半角カナ側の独立実装を追従させた。
  BDFパースは生成器（行分割の状態機械）とは別の実装（正規表現による
  ブロック抽出）、ビット展開も生成器（ビットマップの行を辿って書き込む
  「前方」変換）とは別の実装（セル座標から元のビットマップ位置を逆算する
  「逆方向」変換、かつ整数ビット演算）にしてある。
  `--break-independent-path` で意図的に1行ずらして壊すと不一致で検出される
  ことを実測で確認した（`tools/verify_l2.sh` 2b節、下記の実行結果）。
- `tools/verify_l2.sh`: `--misaki-bdf` の受け渡しを追加。**フルパスで実行し、
  1(生成)〜4b(ピクセル比較+わざと壊す検査)まですべて合格を確認した。**
