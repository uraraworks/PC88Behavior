# m7cq — no_disk軸直前応答の実経路訂正とROM前段関門

日付: 2026-08-25

## 結論

最初の`--fast-no-disk-response-ready`は、
`EXCHANGE3_RESPONSE_PENDING`応答の`CALL SEND_BYTE`だけを
`SEND_BYTE_READY`へ変えた。人間実走は`requested=-3, effective=0,
control=5, fast=5, official=2, artifact_changed=False`でrc=2となった。

原因は、軸直前の1バイト応答がPENDING経路を通っていないことだった。
実経路は`SEND_DISPATCH_IDLE`の要求表にある1バイト`0x06`の
trackedエントリから`SEND_BOOT_SINGLE_TRACKED`を経て`SEND_BYTE`へ入る。
この訂正は症状に合わせたものではない。軸直前は「256バイト応答後の
1バイト要求」で、PENDINGを通らないことが実走で反証された。その条件で
FDC I/Oを挿まない1バイト要求表経路は`0x06` trackedだけである。

## 前周の内訳のどこが正しく、どこが誤りか

待機開始のmain `IN $FE`を0としたI/Oイベント列、

1. sub `IDLE_DISPATCH`の`IN $FE`（+1）
2. sub `SEND_BYTE`の重複`IN $FE`（+2、mainへhandoff）
3. mainの待機`IN $FE` 2件（+3/+4、subへhandoff）
4. sub `OUT $FD`（+5）

は正しい。誤りは、+2の`SEND_BYTE`を呼ぶ上流をPENDING経路としたことである。
実際は0x06 tracked経路なので、旧ノートの314T→241Tという全経路静的内訳も
対象経路の内訳ではない。実経路のtracked入口から`OUT $FD`までは
164T→85Tで、重複`IN $FE`に加え、介入版のtracked終端の命令構成差も6T含む。
T-state差79とI/O通番の予測-3を同一の量とは扱わない。

## 修正した介入

起動時最初のtracked 3応答は`EXCHANGE3_REQUEST_ACTIVE`の構築に必要なので
既定経路を保つ。4件目以降だけ、追跡カウンタを進めた後に
`SEND_BYTE_READY`へ入る。既定ビルドにはパディングを追加せず、
HEAD生成ROMとバイト完全一致する2042バイトのコードに戻した。
介入版は3バイト長い2045バイトで、後続番地も移動するため、
最終ROMの差分は1746バイトである。

## ROM前段関門と故障注入

ROM側フラグを使う走行は、q88measureを起動する前に必ず別ディレクトリへ
HEAD基準/既定/介入の最終`DISK.ROM`を生成する。HEAD基準と既定が不一致、
または既定と介入が同一なら、実測前にrc=2で停止する。介入差分はバイト数と
全offset（出力では連続範囲へ圧縮）を記録する。

前段関門の故障注入は、既定ROMの途中に3バイトを挟み末尾を切った
「既定膨張」と、介入ROMとして既定ROM自身を渡す「フラグ無効」の2種を合成し、
どちらも`SearchError`になることを公式環境なしで検査する。

## 行き止まりと手順上の反省

旧フラグの実走は、未実行のCALL先を変えただけの行き止まりである。ROM側フラグなのに
事前の最終ROM比較を手順に入れず、長い実測の後で初めて介入不成立を扱ったのは手順上の失敗である。
バイト同一のフラグであれば、ROMバイト列の比較を先に通すことで実測前に分かるため、
今後は同一のまま実測へ入れない。

ただし、この特定の旧ROMは実際に`0x0764` 1バイトが既定と異なっていた。
従って「今回もROM比較だけで実測前に誤定位を検出できた」とは記録しない。
今回の誤定位を止めるには、ROM差分関門に加え、静的経路検査で軸の
0x06 tracked経路が短縮入口へ届くことを検査する必要があった。両方をselftestへ入れた。
