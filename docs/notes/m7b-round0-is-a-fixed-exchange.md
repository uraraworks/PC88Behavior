# m7b: ラウンド#0は固定的なやりとりである

測定日: 2026-08-13

## 1. 目的と情報境界

ラウンド#0でmainが最初に受け取る1バイトについて、値そのものを知る・
記録することなく、(1) 一致する自作側定数が存在するか、(2) subが直接
読めるハードウェア状態から生成できるか、(3) 起動条件をまたいで固定か、
を切り分けた。

`private/`配下は開かず、測定ツールへ環境変数として渡しただけである。
公式側の値、自作側で一致した値、生ログの値列は標準出力・会話・本稿の
いずれにも残していない。判定に使ったのは一致長、構造一致件数、条件間の
同値グループ数だけである。実装コードは変更していない。

## 2. 測定の高速化と指標の変更

従来の診断は1800フレームを実行し、1回約9秒を要した。ラウンド#0の
最初の`$FC IN`を判定できる最小条件を探索した結果、**21フレーム**で十分と
分かり、1回約**0.02秒**まで短縮できた。現行ST3実発行の対照では、21フレーム
で値一致プレフィックス長0を再現し、分岐点まで届く35フレームの独立対照で
構造的一致プレフィックス258件も再現した。

探索の指標は「構造的一致プレフィックス」から、`tools/cmp_io.py`の
区間限定・位置のみモードが出す**main `$FC IN`の値一致プレフィックス長**へ
変更した。これにより、分岐点259より前の3応答を0→1→2→3件とラウンド単位で
評価できる。値は比較器内部でだけ扱い、出力しない。

## 3. ラウンド#0に一致する単一定数は存在する

FDCへのSENSE DRIVE STATUS実発行を残し、mainへ送る1バイトだけを自作側の
全256定数へ差し替えた。試行順から一致値を逆算できないよう非表示の
ランダム順とし、最初の一致を検出した時点で停止した。

**値一致プレフィックス長を0から1へ伸ばす単一定数は存在した。** ただし
その条件でも構造的一致プレフィックスは258件のままで、259件目は突破
しなかった。したがってラウンド#0を一致させるだけでは足りず、後続2件は
ラウンド#0とは別の値を要求している。3件を単一の定数で一括解決することは
できない。

一致した定数そのものは、公式ROMの内部値を言い当てた結果になり得るため、
会話・ログ・コメント・文書のいずれにも残していない。

## 4. 直接取得できるハードウェア状態の総当たり

値を焼き込まず、ハードウェアから取得して正当に生成できる可能性を調べた。
次の11取得源について、それぞれ生値、ビット反転、上下ニブル交換、上下
ニブルマスク、各ビット保持、各ビット除外の21加工、合計231条件を測定した。

- ST3
- SENSE INTERRUPT STATUS由来ST0（SIS-ST0）
- PCN
- READ ID結果のST0 / ST1 / ST2（RID-ST0 / RID-ST1 / RID-ST2）
- MSR（`$FA`直接読み）
- `$F8 IN`
- PIO-A（`$FC IN`）
- PIO-C（`$FE IN`）
- 無効命令の結果ST0

`$F7`は1.4節でsubのIN経路が確認されておらず、実装上も読み取り源にできない
ためスキップした。`$FB`単独読みはFDCの結果フェーズを構成せず、意味のある
1バイト取得にならないためスキップした。

**231条件すべてで値一致プレフィックス長は0であり、1以上になる取得源・
加工はゼロだった。** 3件すべてを説明できる源も無い。subが直接読める
ハードウェア状態からはラウンド#0応答を導けないことが、推測ではなく介入
測定で裏付けられた。これはm6xが予見した「公式subは内部ワークエリアから
組み立てていると考えられ、測定では届かない」という見立てを支持する。

## 5. ラウンド#0は4条件で固定的なやりとり

伏せ字済み既存ログは値比較に使えないため、既存4条件の起動時設定を
35フレームへ短縮して再測定した。比較器は値を内部でのみ扱い、同値グループ数
と位置ごとの同一/相違だけを出力した。既知の同一入力と意図的な差を使う
検出力selftestを先に通した。

対象はd0-boot、d1-files、d2-save、d5-seqfileの4条件である。d5は既存条件
どおり使い捨てディスク複製をwritableにした。

- ラウンド#0の公式応答1バイトは、**4条件すべて同一の1グループ**だった。
- ラウンド#0の要求は4条件とも2バイトで、**位置1・位置2の両方が条件間で
  同一**だった。
- `$FF`フェーズ列と`$FE`待ち・遷移も4条件で一致した。
- 参考として、ラウンド#2の5バイト要求も5位置すべて条件間で同一だった。

この結果は、ラウンド#0がディスク操作ごとの可変データではなく、機種識別、
ROMバージョン、初期化ステータス通知などの**「ハードウェア構成の事実」(a)**
を返す固定交換である可能性と整合する。その意味がハードウェア資料や
N88-BASICマニュアルの散文説明に記載されていれば、内部値を複製せず、公開
された意味論から正当に生成できる道がある。

ただし4条件はいずれも同一ディスク系の起動条件である。今回確定したのは
「この4条件では固定」の範囲までであり、ディスク内容から独立した普遍的な
固定値であることの確定には、別ディスク・ディスク無し、または資料上の
意味説明という追加根拠が要る。

## 6. ラウンド番号に関する訂正

今回の調査依頼は「ラウンド#0の5バイト要求」として開始したが、記録を
再確認すると要求長はラウンド#0〜#2の順に`2,1,5`であり、**ラウンド#0は
2バイト、5バイト要求はラウンド#2**である。

ここは隠さず訂正する。同時に、現行の`docs/notes/m6w-main-divergence-259.md`
と仕様書1.18節は既にこの対応を正しく記録していたため、「m6w/1.18自体が
ラウンド#0を5バイトと誤記した」という帰属も正しくない。誤りは今回の
調査開始時に既存記録を読み違えたことにある。

ラウンド#0は、1.11節の固定8バイト読み出し要求より短く、2バイトとも
「継続」サイトで、終端サイトを伴わない独立形式である。単発1バイト応答を
返す他の場面は要求長が1・5・6・8バイトなど複数あり、ラウンド#0と同じ
要求構造に統一されてはいない。

## 7. 採用方針と次の一手

全256定数の総当たりで得た一致値を実装へ焼き込む方針は採らない。値の
**意味**を特定し、規律「データテーブルはルールから生成する」に従って、
ハードウェア構成の事実や公開仕様のルールから生成できる形を目指す。

次は固定2バイト要求／固定1バイト応答が何を意味するかを資料から引く。
資料を読む可否はカバー・まえがきで先に判定し、Web資料は使い捨ての判定係に
先に見せる。読んだ資料とページ番号は`docs/notes/`に記録し、公式ROMの
解析記事・逆アセンブルリストは引き続き扱わない。

## 8. ツール状態

本測定で永続的に追加・変更したツールは無い。値比較には既存の
`tools/cmp_io.py`の区間限定・位置のみモードを使い、そのselftestは
`tools/cmp_io_selftest.sh`として既に`tools/run_all_selftests.sh`の対象に
含まれる。条件間比較には値を出さない一時比較器と内蔵selftestを使ったが、
測定後に削除しており、リポジトリへ残していない。
