# m7ig: 要求の位置を1ビットずつ反転して、位置4の特異性を探す — 結果

実施日: 2026-09-07

## 位置づけ

[m7if](m7if-request-bit-flip-preregistration.md)が事前登録した測定の結果で
ある。事前登録は測定開始前に単独コミット（`67504ca`）してあり、本稿では水準・
分類の閾値・判定規則を後から動かしていない。`src/`・`tools/`は本稿では変更して
いない。

**結論を先に書く: 主判定はM2（特異性なし）である。** 位置4だけが非保持となる
ビットは1つも無かった——位置0と位置2が**8ビットすべてで**構造を壊すためである。

**しかし摂動を弱めたことで、`m7ie`では見えなかった構造が出た。**
**位置ごとに「効くビットの集合」がはっきり分かれ、しかも入れ子になっている。**

## 判定

- **M1（位置4に特異性あり）**: あるビットで位置4が非保持かつ位置0〜3すべてが
  保持 → **不成立**（位置0・位置2が全ビットで非保持のため、どのビットでも
  成立しない）。
- **M2（特異性なし）**: → **成立。主判定はM2である。**
- M3（位置4が全ビットで保持）は不成立（位置4は上位4ビットで壊れる）。

**事前登録どおり、どの位置が効いているかを本稿では決めない。**

## 記述（判定ではない）: 効くビットの集合が入れ子になっている

M2で畳むと「どこも同じ」に読めてしまうので中身を書く（`m7hm`・`m7hw`・`m7ie`と
同じ手当て）。事前登録が「併せて記述すること」として求めた項目でもある。

| 位置 | 非保持になったビットの集合 |
|---|---|
| 位置0 | `{01,02,04,08,10,20,40,80}`（**全部**） |
| 位置1 | `{}`（**空。8ビットすべてで保持**） |
| 位置2 | `{01,02,04,08,10,20,40,80}`（全部。うち`02`のみ暴走） |
| 位置3 | `{40,80}` |
| 位置4 | `{10,20,40,80}` |

**包含関係が成立している:**

```
位置1 {} ⊂ 位置3 {40,80} ⊂ 位置4 {10,20,40,80} ⊂ 位置0 = 位置2 {全部}
```

**言えること:**

- **位置1は8ビットすべてで構造に影響しない。** 全armで`changed>=1`なので、
  これは介入の空振りではなく、**値が変わっても構造が変わらない**という意味で
  ある。
- **位置3と位置4は、上位ビットにだけ感度がある。** 位置3は上位2ビット、
  位置4は上位4ビットで壊れ、それより下のビットでは保持する。
- **位置0と位置2は、どのビットを反転しても壊れる。** この2つは`m7ie`の
  `XOR 0xFF`でも壊れており、1ビットに弱めても区別が付かなかった。
- `m7ie`が「位置0・3・4は同型の効き方」と記述したが、**1ビットに分解すると
  同型ではなかった**——効くビットの集合が違う（全部／`{40,80}`／
  `{10,20,40,80}`）。**摂動を弱めたことで、`m7ie`の「同型」という見立ては
  否定された。**

**言えないこと:**

- **感度の集合から、その位置の値を推し量っていない。** 「どのビットが効くか」は
  受け手がそのビットを使っているかを示すだけで、**元の値が何かは示さない。**
  本稿は値を復元しない（禁止事項5）。
- **包含関係が何を意味するかは分からない。** 位置ごとに感度の幅が違うという
  事実だけで、機序は測っていない。
- **M2である以上、`m7hs`以来の1バイト差が連続READの決定に効いているかは
  未確定のままである。**
- 「暴走」に分類した1arm（位置2・`0x02`）は、構造の話ではなく要求が不正になって
  別経路へ落ちた可能性が高い。本稿の判定はこのarm1件に依存していない
  （位置2は他の7ビットでも非保持のため）。
- 条件O・`disk#10`という1本のディスク・1条件である。一般性は主張しない。

## 次に何を測れば絞れるか

**「位置4だけ」という形の特異性は、この経路では出ない見込みが強い。**
位置0・位置2が全ビットで壊れる以上、M1の形の証拠は原理的に取りにくい。
**問いの立て方を変えるほうが筋が良い。**

1. **特異性の探し方を「位置4だけが壊れる」から「位置4と位置3の感度差」へ移す。**
   位置3は`{40,80}`、位置4は`{10,20,40,80}`で、**差は`{10,20}`である。**
   この2ビットが位置4に固有の感度であり、位置3には無い。**この差が連続READの
   まとまりと関係するかを、`{10,20}`だけを狙って測る**のが次の一手になる。
2. **壊れ方の中身を見る。** 本稿は「run長9が12本か否か」でしか分類していない。
   非保持armについて**run長の並びがどう変わったか**（12本→11本なのか、
   もっと崩れるのか）を記述すれば、位置ごと・ビットごとの効き方の違いが
   さらに分かれる可能性がある。`m7ie`では位置0・3・4がそろって11本だったが、
   1ビットごとに見れば違うかもしれない。
3. **位置0・位置2が全ビットで壊れる理由を、連続READとは別件として切り出す。**
   この2位置は「要求の骨格」に当たる可能性があり、連続READの規則を探る文脈とは
   分けたほうがよい（`m7ie`が位置2の暴走について書いたのと同じ扱い）。

## 開示

- 決定論性の確認で、**シェルのループが1回しか回らない誤りが1件あった。**
  zshでは引用符なしの変数展開が語分割されないため、arm一覧を1つの文字列に
  組み立てて`for A in $ARMS`と書いたところ、1armしか処理されなかった。
  「25arm確認」と報告する直前に件数（N=1）を見て気づき、二重ループに書き直して
  25armすべてを確認し直した。**誤った件数のまま報告していない。**
- 事前登録の取り決めどおり、暴走arm（位置2・`0x02`）の生ログは構造指標を
  取った後にscratchpad内で削除した。**削除したのはリポジトリ外の一時ファイル
  のみ**である。そのためこのarmは決定論性の再測定対象から外れており、
  **25arm中に含まれていない**ことをここに明記する。
- 本稿は委譲を行っていない。測定・解釈・判定はすべて親セッションで行った。
- 上記以外の手順逸脱・事故は無い。無言でSKIPした分岐は無い。測定はすべて
  フォアグラウンドで実行し、測定中に`git stash`・ブランチ切替・`src/`の編集は
  行っていない。
