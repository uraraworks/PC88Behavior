# M6x — 2026-08-12 セッションの到達点と次の一手

記録のみ。追加測定は行っていない。本ノートは次セッションの起点である。

## 到達点

| | セッション開始時 | 終了時 |
|---|---|---|
| sub 側 構造的一致プレフィックス | 27 件 | **102 件** |
| main 側 構造的一致プレフィックス | 258 件 | 258 件（据え置き） |

sub 側は起動時 FDC 初期化区間（1.22節 batch1〜7、event index [15,112)）を

## この日に確定させたこと

1. **run 境界駆動の受信状態機械**（第13版）。「通算8バイトで打ち切る」構造を廃し、
   main が送り手から受け手へ切り替わる境界（bit1 観測）で run を終える構造にした。
   これにより起動時のデッドロック（百万回スピン）が解消し、1800フレームを完走
   するようになった。
2. **`$F8`（TC）の方向と位置**（第15版・第19版）。方向は OUT が主で、
   `IN $F8` は三つ組み末尾の単発確認読みのみ。位置は結果フェーズを読み終えた
   後（旧実装はデータフェーズ直後・結果フェーズ前に読んでいた）。
3. **起動時 FDC 初期化シーケンス**（第16〜18版）。7 バッチ構成であり、
   batch1/2/3=ドライブ0、batch4/5/6=ドライブ1、batch7=ドライブ2 の
   3 ドライブ分の初期化列。batch2・5 は MSR（`$FA`）の Seek Busy ビットにより
   SPECIFY ではなく **SEEK** と確定（`m6r`）。
4. **単発1バイト応答では sub が FDC を叩かない**（第20版、`m6t`・`m6v`）。
   4条件合計 99.6%（32,626/32,752件）で応答直前ウィンドウの FDC イベントが 0 件。

## この日に訂正した誤り（隠さず残す）

- **`m6q` の TC 位置の誤り**（`m6s` で訂正）。`analyze_boot_fdc_sequence.py` の
  `find_tc_triads` は完全な三つ組みしか検出せず、起動区間の単発 TC を
  **1件も拾えていなかった**（保存済み出力に「三つ組み検出数: 0」と残っていた）。
  にもかかわらず別経路で拾った `OUT $F8` の「区間内2番目」を「2番目の batch の
  直後」と取り違えた。正しくは batch1 直後（seq35）と batch4 直後（seq74）。
  **実走が測定の結論を反証した。**
  - 教訓: 解析器を書いたら、検出できるはずのものを食わせて 0 件でないことを
    確かめてから結論に使う。`tools/verify_l3.sh` には break フラグでこの作法が
    あるのに、解析器側には無かった。
- **`MAIN_LOOP` 冒頭の重複 RECALIBRATE**。`BOOT_HANDSHAKE` に起動時 FDC 初期化が
  無かった頃の名残で、batch1〜7 を実装した際に消し忘れていた。
- **単発1バイト応答の値**（第20〜23版の往復）。「構造さえ合えば値は未確定でも
  先へ進める」という想定で ST3 を暫定値 `0x00` に置き換えたところ、main 側が
  258件 → 102件 へ後退した。ST3 実発行に戻して 258件へ復帰。
  **この往復自体が「その1バイトは値が効く」という測定結果である。**

## 次の一手 — 値の壁の設計判断（未着手のまま記録する）

sub 側・main 側の両方が、同じ壁に到達した。

- **sub 側**: 単発1バイト応答。公式 sub は FDC を叩かずに返すが（構造は確定）、
  その値は ST3 相当でなければ main が先へ進まない。公式 sub は自分の内部
  ワークエリアから組み立てていると考えられ、**ワークエリアの構造は規律上
  読めない領域**（CLAUDE.md 資料の使い方 (b)）。測定では届かない。
  - 現行実装は「FDC に SENSE DRIVE STATUS を実発行して ST3 を送る」。
    測定で確定した「叩かない」構造とは食い違うが、**適合条件（5.1節）は
    main が受け取るデータ列であり sub の I/O 列ではない**ため、main 側を
    優先して採用した（第23版）。
- **main 側**: 分岐点259（`m6w`）。直前ラウンドは公式・自作とも
  「5バイト要求→1バイト応答」で**構造が一致している**。main が分岐を変える
  原因は応答1バイトの**値**に絞られる。値は `$FD`/`$FC` の伏せ字対象。

**したがって次に必要なのは、測定手法そのものの設計判断である。**
分岐点を1つずつ潰す作業は、構造の層では有効だったが値の層では機能しない。
選択肢（いずれも未検討。実装ではなく方針の決定が要る）:

1. 伏せ字の運用を変える。どのポートのどの値までなら扱えるかを、
   `docs/notes/disclosure-2026-08-10.md` の整理に立ち返って引き直す
   （`feedback` として既に「ログという容れ物と、運ばれた中身」の分類がある）。
2. 値に依存しない適合条件を立て直す。5.1節の適合条件そのものを、
   値の一致ではなく観測可能な振る舞い（画面出力、ディスクアクセス列など）で
   定義し直せないか検討する。
3. 値を「知らないまま正しく作る」経路を増やす。`5adf82e`（ST3 実発行）が
   その成功例。ハードウェアから取れる値はハードウェアから取る、という方針を
   他の未確定値にも適用できないか洗う。

**この判断は人間が下すべきものであり、エージェントが推測で決めてはならない。**
