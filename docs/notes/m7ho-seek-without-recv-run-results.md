# m7ho: 受信runが先行しないSEEK段は何に駆動されているか — 結果

実施日: 2026-09-07

## 位置づけ

[m7hn](m7hn-seek-without-recv-run-preregistration.md)が事前登録した解析の
結果である。事前登録は解析開始前に単独コミット（`190688c`）してあり、
本稿では群の定義・記述項目・判定規則を後から動かしていない。`src/`・
`tools/`は本稿では変更していない（新規ツールは作らずに済んだ）。

**結論を先に書く:**

- **G1（エラー回復仮説）は反証された。** 候補0件の4段すべてで、直前
  コマンドの結果相にエラーは立っていない（`is_error_status`が全4段で偽）。
  しかも対照群（候補1件以上の19段）では19段中12段で直前がエラーであり、
  **エラーはむしろ「受信runが先行する段」の側に多い**——G1の予測と逆向き
  である。
- **G2（RECALIBRATE随伴仮説）は群Aで反証、群Bで支持された。** 群Aの3段は
  直近`RECALIBRATE`からコマンド列上22・26・30件離れている。群Bの1段は
  差2件であり、かつ**その段自体が`RECALIBRATE`を2件含む**。
- **G3（場面仮説）は支持された。** 候補0件の4段のframeは20・40・41・42で、
  すべて打鍵frame（700）より前＝起動段階にある。**`FILES 2`入口場面
  （frame≥700）の12段には、候補0件の段が1つも無い。**

**したがって、「受信runが先行しないSEEK」は起動段階に固有の現象であり、
1.57節が追う「入口場面での連続READ移行」とは切り離してよい。** これは
`m7hn`が事前に「G3が真ならこう結論してよい」と書いておいた使い道どおり
である。

**真と偽の両方が実際に出ている。** 「常に真を返す実装でも通ってしまう」
という抜けは塞がった。片方向だけの確認では、この判定器が何も判定して
いなくても合格してしまう。

## 群A: 単発の段で受信runが先行しない3段

| 段 | frame | 直前コマンド種別 | 直前エラー | 直近RECALIBRATEとのindex差 | 段内のコマンド種別の並び |
|---:|---:|---|---|---:|---|
| 7 | 40 | READ DATA | 偽（`IC=正常終了/A/head0`） | 22 | SEEK, SENSE INTERRUPT STATUS, SENSE DRIVE STATUS, READ DATA |
| 8 | 41 | READ DATA | 偽（`IC=正常終了/A/head1`） | 26 | 同上 |
| 9 | 42 | READ DATA | 偽（`IC=正常終了/A/head0`） | 30 | 同上 |

3段とも**同一の構造**であり、いずれも正常終了したREAD DATAの直後に来る。

**注目すべき観察（決めつけずに書く）:** 群Aの段内の並び
「SEEK → SENSE INTERRUPT STATUS → SENSE DRIVE STATUS → READ DATA」は、
1.57節が**自作`general_read_request`の振る舞い**として記述した4コマンド
単位そのものである。つまり**公式ROMも、起動段階のA:ドライブ読み出しでは
レコードごとにSEEKし直している。** 1.57節が「公式は連続READへ移行し、
自作はレコードごとに再SEEKする」と書いた対比は、**場面を固定した上での
対比**であって、公式が常に連続READを使うという意味ではない。

ただしこれを「同じ経路が場面で切り替わっている」と読むことはできない。
群Aの段には受信runが1本も先行しておらず、**main→subの要求に駆動されて
いない**（候補0件はそのことを意味する）。入口場面の連続READとは、
そもそも駆動のされ方が違う可能性がある。本稿はどちらとも決めない。

| 1 | 20 | SENSE INTERRUPT STATUS | 偽（`IC=正常終了/SEEK END/B/head0`） | 2 | SEEK, SENSE INTERRUPT STATUS, RECALIBRATE, SENSE INTERRUPT STATUS, RECALIBRATE, SENSE INTERRUPT STATUS |

## 追加で記述したこと: `read_count == 0`の段の構造（新規）

`m7hm`が見落としていた構造である。該当は2段で、**どちらもframe 20**、
**コマンド種別の並びは完全に同一**だった。

| 段 | 候補数 | frame | 段内のコマンド種別の並び |
|---:|---:|---:|---|
| 0 | 1 | 20 | SEEK, SENSE INTERRUPT STATUS, RECALIBRATE, SENSE INTERRUPT STATUS, RECALIBRATE, SENSE INTERRUPT STATUS |
| 1 | 0 | 20 | 同上 |

**何であるかは決めつけない。** 観測された事実は、(1)起動のごく初期
（frame 20）に、(2)READ DATAを1件も伴わないSEEK段が2つ連続して現れ、
(3)いずれも`RECALIBRATE`を2件ずつ含み、(4)種別の並びが互いに完全一致
する、ということだけである。2段のうち一方には受信runが1本先行し、
他方には先行しない。

## G1〜G4の判定

| 候補 | 判定 | 根拠 |
|---|---|---|
| G1 エラー回復 | **反証** | 候補0件の4段すべてで直前エラーが偽。対照群は19段中12段が真で、向きが逆 |
| G2 RECALIBRATE随伴 | **群Aで反証・群Bで支持** | 群Aのindex差は22/26/30、群Bは2で段自体がRECALIBRATEを含む |
| G3 場面（起動段階固有） | **支持** | 候補0件の段のframeは20・40・41・42。frame≥700の12段には候補0件が皆無 |
| G4 いずれでもない | 不成立 | G3が成立したため |

事前登録どおり、群Aと群Bで結論が割れることを許した（G2がまさにそうなった）。

## 言えること・言えないこと

**言えること:**

- 受信runが先行しないSEEKは、**起動段階にのみ現れる**。`FILES 2`入口
  場面（frame≥700）の12段はすべて受信runが先行している。
- **したがってこの現象を、1.57節が追う連続READ移行の規則から切り離して
  よい。** `m7hb`が「数千〜2万クロックの開き」として記録した対応づけの
  破綻のうち、少なくとも候補0件の分は起動段階の話である。
- エラー回復は説明にならない。むしろ直前エラーは、受信runが先行する段の
  側に多い（19段中12段）。
- 公式ROMも起動段階のA:読み出しでは、1.57節が自作の振る舞いとして記述した
  4コマンド単位（SEEK→SIS→SENSE DRIVE STATUS→READ）を使っている。
- `read_count == 0`のSEEK段が2つ、起動のごく初期に同一構造で存在する。

**言えないこと:**

- **本稿は因果を言っていない。** 直前がエラーでないことは「エラーが引き金
  ではない」の証拠になるが、では何が引き金かは本稿では特定していない。
  特定には介入が要る。
- 群Aの4コマンド単位が、入口場面の`general_read_request`と**同じ経路**か
  どうかは分からない。受信runに駆動されていない点で条件が違う。
- 群Bの1段と、もう1つの`read_count == 0`の段（候補1件）の違いが何に由来
  するかは扱っていない。
- 条件O・`disk#10`という1本のディスク・1条件の再解析であり、一般性は
  主張しない。

## 次に何を測れば絞れるか

**本稿の結果により、当初の順序どおり「場面を揃えた比較」へ進んでよい。**
候補0件のSEEKが起動段階に閉じていることが分かったため、入口場面
（frame≥700）だけを見れば、対応づけは12段すべてで受信runが先行する
状態で議論できる。残る障害は「候補が2本ある」という同点解消の問題だけに
なった（`m7hm`）。

次稿では、`m7hm`の「次に何を測れば絞れるか」1項・2項を合わせて事前登録
する。すなわち、(a)群Sを起動段階から取るのをやめ、同じ入口場面で公式と
混成を比較する、(b)候補2本の同点解消規則を、**それが偽陽性を作らないこと
を示す反証条件と併せて**事前に固定する。
