# m7lc: 生成器の窓の関門を直した——末尾だけ窓の外へ伸びた区間も止める

作成日: 2026-09-11

## これは自作生成器（`src/l3_service/make_subrom.py`）の修正である

**仕様（`docs/spec/`）の内容は変わらない。** [m7lb](m7lb-window-tail-confirm-results.md)で
確定した欠陥を、m7lbの事前登録が先に決めた手順（陰性対照を示してから直す）で直した。

## 何を直したか

`find_out_of_window_blocks()`は、ラベル区間の**開始位置**が窓（`0x0800`）以上の
ものしか列挙していなかった。**開始は内側で末尾だけ窓の外へ伸びる区間を
見逃していた。** 周辺のm7apのコメントは「到達可能な命令はすべて境界未満」を
不変条件として掲げており、**実装がその意図に届いていなかった。**

**終了位置が窓を越える区間も列挙するようにした。** 報告するサイズは
**窓の外にあるバイト数**である。

## 既存の陽性対照が穴を見逃した理由

陽性対照4は、命令の跨ぎを避けるために**境界をラベルの位置（区間の開始）に
置いていた。** そのため作れるのは「区間が丸ごと窓の外」という形だけで、
**関門が見逃していた形は1度も作られていなかった。**
**関門が捕まえられる形でしか陽性対照を組んでいなかった。**

陽性対照5は、境界を**最後の区間の内側で本当の命令の先頭**に置く。
開始が外の区間は0、跨ぎも0のまま、末尾の命令だけが外に出る。

## 途中で見つけた2つ目の穴（直していない。記録する）

陽性対照5を最初に組んだとき、境界が「最後の区間の開始+1バイト」に置かれた。
**そこは`call`のオペコードとオペランドの間だった。**

アセンブラは`call`/`jp`を**オペコード（1バイト）とオペランド（2バイト）の
別々の`instr_spans`**として記録する。**境界がちょうどその間に来ると、
`find_fetch_window_straddles()`は跨ぎ0と判定する**（オペコード区間は境界で
終わり、オペランド区間は境界から始まるため）。**整列パディングはこの形を
直さない。**

**今回の修正で、この形も「区間の末尾が窓の外」として`build()`の関門で止まる**
（陽性対照6で固定した）。**ただしパディングで直るのではなく、ビルドが失敗する
側に倒れる。** 安全側ではあるので、**跨ぎ検査そのものは今回変えていない。**
**次にこの形でビルドが止まったときは、跨ぎ検査がオペコードとオペランドを
1つの命令として扱うよう直すこと。**

## これで何ができるようになったか

**既定ビルドの余白9バイトが、実装を足せる上限としてビルド時に見える
ようになった。** **10バイト目から窓の外へ押し出される実装は、黙って通らず、
関門で止まる。** `m7ks`の2版（+11バイト）も、今の生成器ならビルドの時点で
止まる。

**次は、余白の作り方を決めて、`m7kr`の合格条件3を再挑戦する。**

## 情報境界

公式ROM・公式ディスク・`private/`の内容には触れていない。扱ったのは
**自作コードのラベル番地・区間サイズ・全長・窓越えの量・既定ROMのハッシュの
一致**だけである。
