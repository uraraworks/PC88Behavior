# M2 トラップROM足場

作業日: 2026-08-07
対象: PC88Behavior 計測ハーネス（QUASI88-libretro 上に構築）
完了条件（docs/PLAN.md 第8節）: 「全域トラップ ROM で起動し、何番地が要求されたかが一覧で出る」

---

## 何を作ったか

`q88h_trace.c/h` は「触れたアドレスの集合」を取るだけで、ROM が無い番地に
実行が飛べばそこで素直にクラッシュする（未実装の番地は不定バイトを返すため）。
それでは「次にどこを実装すべきか」を安全に洗い出せない。

そこで、任意の番地への**実行アクセス**（fetch）と**データアクセス**（mem_read）を
個別に捕まえ、実行アクセスの場合は

- **RET モード**: その場で `0xC9`（RET）を返し、呼び元へ即座に戻す。
  スタブが「何もせず即リターンする関数」として振る舞うので、CALL の連鎖を
  破壊せずに先へ進める。
- **STOP モード**: `0x76`（HALT）を返し、その場で停止フラグを立てる。
  「最初にどこで需要が発生したか」だけを見たいときに使う。

のどちらかを選べるようにした。RET/HALT は Z80 の公開された命令コードであって、
ROM の内容とは無関係（docs/PLAN.md「やってよいこと」の範囲内）。

構成:

- `tools/harness/core/q88h_trap.h` / `.c` — トラップ状態（メイン/サブ CPU 別）と
  イベント記録（`q88h_trap_record`）。`q88h_trace.c` と同じ遅延初期化パターン。
- `tools/patches/0004-trap-rom.patch` — `src/pc88main.c` の `q88h_fetch` /
  `q88h_mem_read`、`src/pc88sub.c` の同等品にトラップ判定を追加。
  `Makefile.common` に `q88h_trap.c` をソースへ追加する行も含む。
  0002/0003 パッチ適用後の状態に対する差分。
- `tools/harness/make_trap_rom.py` — 全域トラップ ROM（既定）と、
  自己検証用のブートストラップ入り ROM（`--selftest`）、および
  トラップ対象範囲を書いた `trap.map` を生成する。生成物は全部自作のバイト列。
- `tools/harness/frontend/main.c` の拡張 — `--trap-map` / `--trap-mode` /
  `--trap-stop-after` / `--expect-trap-exec` / `--expect-trap-data`。
  コアにトラップ機能が無ければ dlsym が失敗し、警告を出して機能を丸ごと
  無効化する（既存の測定は壊さない）。
- `tools/harness/trap_selftest.sh` — 自己検証。`tools/setup_harness.sh` の
  末尾に組み込んだ。
- `tools/trap_run.sh` — 全域トラップ ROM を stop/ret 両モードで実走し、
  `measurements/t0-trap-all-{stop,ret}.txt` に出す薄いラッパ。公式 ROM 不要。

## どう検証したか

`make_trap_rom.py --selftest` が仕込む既知のブートストラップ（自作コード、
0x0000-0x00FF に配置しトラップ対象から除外）:

```
LD SP,0xF380
CALL 0x1000            ; 1回目
LD BC,0x1234 / DE,0x5678 / HL,0x9ABC
CALL 0x2000
CALL 0x1000             ; 2回目
LD A,(0x3000)
JR $
```

これを ret モードで走らせ、`trap_selftest.sh` が以下を実測して確認した:

- 0x1000 / 0x2000（実行）、0x3000（データ）にトラップが発火する
  （`--expect-trap-exec` / `--expect-trap-data` が通る）
- 0x1000 の実行回数が **2**（同じ番地への複数回の要求を取りこぼさず数えられる）
- 0x2000 の入口イベントで **BC=1234 DE=5678 HL=9ABC** が観測される
  （引数の観測 = レジスタ経由の入力がイベントに正しく載る）

いずれも `tools/harness/frontend/q88measure` の標準出力（`[トラップ ...]` セクション）
から `grep` で機械的に検査しており、目視確認に頼っていない。

## 実走で何が出たか

全域トラップ ROM（`--selftest` 無し、N88.ROM 全体を 0x00 埋め、trap.map で
main 0000-7FFF / sub 0000-07FF 全域を対象）を `tools/trap_run.sh` で実走した。

**stop モード** (`measurements/t0-trap-all-stop.txt`):
リセット直後、最初に要求されたのは **メインCPU 0x0000**（リセットベクタそのもの）。
1 フレーム内で 1923 回同じ番地への fetch が記録され、`停止: した (番地=0000)` で終わった。
サブCPUはこの60フレーム内で一度も実行されなかった（`exec=0`）。

**ret モード** (`measurements/t0-trap-all-ret.txt`):
0x0000 が ROM 全域 0x00 埋めなので、実行は常に「番地 0」に居続ける
（0x00 = 制御構造上フェッチ即トラップ→RET を繰り返す）。RET は毎回
スタックポインタから戻り番地を読むが、SP はリセット直後の既定値
（0xFFFF）から始まり、RET のたびに +2 されながら 0x0000, 0x0001, 0x0002, …
と読み進む。読んだ内容も全部 0x00 なので「戻り先」は常に 0x0000 に
評価され、結果としてスタックポインタだけがひたすら伸びていく暴走に
なった。60フレームで SP は 0x0602 相当まで進み、イベント総数は 2309件
（うち取りこぼし 0件）。**これは「SP 未初期化のまま RET すると暴走する」
という、当初から想定していたとおりの結果であり、隠さずそのまま記録した。**

## 踏んだ失敗

- サブCPU側の caller 計算コードを書いた際、`word caller = sub_mem_read(addr)`
  という不要な仮の代入を残したまま次の行で上書きする書き方をしてしまい、
  意味の無い呼び出しが1回余計に発生する状態でパッチ案を書きかけた。
  ビルド前にコードレビューで気づいて削除した（コミットには残していない、
  というよりコミット前の推敲段階の話）。
- `retro_q88h_trap_reset()` を trace と同じ「全消去」にすると、フロントエンドが
  `--trap-map` で設定した map と mode まで消えてしまう。map の設定は
  ロード後・フレームループ前に一度だけ行う設計なので、reset のたびに
  空になると「2回目の測定区間からトラップが効かない」という無言の劣化に
  なる。reset は map/mode を退避してから全消去し、戻す実装にした。

## 限界（気づいた穴）

- **STOP モードの停止判定はフレーム境界でしか効かない。** `q88measure` は
  1 フレーム分丸ごと `retro_run()` した後にしか `stopped` を見ない。
  HALT 命令は割り込みが来るまで同じ PC を繰り返しフェッチし続ける Z80 の
  挙動があるため、1 フレーム内で同じ番地に何百〜何千回もトラップイベントが
  積み上がることがある（実測: 1923件、stop モードの実走結果を参照）。
  「本当に1回だけ捕まえたい」ならフレーム内でのフック側チェックが要るが、
  M2 の完了条件（何番地が要求されたかの一覧）には影響しないため見送った。
- **caller の算出は「SP の先頭2バイトが戻り番地」という前提でしかない。**
  CALL で来た場合は正しいが、割り込み（RST/INT）や PUSH 済みスタックの
  トップがたまたま何かの値だった場合は無意味な値を拾う。`pc_prev` を
  併記しているのはこの前提が外れたときの手掛かりのため。
- **多バイト命令の途中を対象にトラップを置くと、命令境界を無視して
  発火する。** trap.map はバイト単位の範囲指定であり、Z80 命令のオペランド
  部分（例えば `CALL nn` の nn の2バイト）を実行アクセスとして誤って
  トラップすることは無い（fetch はオペコードの先頭バイトでしか起きない）が、
  データアクセス側は「その番地を読んだ」という事実をそのまま記録するので、
  命令のオペランド自体をデータとして読む経路（例: 自己書き換えや
  テーブル参照）と、意味のある変数アクセスの区別は trap.map だけでは
  付かない。区別したければ発生順ログの `pc_prev`/`caller` を手掛かりに
  人間が判断する必要がある。
- ret モードでの「暴走」は今回の全域トラップ（0x00 埋め）に固有の条件
  （SP 未初期化 + メモリが全部 0）で起きたものであり、実際に L3/L4 の
  実装を段階的に埋めていく運用では SP は既に L1(IPL) の時点で初期化
  されているはずなので、この暴走パターンが再現するとは限らない。
  「トラップROM足場自体は正しく動いている」ことの証拠として記録するに留める。
