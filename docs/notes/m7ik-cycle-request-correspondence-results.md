# m7ik: 入口場面の要求と連続READ周期が1対1かを見る — 結果

実施日: 2026-09-07

## 位置づけ

[m7ij](m7ij-cycle-request-correspondence-preregistration.md)が事前登録した
測定の結果である。事前登録は測定開始前に単独コミット（`e5b89f9`）してあり、
本稿では候補規則・分類・判定規則を後から動かしていない。`src/`・`tools/`は
本稿では変更していない。

**結論を先に書く: 主判定はP1（1対1対応が成立）である。**

事前登録した規則で列挙した候補runは**ちょうど12本**（すべて`main→sub`・長さ6）
であり、**そのどれを壊しても、連続READのまとまりが12本から11本へちょうど1本
減った。** 12本すべてでFDC総数183・READ DATA総数108・run長多重集合
`{1:9本, 9:11本}`が**完全に一致**した。

**これで「12」の側は決まった。** 連続READの周期数は、**入口場面に流れる要求の
本数**に対応している。**一方「9」は本稿でも動かなかった**（C型は0本）。

## 判定

- **P1（1対1対応が成立）**: 候補runのすべてでB型かつrun長9の本数が11 →
  **成立。主判定はP1である。**
- P2・P3・P4はいずれも不成立。
- **C型は0本**（事前登録が「1本でもあれば必ず書く」と定めた項目。**無かった**）。

## 言えること・言えないこと

**言えること:**

- **入口場面の要求12本と、連続READの周期12本は対応している。** どの要求を
  壊しても、周期がちょうど1本減る。
- **どの要求を壊しても結果が完全に同じ**（FDC183・READ108・`{1:9, 9:11}`）。
  12本の要求は、この指標の上では**互いに区別できない**。
- **「12」の側は要求の本数で決まる。** `m7hb`が「9件×12周期」と記録した構造の
  うち、**周期数のほうは要求の数に対応する**ことが分かった。
- **「9」は本稿でも動かなかった。** `m7ii`（交換run36の5位置×8ビット＝40arm）と
  本稿（12run×位置0）を合わせて**52armで一度もC型が出ていない。**
- 全armで`changed=1`。介入は全部届いている。

**言えないこと:**

- **「各要求が1周期を駆動している」とは断定しない**（事前登録に書いたとおり）。
  言えるのは「どの要求を壊しても周期が1本減る」までである。例えば「壊れた
  要求が再送されずに1周期ぶんの読み出しが飛ぶ」以外の機序でも同じ観測に
  なりうる。
- **「9」の出所は依然として不明である。** `m7hb`が挙げたH2（`general_read_
  request`相当の内部固定カウンタ）とH1派生（1トラック分＝トラックあたり
  セクタ数）は、**本稿でも区別できていない。** ただし**「要求のバイト列で
  決まる」という可能性は、52armで一度も動かなかったことで弱まった。**
- **位置0を選んだのは`m7ii`の観測に基づく便宜**であり、他の位置なら「9」が
  動く可能性を排除していない。
- **12本の要求が互いに区別できなかったことは、「同じ内容である」ことを
  意味しない。** 本稿は値を見ておらず、壊した後の指標が同じだっただけである。
- run長や本数から元の値を逆算していない（禁止事項5）。
- 条件O・`disk#10`という1本のディスク・1条件である。一般性は主張しない。

## 次に何を測れば絞れるか

**「9」の出所を、要求の外で探す段階に来た。** 52armで動かなかった以上、
要求のバイト列を触る経路はこれ以上伸ばしにくい。

1. **ディスクの側を変える。** `m7hb`は「9」がトラックあたりセクタ数という
   物理的性質に由来する可能性を挙げていた。**セクタ数の違うディスクで
   同じ測定をすれば、run長が9以外になるかどうかで決着する。**
   これは(a)ハードウェアの事実の範囲であり、クリーンルーム規律上も安全である。
   `m7gg`が調べた候補ディスクの中に、フォーマットの違うものがあるかを先に
   確かめる（**値ではなくフォーマット属性**を見る）。
2. **1で「9」が変われば、H1派生（1トラック分）が支持される。** 変わらなければ
   H2（内部固定カウンタ）側に寄り、その場合は3節・第23版と同じく
   **ROM内部のワークエリアに当たるため測定では届かない**という結論へ進む
   根拠になる。
3. **12本の要求が本当に同一かどうかは、値を見ずには決められない。** 必要なら
   `compare_recv_run_fields`の型で**要求どうしを突き合わせる**（公式と混成の
   比較ではなく、公式内部の要求12本の相互比較）。これは値を出さずにできる。

## 開示

- 本稿は委譲を行っていない。測定・解釈・判定はすべて親セッションで行った。
- 各armの生ログは事前登録の取り決めどおり、指標を取り出した直後にscratchpad
  内で削除した。決定論性の確認対象（run36・run58）は**その場で2回走らせて
  比較**してから削除した。
- 実行したarm数（12）を出力に載せ、候補個数（12）と一致することを確認した
  （`m7ig`でzshの語分割によりループが1回しか回らなかったため、事前登録で
  取り決めた手順）。
- 事前登録は「C型が1本でもあれば必ず書く」と定めていた。**0本だったので
  「無かった」と書いた。**
- 上記以外の手順逸脱・事故は無い。無言でSKIPした分岐は無い。測定はすべて
  フォアグラウンドで実行し、測定中に`git stash`・ブランチ切替・`src/`の編集は
  行っていない。

公式ROM・公式ディスクのバイト列、公式ROMの逆アセンブル、`private/`の内容は
読んでいない・出力していない。記録したのは公開μPD765コマンド種別名、件数、

逆算してもいない。** 資料は参照していない。生ログ・ディスク複製・使い捨て
スクリプトはリポジトリ外（scratchpad配下）に置き、コミットしない。
