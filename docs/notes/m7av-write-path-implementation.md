# m7av: 書き込み経路（WRITE DATA）を実装。窓は検証できた／ディスク反映はハーネスで判定できない

作業日: 2026-08-18

## 情報境界

自作サブROMの実装と、自作の合成ディスク・自作mainドライバによる自己検証が
中心。公式ROM・公式ディスクは**実行のみ**（m7auで取った既存ログの再解析と、
本ノート4節の対照実験1回）。値は扱わず、件数・位置・バイト数だけを記録する。

## 1. 実装したもの（仕様書1.35節の測定にそのまま対応）

- **循環バッファ方式**: 受信バイトを常に `WRITE_BUF`（0x7500、**256バイト
  境界に整列**）へ格納する。添字 `WRITE_IDX` は1バイトなので256で自然に
  巻き戻り、runがどれだけ長くても「最後に受け取った256バイト」だけが
  残る。1.35節が確定した「データ部＝受信列の末尾ちょうど256バイト」を
  **runの長さを事前に知らずに**表せる。
- 追い出される直前の値を `WRITE_PREV` へ退避する。run終端では
  「データ部の直前の1バイト」になる——1.35節で **R（セクタ番号）が
  15/15でその位置に一致**した。
- **C は直前SEEKの目的シリンダ**（1.35節で15/15一致）。`FDC_SEEK` の入口で
  `WRITE_C` にラッチする。**`REQ_HDR+4` を見てはいけない**——書き込みrunの
  制御バイトが `REQ_HDR` を上書きするため。
- unit/head は `drive0 | (H<<2)`（1.35節で15/15一致。第42版が読み出し側で
  確定した規則と同じ）。N/EOT/GPL/DTL は読み出し側と同じ値。
- **トリガはrunの長さだけ**: `RUN_LEN` は0xFFで飽和するので、0xFF は
  「257バイト以上」を意味する。実測の書き込みrunは262/268バイトで、他の
  要求run（最長12）とは桁が違う。**制御バイトの値には一切触れていない**
  （内訳は未確定。推測で埋めない）。
- 結果フェーズ7バイトの後に `FDC_TC`（1.21節の三つ組み）を呼ぶ。読み出し側が
  1セクタ分のバッチ後に呼ぶのと同じ位置。公式側でもWRITE直後30000クロック
  以内に `OUT $F8` が現れる（15件すべて）。

コードは 1895 → 2027 バイト（LIMIT=4）。フェッチ窓 0x0800 の内側だが**残り
21バイト**しかない。次に何か足すなら削減が先。

## 2. 途中で踏んだ2つの間違い（どちらも検査が捕まえた）

- **フォールスルー経路にラベルを差し込んだ。** 新しい入口を
  `_recv_dispatch_hdr_done` の直前に置いたところ、run長8のときにそこへ
  「落ちてくる」既存経路を横取りし、自己検証層の5項目が一斉にNGになった。
  `FDC_WRITE_SECTOR` の `ret` の直後（フォールスルーが来ない位置）へ移動して解決。
  **アセンブリでラベルを足すときは、直上が `ret`/`jp` で終わっているかを見る。**
- **試験用mainが送り続けるとrunが終わらない。** 最初「データ256の直後に
  次の要求ヘッダを送る」形にしたら、subから見たrunが262ではなく270バイトに
  伸び、末尾256の窓がずれてRが別の値になった（実測で確認）。subのrun終端は
  「相手がSEND待ちに転じた」(bit1)で決まるため、mainは**送るのをやめて
  受信待ちに入る**必要がある。書き込みに対してsubが何か返すかは未測定なので、
  応答を期待する形にはしていない（推測でプロトコルを足さない）。

## 3. 検証できたこと

`tools/verify_l3.sh` に2項目を追加した（公式環境不要）:

- **窓の正しさ**: FDCへ流した256バイトが、subがそのrunで最後に受け取った
  256バイトと **256/256 位置一致**。
- **検出力の確認（陽性対照）**: `--break-write-data-window`（データ部の開始を
  1バイトずらす故障注入）版では **0/256** になり、正しく不一致として検出される。

判定は `tools/check_l3_write.py`（出力は件数のみ、値は出さない）。

## 4. 検証できないこと — ディスクへの反映（ハーネスの性質）

「書いたものを読み戻せるか」は**このハーネスでは判定できない**。対照実験で
確認した:

- m7auの公式実測（公式ROM一式・公式ディスクの複製・ライトプロテクト解除済み）
  では `WRITE DATA` が **15件**発行されている。
- にもかかわらず、その複製ファイルは原本と **1バイトしか違わない**——
  その1バイトは実験前にこちらが外したライトプロテクト（オフセット0x1A）で
  あり、**セクタデータは1バイトも変化していない**。

つまり「FDCへ書いてもイメージファイルへ落ちない」のはハーネス側の性質で
あって、自作サブROMの性質ではない。**公式ROMを走らせても同じ**である。
`verify_l3.sh` はここを黙って合格にせず、判定不能（`--`）として毎回表示する。

自己検証層で「別実行で読み戻して突き合わせる」2フェーズ方式を組んで実際に
走らせ、0/256（＝元のディスク内容のまま）であることも確認済み。
`tools/check_l3_write.py` は `--read-log` を渡せばその突き合わせもできる形に
してあるが、上の理由で既定の検査には入れていない。

- 書き込みに対してsubが応答を返すのかどうか（未測定）。

- コード残量21バイト。次に足す前に削る。
