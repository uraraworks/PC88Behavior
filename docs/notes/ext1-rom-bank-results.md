# ext1 — 拡張ROMバンク（4th ROM）読み分け・欠落・割り込み安全性・中継費用 — 結果

記録日: 2026-09-19
根拠: 事前登録
[ext1-rom-bank-preregistration](ext1-rom-bank-preregistration.md)
（改訂1`bd15c51`＋追補1`06b91ee`）。器具は`c672f25`
（`tools/harness/make_ext_rom_test.py`・`tools/harness/ext1_selftest.sh`）と、
本走用ランナー`tools/harness/ext1_run.py`（本コミット）。

**使ったROMは全て自作**（`tools/harness/make_ext_rom_test.py`が
`tools/asm/z80text.py`で組み立てたもの）。`private/`・公式ROMディレクトリ・
`PC88_REF_ROM_DIR`は一切参照していない。写し・生ログ（`--mem-write-log`・
`--io-log`・`--int-log`の出力、最大で`q3-b7`腕が約66万行）はリポジトリ外の
scratchpadに置き、本ノート作成後に削除した。本ノートに載せているのは
自作ROMのRAMマーカー値・カウント・`clock`差分のみで、公式ROM由来の内容は
一切含まない（CLAUDE.md禁止事項1-7のいずれにも該当しない）。

## 訂正（Q4、測定後のレビューによる、2026-09-19）

親（コーディネータ）による確認で、Q4節の`clock`差分=2を「中継の費用」と
書いたのは誤りだと判明した。**本節は追記であり、下のQ4節の本文は
書き換えていない。**

`tools/harness/core/q88h_clock.c`/`q88h_clock.h`（`tools/patches/
0010-shared-clock.patch`が導入するもの）を読んで確認した:

```
static uint32_t g_clock;
uint32_t q88h_clock_tick(void) { g_clock++; return g_clock; }
```

`q88h_clock_tick()`は`q88h_iolog_record`/`q88h_intlog_record`の内部から
**記録される`OUT`/`IN`/割り込み受理イベント1件ごとに1回だけ**呼ばれる
単調増加の通し番号で、コメント自身が「main/sub間の真の発生順を復元する
ための呼び出し順カウンタ」であり「Z80のサイクル数（T-state累積）は
別スコープ」と明記している。**経過時間（実CPUサイクル数・フレーム数の
いずれも）ではなく、記録されたイベントの個数を数えているだけ**である。

実際、`ra`走の`--io-log`を見直すと、`BANK_CALL`1往復の中で「切替OUT」
（`clock=4`）と「復元OUT」（`clock=6`）の間には、`0x32`へのOUT
（バンク番号選択、`clock=5`）が1件だけ記録されている
（窓の中の直接メモリ読み（`LD A,(6000h)`等）はOUT/INではないので
`--io-log`には載らない）。つまり「2」は**「切替と復元の間にログへ
記録されたI/Oイベントが1件あった」という事実**であって、所要時間でも
命令数でもない。

**結論**: Q4節の`q4_relay_cost_clock_delta = 2`は中継の費用を表して
いない。訂正として、**Q4は「定性（中継が経由・往復として成立し、
毎回同じ構造で完了する）のみを採用し、費用は未測定のまま残す**。
コーディネータの許可（「手間がかかるなら定性のみ採用してよい」）に
基づき、中継経由と直接呼び出しをN回（例: 1万回）回してフレーム数の
差を取る、という定量測定は今回は実施しない。実施する場合は、
改めて事前登録の追補（フレーム数を時間の代理指標として使うことの
妥当性・N回のループをどう作るか）が要る。

## Q1 読み分け（B1・B2・B3・B9）

- `q1_default_reads_main`: **成立**。切替前に窓を読むと head=`E0`・tail=`E1`
  （メインROM側の既知パターン、いずれのバンクの `0xA0+n`/`0xB0+n` とも
  異なる）。
- `q1_bank_reads_match_n`: **成立**。バンク0〜3を順に選び読んだ結果、
  4バンクとも期待どおり（バンク`n`で head=`0xA{n}`・tail=`0xB{n}`、
  取り違え0件）。
- `q1_restore_reads_main`: **成立**。4バンク分の往復後、`0x71`を戻すと
  head=`E0`・tail=`E1`に戻った（B1と同じ）。
- `q1_other_bits_preserved`: **成立**。バンク切替前に`0x32`のbit5(PMODE)を
  意図的に立てて（`0x20`）おいたところ、4回の往復・復元を経ても
  `0x20`のまま変化しなかった。
- `q1_rom_version_addr_restores`（B9、B3への追加観測）: **成立**。
  `0x79D7`相当番地（自作マーカー`0xC7`）も、切替前=`C7`・復元後=`C7`で
  一致した。窓が拡張ROM側を指している間は同番地から拡張ROM側のバイト
  （実測では各バンクとも自作ROMの未使用領域の埋め値`0x00`）が読める。

## Q2 欠落（B4）

`N88_2.ROM`を欠落させたROMディレクトリで同じ手順を実行した。

- `q2_missing_bank_reads_ff`: **成立**。バンク2選択時、head/tail/`0x79D7`
  相当番地の3箇所とも`FF`（`memory.c`の`load_rom()`が未発見時に
  `memset(...,0xff,...)`する、というext-rom-bank-survey.md第2節の読みを
  実測で裏取りできた）。
- `q2_other_banks_unaffected`: **成立**。バンク0・1・3は欠落の影響を受けず
  期待どおり（`A0`/`B0`・`A1`/`B1`・`A3`/`B3`）。

## Q3 割り込み安全性（B5・B6・B7）

いずれも200往復ループ、バンク側ルーチンは約2.1フレーム分の空ループ
（実測: バンク有効化から完了まで平均約1.95フレーム/往復——B5・B6とも
200往復が約390フレームで完了した）。

- **B5（陽性対照、割り込み無効）**: `q3_no_interrupt_baseline_ok`
  **成立**（`COMPLETED_COUNT=200`・`MATCH_COUNT=200`、200往復すべて
  期待値と一致）。`q3_baseline_no_active_hit` **成立**
  （`ACTIVE_HIT_COUNT=0`。割り込み自体を有効化していないので0は当然の
  構造確認）。
- **B6（本体、安全な設計）**: `q3_interrupt_during_window_ok` **成立**
  （`COMPLETED_COUNT=200`、200往復とも完走・全一致）。
  `q3_interrupt_actually_occurred_in_window` **成立**
  （`ACTIVE_HIT_COUNT=390 >= 5`——500フレーム中`--int-log`が記録した
  受理499件のうち390件が、バンク有効中フラグを見た時点でフラグが
  立っていた）。`q3_ret_pc_confirms_window` **成立**
  （`ret_pc`が窓`0x6000`–`0x7FFF`内だった件数=388件、1本目の証拠
  （フラグ由来の390件）とほぼ一致する独立の2本目の証拠になった）。
  **割り込みハンドラを窓の外に置き、フラグだけを見る設計なら、
  バンク有効中に実際に割り込みを受理しても壊れない**ことを実測で
  確認した。
- **B7（陰性対照、禁止設計）**: `q3_handler_inside_window_breaks`
  **成立**（broken、条件b: `COMPLETED_COUNT=76 < 200`）。
  `q3_negative_control_did_not_break`は不成立で、これは想定どおり
  （壊れなかったら関門違反になるところ、実際に壊れた）。
  機構の実測: 最初の1回だけハードウェア割り込みを受理
  （`intlog_total=1`）した直後、ハンドラが窓の中`0x6030`へ
  無条件で`CALL`し、そこがバンク側では自作ROMの未使用領域
  （`0xFF`=文書化された`RST 38h`）だったため、`0x0038`（IM1固定
  ベクタ、ハンドラ自身の先頭）へ**割り込み再受理ではなくソフトウェアの
  `RST`によって舞い戻り**、以後は`EI`に到達できないまま
  自分自身を無条件に呼び続けるループに入った（`ACTIVE_HIT_COUNT`は
  このソフトウェア再入の回数を13613回まで数えており、ハードウェア
  割り込みの受理回数（`intlog_total=1`）とは別物——ここは事前登録が
  「受理回数」とだけ書いていた点より詳しい区別で、結果ノートとして
  明記する）。スタックはこの再入のたびに(CALL 1回+RST 1回=4バイト)
  消費し、13613回×4B=約53KBに達して初期SP(`0xFFFE`)から結果マーカー帯
  （`0xC100`台）を大きく超えて巻き戻り、`MATCH_COUNT`が`24625`という
  200を大幅に超える値に化けていた（往復ループの正常な加算ではなく、
  暴走したスタック書き込みによる汚染——これ自体も破損の別の現れ方
  として記録するが、`COMPLETED_COUNT`の未達だけで既に broken の
  合否判定には十分）。

## Q4 呼び出しの費用（B8、参考値）

`q4_relay_cost_clock_delta` = **2**（`--io-log`の`clock`列、`0x71`への
「切替OUT」→「復元OUT」の1往復ぶん。`ra`・`b4`いずれの走でも2走とも
同じ値）。エミュレータ内部の単調増加イベント通し番号の差分であり、
実CPUのT-state数ではない（CLAUDE.md「エミュレータで測った値は
エミュレータの実装を測っている」を踏まえ、定量の絶対値には意味を
持たせない）。**定性的な結論は「中継ルーチン1回の往復は有限のイベント
数で確定的に完了し、毎回同じ値になる」こと。**

## 設計上の結論（中継ルーチンの必須要件）

1. **中継ルーチン（`BANK_CALL`相当）は必ず窓の外に置く。** 自明だが
   B7が裏から実証: 窓の中のコードは自分自身が消えるだけでなく、
   割り込みハンドラのように**別の実行文脈から窓の中の番地へ飛び込む**
   設計も同様に壊れる。
2. **割り込みハンドラは窓の外に置き、窓の中の番地を呼ばない。**
   B6とB7の差はこの1点のみで、結果は「200往復すべて成功」対
   「76往復で完全停止」に分かれた。窓の中に何かがある前提でハンドラを
   書くと、バンク切替のたびにその前提が崩れる。
3. **`0x71`/`0x32`は読んでから、対象ビットだけを書き換えて書き戻す。**
   B1〜B3で無関係ビット（PMODE）が4往復後も保持されることを確認した。
4. **バンクファイルの欠落は該当バンクだけに閉じる。** 他バンク・
   メインROM側には波及しない。呼び出し側で`0xFF`を検出してフォール
   バックする設計にするなら、その判定はバンク側の想定内容と衝突しない
   値（本測定では自作の`0xA0+n`系）を基準に組む必要がある。
5. ~~中継の費用は参考値として有限・安定（`clock`差分=2、2走とも同じ）。
   絶対値は実装依存だが、「バンク切替を挟む呼び出しがコストの見積り
   不能な処理ではない」ことは定性的に確認できた。~~
   **【訂正済み・上記「訂正」節参照】** `clock`はイベント発生順の通し番号
   であって経過時間ではないため、この項目は誤りだった。「中継が
   経由・往復として確定的に成立すること」だけを定性的な結論として残し、
   費用の大小については未測定のままとする。
