# m7jk: run内9件は同じ要求の繰り返しか、別々の対象の走査か — 結果

実施日: 2026-09-08

## 位置づけ

[m7jj](m7jj-run-internal-request-identity-preregistration.md)が事前登録した
測定の結果である。事前登録は測定開始前に単独コミット（`6525eae`）してあり、
本稿では水準・指標・判定規則を後から動かしていない。`src/`・`tools/`は
変更していない。

**結論を先に書く: 主判定はBA1（リトライ型）である。run内の9件は、
すべて同じ対象への要求だった。**

- **土俵が成立した3水準すべて・全12runで、run内のC・H・Rの基数は`1/1/1`。**
- **runをまたぐと、要求は3種類しかない**（run間の要求組の基数=3）。
- **並びは`A A A A B B B B C C C C`**——同じ要求が**4run（=36件）続き**、
  次の要求へ移る。3水準で記号列まで一致した。
- 陰性対照（読める側）は`A B C D E`で、**5件が全部別々の要求**だった。

## 主指標: run内の基数

| 水準 | run数 | **run内基数 C/H/R** | 全runで同一か | run間基数 C/H/R | run間の要求組の基数 |
|---|---:|---|---|---|---:|
| L4（N=4） | 12 | **1/1/1** | 真 | 1/1/3 | **3** |
| L8（N=8） | 12 | **1/1/1** | 真 | 1/1/3 | **3** |
| L26（N=26） | 12 | **1/1/1** | 真 | 1/1/3 | **3** |
| NEG（読める側） | 5 | 1/1/1 | 真 | 1/1/5 | 5 |

判定規則に当てると:

- **BA1（リトライ型: 全runでRの基数が1、C・Hも1）: 成立。**
- BA2（走査型: Rの基数がrun長と一致）: 不成立（9ではなく1）。
- BA3（中間・混在）: 不成立。
- BA4（Cが動く）: 不成立（Cの基数は全runで1。`m7hb`の
  `stage_cylinder_consistency`と整合する）。
- O: 不成立（合格条件9項目すべて通過）。

**主判定はBA1である。**

## run間の構造（値を出さない記号列。事前登録の指標2の細部）

要求の組が同じrunに出現順で記号を振ると、次のようになった。

| 水準 | グループの多重度 | 記号列 |
|---|---|---|
| L4・L8・L26（3水準とも一致） | **4, 4, 4** | **`A A A A B B B B C C C C`** |
| NEG | 1, 1, 1, 1, 1 | `A B C D E` |

**記号は出現順に振っただけで、値とは無関係である。** どの要求かは示していない。

つまり土俵側では、**同じ要求を9件並べたrunがSEEKを挟んで4回繰り返され
（=36件）、そこで次の要求へ移る**という、二段の構造になっている。

## 記述（判定ではない）

**言えること:**

- **run内の9件は同じ対象への要求である。** これは`m7ji`の結論
  （run長はセクタ数に追随しない）と整合するどころか、**なぜ追随しないのかを
  説明する**——1本のrunはそもそも複数のセクタを走査していない。
- **構造は二段である。** 内側が9（同一要求の繰り返し）、外側が4
  （SEEKを挟んだrunの繰り返し）。窓内で扱われた対象は3つだけだった。
- **陰性対照は形がまったく違う。** 読める側は5件が全部別々の要求で、
  runの長さも1である。**同じ集計器が、繰り返しと走査を区別して出力している。**
- `m7hb`が「9件連続」と記述した構造の**中身が初めて分かった。**
  当時のH2（固定回数上限）は、**「同じ要求を繰り返す回数の上限」という
  具体的な形**になった。

**言えないこと:**

- **「9はリトライの上限回数である」と断定しない**（事前登録どおり）。
  言えるのは**「9件は同じ対象への要求である」**までで、繰り返しの理由
  （再試行なのか、別の目的の再要求なのか）は測っていない。
- **外側の「4」が上限だとは言えない。** 3つ目のグループが4で終わっているのは、
  **窓（`--frames 3000`）がそこで切れたためかもしれない**——`m7hb`も
  ログ末尾が窓の打ち切りであることを記録している。**4が規則なのか窓の
  都合なのかは、本稿では区別できていない。**
- **窓内の対象が3つだったことから、対象の総数や順序の規則を導かない。**
- **セクタ番号・シリンダ値は出していない。基数と記号列だけである。**
- 自作ディスクは公式と形が違う。形の違いが効く可能性を排除していない。
- 条件O・水準E・A:=`disk#8`固定という1つの使い方しか見ていない。

## 「9」の追跡に対する意味

| 稿 | 分かったこと |
|---|---|
| `m7hb` | 「SEEK1回＋READ 9件」の周期が12回。H1b反証、H2は起源未特定 |
| `m7ji` | run長9はそのトラックのセクタ数ではない（3点で反証） |
| **本稿** | **9件は同じ対象への要求。外側にもう一段（4）ある** |

**H1派生は`m7ji`で潰れ、本稿でその理由まで分かった。** run長を「読む対象の
個数」と読む解釈は、観測そのものと合わない。**残るH2は「同じ要求を繰り返す
回数」という具体的な形になった。**

## 次に何を測れば絞れるか

1. **窓を延ばして、外側の「4」が規則か窓の都合かを切り分ける。**
   `--frames`を増やして、4件目のグループ以降がどうなるかを見る。
   **これが最優先**（本稿の最大の留保）。
2. **繰り返しの理由を切り分ける。** 途中で結果を成功に変えられる介入
   （既存の故障注入と同じ枠組み）があれば、「成功したらrunが打ち切られるか」で
   再試行かどうかが分かる。
3. 9と4を**同時に動かせる軸**を探す。片方だけが動く軸が見つかれば、
   二段が別々の機構であることが言える。
