# m7fk: 段27のSEEKは直前のOUTでAを潰してからシリンダを送っていた

実施日: 2026-09-03

## 位置づけ

本稿は`m7fj`の次段階であり、**測定ではなくコード読解**である。読んだのは
自分たちが書いた`src/l3_service/make_subrom.py`と`docs/spec/l3-subrom.md`だけで、
公式ROMは読んでいない。エミュレータは起動せず、測定も実行していない。
`src/`・`tools/`は変更していない。

`m7fj`は、`READ DATA` 9段のうち唯一未確定だった段30の`WRONG CYLINDER`について、
公開FDCコマンド51段全体を突き合わせ、段27（段30直前の`SEEK`）のシリンダ指定が
公式と不一致であること、また自作内部では段27のSEEKシリンダと段30のREAD DATAの
Cが整合していない（公式では整合している）ことを記録した。本稿はこの「段27の
シリンダがどこで作られているか」を、自作コードの読解だけで追う。

## 前の版の誤りの訂正

本稿は当初、「段27のSEEKシリンダと段30のREAD DATAのCは、同じ`REQ_HDR+4`という
1バイトを、間に書き換える命令なく参照しているだけなので、コード読解上は
一致するはずである」と結論していた。しかし`m7fj`の実測は自作について不一致
（False）と記録しており、当初の版はこの矛盾を「解消できない」として未解決のまま
残していた。

この矛盾を受けて読解を疑い直した結果、見落としがあった。見ていたのは
`_exchange14_prepare_first_read`内で`REQ_HDR`を書き換える命令の有無だけで、
**`FDC_SEEK`へ渡る値そのものがAレジスタ経由であり、そのAが呼び出し直前の
`out_imm`によって上書きされること**を確認していなかった。以下、この機序を
自分で確認した内容として記す。

## 1. `FDC_SEEK`が送るシリンダは「呼び出し時点のA」である

`FDC_SEEK`（1539〜1553行）を確認した。

- 1540行: `push_af`（呼び出し側が渡したAを退避）
- 1541〜1550行: `REQ_HDR+2`のbit0を読み、E（ユニット選択）へOR伝播する
  （第78版・1.46節）。この区間はAに触れない。
- 1551〜1553行: `pop_af`で1540行の退避を復元し、そのAをそのまま`FDC_OUT`へ
  渡してシリンダとして送出する。

つまり`FDC_SEEK`が送る目的シリンダは、**呼び出し時点でAに入っていた値**であり、
`push_af`/`pop_af`は中間の伝播処理からAを保護しているだけである。シリンダの
生成元は、呼び出し直前にAへ何を積んだかで決まる。ここまではコード上で確認した。

## 2. `out_imm`はAを破壊する

`out_imm`（618〜620行）を確認した。

```
618  def out_imm(self, port, value):
619      self.ld_a(value)
620      self.out_a(port)
```

`out_imm`は「即値をAへロードしてOUT」の2命令であり、**呼び出し前にAへ何が
入っていたかに関わらず、呼び出し後のAは常に`value`になる。** つまり
`FDC_SEEK`呼び出しの直前に`out_imm`を挟むと、その前に用意したシリンダ値は
消える。ここまではコード上で確認した。

## 3. 段27の経路は`out_imm`をAの読み込みより後に置いている

`_exchange14_prepare_first_read`（2380〜2396行）を確認した。

```
2380  a.label("_exchange14_prepare_first_read")
2381  a.ld_hl_imm(REQ_HDR + 4)
2382  a.ld_a_hl()                # A = REQ_HDR[4]
2383  a.ld_mem_a(REQ_UNIT_HEAD)  # REQ_UNIT_HEAD = REQ_HDR[4]
2384  a.ld_hl_imm(REQ_HDR + 6)
2385  a.ld_hl_a()                # REQ_HDR[6] = REQ_HDR[4]（Rの転記）
2386  a.ld_hl_imm(REQ_HDR + 1)
2387  a.ld_a_hl()                # A = REQ_HDR[1]
2388  a.ld_mem_a(REQ_H)          # REQ_H = REQ_HDR[1]
2389  a.ld_hl_imm(REQ_HDR + 4)
2390  a.ld_hl_a()                # REQ_HDR[4] = REQ_HDR[1]（Cの上書き）
2391  a.out_imm(P_F8, F8_CONTROL_VALUE)   # ← ここでAがF8_CONTROL_VALUEへ潰れる
2392  a.ld_e(0x00)               # Eに0。Aは触らない
2393  a.call("FDC_SEEK")         # Aは2391行のF8_CONTROL_VALUEのまま
```

2387行で`REQ_HDR+1`から読んだ値（＝意図した目的シリンダ）は、2390行で
`REQ_HDR+4`へも書き戻される。しかしこの値はAにも残ったまま2391行の
`out_imm(P_F8, F8_CONTROL_VALUE)`に到達し、そこでAは`F8_CONTROL_VALUE`という
モータ制御の定数へ上書きされる。2392行の`ld_e(0x00)`はAを触らない。したがって
**2393行で`FDC_SEEK`が呼ばれる時点のAは、意図した`REQ_HDR+1`由来の値ではなく、
直前のOUT命令が積んだ`F8_CONTROL_VALUE`である。** ここまではコード上で確認した
（`FDC_SEEK`が実際に送出するのが「呼び出し時点のA」であることは1節で確認済み）。

一方、段30のREAD DATAのCは`FDC_READ_SECTOR`（1841行、4節参照）が呼び出し時点の
`REQ_HDR+4`を読むので、2390行で書き戻された「意図どおりの値」がそのまま使われる。
**段27のSEEKシリンダ（`out_imm`に潰されたAの残骸）と、段30のREAD DATAのC
（`REQ_HDR+4`の意図した値）は、この経路では一致しない。** これは`m7fj`の実測
（自作では段27のシリンダ != 段30のC、公式は一致、段27のシリンダは公式と不一致）
と整合する。

## 4. 段30のREAD DATAのCは意図どおり`REQ_HDR+4`から読む

`FDC_READ_SECTOR`（1832〜1866行）の該当行を確認した。

```
1841  a.ld_hl_imm(REQ_HDR + 4); a.ld_a_hl(); a.call("FDC_OUT")   # C = 直前SEEK対象(byte4)
```

`FDC_READ_SECTOR`は呼び出し時点の`REQ_HDR+4`をそのまま読んでCとして送出する
だけであり、Aを事前に用意しておく必要が無い（`ld_hl_imm`/`ld_a_hl`が直接
`REQ_HDR+4`を読む）。3節で確認したとおり2390行で`REQ_HDR+4`へは意図した値が
書き戻されているため、**段30のCは`out_imm`のようなA破壊の影響を受けず、
意図どおりの値になる。** これは`docs/spec/l3-subrom.md`1.29節の規則（要求位置4を
SEEK対象へ転記し、READ DATAのC位置へ同じ対象を引き継ぐ）を共有ルーチンとして
そのまま使い回している構造であり、`m7fa`が「Cは公式と一致」と記録していることと
整合する。

## 5. 他8箇所の`FDC_SEEK`呼び出しとの対比

`src/l3_service/make_subrom.py`内で`FDC_SEEK`を呼んでいる箇所は9箇所ある
（1238, 1267, 1708, 1757, 1796, 1942, 2287, 2307, 2393行）。1942行は
`if break_dispatch_return:`ブロック内（1896行〜）にあり、コード上で確認した
限り本番ビルド（既定構成）では到達しない回帰検査専用の経路である。これを除いた
残り8箇所を、それぞれ`FDC_SEEK`呼び出し直前の数行をコード上で確認した。

| 行 | 経路 | Aの用意のしかた |
|---:|---|---|
| 1238 | 起動時FDC初期化 batch2 | `xor_a()`直後（意図的に定数0。1.22節） |
| 1267 | 起動時FDC初期化 batch5 | `xor_a()`直後（同上） |
| 1708 | `_general_read_request`（一般READ要求） | `call`直前に`rra()`でAを計算、間に`out_imm`無し |
| 1757 | WRITE直前のSEEK（`_recv_dispatch_write_sector`） | `call`直前に`rra()`でAを計算、間に`out_imm`無し |
| 1796 | `_bulk_read_do`（バルクREAD準備） | `out_imm(P_F8,...)`（1789行）→`REQ_HDR`からAを読む（1791〜1794行）→`call` の順。**out_immがAの読み込みより先** |
| 2287 | `_recv_dispatch_hdr_done`（交換#3系、段15） | `call`直前に`REQ_HDR+4`からAを読む、間に`out_imm`無し |
| **2307** | `_exchange3_prepare_sector`（交換#3/6/11共通、段19・23） | `out_imm(P_F8,...)`（2303行）→`REQ_HDR+4`からAを読む（2304〜2305行）→`call`（2307行）の順。**out_immがAの読み込みより先** |
| **2393** | `_exchange14_prepare_first_read`（交換#14 1回目READ、段27） | `REQ_HDR`からAを読む・書き戻す（2386〜2390行）→`out_imm(P_F8,...)`（2391行）→`call`（2393行）の順。**out_immがAの読み込みより後** |

1238・1267行は`xor_a()`直後で、シリンダ0を明示的に送る既存設計（7節参照）であり
本稿の対象外。1708・1757・2287行は`out_imm`を挟まずAを直接使うため問題が無い。
1796・2307行は**`out_imm`をAの読み込みより先に置いており、Aの用意が壊れない
正しい順序である。** そして**2393行（段27）だけが、この順序を逆にしている。**

特に2307行は2393行と同じ「`REQ_HDR+4`を読んで`FDC_SEEK`へ渡す」という目的の
経路でありながら、`out_imm`を先に置くことでAを守っている。**同じ目的の経路が
2箇所あり、片方（2307）は正しく、もう片方（2393）だけが壊れている**という
対比になる。段19・23（2307経由）は段構造とEOT一致から`m7fj`が測定した「食い違いは
段27・段30・段4・段6のみ」と整合し、実際にシリンダの不一致は報告されていない。

## 6. 段3・段9のシリンダ不一致との関係

段3・段9のシリンダは、`_exchange14_prepare_first_read`のような要求ヘッダ由来
ではなく、`BOOT_HANDSHAKE`内で**即値0として明示的にハードコードされている**
（1238行・1267行、いずれも`a.xor_a(); a.call("FDC_SEEK")`）。これは本稿が
特定した「`out_imm`によるA破壊」とも、`m7ey`が特定した「未初期化ワークエリアに
依存する値」とも**別の生成元**である。

- `m7ey`が特定したのは、段3・段5の**ドライブ選択（E/ユニット）**が
  `REQ_HDR+2`という、この時点でまだ書き込まれていないワークエリアに依存する
  という問題である。
- 段3・段9の**シリンダ**は、そもそも`REQ_HDR`を参照しておらず、常に定数0を
  送っている。`docs/spec/l3-subrom.md`1.22節（第17版）は、この値が「mainへ渡らず、
  直後のRECALIBRATE（batch3/batch6）が無条件にトラック0へ戻すため、区間の
  最終観測可能状態に影響しない」という理由で**任意値として意図的に選んだ**
  ことを記録している。

つまり、シリンダの不一致には少なくとも2種類の別々の生成元があることになる。
段3・段9は「意図的な定数0」（1.22節の既存設計判断）、段27は「`out_imm`による
意図しないA破壊」（本稿5節）であり、`m7ey`のドライブ選択問題とも異なる第三の
経路である。

## 7. 仕様との突き合わせ

- `_exchange14_prepare_first_read`が「C = 要求位置1」を`REQ_HDR+4`へ転記する
  規則自体は、仕様書1.34節が明示する未確定性（「C/Hは要求位置1/10が同値で
  意味上の生成元を区別できず、既存規約どおり早い位置1を採る」）をそのまま
  引き継いだ実装であり、**この転記規則自体は仕様どおりである。**
- 一方、`FDC_SEEK`呼び出し直前に`out_imm(P_F8, F8_CONTROL_VALUE)`を置く順序は、
  仕様書のどの節にも明示的な規則として記載されていない。1.34節の周辺注記
  （2373〜2379行のコメント）も、C/Hの生成元の選び方には触れているが、
  `FDC_SEEK`直前の`out_imm`配置がAを破壊することには触れていない。**これは
  仕様の記述漏れというより、実装（`_exchange14_prepare_first_read`）が
  `FDC_SEEK`の呼び出し規約（Aに目的シリンダを積んでから呼ぶ）を、2307行の
  経路とは逆の順序で満たしそこねている、という実装側の問題として読める。**
  ただし、これが仕様の不備なのか実装のバグなのかは、公式の意図が分からない
  以上どちらとも決められない。

## 言えること・言えないこと

言えること:

- `FDC_SEEK`が送出する目的シリンダは、呼び出し時点でAレジスタに入っている値
  そのものである（1節、`push_af`/`pop_af`はこれを中間処理から保護している
  だけ）。
- `out_imm`は`ld_a`+`out_a`の2命令であり、呼び出し後のAを常に指定値へ
  上書きする（2節）。
- 段27の経路（`_exchange14_prepare_first_read`、2380〜2396行）は、意図した
  シリンダ値をAへ用意した後（2387行）、`FDC_SEEK`を呼ぶ前に`out_imm`
  （2391行）を挟んでおり、この`out_imm`がAを`F8_CONTROL_VALUE`へ上書きして
  しまう（3節）。したがって段27のSEEKが実際に送るシリンダは、意図した
  `REQ_HDR+1`由来の値ではなく、`F8_CONTROL_VALUE`である。
- 段30のREAD DATAのCは、呼び出し時点の`REQ_HDR+4`を直接読むため、この
  A破壊の影響を受けず、意図どおりの値になる（4節、`FDC_READ_SECTOR`1841行）。
- 他の`FDC_SEEK`呼び出し8箇所のうち、`REQ_HDR+4`から読んで`FDC_SEEK`へ渡す
  同じ目的の経路が2307行にもう1つあり、そちらは`out_imm`をAの読み込みより
  先に置いているため壊れていない。**同じ目的の経路が2つあり、片方（2307）は
  正しく、もう片方（2393）だけが順序を誤っている**（5節）。
- この機序は`m7fj`の実測（自作では段27シリンダ != 段30のC、公式は一致、
  段27のシリンダは公式と不一致）と整合する（3節）。
- 段3・段9のシリンダ不一致は、要求ヘッダ由来ではなく実装が意図的に選んだ
  定数0が原因であり、本稿が特定した`out_imm`によるA破壊とも、`m7ey`が
  特定したドライブ選択（E）の未初期化ワークエリア問題とも別の生成元である
  （6節）。

言えないこと:

- **これが段30の`WRONG CYLINDER`の原因だとは決めない。** コード読解と
  実測の整合は示唆であって因果の証明ではない。因果は別の介入測定でしか
  決まらない。
- **意図した値が何であるべきかは、この読解からは決まらない。** 公式ROMは
  読んでいないため、公式が実際にどんなシリンダ値を送っているべきかは
  分からない。本稿が言えるのは「自作は意図した値ではなく`F8_CONTROL_VALUE`を
  送っている」ことまでで、「本来送るべき正しい値」は測定でしか決まらない。
- 段31/35/39/43（交換#14の2〜5回目READ）と段47（一般READ）の呼び出し元は、
  前の版と同じく段数の並びから消去法で推定したのみで、個別にコードを
  追ってはいない。
- 要求ヘッダ位置1・位置10に実際どんな値が入っていたか、公式が位置1と位置10の
  どちらを参照しているかは、本稿では確認していない（値は見ていない）。
- 1942行の`FDC_SEEK`呼び出しが本当に本番ビルドで到達不能かは、
  `if break_dispatch_return:`ブロックの外側にあることをコード上で確認した
  範囲での判断であり、`build_subrom`全体の呼び出し木を辿って裏を取った
  わけではない。

## 前の版からの訂正について

当初の版（本節より前の記述を参照していた版）は「両者は同一バイトを参照し、
間に書き換える命令が無いのでコード読解上は一致するはずである」と結論し、
それが実測（`m7fj`）と食い違うことを「解消できない」として残していた。
実際には、見ていた範囲が`REQ_HDR`への書き込みの有無だけに限られており、
**Aレジスタという別の経路でも値が壊れうる**ことを見落としていた。実測と
読解が食い違ったときに、実測を疑うのではなく読解のほうを疑い直し、見落として
いた命令（`out_imm`によるA破壊）を洗い出したことで、この版の結論に至った。

## 次にやること

修正候補は、`_exchange14_prepare_first_read`内の`out_imm(P_F8, F8_CONTROL_VALUE)`
（2391行）を、Aの読み込み（2386〜2390行）より前へ移すことである。これは
2307行の経路と同じ順序にする変更であり、命令の並べ替えだけなので、命令数・
バイト数は変わらない見込みである。**ただし、介入は事前登録してから行う。**
本稿では実装も介入も行っていない。事前登録すべき内容としては、修正後に
段27のSEEKシリンダが段30のCと一致するようになるか、公式と一致するようになるか、
`WRONG CYLINDER`が解消するかを、それぞれ独立した観測量として測ることが
考えられる。
