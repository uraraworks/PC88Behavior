## 3. 腕ごとの結果

いずれも2走で同一。`gate_io_count` はゲート番地での sub の I/O 件数、
`post_gate_io_count` は最後のゲート I/O より後の、PC が異なる sub の I/O 件数。

| 腕 | ゲート | 判定 | `gate_io_count` | `post_gate_io_count` |
|---|---|---|---:|---:|
| D-B0 | なし | `control_no_gate_run` | 0 | 0 |
| D-B1 | リセット直後 | `arm_gate_released` | 1 | 65661 |
| D-B2 | FDC初期化の手前 | `arm_gate_released` | 2 | 2310 |
| D-B3 | 初期化7batchの後 | `arm_gate_released` | 54 | 65544 |
| D-B4 | ラウンド#0の手前 | `arm_gate_released` | 2 | 2199 |
| D-B5 | ラウンド#0の後 | `arm_gate_released` | 1 | 65534 |
| D-B6-A0 | なし | `control_no_gate_run` | 0 | 0 |

**陰性対照が成立した。** ゲートを持たない D-B0・D-B6-A0 では、ゲート番地の
I/O が0件だった。第1回に run 長方式で観測された長いスピンは、PC で錨づけた
本方式では1件も `gate_entered` を立てていない。**観測は「暇な待ちループ」を
ゲートと取り違えていない。**

D-B3 だけ `gate_io_count` が 54 と多いが、その後 65544 件進んでおり、
**解除されている**。ここでは件数の多寡を解釈しない。

## 4. 総合判定

**`m6i_d_no_arm_unverified`**。未検証腕は0である。

**D-B1〜D-B5 の5腕すべてで、停止ゲートは解除された。**
`m6i_d_b1_control_void` は成立しない。

副問は **`m6i_b_b2_b4_survive`**。D-B2 と D-B4 がともに `arm_gate_released`
だった。

## 5. 事前登録の注記のうち、当たらなくなったもの

事前登録 §4 は `m6i_d_no_arm_never_released`（追補1 で
`m6i_d_no_arm_unverified` へ改名）について、

> **m6i-c の結果と食い違う**（m6i-c は B5 と同じ sub ROM を持つ C0・C3 で
> `gate_never_released` を観測している）

と注記し、§5 の行き先も「m6i-c と食い違うので切り分けを別稿へ送る」としていた。

**この前提は、本測定より前に取り下げられている。** m6i-c の副問
`gate_never_released` は誤帰属であり、[訂正](m6i-c-subquestion-correction.md)
を `a8537b7` で committed 済みである。本測定（取り直し）はその後に走らせた。

したがって **本測定は m6i-c と食い違わない。** 訂正後の m6i-c と、本測定は
同じことを言っている——**ゲートは詰まっていない。**

事前登録に書いた注記を、当たらなくなったからといって消さない。
**当たらなくなった経緯ごと残す。**

## 6. 得られたこと

- **m6i-b の腕は、ゲートが詰まることによっては汚染されていない。** 5腕とも
  解除されている。B1 の陰性対照を「sub が再開しなかった」という理由で
  無効にすることはできない。
- **m6i-b の B2・B4 の成立は、ゲートで止まったまま成立したのではない。**
  副問 `m6i_b_b2_b4_survive` が成立した。
- **しかし m6i-b の腕への疑いは消えていない。** m6i-c は、B5 と同じ sub ROM
  （ゲートあり）と、それ以外がバイト一致でゲートだけ無い sub ROM とを比べて、
  **ゲートの有無だけで通常READの成否が変わる**ことを確定している。その一方で、
  本測定はゲートが詰まっていないことを確定した。
  **2つを合わせると、ゲートの実害は「止めること」ではない。**
- ゲートは `IN $FE` / `AND` / `JR Z` の3命令である。止めないのに成否を変える
  のだから、残る経路は**ポートを1回余分に読むこと**しかない。
  **ただし本測定はその機序を測っていないので、ここで確定しない。**

## 7. この測定で決まらないこと

- **ゲートの実害の機序は決まらない。** 「余分な `IN $FE` が何を壊すか」は
  本測定の対象外である。上の §6 最終項は、2つの測定を並べたときに残る可能性を
  述べたものであって、測定された結論ではない。
- **m6i-b の境界判定7種が救えるかは決まらない。** ゲートが詰まっていなくても、
  ゲートの有無で成否が変わる以上、ゲートを持つ腕の結果をそのまま状態の結果と
  して読めない。
- 公式ROM内部の実装、公式の送受信値、実機での絶対時間は決まらない。
- **通常READを許してよい最早時点は決まらない。** `docs/spec/l3-subrom.md`
  1.65節は未確定のままであり、本稿は規則を1つも起こさない。
- ゲートは測定専用の介入であり、公式 sub がそのような待ちを持つとは主張しない。
- `gate_io_count` の腕ごとの差（D-B3 の 54 など）は解釈しない。
- 別媒体、WRITE、複数セクタREAD、BASIC命令一般へ一般化しない。

## 8. 行き先

事前登録 §5 の `no_arm_unverified` の行き先は §5 のとおり前提を失った。
代わりに、本測定と m6i-c を合わせた状態から次を立てる。

1. **m6i-e: ゲートの実害の機序を測る。** 問いは「ラウンド#0の後に
   `IN $FE` を1回足すだけで、通常READの成否が変わるか」。
   ゲート（`IN` + `AND` + `JR Z`）から分岐を取り除き、**`IN $FE` 1回だけ**を
   置いた sub ROM を作れば、m6i-c と同じ 2×2 のバイト直交で切り分けられる。
   さらに「`IN` を別の無害なポートに替えた腕」を対照に置けば、
   **ポートCを読むこと自体**が効いているのかを分けられる。
2. m6i-e が機序を確定してから、m6i-b の境界判定7種を取り直す稿を立てる。
   **機序が分からないまま取り直すと、同じ穴を別の形で踏む。**
3. 1.65節への規則の追加は、それまで行わない。
