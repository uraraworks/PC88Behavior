# 資料判定 2026-08-07 — antun.net「NEC系BASICの内部形式」

URL: `https://www.antun.net/tips/p2v/nBasic.html`（2022/11/28 作成、著者名あり）

## 判定: **保留。L4 の段で、読む前に判定をやり直す**

L2（フォント）には不要なので、いま確定させない。**確定させないこと自体が判断**である。
必要でもないのに近づいて、近づいたせいで汚染するのが一番つまらない負け方なので。

## 何の文書か

NEC 系 BASIC（N-BASIC / N80 / N88-BASIC V1・V2 / N88-漢字BASIC /
N88-日本語BASIC ほか）の**プログラムが内部的にどんなバイナリ形式で
保存されるか**の解説。対象は PC-8001/8801/9801/6001 系と広い。

書かれている種類:
- 中間言語（トークン）フォーマット、行のリンク構造
- **予約語（トークン）テーブル**
- 文字コード対応表、グラフィックキャラクタ仕様
- 漢字コード（JIS / Shift_JIS / EUC）の扱い
- 浮動小数点数の内部形式

逆アセンブルリスト・グリフのビットマップ・実行可能なソースコードは含まれない。

## 引っかかる点が2つある

### 1. 「ROM のバイナリ/16進ダンプが複数箇所に例示あり」と報告された

これは**中間言語で保存されたプログラムのバイト列の例**（＝ファイル形式の例示）
である可能性が高い。そうであれば ROM の中身とは別物で、禁止事項1には当たらない。
**ただし現時点で見分けはついていない。** L4 で読む前に、使い捨ての判定係を立てて
「ROM の内容か、ファイル形式の例か」を先に確定させること。

### 2. 予約語テーブルは「ROM 内のデータテーブル」である

こちらのほうが重い。`docs/PLAN.md` の規律は
**「データテーブルはダンプせず、挙動から再構成するかルールから生成する」**。
他人が起こした対応表を実装者が読むのは、まさにその避けたい経路に乗る。
散文の仕様説明は可・データテーブルは不可、の線引きで言えば**不可の側**。

**そして、これは測定で採れる。** BASIC でキーワードを打って SAVE し、
出力ファイルを読めばコード↔キーワードの対応が採れる。測定ハーネスも
`tools/basic_surface.tsv` の命令表（166 + 16）も既にある。
**読むより測るほうが速い可能性すらある。**

## 効く場所

- **L2 には効かない**（フォントの格納形式には踏み込んでいない）
- **L4 で効く。** ただし効かせ方は「読んで写す」ではなく
  「**何を測ればいいかの地図として使う**」。中間言語という形式が
  存在すること・行がリンク構造を持つこと・浮動小数点が独自形式であることが
  分かるだけでも、測定の設計が変わる
- **浮動小数点の内部形式は例外**。GW-BASIC の MIT 公開ソースが
  明示的に「読んでよい」側（CLAUDE.md）なので、そちらから採ればこの資料は要らない

## L4 に入るときの手順（先に決めておく）

1. 使い捨ての判定係を立て、「例示のバイト列が ROM の内容かファイル形式か」を確定
2. **予約語テーブルの節は、判定係にも中身を報告させない**
3. 散文の仕様説明（形式の構造）だけを `docs/spec/` に起こす
4. 具体的な対応表は測定で採る。**測定コミットが実装コミットに先行する**
