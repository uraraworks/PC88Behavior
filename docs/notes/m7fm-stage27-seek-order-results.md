# m7fm: 段27のOUT順序を直すと9段すべてが正常終了したが、条件5が崩れた

実施日: 2026-09-03

## 位置づけ

本稿は`m7fl`で事前登録した軸D（`_exchange14_prepare_first_read`内の
`out_imm(P_F8, F8_CONTROL_VALUE)`を、Aへ目的シリンダを読み込む一連の命令
より前へ移す介入）の実測結果である。段番号は0起点で数える。条件O（公式ROM
一式）は既存測定を流用し、ベースライン（現行HEAD）と軸Dは各2run新規に取得
した。**4条件とも決定論性が成立した。** 事前登録した合格条件（六条件）に
照らして判定するが、**結論を先に書く。軸Dは事前登録の合格条件を満たさない
ので不合格である。基準は緩めていない。採用していない。`src/`は元へ戻し、
`git diff`は空である。**

## 条件4（容量関門）

`m7fg`が確定した基準（`build()`の`SystemExit`不発生。数値比較は使わない）で
判定した。8構成 × `PC88_BULK_READ_INTERVENTION_LIMIT`=1〜4の全32通りで
`build()`は`SystemExit`を出さず成功した。使用量はベースラインと同じであり、
純粋な並べ替えという事前登録どおりの見込みが的中した。**条件4=yes。**

## 陽性対照

事前登録した三点を先に確認した。三点とも成立している。

1. 自作サブROMのSHA-256が、ベースラインと軸Dで異なった（固定長8192バイト
   パディングなのでファイルサイズ差は使っていない）。
2. 段27のSEEKが指定するシリンダが、ベースライン対軸Dで**変化した**（2runで
   再現）。介入は届いている。
3. 段27のSEEKシリンダと段30のREAD DATAのCの内部整合
   （`stage_cylinder_consistency`）が、**ベースライン=False → 軸D=True**へ
   変化した。条件O（公式ROM一式）は常にTrueである。

- **軸D: 9段すべてIC=正常終了。`$FB` run長も9段すべて条件Oと完全一致した。**

- ベースライン対軸D: 段3・9・27で不一致（変化あり）、他8段は一致（不変）。
- **軸D対条件O: 11段すべて一致した。**

## 条件5（段0〜段26の外形がベースラインから不変か）= no

段4・段6（`SENSE INTERRUPT STATUS`）のunit/head分類が、ベースラインと軸Dで
**異なった**（2runで再現）。軸D側はこの2段で条件O（公式）と一致する値に
なっていた。段0〜段26の他の段（種別列・結果ステータス復号名）は変化して
いない。**条件5=no。**

### なぜこの節を独立して立てるか

`_exchange14_prepare_first_read`は交換#14の経路であり、**段27で実行される。**
段4・段6は起動区間で、**それより前に実行される。** 後で実行される箇所
（段27）の命令の並べ替えが、先に実行される段（段4・段6）の外形を変えるのは、
**実行順序の上では説明がつかない。** 軸Dが動かしたのは`out_imm`1件の位置
だけであり、段4・段6が実行される時点ではまだ段27のコードは実行されて
いない。

したがって、条件5が崩れたことの説明として、少なくとも2つの可能性がある。

**(a) 段4・段6のunit/head分類が、ROMの内容そのもの（バイト列・配置）に依存
している。** `m7ey`は、段3のSEEKが**未初期化のワークエリア**（`REQ_HDR+2`
bit0）を読んでいることを特定し、「この振る舞いは実行環境のRAM初期値に依存
する可能性があり、観測されたB-unitが常に出るとは決めない」と明記している。
軸Dはコードの並べ替えによってROM像（命令列のバイト配置）を変えており、
ROM像が変わればそれをロードするRAM上の初期値（あるいは初期値の与えられ方）
も変わりうる。これが事実なら、段4・段6の変化は「軸Dの意味的な効果」ではなく
「ROM像が変わったことの副作用」ということになる。

**(b) 軸Dの並べ替えに、まだ特定できていない前方への影響がある。** 実行順序上
は段27が段4・段6より後だが、`push_af`/`pop_af`の対応やスタック、あるいは
他の経路との相互作用など、本稿ではまだ洗い出せていない経路を通じて前方へ
影響している可能性は排除できない。

**どちらであるかは本稿では決まらない。推測で(a)に決めない。**

**もし(a)なら、条件5は「ROMのバイト列を変える介入すべてが落ちる条件」に
なり、合格条件として成立しない可能性がある。** これは`m7fg`で記録した容量
条件の誤り（「使用量 ≤ 2048」がベースラインそのものを不合格にしていた）と
同じ形——**手を触れていないものまで落とす条件**——である。**ただし今回は、
ベースラインが落ちることを示せていない**（ベースラインは介入を含まないので
条件5の判定対象になりようがなく、「ベースライン自身が条件5に落ちる」という
形の反証をまだ持っていない）。**したがって、まだ「条件5が壊れている」とは
言えない。** (a)と(b)のどちらかを、次稿で陰性対照によって切り分ける。

## 条件6（WRITE経路のI/O列）= yes

件数・バイト数・SHA-256が期待値と一致した。適合条件5（`tools/conform_l3.sh`）
も軸D版で同じ期待値に一致した。**条件6=yes。**

## 適合条件

`tools/conform_l3.sh`（環境変数3本を全て渡す）は適合条件1〜5すべて合格、
**SKIP 0件**、rc=0だった。出力中のNG3件は既知の陽性対照（自己検査b/c/d、
`m7fh`・`m7fj`と同一の既知挙動）である。

## 判定と採用

事前登録した六条件に照らすと、1=yes、2=yes、3=yes、4=yes、**5=no**、6=yes
である。**一つでも欠ければ合格と呼ばない、という事前登録どおり、総合判定は
不合格である。事前登録の合格条件を満たさないので不合格である。基準は緩めて
いない。採用しなかった。** `src/`は軸D適用前の状態へ戻し、`git diff`は空で
ある。

## 言えること / 言えないこと

言えること:

- 軸Dの介入（`out_imm`の移動）は、段27のSEEKシリンダを変化させ、段27の
  シリンダと段30のREAD DATAのCの内部整合を公式と同じTrueへ変えた。
- 軸D適用後、READ DATA 9段すべてが正常終了し、`$FB` run長も9段すべて条件O
  と完全一致した。
- SEEK 11段は軸D対条件Oで全段一致した。
- 段4・段6のunit/head分類が、軸Dによってベースラインから変化し、条件Oと
  一致する値になった。この変化は、軸Dが直接触れていない起動区間（段27より
  前）に及んでいる。
- WRITE経路・容量関門は不変（yes）である。

言えないこと:

- **段30の`WRONG CYLINDER`が消えた原因を「OUT順序だった」と断定しない。**
  読解（`m7fk`）・陽性対照・実測は整合しているが、これは強い示唆であって
  因果の証明ではない。条件5が崩れている以上、観測された変化のどこまでが
  この並べ替えという介入そのものに帰属するのか（対 ROM像が変わったことの
  副作用）が確定していない。
- **段4・段6・段3・段9が条件Oと一致するようになった理由は決めない。** 上記
  (a)・(b)のどちらかは本稿では切り分けていない。
- **意図した値が公式と同じである理由は決めない。** 公式の値は読んでおらず、
  一致は観測であって設計ではない。
