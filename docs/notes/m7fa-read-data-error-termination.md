# m7fa: 自作subのREAD DATAは9件すべてエラー終了していた

実施日: 2026-09-02

## 位置づけ

本稿は新しい実測ではなく、`m7ew`で取得済みのログに対する再解析である。
対象は公式diskA起動、条件O（公式ROM一式）と条件M（混成）、`--frames 1800`、
各2runであり、両条件とも決定論性が成立している。既存器材
`tools/compare_l3_entry_fdc.py`が使う`analyze_write_path.Command`のデータ構造を
利用した。エミュレータは起動しておらず、測定も実行していない。

`m7ew`は段30、すなわち4本目の`READ DATA`だけが条件Mで長さ263の`$FB` runを
持たず、長さ7であることを記録した。本稿では、その段だけでなく`READ DATA` 9段
すべての結果ステータスとパラメータ位置を見た。

## 観測1: 結果ステータス

`READ DATA`は段18・22・26・30・34・38・42・46・50の9件である。公開された
ステータスビットを復号すると、条件Oは9件すべてIC=正常終了、条件Mは9件すべて
IC=異常終了だった。

条件Mのうち、段18・22・26・34・38・42・46・50の8件は
`ST1=END OF CYLINDER`だった。段30の1件だけは`ST1=NO DATA`、
`ST2=WRONG CYLINDER`だった。

`END OF CYLINDER`は、μPD765系がEOTに達したときに立てる終了条件であり、
IC=異常終了として報告される。これが不具合かどうかは本稿では決まらない。
8件では`$FB` run長が条件Oと同じで、順に263・263・263・3591・4103・4103・
519・263だった。従ってデータフェーズは行われている。段30だけは条件Oが263、
条件Mが7であり、条件Mではデータフェーズが行われていない。

## 観測2: コマンドパラメータの位置一致

`READ DATA`のパラメータは8バイトである。各位置について条件Oと条件Mの
一致／不一致だけを突き合わせた。値は表示も転記もしていない。

| 位置 | 内容（公開FDC仕様の並び） | 一致状況 |
|---:|---|---|
| 0 | unit/head | 9段すべて一致 |
| 1 | C（シリンダ） | 9段すべて一致 |
| 2 | H（ヘッド） | 9段すべて一致 |
| 3 | R（セクタ） | 9段すべて一致 |
| 4 | N（サイズ） | 9段すべて一致 |
| **5** | **EOT** | **段18・22・26・30・46・50の6段で差**（段34・38・42は一致） |
| **6** | **GPL** | **9段すべてで差** |
| 7 | DTL | 9段すべて一致 |

座標（C・H・R・N）とunit/headとDTLは全段一致しており、差はEOTとGPLに
限られる。

## 言えること

自作subの`READ DATA`は9件すべて異常終了で終わり、公式は9件すべて正常終了
していた。この差はこれまで記録されていなかった。

`m7ew`が記録した段30の特異性、すなわちデータフェーズが無いことは、9件の中で
段30だけが`NO DATA`・`WRONG CYLINDER`という別種のステータスで終わることと
対応する。他の8件は`END OF CYLINDER`であり、データフェーズ自体は行われている。

パラメータ差はEOTとGPLだけで、座標は全段一致している。従って、段30の
`WRONG CYLINDER`は、送っているCが公式と違うことによるものではない。

L3仕様6節7項は、書き込み経路について「EOTは媒体形状、GPLは公開形式のN=1
短GAP分類」と記録している。読み出し経路のEOT・GPLが公式と一致しているかは、
これまで測られていなかった。

## 言えないこと

段30が`NO DATA`・`WRONG CYLINDER`になる原因は決まらない。座標が一致している
以上、送った値の違いではないが、ドライブの実際のヘッド位置、直前のシーク結果、
媒体の状態のいずれにも帰属しない。

`END OF CYLINDER`が不具合かどうかも決まらない。EOTに達したときの正常な終了報告
でもあり得る。「9件すべてエラー」という表題を、9件すべてが失敗しているという意味に
読み替えない。8件はデータフェーズを行っている。

EOTとGPLの差が異常終了の原因かどうかも決まらない。EOTが一致している段34・38・42
でも異常終了しているため、EOTだけでは説明されない。GPLは全段で差があるが、GPLが
異常終了を生むかは測っていない。

適合条件1〜5は全て合格している状態でこの差が見つかった。従って、この差が機能上の
欠落だとは本稿では言えない。mainが受け取るデータ列は一致しており、FDCの終了
ステータスは適合条件の条件文に含まれない。

公式が使っているEOT・GPLの値は読んでいない。位置の一致／不一致だけを見ており、
値を推測して実装へ入れない。

`m7ex`・`m7ey`が扱った起動区間のドライブ指定差（段3・段5）との因果は決めない。
段30の直前の`SEEK`は段27で、そこに差は無い（`m7ex`）。

## 次にやること

読み出し経路のEOT・GPLが公式と違うことが分かったため、次の段階では位置対応の
介入により、どちらがどう効くかを測る。値を推測で埋めず、`m7s`（第36版）や
`m7v`（第39・40版）と同じ位置対応・介入の型で、EOT・GPLを動かしたときに
終了ステータスと`$FB` run長がどう変わるかを見る。その測定は事前登録してから行う。
本稿では実装も介入も行わない。

## 情報境界

記録したのはコマンド種別名、段の位置、パラメータ位置の一致／不一致、公開
ステータスビットの復号名、`$FB` run長だけである。パラメータの値、データ部の値、
公式ディスクの実データ、画面本文は表示も転記もしていない。公式ROMは読んでいない。

## 検証

本稿の作成時にはエミュレータを起動せず、測定を実行していない。
`tools/check_cleanroom.sh`を実行し、全項目OK、rc=0を確認した。`git status`で
`src/`・`tools/`の変更と`private/`由来ファイルの混入が無いことも確認した。
