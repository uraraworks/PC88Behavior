# M6i — メイン→サブ方向の要求(コマンド)プロトコル

`docs/notes/m6-sub-proto.md`(第1〜4版)・`docs/notes/m6-fdc-ports.md` で、
$FC/$FD がメイン⇔サブ間のデータ経路であること、$FA/$FB がサブ内部の
FDCポーリング(サブが自分のFDCチップを叩く層)であることまでは確定した。
今回はその一段上、**mainがサブに対して何をどういう手順で要求しているか**
(自作サブROMが解釈・応答しなければならないプロトコル)を、既存の
`measurements/m6c-sub-*`(共通クロック付き)を再解析して調べた。

**方針の確認(タスクで指示された前提)**: サブROM再実装の適合条件は
「メインCPUが `IN $FD` で受け取る値の列の完全一致」に確定済み
(`docs/spec/l3-subrom.md` 5.1節)。したがって **`$FA`/`$FB` 経由でサブが
自分のFDCをどう叩くか(`OUT $FB` の個々の値が何のFDCコマンドか)は
実装に不要であり、本稿でも追わない**。本稿が対象にするのは
`$FD`(main OUT)/`$FC`(main IN)/`$FF`/`$FE` を介した **main⇔sub間の
プロトコル**であり、これは自作サブROMが直接実装しなければならない層である。

## 対象ログと解析器

追加測定は行っていない。既存の `measurements/m6c-sub-{d0-boot,d1-files,
d2-save,d5-seqfile}.iolog.txt`(共通クロック付き、決定論性は
`docs/notes/m6-conformance.md` で確認済み)を再解析した。

新規解析器: `tools/analyze_main_to_sub.py`(第三者が
`python3 tools/analyze_main_to_sub.py --iolog <path> --label <label> --out <path>`
および `cross` サブコマンドで再実行できる)。出力は
`measurements/m6i-main-to-sub-{d0-boot,d1-files,d2-save,d5-seqfile,cross}.txt`。

解析の過程で、対話的に手順を確認するための使い捨てスクリプト(作業用
一時ディレクトリに置いたもので、リポジトリの外)をいくつか書いたが、
そこで見つけたロジックは最終的にすべて `tools/analyze_main_to_sub.py`
に整理し直して収録した(使い捨てコードをそのままリポジトリに残さず、
第三者が再現できる形に清書した)。

**手法の性質**: 本解析が使っているのは iolog に記録された「直前の
リターンアドレス(PC)」だけである。同じ処理が実行されるたびに同じPCへ
戻ってくるという事実からサブルーチン境界を機械的に見分けている
——これは公式ROMのバイト列を読む・逆アセンブルするのとは異なる
(禁止事項2に抵触しない)。**ROMの命令列そのものは一度も参照していない。**
PCクラスタの集合(どのPCが何個現れるか)は各条件の実測から機械的に
決まったものであり、決め打ちしていない。

## 1. main側の送受信プリミティブ(確定)

main の I/O ログを PC 別に集計すると、`$FD`/`$FC`/`$FE`/`$FF` へのアクセスが
明確に2つの定型パターン(プリミティブ)に分かれることが分かった。
全パターンは4条件・数十〜数千サンプルで例外なく再現した。

### 1.1 SEND(1バイト送信: main→sub)

```
OUT $FF 0F        (省略される場合あり)
IN  $FE  ...       "相手の受信準備待ち"ループ (pc=37DC)
OUT $FF 0E
OUT $FD <byte>     実際のデータバイト (pc=37F4 または 3811, 後述)
OUT $FF 09
IN  $FE  ...       "相手の受理確認待ち"ループ (pc=37FF)
OUT $FF 08
IN  $FE            結果ステータス読み出し (pc=381C)
```

### 1.2 RECV(1バイト受信: sub→main)

```
OUT $FF 0B
IN  $FE  ...       "相手のデータ準備待ち"ループ (pc=3853)
OUT $FF 0A
IN  $FC <byte>     実際のデータバイト (pc=3863 または 3880, 後述)
OUT $FF 0D
IN  $FE  ...       "相手の受理解除待ち"ループ (pc=386F)
OUT $FF 0C
```

SENDとRECVは構造的に対称(prepare→wait→strobe→data→strobe→wait→finish)。
$FFの値がプリミティブの「フェーズ」を表すコード(0F/0E/09/08=SEND系、
0B/0A/0D/0C=RECV系)になっている——これは4条件すべてで例外なく
再現し、sub側の `OUT $FF` の値分布(既報 `m6-fdc-ports.md` H4、
`m6-sub-proto.md` Q1補助で「08/09付近に偏る」とされていた集計)とも
**一致する**(1.4節で検算)。

### 1.3 バルク(高速)転送モード

diskA起動時の5635/5632バースト(`m6-sub-invariant.md` 既報)は、上記の
1バイトごとの $FE ハンドシェイクを伴わない**別の**ループを使っている。
main側は `OUT $FF 09`(pc=C25E)→`OUT $FF 08`(pc=C26F)→`IN $FC`(pc=C269)
を単純反復するだけで、`$FE` へのポーリングが一切挟まらない
(d0-bootで5632件、他条件も同数)。

**確定**: mainには「1バイトずつ $FE ハンドシェイクを取る通常モード」と
「ハンドシェイクを省いた高速バルクモード」の2つの転送経路がある。
バルクモードは起動時の固定長データ転送(1.6節、`m6-sub-invariant.md`)
専用で、起動後の個別ファイル操作(FILES/SAVE/シーケンシャル読み書き)は
すべて通常モード側を使う(4条件で確認、後述)。

### 1.4 検算: sub側 `$FF` の値分布との整合性

`docs/notes/m6-fdc-ports.md` H4・`m6-sub-proto.md` Q1補助で
「subのOUT $FFは08/09に強く偏るが、ユニーク値は9〜10種ある」と
既報されていた。d0-bootでsubのOUT $FF値を集計し直すと:

```
08: 6161件  09: 6160件  0C: 67件  0A: 67件  0D: 66件  0B: 66件  91: 2件  81: 1件  0E: 1件
```

**この8種(08,09,0A,0B,0C,0D,0E + 0F相当)は、本節で確定したSEND/RECV
プリミティブのフェーズコードと完全に一致する。** subも同じ語彙で
フェーズを書き戻している(応答のハンドシェイクにsub自身も参加している)
と読める。これは「$FFの正確な意味論は未確定」としていた
`l3-subrom.md` 第3版3節への回答になる(4節参照)。

## 2. SEND/RECVの多バイト連続(交互パターン)— 当初仮説の訂正を含む

### 2.1 当初の仮説とその反証

main OUT $FD の直後PCは `{37F4, 3811}` の2種類しかない。当初、
「37F4=まだ続きがある送信、3811=列の最後の送信バイト(境界マーカー)」
という仮説を立てた(d0-bootの最初の数件だけを見ると、3811は必ず
単発で、直後に256バイトのRECV応答が続くように見えたため)。

**この仮説はd5-seqfile条件で反証された。** 実際にログを見ると、
複数バイトを連続で送る場面(書き込みバースト)では **37F4 と 3811 が
交互に**現れる(`clock=192630`〜付近、8件確認):

```
192630 OUT $FD 11 pc=37F4
192639 OUT $FD 60 pc=3811
192651 OUT $FD 01 pc=37F4
192661 OUT $FD 60 pc=3811
192673 OUT $FD 00 pc=37F4
192683 OUT $FD 60 pc=3811
...(267バイト連続)
```

これはRECV側で既に確認していた `3863`/`3880` の交互パターン
(`m6-sub-proto.md` 第3版registeredの「256バイト単位のRECV」がまさに
この形)と対称であり、**「37F4/3811は境界マーカーではなく、
1バイトおきに折り返す2エントリのループ(ループアンローリング)の
片割れ」と解釈するほうが観測と整合する。** RECV側の3863/3880と
まったく同じ構造。

**訂正の記録**: 本稿の解析器 `tools/analyze_main_to_sub.py` には
`check_3811_is_singleton`(当初仮説の検証用)と `run_lengths`
(訂正後の解釈を裏付けるための連続長ヒストグラム)の両方を残した。
前者だけを見ると「3811は連続0件」で当初仮説が正しく見えてしまう
——これは「3811の直後にまた3811が来るか」という狭い問いにしか
答えていないためで、37F4と交互になるケースを検出できない。
**この見落としに気づいたこと自体を記録として残す**(推測で押し通さず
反例が出た時点で解釈を訂正した、という経緯の証拠)。

### 2.2 連続長ヒストグラム(確定)

`tools/analyze_main_to_sub.py` の `run_lengths` で、他イベントに
中断されないSEND/RECVの連続区間の長さを条件別に集計した。

| 条件 | SEND連続長の主な値 | RECV連続長の主な値 |
|---|---|---|
| d0-boot | 1,2,5,6,8,12 | 1, **256**(4回), 5632(1回) |
| d1-files | 1,2,5,6,8,12 | 1, **256**(9回), 5632(1回) |
| d2-save | 1,2,5,6,8,12 | 1, **256**(14回), 5632(1回) |
| d5-seqfile | 1,2,5,6,8,12, **267**(8回) | 1, **256**(15回), 5632(1回) |

**確定**: 読み出し応答は常にちょうど**256バイト**(4条件×複数回、
すべて一致)。**書き込み側の連続SEND(267バイト)は d5-seqfile
条件でのみ観測され(8回)、d0-boot/d1-files/d2-save では一度も
現れなかった。** d2-save(`SAVE`コマンド)ですら267バイトの
書き込みバーストが無かった点は測定結果としてそのまま記録するが、
**理由は本稿の範囲では特定できない**(このテストでのSAVE対象データが
小さくバッファ内で完結した、あるいは別の書き込み経路を使った、
などの可能性があるが未確認。3節に未確定として残す)。

267という数字は256(データ本体、後述)+ 11(ヘッダ/トレーラ相当の
バイト数)に近いが、書き込み側のヘッダ構造は本稿では読み込み側ほど
明確に切り分けられていない(書き込みバースト中のバイト列には
ファイル内容そのものと思われるASCII的な値が混ざり、どこまでが
制御バイトでどこからがペイロードかを機械的に確定できなかった
——3節に未確定として残す)。

## 3. 要求(リクエスト)の構造 — 読み出し側は確定、書き込み側は未確定

`tools/analyze_main_to_sub.py` の `reconstruct_requests` で、SENDイベントに
直後(次のSENDまで)続くRECV/BULK_RECVを応答として対応付けた
(この対応付け自体は「次のSENDまでの区間」という機械的な定義であり、
恣意的な境界推定ではない)。

### 3.1 256バイト読み出し要求のヘッダ構造(確定)

応答が256バイトになった全15要求(d5-seqfile)についてヘッダ
(直前8バイトのSEND列)を確認すると、**全15件が同じ8バイト形式**
だった:

```
02 01 00 <b3> <b4> 06 12 60
```

- byte0=`02`, byte1=`01`, byte2=`00`, byte5=`06`, byte6=`12`, byte7=`60` は
  **15件全例外なく固定**
- byte3(`<b3>`)とbyte4(`<b4>`)の2バイトだけが要求ごとに変化する

同じ8バイト形式は d0-boot(4件)・d1-files(9件)・d2-save(14件)でも
再現した(全条件で先頭3要求のヘッダが完全一致することは
`measurements/m6i-main-to-sub-cross.txt` で確認済み——4節の
決定論性の裏付けと符合する)。

### 3.2 byte3/byte4 の意味(測定による裏付け・条件付きで確定)

d5-seqfile(シーケンシャル読み書きテスト)での15要求の (byte3, byte4) を
時系列順に並べる:

```
(00,01) (00,02) (03,03) (25,0D) (25,0E) (25,0D) (25,01) (25,02) (25,03)
(25,0E) (25,0D) (25,01) (25,02) (25,03) (0E,09)
```

**観測される規則性**:

1. **byte3は「値が変わる頻度がbyte4より低い」。** 同じbyte3の値
   (例: `25`)が10要求連続する一方、byte4はその間に何度も変化する。
   これは「byte3=トラック(または読み出し単位の大分類)、
   byte4=その中のセクタ番号」という一般的なディスクアドレッシングの
   形と一致する。
2. **byte3が`25`で固定の区間で、byte4は `0D→01→02→03` という
   折り返し(ラップアラウンド)を示す。** 単調増加ではなく、
   ある上限(観測範囲では`0D`=13)に達すると`01`に戻って再び
   増加する。これは「1トラックあたりのセクタ数が一定で、
   境界に達すると先頭セクタへ戻る」という、セクタアドレッシングで
   一般的な折り返し挙動の**形**と一致する。
3. 起動直後の最初の3要求(`(00,01)(00,02)(03,03)`)では、byte4が
   単純に`01,02,03`と単調増加している——これは折り返しに遭遇する前の
   区間であり、規則1・2と矛盾しない。

**確定して言えること(測定のみから)**: byte3/byte4は要求ごとに変化する
2バイトの引数であり、その変化パターン(片方が疎、もう片方が密で
ラップアラウンドする)は、**「粗いアドレス(トラック相当)+
細かいアドレス(セクタ相当、周期的に折り返す)」という2階層の
アドレッシング構造を持つことと矛盾しない。**

**確定できないこと**: この2バイトが実機の「トラック番号」
「セクタ番号」という名前そのものに対応するかどうかは、本測定
(値の並びのみ)からは断定できない。折り返し周期(観測範囲では
13付近)が実際のディスクジオメトリのどの数値と一致するかも
特定していない(特定するにはD88形式のセクタ構成を仕様書ベースで
確認する追加作業が要るが、本稿のスコープ外——`l3-subrom.md`
3節「5635という数値の由来」と同じ理由で未着手のまま残す)。
**「2バイトの引数があり、規則的な変化パターンを持つ」という
構造面の結論だけを採用し、それ以上の意味の断定はしない。**

### 3.3 1バイト応答(ステータス系)の観測

応答が1バイトだけの要求(d0-bootで13件)も存在する。ヘッダが単発の
`06`(SEND1バイトのみ)の場合、応答値は `80`/`C0` の2値のみが
交互のように現れた(d0-bootで6件中: 80,C0,80,C0,80,C0の順)。
これは「状態を尋ねるコマンド(`06`)への1バイトステータス応答」
という定性的な見立てと整合するが、**bit7(0x80)が何を表すかは
本稿では特定していない**(3節に未確定として残す。既報の
`$FA`のbit7=RQM的、という所見と紛れないよう、これは main IN $FC
経由のステータスであり別のポート・別の文脈であることに注意)。

### 3.4 書き込み要求のヘッダ構造 — 未確定

2.2節の267バイト書き込みバーストについて、開始直前の数バイトを
遡って確認すると(例: `clock=192630`直前は`14,00,11,60,01,60,00,60,...`)、
読み出し側の `02 01 00 XX YY 06 12 60` のような単純な固定パターンには
収まらなかった。書き込みバースト中に、ファイル内容と思われる
ASCII的な値(ディレクトリ名やファイル名の断片に見えるバイト列)が
すぐに混ざり込むため、**「どこまでが制御ヘッダで、どこからが
書き込むデータ本体か」を本稿の解析(値の並びのみ)からは
明確に切り分けられなかった。** 推測で境界を引くことはしない。
未確定のまま残す(3節)。

## 4. `$FE`/`$FF` の役割(本稿の結論)

タスクで指定された「`$FE`/`$FF`の役割」について、**本稿の文脈
(main側のSEND/RECVハンドシェイク)に限れば、構造は確定できた。**

### 4.1 `$FE`(main視点): ハンドシェイクの4つの待ち状態(確定)

`tools/analyze_main_to_sub.py` の `wait_loop_transitions` で、
main の `IN $FE` を4つの待ちループのPCごとに集計し、ループを
抜ける際の値遷移を条件横断で比較した(`measurements/m6i-main-to-sub-cross.txt`)。

| PC | 意味(文脈から) | 観測された遷移 | 4条件での一致 |
|---|---|---|---|
| 37DC | SEND前(相手の受信準備待ち) | `80⇄82`(主), まれに`02⇄80⇄82` | 完全一致 |
| 37FF | SEND後(相手の受理確認待ち) | `12⇄14` | 完全一致 |
| 3853 | RECV前(相手のデータ準備待ち) | `20⇄21` | 完全一致 |
| 386F | RECV後(相手の受理解除待ち) | `40⇄41` | 完全一致 |

サンプル数はn=126(d0-boot,37DC)〜n=7752(d5-seqfile,3853)まで幅があるが、
**4条件すべてで、上記以外の遷移は(37DCの少数の副次パターンを除き)
一切現れなかった。** これは高い確度で言える構造である。

**確定**: `$FE`はmain側から見て、SEND/RECVそれぞれの前後2箇所
(計4箇所)で「相手の準備/受理状態」を表すレジスタとして機能して
いる。RECV側(3853/386F)は明確な単一ビット(bit0)のトグルだが、
SEND側(37DC/37FF)は単純な1ビットのON/OFFというより、複数ビットが
組になった状態遷移(`80→82`はbit1のセット、`12⇄14`はbit1↔bit2の
入れ替わり)であり、**「単一の準備完了ビット」というよりは
小さな状態コードに近い。** これ以上細かいビット単位の意味の分解は
本稿では行っていない(3節)。

**留保**: これは`$FA`(既報 `m6-fdc-ports.md`、サブ内部のFDC
ステータス)とは**別のポート・別の文脈**である。`$FE`は
main側のCPUが読むレジスタで、サブ内部のFDCポーリングとは
直接の関係を示す証拠がない(混同しないよう明記する)。

### 4.2 `$FF`: SEND/RECVプロトコルのフェーズコード(確定、既報を補強)

1.2節・1.4節のとおり、main/sub双方が同じ8種の値
(`0F/0E/09/08`=SEND系、`0B/0A/0D/0C`=RECV系)を`$FF`に書き込んでおり、
sub側の値分布(既報「08/09に強く偏る」)とも一致する。

**確定**: `$FF`は「FDCの制御コード」ではなく、**main⇔sub間の
SEND/RECVハンドシェイク・プロトコルにおけるフェーズ識別子**として
機能している。`l3-subrom.md`第3版3節が「ハンドシェイク/コマンド
コード的レジスタ」とぼかしていた記述を、本稿は「具体的に
どのフェーズでどの値を書くか」まで確定させることで置き換える。

**まだ確定できないこと**: sub自身が`$FF`を書くとき、それが
「mainの要求に対する受動的な応答」として書いているのか、
「サブ内部の別のイベント(FDC完了など)に応じて能動的に」書いて
いるのかは、本稿(値の分布のみ)では区別できない。

## 5. 応答側(サブ)の挙動 — 未確定のまま残す

タスクの4番目「サブが要求を受けてから最初の `OUT $FC` までに何を
しているか」について、本稿は**測定を追加していない**(既存の
`m6c-sub-*.iolog.txt`からsub側の詳細なタイミングを引くことは
可能だが、時間の都合で本稿のスコープには含めなかった)。

分かっていること(既報からの再掲): サブの割り込みは main の直接
I/Oを直前イベントとしない(`m6-sub-proto.md`第3版Q3)。つまり、
mainがSENDプリミティブで`$FF`/`$FE`を叩いても、それが**即座に**
サブの割り込みを起こしているわけではなく、サブは自分の
`$FA`/`$FB`ポーリングループの中でmainの書き込みを検知していると
考えられる(構造的整合性のみ。因果の確認はできていない)。

**次に測るべきこと**: SEND要求のトリガー(main側の`OUT $FF 09`など)
の直後、sub側の最初の反応(`IN $FA`/`IN $FB`の値変化)までの
clock差を条件横断で集計すれば、「サブがポーリングでどれくらいの
遅延で要求を検知するか」を定量化できる。自作サブROMがこの遅延を
再現する必要は無い(5.1節の原則どおりPIOの内部実装は自由)が、
「mainがビジーウェイトで待つ設計だと動かない」ような極端な遅延が
無いことの確認にはなる。本稿では未着手。

## 6. まとめ(確定/未確定)

### 確定(測定の根拠つき)

- main⇔sub間には、$FE/$FFによるハンドシェイクを伴う「SEND(1バイト
  送信)」「RECV(1バイト受信)」の2つの定型プリミティブがあり、
  4条件・数十〜数千サンプルで構造が完全に再現する(1節)
- 起動時のバースト転送(5632/5635件)は上記と別の、$FEハンドシェイクを
  省いた高速バルクモードを使う(1.3節)
- SEND/RECVとも、複数バイトを連続で送受信する場面では2つのPC
  (SEND: 37F4/3811、RECV: 3863/3880)が交互に現れる。当初「3811=列の
  終端マーカー」と仮説していたが、d5-seqfileの267バイト書き込み
  バーストでこの仮説は反証され、「ループアンローリングの折返し」と
  解釈し直した(2節、訂正の経緯を含めて記録)
- 読み出し要求は `02 01 00 <b3> <b4> 06 12 60` という固定8バイト
  ヘッダを持ち、応答は必ずちょうど256バイト(4条件・全23回で例外なし)。
  byte3/byte4は要求ごとに変化する2バイトの引数で、
  「疎に変化するbyte3」+「密に変化しラップアラウンドするbyte4」という
  2階層アドレッシングの形を持つ(3.1〜3.2節)
- `$FF`はFDCコマンドではなく、main/sub共有のSEND/RECVフェーズ
  コード(8種の値)として機能する(4.2節)
- `$FE`はmain視点で、SEND前後・RECV前後の4箇所それぞれに固有の
  値遷移パターンを持つ「相手の準備/受理状態」レジスタとして機能する
  (4.1節)

### 未確定(推測で埋めない)

- byte3/byte4が実機の「トラック番号」「セクタ番号」そのものに
  対応するか、折り返し周期(観測範囲で13付近)がディスクジオメトリの
  どの値と一致するか(3.2節)
- 書き込み要求(267バイトバースト)のヘッダ構造。制御バイトと
  データ本体の境界(2.2節・3.4節)
- なぜd2-save(SAVEコマンド)では267バイトの書き込みバーストが
  一度も観測されなかったか(2.2節)
- `$FE`のSEND側(37DC/37FF)の遷移がなぜ単純な1ビットではなく
  複数ビットの組で表れるのか、その各ビットの個別の意味(4.1節)
- subが`$FF`を書くタイミングが「mainへの受動応答」か「能動的な
  自発イベント」かの区別(4.2節)
- サブが要求を受けてから最初に応答するまでの遅延・手順の定量化
  (5節、未着手)
- QUASI88のエミュレーション実装由来である可能性(`m6-sub-proto.md`の
  既報留保と同様、本稿の発見についても複数エミュレータでの再測定・
  実機資料との突き合わせなしには排除できない)

## 7. 自作サブROMへの示唆(実装要件の追加分)

`docs/spec/l3-subrom.md` 第4版(本稿を反映)に転記する要点:

1. 自作サブROMは、main側のSEND/RECVプリミティブ(1節)が期待する
   $FE/$FFのフェーズコード・タイミングに**mainから見て**正しく
   応答しなければならない。内部実装(ポーリングかタイマ割り込みか)
   は自由(5.1節の原則どおり)。
2. 256バイト単位の読み出し応答(3.1節)を実装する必要がある。
   要求ヘッダの2バイト引数(byte3/byte4)をどう解釈してどの
   256バイトを返すかは、**適合条件(mainのIN $FD列の一致)を
   満たす限り自由**——3.2節で「トラック/セクタらしい」という
   形は分かったが、これを名前どおりに実装する義務は無い。
3. 起動時バースト(バルクモード、1.3節)は既存仕様
   (`l3-subrom.md` 1.6節)のとおり再現する。
4. 書き込み側(267バイトバースト)は構造が未確定なため、
   **今回のマイルストーンの実装対象には含めない**——ゴールAの
   範囲(`l3-subrom.md` 4節)はdiskA起動+代表的なファイルI/Oで
   足りるが、SAVE相当の書き込みパスは追加測定してから実装すべき
   (次のスコープ)。
