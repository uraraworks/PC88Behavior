# m7bm: バルク後READ完了応答を実装し、256件送信まで到達した

実施日: 2026-08-20

## 情報境界

実装根拠は`docs/spec/l3-subrom.md` 1.37節だけである。公式ROM一式・公式diskAは
公式main＋自作サブROMの混成環境で**実行して**検証し、内容は読んでいない。
`private/`への`cat`/`xxd`/`od`/`strings`・逆アセンブルは行っていない。
生iologは`mktemp -d`で作ったリポジトリ外の一時ディレクトリだけに置き、
コミット対象にしていない。256件のディスク実データは値を出力せず、公式と
自作の位置別一致数だけを集計した。診断用の伏せ字済みログもリポジトリ外に置いた。

## 1. 実装

`src/l3_service/make_subrom.py`の`POST_BULK_ACTIVE`を、従来の非0ゲートを保った
まま次の段階値として再利用した。

| 値 | 状態 |
|---:|---|
| `0` | 起動時バルク完走前 |
| `1` | バルク完走後・最初のREAD前 |
| `0x06` | 最初のREAD結果263件完了・`0x06`待ち |
| `0x12` | `0x06`受信とack保留後・`0x12`待ち |
| `0xFF` | 1.37節の交換完了 |

一般READが完了するたびに`POST_BULK_ACTIVE`を`0x06`へ再アームするため、
最初の交換後は`0xFF`から`0x06`へ戻る。1.37節が実測したのはバルク後最初の
READの1回だけであり、この反復適用は後続READにも同じ交換を使う実装上の選択である。

受信値を一時退避し、`POST_BULK_ACTIVE`の段階値と一致したときだけ専用遷移へ
入る。`0x06`受信時は既存の1バイト保留経路へ`0xC0`を1件だけ接続し、
`SECTOR_READY`は維持する。次の`0x12`受信時に初めて`SECTOR_BUF`を既存の
256件応答経路へ接続する。起動時交換中はフラグが0なので、同じ値が現れても
専用遷移へ入らない。

追加コードをサブROMの2048バイトフェッチ窓へ収めるため、既存の`LD A,0`を、
直後に条件分岐がフラグを参照しない箇所に限って1バイト短い`XOR A`へ置換した。
生成結果はコード**2044バイト**である。この置換はA=0という既存動作を変えず、
新しい値・遷移を追加しない。

## 2. 混成実走結果

全測定は同期実行し、`conform_l3.sh`は600秒、`diag_l3_mixed.sh`は300秒、
個別混成測定は180秒の上限を付けた。

### 2.1 起動時バルク（後退確認）

`tools/conform_l3.sh`の公式main＋自作サブROM混成実走で、main `IN $FD`は
**5635件**、期待SHA-256とも一致した。無条件値分岐によってバルクが0件に
退行したm7bkの失敗は再発していない。

### 2.2 m7bk停止点以後

混成の生ログを既存`tools/analyze_post_read_response.py`で解析すると、
FDC結果263件目の直後から次の列を検出した。

- `sub IN $FC=0x06` 1件
- `sub OUT $FD=0xC0` 1件
- `sub IN $FC=0x12` 1件
- `sub OUT $FD` 256件

したがって、m7bkの停止点（FDC結果263件）を**259データイベント越えた**。
256件は公式側と**256/256位置一致**した（値自体は非出力）。その後のsub側
イベント列は、連続同種を畳み込んだ残り**15/15件**で構造的分岐が無かった。
subの新しい停止は観測しなかった。

main側で次に現れる構造差は、256件送信完了後の畳み込み後**71件目**で、
公式`OUT $31`に対し混成`OUT $32`だった。これが次の調査基準点である。

注意: `tools/diag_post_bulk.py`でバルク終端から全sub I/Oを厳密比較すると、
従来からあるsub内部FDC制御差（畳み込み後35件目、公式`OUT $F8`対混成
`IN $FA`）を先に報告する。m7bkの「FDC結果263まで」は選択したイベント種別の
ラン列についての一致であり、全ポートの厳密一致を意味しない。本実装で確定した
1.37節の末尾データイベント列は上記のとおり一致した。

### 2.3 適合条件1〜4

| 条件 | 結果 | 数字 |
|---:|---|---:|
| 1 | PASS | 5635件・SHA-256一致 |
| 2 | SKIP | `PC88_REF_DISKB`未設定（判定0本） |
| 3 | 判定不能（従来どおり） | 自作subの割り込み受理0件 |
| 4 | PASS | ディスク無しsub I/O 0件 |

`conform_l3.sh`全体はrc=0。条件2は入力未指定、条件3は判定対象0件であり、
合格へ読み替えていない。条件1・4に後退は無い。

## 3. 自己検証層

試験用mainも1.37節どおり`0x06`送信→`0xC0`受信→`0x12`送信へ追随させた。
`tools/verify_l3.sh`は期待**771件**に対し受信771件（ack 3件、データ768件）で
全件一致し、rc=0となった。ackも位置だけでなく`0xC0`との値一致を必須にした。
`break_response`、`break_write_ack`、`break_fixed_byte_cutoff`を含む既存の全故障
注入は、いずれも成果物が変化して判定NGになることを確認した。期待件数や条件は
下げていない。

## 4. 未確定・次の一手

- 256件送信後、main側の畳み込み後71件目で`OUT $31`対`OUT $32`へ分かれる原因
- 厳密sub I/O比較で先行して残る`OUT $F8`対`IN $FA`の内部FDC制御差
- 条件2（diskB未指定）と条件3（割り込み受理0件）は今回も確定していない
- 1.37節の実測はバルク後最初のREADの1回だけである。一般READ完了のたびに
  `0x06`へ再アームする実装を採ったが、後続READでも同じ交換になるかは未測定

次は、256件送信完了を新しい基準点として、値を出さずにmain側71件目の分岐へ
至る直前の要求・応答構造を既存診断器で分類する。推測でmain分岐の原因を埋めない。
