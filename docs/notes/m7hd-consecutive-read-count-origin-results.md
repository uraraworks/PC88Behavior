# m7hd: 連続READ DATA件数の起源（大きさ／位置）— 結果

測定: 事前登録どおり段階1(大きさ)を進めたが、打鍵の技術的上限で水準M・Lが
保存できず、段階1・段階2とも主判定はN4（梃子が効かなかった）に終わった

実施日: 2026-09-04

## 位置づけ

[m7hc](m7hc-consecutive-read-count-origin-preregistration.md)が事前登録した
測定の結果である。事前登録は測定前に単独コミット（`c17f841`）済みで、本稿
では事前登録の条件・水準・判定規則を後から動かしていない。`src/`は本稿では
変更していない。

## 陽性対照（最初に書く）

1. `build_mixed_rom ... --break-drive-selector`を条件M・`FILES 2`・
   B:=`disk#10`で比較した。`tools/compare_l3_entry_fdc.py --after-frame 700`
   のunit/head差件数は**13件**（0件より大きい）。
2. `tools/analyze_error_exchange_shape_selftest.sh`は全4項目OK・rc=0。

**両方通ったため、以降の解釈を行う。** この2件は`m7ha`/`m7hb`が同一目的で
既に通した陽性対照であり、本稿が使う基盤モジュール
（`compare_l3_entry_fdc.command_names`等）の検出力を確認するものである。

なお、この陽性対照の測定自体が、条件Oの`disk#10`・`FILES 2`で
「SEEK1回＋READ DATA9件連続」の周期構造を再現した（公式FDCコマンド種別列
195件、READ DATA108件が連続run、混成側は79件で56件目からSEEKへ分岐）。
`m7hb`の確定結果と定性的に一致しており、本稿の測定パイプライン
（自前の使い捨てスクリプト）が`m7hb`の結果と矛盾しないことも確認できた。

## 段階1: 大きさを変える（結果）

### 水準Sは保存・読み出しとも成功した

| 項目 | 結果 |
|---|---|
| SAVE | rc=0、`reached(['save"1:qs01"'])`=真、1回で成功（frames=4200） |
| LOAD | rc=0、`reached(['load"1:qs01"'])`=真、1回で成功（frames=3000） |
| 連続READ構造 | 総READ DATA=17件、run長列=`[1]×17`（**連続READが1件も現れなかった**） |

### 水準M・Lは、いずれも保存段階で技術的上限により完了しなかった

各水準とも、複製を1本ずつ作り直しながら4回試したが、**4回とも同じ原因で
失敗した**（frames不足ではない）。

| 水準 | 試行回数 | 結果 |
|---|---|---|
| M（20行） | 4/4失敗 | q88measure標準エラーに`打鍵列が長すぎる`（毎回同一） |
| L（80行） | 4/4失敗 | 同上 |

**原因を特定した:** `tools/harness/frontend/main.c`の
`#define MAX_KEYSTROKES 512`（打鍵1回=1キーイベント。改行も1キーイベント
として数える）。本稿が計算した水準M・Lの打鍵列は、いずれもこの512件を
超える（水準Mは1行あたり約28〜30打鍵×20行+SAVE行で600打鍵超、水準Lは
その4倍）。**これは事前登録した「フレーム不足で打ち切られた」ケースとは
性質が異なる**——打鍵列の長さ自体が起動前の解析段階で上限判定されるため、
`--frames`をいくら増やしても解消しない。この理由により、事前登録した
「framesを1.5倍にしてもう一度だけ試す」規則を字義どおりには実施せず
（増やしても結果は変わらないと分かっているコマンドを再実行しても
情報が増えない）、代わりに**複製を作り直しての4回試行**（いずれも同一の
`打鍵列が長すぎる`エラー、決定論的）によって「frames増加では解決しない」
ことを直接確認した。この判断とその理由をここに明記する。

**大きさが実際に変わったことの独立確認: 実施できなかった。** 水準M・Lが
保存できなかったため、S・M・L間の`FILES`署名比較は水準Sの1点しかなく、
比較そのものが成立しない。事前登録の合格条件3（梃子が効いたことの独立
確認）を段階1では満たせない。

## 段階2: 位置を変える（結果）

事前登録は「M水準を流用」としていたが、**M水準は段階1で保存できなかった
ため、事前登録どおりの段階2は実施できなかった**（M水準に依存する以上、
位置だけを動かす測定の土台がない）。これも合格条件3を満たせない
（N4に該当）。

### 参考測定（事前登録の範囲外、正式判定には使わない）

段階1のS水準（打鍵512件以内に収まる最小構成）を流用し、位置だけを動かす
参考データを追加で取得した。**これは事前登録した設計ではない**ので、
以下のN1〜N5の正式判定には使わない。次稿の設計材料としてのみ記録する。

- 位置P0: ダミー無しで`QP01`（S水準と同一内容）を保存。
- 位置P1: `DF01`〜`DF20`（1行ずつ、20本）を保存後に`QP01`を保存
  （合計打鍵約400、512以内で完了）。

| 項目 | P0 | P1 |
|---|---|---|
| SAVE | rc=0、1回で成功 | rc=0、1回で成功 |
| `FILES 1`署名比較（P0対P1） | `screen_compare=mismatch`（行数17→19、SHA相違） | 同左 |
| LOAD | rc=0、1回で成功 | rc=0、1回で成功 |
| 連続READ構造 | 総READ DATA=17件、run長列=`[1]×17` | 総READ DATA=18件、run長列=`[1]×18` |
| 決定論性 | 独立2回目も同一（83コマンド/17件/全run長1） | 独立2回目も同一（87コマンド/18件/全run長1） |

**位置は`FILES`署名で確かに変わったことを確認した**（この参考測定に限り
合格条件3相当を満たす）。しかし**連続READ DATAはP0・P1いずれでも1件も
現れなかった**（総件数が17→18に1件増えただけで、runはすべて長さ1のまま）。

## ROM取り違え防止

条件Oの測定はすべて公式ROM一式をそのまま`--rom-dir`に渡した
（混成不要）。陽性対照のみ`build_mixed_rom`で混成ROMを作り、既定ビルドと
`--break-drive-selector`の2本を使った。混成ROM構築はビルド直後に確認し、
サブROMファイルの取り違えは無い（陽性対照は既存の確立済み手順の再実行
であり、`m7hb`が既に確認済みの検出力をそのまま踏襲した）。

## 決定論性

- 段階2の参考測定（P0・P1）は差が出たため、いずれも独立2回測定して
  自己一致を確認した（上表のとおり完全一致）。
- 段階1の水準Sは、内容が参考測定のP0と同一のため、P0の2回測定が
  実質的にSの決定論性も裏付けている。
- 水準M・Lは保存自体が成立しなかったため、決定論性の対象外。

## 元ディスクを壊さない

全測定で使ったのは`tools/stage_disk_by_digest.sh`が作る使い捨て複製のみ。
元ファイル（`disk#8`、`650cfac8`）への書込みコマンドは一度も実行して
いない（`--save-to-disk-image`はすべて複製先に対してのみ指定した）。
測定後に元ファイルのSHA-256を計算し、複製時点の理解（読み取り専用の
複製手順しか使っていない）と矛盾しないことを確認した
（`ORIG_UNCHANGED=yes`。値そのものは記録しない）。

## N1〜N5の判定

- **N1**（件数が大きさに追随） / **N2**（変わらない） / **N3**（位置で
  変わる）: **いずれも判定できない。** 段階1・段階2とも、事前登録した
  設計では成立するデータが1水準（S）しか得られず、比較そのものが
  成立しないため。
- **N4**（梃子が効かない）: **成立。** 段階1は水準M・Lが`打鍵列512件上限`
  という技術的制約で保存できず、大きさを変える梃子が3水準中2水準で
  効かなかった。段階2はM水準への依存により、位置を変える梃子の測定
  そのものが実施できなかった。「大きさ・位置を変えても`FILES`署名が
  変わらない」という形のN4ではなく、「梃子（打鍵によるSAVE）自体が
  ハーネスの制約で対象水準に届かなかった」という形のN4である。
- **N5**（陽性対照不通過）: 不成立。陽性対照は2件とも通った。

**主判定はN4。** ただし参考測定（正式設計外）は、位置を動かせたにも
かかわらず連続READが1件も現れないという追加情報を残した。

## 言えること・言えないこと

**言えること:**

- 条件Oの`disk#10`・`FILES 2`で「SEEK1回+READ DATA9件連続」の周期構造が
  再現すること（`m7hb`との整合）を、本稿の陽性対照測定でも確認した。
- `disk#8`起動ディスクへの`LOAD`によるファイル本体読み出しでは、
  読み出したファイルが小さい場合（水準S、参考測定のP0・P1）、
  総READ DATA件数が17〜18件であっても、**連続READ DATAが1件も現れず、
  すべて単発のSEEK→READという単位で処理された。**
- 参考測定に限り、ディスク上の位置（ダミーファイル20本による配置変更）を
  `FILES`署名の変化として独立に確認できた。ただし連続READ構造への
  影響は観測されなかった（そもそも現れないため、位置の影響を判定する
  以前の状態）。
- `tools/harness/frontend/main.c`の`MAX_KEYSTROKES 512`という制約を、
  水準M・Lの保存失敗から特定した。これは`--frames`では解消しない
  構造的な上限であり、次稿で大きさ水準を設計する際に踏まえる必要がある。

**言えないこと:**

- 連続READ DATAの件数が、読ませるデータの「大きさ」で決まるのか
  「位置」で決まるのかは、**本稿では決定できなかった。** 大きさを
  変える梃子（SAVEの打鍵によるプログラムサイズ変更）が、事前登録した
  3水準中2水準（M・L）で技術的に実行できなかったため。
- `LOAD`経路（ファイル本体読み出し）で、そもそもどんな条件なら
  連続READへ移行するのかも分かっていない。本稿が試した範囲
  （最大18件のREAD DATA、水準S相当のごく小さいファイル）では
  一度も現れなかった。`m7hb`が確認した`disk#10`・`FILES 2`の連続READ
  （108件）とは、件数の規模が全く違う（6〜10倍以上）うえ、**FILES
  （ディレクトリ読み出し）とLOAD（ファイル本体読み出し）という別の
  経路である可能性があり、本稿はこの経路差を切り分けていない。**
- 段階2（位置）は正式には未実施であり、参考測定はS水準相当の小さい
  ファイルに限られる。M・L相当の大きなファイルでの位置効果は不明。

## 次に何を測れば絞れるか

1. **打鍵512件上限を回避する水準設計に作り直す。** 候補:
   - 1行に長い文字列リテラルを収める（例: 1行で400文字のA$リテラル）
     ことで、行数を増やさずにファイルサイズだけを大きくする。
   - BASICの`FOR`ループと`PRINT#`/ファイルI/Oを使い、少ない打鍵で
     ランタイムに大きなファイルを生成させる（打鍵数とファイルサイズを
     分離できる）。
   - あるいはA:への`SAVE`ではなく、B:側（`disk#10`のように元から
     多くのファイルを持つディスク）で、既存ファイルの中から大きさの
     異なるものを`LOAD`させる方向に変える（打鍵で新規作成しないため
     512件制約を受けない）。
2. **`LOAD`経路と`FILES`経路の違いを先に切り分ける。** 本稿の参考測定
   では`LOAD`が一度も連続READへ移行しなかった。`m7hb`の連続READは
   `FILES 2`（ディレクトリ読み出し）で観測されたものであり、
   `general_read_request`が両者で同じ入口を通っているかどうかを、
   `--probe-site general_read_request`（`m7gy`/`m7gz`が確立済みの
   経路特定手法）で`LOAD`実行時にも確認する価値がある。
3. 1・2を踏まえた新しい水準で、段階1（大きさ）→段階2（位置）を
   改めて事前登録し直す。

## 開示

水準M・Lの保存で、`打鍵列が長すぎる`という同一エラーが各4回、
計8回発生した（隠さず記録する。上記「段階1の結果」節に理由を書いた
とおり、これはframes不足ではなく`MAX_KEYSTROKES`の構造的上限による
決定論的な失敗であり、5回目以降を試しても結果は変わらないと判断し、
4回で打ち切った）。それ以外の手順逸脱・汚染は無かった。測定はすべて
フォアグラウンドで実行し、測定中に`git stash`・ブランチ切替・
ファイル編集は行っていない。
