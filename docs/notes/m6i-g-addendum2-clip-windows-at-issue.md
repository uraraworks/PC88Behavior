## 2. 本当の原因 — 窓の上限が発行時刻で切られていなかった

G-L0 の走を診断した。数値は次のとおりである。

| 量 | 値 |
|---|---:|
| 通常READ の発行 clock | 11751（frame 60） |
| FDC 初期化の開始 clock | 11778（frame 60） |
| FDC 初期化の終了 clock | 11902（frame 60） |

**初期化は、通常READ の発行より後に始まっている。**

追補1 は「初期化が起きなかった場合」だけを場合分けしたが、G-L0 では
**初期化は起きている。ただし発行より後に。** したがって「初期化あり」の枝が
選ばれ、起動専用の窓は `clock < init_start` = `clock < 11778` になる。

この窓は**発行時刻 11751 を越えている。** その結果、READ 自身が出した
main の送信（発行後）を「起動専用の送信」として数えてしまい、
`startup_send = 1`・`startup_recv = 1` に対してマーカー `b = 0` となって
整合検査が偽になった。

**事前登録が数えたいのは「発行直前の状態」である**（[事前登録](m6i-g-clean-preamble-boundary-preregistration.md) §2）。
窓が発行時刻を越えてよい理由は無い。

### 分かったこと（副産物、結果には使わない）

診断の過程で、**sub は main の最初の送信を受けてから FDC 初期化を始める**
ことが見えた。G-L0 では main が60フレーム何も送らないので、sub は起動
ハンドシェイクで待ち続け、**通常READ 自身の送信が最初の送信になり**、
その後に初期化が走る。

**これは診断であって、事前登録された測定ではない。** 取り直しの結果として
使わない。期待の形として本追補へ書き込まない。

## 3. 直し方

**発行直前の状態を数える窓は、すべて発行時刻を上限にする。**

- 起動専用の窓:
  - 初期化が発行より前に終わっている場合: `clock < init_start`
  - それ以外（初期化が無い、または発行より後に始まる）: `clock < issue_clock`
  - 一般化して **`clock < min(init_start, issue_clock)`**（初期化が無ければ
    `issue_clock`）
- ラウンド#0応答の窓:
  - 初期化が発行より前に終わっている場合: `init_end < clock < issue_clock`
  - それ以外: **窓を作らない**。代わりに `c == 0` を要求する（追補1 §2 と同じ扱い）

`a` の判定（`shape[0] == 7 and shape[2] < issue_clock`）は既に発行時刻で
切られており、変更しない。**追補1 で足した「窓を作らないときは `c == 0` を
要求する」も変更しない。**
