# m7an: サブROMフェッチ窓(0x0800)境界の確定と整列パディングによる部分修正

測定日: 2026-08-17

## 情報境界

公式1800フレームログ（m7ajで新規実走・構造一致確認済み）を基準に、混成ROMを
`PC88_BULK_READ_INTERVENTION_LIMIT`と診断専用パディング環境変数を組み合わせて
新規実走した。データポート値は`tools/cmp_io.py --location-only`・
`tools/cmp_fdc_sectors.py`の内部だけで扱った。自作コード（`src/l3_service/
make_subrom.py`）のラベル・命令のバイト位置・幅は自作コードの構造情報であり、
本ノートに残す。計測ハーネス自身のソース（`tools/patches/`、
`vendor/quasi88-libretro`）は公式ROMではなく自作ハーネス・第三者エミュレータ
コアであり、クリーンルーム規律上読んでよい範囲として直接確認した。生ログ・
介入版ROMはスクラッチに置き、コミットしていない。

## 1. 末尾詰め物対照 — 総サイズは無罪と確定

`_exchange14_prepare_remaining_reads`ループ直後（中間）へ挿入していたm7amの
詰め物対照に加え、今回は**emit済み全コードの最後方**（この関数の最後の命令の
直後、実行されるコードのアドレスが1バイトも動かない位置）へ詰め物を置く版を
作った。LIMIT=2のまま、詰め物バイト数をLIMIT=3の実コード増分と同一の71バイト
に揃えて（総コード長がLIMIT=3と完全に同じ2246バイトになることを確認済み）
2回連続実走した。

**結果: 正常（先頭一致3330件、seqまで完全一致）。** 総コード長がLIMIT=3と
同じでも、既存コードのアドレスが一切動かなければ問題は起きない。
**したがって総サイズ／ROM像の大きさ自体は無罪であり、「どの命令が境界を
跨いだか」の問題と確定した（コーディネータの手順1の分岐どおり）。**

## 2. 境界を跨ぐラベル・命令の機械的列挙

m7amで確立した詰め物対照（LIMIT=2のまま、コード中間へ到達不能なNOP列を
挿入）を使い、詰め物バイト数38（安全）・39（崩壊）の境界で、ラベルの
アドレスを突き合わせた。

- **ラベルの開始位置だけを見るとどの0x100境界（0x0800含む）も跨がない。**
  唯一動いたのは診断用の`jr`自身のdelta（38→39）だけで、既存の相対
  ジャンプ55件は1件も挿入点を跨いでいなかった（m7amで確認済み）。
- ラベル単位ではなく**生バイト列を直接読む**と、`_observed_request_next_6`
  ブロックの末尾にある`JP IDLE_DISPATCH`（`C3 9E 02`、3バイト絶対番地命令）
  が、詰め物38バイトでは3バイトとも0x07FD-0x07FFに収まっていたのに対し、
  詰め物39バイトでは0x07FE-0x0800となり、**3バイト目（ジャンプ先の上位
  バイト）が0x0800に達していた**。これがぴったり閾値と一致する。
- `Asm.fixups`の"abs"種別（`call`/`jp`/`jp_z`/`jp_nz`）で、開始位置posと
  境界0x0800の関係を機械的に照合すると、詰め物38バイトでは0件、
  詰め物39バイトでは1件（上記の`JP IDLE_DISPATCH`）が
  `pos < 0x0800 < pos+2`を満たしていた。**これが唯一動いたfixupであり、
  他の54件は1件も動いていない。**

**跨いだ命令が実行パス上にあるか**: `IDLE_DISPATCH`はディスパッチャの
中心ラベルで頻繁に呼ばれる。`_observed_request_next_6`ブロック自体が
どの程度「実際に実行される」かは、公式ディスクの応答内容（伏せ字対象）に
依存するため断定できないが、少なくとも**跨いだ命令のジャンプ先
（IDLE_DISPATCH）は常に実行される中心ルーチン**であり、跨ぎによる
ジャンプ先の破損は致命的になり得る。

## 3. vendor コアのサブCPUメモリマップ確認

`vendor/quasi88-libretro`（公式ROMではなく第三者エミュレータコア。読んで
よい）を調べた。

- `src/LIBRETRO/libretro.c`の`load_system_file()`（`tools/patches/
  0001-cleanroom-harness.patch`でこのリポジトリ向けに調整済み）が、
  DISK.ROMを**常に0x0800（2048）バイトだけ**`filestream_read()`で読み込む
  （呼び出しは`load_system_file(SUB_ROM, sub_romram, 0x00800)`）。
  読めたバイト数が要求サイズと一致しないと失敗扱いになる実装のため、
  ファイルが0x0800バイトより大きくても超過分は単に読み込まれない
  （エラーにもならない）。実測でも起動ログに
  `Loaded .../DISK.ROM (0x00000800)`と出る。
- サブCPU自体がフェッチできるアドレス空間はもっと広い（vendor本来の
  `memory.c`実装では`sub_romram`は0x8000バイト確保）が、**このリポジトリの
  計測ハーネスが実際にロードするのは先頭0x0800バイトだけ**であり、
  それ以降に何が入っているかはロード処理からは保証されない
  （メモリ確保時の初期値やその後の別処理に依存する、ハーネス側の
  実装詳細）。
- `src/l3_service/make_subrom.py`の`ROM_SIZE = 0x2000`というコメント
  「vendor memory.c: load_rom(...,0x2000,...)」は、**このリポジトリの
  ハーネスが実際に使っている読み込みサイズ（0x0800）とは異なる関数
  （パッチで置き換え済みの古い経路）を指しており、フェッチ可能な窓の
  サイズとしては不正確だった。**

**結論: `ROM_SIZE=0x2000`はファイル（DISK.ROMコンテナ）自体の上限としては
残しつつ、実際にサブCPUが確実にフェッチできる窓は別に`0x0800`
（`SUB_ROM_FETCH_WINDOW`）として持つ必要がある。**

## 4. 修正

`src/l3_service/make_subrom.py`に以下を追加した。

- `SUB_ROM_FETCH_WINDOW = 0x0800`定数（根拠は上記3節）。
- `Asm.db()`が命令ごとの(開始位置,バイト数)を`instr_spans`へ記録するよう
  拡張（`ld_hl_imm`等、固定RAM番地を即値で埋め込む命令はfixupsを経由
  しないため、これが無いと2節のJP以外の跨ぎを見逃す）。
- `find_fetch_window_straddles(a, boundary)`: `fixups`（絶対番地・相対
  分岐のオペランド）と`instr_spans`（全命令）の両方から、境界を跨ぐ命令を
  列挙する。値（ROM内容）は一切出さない。
- `build()`を書き換え、`align_padding_bytes`を0から1バイトずつ増やして
  再アセンブルし、跨ぎが解消するまで繰り返す（`_exchange14_prepare_
  remaining_reads`ループ直後へ到達不能なNOP列を挿入する。`jr`で確実に
  飛び越すので実行中のコードは1バイトも動かない）。解消しないまま
  `MAX_ALIGN_PADDING_ATTEMPTS`（256）を超えたら`SystemExit`。

m7am・m7anの診断専用フック（`PC88_BULK_PADDING_BYTES`・
`PC88_BULK_TAIL_PADDING_BYTES`環境変数）は削除し、上の恒久機構に置き換えた。

## D. 検査自体の陽性対照

- 既存の`resolve()`範囲チェック・`ROM_SIZE`超過チェックはm7amで陽性対照
  済み（変更していないので再確認は省略）。
- 新設の`find_fetch_window_straddles()`: LIMIT=2の既定ビルド（align=0）は
  実際に1件の跨ぎ（`_observed_request_next_6`末尾の`JP IDLE_DISPATCH`。
  2節で特定したものと同一）を検出することを確認した（陽性対照）。
- `MAX_ALIGN_PADDING_ATTEMPTS=0`を意図的に指定すると`build()`が
  `SystemExit`することを確認した（陽性対照）。
- これらは`tools/subrom_fetch_window_selftest.sh`として恒久化し、
  `tools/run_all_selftests.sh`から呼ばれるようにした（公式環境不要）。

## 5. 修正結果の判定

**「変わった」ではなく「一致すべきものが一致するか」で判定した。**

- 既定（LIMIT=1）: 2回連続実走で先頭一致1282件、変わらず。
- LIMIT=2: 2回連続実走で先頭一致3330件、変わらず（整列パディングにより
  コード長は2175→2180バイトへ変化したが、観測される`IN $FD`列は
  1バイトも変化しなかった。跨ぎ自体は実在したが、この特定の実走
  シナリオでは結果に影響しない位置だった可能性がある。安全側の修正
  として維持する）。
- `tools/verify_l3.sh`: 修正前と同じ、既知NG1件のみ（回帰なし）。
- `tools/run_all_selftests.sh`: 全項目OK（新設selftest含む）。

**LIMIT=3・LIMIT=4は、跨ぎ解消後も先頭一致0件のまま変わらなかった
（2回連続実走で確認）。** `find_fetch_window_straddles()`はLIMIT=3の
既定ビルド（align=0）で跨ぎを1件も検出しない。つまり**LIMIT=3の退行は、
今回発見・修正した「命令がフェッチ窓を跨ぐ」パターンとは別の原因で
起きている。**

## 6. 4指標

- 値一致長: 変更なし
- main側構造的一致プレフィックス: 258件（変更なし、既定LIMIT=1で確認）
- sub側構造的一致プレフィックス: 752件（変更なし、既定LIMIT=1で確認）
- main `IN $FD`（既定LIMIT=1）: 5635件到達・先頭一致1282件・全位置一致1300件
  （変更なし）

LIMIT=2（非既定）: 先頭一致3330件、不変（整列パディング適用後も同じ）。
LIMIT=3・LIMIT=4（非既定）: 0件のまま、伸びなかった。

## 7. 次の対象

`find_fetch_window_straddles()`が検出するのは「命令のバイト列が境界を
跨ぐ」ケースだけである。LIMIT=3・LIMIT=4がまだ崩れる理由として、
**跨がずに丸ごと0x0800より後ろに置かれてしまった、しかし実際には実行
される命令列**が残っている可能性が高い（LIMIT=2の既定ビルドでも
`_observed_request_next_8`・`_observed_request_next_9`が丸ごと0x0800より
後ろにあるが、これまでの全ての実走シナリオでは問題が表面化していない
＝この特定のテスト条件下では未到達だった、というだけで、安全とは
確定していない）。この「丸ごと窓の外」パターンを機械的に検出するには、
静的なバイト位置チェックだけでは足りず、**実際の実行パス（到達可能性）**
の情報が要る。次サイクルの候補:

1. `tools/harness/core/`のトラップ機構（別セッション担当領域だが読み取り
   専用の利用は差し支えない範囲か確認のうえ）を使い、0x0800以降の
   アドレスへの実際のフェッチ/実行イベントをLIMIT=3実走で記録し、
   「窓の外を本当に実行しているか」を直接確認する。
2. または、より保守的に「0x0800を超える一切のコードを生成しない」
   （コードサイズをそもそも2048バイト未満に削る）方針へ切り替える。
   この場合はLIMIT=1〜4すべてのコードサイズを見直す必要があり、
   削った結果LIMIT=1の4指標が不変であることの確認が必須になる。

座標（m7ajのB表）・sub側752件の壁は今回もスコープ外のまま。
