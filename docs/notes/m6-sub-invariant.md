# M6d 「sub OUT $FC = 5635件固定」の切り分け

測定日: 2026-08-08
対象: `docs/notes/m6-sub-proto.md`（第4版）・`docs/notes/m6-sub-clock.md` で
残った未解決の不変量 ——「`sub OUT $FC` の発行数が d0-boot / d1-files /
d2-save / d5-seqfile の4条件すべてで厳密に 5635 件」。
測定結果の実体: `measurements/m6d-inv-*.iolog.txt` / `.txt`
（OUT/IN の発生順・ポート番号・値・発行元PC・フレーム番号のみ。ROM の
内容は含まない）。

先に結論だけ書く: **観測系のバッファ上限による頭打ちではない。フレーム数を
増やしても増えない一回限りのバースト転送であり、起動直後の一瞬（frame
42〜62、実時間で1秒未満）に集中して起きる。値の分布は256通り中255通りが
出現し高いエントロピーを持つ一方、末尾73件が0x00で埋まっている**——これは
「ディスク内容量に応じて可変長になる転送」ではなく「**固定長のブロックを
0パディングして送る転送**」の特徴と整合する。ディスク内容そのものを変えた
場合にどうなるかは、今回の手持ち材料（実ディスクが1枚のみ）では確定
できなかった（後述）。

---

## (a) バッファ上限による頭打ちか — 最優先で確認・否定

`tools/harness/core/q88h_iolog.h` のバッファは `Q88H_IOLOG_MAX_EVENTS =
1<<20`（1,048,576件、CPUごと）。4条件の sub 側総イベント数
（`m6-sub-clock.md` の表）は最大でも d5-seqfile の 122,289 件で、上限の
1割強にしかならない。加えて `n_dropped`（取りこぼし件数）は全条件・
全ログ種別で 0 件（`m6-sub-clock.md` に既記載、今回の追加測定
（`measurements/m6d-inv-frames-*.iolog.txt` 全14本）でも同様に確認）。

→ **バッファ上限説は否定できる。** 5635 はハーネスの容量制約ではなく、
実際にサブCPUが `OUT $FC` を5635回しか発行していない、という観測結果である。

## (b-1) フレーム数を振る — 一回限りのバーストであることを確認

d0-boot と同じ起動条件（`--disk-name N88_FE.D88`、打鍵なし）で `--frames`
だけを 60〜3600 まで振った（`measurements/m6d-inv-frames-<N>.*`）。

| frames | sub OUT $FC | sub 総IO件数 |
|---:|---:|---:|
| 60 | 4,847 | 51,737 |
| 65 | 5,635 | — |
| 70〜3600（65,70,75,80,85,90,95,100,150,180,200,220,250,280,300,600,900,1200,1800,3600） | 5,635（全て一致） | 78,798（300以降で一致） |

60フレームではまだ転送の途中（4,847件）で打ち切られるが、**65フレーム
以降はどれだけ長く回しても 5,635 で頭打ちのまま増えない**（3600フレーム
＝60倍走らせても同じ）。これは「起動時に一度だけ走る固定シーケンス」の
挙動そのもので、「定常的なポーリングが積み重なって偶然その回だけ
5635 になった」という可能性は排除できる。

## (b-2) ディスクを変える — 部分的にしか切り分けられなかった

手元の `PC88_REF_DISK_DIR` には実ディスクイメージが `N88_FE.D88` の
1枚しかなく、原本は書き換え禁止（`tools/measure.sh` の使い捨て複製の
仕組みで防止済み）。「別の実ディスク」を用意できなかったため、
サイズだけ同じ（348,848バイト）の全ゼロ埋め合成イメージ
（作業ディレクトリ外の一時ファイル。ディスク内容の複製ではなく
新規生成した0バイト列）を `--disk-name` で読ませて比較した
（`measurements/m6d-inv-blankdisk.*`）。

結果: サブCPU側のI/Oが**一切発生しなかった**（`sub OUT $FC = 0`、
sub 側総イベントも0）。全ゼロ埋めはD88ヘッダとして不正
（ディスクサイズ・トラックテーブルが0）で、エミュレータがディスクを
認識できずマウント段階で弾かれたためと考えられ、`nodisk` 条件と
実質同じ状態になっただけで、「有効なディスクだが中身が違う」という
比較にはならなかった。

→ **この軸は確定できなかった。** 次に切り分けるなら、D88コンテナ形式
（トラックテーブル・セクタヘッダ）を正しく組んだ「有効だが中身の違う」
合成ディスク（例: ディレクトリのファイル数を変える、ブートセクタの
中身だけ変える）を作る必要がある。あるいは実ディスクイメージをもう1枚
入手する。いずれも今回のスコープ外とする。

## (c) 転送内容の構造 — 値のヒストグラムと連続区間

d0-boot の 5,635 件の OUT 値について（バイト列そのものはノートに
転記せず、統計のみ記載）:

- **出現する値の種類**: 256通り中 255通り（ほぼ全域を使っている）。
  最頻値でも出現数は上位10種で 77〜286件程度に分散しており、
  特定の値に極端に偏ってはいない。→ 単純な制御コードの繰り返しではなく、
  実データ（セクタの中身に近いもの）を1バイトずつ送っている転送だと
  解釈するのが自然。
- **同一値の連続区間（run）**: 5,635件は 5,434個の run に分かれ、
  そのうち **5,348個は長さ1**（連続しない、値がバラける）。
  長さ2以上の run は 84個のみで、そのうち3件が突出して長い
  （長さ13・12・73）。
- **末尾の run**: 最後の run は**長さ73・値0x00で、5635件目ちょうどで
  終わる**（開始位置5563件目〜5635件目）。つまり**転送の最後の73件が
  すべて0x00**。これは「ディスクの実データを送り切ったあと、固定長に
  達するまで0パディングしている」典型的な挙動と整合する。
  中盤にも同じ値(0x00)の12〜13件の run が2箇所ある
  （位置2179〜2191、2225〜2236）。

これらは「送信バイト数がディスク内容の量に比例して伸び縮みする」の
ではなく「**固定長の枠を用意し、実データが枠に満たない分は0で埋める**」
という設計を示唆する。5635 という値そのものがどこから来る定数か
（セクタサイズ×セクタ数、あるいはトラック1本分のバイト数など）は
今回の測定だけでは特定できない——サイズの根拠を断定するには D88の
セクタ構成（1トラックあたりのバイト数）を仕様書ベースで確認する必要が
あり、これは次のスコープとする。

## (d) 時間軸上の集中度

d0-boot（`measurements/m6c-sub-d0-boot.iolog.txt`）の 5,635 件が
出現するフレーム番号の範囲を見ると、**全件が frame 42〜62 の21フレーム
（実時間にして1秒未満）に収まっている**。1800フレーム測定した全区間
のうち最初の3.5%未満に完全に集中しており、起動直後の一時点で
バーストして終わる挙動である。(b-1)の「65フレーム以降は増えない」
という結果と整合する。

---

## 結論の形

**5635 は、サブCPUがディスク起動直後（実時間1秒未満）に一度だけ発行する
固定長のバースト転送の長さである、というところまでは分かった。**
根拠:

1. バッファ上限による頭打ちではない（(a)、n_dropped=0・上限の1割強）。
2. フレーム数をどれだけ延長しても増えない一回限りの現象である（(b-1)）。
3. 発生時刻は起動直後の21フレームに完全集中している（(d)）。
4. 値の分布は高エントロピーで実データ転送らしいが、末尾73件は0x00の
   パディングで終わっており、ディスク内容量に応じた可変長転送ではなく
   固定長＋パディングの構造を示唆する（(c)）。

**確定できなかったこと**: ディスクの中身（同じ有効な構造で内容だけ違う
もの）を変えても 5635 が変わらないかどうか。今回は有効な代替ディスクを
用意できず、「弾かれて0件」という縮退した結果しか得られなかった
（(b-2)）。この軸を閉じない限り、「5635 はディスクのファイル配置に
依存しない普遍的なブート長」とは言い切れない。可能性としては
"常に決まったセクタ数を読む固定シーケンス"と"内容次第で変わるが、
たまたま試した唯一の実ディスクでは同じ値になった"の両方が残っている。

## 次に何を測るか（第1版時点）

- D88コンテナ形式を正しく組んだ、**有効だが中身の違う**合成ディスクで
  同じ計測をやり直す（(b-2)の続き）。特に、ディレクトリのファイル数や
  ブートセクタの中身だけを変えたものと、ディレクトリを全く違う配置に
  したものの両方を試すと、5635 がディレクトリ由来かブートセクタ由来かの
  切り分けになる。
- 5635 という値が「1トラック分のバイト数」「1トラックのセクタ数×
  セクタサイズ」などの機種仕様に基づく既知の定数と一致するか、
  `docs/spec/` にあるハードウェア仕様（ポート仕様・ディスク仕様の
  散文説明。ROM解析記事のコード断片は使わない）と突き合わせる。
- 末尾の0パディング(73件)・中盤の0ラン(12・13件)が clock/frame 上で
  何と対応するか（セクタ境界、トラック境界など）を、既存の
  `tools/analyze_sub_proto.py` を拡張して自動検出できるようにする。

# 第2版（2026-08-08 追記）— 別の実ディスク（diskB）での検証

第1版の (b-2) で確定できなかった「ディスクの中身を変えても 5635 は
不変か」を、**新たに入手した実ディスクイメージ（本ノートでは中立な
識別子 `diskB` と呼ぶ。実ファイル名・タイトルは記載しない。
既存の `N88_FE.D88` は `diskA` と呼ぶ）** で検証した。diskB は起動可能な
市販ソフトのディスクで、diskA（N88-BASIC）とは異なる種類のソフトウェア
だと考えられる（後述の傾向から推測。中身は見ていない）。

測定結果の実体: `measurements/m6e-diskB-boot{,600,3600}.iolog.txt` /
`.intlog.txt` / `.txt`（M6c と同じ共通クロック付きハーネス、
`tools/measure_suite.sh` の d0-boot と同じ `--frames 1800` 相当の条件。
600/3600 は frames を振った追加測定）。原本ディスクには一切書かせていない
（`tools/measure.sh` の使い捨て複製の仕組み、`--disk-writable` は
指定していない＝読み取り専用でマウント）。

## (a) sub OUT $FC の発行数 — 5635 とは一致しない

| 条件 | sub OUT $FC | sub 総IO件数 | 備考 |
|---|---:|---:|---:|
| diskA d0-boot（第1版） | **5,635** | 78,798 | 対照群 |
| diskB boot, frames=600 | **0** | 273,677（drop 0） | |
| diskB boot, frames=1800 | **0** | 413,150（drop 0） | |
| diskB boot, frames=3600 | **0** | 413,150（drop 0、1800と同数） | |

**diskB では `sub OUT $FC` が1回も発行されなかった。** 600/1800/3600の
どのフレーム数でも0件で変化せず、sub側総IO件数も1800フレーム時点で
413,150件に達したあと3600フレームまで増えない（diskAの(b-1)で見た
「一回限りのバーストで打ち止め」と同じ形の飽和）。バッファ上限
（1,048,576件/CPU）にはまだ余裕があり（drop 0）、頭打ちの原因が
ハーネス側の制約でないことは診断済み。

## (b) 仮説の判定 — 「5635固定」は棄却、「内容依存の転送」は支持されない形で終わった

**問い1: 5635 はディスク非依存の固定シーケンス（サブROM側の性質）か？**
→ **棄却された。** diskB では同じ条件下で 0 件であり、5635 はディスクに
依らない普遍の定数ではない。

**問い2: それは「ディスク内容に応じて可変長になる転送」で説明できるか？**
→ **支持されない。** 支持されるなら「diskBのほうが転送量が多い/少ない
だけで、port $FC は使われ続ける」という結果を期待するのが自然だが、
実際には diskB は diskA よりサブCPU側の総I/O量がずっと多い
（413,150 件 vs 78,798 件、約5.2倍）にもかかわらず、port $FC の
OUTは皆無だった。「量の違い」ではなく「経路そのものを使うか使わないか」
の違いであり、単純な「同じ転送路をディスクの量に応じて多く/少なく使う」
というモデルには乗らない。

代わりに支持されるのは、**port $FC 経由の固定長バースト転送は
diskA（N88-BASIC）のブート手順に特有の挙動であり、diskB の起動処理は
（同じ DISK.ROM 上で動いているとしても）別の経路でディスクを読んでいる**
という見立てである。参考として、diskB の sub OUT のポート内訳は
`$FF`（51,651〜35,961件規模）、`$FD`（48,145〜32,779件規模）が主体で
`$FC` はゼロ、`$FB`/`$F8`/`$F7` はわずかに出現しており、diskAの
port分布（`$FF`>`$FD`>`$FC`>`$FB`>…、`m6-sub-invariant.md` 第1版
未記載だが `measurements/m6c-sub-d0-boot.iolog.txt` から集計可）と
似た顔ぶれではあるものの `$FC` だけが完全に欠落している点が目立つ。

## (c) まだ確定していないこと

- diskB が具体的に何をしているか（起動処理の種類、$FC を使わない理由が
  「ディレクトリ読み込み方式の違い」なのか「ブートセクタ直読み方式」
  なのか等）は、本測定（ポート番号・発生順・件数のみ）からは分からない。
  仕様として断定するには `docs/spec/` 相当の追加測定（$FF/$FD の
  意味の切り分けなど）が要る。
- 「diskAのようにN88-BASICのBOOTを踏む別の実ディスク」がまだ手元に
  無いため、「port $FC 経由の固定長転送は N88-BASIC ディスクフォーマット
  一般に共通する挙動なのか、それとも diskA 固有なのか」はサンプル数1の
  ままである。今回分かったのは「全ての起動可能ディスクで5635が出るわけ
  ではない」ことまでで、「N88-BASICディスクなら常に5635か」は未検証。
- QUASI88由来（エミュレータの実装上の都合）である可能性は排除できて
  いない。今回の測定はQUASI88コアの挙動を測っているのであって、
  実機のDISK.ROMを直接測っているわけではない
  （`docs/PLAN.md` の測定方針どおり、実機との突き合わせは別軸の課題）。

## 結論（第2版時点の要約）

- 「5635 はサブROM側の固定シーケンスで、ディスク非依存」という仮説は
  **棄却**（diskB で0件、変化を確認）。
- 「ディスク内容量に応じて可変長になる転送」という仮説も、単純な形では
  **支持されない**（diskBのほうが総I/O量は多いのに$FCは不使用）。
- 最も整合するのは「port $FC の固定長バースト転送は diskA の起動処理
  （おそらくN88-BASIC特有のブートローダ手順）に紐づく挙動であり、
  diskB は別の経路でディスクを読んでいる」という見立てだが、これは
  まだ**見立てであって確定した仕様ではない**。次のスコープは (c) の
  各項目、特に N88-BASIC 系の別ディスクをもう1枚用意して
  「N88-BASICディスクなら5635が再現するか」を詰めること。

# 第3版（2026-08-08 追記）— 画面を見て診断が正しいことを確認

第2版は「diskB は sub 側I/O量が diskA の約5.2倍あるので起動している」
という**間接証拠だけ**で判断していた。しかし I/O 量が多いことは
「正常に起動している」でも「ディスクが読めずリトライし続けている」
でも同じ絵になりうる。このリポジトリは過去に2回、数字だけを見て
「動いている」と誤判定した経験がある（`docs/notes/m3-demand-profile.md`）。
そこで今回、**画面を直接見て**診断が正しかったかを確認した。

## 手順

`q88measure --dump-text --screenshot` を diskA・diskB それぞれ
frames=300/600/1800/3600 の4点で実行し、PPM を PNG化・縮小した上で
目視確認した（画像そのものはリポジトリにコミットしない。
`measurements/m6f-diskA-shot-f*.txt` / `m6f-diskB-shot-f*.txt` に
テキスト画面ダンプのみ残す）。diskB の起動には、私物のファイル名が
測定結果ヘッダーに写り込むのを避けるため、中立な名前
`diskB.d88`（作業用の一時コピー、リポジトリ外）を `--disk-name` に
渡した。

## 結果

**diskA**: frames=300 の時点で N88-BASIC のディスク起動プロンプト
（バージョン表示・ファイル数入力・ファンクションキー行）が表示され、
600/1800/3600 でも同一のまま静止していた（プロンプトで入力待ちに
入っているため、動きが無いのは正常）。これを「正常起動の見た目」の
基準とした。

**diskB**: `--dump-text` のテキスト画面は f300〜f3600 の全条件で
文字化けした断片のみで意味を持たない（グラフィック主体の画面で
テキストプレーンには意味のある内容が無いため、想定どおり
「テキストダンプは空/無意味になりうる」ケースだった）。
一方 `--screenshot` では:

- f300: 画面の一部だけが粗いディザパターンで描画されている途中の状態
- f600: 装飾された縁取りの中に人物イラストがフルカラーで完成している
- f1800: f600 の構図に加えて、上部に追加のロゴ的な文字列と
  赤い装飾要素が重ねて描画されている
- f3600: f1800 と**画素レベルで同一**（変化なし＝この時点で描画完了・
  安定している）

これは「真っ暗」「同一のエラー表示のまま」「Disk I/O error」のいずれにも
該当せず、**意味のある画面表示が段階的に完成していく**という、
正常なタイトル画面描画そのものの挙動だった。画面に表示された
具体的な文字列・イラストの内容はここには書かない（規律どおり）。

## (b) 診断の判定

**diskB は正常に起動していた。** 第2版の「sub 側総I/O量が diskA の
約5.2倍あり、port $FC を使わずに別経路でディスクを読んでいる」という
見立ては、画面確認によって**間接証拠から直接証拠に格上げされた**。
「ディスクが読めずリトライしている」という対立仮説は棄却できる
（もしリトライし続けているだけなら、f300→f600→f1800 で画面が
これほど完成度高く進行し、f1800→f3600 で安定するという挙動は
説明しにくい）。

## 第2版からの変更点

**第2版の結論は撤回しない。維持し、補強する。** 変わったのは
確信の根拠であって結論の向きではない:

- 第2版時点: 「diskB のI/O量が多いから起動していると考えられる」
  （間接証拠のみ）
- 第3版時点: 「diskB は画面上でも正常に起動が完了している」
  （直接証拠で確認済み）

したがって「port $FC 経由の固定長バースト転送は diskA
（N88-BASICのブート手順）に固有であり、diskB は別経路でディスクを
読んで正常に起動している」という見立てはより確度が上がった。

## まだ確定していないこと（変更なし＋追加）

第2版 (c) の各項目（diskB が具体的に何をしているか、$FF/$FD の意味、
N88-BASIC系の別ディスクでの再現性、QUASI88実装由来の可能性）は
依然として未確定のまま。加えて今回分かったのは:

- diskB のテキストプレーンには意味のある内容が無く、`--dump-text`
  だけでは起動判定ができない（グラフィック中心のソフトでは
  `--screenshot` が必須になる）。今後同種の診断をするときは
  この教訓を先に踏まえること。
