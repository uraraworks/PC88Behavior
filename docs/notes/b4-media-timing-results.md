## 1. 答え

| 問い | 構成 | BASIC に届くか（J-basic） | (0,0,1) の読み（J-read、1500 フレーム） | 期待値との一致（J-match） |

| Q1 | P: 照合の自作媒体を最初から | **届かない**（2走とも `ZQbt` なし） | 51・51 回 | **0／11**（下の注1） |
| Q2 | Q: 空で起動、フレーム 200 で挿入 | 届く | 0・0 回（挿入は2走とも success=1） | **0／11** |
| Q3 | R: (0,0,1) を C9 で埋めた媒体を最初から | 届く | 1・1 回 | **0／11** |

- 全ての腕で2走の結果が一致した（揺れなし）。
- **どの構成も、照合の期待値と1腕も一致しなかった。** 事前登録第6節の言い方で、
  **「起動後に入れる直し方（Q）は、公式と同値とは言えない」。** Q3 の C9 版も同値ではない。
- 注1: P の 22走は、照合器の compare が `report_read` で読めず ERR になった。終了時の画面に
  ファンクションキーの行（19 行目）しか無く、照合器が前提にする `Ok` の行が無いため

  空の画面は期待値と一致しない。これを不一致として数えた（判定規則の読み方の補足で、規則の変更ではない）。
- 追補1のとおり、a48ee43 のドライバでは Q の FILES・LOAD 22走が引数エラーで走らなかった（記録には
  `RUN_FAILED` として残した）。表の Q はすべて回し直しの走（batch=full-q）。

## 2. 補足の診断（事前登録に無い。判定には使わない）

照合の不一致が「行のずれ」か「中身の違い」かを、署名だけで調べた（`PC88/tmp/b4-media-work/rowshift.py`、
コミットしない使い捨て。画面本文は読み出さず、行の文字数と SHA-256 だけを比べる）。

- Q と R の画面は、全 11 腕で**署名が完全に一致**した（final・late、LOAD は load・load_late も）。
  ドライブ1を後から入れても、戻り命令の起動用セクタから戻っても、同じ状態の BASIC になる。
- Q・R の FILES 7腕は、どれも**応答が1行と `Ok`**。そのうち FILES 2・FILES・FILES 1 の6腕は、
  ドライブも媒体も違うのに**応答行の署名が全て同じ**（残る1腕は E-3 で、`ON ERROR` で ERR を表示する腕）。
  期待値の行（ファイル一覧）は、行番号を無視しても1行も現れなかった。
  → FILES がディスクに対して働いていない状態と読める。
- Q・R の LOAD は、LOAD のあとの LIST で何も表示されない（I-1・I-3・E-3）。
- これは [m6f-d-disk-rules-results.md](m6f-d-disk-rules-results.md) D9 の対照
  （(0,0,1) が C9 の媒体では `nondisk_basic`: BASIC には届くが、ディスク操作の目印 `ok`・`er` がどちらも出ない）と整合する。

## 3. 読み（推定。断定しない）

- 公式の照合の期待値は、ドライブ1の**参照ディスクから起動した**状態で取られている。自作媒体だけでは、
  公式 ROM は「ディスクの操作が働かない BASIC」（Q・R）か「BASIC に届かない」（P）にしかならず、
  期待値の状態を作れなかった。ディスクの操作が働く状態は、参照ディスクの起動が作っていると読める。
- したがって、自作照合の直し方としての「起動後に入れる（Q）」は、**公式との同値を測定で裏付けられない。**
  自作 ROM は ROM の中にディスクの操作を持つ設計なので、Q の構成で自作 ROM が期待値と一致するのは
  「参照ディスクで起動した公式」と同じ結果になる、という**設計上の前提**による。この前提を照合器具の
  冒頭に明記したうえで Q を採るか、別の方法を探すかは、親（利用者）の判断に委ねる。
- 照合の前提とは別に、l3-boot-sector 3.2節「`RET` で戻れば BASIC へ進む」について。公式ではその BASIC が
  ディスクの操作を持たない（m6f-d D9、本測定の R）。自作 ROM が戻ったあとにディスクの操作を持つ BASIC へ
  進むのは公式と違う振る舞いである。これを実装への要求にするかどうかは決めていない（需要の観測が無い）。
  仕様の改版はしていない。
