# m7cj: main→sub要求のドライブ指定位置をFILES 1/2で同定

実施日: 2026-08-24

## 情報境界

公式ROM一式、公式main＋自作sub、公式diskAの使い捨て複製2枚を用いたが、
`private/`配下、公式ROM、公式ディスクの内容は読んでいない。パスは環境変数で
のみ渡した。生iolog、画面、ROM・媒体複製、M3U、標準出力・標準エラーは
`mktemp -d`配下だけで扱った。記録する値はmainがsubへ送った要求バイトであり、
ディスクから読み出したデータ部、sub応答、FDCデータ部、画面本文は記録しない。

## 条件・解析器・決定論性

A:/B:へ同じdiskAの独立複製を入れ、300FでRETURN、700Fから`FILES 1`または
`FILES 2`、3000Fまで実行した。公式／混成を各条件2回、各run 300秒上限で
同期実行した。全8 runで取りこぼし0件。パスを含むヘッダを除くmain/sub全イベント列と
画面は条件内の2回で完全一致した。

`tools/compare_drive_request_runs.py`は既存のmain SEND run境界を再利用し、
700F以降のmain `OUT $FD`（sub `IN $FC`に対応）だけを全run・全位置比較する。
合成selftestでは同一入力を一致させ、1位置だけの変更とrun長変更をそれぞれ
不一致検出した。前者は固定8バイト形の差位置も追随する。

## 結果

公式・混成・各2回とも、A/Bでrun数17、run長列は完全一致し、値差は同じ12位置だけ
だった。全差はbit0の`0→1`である。代表的な6+2分節は次のとおりだった。

```
A: 02 01 00 25 0E 06 | 12 60
B: 02 01 01 25 0E 06 | 12 61
```

1.11節の論理8バイト要求は物理run 6+2として現れ、byte2とbyte7だけが変化した。
同系列の単独6バイト要求5件ではbyte2だけが同じ`00/01`で変化した。byte0/1/5/6、
座標候補byte3/4、全run長、他のrun位置は不変だった。

従ってbyte2 bit0は全読み出し要求で共通するドライブ候補で、byte7 bit0は
8バイト要求にだけ付随する相関候補である。

## 帰属介入

既定Falseの`--intervene-drive-byte2`で、要求byte2 bit0を公開FDC unitへだけ
伝播した。既定ROMは介入追加前の生成物とバイト完全一致する。

第1試行は交換#3専用ラベルへ介入を置いたが、B:のSEEK/SENSE/READは全件A-unitの
ままだった。検査の空振りではなくFILESがそのコード位置を踏まない介入の空振りで、
不採用とした。第2試行で共通SEEK入口へ置くと2回ともSEEK 6件・READ DATA 6件が
B-unitへ変わったがSENSE DRIVE STATUS 6件だけA-unitに残った。最後に同SENSE入口も
byte2へ接続すると、2回ともSEEK・SENSE DRIVE STATUS・READ DATA各6件がすべて
B-unitとなり、公式とのunit/head差は0件になった。FDC種別列は介入前から79件全長一致で
あり、介入後も79件全長一致のためprefix伸長は指標にならなかった。unit分類が独立な
帰属証拠である。介入2回のmain/sub全イベント列ハッシュも一致した。

この帰属介入は`tools/verify_drive_byte2_attribution.sh`で再現できる。公式環境を
明示的にオプトインしたときだけ本体を実行し、必要な環境がなければSKIPを明示する。
判定条件は「介入なしでは公式とのunit/head差がある」かつ「介入ありでは差0件」の
両方である。介入あり側だけを条件にすると、比較器が常に差0件を返す故障を素通し
するため、介入なし側を陰性対照として必須にした。

オーケストレータが公式環境で同スクリプトを実走した結果はrc=0だった。official、
without（介入なし混成）、with（介入あり混成）の3系統を各2回実行し、全runで
取りこぼし0件、各系統でパスを含むヘッダを除く2回のイベント列が完全一致した。
入口区間全体で集計した公式に対するunit/head差は、介入なしがrun1/run2とも21件、
介入ありがrun1/run2とも0件だった。これは入口区間の差の合計であり、上記の
SEEK／SENSE DRIVE STATUS／READ DATA各6件は、介入でB-unitへ変わった対象を
コマンド種別ごとに数えた内訳である。集計粒度が異なるため、21件と各6件を同一の
総数として扱わない。

同スクリプトの判定ロジックselftestも3件すべてOKだった。正常な「介入なしは差あり、
介入ありは差0件」を合格させるだけでなく、陰性対照の差を0件にする故障注入と、
介入あり側に差を入れる故障注入の2種を、いずれも不合格として検出した。

byte7は最後の2バイトrunの末尾で、最初のSEEK/SENSE/READ開始後に届く。この条件では
byte7だけを変えて最初のunitを駆動できないため、ドライブと相関することまでは確定するが、
独立した選択源とは確定しない。

## 結論と次境界

**要求byte2 bit0をFDCドライブ指定と確定する。** 固定8バイト要求については、従来
固定としたbyte2/7を訂正し、byte2は確定ドライブ、byte7は相関候補として3節に残す。
今回は測定周なので既定実装は変更しない。次周はbyte2をSEEK、SENSE DRIVE STATUS、
READ DATAへ恒久伝播し、ドライブ別のシーク・モータ状態を保持する。

行き止まりは、前周からの`FILES "B:"`構文エラーに加え、上記第1介入の空振り、
および初回`conform_l3.sh`で日本語ラベル中の`/`を一時ファイル名へ使ったため期待値
故障注入が実行不能になったこと（解析結果自体には影響なし）。後者はscenario名を
ファイル名に使うよう修正した。初回はdrive1画面期待値も未登録だったためrc=1で、
実測署名を固定後に再検証する。

## 公式環境での検証結果

オーケストレータが公式環境で`tools/conform_l3.sh`を実走し、rc=0を確認した。
出力中のNG行3件はいずれも故意に壊したfixtureを検出した陽性対照である。
`tools/compare_l3_entry_fdc.py`へ差件数集計を追加した後の再実走でも、既存判定は
維持された。

同じくオーケストレータが公式環境変数を設定し、`tools/run_all_selftests.sh`を
`LC_ALL=C`と`LC_ALL=ja_JP.UTF-8`の両方で実走した。両ロケールともrc=0で、
37項目すべてOK、NG 0、SKIP 0、Traceback 0だった。この実走では
`conform_l3.sh`と`verify_drive_byte2_attribution.sh`の本体も実行されている。
