## 3. 判定に数えない観察（次の追補の材料）

以下は事前登録の判定規則の外で読んだものであり、本稿の結論ではない。

- **解釈（FDC の C/H）は、P1 によらず `0x17, 0x0F` の有無だけで分かれた。** 行2〜5 の分類は K-00 と K-01、K-F0 と K-F1 で
  それぞれ完全に同じだった。事前登録の見立て H-A（§0）と同じ形。
- **P1 は成否に効いた。** P1=0x00 の腕では、公式 sub は行ごとに READ DATA を18回発行し（内部9回×main 側の再試行2回）、
  結果ステータスはすべて異常終了＋End of Cylinder だった。P1=0x01 の腕では READ DATA は1回・正常終了。
  **トラック0（行1・6）でも P1=0x00 は失敗した。** 診断（2026-09-29）で見た「P1=0x00 で失敗」がトラックによらないことになる。
- **K-M1 は `split_by_drive`**: `0x17, 0x01` のあと、ドライブ1の行（2・5）は logical、ドライブ2の行（3・4）は cylinder。
  §8 の副次の記録どおり「2バイト目のビット0がドライブ1」と記録する（副次なので総合判定に入れない）。
- 事前送信 `0x17, x` のあと、次の要求までに sub の `OUT $FD` は0件だった（全腕）。**`0x17` に応答は無い**。
- 自作 sub での試走では `0x17` を送る腕の行1が崩れたが、公式 sub では崩れなかった（`agree`）。自作 sub が 1.36節の
  「`0x17` 長さ7」の表どおりに `0x17,0x0F` と後続の `0x02` 要求を連結して読むことと整合する。

## 4. 何が悪かったか（事前登録の欠陥）

対照（行1・6）は「読み経路が生きていること」を示すために置いたが、条件に**成否**を含めたため、
主問（解釈）とは別の軸である P1 の効果（成否）で対照が崩れた。**対照が確かめるべきものは「行が分類できること」
（READ DATA が発行され、FDC の引数が取れること）であり、成功ではなかった。** P1 が成否に効く可能性は、
診断で「P1=0x00 で失敗、0x01 で成功」を見ていたのに、事前登録の対照の定義へ反映しなかった。
