# m7fh: TC入力をFDC_IN_7へ集約し、8段の正常終了を±0バイトで得た

実施日: 2026-09-03

## 位置づけ

本稿は`m7ff`で事前登録した軸C1'（`FDC_IN_7`先頭へのTC入力集約）の実測結果である。
`m7fg`で容量の合否条件（条件4）を訂正した後の測定であり、条件4の判定は
「使用量 ≤ 2048」ではなく、`build()`の`SystemExit`の有無で行っている。
軸C1'は事前登録どおり実装・測定した。合格条件は`m7ff`の五条件から変更していない。

## 条件4（訂正後の基準）

`m7fg`の訂正を反映し、条件4の判定には使用量の数値比較を使っていない。判定は
`build()`が8構成 × `PC88_BULK_READ_INTERVENTION_LIMIT`=1〜4の全32通りで
`SystemExit`を出さずに成功することだけを基準にした。

全32通りで`SystemExit`は0件だった。参考として使用量（LIMIT=4）も記録する。
default 2042 / break_write_ack 2045 / break_response 2046 / inject_spurious 2045 /
restore_length6 2050 / no_disk_wait 2047 / fast_no_disk 2045 /
force_post_bulk_active 2042。**全32通りで、軸C1'の使用量はベースラインと完全一致した。**
共通入口で+2、WRITE呼び出し元で-2という正味0バイトの予想が的中している。条件4=yes。

## 陽性対照

1. **コード使用量とSHA-256。** 自作サブROMのSHA-256は、ベースライン
   `233ac03b0b684842f7ff489f5a029553f2aecbe212fd96885dc462dd526f235c`、軸C1'
   `179e93ebd43696597a25040af6864b5fb758ec1a67dc4796a265da30c1354efa`で異なった。
   使用量は両方2042で±0だった。**使用量が±0でもSHA-256が変われば注入は届いている**
   ことを示す（8192バイト固定長ROMのファイルサイズ差を指標に使わないのは`m7fe`の訂正
   どおり）。
2. **iolog上のTC位置。** TC入力（`IN $F8`）は、WRITE・単発READ・バルクREADの
   3経路すべてで、結果7件を読む直前に1件ずつ現れた。**WRITE経路は8/8コマンドで
   1件のまま**であり、集約前後でTCが2件へ増えていない（呼び出し元の単独TCを削除し、
   `FDC_IN_7`側の1件へ置き換わっただけであることを確認した）。単発READ・バルクREADでも
   結果7件の直前に1件ずつ現れ、段30はデータ相を持たないため、追加TCは結果7件の後に
   現れた（`m7fe`で記録済みの既知の形と一致）。3経路すべてへ注入が届いたことを確認した。

この二点を確認した上で、以下のREAD外形の変化とWRITE外形の不変を結果として扱う。

## 条件5（WRITE経路の不変）

`tools/analyze_write_path.py`でベースラインと軸C1'を比較し、FDCコマンド124件、
コマンド種別内訳、結果バイト数分布、WRITE DATAのデータ部位置対応（余り0×8件、
不一致0件）、書き込み系の初出フレーム（882・84番目）まで完全一致した。
`tools/conform_l3.sh`の適合条件5（書き込みストリームが期待値と一致: 件数8・
2112バイト・SHA-256）もOKだった。条件5=yes。

| 条件 | 結果 |

読み替えていない。

## 採用

合格条件とは別に、事前登録した採用可否の基準（軸C1と同じREAD観測結果を正味0バイトで
得たか、かつ条件4・5を満たしたか）に照らすと、条件4=yes、条件5=yes、READの観測結果は
軸C1と段ごとに完全一致した。**採用条件を満たしたので採用した。**

採用理由は、規則を1箇所（`FDC_IN_7`先頭）へ集約した実装が、軸C1と同じ観測結果を
正味±0バイトで得たことである。規則そのものはWRITE経路が元々持っていた「結果7件直前に
TC入力1件」であり、変えていない。今回変えたのはその規則を書く位置（3箇所の個別実装から
1箇所の共通入口へ）だけである。

## 言えること / 言えないこと

言えること:

- データ相を持つ8段は、TC入力の位置を`FDC_IN_7`へ集約しても、個別実装（軸C1）と
  同じ形で`END OF CYLINDER`から正常終了へ変化した。
- 集約はWRITE経路の発行I/O列を変えず、TCの件数・位置ともにベースラインと完全一致した。
- コード使用量は全32ビルド構成でベースラインと完全一致し、正味0バイトの予想が的中した。

言えないこと:

- **段30の`NO DATA`・`WRONG CYLINDER`の原因は決まらない。** 段30にはデータ相が無く、
  `m7ex`は直前のSEEK（段27）に差が無いと記録している。この不変を媒体状態、先行コマンド、
  TC以外の要因のどれかへ帰属しない。
- 公式READ側のTC位置は未測定である。
- 8段の変化がEOTの問題を解消したのかどうかは分からない。EOTは今回動かしていない。
