## 記述（判定ではない）

**言えること:**

- **要求の入口を変えても、K（対象の数）・L（run長）・M（多重度）は
  1つも動かなかった。**
- **同じ命令を2回打つと、すべての量がちょうど2倍になる**（run 24本・
  FDC 288・READ 216・エラー 216・SEEK 24）。**それでもKは3のまま**で、
  **記号の種類も3種**——**同じ3対象をもう一度たどっている。**
  **1回の要求で扱われる対象が3で、2回打てば2エピソードになる。**
- **`m7jq`の数字は完全に再現した**（E1がD3とも一致）。器具を直しただけで、
  測っている中身は変わっていない。
- 内側9・外側4は、**ディスク側5軸に続いて入口3種でも動かなかった。**

**言えないこと:**

- **「9と4と3は入口と無関係である」とは言えない。** 見たのは3つの入口だけ
  である。
- **とくにE1とE2はFDC側の指標が1つも違わない。** `LOAD`も`FILES`も、
  **同じ下位処理（B:のディレクトリ読み出し）に落ちているだけかもしれない。**
  **「別の命令を試した」ことが「別の経路を試した」ことを意味するとは
  限らない。** 画面署名が違うので**打鍵は届いている**が、届いた先が同じ処理
  である可能性は排除していない。
- **Kが3だったことから、対象の総数や順序の規則を導かない。**
- **「4は再試行の外側の上限」「9はリトライの上限回数」とは断定しない。**
- **画面署名が違うことは「打鍵が届いた」ことしか言わない。** 画面の中身に
  ついては何も言っていない（本文は見ていない）。
- **セクタ番号・シリンダ値・画面本文は出していない。**
- 自作ディスクは公式と形が違う。条件O・A:=`disk#8`固定という1つの使い方
  しか見ていない。

| 稿 | 分かったこと |

| `m7jm` | 窓は打ち切っていない。記号列はFDC活動の全体 |
| `m7jo` | 失敗の原因を変えても二段構造は記号列まで同一 |
| **本稿** | **要求の入口を変えても、3も9も4も動かない** |

**振った軸は合計8つ**（セクタ数・シリンダ・ヘッド・セクタ番号の起点・
失敗の原因・打鍵の命令・打鍵の回数・実行量）。**そのどれもが3・9・4を
動かしていない。** ただし**動かしたのはすべてゲストの外側**（ディスクと
打鍵）である。

## 次に何を測れば絞れるか

1. **実装側の軸へ移る。** このプロジェクトには既に**混成ROM（条件M）と
   故障注入の枠組み**がある（`build_mixed_rom`・`--break-drive-selector`など)。
   **自作の側を変えて3・9・4が動くなら、その量がどこで決まっているかに
   近づける。**
2. **E1とE2が同じ下位処理に落ちている疑いを潰す。** 入口が違っても
   FDC側が完全一致するなら、**入口の違いは合流している**可能性が高い。
   合流点より手前で分かれる指標（main→subの要求列など）を見る。
3. 3・9・4のうち**どれか1つだけが動く条件**を探す。3つが常に一緒に不変な
   ままだと、別々の機構なのか1つの機構なのかが区別できない。
