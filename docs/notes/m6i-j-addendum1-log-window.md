# m6i-j 追補1 — 入出力ログの開始フレームを打鍵の開始に揃える

記録日: 2026-09-29  
状態: **測定前**（有効な測定はまだ無い）

## 1. これまでの起動

- 1回目（器具 `96c3f2c`）: 結果ファイルを作業先の外に指定して `gate_failed result_outside_work`（公式ROM起動0）。
- 2回目: 公式ROM起動1回（J-D1-S-N の1走目）で、解析器の関門 `transfer_count`（main の `OUT $FD` と sub の `IN $FC` の件数の全数一致）で `gate_failed`。
  ドライバの理由欄は、解析器側の同名の例外クラスのため `GateError` としか出なかった。
- 診断（公式ROM起動3回、いずれも J-D1-S-N の1走目、件数とフレームだけを出力）: main の送信 2189 件、sub の受信 2146 件で、
  **入出力ログの最初のイベントがフレーム1872**、送受信はすべてフレーム1872〜2000に入っていた。

## 2. 原因

器具は入出力ログの開始を `TYPE_FRAME + 8 × 打鍵数`（打鍵が全部入り終わるころの見積もり）にしていた。`SAVE` はその見積もりより前に動き出しており、
やりとりの先頭がログから欠けたので、送受信の件数が合わなかったと読める。事前登録 §3 の全数対応は、ログがやりとり全体を含む前提で書いてあり、この前提を器具が満たしていなかった。

## 3. 変更

- 入出力ログの開始フレームを **`TYPE_FRAME`（打鍵の開始）** にする。打鍵そのものは main↔sub のやりとりを起こさない（打鍵前の `CLS` 基準の後、`SAVE` の RETURN までディスク要求は無い）ので、
  この区間のやりとりは `SAVE` のものだけになる。打鍵の区間にやりとりがあれば、それも全数対応の対象に入れる（除外しない）。
- ドライバの理由欄に、解析器側の関門名もそのまま出す（`analyze_m6ij` の `GateError` の文言）。
- 事前登録のほかの項目（腕・候補・判定・関門）は変えない。器具のハッシュを含む凍結値は作り直す。
