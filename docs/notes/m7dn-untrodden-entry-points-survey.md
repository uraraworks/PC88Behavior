# m7dn: 未踏の需要入口サーベイ

実施日: 2026-08-28

**本稿は調査ノートであり、測定ノートではない。** 新しい測定・実装は行っていない。
既存の改訂履歴・`docs/notes/`・N88-BASICのマニュアル由来の言語仕様知識だけを根拠に、
「次にどの需要入口を踏むべきか」を検討した。公式ROM・公式ディスクは開いていない。

## 1. 既踏の需要入口（棚卸し）

`docs/spec/l3-subrom.md` の改訂履歴と該当ノートから、公式環境（または公式main+
自作subの混成）で到達を実測した需要入口を列挙する。

**件数**: 需要入口として到達確認したものは diskA起動を含めて14件（`docs/spec/l3-subrom.md`
2455行目付近が同じ数え方をしている）。うち BSAVE・BLOAD・ランダムアクセスPUT/GET の
3件は改訂履歴の版番号が振られておらず、コミットメッセージとノートにのみ結果がある
（`docs/spec/l3-subrom.md` の改訂表には未反映）。これは仕様書側の記載漏れの可能性があり、
別途指摘する価値はあるが本稿の主題ではないため深追いしない。

## 2. 未踏の候補（マニュアル由来の言語仕様知識から列挙）

N88-BASICのディスク関連命令・機能のうち、上記いずれの実測でも打鍵した記録が
見当たらないものを、思いつく限り挙げる。

1. **CHAIN**（他プログラムをロードして実行、変数を保持するモードあり）
2. **COPY**（ディスク間・ファイルのコピー命令。N88-BASICにファイルコピー命令が
   あるかはバージョン依存の可能性があり要確認）
3. **OPEN のAPPENDモード**（既存シーケンシャルファイルの末尾追記）
4. **複数ファイル同時オープン**（例: #1と#2を同時にOPENし、交互に読み書き）
5. **CLOSE**（個別ファイル番号指定 / 引数なし全ファイル一括）の挙動差
6. **LOF・LOC・EOF**（ファイル関数。長さ・現在位置・終端判定）
7. **ドライブいっぱいの状態でのSAVE（ディスクフル）エラー**
8. **ディレクトリを多数のファイルで埋めた状態でのFILES / SAVE**（ディレクトリが
   複数セクタに拡張される境界）
9. **KILLの対象ファイル不在エラー**（既踏のKILLは存在ファイル前提の可能性が高い）
10. **LOAD・SAVEのプロテクトオプション（","R"などの保護フラグ）**
11. **DSKF**（空き容量取得関数。マニュアル索引に存在するとm7cwが記録している）
12. **B:ドライブへの正常な書き込み系操作**（SAVE・BSAVE・PUT等。B:は第77〜80版で
    FILES＝読み取り系のみ確認、書き込み系unit伝播は78〜80版の恒久実装で汎用化
    されているが、書き込み系入口そのものでのB:実測は無い）

## 3. それぞれの評価（新しい経路を踏む見込み）

第87版の教訓——「入口名が違っても256バイト単位の汎用読み書き経路は同じなら
測る価値は低い」——を物差しにする。加えて、BSAVE（`main IN $FC` 7976件、
既存経路8222件と不一致）とランダムアクセス（9788件、双方と不一致）が
**実際に別の足跡を示した**という実績があるため、「粒度・アクセス単位が
これまでと違う」入口ほど価値が高いと判断する材料が増えている。

- **CHAIN**: マニュアル仕様上はLOAD相当の読み込み＋実行制御であり、
  RUN"file"/MERGEが既存LOADと1バイトも違わなかった（第87版）ことから、
  読み込み経路自体は同じ256バイト単位の汎用ロードを通る可能性が高い。
  **価値は低い。**
- **COPY**: N88-BASICにファイルコピーの直接命令があるか自体が不確実
  （バージョン差の可能性）。存在すれば「読み＋書きが1コマンド内で連続する」
  という新しい制御構造（バッファ使い回し、同時オープン相当）を踏む可能性があり
  価値は中程度だが、まず構文確認（マニュアル参照）が要る。
- **OPEN APPENDモード**: 「シーケンシャルファイル出力・入力」は既踏（第75版）
  だが、OUTPUTは新規作成、APPENDは既存ファイルの末尾検索＋追記という点で
  ディレクトリエントリの再利用とファイル末尾（EOFセクタ）の扱いが異なりうる。
  **価値は中程度。**
- **複数ファイル同時オープン**: これまでの全実測は単一ファイルの開閉で完結して
  いる（m7ct・m7cuも1ファイルずつ）。ディレクトリ検索・バッファ管理が
  ファイル数ぶん並行する状態は、これまでのどの入口も踏んでいない制御構造。
  **価値は高い。** タスク文が挙げる「複数ファイル同時」の候補そのもの。
- **CLOSE個別/一括**: 既踏の全入口はプログラム終了やコマンド完了に伴う暗黙の
  クローズを踏んでいる可能性が高いが、明示的なCLOSE、特に複数ファイルを
  一括CLOSEする経路は単独では踏んでいない。単体では複数ファイルオープンと
  セットでないと新規性が薄い。**単独では価値は低い（複数ファイルとセットなら中）。**
- **LOF・LOC・EOF**: ファイル関数はメモリ上のファイル制御ブロックを参照する
  可能性が高く、ディスクI/O自体を新たに発行しない（FDCコマンドを踏まない）
  可能性が高い。**価値は低い。**
- **ディスクフルエラー**: エラー系はこれまで4種（ライトプロテクト・
  媒体未挿入・規則生成媒体・削除済みLOAD）を踏んでいるが、いずれも
  「読めない/書けない」の入口側の理由であり、「書き込み処理を実際に
  最後まで実行してディレクトリ更新の段階で容量不足に気づく」経路は
  未踏。ディレクトリ・FAT相当の更新シーケンスに新しい分岐がある可能性があり
  **価値は中〜高**だが、使い捨て複製を確実に満杯にする準備の手間が大きい。
- **ディレクトリ拡張境界（多数ファイルでのFILES/SAVE）**: これまでの実測は
  すべて少数ファイル（1〜数個）構成であり、ディレクトリが複数セクタにまたがる
  状態を意図的に作った実測はない。**価値は高い**（タスク文の「ディレクトリ更新」
  「シーク境界」に直接該当）。ただし何ファイルで境界を超えるかはマニュアルからは
  分からず、公式環境での探索的な作業が要る。
- **KILL不在ファイルエラー**: エラー応答の一種としては新しいが、第81〜86版で
  すでにno_disk/unreadable_diskのエラー交換構造（応答プロトコル・待ち構造）を
  深く掘り下げ済みであり、「ディレクトリを検索して見つからない」だけなら
  既存のディレクトリ読み取り経路の範囲内で完結する見込みが高い。**価値は低い。**
- **LOAD/SAVEの保護フラグ**: 保護ビットの読み書きだけで、データ転送経路自体は
  既踏のSAVE/LOADと同一と見込まれる。**価値は低い。**
- **DSKF**: マニュアル索引にはあるが、ディスクの空き容量計算はディレクトリ/FAT
  相当の情報から算出するだけで、新規のFDCコマンド発行を伴わない可能性が高い
  （BASIC内部で保持している値を返すだけの可能性もある）。**価値は低い。**
- **B:への書き込み系入口の直接実測**: 第78〜80版でbyte2 unit伝播を
  「共通SEEK入口・SENSE DRIVE STATUS入口」から恒久化済みとあり、読み取り系
  （READ DATA）と書き込み系（WRITE DATA）が同じ共通入口を通る設計である
  可能性が高い。**価値は低い**（第80版が「正常B:はFDC種別79件・main・画面も
  全長一致」まで確認済みで、機構的にも既に説明がついている）。

## 4. 推薦

**複数ファイル同時オープン（#1と#2を同時にOPENして交互に読み書きし、
両方をCLOSEする）を次に踏むことを推薦する。**

理由:
- これまでの14入口（+BSAVE/BLOAD/ランダムアクセスの3件）はすべて「1回に1ファイル」
  という制御構造の範囲に収まっており、ディレクトリ検索・ファイル制御ブロックの
  同時保持・バッファの取り合いという、質的に異なる制御構造を一度も通していない。
  第3節で見たとおり、これまで新しい足跡が出たのは「粒度が違う」入口（BSAVE・
  ランダムアクセス）だった。複数ファイル同時オープンは粒度ではなく**同時実行数**
  という別の軸で未踏であり、経路が違う可能性を積極的に疑う根拠がある。
- 到達条件の設計がしやすい（既存のPOKE/自己検査マーカー方式をそのまま複数ファイル分
  用意すればよく、m7ct/m7cuの型を流用できる）。

次点として、**ディレクトリ拡張境界（ディレクトリが複数セクタへまたがるだけの
ファイル数でFILES/SAVEを実行）**も価値は高いが、「何ファイルで境界を超えるか」が
事前に分からず、公式環境上での探索的な準備コストが複数ファイル同時オープンより
大きいため、2番目の候補とする。

その他（CHAIN、CLOSE単独、LOF/LOC/EOF、KILL不在エラー、保護フラグ、DSKF、
B:書き込み系の直接実測、COPY）は上記の理由により当面見送るのが妥当と判断した。
特にCHAIN・LOF/LOC/EOF・保護フラグ・DSKF・B:書き込み系は「既踏の経路の外側の
薄いラッパにすぎない」可能性が高く、COPYはBASICのバージョンでの命令有無の確認が
先に要る。
