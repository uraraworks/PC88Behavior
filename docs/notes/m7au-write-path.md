# m7au: 書き込み経路（SAVE）の構造を実測 — 末尾256バイトがそのままFDCへ流れる

測定日: 2026-08-18

## 情報境界

公式ROM一式・公式ディスク（diskA）を**実行して**測定した。読んでいない。
**原本ディスクには書かせていない**——使い捨ての複製を作り、複製側だけ
D88ヘッダのライトプロテクト（offset 0x1A）を外した（`tools/measure.sh` と
同じ手順）。生ログはリポジトリ外（セッションのスクラップパッド）に置き、
リポジトリには入れていない。本ノートに載せる数値は**件数・バイト数・
位置**だけで、値は1バイトも含まない。

## 0. なぜ今か

`docs/PLAN.md` の旧方針が「書き込み経路（SAVE）は読み出し系が5635件へ
到達してから着手する」としており、m7aq でその前提を満たした。

## 1. 新しい解析器が要った理由

既存の `analyze_exchange14_read_rules.py` の `commands()` は、コマンドの
パラメータ列の後に来るのが**結果フェーズ（IN）**である前提で書かれている。
READ系はデータも結果もINなので通るが、**WRITE系はデータフェーズがOUT**
なので、データ部の1バイト目を次のコマンド語と読み違える。実際、素朴に
数えると `0x1f×1238` のような、公開コマンド表と噛み合わない分布が出る。

`tools/analyze_write_path.py` を新設した。**方向の切り替わりでフェーズを
切る**（コマンド語→パラメータn→[方向が変わるまでがデータ部]→[反対方向が
結果フェーズ]）。

selftest `tools/analyze_write_path_selftest.sh` で検出力を確認してから
結論を書いた（合成フィクスチャのみ・公式データ不使用）:

- WRITE(データ部256)+READ(263 IN)+SPECIFY の合成ログを期待どおり分解する
- **陽性対照**: データ部を255に削ると **255** と報告する（256を決め打ちで
  返しているのではないことの確認）
- **陽性対照**: 伏せ字ログでは「解析不可」と言う（黙って0件にしない）

## 2. 結果 — ライトプロテクトの有無だけで書き込みが出る/出ない

同じ打鍵列（`10 PRINT "T"` → `SAVE"TMPQ88"` → …）・同じディスクで、
複製のライトプロテクトを外すかどうかだけを変えた。

| 条件 | FDCコマンド総数 | `WRITE DATA` | sub 総IO |
|---|---:|---:|---:|
| 外さない（`measure_suite.sh` の d2-save 相当） | 108 | **0 件** | 100962 |
| 外す（d3-diskwrite 相当） | 221 | **15 件** | 148627 |

これで仕様書3節の未確定「**なぜd2-save条件では書き込みバーストが一度も
観測されなかったか**」に答えが出た——**プロトコル上の謎ではなく、測定条件
だった**（d2-save は `--disk-writable` を付けていない）。

## 3. `WRITE DATA` の形は完全に一様

15件すべてが パラメータ**8バイト** / データ部**256バイト** / 結果**7バイト**。
例外なし。1回の `SAVE` は **8セクタ + 7セクタの2グループ**として現れた
（frame 913〜925、1066〜1076）。

## 4. データ境界の確定 — 受信列の末尾ちょうど256バイト

各 `WRITE DATA` のデータ部256バイトが、**直前にsubが受信した列
（`sub IN $FC`）のどの位置に現れるか**を全数で調べた（値は出さず、位置だけ）。

**15/15で一致、しかも「受信列の末尾からの余り」は全件0。**

つまり受信列は「制御バイト …… データ256バイト」という並びで終わり、
**subは受け取ったバイトを加工せずそのままFDCのデータフェーズへ流す**。
1.30節（交換#4応答は直前READのデータ部を同じ位置順で送る）の逆向きの
対応であり、**読みも書きも「素通し」という同じ形**をしている。

これで仕様書3節の未確定「制御バイトとデータ本体の境界を切り分けられ
なかった」も解消した。

1セクタあたりの受信バイト数は **262（制御6 + データ256）が基本**で、
**各グループの最後の2回だけ268（制御12）**だった。この差の意味は未確定
として3節に残す（推測で埋めない）。

## 5. 実装はまだしていない（意図的）

コミット規律「測定コミットが実装コミットに先行する」に従い、本サイクルは
測定・仕様化までで止める。実装要件は仕様書6節7項に書いた:

- `WRITE DATA` をパラメータ8・データ部256・結果7で発行する
- **データ部は直前受信列の末尾256バイトをそのまま流す**（加工しない）
- 制御バイトの内訳は未確定なので、そこを推測で埋めた実装を書かない
