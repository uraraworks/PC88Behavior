# SAVE ,A の hybrid 失敗の診断 — 読み要求 0x02 が公式 sub で別の場所を読む

記録日: 2026-09-29
状態: **診断（事前登録なし）。仕様書へは書かない。** 次の測定（m6i-k）の事前登録の材料。

## 1. 症状

ブランチ wip/save-ascii-2（41487e1）の `tools/conform_save.sh hybrid` で J-1 が NG。媒体は1バイトも変わらない。
入出力ログで見ると、自作 main は `SAVE` の最初に書き込み禁止の印を読む
（ドライブ2、論理トラック 37=(18,1)、R=13）要求を送るが、以後 WRITE に進まない。

## 2. 観察（自作 main の送信と、公式 sub の FDC コマンドの先頭・引数のみ）

- 自作 main の要求: `02, 00, 01, 25, 0D`（位置1=0x00、位置2=ドライブ1(=ドライブ2)、論理トラック 0x25、R）。
- 公式 sub の FDC: SEEK をシリンダ 0x25 へ、READ DATA の引数は C=0x25・H=0・R=0x0D・EOT=0x10。
  結果ステータスは異常終了＋End of Cylinder で、同じ READ を9回繰り返した。
  **公式 sub は論理トラック 37 を C=18・H=1 ではなく C=37・H=0 として扱った。**
- 比較のため公式ROM一式で同じ打鍵の `SAVE` を走らせると、公式 main の読み要求は `02, 01, 01, 25, R`
  （位置1=0x01。この走の読み要求 10件すべて）で、公式 sub は SEEK 0x12、READ の引数 C=0x12・H=1 を出した。
- 診断として自作 main の位置1だけを 0x01 にしても（コミットしていない）、公式 sub は依然 C=0x25・H=0 を読んだ。
  **位置1だけでは説明できない。**
- 公式一式では、起動直後・最初の `0x02` より前に、main が `0x17, 0x0F` の2バイトを送っている。
  hybrid（自作 main）は起動時に sub へ何も送らない（最初の送信は SAVE の読み要求）。

## 3. 見立て（未検証）

- H-A: 公式 sub は、`0x17, 0x0F` を受け取るまで（あるいは受け取らない限り）読み要求の論理トラックを
  シリンダとして扱う。`0x0F` はドライブ4台ぶんのマスクに見える。
- H-B: 位置1は公式 main では常に 0x01（件数の可能性）。自作 main は 0x00。
- トラック0では「論理トラック=シリンダ、H=0」と「C*2+H」が一致するので、起動時の既知READ
  （論理トラック0）では差が出ない。FILES・LOAD も自作 main＋公式 sub の組み合わせでは同じ問題を
  持つはずだが、`conform_files.sh`・`conform_load.sh` には hybrid の腕が無く、検出されていなかった。
- 仕様書 l3-subrom 1.36節の表の「`0x17` 長さ7」は、`0x17, 0x0F` と後続の `0x02` 要求（長さ5）が
  1つの受信 run に連結されたものの可能性がある（位置が合う: 7 = 2 + 5）。

## 4. 次

m6i-k として事前登録する: 公式 sub に対し、自作 main から (a) `0x17, 0x0F` の有無 × (b) 位置1 = 0x00/0x01 の
2×2 で、論理トラック奇数（H=1）の座標を読ませ、公式 sub の SEEK・READ の C/H を判定する。
期待値は試験媒体の像から決め、FDC 引数の C/H だけを見る（データ部は件数のみ）。
