# m7hh: disk#8に大きいファイルを作り連続READが現れるかを測る — 結果

実施日: 2026-09-04

## 位置づけ

[m7hg](m7hg-disk8-large-file-consecutive-read-preregistration.md)が事前
登録した測定の結果である。事前登録は測定開始前に単独コミット
（`e48ea03`）してあり、本稿では事前登録の条件・水準・判定規則を後から
動かしていない。`src/`・`tools/`は本稿では変更していない。

**結論を先に書く: 段階1で測定できた2水準（S・M）は、いずれも連続READ
DATAが1件も現れなかった（run長はすべて1）。最大水準（L）は容量超過で
書込みが完了せず、測定できなかった。段階1で連続READが現れなかった
ため、段階2（位置を振る）は事前登録どおり実施していない。主判定は
Q4（測定できた範囲では、データ量では連続READの出現を説明できない）
である。**

## 陽性対照（最初に書く）

1. `build_mixed_rom ... --break-drive-selector`（1.46節の既存故障注入）
   を条件M・`FILES 2`・B:=本稿のS水準複製（書込み後の`disk#8`由来
   複製）で比較した。`tools/compare_l3_entry_fdc.py --after-frame 700`
   のunit/head差件数は**21件**（0件より大きい）。
2. `tools/analyze_error_exchange_shape_selftest.sh`は全4項目OK・rc=0。

**両方通ったため、以降の解釈を行う。**

## 判定規則をベースラインへ当てる（合格条件2）

条件O（公式一式）で、S水準の読み出し測定（後述）を独立2回行い、
`tools/compare_l3_entry_fdc.py --list-all-stages`（`--after-frame`無し）
で比較した。

| 比較 | 結果 |
|---|---|
| O run1 vs O run2（全段、SEEKシリンダ一致/不一致） | 完全一致（不一致0件） |
| FDCコマンド種別列（`command_names`、prefix一致） | 83件全長一致 |
| FDCポート値列 | 16081件全長一致（値そのものは比較のみで出力していない） |

**判定規則は偽陽性を作らないことを確認した。**

## 段階0: 打鍵列の長さ

書込み・読み出しプログラム（`RUN\n`込み）の打鍵数を投入前に機械的に
数えた。書込み: S=121、M=133、L=134（いずれも512未満）。読み出し:
全水準共通で100（512未満）。実測でも「打鍵列が長すぎる」は全試行で
0件だった。水準間で打鍵数がほぼ一定という事前の見積もり
（数値リテラルの桁数差のみ）どおりだった。**通った。**

## 構文の妥当性（段階1項目に相当）

事前登録した`OPEN "2:<ファイル名>" FOR OUTPUT AS #1`/`OPEN "2:<ファイル
名>" FOR INPUT AS #1`という現代形式の構文で実測した。**古い形式
`OPEN "O",#1,"<ファイル名>"`を最初に試したところ`Syntax error`になった
ため、`m7gk`が言語リファレンスから特定していた現代形式（`FOR OUTPUT
AS #1`）に切り替えたところ動作した。** この切替は事前登録した「構文の
妥当性そのものは段階1で実測して確認する」という手続きの範囲内であり、
水準・意図（3水準・大きさで振る）は変えていない。実際に動いたことを
記録する（隠さず記載する手順逸脱として扱う）。

## 段階1: 大きさを変える（結果）

各水準、B:の独立した複製（A:は`disk#8`起動用の固定複製、書込みなし）
に対して測定した。

### 水準S（N=5）

| 項目 | 結果 |
|---|---|
| 書込み | rc=0、`reached(['run'])`=真、1回で成功 |
| 大きさの独立確認 | 未書込み参照複製との`FILES 2`署名比較で`mismatch`
  （行数不変、文字数増加、SHA相違） |
| 読み出し | rc=0、`reached(['run'])`=真、1回で成功 |
| 連続READ構造 | 総READ DATA=17件、run長列=`[1]×17`
  （**連続READが1件も現れなかった**） |
| 決定論性 | 独立2回目も完全一致（FDCコマンド種別列83件・ポート値列
  16081件とも全長一致） |

### 水準M（N=500）

| 項目 | 結果 |
|---|---|
| 書込み | rc=0、`reached(['run'])`=真、1回で成功 |
| 大きさの独立確認 | S水準の書込み後複製との`FILES 2`署名比較で
  `mismatch`（行数不変、文字数がさらに増加、SHA相違） |
| 読み出し | rc=0、`reached(['run'])`=真、1回で成功 |

| 決定論性 | 独立2回目も完全一致（FDCコマンド種別列411件・ポート値列
  39123件とも全長一致） |

### 水準L（N=4000）— 容量超過

| 項目 | 結果 |
|---|---|
| 書込み | rc=0（プロセス自体は正常終了）だが、画面表示が`Disk full`
  というBASICのエラーで打ち切られた。`reached(['run'])`=偽 |

**事前登録どおり「超えた」として記録し、代替の水準を追加していない。**
M水準（N=500、書込み後の空き容量表示は本稿では値として記録しない）から
L水準（N=4000）への間で容量を使い切ったことがわかる。読み出し測定・
大きさの独立確認・連続READ構造の記述はL水準では実施していない
（未完了の書込みを解釈対象にしない）。

## 段階2: 位置を振る

**未実施。** 事前登録のとおり、段階1で連続READが1件も現れなかった
（S・Mともrun長がすべて1）ため、段階2（位置を振る測定）は実施していない。

## `general_read_request`を通るか（合格条件4）

段階1で唯一有効な測定ができた水準のうち、READ DATA件数が最も多い
M水準の読み出し打鍵について、条件M（`build_mixed_rom`混成、
`--probe-site general_read_request --probe-mode cyl`）と探針なし基準を、
同じ書込み済み複製に対して`--list-all-stages`で比較した。

**28段あるSEEK段のうち17段でシリンダ指定が不一致になった**
（探針ありでは、この打鍵が最終的に`File not found`という別のエラーに
分岐したが、これは探針がシリンダを意図的に狂わせた結果であり、
`general_read_request`を通る過程で分岐が生じたことの追加証拠でもある）。
**この打鍵での読み出し区間は`general_read_request`を通る。通った。**

## 決定論性

- S水準・M水準ともに読み出し測定を独立2回行い、FDCコマンド種別列・
  ポート値列とも全長完全一致を確認した（上表のとおり）。
- L水準は書込み自体が完了しなかったため、決定論性の対象外。
- 陽性対照・`general_read_request`探針測定は1回のみ（事前登録の合格
  条件に決定論性を要求されていない項目であり、m7hb〜m7hfも同様の扱い）。

## 元ディスクを壊さない

全測定で使ったのは`tools/stage_disk_by_digest.sh`が作る使い捨て複製の
みである。`disk#8`元ファイルへの書込みコマンド（`--save-to-disk-image`）
は、すべて複製先パスに対してのみ指定した（`--disk`/`--disk2`とも
scratchpad配下の複製パスのみを渡し、元ファイルパスを直接渡したことは
一度もない）。全測定終了後に元ファイルのSHA-256を計算し、
`tools/stage_disk_by_digest.sh`が複製専用に読み取り専用の`cp`しか行わ
ないこと（スクリプト本文で確認済み）と矛盾しないことを確認した
（`ORIG_UNCHANGED=yes`。値そのものは記録しない）。

## Q1〜Q5の判定

- **Q1**（件数が大きさに追随） / **Q2**（変わらない）: 段階1で連続READ
  が1件も現れなかったため、判定対象外（追随する/しないを議論する前提
  である「連続READが現れる」こと自体が成立しなかった）。
- **Q3**（段階2で位置により変わる）: 段階2は未実施のため判定対象外。
- **Q4**（どの水準でも現れない）: **成立。採用（測定できた範囲では）。**
  S水準（総READ DATA17件）・M水準（総READ DATA99件、`disk#10`の
  `FILES 2`が見せた108件に迫る規模）のいずれも、run長がすべて1で、
  連続READ DATAは1件も現れなかった。
- **Q5**（陽性対照不通過／ファイルを作れない）: 陽性対照は通ったが、
  **L水準に限っては「容量超過で作れなかった」という意味でQ5の一部に
  該当する。** ただしS・M水準は正常に作成・測定できているため、
  実験全体がQ5で無効になるわけではない。

**主判定はQ4（S・M水準の範囲で）。ただしL水準は容量超過により未測定
のまま残った（決まらなかった）。**

## 言えること・言えないこと

**言えること:**

- `disk#8`は`OPEN "2:<ファイル名>" FOR OUTPUT AS #1`/`FOR INPUT AS #1`と
  `FOR`〜`NEXT`ループによる打鍵数を増やさない書込み・読み出しが機能する
  （`m7hd`が`SAVE`の打鍵数上限で断念した課題を、ランタイムループで
  回避できることを実証した）。
- `disk#8`上に、`FILES`署名比較で独立に確認できるだけの大きさの違いを
  持つ2つのファイル（S水準・M水準、総READ DATA数で17件・99件）を作り、
  それぞれの本体を`OPEN...FOR INPUT`/`LINE INPUT#`/`EOF`ループで最後
  まで読ませたが、**いずれもREAD DATAはすべて単発（run長1）で、
  一度も連続しなかった。** M水準の99件という規模は、`disk#10`の
  `FILES 2`が見せた108件（`m7hb`）に近い件数でありながら、run構造は
  対照的（disk#10は12コマンド周期で連続、本稿は全件が個別SEEK）である。
- この打鍵（M水準の読み出し）が`general_read_request`を通ることを
  `--probe-site general_read_request --probe-mode cyl`で確認した
  （28段中17段でシリンダ不一致）。
- L水準（N=4000）は`disk#8`の複製上で容量を使い切り、`Disk full`という
  BASICのエラーで書込みが打ち切られることを確認した。

**言えないこと:**

- L水準（大きい方の極値）でどうなるかは、容量超過のため測定できて
  いない。**「データ量をさらに増やせば連続READが現れる」可能性を、
  本稿は否定も肯定もできていない。** S・M水準という、本稿が容量内で
  作れた範囲でのみ「現れない」と言える。
- `OPEN...FOR INPUT`によるファイル本体読み出し経路と、`m7hb`が連続READ
  を確認した`FILES 2`（ディレクトリ読み出し）経路が、**同じ低レベル
  読み出し機構を共有しているのかどうかは、本稿では確認していない。**
  もし別経路であれば、そもそも本稀の実験が問うている「サイズ」は
  disk#10の現象と無関係な変数だった可能性がある。
- `disk#10`の`FILES 2`が見せた連続READが、実は「ファイルの中身の
  大きさ」ではなく「ディレクトリに登録されているファイルの**本数**」
  （＝ディレクトリ領域自体の大きさ）に由来する可能性は、本稿では
  切り分けていない（本稿はファイル1本を大きくしただけで、ファイル数
  は水準間で1本のまま変えていない）。

## 次に何を測れば絞れるか

1. **ディレクトリ本数を振る実験に切り替える。** `disk#10`の連続READは
   `FILES 2`（ディレクトリ読み出し）で観測されたものであり、本稿の
   結果は「ファイル本体の大きさ」という変数がその現象を再現しない
   ことを示した。`m7he`が用意していた位置制御ループ（`DF01`〜のダミー
   ファイルを多数作る）を使い、`disk#8`上にディレクトリがほぼ埋まる
   本数のファイルを作ってから`FILES 2`を打鍵し、連続READが現れるかを
   見る価値が高い——これは「大きさ」ではなく「ファイル数（ディレクトリ
   領域の大きさ）」という、本稿がまだ切り分けていない変数を直接試す
   ことになる。
2. **`OPEN...FOR INPUT`経路と`FILES`経路が同じ下位関数を通るかを
   `--probe-site`で比較する。** 現在`general_read_request`という同じ
   探針地点を両経路で確認できているのは本稿と`m7gz`/`m7hf`だけであり、
   両者が実際に同じ呼び出し文脈（同じ段数・同じ周期を作る条件）を
   通るのか、探針を使った構造比較でさらに絞れる可能性がある。
3. **容量に余裕を残したより大きい水準を新たに事前登録する。** 本稿の
   L水準（N=4000）は今回の`disk#8`複製の空き容量を明らかに超えていた。
   M水準（N=500）と実際に容量超過した点の間（例えばN=1000前後）を
   狙う新水準を、次回の事前登録で改めて固定すれば、「データ量を今回
   より増やしても現れない」という主張の範囲をさらに広げられる。

## 開示

構文の切替（`OPEN "O",#1,...`形式から`OPEN "..." FOR OUTPUT AS #1`
形式への変更）が1回発生した。これは事前登録の「構文の妥当性そのものは
段階1で実測して確認する」という想定内の手順であり、水準・意図は変えて
いない（上記「構文の妥当性」節に記載）。L水準の`Disk full`は隠さず
記録した（事前登録どおり、代替水準を追加せず「超えた」とだけ扱った）。
それ以外の手順逸脱・汚染は無かった。測定はすべてフォアグラウンドで
実行し、測定中に`git stash`・ブランチ切替・ファイル編集は行っていない。
無言でSKIPした分岐は無い。

## 情報境界

公式ROM・公式ディスクのバイト列、公式ROMの逆アセンブル、`private/`の
内容は読んでいない・出力していない。記録したのは公開μPD765コマンド
種別名、件数、run長の並び（値そのものではなく連続長）、画面出力の
行数・文字数・SHA-256の一致/不一致の別、rc、自作ファイル名

（`Disk full`・`Ok`・`Syntax error`という診断メッセージ文字列を除く。
これらはBASIC言語仕様の一部として公開されている診断メッセージであり、
ROM内部構造や逆アセンブル結果ではない）・シリンダ値・PCN値・
画面表示された空き容量等の実際のバイト数は表示も転記もしていない
（本文中でも一切の具体的なバイト数を書いていない）。資料は参照していない（`OPEN...FOR OUTPUT/INPUT AS`
構文は`m7gk`が既に(a)言語仕様の範囲と確認済みの資料に基づいており、
本稿は`refs-nec-manuals-2026-09-04.md`の判定係手順を追加では使って
いない）。生ログ・ディスク複製はリポジトリ外
（`/private/tmp/claude-501/.../scratchpad/m7hg/`）に置き、コミットしない。
