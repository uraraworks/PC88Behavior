# B48: main の `IN $FC` が、サブの出した列のどの位置を読んでいるかを値なしで測る — 結果

記録日: 2026-11-01
規則: [b48-g1-fc-position-preregistration.md](b48-g1-fc-position-preregistration.md) どおり。測定はクラウドの実行環境で OO・SS 各 2 走。ドライバのコミット指定の誤りで 1 回止まり、直して走った。関門 6 項目はすべて通った。値は記録していない。記録は `measurements/b48-g1-fc-position.txt`。

## 結果

- 位置の差（公式−自作）は番号 0 から 76570 まで 4 で、**番号 76571 で 5 に変わる**。そのあとは 5 のままである
- 自作は番号 76570 と 76571 で、サブの同じ `OUT $FD` を読む（`sk=76828` が 2 回）。列全体でこの 1 回だけである
- 公式には同じ `OUT` を 2 回読むところが無い

## 記録の読み方の注意

ツールの `issuer` は、事前登録の「サブの `OUT` の発行元」ではなく **main の `IN $FC` の発行元の `PC`** を出していた（`0x8000` 未満を `rom` と出す）。したがって `A047`・`A055` は main のコードの番地で、`rom` の行は main の `0x8000` 未満を指す。公式の main の ROM への横断は B1 の 8 件から増えていないので（B34）、ここは ROM とは限らない。ROM かどうかは言わない。

## 読み方（推定）

main は番号 76569 まで `A047`・`A055` で読み、76570 から `0x8000` 未満の別のコードで読む。その切り替わりの直後に、自作では main がサブより先に読み、**1 バイトずれる**。B30 の 257 件の違いは、このずれで説明できる。サブが違う値を出していたのではない。

なぜ先に読めるのかを、B49 で切り替わりの前後の出来事の順で測る。
