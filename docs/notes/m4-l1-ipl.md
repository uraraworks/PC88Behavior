# M4 順序付き I/O 記録

測定日: 2026-08-07
対象: 公式 N88-BASIC ROM（32KB, メイン CPU）と DISK.ROM（2KB, サブ CPU）。
測定結果の実体: `measurements/l1-boot-io*.txt` / `measurements/l1-boot-io*.iolog.txt`
（順序・ポート番号・値・発行元PC・フレーム番号のみ。ROM の内容は含まない）

---

## 何を作ったか

M4（L1 IPL のクリーンルーム実装）の完了条件は「自作 IPL でブートシーケンスが
公式版と**同じ I/O 書き込み列**を出す」こと。ところが M2/M3 までの
`q88h_trace`（有無フラグ）と `q88h_trap`（トラップ発火のイベント記録）は、
どちらも「触れたか」の集合か、限定番地への入口記録であって、**I/O 全体の
発生順**は採っていなかった。順序が無いと、この完了条件を判定する物差しが
そもそも存在しない。実装より先にこの物差しを作った（PLAN 第6節が戒める
「実装したから動くはず」を避けるため）。

作ったもの:

- `tools/harness/core/q88h_iolog.c` / `.h` — 順序付き I/O 記録のコア側実装。
  main/sub 別バッファ、既定 off、1CPUあたり最大 2^20 件（取りこぼしは
  `n_dropped` で必ず報告、上書きしない）。
- `tools/patches/0005-io-log.patch` — `pc88main.c` / `pc88sub.c` の
  `q88h_io_in`/`q88h_io_out`（サブ側は `q88h_sub_io_in`/`q88h_sub_io_out`）に
  記録呼び出しを追加。`Makefile.common` にソース追加。
- フロントエンド (`tools/harness/frontend/main.c`) に `--io-log <file>` を追加。
  毎フレーム、走らせる前にコア側へ現在のフレーム番号を渡す。
  出力は main 節・sub 節を明確に分けて書く（後述）。
- `tools/harness/iolog_selftest.sh` — 公式 ROM 不要の自己検証。
  `make_test_rom.py` を拡張し、既知番地 (0x1200) で RAM (0xC000) に
  既知値 0x5A を置いてから本編 (0x1234) の OUT/IN へ進むようにした
  （既存の `--expect-exec` 検査が使う番地は動かしていない）。
- `tools/measure.sh` に `--io-log` 用の redact/sed 経路を追加（後述の失敗参照）。
- `tools/setup_harness.sh` の疎通試験に `iolog_selftest.sh` を追加。

## メインとサブを混ぜない理由

PC-88 のメインCPUとサブCPU（ディスク側）は別々のZ80として並行に走る。
それぞれの `q88h_iolog` は自分のCPUの中でだけ `seq`（通し番号）が意味を持ち、
CPUをまたいで比較しても実際の前後関係にはならない。1本の列に混ぜて出すと
「起きた順」だと誤解されるので、出力は CPU ごとに節を分けている
（コード側のコメントと `--io-log` 出力のヘッダの両方に書いた）。

## 起きた I/O 書き込み列（要約）

条件は `tools/measure.sh` に `--io-log` を渡して測定。
`docs/notes/m3-demand-profile.md` の「アイドル起動は60フレームで飽和する」を
踏まえ、まず 60 フレームで測り、120 フレームでも先頭が同一であることを
確認してから採用した。

- **`l1-boot-io`**（ディスク無し・入力無し・60フレーム）
  main: 8123件（取りこぼし0）／ sub: 0件
  120フレームで再測すると総イベント数は 9340件に増えるが、
  **先頭 8123件はバイト単位で完全一致**した。つまり I/O の発生順そのものは
  60フレームの時点で確定している。増分は起動完了後もキーボード走査などの
  アイドルポーリングが続くために生じるもので、M3 が見た「触れた番地」が
  60フレームで飽和するのとは別の指標だと分かった（触れた番地は増えないが、
  同じ番地へのアクセス回数は増え続ける）。
  目立つポート: `IN 0040` が最多（7012回、タイマ/CRTC系のポーリングと思われる）。
  次いで `OUT 0071`（124回）、`OUT 0032`（87回）、`OUT 0050`（76回）。

- **`l1-boot-io-disk`**（`N88_FE.D88` 挿入・60フレーム）
  main: 51737件（取りこぼし0）／ sub: 70543件（取りこぼし0）。
  ディスク無し条件と比べて2桁増えている。目立つポートは
  `IN 00FE`（22110回）・`OUT 00FF`（11476回）・`IN 00FC`（5626回）・
  `IN 00FD`（4847回）——いずれもディスクコントローラ関連のポート番号帯
  （0xFC-0xFF）に集中しており、ディスクの有無で経路が大きく変わることが
  数値の上でも確認できた。`IN 0040` は共通して最多クラス（7012回）で残る。

## 気づいた限界

- **`PC_prev` は使えなかった。** `z80.h` のコメントには「直前の PC (モニタ用)」
  とあり、実際には CPU セットアップ時に一度 `PC` を写すだけで、以後は
  z80.c 側で更新されていない（実測でも常に 0000 だった）。代わりに
  `PC.W - 2` から発行元PCを逆算している。理由は `z80-code.h` /
  `z80-codeED.h` を実測で確認したとおり、IN/OUT系の命令は（即値ポート形式
  もCレジスタ経由形式も）どちらも命令長2バイトで、io_read/io_write を
  呼ぶ時点で PC がちょうど2進んでいるため。これは既存の `q88h_trap` が
  `pc_prev` を「JP/JR で来た場合の手掛かり」として使っている箇所にも
  同じ限界がある可能性がある（今回は未検証。別途確認が要る）。
- **`--io-log` の出力ファイルは `measure.sh` の redact/sed の対象外だった。**
  実際に走らせて `core` 行に絶対パス（`$HOME` を含む）が残っていることを
  確認してから `tools/measure.sh` に `--io-log` 用の同等処理を足した
  （教訓: 「新しい出力ファイルにも効いているか確認すること」は
  一度サボると即座に事故る）。
- I/O イベント総数はアイドルポーリングのぶんだけ際限なく増える指標なので、
  「何フレーム測れば十分か」を総数の収束で判断できない。今回は
  「先頭が一致するか」で確認した。L1 IPL の完了判定でも、末尾ではなく
  先頭（起動直後の書き込み列）を比較対象にするべきだと分かった。

## わざと壊して確認した結果

`iolog_selftest.sh` の検査ロジックを採用する前に、以下2通りで実際に壊し、
落ちることを確認した（確認後は元に戻した）。

1. **記録を無効化する**——`pc88main.c` の `q88h_io_in`/`q88h_io_out` の
   `if( l->enabled )` を `if( 0 && l->enabled )` に変えてビルドし直し、
   `iolog_selftest.sh` を実行 → `main 節に OUT/IN の行が見つからない` で
   **NG（終了コード1）**になることを確認。元に戻して再実行し、合格に戻ることも確認。
2. **順序判定を反転させる**——スクリプト中の `[ "$OUT_SEQ" -ge "$IN_SEQ" ]`
   を `-le` に変えて実行 → `OUT(seq=1) が IN(seq=2) より先に記録されていない`
   で **NG（終了コード1）**になることを確認。元に戻して合格に戻ることも確認。
