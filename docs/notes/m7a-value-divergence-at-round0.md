# m7a: ラウンド#0からの値不一致と分岐点259

測定日: 2026-08-13

## 1. 目的と情報境界

m6y/m6zに続き、main側の構造的分岐点259がどこで生じた状態差を
表面化させたものかを、値そのものを表示せずに切り分ける。

`private/`配下は開かず、測定ツールへの入力パスとしてのみ扱った。
`$FB`/`$FC`/`$FD`の値は比較器の内部だけで処理し、標準出力・記録・
報告には出していない。本稿に載せるのは件数、一致プレフィックス長、
不一致位置（index/frame/seq）および構造上の位置だけである。

## 2. 追加した比較器と検出力

- `tools/cmp_fdc_sectors.py`: sub側のFDCコマンドフェーズを公開仕様の
  コマンド長に従って追跡し、読み取りセクタ座標列を内部で抽出・比較する。
  出力は抽出件数、一致長、最初の不一致位置・種別、分岐点259との前後だけ。
- `tools/cmp_fdc_sectors_selftest.sh`: 既知入力から非0件を抽出できることと、
  意図的に1座標だけ変えた入力の不一致位置を検出できることを確認する。
- `tools/cmp_io.py`: `--base-before-seq`/`--target-before-seq`による区間限定と、
  値を比較しながら位置情報だけを出す`--location-only`を追加した。
- `tools/cmp_io_selftest.sh`: 区間内の1件を意図的に変更し、一致長と不一致位置を
  検出しながら値を出力しないことを確認する項目を追加した。

両selftestは通過し、`tools/run_all_selftests.sh`にもセクタ座標比較のselftestを
登録した。解析器が対象を1件も検出していないのに結論へ使う、m6sと同型の
失敗を避けるため、非0件抽出と意図的不一致の検出を必須の前提とした。

## 3. 測定結果

### 3.1 セクタ座標列

| 項目 | 結果 |
|---|---:|
| 基準側抽出件数 | 9 |
| 混成側抽出件数 | 61 |
| 座標列の一致プレフィックス長 | 0 |
| 最初の不一致位置 | 1 |
| 基準側位置 | frame 35 / seq 318 |
| 混成側位置 | frame 28 / seq 369 |
| 不一致種別 | 座標が違う |
| 分岐点259との位置関係 | 後 |

最初のセクタ座標不一致を含むバルク転送はframe 42〜62にあり、分岐点259は
frame 34である。したがって座標列の不一致は実在するが、時間順序上、259の
原因にはなり得ない。

### 3.2 分岐直前のバンク選択と判断材料

畳み込み後index 250〜258に対応する生イベントについて、redact済みログで
値が保持されているバンク切替・システム制御ポートだけを比較した。
分岐直前のバンク選択値、制御出力、およびmainが読み取った判断材料は、
基準側と混成側ですべて一致した。値自体は本稿には掲載しない。

よって、259直前にmainが異なるバンクを選んだこと、または直前の入力が異なり
mainの判断を変えたことでは、別コードへ進んだ現象を説明できない。

### 3.3 分岐点259より前のmain受信値列

`cmp_io.py`の区間限定・位置のみモードで、分岐前にmainが受け取った
データポートの値列を比較した。

| ポート/向き | 基準側件数 | 混成側件数 | 値一致プレフィックス長 | 最初の不一致位置 | 構造上の位置 |
|---|---:|---:|---:|---|---|
| `$FD IN` | 0 | 0 | 0 | なし | 該当なし |
| `$FC IN` | 3 | 3 | 0 | index 1（基準 frame 20 / seq 7113、混成 frame 13 / seq 7115） | ラウンド#0 |

核心は、259より前の受信データが`$FC IN`の3件だけであり、その1件目、
すなわち起動シーケンスのラウンド#0から既に値が食い違っていたことである。
分岐点259は原因の局所ではなく、ラウンド#0から蓄積したmain内部状態の差が
制御フロー上に初めて表面化した地点と位置づけ直す。

## 4. 誤推論の記録と訂正

私はm6zの後、259直後に始まるバルク転送へ着目し、「バルク転送でmainが
受け取る内容が原因」と推論した。しかしセクタ座標の最初の不一致は259より
後であり、この推論は外れた。

m6y/m6zで「分岐点の直前にあるものを原因と読むのは相関にすぎない」と
学んだ直後にもかかわらず、今度は分岐点直後のバルク転送を原因と読む同じ型の
誤りを繰り返した。時間順序を先に確認せず、局所的な近接を因果とみなした点を
隠さず記録する。

また、m6yの「値の飽和」は全256通りを調べた結果ではない。単一ビット、
単一ビット反転、下位4ビットを0に固定した上位4ビット全組み合わせまでで、
上位ビットが立った状態に下位4ビットを組み合わせた多数の値は未探索である。
したがって「値軸が259に無関係」とした一般化も広すぎた。

## 5. 次の一手

1. **応答値の全256通りスキャン**: FDC実発行、1バイト応答、ウェイト無しの
   構造を固定し、送出値だけを自作側の全256定数へ差し替える。正解が単一の
   定数として存在するなら、構造的一致プレフィックスは258を超えるはずである。
2. **最適化指標を`$FC IN`の値一致プレフィックス長へ変更**: 構造的一致
   プレフィックスはラウンド#0〜#2の3件をまとめてしか評価できない。
   値一致長なら0→1→2→3件と、各ラウンドを1件ずつ攻略できる。ただし3件が
   互いに異なる値を要求する場合、全ラウンドへ単一の定数を送るスキャンでは
   原理的に解けない。その場合はラウンド別に送出源を切り分ける必要がある。

構造的一致プレフィックスは最終的な制御フロー確認に残しつつ、次の探索では
値を表示しない`--location-only`の一致長を局所的な最適化指標として併用する。
