# B27: G1 の直後の 2 バイトの前後の、ポートの並びを値を見ずに見る — 結果

記録日: 2026-11-01
規則: [b27-g1-two-bytes-window-preregistration.md](b27-g1-two-bytes-window-preregistration.md) どおり。測定はクラウドの実行環境で 5f6d1b4。対照は通過。全行はライブラリの `b27-g1/`（1 本 48 万バイトなのでリポジトリへは入れない。値は含まない）。

## 分かったこと

窓の中の順番は OO・SS とも次のとおり。

1. データの最後の `IN $FC`
2. `OUT $FD` が 688 バイト（`0x0C` の 5＋本体 680、`0x0D` の 3 と数が合う）
3. サブの RAM 上のコードが FDC を動かす（`IN/OUT $FA/$FB` が 10289 件）
4. `OUT $FD` が残り 21 バイト。サブは ROM 側で受け取る
5. **ここで OO はすぐ 1 バイト送る。SS は ROM 側で FDC を動かしてから 1 バイト送る**（FDC の出入り 7 件）

## 訂正

B22 の `index=3840`（0 始まり）は、B25 の表の番号 3841（1 始まり）に当たる。**違う 2 バイトは 3840 バイトのデータの直後ではなく、この 21 バイトの要求の応答である。** B25 の「1 バイト目はデータの直後」という読みと、B22 の `request=02` の表示は誤りだった。B26 が余分のバイトを見なかったことと矛盾しない。

## 読み方（推定）

最後の 21 バイトは要求を含み、サブがメモリの内容を返している可能性がある。[B24](b24-sub-request-15-results.md) で測った `0x15` はこの形である。自作サブは `0x15` を実装していないので、別の処理へ入っているように見える。

仕様は `docs/spec/l3-subrom.md` 1.36c 節（第228版）。実装して G1 で確かめる。
