# M6m `$FE` 待ち判定のビット構造解析

測定日: 2026-08-12
対象: 混成ROM（公式main一式＋自作サブROM）を公式環境で実走したところ、
main が `IN $FE pc=37DC`（1.13節「SEND前」）で1,041,413回スピンし、
sub が `IN $FE pc=00CC`（1.17節「アイドル待ち」）で1,048,477回スピンして
デッドロックした。診断（メインセッション）は「sub のアイドル判別が
`$FE == 0x08` の完全一致になっているため、main が『送るぞ』と示している
状態を認識できない。1.15節の遷移表を見ると意味を持つビットの隣で別の
ビットが動いている。ビット単位の判定にすべき」という見立てだった。
本稿はこの見立てを**推測のまま採用せず**、既存の伏せ字済みログを
再解析して裏を取る。

**追加測定は行っていない。** 既存の `measurements/m6c-sub-{d0-boot,
d1-files,d2-save,d5-seqfile}.iolog.txt.gz` と `measurements/m6g-d0-boot-
run{1,2}.iolog.txt.gz` を再解析した。

解析器: `tools/analyze_sub_fe.py`（第10版で拡張）。`--cpu {main,sub}` を
追加し、従来 sub 専用だった集計ロジック（pc別グループ化・スピン単位の
遷移集計・前後の`OUT $FF`文脈対応付け）を main 側にも同じ関数で適用
できるようにした（二重実装しない）。あわせて `bit_significance()` を
追加した：あるpcの待ちループについて、**「スピンの最終読み取り値
（exit値）の集合」と「スピン継続中に読まれた値（loop継続値）の集合」を
ビットごとに比較し、そのビットの値が exit側で単一の値に揃い、かつ
loop継続側にその値を持つものが一つも無ければ、そのビット単独で
exit/loop継続を分離できる**、という機械的な判定を行う。値の意味を
先に決め打ちせず、観測された値の集合演算だけで判定する。

再実行方法:

```
python3 tools/analyze_sub_fe.py cross --cpu main \
    --iolog measurements/m6c-sub-d0-boot.iolog.txt.gz \
            measurements/m6c-sub-d1-files.iolog.txt.gz \
            measurements/m6c-sub-d2-save.iolog.txt.gz \
            measurements/m6c-sub-d5-seqfile.iolog.txt.gz \
    --label d0-boot d1-files d2-save d5-seqfile \
    --out /tmp/main-fe-cross.txt

python3 tools/analyze_sub_fe.py cross --cpu sub \
    --iolog (同上4本) --label (同上) --out /tmp/sub-fe-cross.txt
```

## 1. 決定論性・検出力の確認

- **決定論性**: `measurements/m6g-d0-boot-run{1,2}.iolog.txt.gz`
  （同一シナリオの2回の独立測定、`m6-conformance.md`で決定論性確認済み）に
  対し `--cpu main` と `--cpu sub` それぞれで `analyze_sub_fe.py` を実行し、
  出力を diff した。**ラベル行以外は1バイトも違わず一致した**（run1/run2）。
- **検出力**: `tools/analyze_sub_fe_selftest.sh` に項目a2を追加した。
  合成フィクスチャで `bit_significance()` が (i) 正常データで正しい単一
  ビットを報告すること、(ii) exit値の集合に loop継続値と同じビットパターン
  を持つ孤立した値を1件混入させると「単一ビットでは説明がつかない」に
  正しく変わること、の両方を確認した。全項目OK（`tools/run_all_selftests.sh`
  に既存登録済み、変更不要）。

## 2. main視点 1.13節4ループの効いているビット

d0-boot/d1-files/d2-save/d5-seqfile 4条件横断、`--cpu main` の結果。

| ループ(1.13節) | 遷移語彙(全条件共通) | 効いているビット | 例外 |
|---|---|---|---|
| SEND前(37DC相当) | `80->80`, `80->82` | **bit1=1** で exit（4条件・0例外） | 無し |
| SEND後(37FF相当) | `12->12`, `12->14` | **bit2=1**（同じ強さでbit1=0も単独で成立） | d5-seqfileのみ3/1273件（0.24%） |
| RECV前(3853相当) | `20->20`, `20->21` | **bit0=1** | d1/d2/d5で2〜4件/1179〜1974件（0.15〜0.20%）、d0-bootは0件 |
| RECV後(386F相当) | `41->40` | **bit0=0** | 全条件で1〜4件/526〜1975件（0.16〜0.20%） |

**SEND前(37DC)は4条件・全サンプルで例外0。** これは「main が既に
`bit1=1`（0x02, 単発で即通過）の状態で待ちループに入る場合」と
「`bit1=0`（0x80）から`bit1=1`（0x82）へ遷移する場合」の両方を含めても
exit値の集合が常に`{0x02, 0x82}`（どちらもbit1=1）、loop継続値の集合が
常に`{0x80}`（bit1=0）だったことによる。**上位ビット(0x80)は
SEND前ループの exit/loop継続 判定には無関係であり、この点は今回の診断
（「意味を持つビットの隣で別のビットが動いている」）と整合する。**

**RECV前/RECV後の例外（0.15〜0.25%）は原因未特定。** サンプル数に
比例して増える（d0-boot<d1-files<d2-save<d5-seqfileの順に件数もサンプル数も
増える）ことから、本解析手法がスピンを「同一pcの連続するIN $FE読み取り」
としてグループ化する際、境界が異なる2つの実際の待ちループ呼び出しを
1つのスピンとして誤って結合してしまうアーティファクトの可能性が高いと
見ているが、**確定はできない**。3節「未確定」に記載する。

**SEND後(37FF)は`bit1=0`と`bit2=1`が同格で単独説明可能**（entry値は
常に`0x12`固定、exit値は`0x14`固定〈d5-seqfileの3件を除く〉であり、
`0x12→0x14`はbit1をクリアしbit2をセットする1組の変化のため、
どちらのビット単体を見ても分離できる）。1.13節の記述
（「12⇄14はbit1↔bit2の入れ替わり」）と一致する。実装では`bit2=1`を
採用する（他の3ループがすべて「意味のあるビットがセットされたら抜ける」
という一貫した形なので、極性を揃える）。

## 3. sub視点 1.15節RECV/SENDプリミティブの効いているビット

同4条件横断、`--cpu sub` の結果（1.15節の手順番号に対応するpcを、
件数・遷移語彙・前後の`OUT $FF`文脈から同定した。PCの具体値は1.14節の
方針にならい本文には書かず、このノートにのみ残す）。

| プリミティブ・手順 | 遷移語彙 | 効いているビット | 例外 |
|---|---|---|---|
| RECV手順2（相手のデータ準備待ち、`20→21`/`28→21`） | `20->20,20->21,28->21,28->28` | **bit0=1** | 4条件とも0件 |
| RECV手順6（相手の受理解除待ち、`41→40`） | `41->40` | **bit0=0** | 4条件とも0件 |
| SEND手順1（相手の受信準備待ち、`00→02`。起動時専用サイトと定常サイトの両方で確認） | `00->02` | **bit1=1** | 4条件とも0件 |
| SEND手順4（相手の受理確認待ち、`12⇄14`。起動時専用サイトと定常サイトの両方で確認） | `12->12,12->14` | **bit1=0／bit2=1**（同格） | 4条件とも0件 |

**sub側の4プリミティブ待ちはmain側と異なり、観測範囲で例外が一件も無い。**
main側RECV前/後の0.15〜0.25%の例外は、少なくとも sub 側の解析条件・
解析手法だけに起因するものではない（同じ手法・同じログを解析している）。

## 4. SEND手順6（「境界的な待ち」、1.15節）の再評価

1.15節はSEND手順6（`IN $FE`でステータス相当を読む）を「単一の固定値
読みではなく、次に続く手順により抜け値が変わる境界的な待ち」と記述し、
確定した目標値を示していなかった。現在の実装（`make_subrom.py`）は
ここを待たない単発読み捨てにしている。

該当pc（起動時専用サイト、n=13/25/…と小さい）を単体で見ると
`bit_significance()`は「単一ビットでは説明がつかない」と判定するが、
これは**ログ末尾での打ち切りにより1件だけ不完全なスピンが混入した
アーティファクト**である（n=13中12件はexit=0x08、残り1件はスピンが
`(無し)`＝直後に別イベントが続かないまま記録が終わっている）。

**定常状態の同型サイト（4条件・件数1024〜3840、起動時専用サイトとは
別のPC）を見ると、`bit2=0`が exit を単独で説明する（4条件とも0例外）。**
exit値は`0x02`と`0x08`の2種類に分かれる（loop継続値は`0x04`固定）が、
どちらもbit2=0という共通点を持ち、bit2=1の`0x04`（loop継続）とは
分離できる。**「境界的」に見えたのは、待ちの終了条件（bit2クリア）と、
終了後に何をするか（bit1/bit3を見た後続の分岐）という2段階の情報が
1バイトに同居していたためであり、待ちの終了条件そのものは単一ビットで
説明できる。** 1.15節の記述はこの点を訂正する（下記スペック改訂）。

## 5. アイドル判別（1.17節・`make_subrom.py`の`IDLE_DISPATCH`）

### 5.1 `0x08`（RECVへ進む）側: ビット構造まで確定

pc=00CC（アイドル待ち）の4条件横断結果:

```
d0-boot:    n=35  遷移語彙=['00->08','01->08']  効いているビット=bit3=1  例外0
d1-files:   n=66  同上                                              例外0
d2-save:    n=98  同上                                              例外0
d5-seqfile: n=136 同上                                              例外0
```

exit値は常に`0x08`（bit3=1）のみ。entry値は`0x00`または`0x01`
（bit0が不定だが exit/loop継続の分離には無関係）。**旧実装の
`cp_n(0x08)`（完全一致）は、この観測範囲では偶然にも正しい判定を
行っていた**（entry値0x00/0x01はいずれもbit3=0なので、完全一致でも
ビット判定でも同じ結果になる）。しかし**この一致は今回のログの
entry値のバリエーションがたまたま狭かったことに依存しており、
bit3以外のビット（例えばbit0以外の未観測ビット）が変化した場合、
完全一致判定は`0x08`以外の値（例:`0x09`,`0x0C`）を「まだアイドル」と
誤認し続ける。** これが診断の見立て（「意味を持つビットの隣で別の
ビットが動いている」）どおりの脆弱性であり、確定した`bit3=1`判定への
置き換えで解消できる。

### 5.2 `0x02`（SENDへ進む）側: 依然として未確定、ただし同一慣行の裏付けが増えた

pc=00CC自体では、4条件のどのスピンも`0x02`（bit1=1）へ到達した事例が
無い（1.17節第8版の追試と同じ結果）。**この点は変わらず未確定のまま
残る。**

ただし、4節で確認した「SEND手順6の定常サイト」（pc=07A5相当）は、
**bit2=0への到達後、実際に`bit1=1`(`0x02`)へ分岐する事例を508件、
`bit3=1`(`0x08`)へ分岐する事例を4件観測しており（4条件合計）、
`bit1=1`の直後には必ず`OUT $FF`に`0x09`（SEND開始）が、`bit3=1`の
直後には必ず`0x0B`（RECV開始）が書かれることを確認した。** つまり
「`bit3=1`→次はRECV、`bit1=1`→次はSEND」という対応そのものは、
pc=00CC以外の場所では実際に両方の分岐が観測されており、単なる机上の
類推ではなく**同一サブROM内の別サイトで確認済みの慣行**である。
**それでも、pc=00CC（アイドル待ち本体）でこの分岐が本当に使われて
いるかどうかは、本測定では直接確認できていない。** 3節に「未確定」
として明記する。

## 6. まとめ（実装への反映方針）

| 対象 | 判定 | 確定度 |
|---|---|---|
| main SEND前(37DC) | bit1=1 | 確定（0例外） |
| main SEND後(37FF) | bit2=1（bit1=0も同格） | 確定（d5-seqfileのみ0.24%例外、未解明） |
| main RECV前(3853) | bit0=1 | 確定（0.15〜0.25%例外、未解明） |
| main RECV後(386F) | bit0=0 | 確定（0.16〜0.20%例外、未解明） |
| sub RECV手順2 | bit0=1 | 確定（0例外） |
| sub RECV手順6 | bit0=0 | 確定（0例外） |
| sub SEND手順1 | bit1=1 | 確定（0例外） |
| sub SEND手順4 | bit2=1（bit1=0も同格） | 確定（0例外） |
| sub SEND手順6（境界的な待ち） | bit2=0で待ち終了 | 確定（定常サイトで0例外。起動時専用サイトの見かけの例外はログ打ち切りアーティファクト） |
| アイドル判別→RECV | bit3=1 | 確定（0例外） |
| アイドル判別→SEND | bit1=1 | **未確定のまま**（pc=00CC自体では0件。ただし同一慣行が別サイトで確認済み） |

`src/l3_service/make_subrom.py`は、上記「確定」の行をすべてビット判定に
置き換える。「未確定のまま」の行（アイドル→SEND）は、既存実装がすでに
採用している暫定構造（`0x02`への一致を仮の判別条件とする）を、
判定方式だけビット判定（`bit1=1`）に揃えて維持する——**これは新しい
推測を追加するものではなく、既存の暫定構造（1.17節・3節に明記済み）を
今回確定したビット判定の書式に合わせただけであり、確定度の格上げでは
ない。** コメント・仕様書側の「未確定」表記は維持する。
