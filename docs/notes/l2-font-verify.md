# L2 フォント検証記録

測定日: 2026-08-07
対象: `tools/verify_l2.sh`（`src/l2_font/make_font_rom.py` が生成する実際の FONT.ROM を使う。
公式 ROM は一切使わない）。

## やったこと

`docs/spec/l2-font.md` 第2版 5節②「ROM非保有者でも検証できる条件」の2項目を実行した。

1. **意図した字形が入っていることの検査（二重検査・独立性を実測）**
   - `src/l2_font/make_font_rom.py`（生成器本体）とは別に、
     `tools/l2_verify_independent.py` を用意した。unscii-8.hex のパース、
     8x8 ASCIIアート→バイト列の変換、セミグラフィックのビット→ブロック展開の
     3か所を、それぞれ生成器と異なるロジック（正規表現でなく手動ニブル変換、
     文字グリッド生成でなくビット位置ごとの真偽判定、2段階変換でなく
     1段階の行バイト畳み込み）で独立に実装した。
   - **突き合わせ結果: 4096バイト完全一致。**
   - **独立であることの実測**: `--break-independent-path` で独立実装側の
     ビット順を意図的に反転させて実行し、257バイトの不一致
     （最初の食い違い: オフセット0x050D、生成器=0x30／独立側=0x0C）で
     **検出できることを確認した**（`docs/notes/m4-l1-impl.md` の先例と同じ手順）。
     検出力の無い「同じことを2回書いただけ」の検査でないことを、
     壊して確認する形で示した。

2. **font_mem までの到達確認（`tools/harness/fontsrc_selftest.sh` と同じ仕組み）**
   - 生成した実際の FONT.ROM（合成パターンではなく、unscii-8由来の英数記号＋
     自作ASCIIアートの半角カナ＋ルール生成のセミグラフィックを含む本物）を
     計測ハーネスの `--rom-dir` に置き、`--font-log` で `font_mem` の内容を
     CRC32で照合した。
   - 期待値は FONT.ROM ファイル自身から `zlib.crc32` で計算（ANK面/GRAPH面
     それぞれ2048バイトずつ）。
   - 実測結果: `font_mem ANK = ROM_FILE, CRC32=66E91562`
     （期待値と一致）、`font_mem GRAPH = ROM_FILE, CRC32=7DCDCD7C`
     （期待値と一致）。**外部ファイル(FONT.ROM)の内容が、画面へ出る唯一の
     バッファ(font_mem)まで欠落・混入なく届いていることを実測確認した。**
   - `font_mem2`・`font_mem3` は `l2-font.md` 1節の観測どおり死んだ経路
     （UNAVAILABLE・0埋め）のままで、6節5「今回の適合条件に含めない」の
     方針と一致する。

## やらなかったこと（次のマイルストーンへ持ち越し）

- **「画面に実際の文字を出して目視する」**（5節②の後段、可能ならの位置づけ）。
  `tools/harness/frontend/q88measure --dump-text` はテキストVRAMの文字コードを
  そのまま人間可読化するだけで、フォントのビットパターンとは無関係
  （font_mem を経由しない別経路）。実際に「打鍵→BASICが文字コードをVRAMへ
  書く→dump-textで見える」という形で確認するには L3/L4（BASIC本体・文字出力
  ルーチン）が要るが、今回のマイルストーンの対象外（未実装）。そのため
  今回は font_mem のビットパターン一致（CRC32、上記2）を「画面に出る内容が
  正しい」ことの代替根拠とした。L4着手時に、既知の文字（'A'・'0'・半角カナの
  一部等）を打鍵してVRAM経由で目視確認するテストを追加することが望ましい。
- 3節「合計7箇所のすり替わり経路」の恒久的な解消（`libretro.c` 側ロードの
  一本化）は `docs/notes/m5-fontsrc-selftest.md` が既に記録済みのとおり、
  今回のセッションでも対象外のまま（フォントデータの用意が今回のスコープ）。

## 追記（2026-08-07・別セッション）— 0x7E の修正と、画面ピクセルまでの検証

### 1. `0x7E`（オーバーライン）の代用をやめた

`src/l2_font/make_font_rom.py` の `latin_code_to_unicode()` は、JIS X0201 の
`0x7E`（‾ オーバーライン、U+203E）を、unscii-8.hex に該当コードポイントが
無いという理由で ASCII チルダ（U+007E）で暫定代用していた（第2版執筆時点の
注記）。チルダとオーバーラインは別の文字であり、見た目（波線 vs 横棒1本）も
異なる。

オーバーラインは横棒1本という形そのものが「セルの最上段ラインを点灯させる」
という幾何規則になっているため、セミグラフィック（`semigraphic_glyph`）と
同じ扱いでルールから生成するよう変更した（`overline_glyph()`。unscii由来の
データは使わない）。生成器の `--selftest` と独立実装
（`tools/l2_verify_independent.py` の `independent_overline()`。ASCIIアート
経由ではなく整数演算で直接バイト列を組む、別経路）の両方を追従させ、
`tools/verify_l2.sh` で生成器と独立実装が完全一致することを確認済み。

`0x5C`（円記号）も合わせて確認した。`vendor/unscii/unscii-8.hex` に
`000A5:C3663C183C181800`（U+00A5、円記号のコードポイント）の行が実在する
ことを確認しており、こちらは代用ではなく unscii-8 由来のままで問題ない
（変更なし）。

### 2. 画面ピクセルまでの検証（バッファに届いた ≠ 画面に出た、を埋めた）

上の「やらなかったこと」に書いた宿題——font_mem への到達確認はあっても
「実際に画面へ描画されたピクセル」までは見ていなかった——に対応した。

- **画面スナップショット機能をハーネスに追加**した。上流 QUASI88 の
  `snapshot.c`（`make_snapshot()` + 実際の描画ループと同じ
  `screen-vram*.h` 変換テーブルを使う `VRAM2SCREEN_ALL` 系ルーチン）を
  そのまま利用し、`q88h_snapshot_capture()`（`tools/patches/0009-screenshot.patch`
  で追加する薄いラッパー1関数）経由で 640x400 の R,G,B バイト列を取得できる
  ようにした。フロントエンド `q88measure` に `--screenshot FILE.ppm` を追加し、
  PPM(P6, バイナリ)で書き出す（外部ライブラリ不使用）。
- **自作 IPL に「フォント見本」モードを追加**した
  （`src/l1_ipl/make_ipl_rom.py --font-sample`）。画面ハードウェア初期化の
  直後・割り込み有効化の直前に、テキストVRAM（`F3C8`、80桁×stride120。
  `docs/spec/l1-ipl.md` 第0節・第5d節）へ文字コード `0x20`-`0xFF`（224種）を
  3行ぶん書き込む。`LD (nn),A` のみを使い OUT を一切出さないため、
  付録Aの適合条件（第6節、OUT列比較）には影響しない
  （`build_n88(font_sample=False)` と `build_n88(font_sample=True)` の両方で
  OUT件数=350、`tools/verify_l1.sh` は引き続き合格することを確認済み）。
- **画面比較の検査**（`tools/l2_verify_pixels.py`）を新規に書いた。FONT.ROM
  のビット列から「画面はこう見えるはずだ」という期待ビットマップ
  （先頭3行ぶん、640x60ピクセル）を、コアの `screen-vram*.h` を一切参照しない
  独自ロジックで組み立て、実際のスクリーンショットと二値化した上で突き合わせる。
  `tools/verify_l2.sh` の4節として組み込んだ。
- **実測結果**: `tools/verify_l2.sh` 実行時、実際に生成した FONT.ROM +
  フォント見本 ROM を計測ハーネスで60フレーム走らせ、スクリーンショットを
  取得。先頭3行・640x60ピクセルが期待ビットマップと**完全一致**した
  （`OK: 先頭3行ぶん（640x60ピクセル）がFONT.ROMからの期待どおりに描画
  されている`）。
- **わざと壊した場合の検出**: `tools/l2_verify_pixels.py --break-expected` は
  期待ビットマップの1文字ぶん（セル col=1,row=0）を丸ごとビット反転させてから
  比較する。実行すると `NG: 128 ピクセル不一致（最初の食い違い: x=8 y=0
  セル(col=1,row=0)）`で確実に落ちることを確認した——「生成器が出すグリフを
  1文字だけ潰したら、画面比較が落ちるか」という要求どおりの検出力がある。
- **目視確認**（`shot.png`。1600x1000へ縮小して確認。元は640x400のPPM/PNG）:
  1行目に `!"#$%&'()*+,-./0123456789:;<=>?@ABCDEFGHIJKLMNOPQRSTUVWXYZ[¥]^_`
  、2行目冒頭に小文字 `abcdefghijklmnopqrstuvwxyz{|}‾`（末尾にオーバーライン
  が見える）、その後ろの空白域（0x7F制御コード・0x80-0xA0未決定コード相当）を
  挟んで半角カナ（｡「」､･ｦｧィゥ…ワン゛゜）が3行目にかけて続く。崩れて見える
  文字は無かった。
- **縦2倍・下4ラインの空白の確認**（ピクセル単位）: `'0'`（0x30）のセルを
  1画素ずつ読み出したところ、20ラスタライン中 0-13行目が「1行おきに同一
  パターンが2回連続」（縦2倍）、14-19行目が空白であることを確認した
  （元グリフ8行のうち最終行が元々空白のため12-13行目までが可視、14-15行目は
  グリフ由来の空白、16-19行目がセルの固定空白域）。オーバーライン(`0x7E`)は
  0-1行目のみ点灯（横棒1本が最上段に来ている）で、rule生成どおりに描画されて
  いることをピクセルで確認した。
