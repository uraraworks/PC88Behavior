# ゴール B に着手する前の方針

記録日: 2026-10-24
位置づけ: ゴール B（市販ソフトが動く）の**測定を始める前に**置く方針ノート。
2026-10-20 の合意「ゴール B に着手するときは測定より先に方針ノートを1本書いてコミットする」
に基づく。このノートより前の日付で、ゴール B のための測定コミットは存在しない。

---

## 1. 何をするのか

[PLAN.md](../PLAN.md) 第1節のとおり、**B = A + 入口番地の配置 + 作業域の配置 + データテーブル**。
ゴール A の実装（内部配置は自由）の上に、市販ソフトが直接触る番地だけを公式と同じ場所に寄せる。

ここで新しく生じる問題は1つだけである。**「どの番地が、何をする入口か」をどこから知るか。**
資料に載っている入口番地・作業域番地は CLAUDE.md の表で (b)「ROM 内部の構造」に当たり、読まない。
だから番地は**市販ソフトの振る舞いから自分で測る**。

## 2. 基本の分担 — ゲームは「どこを」、自作プローブは「何を」

番地の出所と働きの出所を分ける。

| 問い | 何で答えるか | 記録に残るもの |
|---|---|---|
| どの番地が要るか（需要） | 市販ソフトを実走させ、ゲーム側コードから ROM 領域へ制御が移った境界を記録 | 飛び先番地・回数・戻り先の有無 |
| その番地は何をするか（働き） | **自作のプローブプログラム**で、こちらが選んだ入力を与えて公式 ROM のその番地を呼び、外部に出る結果を測る | 入力（自作）と出力の対応、そこから起こした規則 |

- **ゲームの実走からは番地しか採らない。** 呼び出し時のレジスタ値・メモリの中身はゲームの
  データ（表示する文字、内部状態）を運ぶ。それを働きの根拠にすると、記録に画面本文や
  ゲームのデータが混ざり、しかも入力を自分で振れないので規則が決まらない。
  需要の発見と働きの測定を分けることで、両方の問題が消える
- **働きは、入力を自分で決められる場面だけで測る。** これは M6/M7 の測定（自作 BASIC
  プログラム・自作器具で公式 ROM を叩く）と同じ型で、すでに規律が通っている経路である
- 番地は「このゲームがこの番地へ飛んだ」という**こちらの観測**から来る。
  第三者の解析を経由しないので、由来の鎖は「公式 ROM → 自分の測定」で閉じる
  （[CLAUDE.md](../../CLAUDE.md)「自分で解析していないから安全」は逆である、の節）

## 3. 測るもの

1. **境界の横断（需要）**: ROM 領域外（RAM 上のゲームのコード）の PC から、ROM 領域への
   CALL / JP / RST / 割り込みベクタ経由の移動。記録するのは
   飛び先番地・横断の種別・回数・RAM へ戻ってきたか。
   M2 のトラップ ROM（[m2-trap-rom.md](m2-trap-rom.md)）と M3 の需要プロファイル
   （[m3-demand-profile.md](m3-demand-profile.md)）が前例で、fetch ラッパに載せる
2. **ROM 領域のデータ読み（需要）**: ゲーム側コードが ROM 領域を**データとして**読んだ番地範囲と回数。
   **値は記録しない**（禁止事項1・4）
3. **ROM と共有する RAM 番地（需要）**: ゲーム側コードが読み書きした RAM 番地のうち、
   ROM 側のコードも読み書きする番地。番地・読み書きの別・回数のみ
4. **入口の働き（自作プローブ）**: 入力レジスタ・入力メモリを自作で与え、
   出力レジスタ・フラグ・入出力ポート・画面（署名で）・メモリの変化を測る

## 4. 記録しないもの

ディスク B（参照用の公式ディスク）と同じ扱いをゲームのディスクにも適用する。

- **ゲームディスクのバイト列**、RAM に読み込まれたゲームのコード・データのバイト列
- **ゲームの画面本文**、スクリーンショット（禁止事項7。比較は署名ツールで）
- **ゲームのタイトル名・メーカー名・ファイル名**。ノート・コミット・ツール出力では
  `G1`, `G2` … の識別子で呼ぶ。識別子と実物の対応表は `private/` にだけ置く。
  実ファイル名が端末に出る経路は m7gp と同じくヘルパで1点に閉じてから実走する
  （[m7gp-disk-name-leak-path-closed.md](m7gp-disk-name-leak-path-closed.md)）
- **ゲーム実走時のレジスタ値・メモリの値**（第2節の理由）
- **ROM 領域から読まれた値**（ゲームが読んだものも、プローブが読んだものも）
- **ROM の内部の実行経路**。働きの測定では、入口に入ってから出るまでの間の内部 PC を
  記録しない。見るのは入口と出口だけにする。内部の呼び出し構造を測ると、
  実装がそれに引きずられて公式の構造をなぞる方向へ寄る

## 5. 線引き — 番地の働きは外部入出力だけで決める

- 働きを決める根拠は第3節4の入出力の対応だけ。資料・解析記事・他のエミュレータの
  ソースコメントに書かれた「その番地は○○ルーチン」は読まない（(b)）
- **メモリの変化は、そのまま出さない。** ROM がメモリへ書いた値には ROM 内部のテーブルや
  バッファ外の内容が混ざりうる（[contamination-2026-09-25](contamination-2026-09-25-fat-buffer-overrun-values.md)）。
  変化した番地の一覧と、介入（入力を振る）に対して値がどう動くかの規則だけを採る。
  値の並びそのものが要るときは、自作の入力から規則で再現できるものに限る
- **データテーブルが要ると分かった場合**（ゲームが ROM 領域を値として読む等）は、
  L2 フォントと同じく、規則か振る舞いから作り直す。作り直せないものは
  「測定では届かない」として記録し、写さない（禁止事項4）
- **番地は需要のあったものだけを置く。** 「公式の配置表を丸ごと再現する」ことはしない。
  置いた番地にはそれぞれ、根拠になったゲーム実走の測定 ID と、働きを決めたプローブの
  測定 ID が付く状態にする。第三者が同じゲームを持っていれば、同じ番地が出ることを再現できる

## 6. この方針の範囲外（別に判断する）

- **公式の内部コード（トークン番号）との互換。** 市販ソフトのうち、BASIC プログラムを
  バイナリ形式で持つものを動かすには要る。ここは権利上の争点の場所なので
  （[l4-token-design.md](l4-token-design.md)）、**このノートでは扱わず、現状の自前トークンを
  変えない。** 必要になったら、測定より先にそれ専用の方針ノートを書き、判断を記録してから進む
- **ゲームのコードの逆アセンブル。** 禁止事項2の対象は公式 ROM だが、ゲームのコードにも
  ROM の使い方の知識（その作者が資料から得たもの）が入っている。読むと第三者の知識を
  経由することになるので、**ゲームのコードも逆アセンブルしない**。境界の観測だけで足りない
  ことが分かった場合は、そのとき別のノートで判断する
- **公開の時期と範囲。** 2026-10-20 の方針どおり公開は急がない。このノート・仕様書・
  自作プローブ・境界の記録（番地と回数のみ）は、最初から公開してよい形で作る

## 7. 着手の順序

1. このノート（方針）のコミット
2. 境界の横断を記録する器具を作り、**ゲームを使わずに自己検査する**。
   自作の試験プログラムから既知の番地へ飛ばし、陽性対照（記録される）・
   陰性対照（ROM 内部どうしの移動は記録されない、ROM 領域外どうしも記録されない）・
   記録に値が出ないことの検査（画面本文の自己検査 `screen_content_leak_selftest.sh` と同型）を通す
3. ゲーム識別子の対応表とディスクのパスを1点で扱うヘルパを用意する
4. `G1` を1本、公式 ROM 上で実走させ、需要（番地の一覧）だけを測る。
   自作 ROM 上でも同じ記録を取り、どこで止まるかを並べる
5. 番地ごとに、プローブの事前登録 → 測定 → `docs/spec/` に仕様 → 実装、の順で進める
   （測定コミットが実装コミットに先行する規律はそのまま）

止まったら、それを根拠に方針を見直す。見直すときは、このノートを書き換えるのではなく
後続のノートを足し、このノートからリンクする。
