# m7bo: 256件後の単発応答を遅らせてもmain分岐は動かなかった

実施日: 2026-08-20

## 情報境界

公式ROM一式・公式diskAは、公式main＋自作subの混成構成で実行した。内容は
読んでおらず、`private/`への`cat`/`xxd`/`od`/`strings`・逆アセンブルは
行っていない。生iologと介入用サブROM生成器は`mktemp -d`で作った
リポジトリ外の一時ディレクトリだけに置き、コミット対象にしていない。
256件のディスク実データは値を出力・記録せず、適合条件1は件数とSHA-256
一致だけで判定した。

混成ROMの構築・測定は`tools/lib_l3_measure.sh`、基準点は
`tools/analyze_post_read_response.py`、パースと畳み込みは既存の
`analyze_main_to_sub.parse_iolog`と`tools/diag_l3_mixed.py`を再利用した。
新しい解析器は作っていない。`tools/harness/romram_selftest.sh`、`src/`、
仕様書、`docs/PLAN.md`には触れていない。

## 仮説と介入

仮説H1は「subの応答が遅く、mainから見た`$FE`状態遷移が遅れることが、
畳み込み後71件目のmain分岐を引き起こす」である。

今回先に実施した水準は次の2つである。

- (a) 現状の自作sub（基準）
- (c) 256件完了後の単発`0x06→0x80`応答経路で、応答送信前に
  `sub IN $FE`を2回追加した一時ROM

介入用生成器は`src/l3_service/make_subrom.py`のリポジトリ外コピーだけを
変更した。生成コードは2048バイトで、既定ROMには影響しない。

最初の試行では1.37節の`0x06→0xC0`経路へ6回追加したが、対象は256件後の
別の`0x06→0x80`経路だったため、区間内`sub IN $FE`が14件のまま変わらず、
介入の空振りとして棄却した。下表の(c)は介入点を対象経路へ訂正した再実走である。

## 結果

| 観測 | (a) 基準 | (c) 遅延 |
|---|---:|---:|
| main分岐位置（畳み込み後） | 71件目 | 71件目 |
| 分岐イベント | `OUT $32` | `OUT $32` |
| 分岐前main生イベント | 79件 | 81件 |
| 適合条件1の件数 | 5635件 | 5635件 |
| 適合条件1のSHA-256 | 一致 | 一致 |
| 区間内`sub IN $FE` | 14件 | 16件 |
| 区間内`sub OUT $FF` | 7件 | 7件 |
| main RECV前`IN $FE` | 4件 | 6件 |

介入により、狙った`sub IN $FE`は**+2件**、相手側mainのRECV前待ちも
**+2件**となった。したがって介入は空振りではない。一方、(a)と(c)の
main側畳み込み列には構造差がなく、71件目もともに`OUT $32`だった。

## 判定・未実施

応答をさらに2ポーリングぶん遅くしても、分岐位置・分岐種別・適合条件1は
動かなかった。したがって、**今回試した遅延幅ではH1棄却の方向**である。
ただし遅延量は1水準だけなので、「いかなるタイミング差も無関係」とまでは
確定しない。

水準(b)（公式と同じ回数まで縮める）は今回は未実施である。待ちを安全に
短縮する介入点を、この2水準の結果から推測で決めない。必要なら次の診断で
独立に扱う。
