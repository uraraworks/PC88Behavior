# m7ao: フェッチ窓の外の見え方を実測で確定、予算超過を確定・部分対処

測定日: 2026-08-17

## 情報境界

公式ROM・公式ディスクは今回一切使っていない。すべて自作の使い捨て
自作ROM（`src/l3_service/make_subrom.py`のAsmを直接操作）と、既存の
自己検証用インフラ（`tools/make_l3_test_main.py`・`tools/make_l3_testdisk.py`。
`tools/verify_l3.sh`が使っているのと同じ、公式ROM不要の合成main
ドライバ・合成ディスク）だけを使って実測した。ハーネス自身のソース
（`tools/patches/`、`vendor/quasi88-libretro`）は公式ROMではなく自作
ハーネス・第三者エミュレータコアであり、クリーンルーム規律上読んでよい
範囲として直接確認した。自作コードのラベル・アドレス・命令サイズは
自作コードの構造情報であり、本ノートに残す。値（公式ディスクの内容）は
一切扱っていない。

## 1. 窓の外の見え方 — 実測で「一様な0xFF埋め」と確定

3種類の使い捨て自作ROMを作った。いずれも通常のリセット処理の代わりに、
先頭で直接`JP <target>`（生バイト`C3, lo, hi`）を発行するだけの最小限の
変更で、それ以外のコード本体（`build_subrom()`の出力）はそのまま使う。

- 陰性対照: `target = BOOT_HANDSHAKE`（0x009B、境界0x0800の内側、
  実在する正常なコード開始点）
- 陽性対照A: `target = 0x0900`（境界の外側）
- 陽性対照B: `target = 0x0850`（境界の外側、Aとは異なる番地）

`tools/verify_l3.sh`と同じ合成main ROM・合成テストディスクで120フレーム
実走し、sub側のPC分布（値ではなく発生順・PC・件数だけ）を比較した。

- **陰性対照（境界の内側）**: 多数の異なるPC（`010D`・`0129`・`001C`・
  `0023`・`029E`・`0015`・`05B4`等）を巡る、通常のsend/recvやり取りに
  見える健全な分布。総イベント数6014件/120フレーム。
- **陽性対照A・B（境界の外側、2つの異なる番地）**: **両方とも完全に
  同一の結果**——`003A`・`000E`・`0041`の3つのPCだけを固定比率
  （185275:185275:92638）で周回するタイトな空転。総イベント数463188件/
  120フレーム（陰性対照の約77倍、明確な異常空転）。

**解釈:** 番地0x0900と0x0850は異なる番地なのに、結果が1バイトも違わず
完全に一致した。もし境界の外が「番地に応じて下位2KBの対応する番地を
ミラーする」構造なら、異なる番地は異なる内容を指すはずで、結果は
違ってよいはずだが、そうならなかった。これは境界の外が**番地に依存しない
一様な埋め値**であることを示す。空転先の`003A`/`0041`は自作コードの
`RECV_BYTE_ARMED`（0x002E開始）の区間内にあり、`000E`は
`WAIT_FE_RECV_ACK_DONE_LOOP`である。Z80の`0xFF`はRST 38命令（無条件に
0x0038へ分岐する1バイト命令）であり、0x0038は`RECV_BYTE_ARMED`の区間内に
落ちる。**したがって境界の外は`0xFF`の一様埋めであり、そこへ実行が
入ると即座にRST 38が繰り返し発火し、コードの区切りを無視した「ずれた」
位置から実行が再開する、という筋が実測と整合する。**

## 2. LIMIT=3/4の0件退行は同一原因の続きと確定

`find_out_of_window_blocks()`（後述）で列挙すると、LIMIT=3・LIMIT=4の
既定ビルド（m7anの整列パディング適用後、命令の跨ぎは0件）でも、
`_observed_request_next_7`（LIMIT=3で88バイト）・
`_observed_request_next_8`（70バイト）・`_observed_request_next_9`
（9バイト）が丸ごと境界0x0800の外に置かれている（LIMIT=4ではさらに
`_observed_request_next_6`も加わる）。これらは起動時の観測応答決定
チェーンの一部であり、**跨がずに丸ごと外へ出た命令**は1節の実測結果
どおり実行できない（RST 38の一様埋めを踏む）。

これはm7anで確定した「境界を跨ぐ命令」パターンとは別の、**同じ0x0800
制約から来る、もう一つの現れ方**である。LIMIT=3/4がexchange14の
バルク転送到達前に崩れる（m7al・m7an）現象は、実行がこの決定チェーンの
末尾（境界の外）へ到達した時点でRST 38空転に陥り、m7al/m7amで観測した
「起動ハンドシェイクへの再入・pc=0x0007付近の空転」と**症状が完全に
一致する**。したがって、**LIMIT=3/4の0件退行は新規の別原因ではなく、
m7anで発見した0x0800制約の同一原因の別の現れである**と結論する。

## 3. 到達可能命令の不変条件

`src/l3_service/make_subrom.py`に`find_out_of_window_blocks(a, boundary,
known_unreachable)`を追加した。ラベル区間（そのラベルの開始位置から
次のラベルの開始位置の直前まで）の開始位置が境界以上にある区間を
列挙する。**到達可能性は保守的に判定する**——`known_unreachable`
（現時点では空集合）に明示的に列挙したラベル名の区間だけを除外し、
それ以外は全て到達可能とみなす。推測で「これは実行されないはず」と
決めつけて除外することはしていない。

### 陽性対照（`tools/subrom_fetch_window_selftest.sh`に追加）

- 境界を意図的に小さく（0x0100）すると、既知の到達可能ブロックが
  検出されること（73ブロック検出）。
- 境界を意図的に巨大に（0x8000）すると、何も検出されないこと
  （0ブロック、false positiveが無いことの確認）。
両方を確認済み。

### 現状の窓超過（値ではなくバイト数・ブロック数のみ）

| LIMIT | 使用バイト数 | 窓超過 | 超過ブロック |
|---|---|---|---|
| 1（既定） | 2106 | 9 | `_observed_request_next_9` |
| 2 | 2180 | 79 | `_observed_request_next_{8,9}` |
| 3 | 2246 | 167 | `_observed_request_next_{7,8,9}` |
| 4 | 2320 | 228 | `_observed_request_next_{6,7,8,9}` |

**既定（LIMIT=1）の時点で既に9バイト超過している。** これまでの
測定（258/752/1282という確立済みの指標）がこの超過にもかかわらず
成立していたのは、`_observed_request_next_9`（9バイトの小さな
フォールバック区間と見られる）がこれまでの全実走シナリオで一度も
踏まれなかったからに過ぎない——安全である保証ではなく、単に踏んで
いなかっただけである。

## 4. 予算内への削減（未着手、理由つき）

`_observed_request_next_1`〜`_observed_request_next_9`の9エントリ
（合計で最大のコード消費ブロック群、9エントリで約500バイト超）を
テーブル駆動へ書き換えれば大きな削減が見込めるが、**本サイクルでは
着手していない**。理由:

- この決定チェーンは交換#0〜#2（起動直後）の観測応答を決める中核ロジック
  であり、m7hをはじめ複数セッションをかけて確立・検証されてきたもの。
  書き換えは258/752/1282という既存の確立済み指標を壊すリスクが高い。
- 残り時間内で「書き換え→既定LIMIT=1の4指標が不変であることを確認→
  さらにLIMIT=2の3330件も不変であることを確認」という検証サイクルを
  安全に回しきれる見込みが立たなかった。
- 診断専用コード（`$F9`タイムアウトマーカー）を無効化しても6バイトしか
  節約できず（実測済み）、必要な削減量（LIMIT=4で228バイト、既定でも
  9バイト）に遠く届かない。

**したがって`build()`に「到達可能コードは境界未満」という不変条件を
無条件のSystemExitとして組み込むことは、現時点では見送った。** 組み込むと
既定LIMIT=1の`build()`が即座に失敗し、`tools/verify_l3.sh`・
`tools/conform_l3.sh`をはじめ既存のパイプライン全体が動かなくなる
（それ自体が「テストを通すために期待値を緩める」の逆方向の破壊であり、
避けるべきと判断した）。代わりに、`find_out_of_window_blocks()`を
`tools/subrom_fetch_window_selftest.sh`から呼び、**超過量を毎回
可視化して報告するだけ**にとどめた（強制失敗はしない）。この判断の
妥当性は次サイクル以降、削減が実際に進んだ時点で再評価する。
