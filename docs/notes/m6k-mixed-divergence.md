## 第1部: 混成ROM実走の分岐点診断

### 手順

`tools/diag_l3_mixed.sh` をユーザーの公式環境で実走した。混成ROM
（公式main側ROM一式 + 自作サブROM`DISK.ROM`）で diskA を起動し、
公式基準ログ `measurements/m6g-d0-boot-run1.iolog.txt.gz` と
`(cpu, 方向, ポート, pc)` だけで突き合わせた。

### main側の分岐点

7089件目まで公式と完全一致。7090件目で分岐する。

- **公式**: `IN $FE pc=37DC` を4回で抜け → `OUT $FF pc=37F0` →
  `OUT $FD pc=37F4` → `OUT $FF pc=37F8` → `IN $FE pc=37FF`×2 →
  `OUT $FF pc=3815` → `IN $FE pc=381C`×2 → 以降 pc=37CF から同じ形を反復
- **混成**: 同じ `IN $FE pc=37DC` を**655,360件**回し続ける（待ちループから
  抜けない）

main側ポート内訳（総イベント数: 公式95046 / 混成682750）:

| ポート | 公式 | 混成 |
|---|---:|---:|
| `IN $FE` | 26086 | 655360 |
| `OUT $FF` | 13601 | (655360のみ) |
| `IN $FC` | 6672 | 0 |
| `IN $FD` | 5635 | 0 |

`IN $FC`・`IN $FD`・`OUT $FD`・`OUT $F3`・`IN $6E` は混成側で**一度も
現れない**。

### sub側の分岐点

1件目から分岐する。

公式sub先頭13件は、第2部で確定させる**RECVプリミティブ**（後述）そのもの:

```
OUT $F7 pc=036E → OUT $FF pc=00B3 → IN $FE pc=00B5 → IN $FE pc=00CC →
OUT $FF pc=06DB → IN $FE pc=06DD ×2 → OUT $FF pc=06F3 →
IN $FC pc=06F5 → OUT $FF pc=06FA → IN $FE pc=06FC ×2 → OUT $FF pc=070B
```

自作サブROMは `OUT $FF pc=0006` 1回 → `IN $FA`/`OUT $FB`（FDC初期化）→
`IN $FE pc=000E` を **655,359件**回して停止する。

sub側ポート内訳:

| ポート | 公式 | 自作 |
|---|---:|---:|
| `IN $FE` | 26085 | 655359 |
| `IN $FA` | 13884 | 11 |
| `IN $FB` | 13672 | 2 |
| `OUT $FF` | 12591 | 1 |
| `OUT $FD` | 6672 | 0 |
| `OUT $FC` | 5635 | 0 |
| `OUT $FB` | 161 | 6 |
| `IN $FC` | 66 | 0 |
| `OUT $F8` | 13 | 0 |
| `OUT $F7` | 10 | 0 |
| `OUT $FE` | 0 | **1** |

公式subに現れて自作subに無いポート: `IN $F8` `IN $FC` `OUT $F7` `OUT $F8`
`OUT $FC` `OUT $FD`。**逆に自作subにあって公式subに無いのは `OUT $FE`
（公式subは$FEに一度も書き込まない）。**

### 診断

自作サブROMには sub側の RECV プリミティブ（mainのSENDを受ける側の手順）が
実装されておらず、main と sub が互いに `$FE` を待ってデッドロックしている。
main は起動直後にSENDを試み（`IN $FE pc=37DC`のSEND前待ち）、sub は
それに応答するRECV手順を持たないため、mainは相手の受信準備完了を
永遠に待ち続ける。

### 自己検証層の限界（記録しておく価値のある事実）

`tools/verify_l3.sh`（自己検証層）は SEND/RECV ハンドシェイクを「合格」と
報告していた。しかし相手役の試験用mainドライバ
（`tools/make_l3_test_main.py`）も自作である。**両方が同じ誤解を共有して
いたため通っていた**のであり、公式main相手では1バイトも通らない。
この種の自己検証（試験対象と試験駆動側を両方とも自分で書く）が構造的に
持つ限界であり、隠さず記録する。

## 第2部: sub視点の`$FE`待ち状態解析

### 動機

`docs/spec/l3-subrom.md` 1.13節は main の `IN $FE` を4箇所の待ちループに
分類し遷移を確定したが、**main視点でしか**定義していない。第1部の診断
どおり、自作サブROMに欠けているのは「sub がどう`$FE`を待ち、
`$FF`に何を書けば良いか」という**sub視点**の手順である。本節でそれを
確定させる。

### 手法・解析器

`tools/analyze_main_to_sub.py` の `wait_loop_transitions`/`WAIT_LOOP_PCS`
と同じ手法(「直前のリターンアドレス(pc)でグループ化し、値の遷移を集計する」)
を sub 側に一般化した解析器 `tools/analyze_sub_fe.py` を新規に書いた
(**既存の `analyze_sub_proto.py`/`analyze_main_to_sub.py` を流用ではなく、
一般化した新規スクリプトとして追加した**。理由: 前者はmain視点の固定4PC
決め打ち(`WAIT_LOOP_PCS`)であり、sub視点のPCクラスタは未知だったため、
件数閾値による自動発見が要った。パーサ(`cmp_io._open_iolog`・8列regex)は
共有し、二重実装はしていない)。

やっていること:

1. sub の `IN $FE` を直前pcでグループ化する(件数10件以上を「待ちループ
   候補」として自動発見。決め打ちしていない)。
2. 各pcについて、連続する読み取り値の遷移(前の値→次の値)を集計する。
3. 各「待ちループの一続き(スピン)」の直前・直後に sub が `OUT $FF` に
   書いた値を対応付ける。`$FE`/`$FF`はデータポート(`$FB`/`$FC`/`$FD`)
   ではないため伏せ字対象外——値がそのまま読める。
4. 1.12節で確定済みのフェーズコード語彙(`0F/0E/09/08`=SEND系,
   `0B/0A/0D/0C`=RECV系)と前後の`$FF`値を突き合わせ、各待ちループを
   SEND側/RECV側に機械的に分類する。

再実行方法:

```
python3 tools/analyze_sub_fe.py \
    --iolog measurements/m6g-d0-boot-run1.iolog.txt.gz \
    --out /tmp/sub-fe-run1.txt

python3 tools/analyze_sub_fe.py cross \
    --iolog measurements/m6c-sub-d0-boot.iolog.txt.gz \
            measurements/m6c-sub-d1-files.iolog.txt.gz \
            measurements/m6c-sub-d2-save.iolog.txt.gz \
            measurements/m6c-sub-d5-seqfile.iolog.txt.gz \
    --label d0-boot d1-files d2-save d5-seqfile \
    --out /tmp/sub-fe-cross.txt
```

### 決定論性の確認

`measurements/m6g-d0-boot-run{1,2}.iolog.txt.gz`(同一条件の2回測定、
`m6-conformance.md`で決定論性確認済み)に対して本解析器を実行し、
出力を diff したところ、**ラベル行(ファイル名)以外は完全に一致した
(diff 0行差)。**

副産物: 実装初版では、件数が同点のpc(例: 起動時バルクループの2つの
pc、いずれもn=11264)が複数あると出力順が `PYTHONHASHSEED` に依存する
Python の `set` 反復順のせいで実行のたびに入れ替わるバグがあった
(実測で確認)。ソートキーに `pc` 文字列を二次キーとして加えて固定した。
値そのものは変わらないが、「決定論性の確認」という手順自体が意味を
持つために直した(このリポジトリの規律: 手順が意味を持つよう検算器を
先に信用できる形にする)。

### 検出力の確認(わざと壊す)

`tools/analyze_sub_fe_selftest.sh` を新設した。合成フィクスチャ(公式
データ不使用)で以下を確認済み(全項目OK):

- (a) 正常フィクスチャ: 既知のRECV型サイクル(50回)から、期待どおりの
  遷移(`20->21` 50件、`41->40` 50件)とロール判定(RECV)が出る
- (b) clockシャッフル(`tools/verify_analyzer_corruption.py`の
  `make_shuffled_clock`と同じ操作: 各行のclock値集合はそのまま行への
  割当だけをシャッフル): 真の発生順を失わせると、`20->21`遷移の検出数が
  50件から**4件**まで崩れることを確認した(=解析器は本当にclock順を
  見ている)
- (c) pcラベル破壊: 全pcを1値に潰すと候補待ちループが1種に統合される
  ことを確認した(=pc別グループ化が機能している)

`tools/run_all_selftests.sh` に登録した(理由は本ノート末尾参照)。

### 条件横断での一致確認

`measurements/m6c-sub-{d0-boot,d1-files,d2-save,d5-seqfile}.iolog.txt.gz`
(同一の公式サブROMバイナリ、main側ディスク動作のみが異なる4条件)に
対して cross モードを実行した。**全11種の待ちループpcについて、
出現した全条件で遷移語彙・ロール判定が完全に一致した**(d5-seqfile
のみに追加で2種のpc(`0745`/`0765`)が出現。同じ語彙(`20->21`系/`41->40`)
を持ち、既存4種と整合するRECV型ループの別の呼び出し site と見られる)。

### 確定: sub視点のRECVプリミティブ(mainのSENDを受ける側の手順)

**これが本ノートの核心の成果である。** 4条件・sub OUT $FF/IN $FEの
生ログを直接追跡し(手動トレース。以下の値は伏せ字対象外の`$FF`/`$FE`の
実測値そのもの)、`tools/analyze_sub_fe.py`の集計と完全に一致することを
確認した。d0-boot条件での最初のRECVサイクル(main側は同時に
pc=37CFからのSENDを実行中——main側SENDの`OUT $FD`実行clockと、
sub側の`IN $FC`実行clockが直接対応することを確認した。**すなわち
これはmainの1バイトSENDと対になる、sub側のRECVプリミティブそのもの
である**):

| 手順 | sub の動作 | 観測値 |
|---|---|---|
| 1 | `OUT $FF` に `0B` を書く | 固定 |
| 2 | `IN $FE` 待ちループ(相手=mainのデータ準備待ち) | `20→21` または `28→21`(いずれも最終的に`21`で抜ける。下記「未確定」参照) |
| 3 | `OUT $FF` に `0A` を書く | 固定 |
| 4 | `IN $FC` で実データを読む | (伏せ字。値は読めないが、mainの同時刻`OUT $FD`と対応することは確認済み) |
| 5 | `OUT $FF` に `0D` を書く | 固定 |
| 6 | `IN $FE` 待ちループ(相手=mainの受理解除待ち) | `41→40` で抜ける(4条件で例外なく一致) |
| 7 | `OUT $FF` に `0C` を書く | 固定 |

これは main視点の1.10節RECV定義(`OUT $FF 0B → IN $FE待ち(相手のデータ
準備待ち) → OUT $FF 0A → IN $FC<byte> → OUT $FF 0D → IN $FE待ち
(相手の受理解除待ち) → OUT $FF 0C`)と**フェーズコードの並びが文字どおり
一致する**。sub は「自分がRECVする側」であることを、mainが自分の
RECVを行うときと**同じ8種のフェーズコード語彙**で表現している
——SEND/RECVという役割の名前は「どちらが送り手か」で決まり、
送り手はSEND語彙(`0F/0E/09/08`)を、受け手はRECV語彙(`0B/0A/0D/0C`)を
使う、という対称設計であることが、main-sub 双方の同時実測で確定した。

### 確定: sub視点のSENDプリミティブ(mainのRECVに応答する側の手順)

同じ4条件のログから、sub がmainへ1バイトを送る側(main側は
`docs/spec/l3-subrom.md`のRECV_HANDSHAKE_PCS(main IN $FC)で受ける)の
手順も再構成できた:

| 手順 | sub の動作 | 観測値 |
|---|---|---|
| 1 | `IN $FE` 待ちループ(相手=mainの受信準備待ち) | `00→02` で抜ける(4条件で例外なく一致) |
| 2 | `OUT $FD` で実データを書く | (伏せ字) |
| 3 | `OUT $FF` に `09` を書く | 固定 |
| 4 | `IN $FE` 待ちループ(相手=mainの受理確認待ち) | `12→14` で抜ける(4条件で例外なく一致) |
| 5 | `OUT $FF` に `08` を書く | 固定 |
| 6 | `IN $FE` でステータス相当を読む(スピン) | `04`始まりで、次に続く手順によって抜け値が`08`(次がRECVプリミティブ)/`02`(次が同種SENDの反復)に分かれる(下記「反復サイト」参照) |

手順6は単一固定値の1回読みではなく、**次に何が続くかによって抜け値が
変わる境界的な待ち**であることが分かった(1.10節のmain視点定義は
「`IN $FE`(status)」と単純化して書いているが、sub側の実装はこの境界を
次の手順の先頭待ちと連続させている。分類器が pc=`0735`/`07A5` を
「不定(前後で食い違い)」と報告したのはこの構造の反映であり、
誤判定ではない)。

こちらは main視点1.10節SEND定義の「`OUT $FF 0F(省略可)→IN $FE待ち→
OUT $FF 0E→OUT $FD<byte>→OUT $FF 09→IN $FE待ち→OUT $FF 08→
IN $FE(status)`」と比べ、**`0F`/`0E`相当の明示的な`OUT $FF`書き込みを
一度も観測しなかった**(4条件で共通)。sub のSEND手順は、直前の
待ちループ(手順1)から直接`OUT $FD`(手順2)へ進み、`0F`/`0E`に対応する
フェーズコードを書かない設計である可能性が高い。ただし「サブROMの
この実装がそうだから」以上のことは言えない(3節「未確定」参照——
`0F`は元々main視点でも「省略される場合あり」と記載されている)。

さらに、上記のSENDプリミティブを反復する専用の呼び出しsite
(4条件で共通のpc、n=512スピン@d0-boot〜1935スピン@d5-seqfile)を
確認した。ここでは1スピンにつき`OUT $FD`が**2回**現れる(1回目の
`OUT $FF 09`待ちループの後、2回目の`OUT $FD`が続いてから`OUT $FF 08`
へ進む)。1回のSENDサイクルで2バイトを送っているのか、
`OUT $FD`の用途が途中で切り替わる(例: ヘッダ相当+データ相当)のかは、
本ノートの手法(pc/kind/port/フェーズコードの追跡のみ、値は伏せ字)
からは切り分けられない(未確定に追加)。

### 未確定として残ること

- **sub視点RECV前待ち(手順2)の遷移が`20→21`と`28→21`の2種類ある理由。**
  main視点1.13節の対応する待ち(main RECV前=`3853`, 遷移`20⇄21`)は
  単一の遷移語彙だったのに対し、sub視点の対応する待ちは2つの起点
  (`20`/`28`)から同じ`21`へ収束する。起点の違いが何に対応するかは
  未確定。
- **sub視点SENDの`0F`/`0E`相当が本当に存在しないのか、たまたま
  この4条件では踏まなかっただけなのか。** 4条件・数十〜数千サンプルで
  一貫して観測されなかったが、他の操作(未測定の条件)で現れる可能性は
  排除できない。
- **反復SENDサイトでの2回の`OUT $FD`が何を運んでいるか。** 上記のとおり。
- **境界的な待ちループ(前後の`$FF`文脈がSEND語彙とRECV語彙に食い違う
  もの)の扱い。** 自動分類器(`tools/analyze_sub_fe.py`)は、RECVサイクル
  終了直後・SENDサイクル開始直前に位置する境界の待ちループを
  「不定(前後で食い違い)」と正しく報告した(直前=RECV系コード、
  直後=SEND系コード、あるいはその逆)。これは実装バグではなく、
  その待ちループが構造上「1つの手順の内部」ではなく「手順と手順の
  継ぎ目」に位置する、という事実そのものである。継ぎ目のPCが公式ROMの
  内部構造(番地)そのものである以上、`docs/spec/l3-subrom.md`本体には
  PCの具体値を書かない(1.14節と同じ判断)。この継ぎ目の存在自体は
  仕様に反映する。

- 公式subの先頭(畳み込み後): `OUT $F7 pc=036E` → `OUT $FF pc=00B3` →
  `IN $FE pc=00B5` → `IN $FE pc=00CC` → `OUT $FF pc=06DB` →
  `IN $FE pc=06DD x2` → `OUT $FF pc=06F3` → `IN $FC pc=06F5` →
  `OUT $FF pc=06FA` → `IN $FE pc=06FC x2` → `OUT $FF pc=070B` →
  `OUT $F8 pc=00F9` → `OUT $F8 pc=0103` → `IN $FA pc=02A8` →
  `OUT $FB pc=02B1` → 以降 `$FA`/`$FB` の反復(FDC)。
- 自作サブROM: いきなり `IN $FA pc=0062`/`OUT $FB pc=006B`
  (FDC初期化)から始まり、そのあと `OUT $FF pc=0028` →
  `IN $FE pc=000A x2` → `OUT $FF pc=002F` → `IN $FC pc=0031` →
  `OUT $FF pc=0036` …(RECVを2回)→ `$FE` 待ちで停止。
- 公式subに現れて自作subに無い: `IN $F8` `OUT $F7` `OUT $F8` `OUT $FC`
  `OUT $FD`。

### 診断(第4部で裏付ける)

**自作サブROMが公式subの起動順序(`$F7`→ハンドシェイク→RECV1回→
`$F8`×2→FDC初期化)を実装しておらず、いきなりFDC初期化から始めている
ことが分岐点そのものである。** main は起動直後1バイトRECV(1.15節の
RECVプリミティブ)しか要求していないにもかかわらず、自作subはこれを
一切試みずFDC初期化ループへ入るため、mainは相手の応答を待ち続ける。
第1部時点の診断(「sub側RECVプリミティブが未実装」)は解消済みだが、
**「いつRECVプリミティブを呼ぶか」という起動順序が未実装のまま
だった**、という次の層の問題が残っていたことになる。

- **手順5のRECV1回は、手順6〜7の`$F8`書き込みより前に完了している。**
  すなわちsubは、FDC初期化に入る前に、mainから1バイト(用途は伏せ字の

  必ず受け取る。
- **手順5のRECVには対になるSEND応答が無い。** 後述(第5部)で確定する

- **`$FF=0x91`と手順3〜4の単発`IN $FE`の意味論は未確定のまま残す。**
  値そのものは確定したが、mainがこれを観測しているか(＝実装が必須か)
  桁は不明。ただし「公式subが4条件で例外なく行っている」という事実
  そのものは確定しているため、実装は再現する(推測ではなく観測の
  再現という扱い)。

## 第5部: ディスパッチャの判別条件——確定できたことと、できなかったこと

`docs/spec/l3-subrom.md` 6節9項が要求する「main視点のSEND/RECV
(1.10節)に対してsub視点RECV/SENDプリミティブ(1.15節)のどちらで
応答するか」という**選択そのもの**が、どういう条件で決まるのかを
確認した。**追加測定は行っていない。** `tools/analyze_sub_fe.py`の
`cross`モード出力(`/tmp/sub-fe-cross.txt`、本ノート第2部と同じ手法)
と、`measurements/m6c-sub-d0-boot.iolog.txt.gz`/
`measurements/m6c-sub-d5-seqfile.iolog.txt.gz`の手動トレースを併用した。

### 確定: 「アイドル待ち」(pc=00CC)は観測範囲で常にRECVへ進む

第4部の手順4(`00CC`)は起動時だけでなく、定常状態でも繰り返し現れる
(d0-boot条件でn=35件、d1-files/d2-save/d5-seqfileでも比例して出現。
`/tmp/sub-fe-cross.txt`)。**4条件・全出現(26+50+75+101=252回)を機械的に
追跡したところ、`00CC`のスピン終了直後は例外なく`06DB`
(RECVプリミティブの開始)へ進んだ。**`00CC`から直接SENDプリミティブへ
進んだ事例は0件だった。

### 確定: RECVプリミティブは(起動時を除き)常に直後にSEND応答を伴う

d0-boot条件のsub `OUT $FF`値をpc別に集計したところ(以下、起動後の
定常ループ部分):

```
06DB(0B) 66回  06F3(0A) 66回  06FA(0D) 66回  070B(0C) 66回
0722(09) 13回  0733(08) 13回
```

第4部の起動時RECV(1回、`OUT $FF 0B`込みで66回中の1回)を除く65回の
`06DB`RECVのうち、直後(`00CC`アイドル待ちを挟まず)に`0722`/`0733`の
SEND手順が続く事例が13回見つかった。手動トレースで該当13件すべてを
確認したところ、**`070B`(RECV終了)の直後の次のイベントが例外なく
`0710`(SENDプリミティブの開始、`00→02`待ち)であり、SENDプリミティブは
`0722`/`0733`で終わっていた**——RECVとSENDが1組の応答ペアとして
密着している(間に`00CC`を挟まない)。

### 確定: これとは別の、RECVのみを繰り返す専用の呼び出しサイトが存在する(d5-seqfileのみ)

d5-seqfile条件で、`0743`/`0745`/`075B`/`075D`/`0763`/`0765`/`0772`/
`0778`という一連のpcが、1.15節と同一のRECVプリミティブ構造
(`0B`→`$FE`待ち`20→21`→`0A`→`IN $FC`→`0D`→`$FE`待ち`41→40`→`0C`)を
**SEND応答も`00CC`アイドル待ちも挟まず連続して繰り返す**のを確認した
(手動トレース、`0778`(RECV終了)の直後が例外なく次の`0743`
(RECV再開)である事例を連続20件以上確認)。この反復列は最終的に
`OUT $F8=0x07`(pc`06D5`)→FDC書き込みポーリングへ抜ける。d0-boot/
d1-files/d2-saveの3条件ではこのpc群は一度も出現しない
(`/tmp/sub-fe-cross.txt`)。

**これは6節7項が既にスコープ外としている「書き込み側(267バイト連続
SENDバースト)」の**sub側での対応物**と見られる(main側が連続して
SENDする267バイトを、subが連続してRECVで受け続ける側)。呼称を
「ストリーミングRECVループ」とする。

### 確定できなかったこと(推測で埋めない)

**「idle待ち(`00CC`)からRECV(`06DB`)へ進む」以外の分岐が、観測範囲に
一度も現れなかった。** つまり:

- `00CC`のアイドル待ちが、値によってRECV/SENDのどちらに進むかを
  「選ぶ」分岐点なのか、それとも「常にRECVへ進む」ことが構造的に
  固定された非分岐のコードなのかは、**本測定からは区別できない**
  (4条件とも、たまたま「次はRECV」という状況しか踏んでいない可能性を
  排除できない)。
- **通常のRECV+SEND応答ペア(`06DB`→`0710`)と、ストリーミングRECV
  ループ(`0743`〜)のどちらへ進むかを決めている条件が何かは、本測定
  からは確定できない。** 両者とも`$FE`/`$FF`の遷移語彙・構造は
  1.15節の同じRECVプリミティブであり、**`$FE`/`$FF`自体にはこの2つを
  区別する情報が乗っていない**。分岐しているとすれば、それは
  RECVプリミティブの手順4で`IN $FC`により受け取ったデータの**値**
  (＝main側`OUT $FD`で送られた1バイト。d0-boot/d5-seqfileとも
  伏せ字済みで読めない)を、sub内部のコードが解釈して次の分岐先を
  決めている、という可能性が最も自然だが、**これは推測であり、
  本測定では裏付けられない**。
- 上記により、「`$FE`駆動の汎用ディスパッチャ」(受信データの値を見ずに
  `$FE`の値パターンだけでRECV/SEND/ストリーミングを判別する仕組み)を
  公式subが持っているという確証は無い。**確定できるのは構造(3種の
  呼び出しパターンが存在すること)までであり、それらを切り替える
  判別条件(値ベースか、コード上の固定シーケンスか)は未確定として
  残す。**

## 第6部: 1.16節(起動順序)実装後の混成ROM再実走(ユーザーの公式環境、最新)

**追加測定は行っていない。** 自作サブROMに1.16節の起動順序(コミット
`51e919d`)を実装した状態で、ユーザーが公式環境で混成ROM(公式main一式+
自作サブROM)を再実走した結果を記録する。

### sub側: 構造的一致プレフィックスが0件→27件(生34件)に前進

第3部時点で0件だった構造的一致プレフィックスが、起動順序の実装により
27件(畳み込み後)まで前進した。自作subの末尾(畳み込み後)は次のとおり:

```
#28 OUT $FF  → #29 IN $FE x4 → #30 OUT $FF → #31 IN $FC → #32 OUT $FF
→ #33 IN $FE x2 → #34 OUT $FF x2 → #35 IN $FE x262,145 ← 永久停止
```

これは1.15節のRECVプリミティブ(`0B`→待ち→`0A`→`IN $FC`→`0D`→待ち→`0C`)
を1回完遂した直後、**続けて次もRECVだと決め打ちして`OUT $FF`に`0B`
(手順1)を書いてから`$FE==0x21`を待ち続けている**状態に対応する
(#33-34が2回目のRECV手順1相当、#35がその手順2の待ちがそのまま
終わらないケース)。

### main側: 同時刻に`OUT $FF pc=3851`→`IN $FE pc=3853`でスピン

同じ時刻、main は `OUT $FF pc=3851`(1.10節のmain側RECVプリミティブの
開始。第3部で確認済みの`3851`と同一pc)を出し、`IN $FE pc=3853`で
262,144回スピンして最終的にタイムアウトする。第3部と同型の分岐だが、
今回はsubの構造一致が27件まで伸びたぶん、より後方の呼び出しサイトで
同じ形の行き詰まりが再現している。

### 診断

sub は「RECVプリミティブを1回完遂した直後は、次も無条件にRECV」という
構造で書かれており(旧版の`REQ_LOOP`が毎回`RECV_BYTE`を直接呼んでいた
実装、第7版時点の`src/l3_service/make_subrom.py`)、main が実際には
「subが送る番」(mainがRECVする番)を要求している局面で、subが先に
「RECVする(mainが送る番だと決め打つ)」と`$FF`へ`0B`を書いてしまい、
互いに相手の`$FE`遷移を待ち続けて止まる。**「何を要求されているかが
決まる前に`$FF`を書いてしまっている」ことが直接原因である**(第5部の
「ディスパッチャの判別条件は未確定」という結論と整合する——公式subは
`$FF`を書く前に何らかの判別を行っているはずだが、その判別条件そのものは
第5部で確定できなかった)。

**方針の確認**: sub側の構造一致(FDCの叩き方等)は5.1節により適合条件では
ない。今回追うべきはmain側の分岐点(`IN $FE pc=3853`の無限スピン)のみで
あり、sub側の情報は原因診断にのみ用いる。公式サブROMの内部挙動
(分岐点#28で公式が`OUT $F8`を挟んでFDC作業を続けること等)に合わせに
いくことはしない。

## 第7部: アイドル判別条件の独立再検証(既存ログの再解析、追加測定なし)

第5部の「`$FE`/`$FF`自体にはRECV/SEND/ストリーミングを区別する情報が
乗っていない」という結論を、`tools/analyze_sub_fe.py`の`cross`モード

### 追試1: `analyze_sub_fe.py cross`でpc=00CCの遷移語彙が4条件で完全一致

```
pc=00CC
  d0-boot:    n=35  遷移語彙=['00->08', '01->08']
  d1-files:   n=66  遷移語彙=['00->08', '01->08']
  d2-save:    n=98  遷移語彙=['00->08', '01->08']
  d5-seqfile: n=136 遷移語彙=['00->08', '01->08']
```

### 追試2: アイドル待ちの入口値・スピン長と、その後の分岐先の相関

`00CC`スピンの開始値(0x00/0x01/0x08)とスピン長(1連読み・2連読み)を、

4条件すべてで**入口値・スピン長の分布は分岐先ごとに差が無かった**

アイドルへ戻った2件が入口0x08×2で、単独RECVの母集団(入口0x08中心)と

分岐先を予測する材料は無いことを追試でも確認した。**

### 追試3: 決定論性・検出力

- **決定論性**: `measurements/m6g-d0-boot-run1.iolog.txt.gz`と

### 結論: 前回エージェントの結論を追認する

**前回エージェント(第5部)の「`$FE`/`$FF`自体にはこの2つ(RECV/SENDの
どちらへ進むか)を区別する情報が乗っていない」という結論を、独立な
