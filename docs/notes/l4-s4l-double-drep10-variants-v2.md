# l4-s4l v2 — DREP10E/DREP10Aの右辺定数の読み方を訂正

記録日: 2026-09-15。親の手検算で、l4-s4l候補表v1
(`docs/notes/l4-s4l-candidates.tsv`、コミット23ad7ea)のDREP10E/DREP10A列
に食い違いが見つかった。**測定はしていない。判定には使わない。**

## 原因

`tools/l4_dmodels.py` の `_magnitude_drep10`(v1、DREP10E/DREP10Aの本体)は、

```python
acc = Fraction(0)
for ch in digits or "0":
    acc = _round_even_frac(acc * 10)   # <- 常にround-half-even固定
    acc = _round_even_frac(acc + int(ch))
if net_exp > 0:
    ... _round_variant_frac(acc * 10, variant) ...   # ここだけvariant反映
```

数字の**積み上げ**(桁を1つずつ読む段階)を`variant`(even/away)に関係なく
常に`round-half-even`で行っており、**指数適用(×10/真の÷10)の段階だけ**
`variant`を反映していた。

候補式は`x-c`の形(`x`が候補の対象となる定数、`c`はxの厳密値に最も近い
整数)を多用しており、`c`は小数点も指数記号も持たない**桁数の多い
プレーンな整数**である。この場合`net_exp=0`なので指数適用のループが
一度も回らず、**`c`の値は積み上げ段階だけで決まる。** 積み上げが
常にeven固定だったため、`c`の値はDREP10E・DREP10Aのどちらで読んでも
同じになってしまい、`x`側だけがvariantに応じて変わる、という
非対称な計算になっていた。

候補DREP10E/DREP10Aは「N88がすべての定数をどう読むか」の候補なので、
式に出てくるどの定数(桁数の多い整数を含む)にも同じ読み方を一貫して
当てる必要がある——今回のv1はこの一貫性が崩れていた。

## 訂正

`tools/l4_dmodels.py` に `_magnitude_drep10_v2`(新規関数、v1の
`_magnitude_drep10`はそのまま残し、v1のtsvを1バイトも変えないため変更
していない)を追加した。積み上げの段階を常に`round-half-away`
(DREP01/DEXACT/DGWがl4-s4k以来ずっと使ってきた既定)に統一し、指数適用
(×10/真の÷10)の段階だけがDREP10E(even)/DREP10A(away)でわかれる
(ここはv1と同じ)。モデル名は`drep10e_v2`/`drep10a_v2`として
`tools/l4_dmodels.py`の`_MODELS`辞書に追加登録した。

なぜ積み上げを「away固定」にするのか: DEXACT/DGW/DREP01
(l4-s4k以来、tools/l4_dmodels.pyのこれらの実装)はいずれも
「積み上げ・スケーリングの丸めはl4-s4hの仮定どおりaway」で統一されて
おり、DREP10E/DREP10Aは「指数適用のスケーリングだけeven/awayを切り替える
候補」として追加された経緯があるため、積み上げ自体はほかの3候補と
同じaway固定に揃えるのが一貫している。

## 親の2例の確認(手検算)

いずれも`_round_away_frac`(積み上げ)と、指数適用の各手で
`_round_variant_frac(・,"even")`/`_round_variant_frac(・,"away")`を
使って独立に追った。「TIE」はその手でeven/awayの結果が実際に分かれた
(厳密に半分だった)ことを示す。

### 例1: `print 7096509499740639e+4-70965094997406390272`

**左: `7096509499740639e+4`**(桁`"7096509499740639"`16桁、`net_exp=4`)

- 積み上げ後(away固定): `acc=7096509499740639`(16桁は56bitに厳密に
  収まるため、積み上げ自体に丸めの影響はない)。
- 指数適用(×10を4手):
  - 手1: even=away=`70965094997406390`(タイなし)
  - 手2: even=away=`709650949974063904`(タイなし)
  - 手3: **TIE** — even=`7096509499740638976`、
    away=`7096509499740639104`
  - 手4: **TIE** — even=`70965094997406390272`、
    away=`70965094997406391296`
- 最終: **EVEN=70965094997406390272、AWAY=70965094997406391296**

**右: `70965094997406390272`**(桁がそのまま21桁の整数、`net_exp=0`)

- 積み上げ(away固定、指数適用の段階が無いのでこれで確定):
  `acc=70965094997406391296`
- 最終: **EVEN=70965094997406391296、AWAY=70965094997406391296**
  (積み上げは常にawayなので、この定数単体ではEVEN/AWAYの区別が
  そもそも存在しない——`_magnitude_drep10_v2`はvariantを指数適用の
  ループにしか渡さないため)。

**結果**: `E = 70965094997406390272 - 70965094997406391296 = -1024`、
`A = 70965094997406391296 - 70965094997406391296 = 0`。
→ **親の計算(DREP10E=-1024・DREP10A=0)と一致。**

### 例2: `print -962467.4715e+15#+962467471500000002048`

**左: `-962467.4715e+15#`**(桁`"9624674715"`10桁、小数点以下4桁、
指数15、`net_exp=15-4=11`)

- 積み上げ後(away固定): `acc=9624674715`(10桁は厳密)。
- 指数適用(×10を11手): 手1〜10はタイなし。**手11でTIE**:
  even=`962467471500000002048`、away=`962467471500000018432`。
- 最終(符号込み): **EVEN=-962467471500000002048、
  AWAY=-962467471500000018432**。

**右: `962467471500000002048`**(21桁の整数、`net_exp=0`)

- 積み上げ(away固定で確定): `acc=962467471500000018432`。
- 最終: **EVEN=962467471500000018432、AWAY=962467471500000018432**。

**結果**: `E = -962467471500000002048 + 962467471500000018432 = 16384`、
`A = -962467471500000018432 + 962467471500000018432 = 0`。
→ **親の計算(16384/0)と一致。**

`tools/gen_l4_s4l_candidates_v2.py`/`tools/gen_l4_s4l_controls_v2.py`で
`docs/notes/l4-s4l-candidates-v2.tsv`/`docs/notes/l4-s4l-controls-v2.tsv`

  (崩れた対照は0件、`still_control`列は全行`yes`)。

## l4-s4kの表・Codexの探索に同じ問題があったか

### l4-s4kの表(`docs/notes/l4-s4k-candidates.tsv`・`l4-s4k-controls.tsv`、
コミットd5fc8ee)

**同じ問題は無かった。** l4-s4kはDEXACT/DGW/DREP01の3候補で、
DREP10E/DREP10Aのような「積み上げは固定・指数適用だけvariant」という
非対称な構造がそもそも存在しない(3候補とも式のどの定数にも同じ関数を
一貫して適用していた)。念のため、DREP01の積み上げを「×10と+dをまとめて
1回round」ではなく「$MUL10→$FADDDを別々に呼ぶ2回round」に直して
l4-s4kの候補24行・対照12行を再計算したが、**1行も値が変わらなかった**
(l4-s4kのDREP01が使う桁数の範囲では、1回roundと2回roundの差が
表面化しなかった)。l4-s4kの表は書き換えていない。

### Codexの探索(`dfin_model_search.py`、scratchpad)

**同じ問題があった。** Codexの`double_literal()`関数は

```python
accumulation_rounding = "away" if model == "drep01" else "even"
acc = accumulate_digits(lit, accumulation_rounding)
```

としており、`div10-even`/`div10-away`(DREP10E/DREP10Aに相当)の
どちらでも積み上げは`"even"`固定になっていた(`drep01`モデルだけ
`"away"`)。つまりCodexの元の実装にも、v1と同種の「積み上げがvariantに
連動しない」構造があった。

**ただしl4-s4kの実測36件の再現数への影響は無かった**: Codexの元の
`div10-even`/`div10-away`と、積み上げをaway固定に訂正した
`drep10e_v2`/`drep10a_v2`のどちらで計算しても、l4-s4kの実測36件
(候補24件+対照12件、測定した生の値は転記しない)との一致は
**36/36で変わらなかった**(外れは両方とも0件)。l4-s4kの候補で使われた
`c`の桁数がl4-s4lのCodex提示5本ほど極端でなく、積み上げの丸め方の違いが
表面化しなかったためと考えられる。
