# m7al: LIMIT=3（READ#4）・LIMIT=4（READ#5）実測 — 未診断のクラッシュで退行

測定日: 2026-08-17

## 情報境界

公式1800フレームログ（m7ajで新規実走・構造一致確認済み）を基準に、
`PC88_BULK_READ_INTERVENTION_LIMIT=3`・`=4`で混成ROMを新規実走した。
データポート値は`tools/cmp_io.py --location-only`・`tools/cmp_fdc_sectors.py`
の内部だけで扱った。sub側PC・ポート・方向・件数は構造情報として扱い、
本ノートに残した（値ではない）。生ログ・介入版ROMはスクラッチに置き、
コミットしていない。

## B（先）: 同型バグ（m7akのSTACK/BULK_DATA重複）の先回り確認

実装前に机上で確認した。

- `BULK_DATA`(0x4400)からREAD#2(14セクタ)+READ#3(16セクタ)+READ#4(16セクタ)
  +READ#5(2セクタ)を連続配置すると、終端は算術上ちょうど`0x7400`
  （0x4400+0x3000）になる。書き込み可能範囲`0x4000-0x7FFF`の内側に収まる。
- `STACK=0x7FFE`から下へ最大でも数十バイト程度しか伸びない設計
  （ネストしたCALLは高々十数段）なので、0x7400との間に0xBFE（3070バイト）
  の余裕がある。
- `SECTOR_BUF`(0x4000)・`REQ_HDR`(0x4200)・`HDR_PTR`(0x4300)等はいずれも
  `BULK_DATA`(0x4400)より前にあり、重複しない。

机上では重複は見つからなかった。実測でも、後述のとおりREAD#4のFDC
コマンド座標自体は読めていた形跡がない（クラッシュがコマンド発行より
前に起きるため、m7akと同型の「データ書き込みでスタックを壊す」経路とは
挙動が異なる。詳細はC節）。

## A: LIMIT段階ごとの先頭一致件数と帰属

### LIMIT=3（READ#4を追加）

2回連続実走で同一結果（seqまで一致）を確認した。

- main `IN $FD`: 対象側比較件数**0件**（公式5635件に対し）。LIMIT=2の
  3330件から**総崩壊**。
- `tools/cmp_fdc_sectors.py`: 混成側抽出件数**2件**（公式9件・LIMIT=2の
  6件からも後退）。座標列一致プレフィックス2/2。

### LIMIT=4（READ#5を追加）

1回実走（LIMIT=3と同一の壊れ方だったため、既知の破綻パターンの延長と
判断し、費用対効果からLIMIT=3ほどの反復確認は行っていない）。

- main `IN $FD`: 0件（LIMIT=3と同じ）。
- `cmp_fdc_sectors.py`: 抽出2件、座標列一致2/2（LIMIT=3と同じ）。

### 停止点の帰属（値非依存、PC・ポート・方向・frame/seqのみ）

LIMIT=3・LIMIT=4とも、sub側の最後の実質的なI/Oは同一の構造
（`OUT $F7,0x08` pc=009D → `OUT $FF,0x91` pc=00A1 → `IN $FE` pc=00A3 →
`IN $FE` pc=00A5 → `OUT $FF,0x0B` pc=002C）で終わり、直後から
`IN $FE` pc=0007 の無限ポーリングへ入って二度と抜けない
（1800フレーム終了までLIMIT=3で266489件、LIMIT=4でも同水準のsub
イベントが同一PCで空転し続けた）。

`OUT $FF,0x91`はBOOT_FF_VALUE（1.12節の起動時ハンドシェイク専用値）で、
pc=0x0007・0x002C・0x00A1台はいずれもROM先頭付近（起動時リセット直後の
ハンドシェイク処理）のアドレスである。これは**exchange14のREAD#4処理
（cmp_fdc_sectors的にはREAD#4のFDCコマンドを一度も検出できていない＝
座標発行前）よりも前**に起きている。`diag_l3_mixed.py`でLIMIT=2を基準に
LIMIT=3を比較すると、畳み込み後index 2636（frame=30）で分岐し、直前の
回数差はpc=3853の`IN $FE`が基準4回に対し混成71回だった。frame=30は、
これまでのm7aj/m7ak測定でREAD#2以降のバルク転送が始まるframe=40台より
明確に**前**であり、READ#4自体の座標生成やデータ転送ロジックがまだ
実行されていない時点で崩れている。

**帰属:** LIMIT=3・LIMIT=4のクラッシュは、READ#4/#5固有のコマンド
パラメータやデータ書き込み範囲の問題ではなく、sub ROMがexchange14の
READループへ到達する**前**の、より早い段階（起動時ハンドシェイク相当の
アドレス列への回帰）で発生している。挙動（`$FF,0x91`の再送・起動直後の
低位アドレスへの復帰・最終的に特定PCでの無限ポーリング）はm7akで直した
スタック破壊と外見上似ているが、Bで机上確認したとおりBULK_DATA/STACKの
アドレス重複という同型の原因は見当たらない。LIMIT=2→3で追加されるのは
`_exchange14_prepare_remaining_reads`ループのもう1回分の命令列
（約70バイト、ROM末尾側のコードサイズ増加。2175→2246バイト、
`ROM_SIZE=0x2000`の上限には遠く及ばない）だけであり、この命令列自体は
exchange14の判定に達するまで実行されないはずなので、**なぜ実行順序上
そこに到達する前の挙動まで変わるのかは本サイクルでは特定できなかった**。

## $F9（診断マーカー）

LIMIT=3・LIMIT=4いずれの生ログでも`OUT $F9`は0件だった（m7akで陽性
対照済みの検出力を再利用）。sub内のFDCチップ応答待ちタイムアウト
（`FDC_WAIT_TIMEOUT`到達）は起きていない。クラッシュの原因はFDCチップ
待ちではない。

## 対応方針

推測でのコード修正は行っていない（PLAN第5節「候補総当たりで埋めない」
規律に従う）。`src/l3_service/make_subrom.py`は本サイクルで変更していない
（m7akのSTACK修正を含む既存コードのまま）。既定`BULK_READ_INTERVENTION_LIMIT=1`
は無傷。到達点はLIMIT=2の3330件のまま。

## C: 5635件到達の可否

到達しなかった。LIMIT=2止まりでmain `IN $FD`先頭一致3330件が現時点の
最良値。`tools/conform_l3.sh`の`[混成]`は引き続き不一致のままであり、
再測定・変更もしていない。

## 4指標（本サイクル前後で変更なし）

- 値一致長: 変更なし
- main側構造的一致プレフィックス: 258件（変更なし）
- sub側構造的一致プレフィックス: 752件（変更なし。既定LIMIT=1で確認）

## 次の対象

sub側のこのクラッシュ（起動時ハンドシェイクアドレスへの回帰）を、
値非依存のまま追加診断するには、`_exchange14_prepare_remaining_reads`
ループの命令列そのもの（jr相対ジャンプの飛び先、ラベルの再利用有無）を
生成コード側で機械的に検証する診断器が要る。今回はPC・ポート・件数の
比較だけでは「なぜexchange14到達前に崩れるか」まで特定できなかった。
次サイクルはこの一点（READ#4追加でなぜLIMIT=2までと同じ起動シーケンス
すら再現できなくなるか）を先に解かないと、READ#4/#5の座標が正しくても
測れない。座標自体はm7ajのB表で既に一意化済みなので、次サイクルでも
候補探索は不要。
