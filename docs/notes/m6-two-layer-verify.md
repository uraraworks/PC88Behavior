# M6 の検証を二層に分ける

日付: 2026-08-10

## なぜ二層なのか

M4（L1）・M5（L2）の検証（`tools/verify_l1.sh` / `tools/verify_l2.sh`）は
**公式ROM不要**で成立していた。基準ログをリポジトリに置いても、それは
「N88.ROM の入口が発する I/O 書き込み列」や「フォントのCRC32・画面ピクセル」
であり、ROM 由来のバイト列そのものではなかったため。

M6（L3・サブROM）は違う。適合条件（`docs/spec/l3-subrom.md` 5.2節1項）が
問うのは「diskA（N88-BASIC）起動時、main が `IN $FD` で受け取る値の列」
そのものであり、これは **diskA のブートローダの実データ**である
（同node 6節「制限事項」に既に明記されている）。この列をバイト列として
リポジトリに置くと、CLAUDE.md 禁止事項4（「ROM由来のバイト列を含む
ファイルをコミットしない」）に触れる。

そこで、`docs/PLAN.md`「次にやること（M6の続き）」1項で定めた方針どおり、
検証を二層に分けた。

| 層 | 何を検証するか | 公式環境 | ツール |
|---|---|---|---|
| 自己検証層 | 自作サブROM＋自作mainドライバ＋自作D88の組同士でプロトコルが機能すること | 不要 | `tools/verify_l3.sh` |
| 適合テスト層 | 公式ディスクでの受信列が公式版と一致すること | 要る | `tools/conform_l3.sh` |

## 期待値をハッシュにする理由

適合テスト層の期待値は「diskA起動時にmainが受け取る5635件の値の列」
そのものだが、これをリポジトリに置けば禁止事項4に触れる。

**値ではなく「件数」と「SHA-256」だけを `tests/conformance/expected.tsv`
にコミットする。** ハッシュから元の値の列を復元することはできないので、
禁止事項4に触れない。一方で、第三者が公式環境で実測した結果が
「同じ件数・同じハッシュ」になれば、値そのものが一致していることの
十分な証拠になる（衝突を偽装するには元の値の列を知る必要があり、
それは公式ROM/ディスクを持つ者にしかできない——持っていない者が
偽の一致を作れないという意味で、判定として機能する）。

抽出ロジックは `tools/hash_io_stream.py` が `tools/cmp_io.py` の
`parse_iolog` / `filter_port_kind` をそのまま import して使う。
`cmp_io.py --cpu main --port FD --kind IN` と完全に同一の抽出結果に
ハッシュを掛けているだけなので、二重実装によるロジックのずれが無い。

## 使い方

```
# 自己検証層（公式ROM不要。いつでも回せる）
tools/verify_l3.sh

# 適合テスト層（公式ROM・公式ディスクが要る）
PC88_REF_ROM_DIR=/path/to/rom PC88_REF_DISK_DIR=/path/to/disk \
    tools/conform_l3.sh
```

環境変数が未設定なら `conform_l3.sh` は SKIP（終了コード0）で戻り、
何が必要かを表示する。**「検出力の自己検査」は環境変数の有無に関わらず
常に実行される**——期待値ファイルのハッシュを1文字壊したコピー、
件数を壊したコピー、存在しないポートを指定したコピーのそれぞれに対して
`run_conformance` が正しく不一致/エラーとして検出することを、
`measurements/m6g-d0-boot-run1.iolog.txt` を入力に確認する。

期待値の生成（新しいエントリを追加する場合）:

```
tools/hash_io_stream.py <公式環境の測定ログ> \
    --cpu main --port FD --kind IN --name <エントリ名> \
    >> tests/conformance/expected.tsv
```

## いま判定できること／できないこと

判定できる:
- 適合条件1（`docs/spec/l3-subrom.md` 5.2節1項）——diskA起動時、
  mainが `IN $FD` で受け取る値の列の一致。
  `tests/conformance/expected.tsv` の `m6g-d0-boot` 行
  （`measurements/m6g-d0-boot-run1.iolog.txt` から生成。
  `run2` からも同じ値を生成し、件数5635・SHA-256とも一致することを
  確認済み——決定論性の再確認にもなっている）。

未判定のまま残す（5.2節の条件2〜4）:
- 条件2: diskB起動時に `$FC` を一切使わないこと。
- 条件3: サブの割り込み受理がmainの直接I/O操作を直前イベントとしないこと。
- 条件4: ディスク無しでsub相当が1命令も実行されないこと。
  `tools/verify_l3.sh` のネガティブコントロールで、自作実装側が
  既にこの条件を満たしていないと報告済み（既知の未達成）。

これらは `tests/conformance/expected.tsv` にエントリを追加し、
`tools/conform_l3.sh` の照合ロジックを拡張すれば同じ枠組みに乗る形に
なっている。今回のスコープはM6の続き1項（二層の骨格を作ること）であり、
条件2〜4への拡張は次のマイルストーンの宿題として残す。
