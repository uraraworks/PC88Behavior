# m7aj: 交換#14第3 READ以降 — 分岐帰属・位置対応表・介入結果

測定日: 2026-08-17

## 情報境界

公式環境を1800フレームで新規に2回実走し（構造的に完全一致を確認済み）、

## A. 1283位置目（main IN $FD 先頭不一致位置）の帰属

`tools/cmp_io.py --cpu main --port FD --kind IN --location-only` で、公式生ログと
混成生ログ（第2 READのみ実装、既定 `BULK_READ_INTERVENTION_LIMIT=1`）を比較すると、
先頭一致1282件・最初の不一致1283件目で、前サイクルの結果を再現した。

`docs/spec/l3-subrom.md` 1.34節（第47版）で確定済みの配置規則
（位置3=第2READ・第5セクタ・第1位置、以降は`$FC`,`$FD`交互）と、
第2〜第5READのデータ部長（256,3584,4096,4096,512バイト＝1,14,16,16,2セクタ、
`analyze_exchange14_read_rules.py`出力で確認済み）から、件数だけの算術で
帰属を計算できる。

- 定常部は第2READのセクタ5位置2（第2READの1025バイト目、0始まり）から
  `$FC`,`$FD`交互で走査する。
- `$FD`のn番目（1始まり、ヘッダ3位置を含む）は、局所オフセット
  `L = 2n - 7`（n≧4のとき）に対応する（ヘッダ3位置がFD/FC双方に1件ずつ、
  定常部がFD側で奇数ステップに対応するため）。
- 第2READ残り（セクタ5位置2〜セクタ14末尾）はローカルオフセット0〜2558
  （2559バイト）を占める。
- n=1282（最後の一致）→ L=2557 → 第2READ内（オフセット3582、末尾から2バイト目）。
- n=1283（最初の不一致）→ L=2559 → 第2READの範囲外、**第3READ・第1セクタ・
  第1位置**（オフセット0）に一致する。

**結論:** 1283位置目は「第2READのデータ部が尽きて第3READのデータが必要になる
境界そのもの」であり、算術上も1282はちょうど「第2READが供給できる`$FD`件数の
上限」に一致する。第3READ以降が未実装（既定`BULK_READ_INTERVENTION_LIMIT=1`）
であることの直接の帰結であり、新たな未知の分岐ではない。

sub側構造的分岐点（畳み込み後753件目、`tools/diag_l3_mixed.py`で確認）は、
第2READの**データフェーズ内**（`$FB`/`$FA`ポートの反復回数の違い）で起きており、
これは第3READのコマンド発行より前の事象である。したがってsub側752件の壁と、
main側1283件目（第3READ境界）は**別の分岐**であり、752の壁を解かない限り
第3READのコマンド自体を毎回同じ経路で確認することはできても、sub側の
オートノマスな進行は752件目で止まったままになる。

## B. 第3〜第5 READパラメータ8位置の全数位置対応

`tools/analyze_exchange14_read_rules.py` を公式1800フレームログに実行し、
要求12位置・SENSE INTERRUPT STATUSのPCN・直前READ各パラメータとの一致ベクトル
（READ#1〜#5、値は非表示）を得た。

一意化できた位置:

- **R（位置3）**: 要求位置1と要求位置10（同値・区別不可）が、READ#3・#4・#5の
  3件全てに一致（ベクトル`00111`）。READ#1は要求位置4、READ#2は要求位置3に
  一意一致（既存確定と同じ）。
- **C（位置1）**: 単一の要求位置では5件を跨いで一致しない。要求位置2群
  （2/6/9/11、同値）はREAD#2・#3の2件に一致（`01100`）。要求位置1群
  （1/10、同値）はREAD#1・#4・#5の3件に一致（`10011`）。**READ回ごとに
  参照する要求位置群が異なり、単一の「代表位置」に一般化できない。**
  SENSE INTERRUPT STATUSのPCNは5件全てに一致する（`11111`）が、これは
  直前SEEKの結果を読み返しているだけの自明な一致で、SEEK対象そのものの
  生成源は説明しない。
- **H（位置2）**: 要求位置1群がREAD#1・#3・#5、要求位置2群がREAD#2・#4に
  一致。READ間の反転規則（前READから反転）は4/4（全遷移）で成立する。
  要求位置1群と要求位置2群の値が単純に相補（0/1）であれば、両方の記述は
  同じ結果を与える。
- **unit/head（位置0）**: Hから導出される公開エンコード規則により、Hが
  一致すれば自動的に一致する（独立候補ではない）。
- **N（位置4）**: 要求位置1群が5/5一致するが、既存実装どおり固定値として
  扱う（固定パラメータであり要求由来である保証はない）。
- **GPL（位置6）**: 要求位置0のみ5/5一致。既存実装は固定パラメータとして
  扱っており、これと矛盾しない。
- **EOT（位置5）・DTL（位置7）**: 要求12位置・SIS.PCN・直前READ各パラメータの
  いずれとも一致件数0。既存実装は「EOT=R+セクタ数-1」（セクタ数は既知の
  データ部長16,16,2セクタから算出、値としては読んでいない）という算術規則を
  使っており、これは要求からの直接転記ではなく計算式である。

一意化できなかった位置: なし（EOT/DTLは値非依存の算術規則が既に成立しており、
「要求位置との直接一致」という枠では候補がないことを確認しただけで、規則自体は
既存のまま維持する）。

## C. 介入評価（既存候補表 = Bの結果と一致）

`src/l3_service/make_subrom.py` の `_exchange14_prepare_remaining_reads` には、
既にBの結果と一致する候補表が実装済みだった（C位置=2→READ#2/#3、
C位置=1→READ#4/#5、R位置=3→READ#2、R位置=1→READ#3/#4/#5、
EOT=R+セクタ数-1）。ただし既定の `BULK_READ_INTERVENTION_LIMIT=1` により
READ#2までしか実行されない。

`PC88_BULK_READ_INTERVENTION_LIMIT=2`（READ#2+READ#3を実行）で介入評価した。

- `tools/cmp_fdc_sectors.py`: 公式9件・混成6件、**座標列一致プレフィックス6/6**
  （READ#3のC/H/unit-head/R/N/EOT全パラメータが公式と一致）。
- main `IN $FD`: 対象側比較件数**0件**（公式5635件に対し）。既定
  （READ#2のみ）では5635件到達・先頭一致1282件だったのに対し、**退行**。
- sub側構造的一致プレフィックス: 畳み込み後752件のまま変化なし
  （分岐点はREAD#2のデータフェーズ内であり、READ#3の追加より手前で起きるため）。

**解釈:** READ#3のFDCコマンドパラメータ自体はB表どおり正しく生成できる。
しかし高速バルク転送（`OUT $FF`ハンドシェイク経由の`BULK_SEND`）へ到達する前の
どこかで、READ#3実行の追加がプロトコル/タイミング状態を壊し、`$FD`が
1件も出なくなる。これはC/R/EOTの値の問題ではなく、READ#2完了後〜READ#3
コマンド発行、またはREAD#3完了後〜`BULK_SEND`入口のいずれかにある
シーケンス/状態管理の欠陥であり、今回のスコープ（値なし位置対応）では
特定できなかった。PLAN第5節の「候補総当たりで埋めない」規律に従い、
既定は`BULK_READ_INTERVENTION_LIMIT=1`のまま維持し、この介入は採用しない。
