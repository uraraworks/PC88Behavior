# B50: 2 バイトずつ受け取る要求の形を確かめる — 事前登録

記録日: 2026-11-01
位置づけ: [B49](b49-g1-handshake-order-results.md) の次段。[方針追補3](goal-b-policy-addendum3-request-headers-2026-10-31.md) の範囲で、要求の先頭バイトと長さだけを記録する。**このノートは測定より先にコミットする。**

## 1. 問い

1. 27 バイトの送信の中の各要求（B49 の記録から 3、13、3、3、5 バイト）の形と先頭バイトは何か
2. 公式のサブで、2 バイトずつの受信をしているのは ROM 側か RAM 上のコードか
3. 番号 76572 以降の `IN $FC` は、1 バイトずらすと公式と自作で一致するか

## 2. 器具

コアは変えない。`--io-log` の生の記録から出す。

- `burst <i> size=<N> shape=<形> head=<2桁16進>`（番号 76570 の直前の 27 バイトの要求ごと。main が `OUT $FF` に 1 を書くところで切る。形は `5s+8p` のように、1 バイトずつの数と 2 バイトずつの数を順に並べる。先頭バイトは要求の先頭なので追補3の範囲である）
- `sub-reader <single|paired> <hi|lo>`（公式の `IN $FC` の発行元の別。番地は出さない）
- `shift <δ> compared=<N> same=<N>`（δ=-8〜+8 について、公式の `IN $FC` の番号 i と自作の番号 i+δ を 76572 以降で比べる）

**要求の先頭バイト以外の値は出さない。** G1 なしで自己検査する。陽性対照はまとまりの切り分け、発行元の別、ずらしの検出。陰性対照は先頭以外の値が出ないこと。

## 3. 条件

腕 F の 4800 フレーム。OO・SS 各 2 走。クラウドの実行環境で行う。

関門: `IN $FC` の差が B44 と同じ。OO どうし・SS どうしの出力が同じ。OO と SS の `burst` が同じ。要求は 5 本、大きさは 3、13、3、3、5。

## 4. 記録の白リスト

第 2 節の行だけ。

測定前の修正（2026-11-01）: 1 回目はまとまりの切り方が合わず関門で止まった（走のファイルなし）。B49 の記録で main の `OUT $FF` 1 の切れ目を数えると 3、13、3、3、5 だったので、要求ごとに切る形へ改めた。

## 5. 判定（事前に決める）

- まとまりの表をそのまま書く
- `sub-reader paired` が lo なら ROM の機能として、自作のコードと自作の媒体で測る次の事前登録を書く。hi なら RAM 上のコードの動きなので、自作のどこが違うかを別に測る
- `shift` で一致が大きい δ があれば、そのまま書く
