# M6（サブROM）の適合条件検証 — 第1版

`docs/spec/l3-subrom.md` 第1版 5.3節で「未検証」と残した宿題への回答。
M4（L1）で確立した `tools/cmp_io.py --init N --cycle M` の型が、M6の
バースト転送（frame 42〜62・5635件・一回限り）にそのまま流用できるかを
測定で確かめる。

対象は `--cpu sub` の生ログ比較ではなく、5.1節の原則（「メインCPUが
最終的に受け取るデータ列」で判定する）に立ち返って再検討した。

---

## 1. 決定論性の確認（最優先）

同じ条件（diskA = N88_FE.D88、`--frames 1800`、打鍵なし。
`tools/measure_suite.sh` の `d0-boot` と同一条件）で2回測定した。

```
tools/measure.sh m6g-d0-boot-run1 --frames 1800 --disk-name N88_FE.D88 \
    --io-log measurements/m6g-d0-boot-run1.iolog.txt \
    --int-log measurements/m6g-d0-boot-run1.intlog.txt
tools/measure.sh m6g-d0-boot-run2 --frames 1800 --disk-name N88_FE.D88 \
    --io-log measurements/m6g-d0-boot-run2.iolog.txt \
    --int-log measurements/m6g-d0-boot-run2.intlog.txt
```

**結果: 完全に決定論的だった。** `diff measurements/m6g-d0-boot-run1.iolog.txt
measurements/m6g-d0-boot-run2.iolog.txt` は0行（バイト完全一致）。
`.intlog.txt` も同様に0行。main側・sub側の両節、seq・**clock**・frame・
port・value・pcの全列が2回の測定で一致した。揺れは一切無い。

これは「比較による適合判定が成立する」ための土台として確定した。
何が揺れるかを心配する必要は今のところ無い（QUASI88のこの構成では、
少なくとも同一ビルド・同一環境での再実行に限り）。

### 副産物: `tools/cmp_io.py` が8列形式のログを一度も読めていなかった

決定論性の確認中に `python3 tools/cmp_io.py ... --cpu sub` を実行したところ、
**パースエラーで落ちた**（`列数が7でない(8列)`）。

`l3-subrom.md` 第1版 5.3節は「`--cpu main|sub` の引数もすでに実装済み」
「sub側のログを渡す使い方自体はコード上サポートされている」と書いていたが、
これは検証されていなかった。`0010-shared-clock.patch`（共通クロック導入。
`m6-sub-clock.md` 参照）でログ形式が
`seq frame cpu kind port value pc`（7列）から
`seq clock frame cpu kind port value pc`（8列）に変わっており、
`m6c-*` 以降の全ログがこの新形式である一方、`cmp_io.py` は旧7列決め打ちの
ままだった。**つまり第1版執筆時点で「コード上サポートされている」と
書いた `--cpu sub` は、実際にはm6c以降のどのログに対しても一度も
成功実行されていなかった。**

`tools/cmp_io.py` を7列/8列両対応に修正した（`parse_iolog` が列数で
分岐、`Event.clock` を追加。比較ロジック自体はclock列を使わないので、
既存のOUT-only/--with-in/--init--cycleの判定結果には影響しない）。
`tools/cmp_io_selftest.sh` にテスト19〜21として、8列形式の読み込み・
clock列が比較に影響しないこと・列数異常の検出を追加し、いずれも
「わざと壊して検出できる」ことを確認した。

## 2. L1の型（`--init N --cycle M`）の当てはめ

### 2.1 sub側の活動範囲そのものが「定常状態」を持たない

`m6g-d0-boot-run1.iolog.txt` で sub 節のイベントを frame 別に集計すると、
**全78,798件がframe 13〜77の範囲に収まり、frame 78以降（1800フレーム中
残り約1723フレーム）は1件も無い。** L1のmain CPUはVSYNC割り込み駆動で
測定区間全体にわたり周期的にOUTし続けるが、M6のsub CPUはブート処理の
バーストを終えると**完全に沈黙する**。「初期化区間のあとに定常区間が
続く」というL1の前提そのものが成立しない。

frame内訳（抜粋、sub全イベント）:

```
frame 13:    14件
frame 16〜19: 少数（223件@20）
frame 21〜34: 0件（空白）
frame 35〜62: 密（1000〜8000件台、1.6節のバースト本体）
frame 63〜75: 0件（空白）
frame 76〜77: 1953件（末尾の追加活動）
frame 78〜1799: 0件
```

途中に2箇所の空白（21〜34、63〜75）があり、単純な「バースト→定常」の
2段構造でもない。バースト自体も不均一（frame 44や59でだけ件数が落ちる
谷がある）。

### 2.2 OUT-onlyの列でも周期は見つからない

sub の OUT-only列（25,082件: `$FF`12591 / `$FD`6672 / `$FC`5635 /
`$FB`161 / `$F8`13 / `$F7`10）を見ると、`$FC`（5635件）は
OUT-only列のindex 1976〜24512の範囲に**他ポートのOUTと密に混在**して
出現する（同区間中の非`$FC`のOUTは16,902件）。「先頭N件が完全一致、
以降M件周期」という型に当てはめようと `--init 24512 --cycle 1` 等を
試したが、定常状態はどの切り方でも1周すら成立しない
（`cmp_io.py`が「② 定常状態が周期になっていない」で不合格を返す。
周期長を変えて試しても同様——周期という概念に合う繰り返し構造が
そもそも存在しない）。

### 2.3 結論: L1の型は (c) 使えない

「バーストは一回限りで長さが固定なので、むしろ完全一致判定に向いている」
という設問中の仮説は**支持される**。ただし「L1の`--init/--cycle`の
延長」としてではなく、**別の判定モードとして**である（3節）。

## 3. M6の適合条件の定義

### 3.1 比較対象を sub の生ログから main の受信データ列に変更する

`l3-subrom.md` 5.1節の原則（「PIOの内部実装は自由でよい。mainが最終的に
受け取るデータ列だけを見る」）に立ち返ると、**そもそもsub側の生I/Oログ
（`--cpu sub`）を比較対象にすること自体が過剰制約になりうる**ことに
気づいた。sub側のポート往復回数・`$FF`ハンドシェイクの細かい発行パターン
（1.5節「制御/ストローブ的ポート」）は実装の自由度に属する可能性があり、
これをそのまま完全一致条件にすると「同じ実装方式を選んだか」を
判定してしまう——2.1節でPIOの内部実装について既に退けたのと同じ罠である。

そこで比較の主軸を **`main` が `IN $FD` で読み取る値の列** に置く
（5.2節1項がすでに示していた方針）。実測で確認した対応関係:

| 方向 | 件数（d0-boot） |
|---|---|
| sub OUT `$FC` | 5635件 |
| main IN `$FD` | **5635件**（1.2節の対応どおり一致） |
| sub OUT `$FD` | 6672件 |
| main IN `$FC` | **6672件**（同上） |

### 3.2 `tools/cmp_io.py --port/--kind` を新設

L1型の2段階判定（`--init/--cycle`）とは別に、「特定ポート・特定方向の
列だけを取り出し、発生順のまま完全一致（非周期）で見る」判定モードを
`tools/cmp_io.py` に追加した。

```
tools/cmp_io.py <基準> <対象> --cpu main --port FD --kind IN
```

- `--port`/`--kind` は両方必須（片方だけはエラー、終了コード2）
- `--init/--cycle`・`--with-in` とは併用しない（エラー）
- 一致/不一致の判定・不一致時の報告（何件目・どちら向きの差か）は
  既存の `report_mismatch` をそのまま再利用しており、L1向けの①②③とは
  独立した第3の判定軸として動く

`m6g-d0-boot-run1` と `run2`（決定論性の確認に使った2回の測定）を
`--cpu main --port FD --kind IN` で比較すると **5635件で完全一致**した。
1.6節の構造的特徴（末尾73件0パディング等）は既存の解析器
（`tools/analyze_sub_proto.py`）で確認する運用のまま変えていない
（本版では新たな解析は行っていない）。

### 3.3 分岐点検出（3項目）の動作確認

`d0-boot`（打鍵なし）と `d1-files`（`FILES`コマンドを打鍵）を比較すると:

- `--cpu main`（既定のOUT-onlyモード）: **16028件目**（frame 301→302、
  `pc=E7F5`）で最初に食い違い、以降は対象側（d1-files）が長くなる形で
  分岐が明確に報告された。分岐点は「BASICプロンプトへ復帰する定常ループの
  何巡目か」に対応しており、`FILES`打鍵によるコマンド実行がそこから
  始まっていると読める（人間に分かる形——件数・seq・frame・pc——で
  報告される）
- `--cpu main --port FD --kind IN`: d0-boot と d1-files は
  **どちらも5635件で完全一致**した。`FILES`コマンドによる分岐は
  ブート後のBASICプロンプト処理側で起きており、ブート時の`$FD`バースト
  自体には影響しないという1.6節の切り分け（「diskA固有・ブート手順に
  固有の挙動」）と整合する追加の傍証になった

3節で要求された「最初の相違点が人間に分かる形で報告されるか」は
**できる**ことを確認した。

## 4. 結論

- (a) 決定論性: **同一条件2回で完全一致（揺れなし）。** ただし副産物として
  `cmp_io.py`が新形式(8列)ログを一度も正しく読めていなかったバグを発見・
  修正した（1節）
- (b) L1の型（`--init/--cycle`）: **(c) 使えない。** sub側の活動が
  frame 13〜77に限られ、その後は完全に沈黙する（「定常状態」が存在
  しない）ため、周期を仮定する型は成立しない
- (c) M6の適合条件: `docs/spec/l3-subrom.md` 5.3節を、
  `tools/cmp_io.py --cpu main --port FD --kind IN` による
  「mainのIN $FD列の完全一致（非周期）」に確定した（第2版で反映）
- (d) 自己検証: `tools/cmp_io_selftest.sh` にテスト19〜26を追加し、
  8列パース・clock列が比較に無関係であること・`--port/--kind`の
  一致/不一致検出・引数誤りの検出を、いずれも**わざと壊して**確認した
  （全26項目OK）
