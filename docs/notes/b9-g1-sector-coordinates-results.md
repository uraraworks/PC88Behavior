# B9: 自作サブが渡したデータはディスクのどこのものかを、座標だけで比べる — 結果

記録日: 2026-10-31
規則: [b9-g1-sector-coordinates-preregistration.md](b9-g1-sector-coordinates-preregistration.md)（be5750c）どおり。変更なし。
器具: `tools/b9_sector_coordinates.py`。実物の D88 の形（トラック表 160 件、複数の像の連結）を読めるまで 00f919b、3a75a42（自己検査の落ちる版、行き止まり）、ed56bd7 と直した。規則は変えていない。
測定はクラウドの実行環境で、B8 の生ログを再利用した。記録: `measurements/b9-g1-*.txt`。

## ディスクの形（件数のみ）

G1 の先頭の像は 411 セクタで、track 0 の 16 セクタだけが 256 バイト、他は 1024 バイト（5 セクタ/トラック）。

## 結果: `IN $FC` の 15 ブロックの座標

| ブロック | 公式（OO） | 公式main＋自作サブ（OS） | 自作main＋自作サブ（SS） |
|---|---|---|---|
| 0 | セクタ (0,0,2) | none | セクタ (0,0,2) |
| 1 | セクタ (0,0,3) | none | none |
| 2〜14 | セクタ (0,0,4)〜(0,0,16) | uniform | uniform |

公式は `(0,0,2)` から `(0,0,16)` までの 15 セクタを順に渡す（各一致 1 件）。
自作サブはブロック 2 以降をディスクの内容でなく、全部同じ値で渡す。

## 結果: `IN $FE`

OS・SS とも、違うのは **ビット 1 だけ**で 7724 件中 7681 件。他のビットの違いは 0。

## 分かったこと

- 公式の上の G1 は、`(0,0,1)` の次に track 0 の残りを順に受け取る
- 自作サブは、この受け渡しの 15 セクタ分を正しく渡していない。SS でも正しいのは最初の 1 セクタだけである
- 3840 バイトの件数と `OUT $FD` の 10 バイトは公式と同じなので、自作サブは要求を受けて 3840 バイトを返しているが、中身がディスクと合っていない

## 推定（確認していない）

- G1 は 1 回の要求で複数のセクタを読み、自作サブは 1 セクタ分しかディスクから読んでいない、と読むと SS の形に合う
- OS のブロック 0 が none である理由は、この形だけでは説明できない。main が公式だと、自作サブの状態か要求の前後が違う可能性がある
- `IN $FE` のビット 1 は、段取りに使うビットか、それ以外かをこの測定では決められない
- 位置 13510 で途切れる理由がデータの違いである、とはまだ確定していない。データを直して先へ進むかで確かめる

## 次段（別に事前登録する）

自作の媒体と刺激だけで、公式サブの複数セクタの読み出しの規則を測り、仕様書へ起こす。G1 は使わない。
実装は公式の観測を見ていない担当が仕様書から行い、そのあと G1 が位置 13510 を越えるかで確かめる。
