# M6h — FDC制御ポート ($FA/$FB, 補助として $F7/$F8/$FE/$FF) の意味論測定

`docs/spec/l3-subrom.md` 第2版 3節「未確定」のうち、`$FA`/`$FB` の
正確な意味論に絞って追加測定した記録。

## 対象ログ

新規測定は行わず、既存の M6c 測定ログ（共通クロック付き、決定論性は
`docs/notes/m6-conformance.md` で確認済み）をそのまま再利用した。

- `measurements/m6c-sub-d0-boot.iolog.txt`（起動のみ）
- `measurements/m6c-sub-d1-files.iolog.txt`（`FILES`打鍵）
- `measurements/m6c-sub-d2-save.iolog.txt`（`SAVE`）
- `measurements/m6c-sub-d5-seqfile.iolog.txt`（シーケンシャル読み書き）

いずれも diskA（N88-BASIC）条件。解析器は新規に
`tools/analyze_fdc_ports.py` を作成した（第三者が
`python3 tools/analyze_fdc_ports.py single --iolog <path> --label <label> --out <path>`
および `cross` サブコマンドで再実行できる）。出力は
`measurements/m6h-fdc-{d0-boot,d1-files,d2-save,d5-seqfile}.txt` と
`measurements/m6h-fdc-cross-condition.txt`。

## H1: `$FA` の値と「直後アクセスが `$FB` かどうか」の相関 — 確定

sub の `IN $FA` イベントについて、発生順で直後のイベントが `$FB`
（IN/OUT問わず）かどうかを調べ、`$FA` の値のビットごとに相関を取った。

**結果: `$FA` の bit7 が、4条件すべて・例外0件で「直後が `$FB`」を
完全に予測する。**

| 条件 | bit7=1 & 直後$FB | bit7=1 & 直後$FBでない | bit7=0 & 直後$FB | bit7=0 & 直後$FBでない |
|---|---|---|---|---|
| d0-boot | 13833 | 0 | 0 | 51 |
| d1-files | 15800 | 0 | 0 | 79 |
| d2-save | 17770 | 0 | 0 | 108 |
| d5-seqfile | 21142 | 0 | 0 | 156 |

合計 68,879 件の `IN $FA` のうち、bit7 と「直後が `$FB`」の対応が
崩れた事例は**1件も無い**。bit0〜bit2 は「直後$FBでない」群
（値0/1/2/4など）にだけ現れ、「直後$FB」群には現れない（bit3は
`m6-sub-proto.md` Q2既報のとおり全区間で常に0）。

**言えること（測定のみから）**: `$FA` の bit7 は「この直後に `$FB` への
アクセスが起きるかどうか」を100%の精度で分ける。これは定性的には
「準備完了ビットを見てからデータポートを叩く」という定型そのものであり、
一般的なFDCコントローラ設計（μPD765系の Main Status Register における
RQM = Request for Master ビットの働き）と形が一致する。**ただし
これは一般知識との形の一致であって、実機の `$FA` が μPD765 の
Main Status Register そのものだと確認したわけではない。** 本セッションで
μPD765の資料・PC-88固有の解析記事は一切参照していない（下記「資料」節）。

bit4〜bit6 は「直後$FB」群の中でも 0xF0(13568件)/0x90(110件)/0xD0(104件)/
0x80(35件) のようにばらつく。bit7以外の3ビットは「準備完了」の判定には
関与せず、別の状態（ドライブ選択・動作モードなど）を示している可能性が
あるが、**本測定だけでは特定できない（未確定として残す）**。

## `$FA` は読み取り専用（構造的傍証）

`docs/notes/m6-sub-proto.md` 1.4節（既報）どおり、sub が `OUT $FA` を
行った事例は全条件で0件。sub IN専用というポートの使い方は、
H1のbit7所見（ステータス的振る舞い）と整合する。

## H2: `$FB` バースト構造 — 全バースト長1（新知見）

「直前に `IN $FA` を挟まず連続する `OUT $FB`」をバーストと定義して
区切ったところ、**4条件すべてで、全バーストの長さが1だった**
（d0-boot: 161バースト・161件で1:1、他条件も同様）。

**言えること**: `sub OUT $FB` は複数バイトをまとめて書く場面が無く、
**1バイト書くたびに必ずその直前で `IN $FA` を挟んでいる**（=毎バイト
ごとに準備完了を確認してから書く、という厳格な単位）。これはH1の
bit7所見と合わせて「ポーリング→1バイト転送」という単位の粒度を
裏付ける。「コマンド＋複数引数バイトをまとめて書く」型の証拠は
本測定では見つからなかった（見つからなかったこと自体を確定として書く。
複数バイトのコマンドが存在しないと断定はできない——同じ`$FA`ポーリング
1回に対しOUTが1件しか対応しない、という観測事実のみ）。

## H3: `OUT $FB` の先頭バイト分布は操作の種類で変わる — 確定

| 条件 | 上位値（件数・割合） |
|---|---|
| d0-boot | 0x00(23.0%) 0x01(18.0%) 0x08(9.9%) 0x04(9.3%) 0x0F(6.8%) |
| d1-files | 0x00(19.2%) 0x01(16.5%) 0x04(10.9%) 0x08(8.6%) 0x0F(7.1%) |
| d2-save | 0x00(17.7%) 0x01(15.8%) 0x04(11.8%) 0x08(8.0%) 0x12(8.0%) |
| d5-seqfile | 0xFF(16.1%) 0x00(14.9%) 0x01(3.7%) 0xC2(3.2%) 0xC1(3.1%) |

d0-boot/d1-files/d2-save は似た分布（0x00/0x01/0x04/0x08/0x0F付近が
上位）だが、d5-seqfile（シーケンシャル読み書き）だけ分布が明確に
異なり、`0xFF`・`0xC1`・`0xC2` のような高位ビット付きの値が目立つ。

**言えること**: `$FB` に書かれる値は固定シーケンスではなく、操作の
種類に応じて分布が変わる。これは「`$FB` がコマンド/パラメータの
データレジスタである」という H1/H2 の見立てと整合する（固定した
制御コードの反復であれば操作間で分布はもっと似るはず）。
**個々の値が具体的に何のコマンドを意味するかは、本測定（値の分布のみ）
からは特定できない。** 0xC1/0xC2 のような「上位ビットが立った値」は
一般的なFDCコマンド体系（マルチトラック/MFM系フラグをコマンド番号に
OR する構成）の形と類似するが、これも**形が似ているという以上の
主張はしない**。

## H4: `$F7`/`$F8` の役割 — 従来所見の追認（新知見は限定的）

`$F7` の `OUT` は全条件でユニーク値1種（`0x08`）のみ、`$F8` の `OUT` は
92〜97%が `0x07`（既報 `m6-sub-proto.md` 1.5節の追認）。件数も
10〜39回と、`$FA`/`$FB`（数千〜数万回）と比べて桁違いに少ない。

`$FB`バースト（H2、長さ1）の前後2件以内に`$F7`/`$F8`の`OUT`が来る
割合は9割超だったが、**この指標はバースト長が常に1であるため
弱い**（近傍2件以内という粗い窓では、length-1の単発イベントに対して
ほぼ自動的に「近い」と判定されてしまう）。したがって
「`$F7`/`$F8`が`$FB`バーストの開始・終了を積極的にマークしている」
という主張はできない。**制御/ストローブ的ポートである、という
既報の緩い分類（頻度が桁違いに少ない）以上のことは今回も言えない。**

## IN $FB → OUT $FC の直接転送は確認できず（追加確認・棄却）

「`$FB`で読んだFDCデータを、そのまま`$FC`経由でmainへ中継している
のでは」という仮説を、d0-boot条件で軽く確認した。`IN $FB` の直後
5件以内に同じ値の `OUT $FC` が現れる事例は **0/0件**（該当する
`OUT $FC` 自体が5件以内に見つからなかった）。**この経路仮説は
本測定の範囲では支持されない、あるいは少なくとも即時（5イベント
以内）の単純転送ではない。** バッファリングされている、frame単位で
遅延している、あるいは全く別の経路である可能性が残るが、
**本ノートのスコープでは追跡しない**（未確定のまま次の宿題に残す）。

## 資料について

本ノートの作成にあたり、外部資料（書籍・Web・PDF）は**一切新規に
参照していない**。上記「一般的なFDCコントローラ設計」「μPD765系の
RQMビット」への言及は、既存ノート（`m6-sub-proto.md` の
「8251的USART」「8255(PPI)」という記述と同様の）一般的な業界知識の
参照であり、PC-88固有の解析記事・ROM解析物には触れていない。
測定結果を先に確定させ、その形が一般知識と独立に一致するかを
確認する、という `CLAUDE.md`「資料の使い方」の手順に沿っている。

## まとめ（確定/未確定の切り分け）

確定（測定の根拠つき）:

- `$FA` bit7 は「直後に `$FB` アクセスが来るか」を100%予測する
  （4条件・68,879件・例外0）
- `$FA` は sub から読み取り専用（`OUT $FA` は0件、既報の追認）
- `sub OUT $FB` は常に単発（バースト長1）で、直前に必ず `$FA` の
  ポーリングを伴う
- `OUT $FB` の先頭バイト分布は操作の種類（起動系 vs シーケンシャル
  読み書き）で明確に異なる
- `$F7` OUT は常に`0x08`、`$F8` OUTはほぼ`0x07`、頻度は`$FA`/`$FB`より
  桁違いに少ない（既報の再確認）

未確定（推測で埋めない）:

- `$FA` bit4〜bit6 が何を表すか
- `OUT $FB` の各値が具体的に何のコマンド/パラメータに対応するか
- `$FB` で読んだデータが `$FC` へどう中継されるか（即時転送は
  棄却したが、代替の経路は特定できていない）
- `$FA`/`$FB` が実機のFDCチップの物理レジスタそのものかどうか
  （QUASI88のエミュレーション実装がこの形を作っている可能性を
  排除できていない。`m6-sub-proto.md` 3節と同じ留保）
