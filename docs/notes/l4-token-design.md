# L4 設計判断 — 中間コード（トークン）はゴール A では自前の体系を使う

記録日: 2026-08-10
状態: M7（L4）は未着手。実装より先に、この設計判断を日付付きで固定しておく。

## 判断

ゴール A（BASIC が動く箱）の実装では、**公式 N88-BASIC の中間コード（トークン番号）
セットを使わない**。キーワード↔番号の対応はこちらの都合で自前に設計する。

## 導出

これは新しい方針ではなく、`docs/PLAN.md` 第1節のゴール A の定義
「**内部のアドレス配置は自由**。入口番地も、ワークエリアの位置も、こちらの都合で
決めてよい」の系である。中間コードは RAM 上の内部表現であり、
「外から見た振る舞いが一致すればよく、内部表現は自由」の原則がそのまま適用される。

## 境界 — 中間コードが「外部」に出る唯一の場所

中間コードは純粋な内部表現ではない。**バイナリ形式で SAVE するとディスクに書き出され、
外部観測可能になる**。したがって境界は次のとおり。

| 機能 | 公式トークン表 | 帰属 |
|---|---|---|
| プログラムの入力・実行・PRINT 出力 | 不要 | ゴール A |
| アスキー形式の SAVE/LOAD（テキスト） | 不要 | ゴール A |
| バイナリ SAVE ファイルの公式 ROM との相互読み書き | 必要 | **ゴール B** |

公式ディスクとのプログラム交換は、アスキー形式（テキスト）を経由すれば
自前トークン体系のままで成立する。

## 将来バイナリ互換が必要になった場合の出所

ゴール B でバイナリ SAVE 互換に取り組む場合、対応表の出所は**測定**とする。
SAVE 命令の出力はディスクに書かれる外部観測可能なファイル形式であり、
規律上は L2 のコード割り当て（マニュアル記載の割り当てのみ採取）と同じ扱いになる。
着手時には、その時点の法的整理（創作性・規約該当性の評価）を含めて
判断を別途文書化してから進む。

## 経緯

2026-08-09〜10 に、権利者側から X 上で公開の照会があり、その中で
「中間コードのセット」の扱いが論点として提起された。本判断は照会への譲歩ではなく、
上記のとおりゴール A の定義から導かれる系だが、論点化された時点で
実装開始（M7）より先に日付付きで固定しておくことに記録上の価値があるため、
このメモを起こした。なお同スレッドでは第三者からも
「アスキーセーブを経由して独自の中間コードに変換する設計」が独立に提案されており、
この設計が自然な帰結であることの傍証になっている。

## 追記（2026-09-15）

M7 着手にあたり見直したが、上記の判断はそのまま維持する
（詳細は [l4-design.md](l4-design.md)）。

- M7 では、数値の内部表現に **GW-BASIC（MIT 公開ソース）の浮動小数点演算部分
  だけを移植する**方針にした。このため、トークン番号についても改めて
  GW-BASIC の体系を採らないことを明示しておく。GW-BASIC のトークン番号の
  並びは N88 と多数（第三者の実測で184個中128個）が共通しており、数値部を
  移植したからといってトークン番号まで引きずられないよう、番号体系は
  数値表現とは独立に自前で設計する。
- 数値の内部表現（浮動小数点形式）自体は、将来バイナリ SAVE などで外部に
  出る場面（本文の「境界」節、および将来のゴール B）があるが、ゴール A では
  画面出力（PRINT の表示結果）が一致することだけを目的として採る。内部の
  ビット配置がバイナリ互換になるかどうかはこの段階の関心事ではない。

## 追記（2026-09-15、番号の振り方 — 開発者判断）

M7 の段階3（BASIC の核）に入る前に、自前の体系の具体的な作り方を決めた。

### 決定

- **番号は規則から生成する。** リファレンスマニュアルの索引にある命令・関数の語を、大文字の ASCII の辞書順に並べ、0x80 から順に番号を振る
- **対象の語はマニュアルの全語とする。** ゴールA で実装する命令に限らず、N88 固有の拡張命令を含めて索引の全語に最初から番号を振る。後で命令を実装しても表は変わらない
- 語の一覧の出所: `tools/basic_surface.tsv`（M3 で作成。出典は PC-8801FA/MA リファレンスマニュアルの索引で、第2章基本命令・第3章拡張命令の項目を機械的に書き出した表。この tsv を `tools/gen_suite.py` が読んで測定条件を生成しており、マニュアル本文そのものは転記していない）
- 語の数: tsv 本体（コメント行を除く）186 行。内訳は拡張命令(ext) 16、数値関数(numfunc) 13、文字列関数(strfunc) 17、残り(基本命令＋その他分類) 140。tsv 冒頭のコメントは出典の章立てとして「基本命令166項目・拡張命令16項目」（計182）と書いているが、実データ行数186とは一致しない（差4、未解消。番号生成スクリプトを作る段で該当箇所を突き合わせて確定する）
- 0x80〜0xFE の127個を、辞書順の最初の127語に割り当てる（186語のうち先頭127語が入る）。0xFF は拡張の前置きとして取っておき、128語目以降は「0xFF の後ろに 0x80 から順の2バイト目」で表す（残り59語が拡張に回る計算になるが、上記の語数の差4が未解消のため確定値ではない）
- `'`（REM の省略形）や `?`（PRINT の省略形）のような記号は、字句の段階で対応する語に置き換え、番号の規則の外で扱う
- 番号表は `src/l4_basic/` の生成スクリプトが語の一覧から作る。ROM の中の表も、ソースの中の定数も、このスクリプトの出力から作り、手で並べない。生成スクリプトの再実行で同じ表になること、一覧の語がすべて表にあること、番号に重複が無いことを自己検査で確かめる

### 理由

- 番号が規則から決まるので、どこかの番号表を写したのではないことを、規則そのものが説明する。第三者が語の一覧と規則から同じ表を再生成できる
- 公式 N88-BASIC や GW-BASIC の番号の並びは見ておらず、今後も見ない。自前の表がそれらと一致しないかどうかも確かめない。主張するのは「規則で作った」ことだけであり、「一致しない」ことではない
