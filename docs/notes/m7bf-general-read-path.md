# m7bf: 一般読み出し経路を実装した（まだ発火しない。手前で分岐している）

作業日: 2026-08-19

## 情報境界

公式ROM一式・公式diskA（使い捨て複製）を**実行して**測定した。読んでいない。
本ノートに書くのは件数・位置・**プロトコルの種別フィールドの値**だけで、
ディスクの内容は扱わない。種別値は`$FF`のフェーズコードや`0x91`と同類の
プロトコル定数である。

## 1. 応答の形を測ってから実装した

m7beで「起動後の要求も6バイトレコードで、2バイト目が種別」と分かったので、
**応答の形を先に測った**（推測で実装しないため）。

起動後のREAD 11件について、要求から次の要求までを数えると:

- 受信 8バイト → **sub OUT `$FD` 258バイト**（`$FC` 側は0）
- 受信 6バイト → sub OUT `$FD` 1バイト

つまり **6バイトレコード → 1バイト応答 → 2バイト要求 → 256バイト応答**
という、起動時の交換#3/#4と同じ形である。256バイトは`$FD`側
（main `IN $FC`）へ流れる——これは自作の既存の応答経路と同じポートである。

1バイト応答の値は11件すべて同一で、**既存の `EXCHANGE3_OBSERVED_RESPONSE`
と同じ値**だった（新しい値を持ち込まない）。

種別フィールドの値も確定した: **READ = 0x02、WRITE = 0x11**
（起動時の6バイトグループは 0x01 で衝突しない）。

## 2. 実装

`_observed_single_by_request` の入口で「run長6 かつ 2バイト目が READ 種別」
なら `_general_read_request` へ分岐する経路を足した。ハンドラは
レコードの `[論理トラック, R]` から `C = track>>1`・`H = track&1`・
`unit/head = drive0 | (H<<2)` を作り、既存の `FDC_SEEK` →
`FDC_SENSE_DRIVE_STATUS` → `FDC_READ_SECTOR` を呼んで `SECTOR_READY` を立て、
1バイト応答を返す（続く2バイト要求で256バイトを送る既存経路につながる）。
公式もREADの直前に SEEK→SENSE_INT→SENSE_DRV を出している（m7be）。

コードは 1939 → 2009 バイト（窓2048に対して残り39）。

## 3. **まだ発火しない**（正直に書く）

実装しても混成の挙動は変わらなかった（READ 8回のまま、`Bad allocation table`
のまま）。診断ポート`$F9`で「run長6のとき自作が見ている種別バイト」を出したら、
**13件すべて 0x01**——つまり届いているのは起動時グループだけで、
**READ種別(0x02)のレコードは一度も来ていない**。

要求列（main→sub）を公式と突き合わせると、**73バイト目で分岐**していた
（公式2234バイトに対し自作は138バイトで止まる）。応答列（sub→main）は
**6416件目が最初の食い違い**である。6415は「バルク＋プリアンブル」の直後、
つまり**バルク後の最初の応答が既に違う**。

したがって順序はこうなる: バルク直後の応答が違う → mainが別経路へ入る →
READ種別の要求がそもそも発行されない → 一般読み出し経路は出番が来ない。
**実装は測定に基づいて正しいが、出番の手前で止まっている。**

## 4. 次の一手

**バルク直後の最初の応答（応答列6416件目）が公式と何が違うか**を特定する。
そこが直れば、その先の要求（READ種別）が流れ始めるはずで、一般読み出し経路の
出番になる。

回帰なし: 適合条件1（5635件・SHA-256）維持、`verify_l3.sh` 全項目OK、
`conform_l3.sh` rc=0。

## 5. この節の教訓

**「実装したのに変わらない」ときは、実装が呼ばれているかを先に見る。**
今回は診断ポートに種別バイトを出すだけで「そもそも来ていない」と分かり、
実装の中身を疑う無駄をせずに済んだ。前サイクル（m7bd）でも同じ形で
助かっている——**推理を2手以上重ねる前に、1バイト出して確かめる。**
